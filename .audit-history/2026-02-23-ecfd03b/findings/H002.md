# Finding: H002 - Fee Destination Hijack via update_config

## Status: CONFIRMED
## Confidence Score: 9/10

> Confidence scale:
> - **9-10**: Certain — exhaustive code analysis, all paths verified
> - **7-8**: High — strong evidence, minor gaps in coverage
> - **5-6**: Moderate — reasonable analysis, some assumptions unverified
> - **3-4**: Low — significant uncertainty, limited code visibility

## Executive Summary

The `update_config` instruction allows the current authority to instantly redirect 100% of the protocol's fee revenue (treasury: 7%, ops: 3% of every settled pot) to arbitrary attacker-controlled wallet addresses, with no timelock, no pending/accept pattern, no event emission, and no re-validation of the address invariants enforced at initialization. The change takes effect immediately and silently — players cannot detect it on-chain without monitoring `GlobalConfig` account changes between transactions.

The precondition for this attack is that the attacker must first control the authority keypair (the server hot wallet). If the authority is compromised — through key theft, insider threat, or supply chain attack — redirecting all future fee revenue requires a single transaction with no observable warning to players. Because the winner still receives their 90% share (winner is constrained to be a registered player), players may not notice until they examine fee accounting. The attack is low-noise and can run indefinitely until the team discovers the config change.

## Hypothesis Investigated

**H002: Fee Destination Hijack via update_config**

A compromised or malicious authority can redirect all settlement fees to attacker-controlled addresses by calling `update_config` to change treasury and ops addresses. No timelock or validation prevents this.

**Attack Vector:**
1. Attacker gains authority access (or authority acts maliciously)
2. Calls `update_config` with `new_treasury = Some(attacker_wallet1)`, `new_ops = Some(attacker_wallet2)`
3. All subsequent `settle_match` calls send 10% of pot to attacker wallets
4. Players receive correct 90% — attack may go unnoticed

## Investigation Path

### Step 1: Verify update_config handler — any validation on new addresses?

**Location:** `lib.rs:70-89`

**Finding:** The handler contains zero validation on the new address values. The only protection is the `has_one = authority` in the account struct (line 470), which correctly ensures only the current authority can call the instruction. But once past that gate, any `Pubkey` is accepted for treasury and ops — including the authority's own address, a PDA address, the zero address, or an attacker-controlled wallet.

**Evidence:**
```rust
// lib.rs:70-89
pub fn update_config(
    ctx: Context<UpdateConfig>,
    new_authority: Option<Pubkey>,
    new_treasury: Option<Pubkey>,
    new_ops: Option<Pubkey>,
) -> Result<()> {
    let config = &mut ctx.accounts.config;

    if let Some(a) = new_authority {
        config.authority = a;
    }
    if let Some(t) = new_treasury {
        config.treasury = t;     // No validation on t
    }
    if let Some(o) = new_ops {
        config.ops = o;           // No validation on o
    }

    Ok(())
}
```

No `require!` checks. No emit!(). No timelock state. Three field updates and an `Ok(())`.

### Step 2: Verify initialize_config distinctness checks — are they re-enforced in update_config?

**Location:** `lib.rs:47-65` (initialize_config handler)

**Finding:** `initialize_config` enforces three distinctness checks (lines 53-55). `update_config` re-enforces NONE of them.

**Evidence:**
```rust
// lib.rs:53-55 — initialize_config
require!(authority != treasury, EscrowError::InvalidConfig);
require!(authority != ops, EscrowError::InvalidConfig);
require!(treasury != ops, EscrowError::DuplicateFeeAccount);
```

These three `require!` statements are absent from `update_config`. The invariant `authority != treasury != ops` holds only at initialization time. After a single `update_config` call, any combination is possible.

### Step 3: Verify settle_match reads treasury/ops from config at execution time

**Location:** `lib.rs:560-610` (SettleMatch account struct), `lib.rs:287-291` (lamport transfers)

**Finding:** This is the critical link in the exploit chain. The `settle_match` instruction reads `config.treasury` and `config.ops` freshly at execution time, not from any cached value. The constraints on lines 587 and 596 bind the instruction-level `treasury` and `ops` accounts to whatever `config.treasury` and `config.ops` currently contain.

**Evidence:**
```rust
// lib.rs:585-597 — SettleMatch account struct constraints
/// Treasury: validated against config PDA (OC-03)
/// CHECK: Constrained to config.treasury; uniqueness check vs ops
#[account(
    mut,
    constraint = treasury.key() == config.treasury @ EscrowError::InvalidTreasury,
    constraint = treasury.key() != ops.key() @ EscrowError::DuplicateFeeAccount,
)]
pub treasury: UncheckedAccount<'info>,

/// Ops: validated against config PDA (OC-03)
/// CHECK: Constrained to config.ops
#[account(
    mut,
    constraint = ops.key() == config.ops @ EscrowError::InvalidOps,
)]
pub ops: UncheckedAccount<'info>,
```

And the actual transfers:
```rust
// lib.rs:287-291
**ctx.accounts.escrow.to_account_info().try_borrow_mut_lamports()? -= treasury_amount;
**ctx.accounts.treasury.to_account_info().try_borrow_mut_lamports()? += treasury_amount;

**ctx.accounts.escrow.to_account_info().try_borrow_mut_lamports()? -= ops_amount;
**ctx.accounts.ops.to_account_info().try_borrow_mut_lamports()? += ops_amount;
```

The design of `settle_match` trusts `config.treasury` and `config.ops` as the authoritative fee destinations. This is a correct design decision in isolation — it means the settlement is always consistent with the current config — but it means that whoever controls `update_config` controls all future fee routing.

### Step 4: Verify there is no timelock, pending state, or multi-sig on update_config

**Location:** `lib.rs:464-475` (UpdateConfig account struct), `lib.rs:70-89` (handler)

**Finding:** The `UpdateConfig` account struct requires only two accounts: the `config` PDA (with `has_one = authority`) and the `authority: Signer<'info>`. There is no `pending_authority` field in `GlobalConfig`. There is no timelock mechanism. There is no event emission. There is no secondary signer requirement. A single transaction from the authority keypair changes the fee destinations immediately and permanently until another `update_config` is issued.

**Evidence:**
```rust
// lib.rs:464-475
#[derive(Accounts)]
pub struct UpdateConfig<'info> {
    #[account(
        mut,
        seeds = [GlobalConfig::SEED],
        bump = config.bump,
        has_one = authority @ EscrowError::Unauthorized,
    )]
    pub config: Account<'info, GlobalConfig>,

    pub authority: Signer<'info>,
}
```

```rust
// lib.rs:690-708 — GlobalConfig struct has no pending fields
#[account]
pub struct GlobalConfig {
    pub authority: Pubkey,
    pub treasury: Pubkey,
    pub ops: Pubkey,
    pub is_paused: bool,
    pub bump: u8,
}
```

No `pending_treasury`, `pending_ops`, `change_after_timestamp`, or similar field exists in `GlobalConfig`.

### Step 5: Verify no on-chain event reveals the fee destination change

**Location:** Searched all `emit!()` calls: `lib.rs:144`, `lib.rs:199`, `lib.rs:216`, `lib.rs:294-303`, `lib.rs:369-373`, `lib.rs:431-435`

**Finding:** No event is emitted by `update_config`. The six `emit!()` calls in the program cover: MatchCreated, WagerDeposited, MatchActive, MatchSettled, MatchCancelled (two call sites). Zero events for config changes.

Note: `MatchSettled` (lines 294-303) does include `treasury_account` and `ops_account` pubkeys — this is OC-11, an on-chain monitoring feature. However, this event fires AFTER the misdirected payment has already been made. It reveals the destination but does not prevent the theft.

**Evidence (the OC-11 event):**
```rust
// lib.rs:294-303
emit!(MatchSettled {
    match_id,
    winner,
    winner_amount,
    treasury_account: treasury_key,
    treasury_amount,
    ops_account: ops_key,
    ops_amount,
});
```

OC-11 is reactive, not preventive. An off-chain monitoring system watching for `MatchSettled` events with unexpected `treasury_account` values could detect the theft after the first settlement but cannot block in-progress settlements.

## Invariant Analysis

### Target Invariant

The target invariant is: "Fee revenue flows only to the protocol-controlled treasury and ops addresses that were established through authorized governance processes and are known to all stakeholders."

More formally: `config.treasury` and `config.ops` must only be modifiable through a process that provides notice to stakeholders and cannot be executed unilaterally in a single transaction by a single key.

### Enforcement Points

| Location | What It Enforces | Complete? |
|----------|-----------------|-----------|
| `lib.rs:53-55` | `authority != treasury`, `authority != ops`, `treasury != ops` at init time | PARTIAL — init only |
| `lib.rs:470` `has_one = authority` | Only current authority can call update_config | YES — signer gate |
| `lib.rs:587` `treasury.key() == config.treasury` | settle_match uses whatever is in config | YES — but trusts config |
| `lib.rs:596` `ops.key() == config.ops` | Same as above | YES — but trusts config |
| Timelock | Change cannot take effect immediately | NOT PRESENT |
| Pending/accept pattern | New address must be accepted by recipient | NOT PRESENT |
| Event emission | Change is logged on-chain | NOT PRESENT |
| Distinctness re-check in update_config | Config remains coherent after updates | NOT PRESENT |

### Enforcement Gap Assessment

The invariant that matters for this attack — "treasury/ops cannot be instantly redirected to arbitrary addresses" — is NOT enforced. The `has_one = authority` gate is the sole enforcement point, and it is bypassed the moment the authority keypair is compromised or acts maliciously. There is no second factor, no timelock, no re-validation of addresses, and no on-chain audit trail of the change itself (only of post-change settlements via OC-11).

## Blocking Factors

- **`has_one = authority` on UpdateConfig (lib.rs:470):** The only blocking factor. An attacker without the authority keypair cannot call `update_config`. This is a necessary but insufficient protection.
- **`treasury.key() != ops.key()` in SettleMatch (lib.rs:588):** Prevents the trivial case of setting both to the same attacker address. The attacker must use two distinct controlled addresses. This is a minor obstacle — any attacker with the authority key controls multiple wallets.
- **OC-11 MatchSettled event (lib.rs:294-303):** Reveals the fee destination addresses after each settlement. Reactive monitoring could detect an anomaly after the first misdirected payment, but by then funds have already moved.

---

## Enabling Factors

- **No timelock on update_config (lib.rs:70-89):** Changes apply in the same block as the transaction.
- **No event for config changes:** The redirect is silent on-chain until the next settlement's `MatchSettled` event reveals the new addresses.
- **singleton GlobalConfig:** One update redirects all future settlements for the entire protocol.
- **Authority is a single hot wallet:** No multisig requirement means one compromised key enables the attack.
- **settle_match reads config at execution time:** There is no snapshot of fee destinations at match creation; whatever is in config when `settle_match` runs is used.
- **Distinctness invariant not re-enforced (lib.rs:70-88):** update_config adds no additional invariants, making it trivial to set treasury = authority's own address without constraint.

## Exploitation Scenario

### Prerequisites

1. Attacker must control or compromise the authority keypair (`config.authority` — the server hot wallet at `HPyVPj2VH9yBirr7FMgAJeDH8xJgaMKy5UnwLkjSnovk` per MEMORY.md).
2. Attacker needs two controlled wallet addresses to receive redirected fees (to satisfy the `treasury.key() != ops.key()` constraint in SettleMatch).

### Attack Steps

1. Attacker prepares two clean wallets: `attacker_treasury` and `attacker_ops`.
2. Attacker signs and submits a single transaction calling `update_config`:
   - `new_authority = None` (keep authority unchanged to avoid detection)
   - `new_treasury = Some(attacker_treasury)`
   - `new_ops = Some(attacker_ops)`
3. Transaction succeeds. `GlobalConfig.treasury` and `GlobalConfig.ops` are now attacker addresses. No event is emitted.
4. All subsequent `settle_match` calls execute normally from every player's perspective. Winners receive their 90%. The 10% fee split goes to `attacker_treasury` (7%) and `attacker_ops` (3%).
5. Fee revenue accumulates in attacker wallets until the team detects the anomaly via `MatchSettled` event monitoring or financial reconciliation.
6. **Optional stealth enhancement:** After extracting sufficient fee revenue, the attacker can restore the legitimate treasury/ops addresses via a second `update_config` call to erase evidence at the config level. The `MatchSettled` event logs would still record the period of theft, but casual observers checking the current config would see legitimate addresses.

### Impact

**Per-match impact:**
- At median wager (1 SOL each → 2 SOL pot): attacker receives 0.14 SOL per match
- At max wager (100 SOL each → 200 SOL pot): attacker receives 20 SOL per match
- At typical play volume (100 matches/day): continuous extraction of 14 SOL/day at median wager

**Protocol impact:** Total fee loss scales with match volume and wager size. The attack extracts ALL protocol revenue (treasury + ops = 10%) for every match settled while the redirect is active. Players are financially unaffected (90% still goes to winner), making the attack difficult to detect from player-facing signals.

**Governance impact:** If the attacker also rotates `new_authority` (line 78-80), they permanently lock the original team out of all protocol governance, compounding the fee theft with a total takeover.

### Recommended Fix

**Primary fix: Implement a timelock on fee destination changes.**

A timelock ensures that any change to treasury or ops is announced on-chain and does not take effect until a delay period has passed, giving the team and monitoring systems time to detect and respond.

```rust
// Recommended additions to GlobalConfig struct:
#[account]
pub struct GlobalConfig {
    pub authority: Pubkey,
    pub treasury: Pubkey,
    pub ops: Pubkey,
    pub is_paused: bool,
    pub bump: u8,
    // NEW: timelock fields
    pub pending_treasury: Option<Pubkey>,
    pub pending_ops: Option<Pubkey>,
    pub pending_treasury_effective_at: i64,  // Unix timestamp
    pub pending_ops_effective_at: i64,
}

// NEW: propose_treasury_update instruction
pub fn propose_treasury_update(ctx: Context<ProposeConfigUpdate>, new_treasury: Pubkey) -> Result<()> {
    let config = &mut ctx.accounts.config;
    let effective_at = Clock::get()?.unix_timestamp
        .checked_add(TIMELOCK_SECONDS)
        .ok_or(EscrowError::ArithmeticOverflow)?;
    config.pending_treasury = Some(new_treasury);
    config.pending_treasury_effective_at = effective_at;
    emit!(TreasuryUpdateProposed { new_treasury, effective_at });
    Ok(())
}

// NEW: apply_treasury_update instruction
pub fn apply_treasury_update(ctx: Context<ApplyConfigUpdate>) -> Result<()> {
    let config = &mut ctx.accounts.config;
    require!(
        Clock::get()?.unix_timestamp >= config.pending_treasury_effective_at,
        EscrowError::TimelockNotExpired
    );
    if let Some(new_treasury) = config.pending_treasury {
        config.treasury = new_treasury;
        config.pending_treasury = None;
        emit!(TreasuryUpdateApplied { new_treasury });
    }
    Ok(())
}
```

**Secondary fix: Add re-validation of distinctness invariant in update_config.**

At minimum, re-check that the post-update config maintains `authority != treasury != ops`. This prevents the degenerate case where the authority accidentally or intentionally sets overlapping addresses:

```rust
// After (fixed update_config with re-validation):
pub fn update_config(...) -> Result<()> {
    let config = &mut ctx.accounts.config;
    if let Some(t) = new_treasury {
        config.treasury = t;
    }
    if let Some(o) = new_ops {
        config.ops = o;
    }
    if let Some(a) = new_authority {
        config.authority = a;
    }
    // Re-validate distinctness after any update
    require!(config.authority != config.treasury, EscrowError::InvalidConfig);
    require!(config.authority != config.ops, EscrowError::InvalidConfig);
    require!(config.treasury != config.ops, EscrowError::DuplicateFeeAccount);
    Ok(())
}
```

**Tertiary fix: Emit an event for all config changes.**

All changes to `GlobalConfig` should emit an on-chain event with the old and new values, enabling off-chain monitoring to detect any unauthorized changes immediately:

```rust
emit!(ConfigUpdated {
    old_treasury: old_treasury,
    new_treasury: config.treasury,
    old_ops: old_ops,
    new_ops: config.ops,
    updated_by: ctx.accounts.authority.key(),
    timestamp: Clock::get()?.unix_timestamp,
});
```

**Quaternary fix: Consider multisig for update_config.**

For mainnet, `update_config` should require a multisig (e.g., 2-of-3) rather than a single hot wallet. This is consistent with the OC-13 note in the code (`// NOTE: OC-13 — transfer upgrade authority to multisig before mainnet deploy`) and would apply the same principle to runtime governance operations.

## Incidental Discoveries

The following issues were observed while investigating this hypothesis. They are suggested as new hypothesis candidates for the orchestrator:

- **No event emission for update_config:** Config changes are entirely silent on-chain. An off-chain monitoring system watching the `GlobalConfig` account for changes would need to poll the account, not subscribe to events. Given that OC-11 was added specifically to address monitoring concerns (comments on line 583 reference OC-11 and multiple hypothesis numbers), the absence of a `ConfigUpdated` event is a gap in the monitoring design. Suggested hypothesis: "Can a compromised authority mask a governance attack by operating between monitoring intervals?" (relates to timing of detection)

- **Authority rotation during active matches creates unsettleable escrows:** As noted in `ARCHITECTURE.md` Area 2, if `update_config` is used to rotate the authority key while matches are Active, those matches become permanently unsettleable because `settle_match` requires `has_one = authority` on BOTH `escrow` (which stores the creation-time authority, line 565) AND `config` (which stores the current authority, line 604). If the attacker rotates the authority away in the same transaction as the fee redirect, this immediately bricks settlement for all in-flight Active matches, forcing 24h/48h timeout refunds. This compounds the H002 fee theft with a denial-of-service on settlement. Suggested hypothesis: "Combined update_config attack: rotate authority + redirect fees in one transaction to simultaneously brick active matches and redirect future fee revenue."

## Raw Investigation Notes

### Code Path for a Complete Attack Transaction

```
1. attacker_keypair signs update_config:
   - UpdateConfig accounts: { config (PDA, mut), authority (attacker_keypair, signer) }
   - Anchor validates: config.bump matches, config.authority == attacker_keypair.pubkey()
   - Handler runs: config.treasury = attacker_wallet_A, config.ops = attacker_wallet_B
   - No emit!(), no require!() beyond has_one, Ok(())

2. Next settle_match call:
   - SettleMatch accounts: { escrow, authority, winner, treasury=attacker_wallet_A, ops=attacker_wallet_B, config }
   - Anchor validates: treasury.key() == config.treasury → passes (attacker_wallet_A == attacker_wallet_A)
   - Anchor validates: ops.key() == config.ops → passes (attacker_wallet_B == attacker_wallet_B)
   - Anchor validates: treasury.key() != ops.key() → passes (two distinct attacker wallets)
   - Handler runs: wager math, lamport transfers to attacker_wallet_A and attacker_wallet_B
   - emit!(MatchSettled { treasury_account: attacker_wallet_A, ops_account: attacker_wallet_B, ... })
```

### Why This Is CONFIRMED, Not POTENTIAL

The attack path requires zero steps that "might work" or "depend on conditions." Every step is guaranteed by the code:
1. `update_config` accepts any Pubkey for treasury/ops — no validation possible to block this
2. `settle_match` uses whatever is in config — by design, and confirmed in code
3. No timelock, event, or second-factor check exists — confirmed by reading the entire handler and struct

The only non-deterministic element is "attacker gains authority access." This is the precondition, which is why severity is HIGH rather than CRITICAL. But once that precondition is met, the exploit is deterministic and complete. This is textbook CONFIRMED.

### EP-119 Relevance Assessment

EP-119 (Fee Destination Hijacking) is directly applicable. The `exploit-patterns-index.md` grep pattern `UncheckedAccount for fee/revenue destination` partially applies here (treasury/ops are `UncheckedAccount` in `SettleMatch`) but the root cause is in `update_config`, not in the account type of the settlement recipients. The `treasury` and `ops` accounts in `SettleMatch` are correctly constrained against `config.treasury` and `config.ops` — the vulnerability is that those config values can be freely changed by the authority without any protective mechanism.

EP-098 (CPI Destination Injection) is a secondary reference: the fee destination manipulation here is via `update_config` rather than a CPI argument injection, but the outcome (fees flow to attacker) is identical.

### Comparison: initialize_config vs update_config Protection Levels

| Check | initialize_config | update_config |
|-------|-------------------|---------------|
| authority != treasury | YES (line 53) | NO |
| authority != ops | YES (line 54) | NO |
| treasury != ops | YES (line 55) | NO |
| Event emission | NO (missing for init too) | NO |

The protection level dropped from "3 distinctness checks" at init to "0 checks" for all subsequent updates. This asymmetry is the fundamental gap.
