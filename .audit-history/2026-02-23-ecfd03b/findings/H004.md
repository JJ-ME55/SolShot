# Finding: H004 - Same-Transaction PDA Close-and-Revive

## Status: NOT VULNERABLE
## Confidence Score: 9/10

> Confidence scale:
> - **9-10**: Certain — exhaustive code analysis, all paths verified
> - **7-8**: High — strong evidence, minor gaps in coverage
> - **5-6**: Moderate — reasonable analysis, some assumptions unverified
> - **3-4**: Low — significant uncertainty, limited code visibility
> - **1-2**: Minimal — couldn't adequately assess, treat as NEEDS MANUAL REVIEW

## Executive Summary

The H004 hypothesis posits that an attacker could include `settle_match` (or `cancel_match`) and `create_match` for the same `match_id` in a single transaction, causing the PDA to be closed by the first instruction and then re-created by the second. The theory is that this re-creation could extract rent multiple times or reset match state in a harmful way.

After full code inspection of `lib.rs`, the attack is not financially exploitable in any meaningful sense. Two independent mechanisms block it: (1) Anchor's `init` constraint uses the Anchor discriminator as a uniqueness guard, and while a same-transaction close-then-init is theoretically possible, (2) the re-created escrow starts with a completely fresh state — zero deposits, no funds — making it economically inert to any attacker. The old deposits have already been paid out or refunded by the closing instruction. The only observable effect is match_id namespace reuse within one transaction, which has no on-chain financial impact. The pre-existing context files (03-state-machine.md) already noted this as LOW risk and correctly assessed it as non-financially-exploitable.

## Hypothesis Investigated

> If `settle_match` or `cancel_match` closes the escrow PDA (via Anchor's `close` attribute) and returns rent to a recipient, an attacker could include a `create_match` instruction in the same transaction to re-create the PDA at the same address, potentially extracting rent multiple times or resetting match state.
>
> Attack Vector:
> 1. Attacker constructs a transaction with: [settle_match (closes PDA)] → [create_match (same match_id)]
> 2. settle_match distributes funds and closes account
> 3. create_match re-creates the PDA at the same address (same seeds)
> 4. New escrow has fresh state, potentially allowing new deposits into a "ghost" match

## Investigation Path

### Step 1: Anchor `close` Constraint Behavior
**Location:** `lib.rs:566` (SettleMatch), `lib.rs:619` (CancelMatch), `lib.rs:659` (PermissionlessReclaim)

**Finding:** All three terminal instructions use Anchor's `close = <destination>` constraint on the escrow account. Per the Anchor framework and FP-005 in common-false-positives.md, Anchor's `close` constraint performs three operations atomically at the end of the instruction:
1. Zeros all account data (including the 8-byte discriminator)
2. Transfers all remaining lamports to the destination
3. Assigns account ownership to the system program

**Evidence:**
```rust
// SettleMatch (lib.rs:561-568)
#[account(
    mut,
    seeds = [b"match", escrow.match_id.as_bytes()],
    bump = escrow.bump,
    has_one = authority,
    close = authority,      // <-- Anchor closes to authority
)]
pub escrow: Account<'info, MatchEscrow>,

// CancelMatch (lib.rs:615-620)
#[account(
    mut,
    seeds = [b"match", escrow.match_id.as_bytes()],
    bump = escrow.bump,
    close = caller,         // <-- Anchor closes to caller
)]
pub escrow: Account<'info, MatchEscrow>,

// PermissionlessReclaim (lib.rs:655-660)
#[account(
    mut,
    seeds = [b"match", escrow.match_id.as_bytes()],
    bump = escrow.bump,
    close = caller,         // <-- Anchor closes to caller
)]
pub escrow: Account<'info, MatchEscrow>,
```

**Critical observation:** After `close` executes, the account has zero lamports, zeroed data (including discriminator), and is owned by the system program. The discriminator is gone.

### Step 2: Anchor `init` Constraint Behavior for a Closed Account
**Location:** `lib.rs:511-518` (CreateMatch account struct)

**Finding:** The `create_match` instruction uses Anchor's `init` constraint:

```rust
// CreateMatch (lib.rs:510-518)
#[derive(Accounts)]
#[instruction(match_id: String)]
pub struct CreateMatch<'info> {
    #[account(
        init,
        payer = authority,
        space = MatchEscrow::SPACE,
        seeds = [b"match", match_id.as_bytes()],
        bump,
    )]
    pub escrow: Account<'info, MatchEscrow>,
    ...
}
```

Anchor's `init` constraint checks whether the account already exists by examining its discriminator (first 8 bytes). Per FP-004 in common-false-positives.md: "Anchor's `init` constraint creates the account with a discriminator. If the account already exists with a non-zero discriminator, `init` will fail."

The key question is: what happens when `close` runs in instruction 1, zeroing the discriminator, and then `init` runs in instruction 2 of the same transaction?

**Solana runtime behavior:** Within a single transaction, account mutations from earlier instructions ARE visible to later instructions — the runtime uses a cache of account states throughout transaction execution. When `close` runs in instruction 1, the account's data is zeroed and lamports are transferred. By instruction 2, the account exists at the same address but with zeroed data and zero lamports (system-owned).

From Anchor's perspective in instruction 2, the account has no discriminator (all zeros). Anchor `init` treats a zero-discriminator system-owned account as uninitialized and can proceed to create it. The system program must also agree to create/reallocate the account, and since the payer provides rent, this succeeds.

**Conclusion:** The close-then-init sequence in one transaction IS technically possible. Anchor's `init` will not prevent it because after `close`, the discriminator is zeroed and the account appears uninitialized. This is the "same-TX PDA revival" scenario that EP-036 describes and that the context files noted at LOW risk.

### Step 3: Financial Impact Analysis — Does Revival Cause Fund Loss?
**Location:** `lib.rs:110-152` (create_match handler), `lib.rs:228-305` (settle_match handler)

**Finding:** The critical question is whether re-creating the PDA at the same address causes any financial harm. Let's trace the state at each step:

**Before instruction 1 (settle_match):**
- Escrow PDA holds: `wager * 2` lamports (player deposits) + rent reserve
- Escrow state: `Active`
- Player deposits: both `player_one_deposited = true`, `player_two_deposited = true`

**After instruction 1 (settle_match):**
- OC-10 pattern: state set to `Settled` before any transfer (line 279)
- `winner_amount` transferred to winner (lines 284-285)
- `treasury_amount` transferred to treasury (lines 287-288)
- `ops_amount` transferred to ops (lines 290-291)
- `close = authority` runs: remaining lamports (rent) to authority, data zeroed, ownership to system
- Net: escrow PDA has 0 lamports, zeroed data, system-owned

**After instruction 2 (create_match, same match_id):**
- Anchor `init` recreates the account (system program allocates space, payer provides rent)
- `create_match` sets: `state = AwaitingDeposits`, `player_one_deposited = false`, `player_two_deposited = false`, `wager_lamports = <new value>`, `activated_at = 0`
- Net: escrow PDA has only rent lamports (from payer), no player deposits

**What does the attacker gain?**

The attacker is the one who must provide the payer (authority signer) for `create_match`. The rent for the new escrow comes from the attacker's own pocket. The previous match's funds have already been fully distributed by `settle_match`. The new escrow is in `AwaitingDeposits` state with no real players involved unless new `deposit_wager` calls are made.

**There is no double-rent-extraction:** The closed escrow's rent was swept to `authority` (the `close = authority` destination). The new escrow costs fresh rent from `payer = authority`. These are the same person in the normal flow. Even if a different signer calls `create_match`, they pay fresh rent for the new account. No lamports are duplicated.

**Evidence of why no financial harm occurs:**
```rust
// settle_match already distributes ALL funds before close runs:
**ctx.accounts.escrow.to_account_info().try_borrow_mut_lamports()? -= winner_amount;  // line 284
**ctx.accounts.winner.to_account_info().try_borrow_mut_lamports()? += winner_amount;  // line 285
**ctx.accounts.escrow.to_account_info().try_borrow_mut_lamports()? -= treasury_amount; // line 287
**ctx.accounts.treasury.to_account_info().try_borrow_mut_lamports()? += treasury_amount; // line 288
**ctx.accounts.escrow.to_account_info().try_borrow_mut_lamports()? -= ops_amount;     // line 290
**ctx.accounts.ops.to_account_info().try_borrow_mut_lamports()? += ops_amount;        // line 291
// After these, escrow only holds rent lamports.
// close = authority then sweeps the rent.
// create_match in next instruction: payer provides NEW rent. Old rent is already gone.
```

### Step 4: Cancel Path Analysis
**Location:** `lib.rs:310-376` (cancel_match), same logic applies

**Finding:** The same analysis applies to `cancel_match`. After cancel, player wagers have been refunded, escrow is closed, and any revived PDA starts fresh with no deposits and no connection to the old match's funds. No financial harm.

### Step 5: Who Controls the Multi-Instruction Transaction?
**Finding:** `create_match` requires an `authority: Signer<'info>` that is the payer. The authority signer for a legitimate `create_match` is the server keypair. For a same-TX attack:

- If the attacker is the server authority: They already control settlement/cancellation and gain nothing additional from a PDA revival they engineered themselves.
- If the attacker is NOT the server authority: They cannot include `settle_match` or `cancel_match` in the first instruction because those require the authority as signer, and an attacker doesn't have that key. Additionally, `create_match` requires the `authority: Signer<'info>` to pay rent — the attacker would need to be the signer there too.

For a non-authority attacker to execute this attack, they would need to:
1. Sign a `settle_match` as the server authority (impossible — they don't have the key)
OR
1. Sign a `cancel_match` as a valid player (possible for a player after timeout)
2. THEN sign a `create_match` (they would become the `escrow.authority` in the new escrow)

In the cancel-then-create scenario: The player can cancel after 24h timeout (paying for the cancel tx and receiving rent). Then in the same tx, they call `create_match` with themselves as authority. The new escrow has `escrow.authority = attacker_key`, but `config.authority` remains the server key. Settlement of this new escrow requires BOTH `escrow.authority == signer` AND `config.authority == signer` (lines 565 and 604). Since the attacker's key is not `config.authority`, this new escrow can never be settled — it will timeout and be cancelled/reclaimed. The attacker has not gained anything; they've created an unsettleable escrow using their own rent.

### Step 6: State Machine Integrity
**Finding:** Even if the same PDA address is re-created, the state machine starts fresh. The Anchor discriminator is rewritten during `init`, so the account is now a new, valid `MatchEscrow` with `state = AwaitingDeposits`. Old state (Settled/Cancelled) is gone — it was zeroed by `close`. But this is not a problem because:

1. The old match is already fully settled/cancelled (funds distributed)
2. The new account starting in `AwaitingDeposits` is identical to any other newly created match
3. No state from the old match "leaks" into the new match (data was zeroed by close)

The match_id is reused at the PDA seed level, but from the program's perspective, the new account is completely fresh. There is no way to "inherit" the old match's deposits or state.

## Invariant Analysis

### Target Invariant
Each deposited wager is distributed exactly once: either via `settle_match` (winner/fees) or `cancel_match`/`permissionless_reclaim` (refund to player). The PDA close-and-revive should not allow a second distribution of funds that were already paid out.

### Enforcement Points
| Location | What It Enforces | Complete? |
|----------|-----------------|-----------|
| `lib.rs:279` (settle_match OC-10) | State set to `Settled` BEFORE any lamport transfer | Yes |
| `lib.rs:354` (cancel_match OC-10) | State set to `Cancelled` BEFORE any lamport transfer | Yes |
| `lib.rs:416` (permissionless_reclaim OC-10) | State set to `Cancelled` BEFORE any lamport transfer | Yes |
| `lib.rs:229-232` (settle_match state guard) | Only `Active` matches can be settled | Yes |
| `lib.rs:346-349` (cancel_match terminal guard) | Cannot cancel already-terminal matches | Yes |
| `lib.rs:390-394` (reclaim terminal guard) | Cannot reclaim already-terminal matches | Yes |
| `lib.rs:566` (close = authority on settle) | All lamports swept from escrow after settle | Yes |
| `lib.rs:619` (close = caller on cancel) | All lamports swept from escrow after cancel | Yes |
| `lib.rs:137-138` (create_match fresh state) | New escrow always starts with zero deposits | Yes |

### Enforcement Gap Assessment
The invariant is fully enforced. By the time `create_match` could run in instruction 2, ALL of the following are true:
- The closing instruction has already set terminal state (OC-10)
- All player funds have been transferred OUT of the escrow
- Only rent lamports (if any) remain, which are swept by `close`
- The new `create_match` allocates a fresh account with its own rent paid by payer
- The new account has no connection to the old match's funds

The one gap — same-TX PDA recreation — does not violate the financial invariant because there are no funds left to double-spend.

## Blocking Factors

- **OC-10 state-before-transfer pattern**: `lib.rs:279` — State is set to `Settled`/`Cancelled` before any lamport transfer. Any hypothetical second instruction targeting the same PDA for settlement would fail with `InvalidState` because the account data was zeroed by `close`, meaning Anchor would treat it as a new (uninitialized or fresh-init) account with `AwaitingDeposits` state.
- **Anchor `close` zeros lamports before same-TX revival**: `lib.rs:566` — By the time `create_match` runs, all wager lamports have been transferred to winner/treasury/ops/players. The escrow holds only rent, which is swept to the destination. The new `create_match` starts with fresh rent from the payer.
- **Dual `has_one = authority` on `SettleMatch`**: `lib.rs:565,604` — Only the server authority can call `settle_match`, meaning the attack (if attempted) is self-directed by the server. The server has no incentive to double-create its own matches.
- **`create_match` sets fresh state**: `lib.rs:137-142` — Any revived escrow starts with `state = AwaitingDeposits`, `player_one_deposited = false`, `player_two_deposited = false`. No old data survives.
- **Settle/cancel require active player deposits**: Only an escrow in `Active` state (both players deposited) can be settled. The new escrow from `create_match` starts in `AwaitingDeposits` with no deposits. It has nothing to settle.

## Enabling Factors

- **Anchor `close` zeros discriminator**: After `close`, the account's first 8 bytes are 0x00. Anchor's `init` in a subsequent instruction of the same transaction would succeed because it treats a zero-discriminator system-owned account as uninitialized. This is the theoretical enabler of same-TX revival.
- **`create_match` lacks `has_one = authority` on config**: `lib.rs:524-529` — Any signer can call `create_match`. This means a player could cancel a match and then create a new match with the same `match_id` in the same transaction. However, as analyzed above, the new escrow is financially inert without new deposits from legit players.

## Exploitation Scenario

No financially harmful exploitation scenario exists. The attack is theoretically constructable but produces no financial gain.

**Theoretical (harmless) same-TX close-and-revive:**
1. Server authority calls `settle_match` + `create_match` (same `match_id`) in one transaction
2. The settled match's funds are fully distributed; the new escrow starts empty
3. The server authority pays fresh rent for the new escrow
4. Net result: no financial gain, just a new empty escrow at the same PDA address

**Why a player cannot weaponize this:**
A player calling `cancel_match` (after 24h timeout) could include `create_match` with the same `match_id` in the same tx. But:
- The new `escrow.authority` would be the player's key, not `config.authority`
- Settlement of the new escrow requires both `escrow.authority == signer` AND `config.authority == signer` (lines 565 and 604), which the player cannot satisfy for `config.authority`
- The new escrow would never be settable, and the player just spent rent creating an unresolvable escrow
- The player gets no access to any funds that were already refunded to the players in step 1 of cancel_match

## Incidental Discoveries

- **Match ID namespace squatting via create_match + cancel in same TX (DOS variant):** A player cancelling a match can immediately re-create a new escrow at the same PDA address in the same transaction, preventing the server from re-using that match_id for a new legitimate room. Since `create_match` has no `has_one = authority` on config, anyone can occupy a PDA slot. However this is already noted as R2 in the access control context. The attacker pays rent for each squatted PDA and recovers it 48h later via `permissionless_reclaim`. Sustained squatting requires continuous capital. → Suggested new hypothesis: **H-SQUAT: PDA Namespace Exhaustion via create_match Spam** (DoS severity, not financial loss).

- **Rent arbitrage at minimum wager:** The PDA rent (~0.00146 SOL for 168 bytes) exceeds `MIN_WAGER_LAMPORTS` (0.00001 SOL) by 146x. When a player cancels a match they initiated and re-creates it (as above), the `close = caller` gives them the rent from the old escrow. The new `create_match` costs them fresh rent. Net effect: zero arbitrage between close and recreate on the same match_id (they get rent then immediately pay it back). This is consistent with the ARCHITECTURE.md observation about rent incentive imbalance.

### Key Code Sequence: OC-10 Pattern Prevents Double-Spend

The OC-10 state-before-transfer pattern is the principal defense:

```rust
// lib.rs:276-291 (settle_match)
// OC-10: set terminal state BEFORE transfers (defense-in-depth)
{
    let escrow = &mut ctx.accounts.escrow;
    escrow.state = MatchState::Settled;  // LINE 279 — written first
} // mutable borrow dropped here

// Direct lamport transfers from escrow PDA to recipients
**ctx.accounts.escrow.to_account_info().try_borrow_mut_lamports()? -= winner_amount;   // 284
**ctx.accounts.winner.to_account_info().try_borrow_mut_lamports()? += winner_amount;   // 285
**ctx.accounts.escrow.to_account_info().try_borrow_mut_lamports()? -= treasury_amount; // 287
**ctx.accounts.treasury.to_account_info().try_borrow_mut_lamports()? += treasury_amount; // 288
**ctx.accounts.escrow.to_account_info().try_borrow_mut_lamports()? -= ops_amount;      // 290
**ctx.accounts.ops.to_account_info().try_borrow_mut_lamports()? += ops_amount;         // 291
```

By the time `close` runs, the escrow holds only `rent_reserve` lamports (the initial allocation for rent-exempt storage). These rent lamports are swept to `authority`. The new `create_match` allocates a completely new escrow, paid by the signer — no lamport duplication.
