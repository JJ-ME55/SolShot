## Executive Summary

The hypothesis as stated — that the authority can select any arbitrary wallet as winner — is **NOT VULNERABLE** at the on-chain level. An Anchor constraint on the `winner` account in `SettleMatch` (lines 575-580 of `lib.rs`) hard-blocks the authority from designating any address other than `escrow.player_one` or `escrow.player_two` as the winner. The `EscrowError::InvalidWinner` error fires before the handler body runs.

However, the core economic concern behind the hypothesis IS valid and classified as **POTENTIAL**: the authority has unchecked, unilateral power to choose WHICH of the two registered players wins any match. There is no on-chain game state, no dispute mechanism, and no constraint tying the winner selection to an actual game outcome. A compromised or colluding authority can systematically designate the colluding player as winner across every match, extracting 90% of all pots while distributing the 10% fee to authority-controlled treasury/ops addresses. The full 100% economic extraction path described in the hypothesis is achievable via authority collusion with a registered player (not via third-party winner injection, which is blocked).

The distinction matters: the vulnerability is a **centralization/trust risk** with real economic impact, not a code-level bug. It is classified POTENTIAL because it requires a compromised or malicious authority, which is a precondition outside the protocol itself.

## Hypothesis Investigated

> The authority has unchecked power to select any winner in `settle_match`. A compromised or colluding authority could systematically select a controlled wallet as the winner, extracting 90% of all match pots.
>
> **Attack Vector:**
> 1. Authority creates matches via `create_match`
> 2. Legitimate players deposit wagers
> 3. Authority always calls `settle_match` with `winner = controlled_wallet`
> 4. Controlled wallet receives 90% of pot for every match
> 5. Combined with fee redirect, attacker gets 100% of all deposited funds

## Investigation Path

### Step 1: Locate the winner constraint in SettleMatch

**Location:** `lib.rs:573-581`

**Finding:** The `winner` account in `SettleMatch` is an `UncheckedAccount` but is bound by a hard Anchor `constraint` expression that must evaluate to `true` before the instruction handler executes.

**Evidence:**
```rust
/// Winner: must be one of the registered players (OC-02 — resolves H008, H002, S001)
/// CHECK: Constrained to escrow.player_one or escrow.player_two
#[account(
    mut,
    constraint = winner.key() == escrow.player_one
        || winner.key() == escrow.player_two
        @ EscrowError::InvalidWinner
)]
pub winner: UncheckedAccount<'info>,
```

The constraint compares the winner account's public key against the two player pubkeys stored in the `MatchEscrow` PDA at match creation. If the provided `winner` account is neither `player_one` nor `player_two`, Anchor returns `EscrowError::InvalidWinner` immediately — before any instruction logic runs. The authority cannot pass a controlled third-party wallet address as winner.

### Step 2: Verify the player pubkeys stored in MatchEscrow are fixed at creation

**Location:** `lib.rs:131-135` (create_match handler), `lib.rs:710-726` (MatchEscrow struct)

**Finding:** `player_one` and `player_two` are written once during `create_match` and are never subsequently modified. No instruction exists that updates `escrow.player_one` or `escrow.player_two` after initialization.

**Evidence:**
```rust
// create_match handler (lines 131-135):
let escrow = &mut ctx.accounts.escrow;
escrow.match_id = match_id;
escrow.authority = ctx.accounts.authority.key();
escrow.player_one = player_one;
escrow.player_two = player_two;
// ...
escrow.state = MatchState::AwaitingDeposits;
```

```rust
// MatchEscrow struct fields (lines 714-725):
pub player_one: Pubkey,
pub player_two: Pubkey,
// No instruction ever modifies these after create_match
```

The PDA is created with Anchor `init` (line 511-517), which means its discriminator prevents any re-initialization. The player fields cannot be overwritten.

### Step 3: Trace full settle_match authority requirements

**Location:** `lib.rs:560-610`

**Finding:** Settlement requires the signer to satisfy TWO independent `has_one = authority` constraints: one on the `escrow` account (line 565) and one on the `config` account (line 604). The signer must be both the match creator AND the current config authority. This double constraint is correctly implemented.

**Evidence:**
```rust
pub struct SettleMatch<'info> {
    #[account(
        mut,
        seeds = [b"match", escrow.match_id.as_bytes()],
        bump = escrow.bump,
        has_one = authority,           // signer must match escrow.authority
        close = authority,
    )]
    pub escrow: Account<'info, MatchEscrow>,

    #[account(mut)]
    pub authority: Signer<'info>,

    // ... winner constraint (lines 575-580) ...

    #[account(
        seeds = [GlobalConfig::SEED],
        bump = config.bump,
        has_one = authority @ EscrowError::Unauthorized,   // signer must match config.authority
        constraint = !config.is_paused @ EscrowError::ProgramPaused,
    )]
    pub config: Account<'info, GlobalConfig>,
```

### Step 4: Assess what the authority CAN freely do regarding winner selection

**Location:** `lib.rs:228-305` (settle_match handler)

**Finding:** While the authority cannot designate an arbitrary third-party as winner, it has total, unconstrained freedom to choose WHICH of the two registered players is the winner. The `winner` argument to `settle_match` is a `Pubkey` parameter (line 228), but this parameter is NOT compared against any game-outcome state stored on-chain — the contract has no knowledge of the actual game result. The authority's choice is unreviewable by the program.

**Evidence:**
```rust
// settle_match handler signature (line 228):
pub fn settle_match(ctx: Context<SettleMatch>, winner: Pubkey) -> Result<()> {
    require!(
        ctx.accounts.escrow.state == MatchState::Active,
        EscrowError::InvalidState
    );
    // OC-07: settlement deadline check
    // ... (1-hour window check) ...

    // Fee math: 90% winner, 7% treasury, 3% ops
    // ...

    // OC-10: state transition THEN transfers
    // ...

    // Direct lamport transfers to winner, treasury, ops
    // NO CHECK: Is `winner` the actual game winner? None exists on-chain.
```

The `winner` Pubkey argument is used only to route lamports — it is validated against the set `{player_one, player_two}` via the account constraint, but there is no additional check verifying the outcome is correct. The authority is trusted entirely for the outcome determination.

### Step 5: Evaluate the fee-redirect combination (full 100% extraction path)

**Location:** `lib.rs:70-88` (update_config), `lib.rs:585-597` (SettleMatch treasury/ops constraints)

**Finding:** The authority can also update `config.treasury` and `config.ops` to authority-controlled addresses via `update_config` (no timelock, no re-validation, instant effect). Combined with biased winner selection, a malicious authority can extract:
- 90% via winner (to a colluding player wallet)
- 7% via treasury (redirected to attacker's address via update_config)
- 3% via ops (same)

This yields 100% extraction, matching the hypothesis. However, the winner must still be `player_one` or `player_two` — the attacker must CONTROL one of the registered player wallets to receive the 90%.

**Evidence (update_config, no re-validation):**
```rust
pub fn update_config(
    ctx: Context<UpdateConfig>,
    new_authority: Option<Pubkey>,
    new_treasury: Option<Pubkey>,
    new_ops: Option<Pubkey>,
) -> Result<()> {
    let config = &mut ctx.accounts.config;
    if let Some(a) = new_authority { config.authority = a; }
    if let Some(t) = new_treasury  { config.treasury = t; }   // No re-validation
    if let Some(o) = new_ops       { config.ops = o; }         // No re-validation
    Ok(())
}
```

## Attack Path Analysis

### Can the attacker...

| Step | Required Action | Possible? | Evidence |
|------|-----------------|-----------|----------|
| 1 | Create matches with legitimate players | Yes | `create_match` is callable by any signer (no config authority gate) |
| 2 | Wait for both players to deposit | Yes | Players deposit via `deposit_wager` normally |
| 3 | Settle with `winner = arbitrary_controlled_wallet` | **NO** | `lib.rs:575-580`: Anchor constraint blocks any address that is not `player_one` or `player_two` |
| 3 (alt) | Settle with `winner = player_one` where attacker controls `player_one` | Yes | Authority creates match with colluding wallet as `player_one`; constraint only requires match to a registered player |
| 4 | Redirect 7% treasury to attacker wallet | Yes | `update_config` has no timelock; takes effect immediately |
| 5 | Redirect 3% ops to attacker wallet | Yes | Same |
| 6 | Extract 100% of pot across many matches | Yes (requires player collusion) | 90% via winner (colluding player), 10% via fee redirect |

**Key finding:** Step 3 as literally described (winner = arbitrary controlled wallet) is blocked. The modified step 3 (winner = a registered player the attacker also controls) succeeds.

## Invariant Analysis

### Target Invariant

The winner of every settled match must be the actual game winner — preventing the authority from systematically selecting a predetermined winner to extract funds from legitimate players.

### Enforcement Points

| Location | What It Enforces | Complete? |
|----------|-----------------|-----------|
| `lib.rs:575-580` | Winner must be `player_one` or `player_two` (no third-party winner) | Yes — Anchor constraint, checked before handler runs |
| `lib.rs:565` | Signer must be `escrow.authority` (match creator) | Yes — `has_one` |
| `lib.rs:604` | Signer must be `config.authority` (config authority) | Yes — `has_one` |
| `lib.rs:228-305` (handler body) | Winner equals actual game winner | **NO ENFORCEMENT** — no on-chain game state exists |
| Off-chain | Game outcome integrity | Off-chain only — no on-chain component |

### Enforcement Gap Assessment

The invariant "winner = correct game winner" has a complete enforcement gap on-chain. The program enforces only that the winner is ONE OF the two registered players — not WHICH one was the legitimate winner. The authority has sole, unchecked power to select between the two players.

This gap is by design: a server-authoritative game cannot submit its full state to the blockchain economically. The design choice is acknowledged in the `GlobalConfig` doc comment: "Settlement/cancel authority — the server hot wallet pubkey."

The gap is real and exploitable if the authority is compromised or colluding, but it is not a code defect — it is a trust boundary that the protocol explicitly places in the server authority.

## Blocking Factors

- **Winner third-party injection blocked:** `lib.rs:575-580` — Anchor constraint enforces `winner.key() == escrow.player_one || winner.key() == escrow.player_two`. The authority cannot designate a wallet that is not one of the two registered players.
- **Authority cannot be a player:** `lib.rs:127-129` — `create_match` enforces `player_one != authority.key()` and `player_two != authority.key()` (OC-06). The authority's own wallet cannot receive the winner payout directly.
- **OC-11 on-chain monitoring events:** `lib.rs:293-302` — `MatchSettled` event includes `winner`, `treasury_account`, and `ops_account` pubkeys. Systematic winner-biasing is detectable via on-chain event monitoring if the same player always wins.

## Enabling Factors

- **No on-chain game outcome verification:** `lib.rs:228-305` — The handler has zero checks connecting the `winner` argument to any on-chain game state. The authority's selection is unconstrained between the two players.
- **Authority can create matches with controlled player wallets:** `lib.rs:510-532` — `create_match` has no `has_one = authority` on `config`. Any signer can create a match, and the authority can register attacker-controlled wallets as `player_one` or `player_two` even if the opponent provides a different wallet. The authority sets both player pubkeys as parameters.
- **Fee redirect via update_config:** `lib.rs:70-88` — Treasury and ops can be changed to attacker-controlled addresses instantly, with no timelock.
- **No multisig on authority:** Single server hot wallet per `ARCHITECTURE.md` and context analysis. One compromised key enables full extraction.
- **No dispute mechanism:** Players cannot challenge a settlement outcome on-chain.

## Exploitation Scenario

### Prerequisites
1. Attacker controls the server authority keypair (via compromise, insider threat, or the authority being the attacker)
2. Attacker controls at least one wallet used as `player_one` or `player_two` in created matches — this is trivially satisfied since the authority creates all matches and sets both player pubkeys

### Attack Steps

1. **Setup:** Authority calls `update_config` with `new_treasury = attacker_wallet` and `new_ops = attacker_wallet` (redirect 10% fees to self).
2. **Match creation:** Authority calls `create_match` with `player_one = attacker_controlled_wallet`, `player_two = victim_wallet`, `wager_lamports = max_wager (100 SOL)`. Victim is a legitimate player invited to play.
3. **Deposits:** Victim deposits 100 SOL. Attacker deposits 100 SOL from `player_one` wallet (or any colluding wallet that controls `player_one`).
4. **Settlement:** Authority calls `settle_match` with `winner = player_one (attacker wallet)`. The Anchor constraint passes because `player_one` is a registered player.
5. **Outcome:** Attacker's `player_one` receives 180 SOL (90%). Attacker's treasury/ops wallets receive 14 SOL + 6 SOL (10%). Total attacker receipt: 200 SOL. Total attacker cost: 100 SOL (own deposit). Net attacker gain per match: 100 SOL (the victim's wager).
6. **Repeat** across every match.

### Impact

- Victim loses entire wager (100 SOL at max wager) per match.
- Attacker gains victim's wager per match with no on-chain evidence distinguishing this from legitimate play.
- If authority is compromised, ALL matches in progress at that moment are at risk.
- Historical matches already settled are unaffected (escrow closed).
- 10% fee extraction is detectable via `update_config` event only if monitoring is in place; the biased winner selection is detectable only via off-chain pattern analysis (same player always wins).

### PoC Transaction Sequence

```
TX 0: update_config
  Accounts: config (mut), authority (signer)
  Args: new_treasury = attacker_wallet, new_ops = attacker_wallet
  Prerequisite: Attacker controls config.authority
  Result: All future settlements send 10% fees to attacker_wallet

TX 1: create_match
  Accounts: escrow (init), authority (signer, payer), config (pause check)
  Args: match_id="game-123", wager_lamports=100_000_000_000, player_one=attacker_wallet, player_two=victim_wallet
  Prerequisite: TX 0 complete; victim agreed to game off-chain
  Result: Escrow PDA created with attacker_wallet as player_one

TX 2: deposit_wager (attacker_wallet signs)
  Accounts: escrow (mut), player=attacker_wallet (signer), config
  Prerequisite: TX 1 complete
  Result: 100 SOL deposited from attacker_wallet; player_one_deposited=true

TX 3: deposit_wager (victim_wallet signs)
  Accounts: escrow (mut), player=victim_wallet (signer), config
  Prerequisite: TX 2 complete
  Result: 100 SOL deposited from victim_wallet; both deposited → state=Active

TX 4: settle_match
  Accounts: escrow (mut, close=authority), authority (signer), winner=attacker_wallet,
            treasury=attacker_wallet, ops=attacker_wallet, config
  Args: winner=attacker_wallet (is valid: attacker_wallet == escrow.player_one)
  Prerequisite: Within 1h of TX 3; Anchor constraint passes because winner == player_one
  Result: attacker_wallet receives 180 SOL; attacker_wallet (as treasury) receives 14 SOL;
          attacker_wallet (as ops) receives 6 SOL. Victim loses 100 SOL entirely.

Final State: Attacker net gain = +100 SOL per match (victim's wager).
             Repeat TX 1-4 indefinitely for each new victim.
```

**Note:** TX 2 and TX 3 can be in either order. The attacker's deposit in TX 2 must come from the registered `player_one` wallet — this requires the attacker to control that wallet, which they do by design since they set `player_one = attacker_controlled_wallet` in TX 1.

### Recommended Mitigations

The following are mitigations in order of increasing implementation cost:

**1. Monitoring (Low cost, off-chain):**
The OC-11 `MatchSettled` event (lines 293-302) already emits winner, treasury, and ops pubkeys. Deploy off-chain monitoring to:
- Alert on any `update_config` transaction
- Alert when the same player wallet wins an statistically anomalous proportion of matches
- Alert when treasury/ops addresses change

**2. Multisig authority (Medium cost):**
Replace the single server hot wallet with a multisig (e.g., Squads) for the `config.authority`. This prevents a single key compromise from enabling systematic winner fraud.

**3. Two-step authority transfer (Low code cost):**
Implement a propose/accept pattern for `update_config` changes to treasury, ops, and authority to add a delay window.

**4. Timelock on config changes (Medium code cost):**
Require a delay (e.g., 24-48 hours) between `update_config` submission and effect, giving players time to exit before fee destinations change.

**5. Commit-reveal winner scheme (High code cost):**
Have the server commit to a winner hash at match creation or activation, then reveal the preimage at settlement. This doesn't prevent cheating but makes pre-settlement winner manipulation detectable after the fact.

```rust
// Conceptual fix sketch — commit-reveal pattern
// At settle_match, require winner matches committed hash:
require!(
    hash_winner(winner.key(), match_id) == escrow.winner_commitment,
    EscrowError::WinnerMismatch
);
// The commitment would be set off-chain and stored in MatchEscrow at creation
// or via a separate commit instruction
```

## Raw Investigation Notes

### Code Path for Third-Party Winner Injection Attempt

```
Attacker calls settle_match(ctx, winner=arbitrary_wallet)
  → Anchor account deserialization fires
  → For `winner: UncheckedAccount`:
     → Evaluate: winner.key() == escrow.player_one  [false]
     → Evaluate: winner.key() == escrow.player_two  [false]
     → Constraint fails → return EscrowError::InvalidWinner
  → Instruction handler body NEVER executes
```

Verdict: Blocked at account validation layer.

### Code Path for Colluding-Player Winner Selection

```
Attacker controls authority + player_one_wallet

1. create_match(match_id, wager, player_one=attacker_wallet, player_two=victim)
   → escrow.player_one = attacker_wallet stored in PDA
   → escrow.player_two = victim stored in PDA

2. victim calls deposit_wager → victim's lamports in escrow

3. attacker_wallet calls deposit_wager → attacker's lamports in escrow
   → state transitions to Active

4. settle_match(ctx, winner=attacker_wallet)
   → Anchor validates: attacker_wallet == escrow.player_one → TRUE → constraint passes
   → State → Settled
   → attacker_wallet receives 90% of pot
   → attacker-controlled treasury/ops receive 10%
```

Verdict: Succeeds. Requires authority + one registered player wallet under attacker control.

### Minimum Attack Preconditions Summary

| Precondition | Required for | Achievable Without Authority Compromise? |
|-------------|-------------|------------------------------------------|
| Control of config.authority | Calling settle_match at all | No |
| Control of player_one or player_two | Receiving winner payout | No (authority sets player addresses at create_match, but authority must also be compromised) |
| Control of treasury/ops addresses | Receiving fee payout (10%) | Only via update_config (requires authority) |

All three preconditions require the authority to be compromised or malicious. No external attacker can exploit this without that precondition.
