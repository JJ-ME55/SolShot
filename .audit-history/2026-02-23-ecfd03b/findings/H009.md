## Executive Summary

The hypothesis is confirmed as POTENTIAL. `update_config` contains no validation that the new treasury or ops address is a non-executable, non-reserved account. If a compromised or misconfigured authority calls `update_config(new_treasury = Some(program_address))`, all subsequent `settle_match` calls will attempt to credit lamports to the executable program address. Per the Solana runtime write-demotion trap (EP-106), the `+=` operation on an executable account's lamports succeeds in-memory but the runtime silently discards the write at commit time. Crucially, `try_borrow_mut_lamports()?` does NOT detect this: it returns `Ok(RefMut)` successfully — the Rust `?` operator passes, and the instruction returns `Ok(())`. However, the debit from the escrow PDA is committed. The result is permanent lamport loss: funds are silently removed from the escrow but never arrive at the treasury/ops wallet.

The classification is POTENTIAL rather than CONFIRMED because: (1) the condition requires a compromised or misconfigured authority (`update_config` is authority-gated), and (2) there is a minor runtime-version uncertainty about whether `try_borrow_mut_lamports` on an executable account returns Err vs silently succeeds — however, EP-106 and the CPI context audit both explicitly describe the "silently succeeds but gets discarded" behavior, and the context audit (CPI-R01) also flags this uncertainty and sides with the same conclusion. The precondition of a compromised authority is consistent with the overall attack surface of this protocol, which is dominated by centralization risk.

## Hypothesis Investigated

**Category:** CPI/External, Token/Economic
**Priority:** Tier 2 (HIGH)
**Precedent:** EP-106

### Hypothesis
If `update_config` sets treasury or ops to an executable program address, the direct lamport credit (`try_borrow_mut_lamports` += amount) may silently fail or behave unexpectedly. The Solana runtime may discard the write if the recipient is an executable account not owned by the program.

### Attack Vector
1. Compromised authority calls `update_config(new_treasury = Some(program_address))`
2. `settle_match` attempts to credit lamports to the program address
3. `try_borrow_mut_lamports` behavior on executable accounts
4. Treasury fees potentially burned/lost

## Investigation Path

### Step 1: Does update_config validate that new addresses are non-executable?
**Location:** `lib.rs:70-88`
**Finding:** No validation exists. The function accepts any `Option<Pubkey>` and unconditionally overwrites the config fields if `Some`.
**Evidence:**
```rust
pub fn update_config(
    ctx: Context<UpdateConfig>,
    new_authority: Option<Pubkey>,
    new_treasury: Option<Pubkey>,
    new_ops: Option<Pubkey>,
) -> Result<()> {
    let config = &mut ctx.accounts.config;

    if let Some(a) = new_authority {
        config.authority = a;
    }
    if let Some(t) = new_treasury {
        config.treasury = t;   // No check: is t executable? Is t reserved?
    }
    if let Some(o) = new_ops {
        config.ops = o;        // No check: is o executable? Is o reserved?
    }

    Ok(())
}
```
The function body contains zero validation. There is no `require!(!new_treasury.is_executable, ...)` or equivalent. Contrast with `initialize_config` (lines 53–55) which at least checks distinctness:
```rust
require!(authority != treasury, EscrowError::InvalidConfig);
require!(authority != ops, EscrowError::InvalidConfig);
require!(treasury != ops, EscrowError::DuplicateFeeAccount);
```
Even `initialize_config` does not check for executable/reserved addresses, but `update_config` also drops the distinctness checks entirely.

### Step 2: Can a compromised authority reach update_config?
**Location:** `lib.rs:464-475` (UpdateConfig account struct)
**Finding:** `update_config` is gated only by `has_one = authority` on the config PDA. Any holder of the current authority private key can call this instruction with arbitrary `new_treasury`/`new_ops` pubkeys.
**Evidence:**
```rust
#[derive(Accounts)]
pub struct UpdateConfig<'info> {
    #[account(
        mut,
        seeds = [GlobalConfig::SEED],
        bump = config.bump,
        has_one = authority @ EscrowError::Unauthorized,  // Only check: caller must be current authority
    )]
    pub config: Account<'info, GlobalConfig>,

    pub authority: Signer<'info>,
}
```
No timelock, no multisig, no two-phase commit. A single authority signature is sufficient to change treasury/ops to any pubkey, including a deployed program address, a sysvar, or the System Program itself.

### Step 3: What accounts are valid in settle_match for treasury and ops?
**Location:** `lib.rs:583-598`
**Finding:** `settle_match` validates that the passed `treasury` account matches `config.treasury` and the passed `ops` account matches `config.ops`. If the attacker has set `config.treasury` to a program address, the constraint is satisfied as long as the caller also passes that program address as the `treasury` account. The constraint does NOT check executability.
**Evidence:**
```rust
/// Treasury: validated against config PDA
/// CHECK: Constrained to config.treasury; uniqueness check vs ops
#[account(
    mut,
    constraint = treasury.key() == config.treasury @ EscrowError::InvalidTreasury,
    constraint = treasury.key() != ops.key() @ EscrowError::DuplicateFeeAccount,
)]
pub treasury: UncheckedAccount<'info>,

/// Ops: validated against config PDA
/// CHECK: Constrained to config.ops
#[account(
    mut,
    constraint = ops.key() == config.ops @ EscrowError::InvalidOps,
)]
pub ops: UncheckedAccount<'info>,
```
Both accounts are `UncheckedAccount<'info>` — Anchor does not inspect their `executable` flag, owner, or data. The only validation is key identity against the config PDA. A program address passes both constraints.

### Step 4: What happens when settle_match tries to credit lamports to an executable account?
**Location:** `lib.rs:287-291`
**Finding:** The code uses `try_borrow_mut_lamports()?`. Per EP-106, the Solana runtime performs write-demotion at message sanitization time: executable accounts are downgraded from writable to read-only BEFORE instruction execution. The in-process memory view of the account's lamports may appear writable, so `try_borrow_mut_lamports()` returns `Ok(RefMut)`. The `?` operator passes. The `+=` modifies the in-memory lamport value. But the runtime's post-execution commit step discards the write because the account was demoted to read-only. Meanwhile, the escrow debit (line 287) IS committed because the escrow PDA is a legitimate program-owned writable account.
**Evidence:**
```rust
**ctx.accounts.escrow.to_account_info().try_borrow_mut_lamports()? -= treasury_amount;  // line 287 — COMMITTED
**ctx.accounts.treasury.to_account_info().try_borrow_mut_lamports()? += treasury_amount; // line 288 — SILENTLY DISCARDED if treasury is executable
```
EP-106 explicitly classifies sub-trap #2 as: "Executable Account Trap: Executable accounts (programs) reject lamport writes — `set_lamports` fails silently." The instruction returns `Ok(())`. No error is raised.

The context documents also confirm this interpretation. From `04-cpi-external.md` (CPI-R01):
> "If any recipient is an executable program account, the lamport credit would be silently discarded (the `+=` appears to succeed in the instruction's memory view, but the runtime does not commit the change). The debit from the escrow PDA, however, DOES take effect, resulting in lost lamports."

From `05-token-economic.md`:
> "EP-106 risk: If winner/treasury/ops were executable or reserved accounts, write would fail. Winner is constrained to player_one/player_two (who must sign to deposit, so they hold private keys and are not programs). Treasury/ops are set by authority via config and could theoretically be set to program addresses via update_config. This would cause settlement DoS (not theft)."

Note the token/economic context classifies this as "settlement DoS (not theft)" — but this is imprecise. The correct characterization is **lamport loss**: the debit from the escrow PDA is committed, so the funds leave the escrow but are silently discarded by the runtime rather than landing in a recoverable location. This is fee burning, not merely a revert. The distinction matters because the economic invariant `winner + treasury + ops == total_pot` does NOT hold: only winner and (discarded) treasury+ops are debited, but treasury/ops never receive them.

### Step 5: Examining the runtime-version uncertainty
**Finding:** The CPI context explicitly flags this uncertainty: "Confirm whether `try_borrow_mut_lamports()` on an executable account returns an error (which would cause TX revert) or silently succeeds (which would cause fund loss). The behavior may differ between Solana runtime versions."

This is the key uncertainty that prevents CONFIRMED classification. Two possible behaviors:
- **Behavior A (Write-Demotion / Silent Loss):** `try_borrow_mut_lamports()` returns `Ok(RefMut)`. The `?` passes. The in-memory write happens. The runtime discards it at commit time. Escrow debit is committed, treasury credit is lost. This is what EP-106 describes.
- **Behavior B (Explicit Error / TX Revert):** The runtime marks the account's lamports as read-only at the BPF layer, causing `try_borrow_mut_lamports()` to return `Err(ProgramError::AccountBorrowFailed)`. The `?` propagates. The entire transaction reverts atomically, including the escrow state change back from `Settled` to its pre-instruction state. No lamports are lost; settlement is simply blocked (DoS, not theft).

Under Behavior A: lamports are permanently burned.
Under Behavior B: settlement permanently fails for any match while the malicious config is in place — players must wait 24–48 hours for the timeout path. No lamport loss, but protocol liveness is broken.

Both behaviors are harmful. Behavior A is the lamport-loss scenario from the hypothesis. Behavior B is a liveness attack. The hypothesis specifically asks about Behavior A.

The EP-106 pattern description ("fails silently") and the CPI context audit analysis both support Behavior A as the described mechanism. However, since the exact behavior may vary with Solana runtime version and cannot be conclusively determined from static analysis alone, the finding is POTENTIAL rather than CONFIRMED.

### Step 6: Is the winner account also at risk?
**Location:** `lib.rs:575-581`
**Finding:** The winner account is constrained to `escrow.player_one` or `escrow.player_two`. Players must be signers of `deposit_wager` to deposit their wager (line 544: `pub player: Signer<'info>`). Therefore players are keypair holders — not executable program accounts. The winner account is NOT at risk from this vector under normal operation.

However, there is a subtle edge case: player addresses are stored in the escrow as `Pubkey` values at `create_match` time. The program does NOT require players to sign `create_match`. So in theory, an attacker creating a match via the ungated `create_match` instruction could set `player_one` to an executable program address. But then `deposit_wager` would fail because it requires the player to be a `Signer<'info>` (a program address cannot sign). So the winner's lamport credit is effectively safe in practice.

## Invariant Analysis

### Target Invariant
"Every lamport deducted from the escrow PDA must be credited to exactly one of: the winner, the treasury, or the ops wallet. Total lamports in == total lamports out."

### Enforcement Points
| Location | What It Enforces | Complete? |
|----------|-----------------|-----------|
| `lib.rs:270-274` | Remainder strategy: winner + treasury + ops == total_pot (arithmetic) | Yes (arithmetic) |
| `lib.rs:585-588` | treasury account key == config.treasury (key identity) | Partial — does not check executability |
| `lib.rs:594-597` | ops account key == config.ops (key identity) | Partial — does not check executability |

### Enforcement Gap Assessment
The invariant is enforced at the arithmetic level (amounts sum correctly) but NOT at the physical lamport transfer level. The code computes correct amounts and performs the debits and credits, but cannot detect when a credit to an executable account is silently discarded by the runtime. The gap is at line 70-88 (`update_config`) which allows an executable program address to be stored as `config.treasury` or `config.ops`.

## Blocking Factors

- **Authority access control:** `update_config` requires the current authority signature (lib.rs:470). A random user cannot execute this attack without first compromising the authority private key.
- **winner account safety:** The winner is constrained to player_one or player_two, both of whom must be deposit signers (non-executable wallets), so the winner's 90% share is protected.
- **Transaction atomicity on explicit errors:** If Behavior B applies (runtime returns explicit error from borrow), the full transaction reverts and no lamports are lost — the attack reduces to a DoS only.

## Enabling Factors

- **No executable check in update_config:** lib.rs:70-88 accepts any Pubkey.
- **No executable check in settle_match accounts:** `UncheckedAccount` for treasury/ops — lib.rs:583-598.
- **No re-validation of distinctness/validity after update:** distinctness is checked at init (lib.rs:53-55) but not re-checked on update.
- **Silent write-demotion (EP-106):** The runtime discards the credit without raising an error, allowing the instruction to return `Ok(())` and the escrow debit to be committed.
- **Centralized authority model:** One-step authority transfer with no timelock means a key compromise immediately enables this attack.

## Exploitation Scenario

### Prerequisites
1. Attacker has compromised or controls the authority private key (server hot wallet)
2. At least one match is in Active state (both players deposited, awaiting settlement)
3. The attacker knows the pubkey of any deployed executable program on Solana (e.g., the System Program `11111111111111111111111111111111`, any token program, any deployed program)

### Attack Steps
1. Attacker calls `update_config(new_treasury = Some(system_program_id))` — overwrites `config.treasury` with the System Program address (or any executable program)
2. Attacker (or legitimate server) calls `settle_match` for a match, passing `treasury = system_program` as the treasury account. Constraint at line 587 is satisfied (`treasury.key() == config.treasury` passes).
3. `settle_match` executes:
   - Sets `escrow.state = Settled` (line 279) — committed
   - Debits `winner_amount` from escrow, credits winner — committed (winner is a wallet)
   - Debits `treasury_amount` from escrow — committed
   - Attempts to credit `treasury_amount` to System Program — silently discarded by runtime
   - Debits `ops_amount` from escrow — committed (if ops is also executable) OR committed to real ops wallet
4. Instruction returns `Ok(())` — no error
5. `treasury_amount` lamports have been debited from escrow but never credited anywhere — permanently lost

### Impact
- **Direct loss:** For every settled match, 7% of the total pot is permanently lost (burned). At a 1 SOL wager, this is 0.14 SOL per match. At the maximum 100 SOL wager, this is 14 SOL per match.
- **Protocol integrity:** The economic invariant (`winner + treasury + ops == total_pot`) is silently violated.
- **Detection difficulty:** The instruction returns `Ok(())`, the escrow state transitions to `Settled`, and events are emitted. Off-chain monitoring of the `MatchSettled` event would show a valid settlement. The only detectable anomaly is that `config.treasury`'s balance does not increase — detectable by monitoring the treasury wallet balance, but NOT by on-chain event monitoring alone.
- **Simultaneous ops attack:** If both `config.treasury` AND `config.ops` are set to executable program addresses, 10% of every pot is burned per settlement. At scale (many matches), this could represent significant total lamport loss.

### PoC Transaction Sequence

## Recommended Fix

Two complementary fixes:

**Fix 1 (Primary): Add executable and reserved account checks in `update_config`**

```rust
// Before (vulnerable)
pub fn update_config(
    ctx: Context<UpdateConfig>,
    new_authority: Option<Pubkey>,
    new_treasury: Option<Pubkey>,
    new_ops: Option<Pubkey>,
) -> Result<()> {
    let config = &mut ctx.accounts.config;
    if let Some(t) = new_treasury {
        config.treasury = t;  // No validation
    }
    // ...
    Ok(())
}

// After (fixed) — pass in AccountInfo for treasury/ops candidates for executable check
// NOTE: Anchor does not pass AccountInfo for Option<Pubkey> args.
// Alternative approach: add treasury_info and ops_info as optional UncheckedAccount
// params, and check their executable flag.
pub fn update_config(
    ctx: Context<UpdateConfig>,
    new_authority: Option<Pubkey>,
    new_treasury: Option<Pubkey>,
    new_ops: Option<Pubkey>,
) -> Result<()> {
    let config = &mut ctx.accounts.config;

    if let Some(a) = new_authority {
        // Ensure new authority is not zero address
        require!(a != Pubkey::default(), EscrowError::InvalidConfig);
        config.authority = a;
    }
    if let Some(t) = new_treasury {
        // Validate new treasury is not zero, distinct from ops, and not on reserved list
        require!(t != Pubkey::default(), EscrowError::InvalidConfig);
        require!(t != config.ops, EscrowError::DuplicateFeeAccount);
        require!(t != config.authority, EscrowError::InvalidConfig);
        // Executable check requires passing AccountInfo — see Fix 2
        config.treasury = t;
    }
    if let Some(o) = new_ops {
        require!(o != Pubkey::default(), EscrowError::InvalidConfig);
        require!(o != config.treasury, EscrowError::DuplicateFeeAccount);
        require!(o != config.authority, EscrowError::InvalidConfig);
        config.ops = o;
    }

    Ok(())
}
```

**Fix 2 (Preferred): Add executable flag check on treasury/ops accounts in SettleMatch**

Since `update_config` only receives `Pubkey` (not `AccountInfo`), executable checking is easier at instruction execution time. Add the check to the `SettleMatch` account struct:

```rust
// In SettleMatch account struct:
/// Treasury: validated against config PDA and confirmed non-executable
/// CHECK: Constrained to config.treasury; uniqueness check vs ops; non-executable
#[account(
    mut,
    constraint = treasury.key() == config.treasury @ EscrowError::InvalidTreasury,
    constraint = treasury.key() != ops.key() @ EscrowError::DuplicateFeeAccount,
    constraint = !treasury.executable @ EscrowError::InvalidTreasury,  // ADD THIS
)]
pub treasury: UncheckedAccount<'info>,

/// Ops: validated against config PDA and confirmed non-executable
/// CHECK: Constrained to config.ops; non-executable
#[account(
    mut,
    constraint = ops.key() == config.ops @ EscrowError::InvalidOps,
    constraint = !ops.executable @ EscrowError::InvalidOps,  // ADD THIS
)]
pub ops: UncheckedAccount<'info>,
```

This is the simpler and more robust fix: it prevents settlement from executing when treasury or ops is executable, causing a clear error rather than a silent fund loss.

## Incidental Discoveries

1. **Zero-address authority lockout:** `update_config` has no check against `Pubkey::default()` (the zero address). If the authority accidentally or maliciously sets `new_authority = Some(Pubkey::default())`, the protocol is permanently locked — no signer can ever match the zero address. All settle/pause/unpause/update operations become permanently unavailable. Suggested hypothesis: Investigate whether `Pubkey::default()` (zero address) is accepted by `update_config` and what the consequence is. The fix is a single `require!(a != Pubkey::default(), ...)` check.

2. **Ops address also vulnerable to same attack:** The analysis focuses on treasury, but the ops field (`config.ops`) has identical exposure: `update_config` can set ops to any executable program address with the same lamport-burning consequence. The fix must cover both fields.

3. **Same-transaction config-change attack:** The `update_config` and `settle_match` instructions can be composed in the same Solana transaction. An authority could: (TX1-ix1) call `update_config` setting treasury to their personal wallet, (TX1-ix2) call `settle_match`, (TX1-ix3) call `update_config` restoring original treasury — all atomically. This redirects 7% of the fee to the authority's personal wallet with no persistent trace in the config state. This is a fee redirection attack (EP-119) rather than a lamport-burning attack, but uses the same vulnerability (no timelock on config changes). Suggested hypothesis: Investigate whether a single-transaction sequence of `update_config` → `settle_match` → `update_config` enables transient fee redirection with no persistent config change detectable post-execution.

## Raw Investigation Notes

### The EP-106 Behavior in SolShot's Context

The King-of-the-SOL exploit (OtterSec, May 2025) used `**old_king.lamports.borrow_mut() += bid` — note this is raw `borrow_mut()` without `try_`. In SolShot, the pattern is `**account.try_borrow_mut_lamports()? += amount` — using the fallible variant.

The question is whether the fallible variant detects the write-demotion. Based on the EP-106 description and the CPI context analysis, the answer is no: the write-demotion occurs at the runtime's message sanitization and account commit phase, AFTER the BPF instruction has completed execution. The `try_borrow_mut_lamports()` function operates on the in-process account data view (within the BPF VM), which does not have visibility into the runtime's intent to demote the write. Therefore `try_borrow_mut_lamports()` returns `Ok(RefMut)`, the in-memory write completes, and the instruction returns `Ok(())`. The runtime then commits the escrow debit (which was on a legitimate program-owned mutable account) but discards the treasury credit (which was on a write-demoted executable account).

This asymmetric commit is the fund-loss mechanism: the debit side is committed, the credit side is discarded.

### Why Behavior A vs Behavior B Matters for Classification

If Behavior B applies (runtime returns `ProgramError::AccountBorrowFailed` before the write), then `try_borrow_mut_lamports()` would return `Err(...)`, the `?` would propagate, and the transaction would revert atomically. In that case, no lamports are lost — the effect is a permanent settlement DoS for the affected match. Players would eventually get refunds via the 24h/48h timeout mechanism, losing only time.

Under Behavior B, the attack is still harmful (liveness), but not the lamport-burning described in H009. The finding would be POTENTIAL for DoS rather than POTENTIAL for fund loss.

Given the ambiguity, the finding is classified POTENTIAL (not CONFIRMED) and the investigation notes the behavioral dependency. A runtime test (deploy to devnet, set treasury to a program address, attempt settlement) would definitively resolve this.
