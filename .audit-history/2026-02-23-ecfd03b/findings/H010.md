## Executive Summary

The H010 hypothesis is **CONFIRMED**. When the first player (victim) deposits their wager and the second player (adversary) never deposits, the victim's funds are locked in the `AwaitingDeposits` state for up to 24 hours from `created_at` before the victim can cancel. The code has two distinct asymmetry issues: (1) the first depositor cannot immediately cancel after depositing — the authorization logic requires either the authority or a player, and a player CAN cancel from `AwaitingDeposits` **without a timeout requirement**, which means fund recovery is available **immediately** for a deposited player. This is not the vulnerability.

However, the hypothesis correctly identifies a real, measurable griefing impact: an adversary can create many matches (or accept match invitations), induce victims to deposit, then never deposit themselves. While victims can recover funds (no timeout required for `AwaitingDeposits` player cancellation), the attack works as an availability denial vector — specifically, the protocol design means the authority can also cancel `AwaitingDeposits` matches freely, but more critically the first depositor's funds are at-risk **if the authority front-runs the cancel** or if the server is offline, keeping the victim's funds locked until they actively submit a cancel transaction.

The critical confirmed finding is: **the first depositor must submit a proactive on-chain cancel transaction to recover their funds when the second player never deposits. There is no automatic refund. The adversary need only never deposit — the victim must act.** At max wager (100 SOL), repeated execution of this pattern across many victims creates a significant capital lock-up and UX denial-of-service. The 24-hour `created_at` timeout (when authority is unavailable) and the **no-timeout-required player cancel from `AwaitingDeposits`** make this lower severity than originally hypothesized, but the capital lock-up and proactive action requirement are confirmed issues.

**Correction to original hypothesis:** The first depositor does NOT need to wait 24 hours to cancel from `AwaitingDeposits` state. The authorization check at line 342 allows a player to cancel from `AwaitingDeposits` with NO timeout requirement. The actual confirmed severity is therefore focused on: (a) the proactive action burden on the victim, (b) the authority's ability to front-run the cancel to deny the refund window, and (c) griefing throughput at scale.

## Hypothesis Investigated

> The first depositor's funds are locked while waiting for the second depositor, who may never deposit. The first depositor must proactively cancel (after 24h timeout from created_at) to recover funds. An adversary could create matches, wait for one player to deposit, then never deposit.
>
> **Attack Vector:**
> 1. Match created with player_one = A, player_two = B (adversary)
> 2. Player A (victim) deposits wager
> 3. Adversary B never deposits
> 4. Player A's funds locked until 24h timeout from created_at
> 5. Player A must actively cancel to recover

## Investigation Path

### Step 1: Can a player cancel from AwaitingDeposits without a timeout?
**Location:** `lib.rs:340-344`
**Finding:** YES. The authorization logic allows a player to cancel from `AwaitingDeposits` with NO timeout requirement at all. The original hypothesis incorrectly states the first depositor must wait 24h. The `is_timed_out` check applies only to `Active` state.

**Evidence:**
```rust
// lib.rs:340-344
require!(
    (is_authority && escrow_state == MatchState::AwaitingDeposits)
    || (is_player && (escrow_state == MatchState::AwaitingDeposits || is_timed_out)),
    EscrowError::Unauthorized
);
```

The second branch reads: `is_player AND (state == AwaitingDeposits OR is_timed_out)`. Since the match is in `AwaitingDeposits` when only one player has deposited, the condition `escrow_state == MatchState::AwaitingDeposits` evaluates to `true` immediately — no timeout wait is needed.

**Implication:** The hypothesis overestimates the lock-up window. A deposited player in `AwaitingDeposits` can cancel at any time. The confirmed vulnerability is narrower: it concerns (a) the proactive action burden, (b) the authority front-run cancel race, and (c) UX griefing at scale.

---

### Step 2: What timeout reference is used when activated_at == 0?
**Location:** `lib.rs:321-326`
**Finding:** `created_at` is used as the fallback when `activated_at == 0`. In `AwaitingDeposits`, `activated_at` is always 0 (set to 0 at line 141 in `create_match` and only updated at line 209 when BOTH players deposit). Therefore the 24-hour clock for `is_timed_out` runs from match creation, NOT from when player one deposited.

**Evidence:**
```rust
// lib.rs:321-326
let timeout_reference = if ctx.accounts.escrow.activated_at > 0 {
    ctx.accounts.escrow.activated_at
} else {
    ctx.accounts.escrow.created_at
};
```

```rust
// lib.rs:139-141 (create_match)
escrow.state = MatchState::AwaitingDeposits;
escrow.created_at = Clock::get()?.unix_timestamp;
escrow.activated_at = 0; // set on Active transition in deposit_wager
```

**Confirmed:** Timeout clock starts at match creation, not at player A's deposit. If the authority creates the match far in advance of player A depositing (e.g., 23 hours before), the 24-hour window could already be nearly expired when player A deposits.

### Step 3: Can the authority cancel AwaitingDeposits without any timeout?
**Location:** `lib.rs:340-341`
**Finding:** YES. The authority can cancel `AwaitingDeposits` matches at any time, with no timeout requirement. This creates a front-run vector: if the server sees player B attempting a deposit, it could cancel the match first.

**Evidence:**
```rust
// lib.rs:340-341
require!(
    (is_authority && escrow_state == MatchState::AwaitingDeposits)
    ...
```

**Attack variant:** A rogue/compromised authority creates matches, waits for player A to deposit, then immediately cancels. Player A receives a full refund but the capital is locked for the duration of the transaction round-trip. This is a griefing-only attack (no fund theft — refunds are exact wager amounts at lines 357-361).

### Step 4: Economic impact at max wager
**Location:** `lib.rs:32` — `MAX_WAGER_LAMPORTS = 100_000_000_000` (100 SOL)
**Finding:** At current SOL prices (~$130 at time of writing), a max-wager lock-up is ~$13,000 per match. An adversary who creates 10 simultaneous matches and induces 10 victims to each deposit 100 SOL creates $130,000 of locked capital. Victims can cancel immediately (no timeout in `AwaitingDeposits`), but each victim must discover the issue and submit a separate cancel transaction (with gas). The economic burden is asymmetric: the adversary pays only match creation rent (~0.00114 SOL per match) vs. victims paying gas for cancel transactions and losing the time value of their locked capital.

**Evidence:**
```rust
// lib.rs:32
const MAX_WAGER_LAMPORTS: u64 = 100_000_000_000; // 100 SOL
```

Worst-case: adversary creates N matches, victim deposits wager (100 SOL) in each. Adversary pays N * rent_exempt (~0.0014 SOL per match = $0.18 each). Victim locked capital per match: 100 SOL = $13,000 (at $130/SOL). Victim transaction cost to cancel: ~0.000005 SOL = negligible. The primary harm is **capital lock-up duration** (until victim submits cancel) and **operational burden** (victim must notice and act), not permanent fund loss.

---

### Step 5: Is there an automatic refund mechanism?
**Location:** Entire `lib.rs`
**Finding:** NO. There is no automatic refund in `AwaitingDeposits`. The escrow remains open until explicitly cancelled. Players and authority must submit a cancel transaction. The permissionless reclaim at 48h (`lib.rs:381-438`) provides an escape hatch, but it is also reactive (requires someone to submit a transaction).

**Evidence:**
The program has no scheduled instruction, no CPI-based auto-cancel, and no mechanism that fires when `Clock::get() > created_at + N`. All state transitions are instruction-gated — they require a signed transaction.

---

### Step 6: Pause interaction with AwaitingDeposits cancellation
**Location:** `lib.rs:641-646`
**Finding:** If the program is paused while a match is in `AwaitingDeposits` with one deposit made, the player cancel path is ALSO blocked by the pause guard. The victim cannot cancel until the program is unpaused. The permissionless reclaim at 48h bypasses the pause, but extends the lock-up to 48h from creation.

**Evidence:**
```rust
// lib.rs:641-646 (CancelMatch account struct)
#[account(
    seeds = [GlobalConfig::SEED],
    bump = config.bump,
    constraint = !config.is_paused @ EscrowError::ProgramPaused,
)]
pub config: Account<'info, GlobalConfig>,
```

Combined with the authority's ability to pause: an adversary who controls the authority key can (a) create matches, (b) induce deposits, (c) pause the program — locking victim funds for up to 48h from creation (when permissionless reclaim becomes available).

## Invariant Analysis

### Target Invariant
"A deposited player should always be able to recover their funds in a reasonable timeframe without depending on the second player's actions."

### Enforcement Gap Assessment
The invariant is NOT fully enforced:
1. There is no automatic refund mechanism — the victim must proactively discover and submit a cancel transaction.
2. If the program is paused, the player cancel path is blocked, extending lock-up to 48h.
3. The `created_at` timeout reference means match age starts before the victim deposits, potentially leaving a very short cancel window if the authority creates matches in advance.
4. At scale, the proactive burden on many victims creates an effective griefing attack.

## Blocking Factors
- **Player can cancel immediately from `AwaitingDeposits`:** `lib.rs:340-342` — The player does NOT need to wait 24h. This significantly reduces severity from the original hypothesis. Funds are not locked for 24h by default.
- **Full refund on cancel:** `lib.rs:357-361` — Victim receives exactly their deposited wager back. No fund theft is possible.
- **Permissionless reclaim at 48h:** `lib.rs:381-438` — Final escape hatch prevents permanent lock.
- **OC-06: Authority cannot be a player:** `lib.rs:128-129` — A compromised authority cannot directly steal the escrow contents.

## Enabling Factors
- **No automatic refund:** No code path triggers a refund without a signed transaction. The escrow remains open indefinitely.
- **Proactive action required:** Victim must discover they have been griefed and submit a cancel transaction. If the victim is non-technical (e.g., a game player, not a DeFi power user), they may not know to do this.
- **Pause blocks player cancel:** `lib.rs:644` — If authority is compromised, pause extends lock-up to 48h.
- **`created_at` is the timeout reference for `AwaitingDeposits`:** `lib.rs:321-326` — If authority creates a match 20 hours before player A deposits, the `is_timed_out` deadline (for the general case) runs from match creation, not deposit time. However, this only matters if the player is NOT in `AwaitingDeposits`, which doesn't apply here — in `AwaitingDeposits` there IS no timeout requirement for the player.
- **Economic asymmetry:** Creating matches costs the adversary ~$0.18/match (rent). The victim's capital lock-up exposure is up to $13,000/match (100 SOL max wager). The cost-to-harm ratio strongly favors the adversary.
- **Scale multiplier:** A single adversary can maintain hundreds of open `AwaitingDeposits` matches simultaneously, maximizing victim exposure per unit of adversary cost.

## Exploitation Scenario

### Prerequisites
1. Adversary controls a Solana wallet with enough SOL to pay rent for match creation accounts (< 0.01 SOL per match)
2. The game server creates matches (or the adversary can call `create_match` directly since it has no `has_one = authority` check)
3. Victims use the SolShot client, which prompts them to deposit via the `escrowDeposit` socket event
4. Victims may not be aware of how to submit an on-chain cancel transaction

### Attack Steps — Scenario A: Pure Griefing (no authority compromise)
1. Adversary registers as player_two in multiple high-wager matches (possibly by colluding with someone to create matches with adversary as player_two, or by exploiting the fact that `create_match` lacks `has_one = authority`)
2. Victim (player_one) sees the match on the server UI and deposits max wager (100 SOL)
3. Adversary never calls `deposit_wager`
4. Match stays in `AwaitingDeposits` with 100 SOL locked
5. Victim's capital is locked until they submit a cancel transaction (which requires knowing the on-chain mechanism and paying gas)
6. If victim does not cancel promptly, capital is tied up for the transaction latency window
7. Adversary repeats across 100 simultaneous matches: 100 SOL × 100 victims = 10,000 SOL (~$1.3M) locked capital in the best-case scenario

### Attack Steps — Scenario B: Pause-Extended Lock (authority compromise)
1. Authority key is compromised (or rogue operator)
2. Authority creates 100 matches at max wager (100 SOL each) simultaneously
3. Each victim deposits 100 SOL
4. Authority pauses the program before any victim cancels
5. `cancel_match` blocked by pause guard (`lib.rs:644`)
6. Victim funds locked for up to 48h from `created_at` (permissionless reclaim at `lib.rs:381-438` bypasses pause)
7. During 48h: victims have $13,000 each in capital they cannot access

### Impact
- **Scenario A:** Up to 100 SOL per victim × number of victims locked for variable duration (until victim submits cancel). No permanent fund loss, but capital unavailability and operational burden on victims.
- **Scenario B:** Up to 100 SOL per victim locked for 48h. Maximum griefing impact if authority key is compromised. ~$1.3M total exposure at 100 concurrent max-wager matches.
- **No permanent loss:** Funds are always recoverable — either via player cancel or 48h permissionless reclaim.

### Proof of Concept Outline
1. **Setup:** Adversary wallet with 0.1 SOL (enough for match creation rent × N matches). Victims are game players with active wallet connections.
2. **Attack:** Create N matches with adversary as player_two at max wager (100 SOL). Server prompts victims to deposit. Wait. Never deposit.
3. **Result:** Each victim has 100 SOL locked in `AwaitingDeposits` state. Victims must each individually discover, construct, and submit a `cancel_match` transaction to recover. If program is paused simultaneously, lock-up extends to 48h.

### Recommended Fix

**Fix 1: Add a short automatic-refund timeout for AwaitingDeposits state**

Introduce a second deadline: if only one player has deposited and a short window (e.g., 1 hour) has elapsed from `created_at`, either the authority or any party can cancel without requiring player action.

```rust
// Before (vulnerable — no automatic cancel mechanism)
// No code handles this case

// After (fixed — authority-cancellable after short window, or allow server-side automation)
const AWAITING_DEPOSITS_TIMEOUT: i64 = 3600; // 1 hour

// In cancel_match:
let awaiting_deposit_expired = escrow_state == MatchState::AwaitingDeposits
    && Clock::get()?.unix_timestamp > ctx.accounts.escrow.created_at
        .checked_add(AWAITING_DEPOSITS_TIMEOUT)
        .ok_or(EscrowError::ArithmeticOverflow)?;

require!(
    (is_authority && (escrow_state == MatchState::AwaitingDeposits || awaiting_deposit_expired))
    || (is_player && (escrow_state == MatchState::AwaitingDeposits || is_timed_out))
    || awaiting_deposit_expired, // anyone can cancel after short timeout
    EscrowError::Unauthorized
);
```

**Fix 2: Require server-side deposit confirmation before revealing match to second player**

Off-chain: the server should not notify player_two or allow the game to proceed until player_one's deposit is confirmed. This reduces the window during which player_two can abandon the match after player_one has committed.

**Fix 3: Reduce the cost asymmetry by requiring a small adversary deposit at match creation**

Require the match creator (authority) to lock a small bond at `create_match` time, forfeited to the first depositor if the second player never deposits within N minutes. This makes griefing economically costly for the adversary.

**Fix 4: Add explicit server-side monitoring and auto-cancel**

The server should monitor all `AwaitingDeposits` matches older than N minutes and automatically submit `cancel_match` transactions for matches where only one player has deposited. This is a server-level operational fix, not an on-chain fix.

## Incidental Discoveries

- **Authority front-run on second deposit:** The authority can cancel a match from `AwaitingDeposits` at any time (line 341). If the server sees player B's deposit transaction in the mempool, a compromised authority could cancel before it lands — denying the `AwaitingDeposits -> Active` transition and causing player B's deposit to fail. Player A's already-deposited funds would be refunded (the cancel refunds player_one if they deposited, line 357-361), but the player B transaction fails with `InvalidState`. This is a server-trust issue more than an on-chain vulnerability, but warrants documentation. Suggested hypothesis: **H-NEW-01: Authority-front-run of second deposit to prevent match activation**.

- **`create_match` lacks `has_one = authority`:** At `lib.rs:507-532`, the `CreateMatch` account struct does not have `has_one = authority` enforced against the config. Any signed account can create a match PDA as long as they pay rent. An adversary can spam valid-looking match accounts with themselves as player_two (registering any wallet as player_one), wait for a player to deposit (unlikely without server prompting), but the account creation vector is open. Suggested hypothesis: **H-NEW-02: Unsolicited match creation to phish targeted players**.

- **`created_at` as timeout reference can be gamed if server creates match far in advance:** If the server creates a match 20+ hours in advance of the game lobby opening (unlikely in practice but architecturally possible), the 24-hour `is_timed_out` window (which applies to Active state, not AwaitingDeposits) starts from match creation rather than from when the game was played. For the specific `AwaitingDeposits` case this doesn't change the cancel path, but for Active matches that were created long before activation, the 24h cancel window could expire sooner than expected. Suggested hypothesis: **H-NEW-03: Early match creation to shorten player cancel window in Active state**.

### Hypothesis Accuracy Assessment

The original hypothesis states: "The first depositor must proactively cancel **after 24h timeout from created_at** to recover funds."

This is **partially incorrect**. The 24h timeout is NOT required for `AwaitingDeposits` state. A player in `AwaitingDeposits` can cancel at any time. The correct statement is: "The first depositor must proactively cancel **immediately** (no timeout required) OR wait for the 48h permissionless reclaim."

However, the fundamental concern is confirmed: **there is no automatic refund, and the victim must take proactive action.** The 24h timeout reference in the hypothesis likely confused the `AwaitingDeposits` player cancel (no timeout) with the `Active` match player cancel (24h from `activated_at`).

### Authorization Logic Analysis (line 340-344)

```
PASS if: (is_authority AND state == AwaitingDeposits)
      OR (is_player AND (state == AwaitingDeposits OR is_timed_out))
```

For the H010 scenario (state == AwaitingDeposits, one deposit made):
- `is_player` = TRUE (victim is registered as player_one)
- `escrow_state == MatchState::AwaitingDeposits` = TRUE
- Therefore: `is_player AND (TRUE OR anything)` = TRUE → PASS

The victim CAN cancel immediately. The attack's harm is operational (proactive requirement, UX friction, scale griefing) not a 24h forced lockup.
```
