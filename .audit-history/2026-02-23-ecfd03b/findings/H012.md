# Finding: H012 - Lamport Underflow on Cancel/Reclaim

## Status: NOT VULNERABLE
## Confidence Score: 9

> Confidence scale:
> - **9-10**: Certain — exhaustive code analysis, all paths verified
> - **7-8**: High — strong evidence, minor gaps in coverage
> - **5-6**: Moderate — reasonable analysis, some assumptions unverified
> - **3-4**: Low — significant uncertainty, limited code visibility
> - **1-2**: Minimal — couldn't adequately assess, treat as NEEDS MANUAL REVIEW
>

## Executive Summary

The hypothesis posits that if the escrow PDA's lamport balance is reduced below the expected refund amount, the unchecked `-=` subtraction in `try_borrow_mut_lamports()` could underflow and permanently lock funds. Investigation of the code reveals this attack has no viable path.

Two independent protection layers prevent the scenario: (1) The Solana runtime enforces lamport conservation as a post-instruction invariant — if any account's deducted amount would produce a net negative lamport change across the instruction, the runtime rejects the transaction outright, reverting all state changes cleanly. (2) `overflow-checks = true` in the workspace `Cargo.toml` release profile causes the unchecked `-=` operator to produce a program panic (not a silent wrap) on overflow, which also results in a clean transaction revert with no partial state changes persisting. Neither protection permanently locks funds; both cause transaction failure before any state is committed. Additionally, no code path exists by which the PDA's deposited lamport balance can be reduced below the deposit total by an external actor.

## Hypothesis Investigated

> If the escrow PDA's lamport balance is reduced below the expected refund amount, the `try_borrow_mut_lamports` subtraction could underflow, causing the transaction to fail and permanently locking funds.
>
> Investigation:
> 1. Check if lamport subtraction uses checked arithmetic
> 2. Can the PDA balance be reduced externally? (e.g., by someone crediting negative lamports?)
> 3. What is the expected balance vs actual balance at settlement/cancel/reclaim time?
> 4. Is the Solana runtime's u64 lamport arithmetic checked?

## Investigation Path

### Step 1: Verify whether lamport subtractions use checked arithmetic

**Location:** `lib.rs:284-291` (settle), `lib.rs:359-366` (cancel), `lib.rs:421-428` (reclaim)

**Finding:** All lamport mutations use unchecked Rust arithmetic operators (`-=` and `+=`) on `u64` values obtained from `try_borrow_mut_lamports()`. No `checked_sub` is used for these operations. The `checked_*` methods are reserved for higher-level financial calculations (BPS math, timeout deadlines). This is consistent across all three disbursement paths.

**Evidence:**
```rust
// cancel_match (lib.rs:359-366)
if player_one_deposited {
    **ctx.accounts.escrow.to_account_info().try_borrow_mut_lamports()? -= wager_lamports;
    **ctx.accounts.player_one.to_account_info().try_borrow_mut_lamports()? += wager_lamports;
}
if player_two_deposited {
    **ctx.accounts.escrow.to_account_info().try_borrow_mut_lamports()? -= wager_lamports;
    **ctx.accounts.player_two.to_account_info().try_borrow_mut_lamports()? += wager_lamports;
}

// permissionless_reclaim (lib.rs:421-428) — identical pattern
```

### Step 2: Determine behavior of unchecked `-=` under overflow conditions

**Location:** `Cargo.toml:8`

**Finding:** The workspace `Cargo.toml` declares `overflow-checks = true` in the release profile. Under this setting, integer overflow/underflow on primitive arithmetic operators (`+`, `-`, `*`) causes a Rust panic rather than silent two's-complement wrapping. A panic in a Solana BPF program causes the transaction to fail with a `ProgramError::ComputationalBudgetExceeded` or a program-specific error. Crucially, it does NOT commit any partial state changes — the entire transaction is atomically reverted.

**Evidence:**
```toml
# Cargo.toml:7-9
[profile.release]
overflow-checks = true
```

**Note from prior audit context (02-arithmetic.md):** BOK NC-001 documents that `overflow-checks = true` is "not verified to work on all SBF toolchain versions." This means the panic-on-underflow behavior is a defense-in-depth measure but cannot be relied upon as the sole safeguard. However, the Solana runtime conservation check (Step 3) is independent of this and is authoritative.

### Step 3: Verify Solana runtime lamport conservation invariant

**Finding:** The Solana runtime enforces a post-instruction invariant: the sum of all lamports across all accounts touched by a transaction must be unchanged from before the instruction executed. This is enforced at the runtime level, not within the program code. If any account's lamport balance would go negative (which is impossible to represent in u64, and would manifest as a massive wrap-around value), the conservation check would detect that the sum of all account lamports changed and reject the transaction.

This is documented explicitly in the arithmetic audit context:

> "In Rust release builds, if `escrow.lamports() < amount`, the subtraction wraps to a huge u64 value. The Solana runtime WOULD reject this because the account's lamports cannot go below 0 (the runtime enforces lamport conservation)."

**Source:** `02-arithmetic.md` lines 224 and 291 (Lamport Transfer Note section)

The result is: regardless of whether `overflow-checks = true` fires, the Solana runtime's own conservation invariant rejects the transaction. In neither case are funds permanently locked — the transaction fails and all state changes (including the `MatchState::Cancelled` assignment at lines 354/416) are reverted. The match remains in its pre-call state, available for retry once the condition (if any) causing insufficient lamports is resolved.

### Step 4: Examine whether the PDA balance can be externally reduced

**Finding:** This is the critical question: can an attacker reduce the escrow PDA's lamport balance below `wager_lamports * (number_of_deposited_players)` before a cancel or reclaim call?

Three sub-questions:

#### 4a: Can lamports be withdrawn from the PDA by an unauthorized actor?

No. The escrow PDA is owned by the SolShot escrow program. The Solana runtime enforces that only the owning program can modify an account's data or debit its lamports via direct manipulation. Only the four disbursement paths in the program (settle, cancel, reclaim, and Anchor's `close`) can reduce the PDA's lamport balance. No external actor can extract lamports from a program-owned PDA without invoking the program.

#### 4b: Can lamports be added to the PDA (inflation), and does this cause problems?

Anyone can credit lamports to any account (the System Program's transfer instruction can send to any writable account). Adding extra lamports to the PDA only increases its balance above the `2 * wager_lamports` floor. This cannot cause an underflow on disbursement — it means there are more lamports available, not fewer. Extra lamports beyond `2 * wager_lamports` are reclaimed by Anchor's `close = authority` (in settle and reclaim) or `close = caller` (in cancel) after the instruction body returns. This is a separate concern (see Related Findings) but does not enable the H012 attack.

#### 4c: Can rent collection drain the PDA?

No. Anchor's `init` creates accounts with rent-exempt lamport balances. Rent-exempt accounts are immune to rent collection by the Solana runtime's rent collector. The escrow PDA is initialized with `space = MatchEscrow::SPACE` (168 bytes) and is payer-funded for rent exemption at creation by `create_match`. The PDA's lamport balance at time of settlement/cancel/reclaim is:

```
PDA balance = rent_exempt_minimum + (wager_lamports * deposited_count)
```

This is always >= `wager_lamports * deposited_count`, never less.

**Account struct confirming rent-exempt init:**
```rust
// lib.rs:511-518 (CreateMatch)
#[account(
    init,
    payer = authority,
    space = MatchEscrow::SPACE,
    seeds = [b"match", match_id.as_bytes()],
    bump,
)]
pub escrow: Account<'info, MatchEscrow>,
```

Anchor `init` always allocates at rent-exempt minimum. The deposit CPI adds wager lamports on top.

### Step 5: Verify expected vs actual PDA balance at refund time

**Finding:** Tracing the exact lamport balance through the full lifecycle:

**At `create_match`:**
- Authority pays rent-exempt minimum (approximately 1,447,680 lamports for 168 bytes on mainnet, ~0.00145 SOL)
- PDA balance = `rent_exempt_min`
- Deposits: 0

**After player_one `deposit_wager`:**
- CPI transfers `wager_lamports` from player_one to PDA
- PDA balance = `rent_exempt_min + wager_lamports`
- `player_one_deposited = true`

**After player_two `deposit_wager`:**
- CPI transfers `wager_lamports` from player_two to PDA
- PDA balance = `rent_exempt_min + 2 * wager_lamports`
- Both deposited = true, state → Active

**At `cancel_match` (both deposited):**
- Refund logic: subtract `wager_lamports` twice (lines 359, 365)
- Total subtracted: `2 * wager_lamports`
- PDA balance after lamport ops: `rent_exempt_min`
- `close = caller` then reclaims `rent_exempt_min` after instruction body returns
- Net PDA balance: 0 (account closed)

At no point during this sequence does `escrow.lamports < amount_to_subtract`. The balance is always `rent_exempt_min + deposited_amount`, and the subtracted amount never exceeds `deposited_amount`.

**At `cancel_match` (only player_one deposited — AwaitingDeposits state):**
- Refund logic: only the `if player_one_deposited { ... }` branch executes (lines 358-361)
- Total subtracted: `wager_lamports`
- PDA balance = `rent_exempt_min + wager_lamports - wager_lamports = rent_exempt_min`
- `close = caller` reclaims rent
- No underflow possible: escrow holds exactly `wager_lamports` from deposit, which equals the refund

**At `permissionless_reclaim` (same logic as cancel):**
- Same two if-branches with same balance invariant
- Identical safety argument applies

### Step 6: Confirm state-before-transfer prevents double-spend enabling underflow

**Location:** `lib.rs:351-355` (cancel), `lib.rs:413-417` (reclaim)

**Finding:** Both `cancel_match` and `permissionless_reclaim` set `MatchState::Cancelled` BEFORE executing any lamport transfers (OC-10 pattern). Once the state is set to Cancelled, neither instruction can be invoked again (the state guards at lines 346-349 and 390-394 check for already-terminal states). This prevents the following attack sequence: call cancel, have the first `-=` succeed, have the second `-=` fail, retry the instruction. After any such failure, the transaction is fully reverted including the state transition, so the match remains in a non-terminal state and can be retried cleanly.

**Evidence:**
```rust
// lib.rs:351-355 (cancel_match OC-10 pattern)
{
    let escrow = &mut ctx.accounts.escrow;
    escrow.state = MatchState::Cancelled;
} // mutable borrow dropped here

// Refund player one if they deposited
if player_one_deposited {
    **ctx.accounts.escrow.to_account_info().try_borrow_mut_lamports()? -= wager_lamports;
    ...
}
```

Even though the state is set before transfers, Solana's transaction atomicity means that if the lamport operation fails (for any reason), the entire transaction — including the state change — is reverted. The match would revert to its pre-cancel state.

## Invariant Analysis

### Target Invariant
"The escrow PDA's lamport balance is always >= the sum of lamports owed to deposited players at the time cancel/reclaim executes."

Formally: `escrow.lamports() >= (player_one_deposited ? wager_lamports : 0) + (player_two_deposited ? wager_lamports : 0)`

### Enforcement Points
| Location | What It Enforces | Complete? |
|----------|-----------------|-----------|
| `lib.rs:179-188` (deposit_wager CPI) | Each deposit adds exactly `wager_lamports` to PDA | Yes |
| `lib.rs:511-518` (CreateMatch init) | PDA created at rent-exempt minimum; authority pays rent | Yes |
| `Cargo.toml:8` (overflow-checks = true) | Underflow causes panic, not silent wrap | Yes* |
| Solana runtime conservation | Post-instruction lamport sum must be unchanged | Yes (authoritative) |
| `lib.rs:346-349` / `lib.rs:390-394` (state guards) | Terminal states cannot be re-entered | Yes |

*Subject to BOK NC-001 caveat regarding SBF toolchain version behavior.

### Enforcement Gap Assessment

The invariant is enforced across ALL code paths. There is no instruction in the program that can reduce the PDA's lamport balance without crediting the corresponding amount to an authorized recipient, and no external mechanism can drain the PDA. The arithmetic invariant `escrow.lamports >= deposited_wagers` is maintained by construction from account initialization through deposit through disbursement.

## Blocking Factors

- **Program account ownership**: `lib.rs` program owns all escrow PDAs. Only the program can debit them. External actors cannot drain lamports without invoking program instructions that enforce state validation.

- **Rent exemption**: Anchor `init` at `lib.rs:511-518` ensures the PDA is created rent-exempt. Solana does not collect rent from rent-exempt accounts.

- **Overflow-checks = true**: `Cargo.toml:8` — unchecked underflow on u64 causes a panic (program abort), resulting in full transaction revert. No partial state persists.

- **Solana runtime lamport conservation**: Runtime-level post-instruction invariant. If escrow lamports would go negative (appearing as a huge wrap value), the net lamport change across the instruction would be non-zero and the transaction would be rejected with all state reverted.

- **Transaction atomicity**: Any failure in a lamport operation reverts the entire transaction including the `MatchState::Cancelled` assignment. The match returns to its pre-call state and can be retried.

## Enabling Factors

None identified. There is no code path, external mechanism, or economic condition that can place the escrow PDA's lamport balance below the amount owed to deposited players.

## Related Findings

- Related to H009/H010 (double-deposit / deposit manipulation) — if deposit logic were broken and `player_one_deposited` could be false when a wager was actually CPI-transferred, the cancel logic might skip a refund, leaving lamports stuck. But this is an underpayment scenario (PDA has MORE than the refund code disburses), not an underflow scenario.
- The lamport surplus left by `close = caller/authority` sweep is analyzed in the Economic section of the Architecture document. That sweep handles rent; it does not interact with this hypothesis.

## Incidental Discoveries

- **Lamport donation to PDA (economic incentive mis-alignment)**: Anyone can send SOL to the escrow PDA via `system_program::transfer`. Extra lamports above `2 * wager + rent_exempt_min` will be swept to the instruction caller via `close = caller` (cancel/reclaim) or `close = authority` (settle). In `cancel_match`, the caller of the cancel instruction receives the donation, not the players. In `permissionless_reclaim`, the third-party caller receives it. This creates a slight incentive for griefing (donating tiny amounts to make the match escrow appealing to reclaim-callers) but does not threaten player funds or enable underflow. Suggested new hypothesis: **H-DONATION: PDA Lamport Donation Griefing** — Can an attacker systematically exploit the donation sweep to profit from reclaim incentives at the expense of players or the authority?

- **Incomplete `overflow-checks` guarantee (BOK NC-001)**: The SBF toolchain may not honor `overflow-checks = true` in all versions. The program relies on the Solana runtime conservation check as the authoritative backstop. Consider adding explicit `checked_sub` to lamport operations as defense-in-depth, even though it is not required for security under current parameters.

## Raw Investigation Notes

### Lamport Balance Trace

```
create_match:
  escrow.lamports = rent_exempt_min  (~1,447,680 for 168-byte account)

deposit_wager (player_one):
  CPI: player_one → escrow += wager_lamports
  escrow.lamports = rent_exempt_min + wager_lamports

deposit_wager (player_two):
  CPI: player_two → escrow += wager_lamports
  escrow.lamports = rent_exempt_min + 2 * wager_lamports
  state → Active

cancel_match (both deposited, timed out):
  [state set to Cancelled first]
  escrow -= wager_lamports  → escrow = rent_exempt_min + wager_lamports  (> 0, no underflow)
  player_one += wager_lamports
  escrow -= wager_lamports  → escrow = rent_exempt_min                    (> 0, no underflow)
  player_two += wager_lamports
  [Anchor close = caller]
  escrow → 0, caller += rent_exempt_min

cancel_match (only player_one deposited, AwaitingDeposits):
  [state set to Cancelled]
  escrow -= wager_lamports  → escrow = rent_exempt_min                    (> 0, no underflow)
  player_one += wager_lamports
  player_two branch: skipped (player_two_deposited = false)
  [Anchor close = caller]
  escrow → 0, caller += rent_exempt_min

cancel_match (neither deposited, AwaitingDeposits):
  [state set to Cancelled]
  both branches skipped
  [Anchor close = caller]
  escrow → 0, caller += rent_exempt_min
  (no lamport subtraction at all — no underflow risk)
```

In every case, the lamport subtraction amount is always <= the deposited amount held in the PDA. The rent floor is an additional cushion, not a deficit.

### Why Permanent Fund Locking Cannot Occur

The hypothesis requires a scenario where the PDA has insufficient lamports AND the cancel/reclaim fails AND the failure prevents future recovery. This breaks down because:

1. The insufficient-lamport scenario cannot occur (PDA balance = rent_floor + deposits >= deposits = refund_amount)
2. Even if a transaction fails (for any reason), it reverts completely — state goes back to Active/AwaitingDeposits
3. A reverted match can be retried (cancel or reclaim) — there is no code path that permanently marks a match as "unrefundable" without actually performing the refund
4. The permissionless_reclaim instruction (callable by anyone after 48h) provides a final escape hatch — even if cancel_match somehow failed, reclaim with its identical logic would succeed under the same conditions

### Solana Runtime Lamport Conservation — Technical Details

The Solana BPF runtime validates the following after every instruction executes:
- Sum of lamports across all accounts (pre-instruction) == Sum of lamports across all accounts (post-instruction)

If any `-=` produces a wraparound value (e.g., `0 - 1 = u64::MAX`), the escrow account would appear to have `u64::MAX` lamports. The recipient's `+=` would add a smaller amount. The conservation check would see a net INCREASE in total lamports (because u64::MAX >> any reasonable increment), and reject the transaction.

This check runs AFTER the instruction body but BEFORE any state is committed to the ledger — making it a clean revert, not a partial commit.
