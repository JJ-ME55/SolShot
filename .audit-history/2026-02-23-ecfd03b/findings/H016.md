# Finding: H016 - AwaitingDeposits Cancel Without Depositing (Rent Theft)

## Status: CONFIRMED
## Confidence Score: 9

> Confidence scale:
> - **9-10**: Certain — exhaustive code analysis, all paths verified
> - **7-8**: High — strong evidence, minor gaps in coverage
> - **5-6**: Moderate — reasonable analysis, some assumptions unverified

## Executive Summary

A player registered to a match in `AwaitingDeposits` state — regardless of whether they personally deposited — can call `cancel_match` and receive the escrow PDA's rent-exemption lamports via the `close = caller` constraint. The rent (~0.00197 SOL for a 168-byte account) was funded by the match creator (the server authority) at `create_match`. A non-depositing player who cancels claims this rent at the authority's expense while paying only a transaction fee (~0.000005 SOL), yielding a net profit of roughly 0.00196 SOL per match.

The financial impact per exploit is small (under $0.001 at most SOL prices), but the attack requires no special skill beyond being a registered player and can be repeated at scale if an attacker controls many wallets that are assigned to matches. The rent claim is unambiguously a design gap: the `close` destination was set to `caller` to incentivize cleanup, but it also transfers value to players who have no deposited stake in the escrow.

---

## Hypothesis Investigated

> A player assigned to a match (player_one or player_two) might call `cancel_match` from AwaitingDeposits state without depositing, potentially claiming rent via the `close` attribute.
>
> 1. Who receives rent on cancel_match close? Check `close = ` in CancelMatch struct
> 2. Does cancel from AwaitingDeposits require the caller to have deposited?
> 3. Can a non-depositing player claim rent by cancelling?
> 4. Is there a net profit for the attacker?

## Investigation Path

### Step 1: Who Receives Rent on close in CancelMatch
**Location:** `programs/solshot-escrow/src/lib.rs:619`

**Finding:** The `close` constraint on the `escrow` account in `CancelMatch` is set to `caller`, not to `authority` or to the depositing player. Whoever signs and submits the `cancel_match` transaction receives the full rent-exemption lamport balance remaining in the PDA after any wager refunds are processed.

**Evidence:**
```rust
/// CancelMatch — refund players (OC-04, OC-05, OC-07, OC-09, OC-10)
#[derive(Accounts)]
pub struct CancelMatch<'info> {
    #[account(
        mut,
        seeds = [b"match", escrow.match_id.as_bytes()],
        bump = escrow.bump,
        close = caller,           // <-- rent goes to the caller, not authority
    )]
    pub escrow: Account<'info, MatchEscrow>,

    #[account(mut)]
    pub caller: Signer<'info>,
```

Contrast with `SettleMatch` at line 566, where `close = authority` — the match creator recovers rent on a successful settlement.

---

### Step 2: Who Is Authorized to Cancel from AwaitingDeposits
**Location:** `programs/solshot-escrow/src/lib.rs:336-344`

**Finding:** Either the authority OR any registered player can cancel a match in `AwaitingDeposits` state. There is no requirement that the caller (when a player) has actually deposited their wager.

**Evidence:**
```rust
let is_authority = caller == config_authority;
let is_player = caller == ctx.accounts.escrow.player_one
    || caller == ctx.accounts.escrow.player_two;

require!(
    (is_authority && escrow_state == MatchState::AwaitingDeposits)
    || (is_player && (escrow_state == MatchState::AwaitingDeposits || is_timed_out)),
    EscrowError::Unauthorized
);
```

The `is_player` check only tests whether the caller's pubkey matches `escrow.player_one` or `escrow.player_two`. It does not read `player_one_deposited` or `player_two_deposited`. A player who has not yet deposited satisfies `is_player` equally to one who has.

---

### Step 3: Refund Logic — What Happens When No Deposit Was Made
**Location:** `programs/solshot-escrow/src/lib.rs:357-367`

**Finding:** Refunds are gated on the deposit flags. If neither player has deposited, no wager lamports are transferred, and the only lamports remaining in the PDA are the rent-exemption reserve. These are swept to `caller` by the `close = caller` constraint after the instruction body returns.

**Evidence:**
```rust
// Refund player one if they deposited
if player_one_deposited {
    **ctx.accounts.escrow.to_account_info().try_borrow_mut_lamports()? -= wager_lamports;
    **ctx.accounts.player_one.to_account_info().try_borrow_mut_lamports()? += wager_lamports;
}

// Refund player two if they deposited
if player_two_deposited {
    **ctx.accounts.escrow.to_account_info().try_borrow_mut_lamports()? -= wager_lamports;
    **ctx.accounts.player_two.to_account_info().try_borrow_mut_lamports()? += wager_lamports;
}
```

If both flags are false (zero deposits), no lamports are transferred by the instruction body. Anchor's close constraint then moves the residual escrow lamports — exactly the rent-exemption balance — to `caller`.

---

### Step 4: Who Funded the Rent, and Is There Net Profit
**Location:** `programs/solshot-escrow/src/lib.rs:511-532` (CreateMatch account struct)

**Finding:** The `payer = authority` in the `CreateMatch` struct means the server authority paid the rent-exemption deposit (~0.00197 SOL for 168 bytes at current Solana rent rate). When a non-depositing player cancels, they receive this balance minus the transaction fee they paid (approximately 0.000005 SOL). Net profit to attacker: ~0.00196 SOL per exploit.

**Evidence:**
```rust
pub struct CreateMatch<'info> {
    #[account(
        init,
        payer = authority,        // <-- authority funds rent at creation
        space = MatchEscrow::SPACE,
        seeds = [b"match", match_id.as_bytes()],
        bump,
    )]
    pub escrow: Account<'info, MatchEscrow>,

    #[account(mut)]
    pub authority: Signer<'info>,
```

The authority pays the rent to create the escrow. If the match is settled normally, `close = authority` at line 566 returns that rent to the authority. If the match is cancelled (by player without deposit), `close = caller` redirects it to the player instead. The authority loses its rent deposit.

---

### Step 5: Verifying the Attack Is Reachable in Practice
**Location:** `programs/solshot-escrow/src/lib.rs:508-532` and server-side `create_match` invocation

**Finding:** The `CreateMatch` struct does not include a `has_one = authority` constraint against the `config` PDA — any signer can call `create_match`. However, for the hypothesized attack, the attacker does not need to create the match themselves. They only need to be registered as `player_one` or `player_two` in a server-created match in `AwaitingDeposits` state.

In a normal game flow, after a room is created on the server and `create_match` is called on-chain:
1. The escrow is in `AwaitingDeposits`.
2. Player two (or player one) can immediately call `cancel_match` before depositing.
3. They receive the PDA rent. The other player, if they had deposited, gets their wager back.
4. The cancelling player pays only the transaction fee.

This does not require any special setup beyond being assigned to a wager match — a routine game event.

## Invariant Analysis

### Target Invariant
The escrow account rent, funded by the authority at creation, should be returned to the authority upon normal match closure. In cancellation scenarios, it should incentivize legitimate cleanup, not reward a non-participating player for sabotaging a match.

### Enforcement Points
| Location | What It Enforces | Complete? |
|----------|-----------------|-----------|
| `lib.rs:340-344` | Caller must be authority or registered player | Yes — prevents random wallets |
| `lib.rs:358-366` | Wager refunds are conditional on deposit flags | Yes — no wager funds leak |
| `lib.rs:619` | `close = caller` sends rent to caller | Yes — enforced, but sends to non-depositor |
| (missing) | Caller must have deposited to receive close rent | **No** — this check does not exist |

### Enforcement Gap Assessment
The invariant "rent goes to authority on cancel" is enforced by `SettleMatch` (`close = authority`, L566) but is entirely absent from `CancelMatch` (`close = caller`, L619). There is no code anywhere in `CancelMatch` that restricts the close destination based on the caller's deposit status. A player who has not deposited a single lamport receives the full rent when they cancel.

---

## Blocking Factors

- A non-player (random wallet) cannot exploit this: `is_player` check at `lib.rs:337-343` blocks callers who are not `player_one` or `player_two`.
- The attack does not drain player wager funds: deposit-conditional refunds at lines 358-366 ensure wager lamports are returned to depositors if applicable.
- The program being paused blocks `cancel_match`: `constraint = !config.is_paused` at L644. However, the attacker would simply wait for the program to be unpaused.

---

## Enabling Factors

- `close = caller` at `lib.rs:619`: Unconditionally assigns residual PDA lamports to the transaction signer, regardless of their deposit status.
- No deposit-status requirement in authorization check at `lib.rs:340-344`: `is_player` is purely identity-based.
- `payer = authority` at `lib.rs:513`: Authority funds the rent, so extracting it transfers value from the protocol to the attacking player.
- `create_match` is accessible to any signer (`lib.rs:520-521`): An attacker can construct their own match with their own wallets and self-cancel, though that yields zero net profit (they paid their own rent). The real attack uses server-created matches.

## Exploitation Scenario

### Prerequisites
1. Attacker controls a wallet that is registered as `player_one` or `player_two` in a server-created match.
2. The match is in `AwaitingDeposits` state (the attacker's counterpart has not yet deposited, or the attacker acts before depositing themselves).
3. The program is not paused.

### Attack Steps
1. The attacker's wallet is assigned to a wager match by the server. The authority calls `create_match`, paying the rent-exemption deposit (~0.00197 SOL) to initialize the escrow PDA.
2. The attacker does NOT call `deposit_wager`. Their `player_X_deposited` flag remains false.
3. The attacker calls `cancel_match` with their wallet as `caller`.
4. The authorization check at L340 passes: `is_player && escrow_state == AwaitingDeposits` is true.
5. No wager refund transfers occur (deposit flag is false).
6. Anchor's close constraint moves all residual PDA lamports (~0.00197 SOL) to the attacker's wallet.
7. Net gain: ~0.00196 SOL (rent received minus transaction fee). The server authority loses ~0.00197 SOL it paid at match creation.

### Impact
- **Per exploit:** ~0.00197 SOL extracted from the authority per match sabotaged.
- **Match disruption:** The match is cancelled on-chain. If the attacker's counterpart had already deposited, they are refunded their wager. The match is unrecoverable.
- **Scale potential:** An attacker who participates in many matches and cancels each one before depositing could drain the authority's wallet over time. At 100 matches/day, this is ~0.197 SOL/day (~$30/day at $150/SOL).
- **Denial of service:** The match cannot proceed after cancellation, denying legitimate gameplay to the non-attacking player.

### PoC Transaction Sequence

```
TX 1: create_match
  Accounts: authority (server keypair), escrow PDA (new), config PDA, system_program
  Args: match_id="room-abc123", wager_lamports=1_000_000_000 (1 SOL), player_one=victim_wallet, player_two=attacker_wallet
  Prerequisite: Server creates match for a wager game
  Result: Escrow PDA created, state=AwaitingDeposits, authority pays ~0.00197 SOL rent

TX 2: cancel_match
  Accounts: escrow PDA (mut), caller=attacker_wallet (signer), player_one=victim_wallet, player_two=attacker_wallet, config PDA, system_program
  Args: (none — cancel_match takes no explicit args)
  Prerequisite: TX 1 complete; attacker has NOT called deposit_wager; state is AwaitingDeposits
  Result:
    - Authorization check passes: is_player=true, escrow_state=AwaitingDeposits
    - player_two_deposited=false → no wager refund to player_two
    - player_one_deposited=false → no wager refund to player_one
    - escrow.state set to Cancelled
    - close=caller → ~0.00197 SOL transferred to attacker_wallet
    - Attacker paid ~0.000005 SOL in tx fees

Final State:
  - Attacker net gain: ~0.00196 SOL (authority's rent)
  - Authority net loss: ~0.00197 SOL (rent not recovered)
  - Match destroyed: cannot be replayed with same match_id without create_match again
  - Victim player: unaffected (their wager was never taken; they suffer only the disruption)
```

### Proof of Concept Outline
1. Setup: Attacker controls wallet `W` assigned as `player_two` in a server-created match. Match is in `AwaitingDeposits`.
2. Attack: Attacker calls `cancel_match` with `W` as `caller`, `player_one` = registered player one address, `player_two` = W, `config` = program config PDA.
3. Result: Transaction succeeds, escrow account closed, ~0.00197 SOL credited to W, match cancelled.

### Recommended Fix

The fix should redirect the `close` destination in `CancelMatch` to `authority` (mirroring `SettleMatch`) rather than `caller`. This removes the economic incentive for players to cancel without depositing while preserving all legitimate cancel functionality.

Alternatively, if the design intent is to incentivize player-initiated cleanup specifically, the close rent should be returned to the depositing players proportionally, or retained by the authority.

```rust
// Before (vulnerable): close = caller — any player signing the cancel tx receives rent
#[account(
    mut,
    seeds = [b"match", escrow.match_id.as_bytes()],
    bump = escrow.bump,
    close = caller,
)]
pub escrow: Account<'info, MatchEscrow>,

// After (fixed option A): close = authority — rent always returns to match creator
#[account(
    mut,
    seeds = [b"match", escrow.match_id.as_bytes()],
    bump = escrow.bump,
    close = authority,          // authority must be added as a mut account if not already present
)]
pub escrow: Account<'info, MatchEscrow>,

// After (fixed option B): add authority as mut UncheckedAccount to CancelMatch,
// constrained to config.authority, and set close = authority
// This matches the pattern already used in SettleMatch (lib.rs:566).
```

For option B, the `CancelMatch` struct would need an `authority` account added, validated against `config.authority`. The caller remains the signer for authorization purposes; the close destination is separate.

A simpler approach that avoids adding an account is to keep `close = caller` but add a guard requiring the caller to have deposited if they are a player (not authority):

```rust
// In cancel_match handler, after authorization check:
if is_player {
    let caller_deposited = (is_p1 && player_one_deposited) || (is_p2 && player_two_deposited);
    require!(
        caller_deposited || escrow_state == MatchState::AwaitingDeposits && !player_one_deposited && !player_two_deposited,
        EscrowError::Unauthorized
    );
}
// NOTE: This logic is complex and must handle the "neither deposited" edge case.
// Option A (change close destination) is simpler and less error-prone.
```

Option A (change `close = authority`) is the recommended fix due to simplicity and alignment with `SettleMatch`.

## Incidental Discoveries

- **`permissionless_reclaim` also uses `close = caller`** (L659): By design (DCA-02), the caller receives rent as a cleanup incentive. This is intentional and documented. However, the same design question applies: should the protocol be paying third-party cleanup actors ~0.002 SOL each? For permissionless_reclaim this is an explicit and acceptable tradeoff; for `cancel_match` by a non-depositing player it is not. Suggested new hypothesis: **H017 — PermissionlessReclaim Rent Incentive: Is ~0.002 SOL per reclaim economically appropriate or does it create an over-incentivized spam vector?** (Likely LOW / acceptable by design, but worth confirming.)

- **Match disruption without deposit loss**: The attacker in this scenario causes a match cancellation without personal financial risk beyond the transaction fee. This is a **griefing vector** — an attacker can systematically destroy the opponent's matches at near-zero cost. Even if the rent extraction is patched (by changing `close = authority`), a player could still cancel before depositing to grief their opponent. A separate guard should be considered: once a match is created and the counterpart has deposited, the non-depositing player should be penalized or prevented from cancelling for some brief window. Suggested new hypothesis: **H018 — Griefing via No-Deposit Cancel: Can a player cancel after their opponent deposits, with zero personal loss, purely to disrupt gameplay?** This is distinct from the rent theft aspect of H016.

## Raw Investigation Notes

**`close = caller` vs `close = authority` contrast:**
- `SettleMatch` (L566): `close = authority` — rent returns to match creator on normal completion
- `CancelMatch` (L619): `close = caller` — rent goes to whoever triggers the cancel
- `PermissionlessReclaim` (L659): `close = caller` — intentional third-party cleanup incentive

**Rent amount calculation:**
- `MatchEscrow::SPACE = 168` bytes (L753)
- Rent-exemption for 168 bytes on Solana mainnet ≈ 1,461,600 lamports ≈ 0.00146 SOL at current rates
- More precisely: `128 + 168 = 296` bytes including account header; rent = 296 * (3480/2) = ~0.00146 SOL
- Context docs note ~0.00197 SOL; the exact amount depends on the current rent epoch but is in the 0.001-0.002 SOL range

**Attack path when one player has already deposited:**
- Scenario: Player one deposits, player two has not yet deposited
- Player two calls cancel_match (is_player=true, state=AwaitingDeposits → authorized)
- player_one_deposited=true → player one is refunded their wager (lines 358-360)
- player_two_deposited=false → no refund for player two (they never deposited)
- close=caller (player two) → player two receives PDA rent (~0.002 SOL)
- Victim: player one gets their wager back, no net loss
- Authority: loses rent (~0.002 SOL) that was not recovered
- Attacker (player two): receives ~0.002 SOL for ~0.000005 SOL transaction fee

**Self-cancellation with self-created match yields zero profit:**
- If attacker calls create_match (which has no authority check), they pay their own rent
- If they then call cancel_match on their own match, they receive the same rent back via close=caller
- Net: zero profit, just a wasted transaction fee
- Therefore the attack only makes money when exploiting authority-created matches
