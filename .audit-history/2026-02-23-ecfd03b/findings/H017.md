# Finding: H017 - Config State Read During Same-TX Mutation

## Status: POTENTIAL
## Confidence Score: 7

> Confidence scale:
> - **9-10**: Certain — exhaustive code analysis, all paths verified
> - **7-8**: High — strong evidence, minor gaps in coverage
> - **5-6**: Moderate — reasonable analysis, some assumptions unverified

## Executive Summary

The hypothesis is **structurally valid** with a meaningful qualifier: composing `update_config` → `settle_match` → `update_config(restore)` in a single transaction IS technically possible on Solana — later instructions see state written by earlier instructions in the same transaction — and the config account IS shared between the two instructions in compatible modes (mutable in `UpdateConfig`, immutable-read in `SettleMatch`). An attacker who already controls the authority key can thus redirect one match's treasury and ops fees to attacker-controlled addresses and then restore the config, leaving no persistent trace.

However, this attack has an absolute prerequisite: **full compromise of the current authority private key**. Without the authority signature, `update_config` cannot execute (enforced by `has_one = authority` on the config account). This makes the attack a consequence of authority compromise rather than an independent vulnerability. It is rated POTENTIAL rather than CONFIRMED because (a) it requires a precondition that is itself a critical security failure and (b) the incremental damage — redirecting fees on one match while restoring config — is bounded and reversible off-chain. The finding is meaningfully distinct from H002 (which concerns direct winner manipulation) because H017 concerns fee destination manipulation, an attack vector H002 does not address.

## Hypothesis Investigated

> If `update_config` and `settle_match` are composed in the same transaction, the config read by `settle_match` sees the updated state. An attacker could change treasury/ops in the same TX as settlement, redirecting fees for one match, then optionally restore config in a third instruction.
>
> 1. Can update_config and settle_match be in the same TX? (Both use config as writable account)
> 2. In Solana, do later instructions in a TX see prior instructions' state changes?
> 3. Could an attacker: [update_config(new_treasury=attacker)] → [settle_match] → [update_config(restore_treasury)] in one TX?
> 4. Is this meaningfully different from H002 (which already requires authority compromise)?

## Investigation Path

### Step 1: Account mutability in each instruction

**Location:** `lib.rs:464-475` (UpdateConfig), `lib.rs:558-610` (SettleMatch)

**Finding:** `UpdateConfig` declares `config` as `mut`. `SettleMatch` declares `config` as read-only (no `mut`). Both share the same PDA (`seeds = [GlobalConfig::SEED]`). The question is whether a non-`mut` load in instruction N+1 sees writes made by instruction N.

**Evidence:**
```rust
// UpdateConfig — config is mut
#[derive(Accounts)]
pub struct UpdateConfig<'info> {
    #[account(
        mut,
        seeds = [GlobalConfig::SEED],
        bump = config.bump,
        has_one = authority @ EscrowError::Unauthorized,
    )]
    pub config: Account<'info, GlobalConfig>,
    pub authority: Signer<'info>,
}

// SettleMatch — config is NOT mut (read-only)
#[account(
    seeds = [GlobalConfig::SEED],
    bump = config.bump,
    has_one = authority @ EscrowError::Unauthorized,
    constraint = !config.is_paused @ EscrowError::ProgramPaused,
)]
pub config: Account<'info, GlobalConfig>,
```

### Step 2: Solana intra-transaction account state visibility

**Finding:** Within a single Solana transaction, all instructions share the same account data. When instruction N writes to an account, the modified data is visible to instruction N+1 in the same transaction. This is a fundamental property of how the Solana runtime processes transactions: accounts are loaded once, instructions execute sequentially against the shared state, and writes are committed atomically at transaction end. The `mut` / non-`mut` distinction in Anchor only controls whether the Anchor framework will call `exit()` on the account (writing it back to the account's data) at the end of that instruction; it does NOT prevent a later instruction from reading the updated bytes.

This is confirmed by Solana's documented account model: the same account key appearing in multiple instructions in a transaction refers to the same underlying memory in the Sealevel execution environment.

**Impact:** If `update_config` executes in instruction 1 and `settle_match` executes in instruction 2 of the same TX, `settle_match` will see the config state written by `update_config`. Specifically, `config.treasury` and `config.ops` as read by `settle_match`'s account constraints (lines 587, 596) will reflect whatever `update_config` wrote, not the pre-TX values.

### Step 3: Authority requirement for update_config

**Location:** `lib.rs:464-475`

**Finding:** `update_config` requires the current `config.authority` as a signer via `has_one = authority`. The instruction checks `ctx.accounts.authority` is a signer AND matches `config.authority`. Without the authority private key, this instruction will fail at the Anchor validation layer before the handler body executes.

**Evidence:**
```rust
#[account(
    mut,
    seeds = [GlobalConfig::SEED],
    bump = config.bump,
    has_one = authority @ EscrowError::Unauthorized,
)]
pub config: Account<'info, GlobalConfig>,

pub authority: Signer<'info>,
```

The `has_one = authority` constraint expands to: `require!(config.authority == ctx.accounts.authority.key())`. Since `authority` is also declared as `Signer<'info>`, the transaction must include a valid signature from `config.authority`. This is enforced before any instruction body runs.

### Step 4: Authority requirement for settle_match

**Location:** `lib.rs:558-610`

**Finding:** `settle_match` has TWO `has_one = authority` constraints: one on `escrow` (line 565) and one on `config` (line 604). The one on `escrow` checks `ctx.accounts.authority == escrow.authority` (where `escrow.authority` was baked in at match creation, line 133). The one on `config` checks `ctx.accounts.authority == config.authority`.

**Critical observation:** Both constraints reference the same `ctx.accounts.authority` signer account. After `update_config` runs in instruction 1 and sets `config.authority = attacker_key`, a subsequent `settle_match` in instruction 2 would fail the `has_one = authority` constraint on the `config` account (line 604) unless the TX is signed by the new `config.authority` (attacker key). But it would also fail the `has_one = authority` constraint on the `escrow` account (line 565) because `escrow.authority` was set to the ORIGINAL authority key at match creation.

**Evidence:**
```rust
// SettleMatch escrow constraint (line 561-568)
#[account(
    mut,
    seeds = [b"match", escrow.match_id.as_bytes()],
    bump = escrow.bump,
    has_one = authority,   // checks escrow.authority == ctx.accounts.authority
    close = authority,
)]
pub escrow: Account<'info, MatchEscrow>,

// SettleMatch config constraint (line 601-607)
#[account(
    seeds = [GlobalConfig::SEED],
    bump = config.bump,
    has_one = authority @ EscrowError::Unauthorized,  // checks config.authority == ctx.accounts.authority
    constraint = !config.is_paused @ EscrowError::ProgramPaused,
)]
pub config: Account<'info, GlobalConfig>,
```

```rust
// create_match stores the authority at match creation time (line 133)
escrow.authority = ctx.accounts.authority.key();
```

### Step 5: Fee destination constraints in settle_match

**Location:** `lib.rs:585-597`

**Finding:** `settle_match` validates that `treasury` and `ops` accounts match `config.treasury` and `config.ops` at constraint-evaluation time. Because constraints are evaluated AFTER instruction N's account mutations are visible, if instruction N (`update_config`) changed `config.treasury` to `attacker_treasury`, then `settle_match`'s constraint `treasury.key() == config.treasury` would accept `attacker_treasury` as the treasury account.

**Evidence:**
```rust
/// Treasury: validated against config PDA (OC-03)
#[account(
    mut,
    constraint = treasury.key() == config.treasury @ EscrowError::InvalidTreasury,
    constraint = treasury.key() != ops.key() @ EscrowError::DuplicateFeeAccount,
)]
pub treasury: UncheckedAccount<'info>,

/// Ops: validated against config PDA (OC-03)
#[account(
    mut,
    constraint = ops.key() == config.ops @ EscrowError::InvalidOps,
)]
pub ops: UncheckedAccount<'info>,
```

This is the core of the attack: the fee destination constraints are validated dynamically against the config state, not against the config state at match creation time. If the config is mutated before `settle_match` runs, the mutated values propagate to fee routing.

### Step 6: The self-defeating constraint in SettleMatch — authority conflict

**Finding (CRITICAL):** There is a structural conflict that partially defeats the attack. The scenario requires:

- Instruction 1: `update_config(new_authority = attacker_key_OR_keep_original, new_treasury = attacker_treasury, new_ops = attacker_ops)` — signed by `original_authority`
- Instruction 2: `settle_match(winner=...)` — must be signed by an authority that satisfies BOTH `escrow.has_one = authority` AND `config.has_one = authority`

After instruction 1 runs:
- If `new_authority` was NOT changed: `config.authority` is still `original_authority`. The TX signer for instruction 2 can remain `original_authority`, and both `has_one` checks pass. **This variant of the attack WORKS.**
- If `new_authority` WAS changed to `attacker_key`: `config.authority` is now `attacker_key`, but `escrow.authority` is still `original_authority`. The TX must be signed by an account that satisfies both `escrow.authority == authority` AND `config.authority == authority`, but these are now different keys. **This variant FAILS** (both constraints reference the same `ctx.accounts.authority`).

**Therefore, the viable attack path is: update_config(keep authority, change treasury+ops only) → settle_match → optionally update_config(restore treasury+ops).**

## Invariant Analysis

### Target Invariant

The fee destination invariant: "Settlement fees (treasury 7%, ops 3%) always flow to the protocol-controlled treasury and ops wallets as configured in GlobalConfig, not to attacker-controlled accounts."

### Enforcement Points

| Location | What It Enforces | Complete? |
|----------|-----------------|-----------|
| `lib.rs:587` | `treasury.key() == config.treasury` | Yes — but validates against RUNTIME config, not match-creation config |
| `lib.rs:596` | `ops.key() == config.ops` | Yes — same issue, validates against RUNTIME config |
| `lib.rs:53-55` | Distinctness at initialization | Yes — but NOT re-enforced in update_config |
| `lib.rs:470` | `has_one = authority` on UpdateConfig | Yes — blocks unauthorized config mutation |

### Enforcement Gap Assessment

The invariant is enforced against the config state at the moment `settle_match`'s account constraints are evaluated, not against the config state at match creation. There is no snapshot mechanism that records the treasury/ops destinations at match creation and validates against those. This creates the gap: if the config is mutated (by the authority, in the same TX) before `settle_match` runs, the fee routing follows the mutated config.

The gap is only exploitable if the attacker controls the authority key, because `update_config` requires an authority signature. The invariant is therefore enforced against unauthorized parties but not against a malicious or compromised authority.

## Blocking Factors

- **Authority signature required for update_config**: `lib.rs:470-474` — `has_one = authority` + `Signer<'info>` means `update_config` CANNOT be called without the authority private key. An external attacker with no access to the key is fully blocked.
- **Authority cannot change itself and then settle**: `lib.rs:565` + `lib.rs:604` — if `update_config` changes `config.authority`, a subsequent `settle_match` in the same TX would fail because `escrow.authority` (set at match creation) no longer matches `config.authority`. The attacker cannot change authority AND settle in one TX.
- **Anchor account discriminators prevent fake config**: The config PDA is uniquely derived at `[b"config"]`. Passing a fake config account would fail the seeds/bump check at `lib.rs:603`.
- **Solana transaction atomicity**: If any instruction fails, all state changes revert. The attacker cannot leave the config in a partially mutated state if the settlement fails.

## Enabling Factors

- **No config snapshot at match creation**: `lib.rs:131-142` — `create_match` does not record treasury/ops from config into the escrow account. Settlement reads treasury/ops live from config at settlement time.
- **Solana intra-TX state sharing**: State written by instruction N is visible to instruction N+1 in the same transaction. There is no isolation mechanism between instructions.
- **update_config has no distinctness re-validation**: `lib.rs:70-88` — the handler applies changes without validating that treasury != ops != authority post-change.
- **Fee destination accounts are UncheckedAccount**: `lib.rs:581, 590, 597` — treasury and ops are `UncheckedAccount<'info>`, validated only via constraint expressions against the (potentially-mutated) config.

## Exploitation Scenario

### Prerequisites
1. Attacker has compromised or is the authority private key (necessary to sign `update_config`)
2. At least one Active match exists with a valid settlement window (within 1 hour of activation)
3. Attacker controls two wallet addresses (`attacker_treasury`, `attacker_ops`) to receive fees

### Attack Steps
1. Attacker constructs a transaction with three instructions:
   - Instruction 1: `update_config(new_treasury = attacker_treasury, new_ops = attacker_ops, new_authority = None)` — signed by authority
   - Instruction 2: `settle_match(winner = player_A)` with accounts `treasury = attacker_treasury`, `ops = attacker_ops` — signed by authority
   - Instruction 3: `update_config(new_treasury = real_treasury, new_ops = real_ops, new_authority = None)` — signed by authority (optional, restores config to avoid detection)
2. Transaction is submitted to the Solana network
3. Instruction 1 mutates `config.treasury = attacker_treasury` and `config.ops = attacker_ops`
4. Instruction 2 reads the mutated config; constraints at lines 587 and 596 evaluate `attacker_treasury == config.treasury` (now true) and `attacker_ops == config.ops` (now true); settlement executes, sending 7% + 3% of pot to attacker
5. Instruction 3 restores config to original values
6. Transaction commits; config appears unchanged to any observer checking after-state; attacker has received 10% of the pot

### Impact
- At max wager (100 SOL per player): 200 SOL pot × 10% = 20 SOL per match
- At typical wager: scales linearly with wager amount
- Config restore in instruction 3 makes the attack forensically invisible unless someone observes the mid-transaction state (via transaction logs / event inspection)
- The `MatchSettled` event (line 294-302) DOES include `treasury_account` and `ops_account` pubkeys, which would reveal attacker addresses in on-chain logs — monitoring this event would detect the attack

### Recommended Fix

**Primary fix — Snapshot treasury/ops at match creation:**

Record treasury and ops destinations in the escrow account at `create_match` time and validate against those stored values in `settle_match`, removing the dependency on live config state for fee routing:

```rust
// In MatchEscrow struct — add snapshot fields
pub treasury_at_creation: Pubkey,
pub ops_at_creation: Pubkey,

// In create_match handler
escrow.treasury_at_creation = ctx.accounts.config.treasury;
escrow.ops_at_creation = ctx.accounts.config.ops;

// In SettleMatch account constraints — validate against stored snapshots
#[account(
    mut,
    constraint = treasury.key() == escrow.treasury_at_creation @ EscrowError::InvalidTreasury,
    constraint = treasury.key() != ops.key() @ EscrowError::DuplicateFeeAccount,
)]
pub treasury: UncheckedAccount<'info>,

#[account(
    mut,
    constraint = ops.key() == escrow.ops_at_creation @ EscrowError::InvalidOps,
)]
pub ops: UncheckedAccount<'info>,
```

This eliminates the intra-TX mutation vector entirely: even with the authority key, the fee destinations are locked to what they were when the match was created.

**Secondary fix — Timelock on update_config:**

Adding a 24-hour timelock on config changes (propose + execute pattern) would prevent same-TX mutation regardless of implementation approach. This also addresses H002 and other authority-compromise scenarios.

## Differentiation from H002

H017 is meaningfully distinct from H002. H002 concerns winner manipulation — the authority selecting the wrong player as winner to redirect the 90% winner portion. H017 concerns fee destination manipulation — redirecting the 7% treasury and 3% ops fees to attacker-controlled accounts rather than the legitimate protocol wallets. The attack surfaces are different:

- H002: attacker changes WHICH PLAYER receives the 90% winner share
- H017: attacker changes WHERE the 10% fee portion flows

The combination of H002 + H017 in the same transaction (with authority key compromise) would allow an attacker to redirect 100% of the pot. H002 + H017 are complementary, not overlapping. However, both require the same precondition (authority key compromise), so they are co-exploitable but independently categorized.

If the attack is performed with instruction 3 (config restore), the event will still record the attacker addresses. This is a detection mechanism, but only if an off-chain monitor parses these events. Suggested new hypothesis: **H_EVENT_MONITORING** — Does the protocol have or plan to have off-chain monitoring of MatchSettled events? If not, the only forensic trace of this attack is the event log, which requires active polling.

- **create_match does not verify config accounts**: At `lib.rs:110-152`, `create_match` loads `config` only for the pause guard (line 527) and uses `authority` from the signer (not from `config.authority`, since `CreateMatch` lacks `has_one = authority`). This means any signer can call `create_match`, and the resulting escrow's `escrow.authority` will be whatever signer called it. If a non-authority creates a match, `escrow.authority != config.authority`, and `settle_match` would fail because it requires BOTH `escrow.has_one = authority` AND `config.has_one = authority` with the same key. Already noted in `ARCHITECTURE.md`; no new hypothesis needed.

## Raw Investigation Notes

### Account Mutability Matrix for H017 Scenario

| Account | UpdateConfig | SettleMatch | Notes |
|---------|-------------|-------------|-------|
| config PDA | MUT (writes treasury/ops) | IMMUTABLE (reads treasury/ops) | Same account; instruction 1 writes are visible to instruction 2 |
| authority | Signer | Signer (must match BOTH escrow.authority AND config.authority) | Single key must satisfy both constraints |
| treasury | — | UncheckedAccount (mut) | Validated against runtime config.treasury |
| ops | — | UncheckedAccount (mut) | Validated against runtime config.ops |

### Why authority cannot be changed mid-TX and still settle

`SettleMatch` has TWO `has_one = authority` constraints (lines 565 and 604), both resolving against the SAME `ctx.accounts.authority` key:
- `escrow.authority` — set at match creation (lib.rs:133), baked into escrow account data, NOT readable from config
- `config.authority` — live from config PDA

If instruction 1 changes `config.authority` from `ORIG` to `NEW`, then in instruction 2:
- `config.has_one = authority` requires authority == `NEW` (post-mutation)
- `escrow.has_one = authority` requires authority == `ORIG` (baked in at creation)

Since `ORIG != NEW`, no single key can satisfy both constraints simultaneously. Therefore, the attack cannot change the authority and then immediately settle — the authority must remain unchanged through the settlement.

### Viable attack signature: treasury+ops only, authority unchanged

The only viable same-TX sequence is:
1. `update_config(treasury=X, ops=Y, authority=None)` — authority unchanged
2. `settle_match(...)` with X as treasury, Y as ops accounts
3. (optional) `update_config(treasury=ORIG_T, ops=ORIG_O, authority=None)` — restore

This is the canonical H017 exploit path. It requires the authority key and redirects only the 10% fee portion per match.

### Detection via on-chain events

`MatchSettled` (lib.rs:789-799) includes:
```rust
pub treasury_account: Pubkey,
pub ops_account: Pubkey,
```

Any off-chain monitor that compares these emitted values against the expected protocol treasury/ops addresses would immediately detect the mismatch. This is an existing detection mechanism noted in OC-11 (line 293 comment). The attack is covert only if no such monitoring exists or is bypassed.
