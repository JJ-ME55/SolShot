# H020: Clock Drift Exploitation at Settlement Deadline

**Status:** RESOLVED (No Vulnerability)
**Severity:** Tier 3
**Precedent:** EP-089 (Clock Drift in Solana)

---

## Hypothesis

Solana Clock::get() has 1-2 second drift per Solana documentation. At the exact settlement deadline (activated_at + 3600 seconds), clock drift might affect settlement eligibility.

---

## Investigation

### Settlement Deadline Check (lib.rs:236-243)

```rust
if ctx.accounts.escrow.activated_at > 0 {
    let deadline = ctx.accounts.escrow.activated_at
        .checked_add(SETTLEMENT_TIMEOUT_SECONDS)  // SETTLEMENT_TIMEOUT_SECONDS = 3600
        .ok_or(EscrowError::ArithmeticOverflow)?;
    require!(
        Clock::get()?.unix_timestamp <= deadline,  // ← INCLUSIVE UPPER BOUND
        EscrowError::SettlementExpired
    );
}
```

**Key observations:**
- Uses `<=` (inclusive) comparison — settlement allowed up to and including the deadline second
- Deadline is a fixed offset: `activated_at + 3600`
- Clock::get() reads directly from sysvar (cannot be injected, immune to EP-006)

### Clock Drift vs. Window Size

| Factor | Value | Notes |
|--------|-------|-------|
| Settlement window | 3600 seconds (1 hour) | From OC-07 constant |
| Clock drift | 1-2 seconds (documented) | Per Solana runtime docs |
| Drift as % of window | 0.028–0.056% | Negligible |
| Comparison operator | `<=` | Inclusive; 1-second grace built-in |

### Edge-Case Analysis

**Scenario:** Settlement attempt exactly at deadline (t = activated_at + 3600)

| Actual Time | Observed Clock | Deadline Check | Outcome |
|-------------|---|---|---|
| t=3599 (1s early) | t=3598 to t=3600 | 3598 ≤ 3600? YES | **SETTLES** (correct) |
| t=3600 (at deadline) | t=3599 to t=3601 | 3599 ≤ 3600? YES | **SETTLES** (correct) |
| t=3601 (1s late) | t=3600 to t=3602 | 3600 ≤ 3600? YES | **SETTLES** (acceptable: `<=` allows +1s grace) |
| t=3602 (2s late) | t=3601 to t=3603 | 3601 ≤ 3600? NO | **REJECTED** (correct) |

**Conclusion:** Even at the extreme edge, drift cannot enable settlement > 2 seconds beyond the deadline.

---

## Findings

1. **Immaterial deviation:** 1-2 seconds of drift on a 3600-second window is 0.056% — well within tolerance for a hard deadline that is explicitly a social contract, not a security boundary.

2. **Inclusive comparison aids fairness:** The `<=` operator naturally provides a 1-second grace period for transactions observed at exactly the deadline second.

3. **No timestamp injection:** All 5 Clock accesses use `Clock::get()?` (sysvar API), not an injected account, eliminating sysvar manipulation entirely.

4. **Backward-compat guard redundant:** Line 236 checks `activated_at > 0` as a safety net for pre-OC-07 matches, but this guard is unreachable (activated_at is ALWAYS set during Active transition at line 209). Harmless.

---

## Recommendation

**None.** The settlement deadline check is sound. Clock drift is immaterial for the 1-hour window. No code changes required.
