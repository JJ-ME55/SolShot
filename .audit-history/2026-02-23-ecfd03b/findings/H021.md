# H021: Permissionless Reclaim During Active Pause

**Severity:** TIER 3 (INFO)
**Status:** CONFIRMED AS INTENDED
**Reviewed:** 2026-02-23

---

## Hypothesis
**permissionless_reclaim has no pause guard. During pause, funds flow out via this path. Is this intentional (DCA-02 escape hatch) or exploitable?**

---

## Investigation Findings

### Q1: Does PermissionlessReclaim struct include config account?
**ANSWER: NO** — The account struct at lines 654-681 includes:
- `escrow` (MatchEscrow PDA)
- `caller` (Signer)
- `player_one` (UncheckedAccount)
- `player_two` (UncheckedAccount)

The config PDA is **intentionally omitted**. No `#[account(... has_one = authority ...)]` constraint. No config account passed to the function.

### Q2: Is the lack of pause guard documented as intentional?
**ANSWER: YES** — Multiple documentation layers confirm:
1. **lib.rs line 378-380:** Comment explicitly states:
   > "DCA-02: Permissionless reclaim — anyone can trigger refund after 48 hours. Separate from cancel_match (which requires authority or player)."
2. **ARCHITECTURE.md line 181:** Table documents `is_paused` NOT checked by `permissionless_reclaim` **(by design)**
3. **08-timing-ordering.md line 19-20:** Identifies pause as griefing vector, notes `permissionless_reclaim` intentionally has NO pause guard (escape hatch)

### Q3: Can this be exploited to extract funds faster than intended?
**ANSWER: NO** — The 48-hour timeout is hardcoded and **non-bypassable**:
- Line 405: `timeout_reference.checked_add(PERMISSIONLESS_RECLAIM_TIMEOUT)` (172800 seconds)
- Line 408-410: `require!(Clock::get()?.unix_timestamp > reclaim_deadline, ...)`
- No signer requirement can waive the deadline
- Caller cannot influence `activated_at` or `created_at` (both immutable after set)

**Exploitation scenario:** Authority pauses program → Player cannot cancel (blocked by pause guard at line 644) → **But** player can wait 48h and call `permissionless_reclaim` (no pause guard) → funds released.

This is **intentional safeguard**, not a vulnerability. Without it, pause could permanently lock funds.

---

## Conclusion
**NOT EXPLOITABLE. INTENTIONAL DESIGN.**

The absence of pause guard on `permissionless_reclaim` is a documented escape hatch (DCA-02) ensuring funds can never be permanently stuck, even if authority is compromised or pauses program. The 48-hour window provides sufficient delay for legitimate pause operations while guaranteeing eventual recovery.

**Risk Level:** NONE
