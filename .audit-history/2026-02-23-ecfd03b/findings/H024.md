# H024: Settlement Deadline Bypass via activated_at Path

**Hypothesis:** The settlement check uses `if activated_at > 0`. If there's a path to Active without activated_at being set, the deadline check is skipped.

**Status:** CONFIRMED SAFE | Tier 4 (Defense-in-Depth)

---

## Investigation

### 1. Settlement Deadline Check
**Location:** `lib.rs:234–244`

```rust
if ctx.accounts.escrow.activated_at > 0 {
    let deadline = ctx.accounts.escrow.activated_at
        .checked_add(SETTLEMENT_TIMEOUT_SECONDS)
        .ok_or(EscrowError::ArithmeticOverflow)?;
    require!(
        Clock::get()?.unix_timestamp <= deadline,
        EscrowError::SettlementExpired
    );
}
```

The guard checks `if activated_at > 0` before enforcing the settlement deadline.

### 2. All Paths to MatchState::Active
**State Machine Scan:**

Only ONE path transitions to Active:
- **deposit_wager** (lines 205–220)
  - Requires: `state == AwaitingDeposits` (line 164)
  - Transition: Both players deposit → sets `state = Active` (line 207)
  - **Atomic with activated_at assignment** (line 209)

Code flow:
```rust
if escrow.player_one_deposited && escrow.player_two_deposited {
    escrow.state = MatchState::Active;
    escrow.activated_at = Clock::get()?.unix_timestamp;  // ← Always set
    emit!(MatchActive { ... });
}
```

### 3. Bypass Feasibility

**Question:** Can a match reach Active without activated_at being set?

**Answer:** No. Proof:
- At creation (line 141): `activated_at = 0`
- Only transition to Active is in deposit_wager (line 207)
- deposit_wager **always** sets `activated_at = Clock::get()?.unix_timestamp` on line 209
- No other code path modifies state to Active
- Therefore: All Active matches have `activated_at > 0`

The guard condition is always **true** at runtime.

---

## Finding

**Exploit Possible?** No.

The deadline check is correctly implemented. The guard `if activated_at > 0` is **defensive programming for backward compatibility**, not a vulnerability:

- **Pre-OC-07 (old deployment):** hypothetically could have had code that reached Active without setting activated_at
- **Current version (OC-07+):** impossible—activated_at is set atomically with the state transition
- **Consequence:** Even if an old match somehow existed with `state=Active && activated_at=0`, the guard would skip the deadline (but no such match can exist in new code)

This is **intentional defensive design**, not an exploit path.

---

## Recommendation

**None.** The code is sound. The guard demonstrates good engineering: anticipating edge cases and protecting against them defensively.

Consider documenting the backward-compatibility intent in a code comment for future auditors.
