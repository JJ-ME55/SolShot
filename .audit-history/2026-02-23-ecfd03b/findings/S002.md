## Executive Summary

This finding confirms a two-step chain attack that combines two independently confirmed vulnerabilities (H003 and H007) into a compounded griefing scenario delivering the maximum possible fund lockup under the protocol's design.

**Step 1 (H003 building block):** The authority calls `update_config` to set `config.treasury == config.ops`. This poisons the config so that `settle_match` becomes permanently unsatisfiable — the `DuplicateFeeAccount` constraint at `lib.rs:588` fires unconditionally when both fee destinations are the same address. All Active matches are immediately unable to be settled.

**Step 2 (H007 building block):** The authority calls `pause_program`. This sets `config.is_paused = true`, which blocks `cancel_match` via the Anchor constraint at `lib.rs:644`. Now even player-initiated 24-hour timeout cancellation is unavailable.

**Combined result:** With settlement impossible (poisoned config) and cancellation blocked (pause), the **only remaining exit for deposited funds is `permissionless_reclaim` after 48 hours from `activated_at`**. This is the maximum lockup the protocol can deliver. Neither step is redundant — Step 1 eliminates settlement even if the pause is later lifted; Step 2 eliminates the 24-hour player escape that would otherwise survive the config poison alone.

The chain requires a single authority key (either legitimately compromised or a rogue insider) and executes in two transactions. No funds are permanently lost — `permissionless_reclaim` is not blocked by either attack component — but maximum temporal fund denial is achieved.

> A compromised authority can execute a two-step griefing attack: (1) set treasury == ops via update_config to break all settlement, then (2) pause the program. Now neither settle (broken by distinctness) nor cancel (blocked by pause) work. Only permissionless_reclaim after 48h remains as escape. Maximum fund lockup.

## Investigation Path

### Step 1: Verify TX0 — Does update_config accept treasury == ops?

**Location:** `lib.rs:70-89`

**Finding:** Confirmed. The function applies any `Option<Pubkey>` values with zero distinctness validation. There is no `require!` that prevents `new_treasury == new_ops`.

**Evidence:**
```rust
pub fn update_config(
    ctx: Context<UpdateConfig>,
    new_authority: Option<Pubkey>,
    new_treasury: Option<Pubkey>,
    new_ops: Option<Pubkey>,
) -> Result<()> {
    let config = &mut ctx.accounts.config;

    if let Some(a) = new_authority {
        config.authority = a;
    }
    if let Some(t) = new_treasury {
        config.treasury = t;
    }
    if let Some(o) = new_ops {
        config.ops = o;
    }

    Ok(())
}
```

Contrast with `initialize_config` at `lib.rs:53-55`, which explicitly enforces:
```rust
require!(authority != treasury, EscrowError::InvalidConfig);
require!(authority != ops, EscrowError::InvalidConfig);
require!(treasury != ops, EscrowError::DuplicateFeeAccount);
```

The invariant established at initialization is never re-enforced on updates. The `UpdateConfig` account struct at `lib.rs:465-475` only validates `has_one = authority` — it does not prevent poisoning.

**Chain step status: EXECUTABLE** — TX0 will succeed with `new_treasury = Some(X), new_ops = Some(X)`.

### Step 2: Verify that poisoned config unconditionally blocks settle_match

**Location:** `lib.rs:583-598` (SettleMatch account struct), `lib.rs:228-305` (handler)

**Finding:** Confirmed. When `config.treasury == config.ops == X`, any call to `settle_match` must simultaneously satisfy:
- `treasury.key() == config.treasury` (line 587) → caller must pass X as treasury
- `ops.key() == config.ops` (line 596) → caller must pass X as ops
- `treasury.key() != ops.key()` (line 588) → X != X → unconditionally FALSE

This is a logical contradiction with no valid resolution. Settlement is permanently impossible until the config is repaired.

**Evidence:**
```rust
/// Treasury: validated against config PDA (OC-03 — resolves H001, H003, S001, GAP-003, H048)
/// CHECK: Constrained to config.treasury; uniqueness check vs ops
#[account(
    mut,
    constraint = treasury.key() == config.treasury @ EscrowError::InvalidTreasury,
    constraint = treasury.key() != ops.key() @ EscrowError::DuplicateFeeAccount,
)]
pub treasury: UncheckedAccount<'info>,

/// Ops: validated against config PDA (OC-03)
/// CHECK: Constrained to config.ops
#[account(
    mut,
    constraint = ops.key() == config.ops @ EscrowError::InvalidOps,
)]
pub ops: UncheckedAccount<'info>,
```

All three cases exhaustively fail (see Raw Notes). The constraint evaluation fires at Anchor's account deserialization layer, before the instruction body at line 228 is ever reached.

**Chain step status: BLOCKER CONFIRMED** — settle_match is dead after TX0.

### Step 3: Verify TX1 — Does pause_program succeed regardless of config poison?

**Location:** `lib.rs:93-95` (handler), `lib.rs:480-490` (PauseProgram account struct)

**Finding:** Confirmed. The `PauseProgram` struct requires only:
- `config` with `has_one = authority` (line 485)
- `authority: Signer<'info>` (line 489)

There is no constraint that prevents calling `pause_program` when `config.treasury == config.ops`. The pause flag is entirely independent of the fee address configuration. TX1 succeeds unconditionally after TX0.

**Evidence:**
```rust
pub fn pause_program(ctx: Context<PauseProgram>) -> Result<()> {
    ctx.accounts.config.is_paused = true;
    Ok(())
}

pub struct PauseProgram<'info> {
    #[account(
        mut,
        seeds = [GlobalConfig::SEED],
        bump = config.bump,
        has_one = authority @ EscrowError::Unauthorized,

    pub config: Account<'info, GlobalConfig>,

    pub authority: Signer<'info>,
}
```

**Chain step status: EXECUTABLE** — TX1 will succeed.

### Step 4: Verify pause blocks cancel_match

**Location:** `lib.rs:640-646` (CancelMatch account struct)

**Finding:** Confirmed. The `CancelMatch` struct includes the config account with an explicit pause guard:

```rust
/// Config PDA — provides authority pubkey + pause guard (OC-04, OC-05)
#[account(
    seeds = [GlobalConfig::SEED],
    bump = config.bump,
    constraint = !config.is_paused @ EscrowError::ProgramPaused,
)]
pub config: Account<'info, GlobalConfig>,
```

When `config.is_paused == true`, every `cancel_match` call fails at Anchor constraint evaluation time with `EscrowError::ProgramPaused`. Players cannot cancel even after 24 hours from activation — the timeout check at `lib.rs:333` is never reached because the Anchor constraint fires first (the config account is deserialized before the handler body runs).

**Chain step status: BLOCKER CONFIRMED** — cancel_match is dead after TX1.

### Step 5: Verify permissionless_reclaim is NOT affected by either TX0 or TX1

**Location:** `lib.rs:651-681` (PermissionlessReclaim account struct), `lib.rs:381-438` (handler)

**Finding:** Confirmed. The `PermissionlessReclaim` struct contains:
- `escrow` (with PDA constraint)
- `caller: Signer<'info>`
- `player_one` and `player_two` (validated against escrow fields)
- `system_program`

**There is no `config` account.** The pause flag lives exclusively in `config.is_paused`. Without loading the config account, the pause cannot be enforced. Similarly, the distinctness check at `lib.rs:588` is in the `SettleMatch` struct, not in `PermissionlessReclaim`. The reclaim instruction is completely unaffected by both TX0 and TX1.

```rust
#[derive(Accounts)]
pub struct PermissionlessReclaim<'info> {
    #[account(
        mut,
        seeds = [b"match", escrow.match_id.as_bytes()],
        bump = escrow.bump,
        close = caller,
    )]
    pub escrow: Account<'info, MatchEscrow>,

    #[account(mut)]
    pub caller: Signer<'info>,

    // player_one, player_two, system_program only
    // NO config account — pause cannot be checked, distinctness irrelevant
    pub system_program: Program<'info, System>,
}
```

The reclaim is time-gated at 48h from `activated_at` (or `created_at` if never activated). This is the only remaining escape path after the double lock is applied.

**Chain step status: ESCAPE HATCH CONFIRMED ACTIVE** — 48h lockup is the hard cap.

### Step 6: Assess whether the two steps are redundant or additive

**Finding:** The two steps are strictly additive — neither provides complete lockup alone.

**If only TX0 (config poison, no pause):**
- `settle_match`: Blocked (DuplicateFeeAccount)
- `cancel_match`: **Still available** — after 24h, players can call `cancel_match` to recover funds
- `permissionless_reclaim`: Available after 48h
- **Maximum lockup: 24 hours** (until player cancel window opens)

**If only TX1 (pause, no config poison):**
- `settle_match`: Blocked (ProgramPaused)
- `cancel_match`: Blocked (ProgramPaused)
- `permissionless_reclaim`: Available after 48h
- **Maximum lockup: 48 hours** (if attacker also locks out unpause via authority rotation per H007)

**If TX0 + TX1 (both applied):**
- `settle_match`: Blocked (DuplicateFeeAccount — fires even if pause is later lifted)
- `cancel_match`: Blocked (ProgramPaused)
- `permissionless_reclaim`: Available after 48h
- **Maximum lockup: 48 hours**
- **Additional concern: settlement permanently disabled** — even if the pause is lifted (by authority key recovery), settlement is STILL blocked because the config poison remains. The attacker achieves both: maximum temporal lockup AND permanent settlement denial until config is also repaired.

The compounding effect is: TX1 alone achieves 48h lockup, but if the authority is later recovered and `unpause_program` is called, settle could theoretically resume. TX0 ensures that even a successful recovery of the authority key and unpausing does not restore settlement — the config must also be fixed.

**Chain step status: CONFIRMED ADDITIVE** — combination is worse than either individual attack.

---

### Step 7: Assess atomic execution risk

**Finding:** TX0 and TX1 can be sent as two separate transactions or combined into a single transaction with multiple instruction calls. Solana supports multiple instructions per transaction. An attacker can atomically execute:

1. Instruction 1: `update_config(new_treasury=X, new_ops=X)` — poisons config
2. Instruction 2: `pause_program` — locks cancel

Both instructions use the same `config` account and the same `authority` signer. They can be batched in a single atomic transaction, providing zero opportunity for the legitimate team to detect TX0 and respond before TX1 lands.

Furthermore, per H007's analysis, the attacker can optionally extend the attack with:

3. Instruction 3 (optional): `update_config(new_authority=dead_key)` — permanently locks out governance

This third instruction would be executed AFTER `pause_program` because at that point `config.authority` is still the original key. After instruction 3, the legitimate team cannot call `unpause_program` or fix the config — both require `has_one = authority`.

**Chain step status: SINGLE ATOMIC TRANSACTION POSSIBLE** — three instructions, one TX, no detection window.

## Invariant Analysis

### Target Invariant

"Player funds in Active escrow accounts must be accessible (settleable or cancellable) within a reasonable timeframe, and a compromised authority must not be able to create a state where no exit path exists within the designed safety window."

### Enforcement Points

| Location | What It Enforces | Complete? |
|----------|-----------------|-----------|
| `lib.rs:53-55` (initialize_config) | Distinctness of authority, treasury, ops at init time | Yes — at init only |
| `lib.rs:70-89` (update_config) | Nothing — no re-validation | NO — gap identified |
| `lib.rs:587-588` (SettleMatch constraint) | `treasury != ops` at instruction time | Yes — but creates contradiction when config is poisoned |
| `lib.rs:605` (SettleMatch config constraint) | Pause blocks settlement | Yes |
| `lib.rs:644` (CancelMatch config constraint) | Pause blocks player cancel | Yes |
| `lib.rs:408-411` (permissionless_reclaim) | 48h hard cap on lockup | Yes — not bypassable |
| `lib.rs:653-681` (PermissionlessReclaim struct) | No config required → pause-immune | Yes — by design (DCA-02) |

### Enforcement Gap Assessment

Two distinct gaps combine:

**Gap 1 (H003):** The `treasury != ops` invariant is enforced at initialization (`lib.rs:53-55`) but not at subsequent updates (`lib.rs:70-89`). The `update_config` instruction has no equivalent `require!` checks. One transaction poisons the settlement path permanently.

**Gap 2 (H007):** The pause mechanism correctly blocks `cancel_match` as a protocol safety measure, but this design choice — when combined with Gap 1 — eliminates the only remaining exit path for Active matches until the 48h permissionless reclaim window opens.

The invariant is NOT enforced across the combined attack surface. The two gaps compound: Gap 1 makes settlement impossible, Gap 2 makes player-cancel impossible, and the combination leaves only the 48h reclaim. The reclaim IS correctly implemented as an escape hatch (DCA-02), so funds are not permanently lost — but the maximum fund denial duration the attacker can achieve is the full 48h window.

## Blocking Factors

- **permissionless_reclaim is not blockable:** `lib.rs:653-681` — the escape hatch is not loaded with the config account. Pause cannot reach it. The 48h cap is a genuine hard ceiling on fund lockup. Funds are never permanently lost.
- **Authority is required for both steps:** The attack requires `config.authority` control. An unauthenticated external attacker cannot execute TX0 or TX1.
- **Config is recoverable if authority key is not rotated:** If the legitimate team retains the authority key, they can call `update_config` with distinct treasury/ops AND call `unpause_program`. Both fixes resolve the chain. However, in a key-compromise scenario, the attacker may optionally rotate authority to a dead key in the same atomic transaction, making recovery impossible without a program upgrade.

---

## Enabling Factors

- **Missing re-validation in update_config:** `lib.rs:70-89` — no distinctness checks are applied after the `Option<Pubkey>` fields are set. This is the root cause of the settlement block component.
- **Pause blocks cancel_match:** `lib.rs:644` — the pause guard on cancel is intentional for protocol safety, but becomes a griefing vector when combined with config poisoning.
- **Single-key authority with no multisig:** `config.authority` is a single hot wallet Pubkey. No on-chain multisig. Compromise of one key enables the entire chain.
- **No timelock on config changes or pause:** Both `update_config` and `pause_program` take effect in the same block they are called. No delay for detection or response.
- **Atomic multi-instruction transactions:** Solana allows batching multiple instructions in one transaction. TX0, TX1, and the optional authority lock-out (instruction 3) can all land atomically with no detection window between steps.
- **No events emitted:** Neither `pause_program` (line 93-95) nor `update_config` (line 70-89) emit events. Off-chain monitoring cannot detect the attack until it independently indexes the transaction. This extends attacker dwell time.

## Exploitation Scenario

### Prerequisites

1. Attacker controls `config.authority` private key (insider threat, hot wallet compromise, phishing, or infrastructure breach).
2. Active matches exist — both players have deposited, match is in `Active` state. The attack has maximum impact when TVL is highest.
3. Program is currently unpaused (`config.is_paused == false`).

### Attack Steps

1. Attacker constructs a single transaction with three instructions (or sends two transactions in rapid succession if atomicity is not required):
   - **Instruction 1:** `update_config(new_treasury = Some(X), new_ops = Some(X))` where X is any pubkey (can be the attacker's wallet, or any address).
   - **Instruction 2:** `pause_program()`.
   - **Instruction 3 (optional hardening):** `update_config(new_authority = Some(dead_key))` where `dead_key` is a pubkey nobody controls, permanently locking out governance recovery.

2. The transaction lands on-chain. In a single slot:
   - `config.treasury == config.ops == X` (distinctness invariant violated)
   - `config.is_paused == true`
   - (optionally) `config.authority` is now `dead_key` — no recovery possible

3. All subsequent calls to `settle_match` on any Active match fail with `EscrowError::DuplicateFeeAccount` at Anchor constraint evaluation time (`lib.rs:588`).

4. All subsequent calls to `cancel_match` fail with `EscrowError::ProgramPaused` at Anchor constraint evaluation time (`lib.rs:644`). This applies even after 24 hours from activation — the timeout threshold is never checked because the pause guard fires first.

5. Players are locked in Active matches with no on-chain recourse until 48 hours from their respective `activated_at` timestamps.

6. After 48h, anyone (including the players themselves) can call `permissionless_reclaim`. Both players receive their exact wager back. The caller receives PDA rent (~0.00146 SOL) as incentive. The match account is closed.

7. Protocol has received no fee revenue for any affected match. Winners received no winnings. Reputational damage to the platform is significant.

### Impact

- **Maximum fund lockup:** All Active matches are inaccessible for up to 48 hours from `activated_at`. For a match activated 1 second before the attack, lockup is the full 48 hours.
- **Settlement permanently denied:** Even if the authority key is recovered and the pause is lifted, `settle_match` remains blocked until `config.treasury != config.ops` is also restored. The config poison persists independently of the pause.
- **Winner payout denial:** Legitimate match winners receive nothing — both players receive equal refunds through the reclaim path.
- **Protocol revenue forfeited:** The 7% treasury and 3% ops fees are not collected for any affected match.
- **Governance destruction (if instruction 3 executed):** If authority is rotated to a dead key, the protocol cannot accept new matches, settle matches, update config, or unpause — ever. Only a program upgrade can recover. All future deposits are permanently blocked.
- **No permanent fund loss for existing deposits:** `permissionless_reclaim` correctly refunds all depositors.

### Proof of Concept Outline

1. **Setup:** Program deployed. `config.authority = SERVER_KEY`, `config.treasury = TREASURY_KEY`, `config.ops = OPS_KEY`, `config.is_paused = false`. Multiple matches in Active state (players deposited).
2. **Attack:** Submit single transaction with instructions: (1) `update_config(new_treasury=ATTACKER_KEY, new_ops=ATTACKER_KEY)`, (2) `pause_program()`, (3, optional) `update_config(new_authority=DEAD_KEY)`.
3. **Verify settlement blocked:** Attempt `settle_match` on any Active match → fails `DuplicateFeeAccount` at constraint `lib.rs:588`.
4. **Verify cancel blocked:** Attempt `cancel_match` (even after 24h from activation) → fails `ProgramPaused` at constraint `lib.rs:644`.
5. **Verify reclaim available after 48h:** Invoke `permissionless_reclaim` after 48h from `activated_at` → succeeds, both players refunded.
6. **Result:** Maximum 48h fund lockup delivered; settlement permanently denied until both config and pause are repaired.

### Recommended Fix

Three independent fixes address the chain at its root causes.

**Fix A — Re-validate distinctness in update_config (closes H003, eliminates TX0):**

```rust
// Before (vulnerable)
pub fn update_config(
    ctx: Context<UpdateConfig>,
    new_authority: Option<Pubkey>,
    new_treasury: Option<Pubkey>,
    new_ops: Option<Pubkey>,
) -> Result<()> {
    let config = &mut ctx.accounts.config;

    if let Some(a) = new_authority { config.authority = a; }
    if let Some(t) = new_treasury  { config.treasury = t; }
    if let Some(o) = new_ops       { config.ops = o; }

    Ok(())
}

// After (fixed) — re-validate final state after all updates are applied
pub fn update_config(
    ctx: Context<UpdateConfig>,
    new_authority: Option<Pubkey>,
    new_treasury: Option<Pubkey>,
    new_ops: Option<Pubkey>,
) -> Result<()> {
    let config = &mut ctx.accounts.config;

    if let Some(a) = new_authority { config.authority = a; }
    if let Some(t) = new_treasury  { config.treasury = t; }
    if let Some(o) = new_ops       { config.ops = o; }

    // Re-validate distinctness invariant — mirrors initialize_config lines 53-55
    require!(config.authority != config.treasury, EscrowError::InvalidConfig);
    require!(config.authority != config.ops,      EscrowError::InvalidConfig);
    require!(config.treasury  != config.ops,      EscrowError::DuplicateFeeAccount);

    Ok(())
}
```

**Fix B — Remove pause guard from cancel_match (closes H007's lockup component, degrades TX1 from full-lockup to partial-lockup):**

```rust
// Before (vulnerable — pause blocks player cancellation)
```

## Incidental Discoveries

- **update_config is not pause-blocked (by design, but worth noting):** `lib.rs:70-89` — `update_config` can be called even while `config.is_paused == true`. This is intentional (the authority needs to be able to fix config during an emergency). However, this means that if the attacker applies Fix B (pause without config poison), the authority can still call `update_config` to fix the config during a pause. This is actually a positive design choice that partially mitigates the pure H007 attack — it means the authority can respond to a pause by immediately repairing config. The S002 chain avoids this by combining TX0 before TX1, but it's worth noting for incident response planning. → No new hypothesis needed; this is a positive attribute.

- **Three-instruction atomic attack vs. two-transaction attack:** The attacker does NOT need atomicity for maximum impact. TX0 (config poison) alone is sufficient to block settlement forever. TX1 (pause) only adds the cancel block. An attacker who executes TX0 and then delays TX1 by hours still achieves the 48h lockup — the pause starts the cancel block, but the config poison is already in effect from the moment TX0 landed. The compound state is achievable even with detection between the two steps if the team does not fix the config within the 1-hour settlement window for in-flight matches. → Suggested new hypothesis: **"Detection window between TX0 and TX1 — is there a response path for the legitimate team if TX0 lands but TX1 has not yet?"** The answer is yes (call `update_config` to fix config before TX1 lands, then settle in-flight matches within the 1h window), but the window may be too narrow in practice.

- **Config fix after pause is itself blocked-by-pause analysis:** `update_config` is NOT pause-blocked (confirmed above). So even during a pause, the authority can call `update_config` to fix `config.treasury != config.ops`. This means: if the legitimate team retains the authority key and detects TX0+TX1, they CAN call `update_config` to fix the config even while paused, then call `unpause_program`, then settle in-flight matches — IF they still have time within the 1h settlement window. This is a narrow but real recovery path. The optional Instruction 3 (authority rotation) is what closes this path entirely. → No new hypothesis needed; this is recovery planning context.

## Raw Investigation Notes

### Exhaustive constraint failure analysis for settle_match when config.treasury == config.ops == X

**Caller attempts settle_match with accounts: treasury=X, ops=X**
- Constraint `lib.rs:587`: `treasury.key() == config.treasury` → `X == X` → PASS
- Constraint `lib.rs:588`: `treasury.key() != ops.key()` → `X != X` → FAIL (DuplicateFeeAccount)
- **Result: FAILS**

**Caller attempts settle_match with accounts: treasury=X, ops=Y (any other address)**
- Constraint `lib.rs:587`: `treasury.key() == config.treasury` → `X == X` → PASS
- Constraint `lib.rs:588`: `treasury.key() != ops.key()` → `X != Y` → PASS
- Constraint `lib.rs:596`: `ops.key() == config.ops` → `Y == X` → FAIL (InvalidOps)
- **Result: FAILS**

**Caller attempts settle_match with accounts: treasury=Y, ops=X (any other address for treasury)**
- Constraint `lib.rs:587`: `treasury.key() == config.treasury` → `Y == X` → FAIL (InvalidTreasury)
- **Result: FAILS**

All three cases fail. No valid account combination satisfies all three constraints simultaneously when config.treasury == config.ops. The contradiction is exhaustive and unconditional.

### PauseProgram does not check is_paused — relevant ordering note

`pause_program` (lib.rs:93-94) does NOT check `!config.is_paused`. It is idempotent. This means TX1 can be sent even if the program is already paused, which has no relevance for the attack ordering but confirms there is no self-referential protection.

### Confirming update_config requires no co-signer from new treasury/ops addresses

The `UpdateConfig` struct (lib.rs:465-475) only requires:
- `config: Account<'info, GlobalConfig>` with `has_one = authority`
- `authority: Signer<'info>`

The new treasury and ops addresses are pure `Pubkey` instruction arguments. No co-signer or account presence is required for the new fee destinations. The attacker can set `new_treasury` and `new_ops` to any pubkey they choose — including each other — without controlling those addresses.

### Cancel_match pause check ordering relative to timeout check

The Anchor constraint at `lib.rs:644` (`!config.is_paused`) is evaluated at account deserialization time — before any handler code runs. The timeout calculation at `lib.rs:329-333` is inside the handler body. This means the pause guard fires first regardless of how long the match has been running. A player whose match has been Active for 47 hours still cannot call `cancel_match` during a pause, even though the 24h timeout has long passed. The pause effectively resets the player's available exit to 48h reclaim.

### One-instruction variant of the attack

If the attacker only wants settlement DoS (not the full 48h lockup), a single call to `update_config(new_treasury=X, new_ops=X)` is sufficient. Settlement is permanently blocked from that moment until the config is repaired. The pause is additive griefing that extends the lockup from ~24h (player cancel at 24h, which still works without the pause) to 48h (only reclaim path). This shows the attack has a simpler one-TX variant with meaningful impact even without the pause step.
