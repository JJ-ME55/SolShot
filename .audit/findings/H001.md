# Finding: H001 — One-Step Authority Transfer Takeover

## Status: CONFIRMED (STILL_OPEN by design)
## Confidence Score: 10/10

> Confidence scale:
> - **9-10**: Certain — exhaustive code analysis, all paths verified
>
> *This is a recheck of a previously-confirmed finding. Code confirmed unchanged in both v1 and v2. JJ has acknowledged the design choice in `Docs/internal/PRIOR_AUDIT_DELTA.md`.*

---

## Executive Summary

Both `solshot-escrow` (v1, deployed `4kzr...nH1`) and `solshot-escrow-v2` (v2, deployed `BVKX...G7N`) implement authority rotation as a single-transaction, no-confirmation overwrite. `GlobalConfig` in both programs carries no `pending_authority` field; `update_config` sets `config.authority` directly in one step. A hot-wallet compromise gives an attacker immediate, irrecoverable control over: winner selection for all active escrows, treasury/ops fee destinations, and the pause flag — across both programs simultaneously, since both use the same operator wallet (`HPyV...nokv`).

This finding was first confirmed in the 2026-02-23 audit (`H001`, CVSS 8.7). The recheck on 2026-05-07 confirms the code is **structurally unchanged in v1** and **identically absent in v2**. Per `Docs/internal/PRIOR_AUDIT_DELTA.md`, JJ has acknowledged this as an intentional pre-mainnet hot-wallet posture. The finding remains OPEN and is documented here for the audit report.

---

## Hypothesis Investigated

H001 (CRITICAL, CVSS 8.7): No `pending_authority` field, no propose/accept pattern, no timelock. A single `update_config` call by any holder of the current authority private key permanently rotates protocol governance with no confirmation from the new key. Per JJ, intentional pre-mainnet hot-wallet posture.

### Step 2: Confirm absence of `pending_authority` in v2 GlobalConfig
**Location:** `programs/solshot-escrow-v2/src/lib.rs:810-818`
**Finding:** No `pending_authority` field. v2 adds `fee_bps_treasury`/`fee_bps_ops` but no two-step transfer fields.

```rust

    pub fee_bps_ops: u16,
```

### Step 3: Confirm one-step rotation in v1 `update_config`
**Location:** `programs/solshot-escrow/src/lib.rs:72-108`
**Finding:** Authority overwritten in a single assignment at line 83. The zero-address guard at line 82 catches `Pubkey::default()` only — no other constraint on the incoming key.

```rust
if let Some(a) = new_authority {
    require!(a != Pubkey::default(), EscrowError::InvalidConfig);  // v1:82 — only guard
    config.authority = a;  // v1:83 — IMMEDIATE, ONE-STEP, IRREVERSIBLE
}
```

Post-update distinctness validation at `v1:96-98` ensures `authority != treasury`, `authority != ops`, `treasury != ops`, but does not provide any confirmation window.

### Step 4: Confirm one-step rotation in v2 `update_config`
**Location:** `programs/solshot-escrow-v2/src/lib.rs:96-142`
**Finding:** Identical pattern. Zero-address guard at line 107; one-step write at line 108.

```rust
if let Some(a) = new_authority {
    require!(a != Pubkey::default(), EscrowError::InvalidConfig);  // v2:107

```

v2 also rotates `fee_bps_treasury`/`fee_bps_ops` with no timelock, bounded only by `MAX_FEE_BPS=1000` at `v2:128-131`.

## Invariant Analysis

### Target Invariant
"Only the legitimate protocol operator can rotate configuration, select match winners, and redirect fee destinations."

### Enforcement Points

| Location | What It Enforces | Complete? |
|----------|-----------------|-----------|
| `v1:470, v2:603` `has_one = authority` on `UpdateConfig` | Current authority signer required | Yes — but collapses on key compromise |
| `v1:82, v2:107` zero-address guard | New authority cannot be `Pubkey::default()` | Yes — but catches only one degenerate case |
| `v1:96-98, v2:125-127` distinctness re-validation | `authority != treasury != ops` | Yes — prevents some multi-step self-redirects |
| `pending_authority` propose/accept pattern | Two-key confirmation of transfer | **NO — does not exist** |
| Timelock on authority change | Observation window before change takes effect | **NO — does not exist** |
| Multisig threshold | Multiple signers required | **NO — does not exist** |

### Enforcement Gap Assessment
The invariant is consistently enforced across all privileged code paths. The gap is architectural: a single private key is the sole enforcement mechanism, with no second factor. Enforcement is complete but not resilient.

## Exploitation Scenario

### Prerequisites
1. Attacker holds `HPyV...nokv` private key (phishing, malware, leaked `.env`, insider)
2. At least one Active match exists in v1 or v2

### Attack Steps
1. Using compromised key, call `settle_match` for all Active escrows in v1 and v2, passing an attacker-controlled player wallet as `winner` — 90% of each pot flows to attacker
2. Call `update_config` (on both programs) with `new_authority = attacker_pubkey2`, `new_treasury = attacker_wallet`, `new_ops = attacker_wallet`
3. Original team is locked out of both programs
4. Call `pause_program` on both to block player cancellations (v1: blocks cancel; v2: does not block cancel/settle but blocks new deposits)
5. All future match settlement fees route to attacker until a Layer-1 program upgrade is executed

### PoC Transaction Sequence

```
TX 1: settle_match (repeat for every Active match on v1 + v2)
  Accounts: escrow PDA, authority=compromised key (signer), winner=attacker wallet,
            treasury=current config.treasury, ops=current config.ops, config PDA
  Args: winner = attacker-controlled player wallet
  Prerequisite: match in Active state; attacker controls or has colluded with a registered player
  Result: 90% of each pot transferred to attacker wallet; escrow accounts closed

TX 2: update_config (v1)
  Accounts: config PDA (mut), authority=compromised key (signer)
  Args: new_authority=Some(attacker_pubkey2), new_treasury=Some(attacker_wallet),
        new_ops=Some(attacker_wallet)
  Prerequisite: TX 1 complete
  Result: v1 config permanently rotated; original team locked out of v1

TX 3: update_config (v2) — identical to TX 2 for v2 program
  Result: v2 config permanently rotated; all future v2 match fees to attacker

TX 4: pause_program (v1)
  Accounts: config PDA (mut), authority=attacker_pubkey2 (signer)
  Result: v1 frozen; no new matches, no player cancels

Final State:
  — All active-match wagers at time of compromise settled to attacker's benefit
  — Both programs' authority permanently transferred to attacker
  — Future match fees (7%+3% = 10% per pot) routed to attacker indefinitely
  — No on-chain recovery path without Layer-1 program upgrade
  — v2 in-flight matches at compromise time may be immune to fee redirect
    (per-match snapshot protects treasury/ops/BPS for those matches only)
```

### Impact
- **Direct fund theft:** Up to `wager × max_players × 0.9` per match × number of active matches. At 10 × 100 SOL concurrent v2 matches: up to 900 SOL stealable per settlement pass.
- **Permanent governance loss:** Recovery requires Layer-1 program upgrade (Layer-1 upgrade authority is the same hot wallet — double jeopardy).
- **Fee exfiltration:** 10% of all future pots until authority is restored via upgrade.
- **v2 partial mitigation:** Per-match snapshots at `v2:211-214` protect treasury/ops/BPS for matches that were created before the compromise. Winner selection fraud still applies to all Active matches.

## Recommended Fix

**Minimum viable:** Two-step propose/accept pattern for authority rotation, 24h timelock on treasury/ops/BPS changes.

```rust
// Add to GlobalConfig (both v1 and v2):
pub pending_authority: Option<Pubkey>,

// New instruction: propose_authority (called by current authority)
pub fn propose_authority(ctx: Context<UpdateConfig>, proposed: Pubkey) -> Result<()> {
    require!(proposed != Pubkey::default(), EscrowError::InvalidConfig);
    ctx.accounts.config.pending_authority = Some(proposed);
    Ok(())
}

// New instruction: accept_authority (called by the PROPOSED key — proves key control)
pub fn accept_authority(ctx: Context<AcceptAuthority>) -> Result<()> {
    let cfg = &mut ctx.accounts.config;
    require!(
        cfg.pending_authority == Some(ctx.accounts.new_authority.key()),
        EscrowError::Unauthorized
    );
    cfg.authority = ctx.accounts.new_authority.key();
    cfg.pending_authority = None;
    emit!(AuthorityTransferred { new_authority: cfg.authority });
    Ok(())
}
```

**Additional mitigations (in priority order):**
1. 24h timelock on `update_config` changes to `treasury`, `ops`, and (v2) `fee_bps_*` — store `pending_treasury` + `treasury_valid_after: i64`.
2. Separate settlement authority (hot wallet, higher exposure) from config-update authority (cold key or multisig, lower exposure).
3. Migrate both programs' upgrade authority to a Squads multisig before mainnet.
4. Add `actor: Pubkey` field to `ConfigUpdated` event for indexer-friendly monitoring.
