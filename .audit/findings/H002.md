# Finding: H002 — Treasury Self-Redirect via Multi-TX Rotation Chain

## Status: POTENTIAL (requires authority key compromise + secondary wallet control)
## Confidence Score: 8/10

> Confidence scale:
> - **9-10**: Certain — exhaustive code analysis, all paths verified
> - **7-8**: High — strong evidence, minor gaps in coverage
> - **5-6**: Moderate — reasonable analysis, some assumptions unverified
> - **3-4**: Low — significant uncertainty, limited code visibility
> - **1-2**: Minimal — couldn't adequately assess, treat as NEEDS MANUAL REVIEW

---

**One-line summary:** `update_config` distinctness checks fire post-update on the current state only; a two-step rotation lets the authority redirect the treasury to any wallet it controls while satisfying the checks at every step — redirecting 7% of every v1 settlement to an attacker wallet, with v2 in-flight matches immune but all new v2 matches also exposed.

---

## Executive Summary

The `update_config` instruction in both v1 and v2 re-validates pairwise distinctness of `{authority, treasury, ops}` after applying the requested changes. The check only looks at the resulting post-update state; it does not compare new values against any historical role assignment or detect that the incoming treasury value is a wallet already controlled by the authority operator.

A two-transaction rotation chain — rotate `treasury` to attacker-controlled `A2`, all three keys remain distinct, check passes — redirects 7% of every future settlement (v1: in-flight and new; v2: new only) to the attacker wallet. There is no timelock, no propose/accept, and no sentinel that distinguishes "authority changes treasury to honest wallet" from "authority changes treasury to secondary wallet it controls." The attack requires the authority key to be compromised or malicious, but once that precondition is met, the redirect is silent, on-chain, and permanent until reversed.

---

## Hypothesis Investigated

> Distinctness checks (`authority != treasury`, `authority != ops`, `treasury != ops`) only fire post-update. Authority can use a secondary wallet they control as `treasury_alt`. Multi-TX rotation: rotate authority → secondary, set treasury = original_authority's secondary, rotate authority back. Distinctness holds at each step.
>
> - Start: authority=A1, treasury=T1, ops=O1
> - TX1: update_config(new_authority=A2). Now authority=A2, treasury=T1, ops=O1. Distinctness: A2≠T1, A2≠O1, T1≠O1. OK.
> - TX2: update_config(new_treasury=A1). Now authority=A2, treasury=A1, ops=O1. Distinctness: A2≠A1, A2≠O1, A1≠O1. OK.
> - TX3: update_config(new_authority=A3) — A1 receives 7% on every settle while A3 is authority.
> - Simpler: A1 just sets treasury directly to a controlled `treasury_alt` wallet (not the authority key, but operator-controlled).
> - Verify v1 settle reads live config; v2 in-flight matches protected by snapshot, new matches use new treasury.

## Investigation Path

### Step 1: Confirm v1 `update_config` distinctness check (post-update, not cross-role)

**Location:** `programs/solshot-escrow/src/lib.rs:72-108`

The handler applies all optional field updates first, then runs three `require!` checks on the resulting state:

```rust
// v1:96-98
require!(config.authority != config.treasury, EscrowError::InvalidConfig);
require!(config.authority != config.ops, EscrowError::InvalidConfig);
require!(config.treasury != config.ops, EscrowError::DuplicateFeeAccount);
```

These checks only enforce that all three CURRENT config fields are pairwise distinct after the update completes. They do not:
- Check whether the new `treasury` value is a wallet the authority operator controls.
- Maintain any record of prior field values to detect cycling.
- Prevent the same operator from controlling wallets at different config positions across transactions.

**Finding:** The distinctness guard is necessary to prevent settlement DoS (treasury == ops would prevent Anchor's two-constraint settle) but is not sufficient to prevent self-redirect. Any pubkey that is currently distinct from the other two slots can be placed in the treasury slot.

### Step 2: Confirm v2 carries the same check with the same scope

**Location:** `programs/solshot-escrow-v2/src/lib.rs:96-142` (esp. lines 125-127)

```rust
// v2:125-127
require!(cfg.authority != cfg.treasury, EscrowError::InvalidConfig);
require!(cfg.authority != cfg.ops, EscrowError::InvalidConfig);
require!(cfg.treasury != cfg.ops, EscrowError::DuplicateFeeAccount);
```

Identical constraint scope. Same gap applies.

### Step 3: Walk the simplest attack path — direct treasury redirect (no rotation needed)

The rotation chain in the hypothesis is one valid approach, but the simplest path does not even require rotating authority:

- Start: authority=A1, treasury=T1, ops=O1. A1 also controls wallet A2 (a fresh keypair).
- TX1 (from A1): `update_config(new_treasury = A2)`. Post-update state: authority=A1, treasury=A2, ops=O1. Check: A1≠A2 ✓, A1≠O1 ✓, A2≠O1 ✓. **Passes.**
- A2 is now the treasury — owned by the attacker. Every subsequent v1 settle sends 7% to A2.

No authority rotation is required. The multi-step rotation in the hypothesis is a more elaborate version that makes tracing harder but the simple path is already fully viable.

### Step 4: Verify v1 settle reads LIVE config at settlement time

**Location:** `programs/solshot-escrow/src/lib.rs:684-706` (`SettleMatch` account struct)

```rust
// v1:684-687
#[account(
    mut,
    constraint = treasury.key() == config.treasury @ EscrowError::InvalidTreasury,
    constraint = treasury.key() != ops.key() @ EscrowError::DuplicateFeeAccount,
)]
pub treasury: UncheckedAccount<'info>,

// v1:700-706
#[account(
    seeds = [GlobalConfig::SEED],
    bump = config.bump,
    has_one = authority @ EscrowError::Unauthorized,
    constraint = !config.is_paused @ EscrowError::ProgramPaused,
)]
pub config: Account<'info, GlobalConfig>,
```

At v1 settlement, `config` is the live `GlobalConfig` PDA. The `treasury` account is validated against `config.treasury` at TX execution time, not at match-creation time. Any `update_config` that ran before this `settle_match` TX is immediately reflected — including one that ran mid-match after all deposits were in.

**Impact for v1:** Both IN-FLIGHT matches (already activated, not yet settled) and NEW matches are redirected from the moment `update_config` fires.

### Step 5: Verify v2 snapshot protects in-flight but not new matches

**Location:** `programs/solshot-escrow-v2/src/lib.rs:211-214` (create_match write) and `v2:715-728` (SettleMatch constraints)

Create_match snapshot write:
```rust
// v2:211-214
escrow.treasury_snapshot = cfg.treasury;
escrow.ops_snapshot = cfg.ops;
escrow.fee_bps_treasury_snapshot = cfg.fee_bps_treasury;
escrow.fee_bps_ops_snapshot = cfg.fee_bps_ops;
```

SettleMatch constraint (reads from escrow, not config):
```rust
// v2:715-718
#[account(
    mut,
    constraint = treasury.key() == escrow.treasury_snapshot @ EscrowError::InvalidTreasury,
    constraint = treasury.key() != ops.key() @ EscrowError::DuplicateFeeAccount,
)]
pub treasury: UncheckedAccount<'info>,
```

The snapshot is atomic with `create_match` (written in the same instruction handler before any player deposits). Once the escrow PDA is initialised, `treasury_snapshot` is immutable — no instruction modifies it after creation (verified via grep: no other write to `treasury_snapshot` in v2).

**Impact for v2:** Matches created BEFORE the attacker's `update_config` are fully protected. Matches created AFTER the `update_config` (new matches) have the attacker-controlled address baked into their snapshot at create time and cannot be updated.

## Invariant Analysis

### Target Invariant

Fee destinations (`treasury`, `ops`) should only route to wallets that are legitimately owned by the protocol operators, not to secondary wallets controlled by a compromised or malicious authority.

### Enforcement Points

| Location | What It Enforces | Complete? |
|----------|-----------------|-----------|
| `v1:96-98` | authority ≠ treasury, authority ≠ ops, treasury ≠ ops post-update | **No** — enforces pairwise inequality of keys, not operator independence |
| `v2:125-127` | Same three checks for v2 | **No** — same gap |
| `v1:686` | `treasury.key() == config.treasury` at settle (live read) | N/A — enforces consistency with config, not that config is honest |
| `v2:717` | `treasury.key() == escrow.treasury_snapshot` (frozen at create) | Partial — protects in-flight, not new match creation |

### Enforcement Gap Assessment

The distinctness check enforces that all three config keys are **different from each other at the instant of update**. It does not enforce that the key holder of `treasury` is independent from the key holder of `authority`. An operator who generates and controls both A1 (authority) and A2 (treasury) satisfies the check because A1 ≠ A2 as pubkeys, even though they are economically equivalent to a single actor.

This is a design-level gap, not an implementation bug: the invariant was written to prevent settlement DoS, not to enforce organizational separation of authority and treasury.

## Blocking Factors

- `v2:125-127` distinctness check: blocks setting `treasury = authority` directly (single-TX path where the same key holds both roles). Does NOT block the 2-TX rotation or the simpler "secondary wallet" pattern.
- `v2:211-214` snapshot at create_match: blocks mid-match redirect for v2 in-flight matches. Does NOT protect new matches or v1 of any match.
- `has_one = authority` on `update_config`: ensures only the current authority can call this. Does NOT help once authority is compromised.

## Enabling Factors

- `v1:80-83, v2:106-108`: `new_authority`, `new_treasury`, `new_ops` all accept any non-default pubkey with no additional constraint.
- `v1:686`: live `config.treasury` read at settle means every `update_config` after match creation and before settlement affects the settlement.
- No timelock, no propose/accept, no multi-sig on `update_config`.
- No on-chain monitoring of treasury rotation frequency (ConfigUpdated event does not include actor/timestamp, only end state — `v1:101-105`).

## Exploitation Scenario

### Prerequisites

1. Attacker has compromised the authority private key (`HPyVPj2VH9yBirr7FMgAJeDH8xJgaMKy5UnwLkjSnovk` on devnet), OR the authority is a malicious insider.
2. Attacker controls a secondary wallet (`treasury_alt`) not already in the config.

### Attack Steps (minimal — no rotation chain required)

1. Attacker calls `update_config(new_treasury = treasury_alt)` from the compromised authority key. Distinctness check passes because `treasury_alt ≠ authority` and `treasury_alt ≠ ops`.
2. From this point: every `settle_match` in v1 sends 7% of the pot to `treasury_alt`. In v2, every new `create_match` snapshots `treasury_alt` into the escrow, so every subsequent settlement also sends 7% there.
3. Optionally: also call `update_config(new_ops = ops_alt)` to capture the 3% ops share, bringing total diversion to 10%.
4. Attacker can revert the redirect after extracting funds by calling `update_config` again with the original treasury pubkey (if they want to evade monitoring).

### Multi-TX rotation variant (obscures intent)

For a more complex pattern that avoids leaving `treasury = treasury_alt` in config long-term:
- TX1: `update_config(new_authority = A2)`. Now A2 is authority.
- TX2 (from A2): `update_config(new_treasury = A1_controlled_wallet)`. Now treasury = A1's secondary wallet.
- TX3 (from A2): `update_config(new_authority = A3)` or back to A1. Attacker now collects 7% silently.

Every step passes distinctness because all three keys remain pairwise distinct at each individual TX.

### Impact

- **v1**: 7% (or 10% if ops also redirected) of every pot across ALL in-flight and future matches, from the moment `update_config` is executed, until the redirect is detected and reverted.
- **v2**: 7% (or 10%) of every pot in ALL NEW matches created after the config change. In-flight v2 matches (already created) are safe.
- At current stakes (wager ~1 SOL, 4-player), per-match extraction ≈ 0.28 SOL treasury + 0.12 SOL ops = 0.40 SOL per match. At higher stakes (100 SOL wager, 4 players = 400 SOL pot), extraction = 40 SOL per match.

## Recommended Fix

### Primary: Timelock on treasury/ops rotation

Add a `pending_treasury` / `pending_ops` proposal mechanism with a minimum delay (24-72 hours) before the new address takes effect. This mirrors the standard two-step authority transfer pattern and gives operators a window to detect and revert malicious rotation.

```rust
// Before (vulnerable) — v1:78-98, v2:110-127
if let Some(t) = new_treasury {
    require!(t != Pubkey::default(), EscrowError::InvalidConfig);
    config.treasury = t;  // ← immediate, no timelock
}
// ... distinctness check fires immediately on new state

// After (fixed) — introduce pending_treasury + pending_treasury_valid_at
if let Some(t) = new_treasury {
    require!(t != Pubkey::default(), EscrowError::InvalidConfig);
    config.pending_treasury = Some(t);
    config.pending_treasury_valid_at =
        Clock::get()?.unix_timestamp.checked_add(TREASURY_ROTATION_DELAY).unwrap();
    // Do not update config.treasury yet; emit PendingConfigChange event
}

// Separate accept_config instruction (callable by anyone after timelock expires):
// if Clock::get()?.unix_timestamp >= config.pending_treasury_valid_at {
//     config.treasury = config.pending_treasury.take().unwrap();
// }
```

### Secondary: Multi-sig on `update_config`

Require 2-of-3 (or M-of-N) signatures on any call to `update_config` that modifies `treasury` or `ops`. This prevents a single compromised key from redirecting fees without co-signers noticing.

### Monitoring (operational, not on-chain)

Until a timelock or multi-sig is implemented: monitor the `ConfigUpdated` event (`v1:101-105, v2:133-139`) and alert if `treasury` or `ops` change to any address not in the approved set. The event currently emits the end-state pubkeys but no actor field — consider adding `actor: config.authority` to the event struct for traceability.

## Incidental Discoveries

- **ConfigUpdated event missing `actor` field**: `v1:101-105` and `v2:133-139` emit the resulting config state but not which address signed the update. Adding `actor: ctx.accounts.authority.key()` would enable off-chain tooling to detect authority rotation events immediately. Suggested new hypothesis: check whether the absence of an actor field creates a monitoring blind spot in any downstream dashboard code.
- **v1 BPS are hardcoded constants**: Unlike v2, v1 uses `TREASURY_BPS = 700` and `OPS_BPS = 300` defined as `const u64` in the program (`v1:290-298`). A treasury redirect in v1 does not change the BPS split, only where the 7% is sent. This means the H002 attack in v1 has a fixed 7% extraction ceiling per-match, bounded by the constant — while v2 can combine H002 (treasury redirect) with H011/H028 (BPS elevation) for up to 10% extraction.

## Raw Investigation Notes

**Key code locations verified:**

- `v1:72-108`: `update_config` — optional fields applied then distinctness validated. No cross-role check. Confirmed.
- `v1:96-98`: The three `require!` lines that constitute the entire distinctness guard. Confirmed post-update-only scope.
- `v1:684-706`: `SettleMatch` struct — treasury constrained to `config.treasury` (live). Confirmed.
- `v2:96-142`: `update_config` v2 — same pattern plus BPS fields. Confirmed identical gap.
- `v2:125-127`: v2 distinctness check — same scope, same gap. Confirmed.
- `v2:211-214`: `create_match` snapshot write — atomic, immutable post-creation. Confirmed protection for in-flight v2 matches.
- `v2:715-718`: `SettleMatch` v2 struct — treasury constrained to `escrow.treasury_snapshot`, NOT live config. Confirmed in-flight protection.
- No `treasury_snapshot` write outside `create_match` handler in v2 (no grep matches for `treasury_snapshot =` other than create_match). Confirmed snapshot immutability.

**Rotation chain feasibility check:**

Each TX in the multi-step rotation chain was verified step by step:
- TX1 `update_config(new_authority=A2)`: authority slot changes to A2. treasury=T1, ops=O1 unchanged. Post-update: A2≠T1 ✓, A2≠O1 ✓, T1≠O1 ✓. Passes.
- TX2 (from A2) `update_config(new_treasury=A1)`: treasury changes to A1 (old authority key). Post-update: A2≠A1 ✓, A2≠O1 ✓, A1≠O1 ✓. Passes.
- Result: A1 receives 7% on every future v1 settle. A2 is now authority and can continue operating normally or rotate back.

Both the simple single-TX path and the more complex multi-TX rotation chain pass all on-chain checks at every step. The hypothesis is fully confirmed as a viable attack path given the H001 precondition.
