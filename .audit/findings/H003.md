# Finding: H003 — Authority Winner Selection Fraud

## Status: CONFIRMED (POTENTIAL — authority compromise precondition)
## Confidence Score: 9

> - **9-10**: Certain — exhaustive code analysis, all paths verified

**One-line summary:** The authority key freely picks any registered player as winner with no on-chain proof of game outcome; v2's 10-player cap raises worst-case extraction to 900 SOL per match (2.5× v1's 360 SOL).

---

## Executive Summary

Both `solshot-escrow` (v1) and `solshot-escrow-v2` (v2) enforce a single winner constraint in `settle_match`: the supplied winner pubkey must appear somewhere in `escrow.players[0..max_players]`. No further validation exists. There is no commit-reveal scheme, no VRF outcome, no loser signature, and no game-state proof. The on-chain program trusts the authority's off-chain assertion of who won entirely.

This is an acknowledged structural property of the server-as-authority model, not an implementation bug. However, it constitutes a real economic risk: a compromised (or malicious) authority can settle any active match in favour of any player it controls, extracting up to 90% of the pot per settlement. v2 expands the attack surface by allowing 10 players per match at 100 SOL each, raising the single-match worst case to 900 SOL.

---

## Hypothesis Investigated

H005: Authority winner constraint = `players.contains(&winner.key())` only — no game-state proof. Authority freely picks any registered player as winner. Combined with H006 (authority creates match with controlled wallet listed as player), full 90% pot extraction.

---

## Investigation Path

### Step 1: Verify winner constraint — v1

**Location:** `programs/solshot-escrow/src/lib.rs:674-679`

**Finding:** The only on-chain constraint on `winner` is membership in the players array.

**Evidence:**
```rust
// v1:674-679
#[account(
    mut,
    constraint = (0..escrow.max_players as usize)
        .any(|i| escrow.players[i] == winner.key())
        @ EscrowError::InvalidWinner
)]
pub winner: UncheckedAccount<'info>,
```

No additional constraint. The authority signs the TX; Anchor validates the winner's pubkey is in `escrow.players[0..max_players]`. That is the entirety of winner validation.

### Step 2: Verify winner constraint — v2

**Location:** `programs/solshot-escrow-v2/src/lib.rs:705-710`

**Finding:** Identical constraint; max_players is 10 (up from 4 in v1's practical limit).

**Evidence:**
```rust
// v2:707-710
constraint = (0..escrow.max_players as usize)
    .any(|i| escrow.players[i] == winner.key())
    @ EscrowError::InvalidWinner
```

v2 constant at line 31: `const MAX_PLAYERS: usize = 10;`
v2 constant at line 35: `const MAX_WAGER_LAMPORTS: u64 = 100_000_000_000;` (100 SOL)

### Step 3: Search for game-state proof mechanisms

**Location:** Full-text search of both `lib.rs` files for `commit`, `reveal`, `vrf`, `loser`, `signature`, `game_state`, `proof`, `outcome`

**Finding:** Zero matches in either program. No commit-reveal hash, no VRF output, no loser cosign, no game state field on `MatchEscrow`. The Rust grep returns only an unrelated timestamp test comment.

### Step 4: Verify settle_match handler body

**Location:** `programs/solshot-escrow/src/lib.rs:258-338` (v1); `programs/solshot-escrow-v2/src/lib.rs:387-454` (v2)

**Finding:** The handler checks state == Active and (v1 only) a settlement deadline. It then reads wager and mask values, computes the pot split, sets state to Settled, and performs direct lamport math. No game-state fields are read. No loser signature is checked. The `winner` parameter is a `Pubkey` passed by the authority; the struct constraint (Step 1/2) is the only validation.

### Step 5: Quantify worst-case v2

- `MAX_PLAYERS = 10`, `MAX_WAGER_LAMPORTS = 100 SOL`
- Full-pot: 10 × 100 SOL = 1000 SOL
- Winner share: 1000 SOL × 90% = **900 SOL** per single match
- v1 practical worst case: 4 × 100 SOL × 90% = 360 SOL
- Ratio: 900 / 360 = **2.5×**

## Invariant Analysis

### Target Invariant

Only the actual game winner should receive the pot. The on-chain program should be unable to pay out to a player who did not legitimately win the match.

### Enforcement Points

| Location | What It Enforces | Complete? |
|----------|-----------------|-----------|
| `v1:676-679` | Winner is in `escrow.players[0..max_players]` | Partial — limits to registered players, not to the actual winner |
| `v2:707-710` | Same check | Partial |
| `v1:258-262` / `v2:388-391` | Match must be Active | Yes — prevents settle on unstarted/cancelled matches |
| `v1:266-274` | Settlement deadline (v1 only) | Orthogonal — time limit, not outcome proof |

### Enforcement Gap Assessment

The invariant "only legitimate winner can be paid" is NOT enforced across any code path. The only winner-check is a player-membership check. The legitimate outcome is determined off-chain by the game server. On-chain there is no commitment, no signature from the loser, no oracle, and no state field recording the match result.

---

## Blocking Factors

- **Player membership check** (`v1:676-679`, `v2:707-710`): authority cannot pay a wallet that was not registered as a player at create_match. Limits targets to those who deposited into the specific match.
- **`AuthorityAsPlayer` check** (`v1:145-147`, `v2:186-188`): the authority's own signing key cannot be listed as a player. Authority must use a derivative/secondary wallet.
- **Pause-blocked settle in v1** (`v1:704`): `constraint = !config.is_paused` on v1 `SettleMatch`. A paused program cannot settle — but the authority controls pause, so this is not a meaningful blocker if authority is compromised.
- **v2 settlement not pause-blocked** (`v2:730-737`): explicit "Pause does NOT block settlement" — no blocker at all in v2.

## Enabling Factors

- **Server-as-authority design**: all game outcome determination is off-chain; on-chain trusts the authority's word entirely — `v1:258-338, v2:387-454`.
- **No loser cosign**: nothing in the settle instruction requires any player other than the authority to sign.
- **No commit-reveal**: no hash commitment made at match-start that would bind the outcome.
- **No VRF**: no verifiable randomness oracle consulted.
- **Authority controls player selection**: authority builds the players array at `create_match` — it can ensure a wallet it controls is always listed — `v1:130-182, v2:161-235`.
- **`AuthorityAsPlayer` gap**: only the signing key is excluded. Any secondary wallet owned by the same operator passes — `v1:145-147, v2:186-188` (documented as H027 / H014 in access-control context).

## Exploitation Scenario

### Prerequisites

1. Authority key is compromised or the authority operator is malicious.
2. Authority controls at least one wallet (secondary key) not equal to `config.authority`.
3. A high-value match (ideally v2, 10 players, max wager) is Active with legitimate victims' funds.

### Attack Steps

1. Authority calls `create_match` listing secondary wallet `ATTACKER_PLAYER` as one of the N players.
2. Legitimate players deposit wagers; `ATTACKER_PLAYER` deposits its wager.
3. Match state transitions to Active.
4. Authority calls `settle_match(winner = ATTACKER_PLAYER)`. Constraint passes: `ATTACKER_PLAYER` is in `escrow.players`.
5. 90% of the pot (up to 900 SOL for v2 max match) is transferred to `ATTACKER_PLAYER`.
6. Authority reclaims PDA rent via `close = authority`.

### Impact

- **v1 worst case**: 4 players × 100 SOL × 90% = **360 SOL** per match.
- **v2 worst case**: 10 players × 100 SOL × 90% = **900 SOL** per match.
- Remaining 10% split: 7% treasury + 3% ops — both also under authority control if H011 is simultaneously exploited.
- Repeatable: every active match can be settled fraudulently in sequence.
- Victims: all depositors except the attacker-controlled player lose their wager.

### PoC Transaction Sequence

```
TX 1: create_match
  Accounts: authority (signer), config (has_one = authority), new escrow PDA
  Args: match_id, wager_lamports = 100_000_000_000 (100 SOL),
        players = [VICTIM_1, VICTIM_2, ..., VICTIM_9, ATTACKER_PLAYER],
        max_players = 10 (v2)
  Prerequisite: authority key controls ATTACKER_PLAYER's private key
  Result: MatchEscrow initialised in AwaitingDeposits; ATTACKER_PLAYER listed at players[9]

TX 2–11: deposit_wager (×10, one per player)
  Accounts: player (signer), escrow (mut), config
  Args: (no args — wager is pre-set at create)
  Prerequisite: each player is in escrow.players, hasn't deposited yet
  Result: 100 SOL × 10 = 1000 SOL locked in escrow PDA; state → Active

TX 12: settle_match
  Accounts: authority (signer), escrow (mut, close=authority), winner = ATTACKER_PLAYER,
            treasury (= config.treasury, ideally also attacker-controlled), ops
  Args: winner = ATTACKER_PLAYER
  Prerequisite: escrow.state == Active; ATTACKER_PLAYER in escrow.players
  Result: ATTACKER_PLAYER receives 900 SOL (90%); treasury receives 70 SOL (7%);
          ops receives 30 SOL (3%); escrow PDA closed, rent to authority

Final State: Attacker has extracted 900 SOL from 9 victims' deposits.
             If treasury and ops are also authority-controlled (H011), total extraction = 1000 SOL.
```

## Recommended Fix

This is a design limitation of the server-as-authority model, not an implementation bug. On-chain proof of game outcome is not achievable without architectural change. Recommended mitigations (post-mainnet, in order of precedence):

**Option A — Commit-reveal (minimal on-chain surface):**
```rust
// Before (vulnerable): authority freely picks winner
settle_match(winner: Pubkey) -> Result<()>

// After (commit-reveal): authority commits a hash at match-start,
// reveals preimage at settlement
create_match(..., outcome_commitment: [u8; 32])  // hash(winner_pubkey || nonce)
settle_match(winner: Pubkey, nonce: [u8; 32]) -> Result<()>
// on-chain: require!(hash(winner || nonce) == escrow.outcome_commitment)
```
Limitation: authority still controls the preimage; deters casual fraud, not determined attacker.

**Option B — Loser cosign (stronger):**
```rust
// settle_match requires all non-winner players to cosign,
// or provide a signed acknowledgement instruction
// Practical challenge: requires all players to be online at settlement time
```

**Option C — VRF / oracle (strongest, most complex):**
- Use Switchboard or Pyth VRF for outcome determination
- Practical for random outcomes; inapplicable to skill-based game results without a trusted oracle

**Minimum viable pre-mainnet mitigation:**
Move upgrade authority to a 3-of-5 multisig (Squads) and add a two-step authority transfer for `update_config`. This does not eliminate winner fraud but raises the precondition cost substantially above a single hot-wallet compromise.

## Design Limitation Acknowledgement

Per JJ's stated posture, the server-as-authority model is an intentional pre-mainnet choice. This finding is documented as CONFIRMED (POTENTIAL — authority compromise precondition) rather than CONFIRMED (unconditional) because the precondition (authority compromise or malice) is required. Under normal operation with an honest server, no fraud occurs. The finding establishes the blast radius if that assumption breaks.
