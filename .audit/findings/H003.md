## Executive Summary

The `update_config` function at `lib.rs:70-89` allows the authority to freely change the `treasury` and `ops` addresses in the `GlobalConfig` PDA without re-validating that these addresses remain distinct. The `initialize_config` function enforces `treasury != ops` at lines 53-55 via `require!`, but this invariant is never re-checked after initialization.

If the authority calls `update_config(None, Some(X), Some(X))` — setting both treasury and ops to the same address X — all future calls to `settle_match` will fail. The `SettleMatch` account struct has an Anchor constraint at line 588 (`constraint = treasury.key() != ops.key() @ EscrowError::DuplicateFeeAccount`) that compares the two instruction accounts. Because `settle_match` also requires `treasury.key() == config.treasury` (line 587) and `ops.key() == config.ops` (line 596), when `config.treasury == config.ops`, the caller is forced to pass the same pubkey for both treasury and ops — which directly triggers the distinctness constraint violation. Settlement becomes permanently impossible until the config is corrected or the authority is rotated to a key that will fix the config. All Active matches are stranded, recoverable only via the 24h cancel timeout or 48h permissionless reclaim.

The attack is fully within the authority's unilateral capability and requires exactly one transaction. As a self-grief or insider-threat attack vector, it constitutes a confirmed settlement denial-of-service.

## Hypothesis Investigated

> The `update_config` function does not re-validate that authority, treasury, and ops addresses are distinct (unlike `initialize_config`). Setting treasury == ops could cause settlement to fail (Anchor constraint requiring distinct writable accounts), permanently blocking settlement of all active matches.
>
> **Attack Vector:**
> 1. Authority calls `update_config(new_treasury = Some(X), new_ops = Some(X))` where X is the same address
> 2. `settle_match` passes treasury and ops as separate `UncheckedAccount` but both resolve to the same pubkey
> 3. Anchor may reject the transaction because two writable accounts have the same key, or runtime may error on double borrow
> 4. All settlement becomes impossible; matches can only be cancelled after 24h timeout

## Investigation Path

### Step 1: Does update_config enforce authority != treasury != ops?

**Location:** `lib.rs:70-89`

**Finding:** No distinctness checks whatsoever. The function blindly applies any `Some` value to each config field.

**Evidence:**
```rust
pub fn update_config(
    ctx: Context<UpdateConfig>,
    new_authority: Option<Pubkey>,
    new_treasury: Option<Pubkey>,
    new_ops: Option<Pubkey>,
) -> Result<()> {
    let config = &mut ctx.accounts.config;

    if let Some(a) = new_authority {
        config.authority = a;
    }
    if let Some(t) = new_treasury {
        config.treasury = t;
    }
    if let Some(o) = new_ops {
        config.ops = o;
    }

    Ok(())
}
```

There is no `require!(treasury != ops)`, no `require!(authority != treasury)`, no `require!(authority != ops)`. Compare this to `initialize_config` at lines 53-55, which explicitly enforces all three:

```rust
require!(authority != treasury, EscrowError::InvalidConfig);
require!(authority != ops, EscrowError::InvalidConfig);
require!(treasury != ops, EscrowError::DuplicateFeeAccount);
```

The invariant established at initialization is not re-enforced on subsequent updates. **Gap confirmed.**

### Step 2: What happens in settle_match if config.treasury == config.ops?

**Location:** `lib.rs:583-598` (SettleMatch account struct)

**Finding:** The `SettleMatch` account struct enforces two things about treasury and ops:
1. `treasury.key() == config.treasury` — the treasury account passed must match `config.treasury`
2. `ops.key() == config.ops` — the ops account passed must match `config.ops`
3. `treasury.key() != ops.key()` — treasury and ops must be DIFFERENT accounts

If `config.treasury == config.ops` (set via the broken `update_config`), then ANY valid call to `settle_match` must provide:
- a treasury account whose key equals the poisoned `config.treasury` value
- an ops account whose key equals the poisoned `config.ops` value

Since both config values are identical, the caller must pass the same pubkey for both treasury and ops. But constraint 3 (`treasury.key() != ops.key()`) then immediately fires with `EscrowError::DuplicateFeeAccount`.

This is a logical contradiction: the caller is simultaneously required to pass the same key for both (constraints 1 and 2), and forbidden from passing the same key for both (constraint 3). No valid set of accounts can satisfy all three constraints. Settlement is unconditionally impossible.

**Evidence:**
```rust
/// Treasury: validated against config PDA (OC-03 — resolves H001, H003, S001, GAP-003, H048)
/// CHECK: Constrained to config.treasury; uniqueness check vs ops
#[account(
    mut,
    constraint = treasury.key() == config.treasury @ EscrowError::InvalidTreasury,
    constraint = treasury.key() != ops.key() @ EscrowError::DuplicateFeeAccount,
)]
pub treasury: UncheckedAccount<'info>,

/// Ops: validated against config PDA (OC-03)
/// CHECK: Constrained to config.ops
#[account(
    mut,
    constraint = ops.key() == config.ops @ EscrowError::InvalidOps,
)]
pub ops: UncheckedAccount<'info>,
```

### Step 3: Is the failure at the Anchor constraint layer or the Solana runtime layer?

**Location:** `lib.rs:585-597` (Anchor constraints evaluated before instruction body executes)

**Finding:** The failure occurs at the Anchor constraint evaluation layer, BEFORE any instruction logic runs. Anchor evaluates all account constraints when deserializing the `SettleMatch` accounts context. The `treasury.key() != ops.key()` constraint at line 588 fires with `EscrowError::DuplicateFeeAccount` regardless of whether the Solana runtime would also reject two writable accounts with the same key.

The hypothesis mention of "Anchor may reject the transaction because two writable accounts have the same key" is a secondary mechanism that is actually moot — the Anchor constraint fires first. The instruction body at line 228 is never reached.

**Note on the Solana runtime behavior:** The Solana runtime DOES reject transactions where the same writable account appears twice in the accounts list (unless one of them is read-only). This would be a second independent blocker even if the Anchor constraint were removed. The hypothesis is therefore correct on both the Anchor constraint path and the runtime path, but the Anchor constraint is the primary failure mode.

### Step 4: Can the authority recover from the poisoned config state?

**Location:** `lib.rs:70-89` (update_config)

**Finding:** Yes, but only if the authority still controls the key. The same `update_config` instruction can fix the broken config by calling `update_config(None, Some(valid_treasury), Some(valid_ops))` with distinct treasury and ops addresses. However:

- If the authority key itself was compromised (the attacker rotated authority away via `new_authority`), recovery is impossible without program upgrade.
- If the attack is used as a griefing vector during a live match, the settlement window (1 hour from activation) may expire before the operator detects the broken config and issues a fix transaction.
- The fix requires a correctly-formed `update_config` call from the legitimate authority, not an automated on-chain recovery mechanism.

### Step 5: Impact scope — which matches are affected?

**Finding:** ALL Active matches are affected simultaneously, not just a specific match. The `GlobalConfig` PDA is a singleton — there is exactly one `config.treasury` and one `config.ops` for the entire program. When these are poisoned, every match in the Active state becomes unsettleable until the config is repaired.

Matches in `AwaitingDeposits` are indirectly affected: new deposits can complete (both players deposit → Active), but then immediate settlement is also impossible.

Recovery path for stranded funds:
- Players can call `cancel_match` after 24h from activation (requires `!is_paused`)
- Anyone can call `permissionless_reclaim` after 48h from activation (bypasses pause guard per DCA-02)
- These paths refund players correctly, so NO funds are permanently lost
- Impact is primarily: settlement denied (winners do not receive their 90% payout), forced refunds (both players get wager back, nobody wins)

## Invariant Analysis

### Target Invariant

**INV-7 (from State Machine context):** Config addresses are distinct at initialization.

This invariant is stated as enforced only at initialization. The broader intended invariant should be: **config.treasury != config.ops must hold at all times**, because `settle_match` relies on it for the `DuplicateFeeAccount` constraint to be passable.

### Enforcement Points

| Location | What It Enforces | Complete? |
|----------|-----------------|-----------|
| `lib.rs:53-55` (initialize_config) | `authority != treasury`, `authority != ops`, `treasury != ops` | Only at init — YES |
| `lib.rs:70-89` (update_config) | Nothing — no re-validation | NO — gap identified |
| `lib.rs:587-588` (SettleMatch constraint) | `treasury.key() == config.treasury` AND `treasury.key() != ops.key()` | Enforced at use-time, but creates contradiction when config is broken |

### Enforcement Gap Assessment

The invariant `treasury != ops` is enforced exactly once (at initialization) and then never re-checked. The `update_config` instruction is the gap. The use-site check in `SettleMatch` is present but cannot be satisfied when the config is poisoned — it prevents settlement but cannot prevent the config poisoning that causes the problem.

The invariant is NOT enforced across ALL code paths. The gap in `update_config` is the single exploitable point.

## Blocking Factors

- **None that prevent the attack.** The only check on `update_config` is `has_one = authority` — the attacker IS the authority.
- The `DuplicateFeeAccount` error in `SettleMatch` is a blocking factor for settlement (which is the attack's goal), not a blocker for the attack itself.

## Enabling Factors

- **Missing re-validation in update_config:** `lib.rs:70-89` — no distinctness checks after the three `Option<Pubkey>` fields are applied.
- **Singleton config scope:** The single `GlobalConfig` PDA affects all matches program-wide. Poisoning one config poisons all settlements.
- **Logical contradiction at settle-time:** `lib.rs:587-596` — the combination of `treasury.key() == config.treasury`, `ops.key() == config.ops`, and `treasury.key() != ops.key()` is unsatisfiable when `config.treasury == config.ops`.
- **No timelock on config updates:** Config changes take effect immediately with no delay for detection/response.
- **Settlement window is narrow (1 hour):** `SETTLEMENT_TIMEOUT_SECONDS = 3600` at `lib.rs:26`. If the poisoning happens during an active match's settlement window and is not fixed within the window, the match expires unsettleable.

## Exploitation Scenario

### Prerequisites

1. Attacker has control of the `config.authority` key (either legitimately as the server operator, via key compromise, or as a rogue insider).
2. Active matches exist (players have deposited, match is in `Active` state). The attack is most damaging when there are many high-value active matches.

### Attack Steps

1. Attacker sends a transaction calling `update_config` with `new_treasury = Some(X)` and `new_ops = Some(X)` where X is any valid pubkey (e.g., the attacker's own wallet, or any address).
2. The `update_config` instruction succeeds. `config.treasury` and `config.ops` are now identical.
3. Any authority attempt to call `settle_match` on any Active match fails with `EscrowError::DuplicateFeeAccount` at Anchor constraint evaluation time.
4. All Active matches remain in Active state until:
   - The authority fixes the config (calls `update_config` again with distinct addresses), OR
   - The 1-hour settlement window expires (after which authority cannot settle even if config is fixed), OR
   - The 24-hour cancel timeout elapses (players can cancel), OR
   - The 48-hour reclaim timeout elapses (anyone can reclaim via `permissionless_reclaim`).
5. Winners receive nothing; both players get their wagers refunded. The protocol's fee revenue for these matches is lost.

### Impact

- **Settlement DoS:** All active matches become unsettleable for the duration of the broken config state.
- **Winner payout denied:** Legitimate match winners do not receive their 90% share of the pot.
- **Protocol revenue lost:** The 7% treasury and 3% ops fees are not collected for affected matches.
- **Fund lockup:** Players' funds are locked until timeout paths activate (24h for cancel, 48h for reclaim).
- **Reputational damage:** Players trust the server to settle correctly; settlement failure erodes trust.
- **No permanent fund loss:** Players eventually receive full refunds via cancel or reclaim paths.

### Proof of Concept Outline

1. **Setup:** Deploy program with `config.authority = SERVER_KEY`, `config.treasury = TREASURY_KEY`, `config.ops = OPS_KEY`. Create a match; both players deposit; match transitions to Active state.
2. **Attack:** Call `update_config(authority = SERVER_KEY, config = GlobalConfig, new_treasury = Some(ATTACKER_KEY), new_ops = Some(ATTACKER_KEY))` — sets both fee destinations to the same address.
3. **Observe:** Call `settle_match(authority = SERVER_KEY, treasury = ATTACKER_KEY, ops = ATTACKER_KEY, ...)` — transaction fails with `DuplicateFeeAccount`. Call with any other treasury/ops values fails with `InvalidTreasury` or `InvalidOps`. Settlement is impossible.
4. **Result:** Match remains Active; 1-hour settlement window expires; match becomes permanently unsettleable via `settle_match`; players must wait for 24h cancel or 48h reclaim.

### Recommended Fix

Add distinctness re-validation to `update_config`, applying it against the final (post-update) config state.

```rust
// Before (vulnerable)
pub fn update_config(
    ctx: Context<UpdateConfig>,
    new_authority: Option<Pubkey>,
    new_treasury: Option<Pubkey>,
    new_ops: Option<Pubkey>,
) -> Result<()> {
    let config = &mut ctx.accounts.config;

    if let Some(a) = new_authority {
        config.authority = a;
    }
    if let Some(t) = new_treasury {
        config.treasury = t;
    }
    if let Some(o) = new_ops {
        config.ops = o;
    }

    Ok(())
}

// After (fixed) — validate final state after all updates are applied
pub fn update_config(
    ctx: Context<UpdateConfig>,
    new_authority: Option<Pubkey>,
    new_treasury: Option<Pubkey>,
    new_ops: Option<Pubkey>,
) -> Result<()> {
    let config = &mut ctx.accounts.config;

    if let Some(a) = new_authority {
        config.authority = a;
    }
    if let Some(t) = new_treasury {
        config.treasury = t;
    }
    if let Some(o) = new_ops {
        config.ops = o;
    }

    // Re-validate distinctness invariant after all updates are applied
    // Mirrors the checks in initialize_config (lines 53-55)
    require!(
        config.authority != config.treasury,
        EscrowError::InvalidConfig
    );
    require!(
        config.authority != config.ops,
        EscrowError::InvalidConfig
    );
    require!(
        config.treasury != config.ops,
        EscrowError::DuplicateFeeAccount
    );

    Ok(())
}
```

**Alternative fix (defense-in-depth):** Additionally add an Anchor constraint in the `UpdateConfig` account struct to enforce that the new values (if provided) are non-zero pubkeys:

```rust
// In UpdateConfig account struct — validate new authority is not the zero address
// (prevents lockout via Pubkey::default())
#[account(
    mut,
    seeds = [GlobalConfig::SEED],
    bump = config.bump,
    has_one = authority @ EscrowError::Unauthorized,
)]
pub config: Account<'info, GlobalConfig>,
```

Note: The constraint-level fix alone is insufficient since constraints cannot see the instruction arguments. The handler-level re-validation (shown above) is the correct and complete fix.

## Raw Investigation Notes

### Tracing the constraint logic in settle_match when treasury == ops

Assume `config.treasury = ADDR_X` and `config.ops = ADDR_X` (after poisoning).

Caller attempts `settle_match` with:
- Case A: `treasury = ADDR_X`, `ops = ADDR_X`
  - Constraint: `treasury.key() == config.treasury` → `ADDR_X == ADDR_X` → PASS
  - Constraint: `ops.key() == config.ops` → `ADDR_X == ADDR_X` → PASS
  - Constraint: `treasury.key() != ops.key()` → `ADDR_X != ADDR_X` → FAIL with DuplicateFeeAccount
  - **Result: FAILS**

- Case B: `treasury = ADDR_X`, `ops = ADDR_Y` (any other address)
  - Constraint: `treasury.key() == config.treasury` → `ADDR_X == ADDR_X` → PASS
  - Constraint: `ops.key() == config.ops` → `ADDR_Y == ADDR_X` → FAIL with InvalidOps
  - **Result: FAILS**

- Case C: `treasury = ADDR_Y`, `ops = ADDR_X` (any other address for treasury)
  - Constraint: `treasury.key() == config.treasury` → `ADDR_Y == ADDR_X` → FAIL with InvalidTreasury
  - **Result: FAILS**

All three cases fail. There is no valid combination of accounts that can pass all constraints when `config.treasury == config.ops`. The contradiction is exhaustive and unconditional.

### Verification: Is the Anchor constraint at line 588 comparing instruction accounts or config values?

Line 588: `constraint = treasury.key() != ops.key() @ EscrowError::DuplicateFeeAccount`

This compares the KEYS OF THE INSTRUCTION ACCOUNTS `treasury` and `ops`, not the config values directly. However, constraints at lines 587 and 596 bind the instruction accounts to the config values:
- `treasury.key() == config.treasury` (line 587): instruction treasury must equal config.treasury
- `ops.key() == config.ops` (line 596): instruction ops must equal config.ops

So when config.treasury == config.ops == X, the instruction accounts must both be X, and the `treasury.key() != ops.key()` check then compares X != X, which is false. This analysis is correct.

### Anchor constraint evaluation order

Anchor evaluates account constraints in declaration order within the `#[derive(Accounts)]` struct. The `treasury` account is declared before `ops` (lines 584-598). Within the `treasury` declaration:
1. `mut` (line 585)
2. `constraint = treasury.key() == config.treasury` (line 587)
3. `constraint = treasury.key() != ops.key()` (line 588)

Constraint 3 references `ops.key()`, which requires `ops` to already be deserialized when `treasury`'s constraints are evaluated. In Anchor, all accounts in the struct are deserialized first, then constraints are evaluated in order. So `ops.key()` is available when constraint 3 on `treasury` is evaluated. This is standard Anchor behavior and the constraint is valid.

### Confirming update_config requires no witness from new treasury/ops addresses

The `UpdateConfig` account struct (lines 464-475) only requires:
- `config: Account<'info, GlobalConfig>` with `has_one = authority`
- `authority: Signer<'info>`

There is no requirement for the NEW treasury or ops addresses to sign or be present as accounts. The new addresses are pure `Pubkey` instruction arguments. This means the attacker does not need to control the address they set — they can set treasury and ops to any arbitrary pubkey, including each other, without any co-signer requirement.
