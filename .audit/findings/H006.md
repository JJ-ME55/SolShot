# Finding: H006 - Authority Collusion to Settle in Favor of Controlled Wallet

**One-line summary:** The authority operator can register a secondary wallet they control as a legitimate player, then settle the match in its favor — the on-chain winner constraint is satisfied because the colluding wallet IS in `escrow.players[]`.

## Status: CONFIRMED (design limitation)
## Confidence Score: 9

> 9 — exhaustive code analysis; all enforcement paths verified; attack path requires no on-chain exploit, only operational deception by the authority operator.

---

## Executive Summary

`create_match` accepts an arbitrary `players: Vec<Pubkey>` from the signing authority with no proof-of-key-ownership, liveness check, or independent registration. The only exclusion at the player-validation step is the authority's **current signing key** (`ctx.accounts.authority.key()`). A secondary wallet generated and held by the same authority operator passes this check silently.

`settle_match` validates the winner against `escrow.players[0..max_players]` — a constraint fully satisfied by the colluding wallet because it was legitimately inserted at create time. No on-chain mechanism distinguishes a player recruited through off-chain matchmaking from one generated by the authority operator a moment before creating the match. The attack is entirely in the server trust layer; the program behaves correctly by its own specification.

This is a design limitation of the server-as-authority model, not a code bug. It is distinct from H003 (compromised key) because here the authority operator acts **deliberately and without any key compromise**.

---

## Hypothesis Investigated

> `create_match` accepts arbitrary `players: Vec<Pubkey>`. OC-06 only excludes the SIGNING authority key, not derivatives. Authority operator can:
> 1. Generate a secondary wallet they control.
> 2. List it as one of the players in `create_match`.
> 3. Have other (legitimate) players join and deposit.
> 4. Settle in favor of the secondary wallet — passes winner constraint (it IS in `players[]`).

## Investigation Path

### Step 1: Verify `create_match` accepts arbitrary pubkeys with no ownership proof

**Location:** `programs/solshot-escrow/src/lib.rs:130-159` (v1), `programs/solshot-escrow-v2/src/lib.rs:161-199` (v2)

**Finding:** `players: Vec<Pubkey>` is a raw argument passed by the calling authority. The program applies three checks only:
1. Length bounds (`>= 2`, `<= 4` v1 / `<= 10` v2).
2. Authority-key exclusion (see Step 2).
3. Pairwise player distinctness.

No proof-of-key-ownership. No signature from the wallet being registered. No liveness check. No matchmaking registry.

**Evidence:**
```rust
// v1:144-154
// ESC-03: authority (server keypair) cannot be a player
for p in &players {
    require!(*p != ctx.accounts.authority.key(), EscrowError::AuthorityAsPlayer);
}
// ESC-03: all players must be distinct
for i in 0..players.len() {
    for j in (i + 1)..players.len() {
        require!(players[i] != players[j], EscrowError::SamePlayer);
    }
}
```

### Step 2: Verify OC-06 only checks `authority.key()` — not derivatives

**Location:** `v1:144-147`, `v2:185-188`

**Finding:** The guard is `*p != ctx.accounts.authority.key()`. This is the pubkey of the **currently signing keypair**. Any other keypair generated by the same operator — even one derived from the same seed — passes this check. The code has no concept of "operator-controlled wallets." The on-chain constraint is syntactically correct but semantically insufficient to prevent insider fraud.

**Evidence:**
```rust
// v2:185-188 (identical pattern in v1:144-147)
// Authority cannot be a player
for p in &players {
    require!(*p != ctx.accounts.authority.key(), EscrowError::AuthorityAsPlayer);
}
```

### Step 3: Verify `settle_match` winner constraint checks only `escrow.players[]`

**Location:** `v1:676-679`, `v2:707-710`

**Finding:** Winner validation is a membership test against the pre-registered players array. Any pubkey that appears in `escrow.players[0..max_players]` passes. The constraint does not consult matchmaking history, user accounts, or any identity proof. A colluding wallet inserted at create time passes unconditionally.

**Evidence:**
```rust
// v1:674-679
/// Winner: must be one of the N registered players (OC-02, ESC-07)
/// CHECK: Constrained to one of escrow.players[0..max_players]
#[account(
    mut,
    constraint = (0..escrow.max_players as usize)
        .any(|i| escrow.players[i] == winner.key())
        @ EscrowError::InvalidWinner
)]
pub winner: UncheckedAccount<'info>,
```

### Step 4: Confirm no on-chain mechanism distinguishes legitimate players from operator-controlled wallets

**Location:** Both programs, full account-validation surface

**Finding:** The program stores only `Pubkey` values in `escrow.players[]`. There is no linked identity account, no deposit-origin validation, no commitment scheme binding a player's wallet to an external identity. The only restriction on who appears in `players[]` is: not the current authority signing key, not a duplicate, and within the player-count bounds. All other pubkeys are treated identically.

| 1 | Generate a secondary wallet (not the authority signing key) | Yes | Standard Solana keypair generation; completely off-chain |

## Invariant Analysis

### Target Invariant

"The winner of a settled match must be the player who legitimately won the game, not a wallet planted by the authority operator."

### Enforcement Points

| Location | What It Enforces | Complete? |
|----------|-----------------|-----------|
| `v1:146`, `v2:187` — `AuthorityAsPlayer` guard | Prevents the authority's **current signing key** from being a player | **Partial** — does not cover derivative/secondary wallets |
| `v1:676-679`, `v2:707-710` — winner membership constraint | Winner must be in `escrow.players[]` | **No** — satisfied by any registered player including operator-controlled ones |
| Off-chain server logic | Server determines match outcome and calls `settle_match` | **Not enforced on-chain** — server is the attacker in this scenario |

### Enforcement Gap Assessment

The invariant "winner is the legitimate game winner" is enforced **only off-chain** — the server controls both match outcome determination and the `settle_match` call. On-chain code enforces that the winner is a **registered** player, not that the registration was honest. A malicious authority operator satisfies both on-chain constraints (create_match player validation + settle winner constraint) while violating the invariant entirely.

---

## Blocking Factors

None that prevent this attack from the on-chain side.

- `AuthorityAsPlayer` check at `v1:146`/`v2:187`: blocks **only** the authority signing key itself — not a different keypair held by the same operator.
- Anchor PDA + signer validation: ensures transaction authenticity, but the signer IS the legitimate authority.
- `SamePlayer` distinctness check: prevents double-registration of the same wallet, but a fresh secondary wallet passes trivially.

---

## Enabling Factors

- `players: Vec<Pubkey>` is fully attacker-supplied at `create_match` — `v1:134`, `v2:165`.
- No consent mechanism: player wallets don't sign to accept inclusion in a match.
- No identity binding: `escrow.players[]` stores raw pubkeys with no associated proof or registry.
- Server-authoritative settlement: authority freely chooses the winner argument in `settle_match` — `v1:258`, `v2:387`.
- v2 amplification: up to 10 players per match means larger pots are at risk (`MAX_PLAYERS = 10`, `MAX_WAGER = 100 SOL` → max pot = 1000 SOL).

## Exploitation Scenario

### Prerequisites

1. Authority operator has access to the server keypair (`HPyV...nokv` on devnet).
2. Authority generates a secondary wallet `W_evil` (any standard Solana keypair).
3. Authority has funds to deposit `wager_lamports` from `W_evil` (can be sourced from treasury wallet without touching authority key).

### Attack Steps

1. Authority calls `create_match` with `players = [W_evil, W_victim1, W_victim2, ...]`. All on-chain checks pass: `W_evil != authority.key()`, all pubkeys distinct.
2. `W_victim1`, `W_victim2` receive the usual server-side UX prompt and call `deposit_wager` normally. `W_evil` also deposits (funded by operator off-chain).
3. Match runs; regardless of actual game outcome, authority calls `settle_match` with `winner = W_evil`.
4. On-chain: `escrow.players[0] == W_evil.key()` → constraint satisfied → `W_evil` receives 90% of total pot.
5. Authority sweeps `W_evil` wallet balance back to itself off-chain.

### Impact

- Each match: victims lose their full wager. Authority extracts `pot * 0.9 - W_evil_deposit`. Net profit per 2-player match at 1 SOL wager = `2 * 1 * 0.9 - 1 = 0.8 SOL`.
- v2 at max capacity: `10 * 100 SOL * 0.9 - 100 SOL = 800 SOL` per match.
- Undetectable on-chain: all transactions are valid, all constraints satisfied.
- Detectable only by: (a) off-chain analysis of win-rate statistics, (b) cross-referencing `W_evil` wallet origin with authority wallet in block explorers.

### PoC Transaction Sequence

```
TX 1: create_match
  Accounts: authority (HPyV...), config PDA, new escrow PDA, system_program
  Args: match_id="rigged-001", wager_lamports=1_000_000_000 (1 SOL), players=[W_evil, W_victim]
  Prerequisite: W_evil keypair generated and held by authority operator
  Result: escrow PDA initialized with players=[W_evil, W_victim], state=AwaitingDeposits

TX 2: deposit_wager (signed by W_evil)
  Accounts: W_evil (signer), escrow PDA, config PDA, system_program
  Args: (none beyond accounts)
  Prerequisite: W_evil funded with >= 1 SOL; TX 1 complete
  Result: deposits_mask bit 0 set; 1 SOL transferred to escrow

TX 3: deposit_wager (signed by W_victim)
  Accounts: W_victim (signer), escrow PDA, config PDA, system_program
  Args: (none)
  Prerequisite: TX 1 complete; W_victim willing participant
  Result: deposits_mask bit 1 set; state → Active (full mask)

TX 4: settle_match (signed by authority)
  Accounts: authority (HPyV...), escrow PDA, config PDA, W_evil (winner), treasury, ops
  Args: winner=W_evil.pubkey()
  Prerequisite: state=Active; within settlement deadline (v1 only)
  Result: W_evil receives 1.8 SOL (90% of 2 SOL pot); treasury +0.14 SOL; ops +0.06 SOL;
          escrow closed → state=Settled

Final State: W_evil holds 1.8 SOL (net +0.8 SOL profit for operator);
             W_victim lost 1 SOL with no recourse on-chain.
```

## Recommended Fix

**On-chain (partial mitigation):** There is no practical on-chain mechanism to prove that a player wallet is not operator-controlled. Key derivation is invisible to the program.

**Off-chain architectural mitigations (recommended):**

1. **Identity binding**: Require players to sign a registration message with their wallet before match creation; server persists a wallet → verified identity (e.g., Telegram user ID, social login via Privy) mapping. Server rejects match creation if any player wallet maps to operator-controlled identity.

2. **Commit-reveal for game outcome**: Players or a neutral game-state oracle commit to the outcome before the authority submits `settle_match`. Authority is a relay rather than the sole arbiter. Requires significant architectural rework.

3. **Statistical monitoring**: Off-chain monitor tracks win-rates per wallet. Flag wallets with anomalously high win-rates that also appear as the `winner` in `settle_match` more than expected.

4. **Transparent match log**: Server publishes the full match replay log before calling `settle_match`. Players can challenge outcomes via a time-window dispute layer (significant redesign, appropriate for mainnet).

```rust
// There is no one-line on-chain fix. The root cause is the server-as-authority design.
// The closest on-chain addition would be:
//
// In create_match handler, require each player to have signed an on-chain
// "join_match" instruction in the same or prior block, proving key liveness.
// This prevents ghost wallets that were never held by a real user — but does
// not prevent a determined operator who genuinely controls both the server
// and a player keypair.
```

## Incidental Discoveries

- **No consent mechanism for player enrollment**: A wallet can be enrolled as a match player entirely without its owner's knowledge or consent. If a non-participating wallet is listed and the match times out, the refund loop in `cancel_match` / `permissionless_reclaim` would simply skip their slot (mask bit unset). No SOL is lost for the unlisted wallet, but this could be used for spam or denial-of-service against a target wallet (enumeration in explorer history). → Suggested hypothesis: **H-NEW: Unsolicited player enrollment as reputational or operational harassment vector**.

## Raw Investigation Notes

OC-06 (`AuthorityAsPlayer`) is the named control point. Its scope is explicitly one key: `ctx.accounts.authority.key()`. The access-control context document at `01-access-control.md:52` notes: "C4 (HIGH — H027 design limitation): Authority exclusion only excludes `authority.key()`. Authority operator can use a fresh wallet as a player and pre-fund it from the treasury, then settle in its favor." This matches the hypothesis exactly.

The RECHECK table in `01-access-control.md:83` explicitly marks H014 as **STILL_OPEN** with the same rationale: "Design limitation, not a fixable vulnerability without architectural change." H006 and H014 are aliases in the strategy numbering; this finding covers both.

`create_match` struct at `v1:606-631` and `v2:641-665` confirms the only account-level gate on who can create a match is `has_one = authority` on config — verifying the signer is the current authority. It does not constrain the content of `players[]` beyond the handler-level checks documented above.

No additional on-chain enforcement was found in either program. Search confirmed no `player_registry`, `identity`, or `consent` account types exist in either program. The program is intentionally minimal.
