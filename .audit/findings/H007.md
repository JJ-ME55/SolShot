# Finding: H007 - Authority Self-Play Bypass via Secondary Wallet

**One-line summary:** OC-06 only excludes `authority.key()` itself; the authority operator can register any other keypair they control as a player and settle in its favor — identical root cause to H006, distinct framing as an access-control bypass rather than collusion.

## Status: CONFIRMED (design limitation)
## Confidence Score: 9

> 9 — exhaustive code analysis; both v1 and v2 OC-06 guard verified line-by-line; attack path requires no on-chain exploit; H006 PoC covers this scenario fully.

---

## Executive Summary

H007 is a subset of H006. The OC-06 guard at `v1:146` / `v2:187` reads `*p != ctx.accounts.authority.key()` — it excludes only the single pubkey that is currently signing the transaction. Any other keypair held by the authority operator, including ones generated moments before `create_match` is called, passes this check unconditionally.

The authority operator can therefore enroll a self-controlled wallet as a match participant, have legitimate players deposit, and call `settle_match` naming that wallet as winner. All on-chain constraints are satisfied. The bypass is architectural, not a code defect: the program cannot distinguish a keypair held by the operator from one held by an independent player.

---

## Hypothesis Investigated

> OC-06 only excludes `ctx.accounts.authority.key()`. Authority operator can use any other wallet they control as a player — registering it via `create_match`, depositing from it, and settling in its favor. This is the same root cause as H006 but framed as an access-control bypass (self-play) rather than collusion.

## Investigation Path

### Step 1: Verify OC-06 only checks `authority.key()`

**Location:** `programs/solshot-escrow/src/lib.rs:144-147` (v1), `programs/solshot-escrow-v2/src/lib.rs:185-188` (v2)

**Finding:** Both versions use the identical single-key exclusion pattern. No additional check exists for derivative wallets, operator-owned wallets, or wallets that share a funding source with the authority.

**Evidence:**
```rust
// v1:144-147
// ESC-03: authority (server keypair) cannot be a player
for p in &players {
    require!(*p != ctx.accounts.authority.key(), EscrowError::AuthorityAsPlayer);
}

// v2:185-188 — identical pattern
// Authority cannot be a player
for p in &players {
    require!(*p != ctx.accounts.authority.key(), EscrowError::AuthorityAsPlayer);
}
```

### Step 2: Confirm authority can register any other pubkey as a player

**Location:** `v1:130-154`, `v2:161-193`

**Finding:** `players: Vec<Pubkey>` is fully caller-supplied. The only validation applied to each pubkey is: (a) not equal to `authority.key()`, (b) not a duplicate of another entry. No ownership proof, no co-signature from the player wallet, no registry lookup. A freshly generated keypair held entirely by the operator passes both checks.

### Step 3: Cross-reference H006 — same root cause

**Reference:** `.audit/findings/H006.md`

H006 documents this mechanism in full, including the complete PoC transaction sequence (TX 1–4), CVSS scoring, and fix recommendations. H007 is the same on-chain gap described from the access-control angle: OC-06 is the named control whose scope is insufficient. H006 is the canonical finding ID.

## Invariant Analysis

### Target Invariant

"The authority's self-play bypass is prevented — no wallet ultimately controlled by the authority operator can be enrolled as a match player."

### Enforcement Points

| Location | What It Enforces | Complete? |
|----------|-----------------|-----------|
| `v1:146`, `v2:187` — `AuthorityAsPlayer` guard | Prevents the authority's **current signing pubkey** from being a player | **Partial** — covers one key; does not cover any other operator-held wallet |

### Enforcement Gap Assessment

The invariant requires operator-wallet exclusion across **all keys the operator controls**. On-chain, that set is unknowable — the program has no concept of key ownership beyond signature verification. OC-06 enforces only the narrowest possible interpretation (the literal signing key). The broader intent is unenforceable on-chain without external identity binding.

## Recommended Fix

Same as H006 — no practical on-chain fix exists for the general case. Recommended mitigations:

1. **Off-chain identity binding**: Require players to authenticate via Privy (or equivalent) before match creation; server enforces that no two players map to the same verified identity, and that no player identity matches the operator's registered identity.

2. **Statistical monitoring**: Flag wallets appearing as `settle_match` winner at anomalously high rates, especially wallets funded directly from the server treasury wallet.

3. **Commit-reveal outcome**: Significant architectural rework; appropriate for mainnet.
