# Finding: H008 — NOVEL — initialize_config Race-Init

## Status: CONFIRMED (theoretical for new deployments; not exploitable on current devnet deployment)
## Confidence Score: 9/10

> Confidence scale:
> - **9-10**: Certain — exhaustive code analysis, all paths verified
>
> *All relevant code paths traced. Current devnet state verified via project memory.*

---

**One-line summary:** `initialize_config` accepts any funded payer and takes authority/treasury/ops entirely from caller arguments — no binding to the upgrade authority — so a race-init is structurally possible on any new program deploy until the legitimate operator calls init.

---

## Executive Summary

Both `solshot-escrow` (v1) and `solshot-escrow-v2` (v2) expose an `initialize_config` instruction whose account struct (`InitializeConfig`) requires only a generic `Signer<'info>` as payer. The authority, treasury, and ops pubkeys are all instruction arguments supplied by the caller. Nothing in the program — no constraint, no account attribute, no assertion — verifies that the payer or the supplied `authority` argument is the BPF Loader upgrade authority for the program. Any funded wallet can submit this transaction and set themselves as authority, treasury, and ops.

On the current devnet deployment this race was already won legitimately: per project memory the GlobalConfig PDA (`92wnuoauqtxkkxDu22fBWGZMBjfNmvSXfKrsJ8nrfSU4`) was initialized by the operator on 2026-05-04 immediately after deploy, and Anchor's `init` constraint blocks any second call. The finding is therefore not exploitable against the live deployment. However the same structural gap applies to any future mainnet (or redeploy) scenario where `initialize_config` is not called in the same operator session as `solana program deploy`. The init-config scripts are a separate step, not bundled into a single atomic transaction with the deploy.

---

## Hypothesis Investigated

`initialize_config` accepts any payer (`payer: Signer<'info>`); the authority/treasury/ops arguments are passed by the caller. If the deployer doesn't fire init in the same script as deploy, an attacker can race-init and set themselves as authority.

---

## Investigation Path

### Step 1: Confirm payer is unconstrained in v1 InitializeConfig
**Location:** `programs/solshot-escrow/src/lib.rs:544-559`
**Finding:** No constraint ties payer to the program's upgrade authority. Any signer can be payer and supply any pubkeys as authority/treasury/ops.

```rust
#[derive(Accounts)]
pub struct InitializeConfig<'info> {
    #[account(
        init,
        payer = payer,
        space = GlobalConfig::SPACE,
        seeds = [GlobalConfig::SEED],
        bump,
    )]
    pub config: Account<'info, GlobalConfig>,

    #[account(mut)]
    pub payer: Signer<'info>,

    pub system_program: Program<'info, System>,
}
```

No `address = <upgrade_authority>` or `constraint = payer.key() == <expected>` anywhere.

### Step 2: Confirm handler sets authority from argument, no binding check
**Location:** `programs/solshot-escrow/src/lib.rs:47-65`
**Finding:** The handler takes `authority: Pubkey` as a plain argument and writes it directly to config. The only validation is pairwise distinctness among the three pubkeys.

```rust
pub fn initialize_config(
    ctx: Context<InitializeConfig>,
    authority: Pubkey,
    treasury: Pubkey,
    ops: Pubkey,
) -> Result<()> {
    require!(authority != treasury, EscrowError::InvalidConfig);
    require!(authority != ops, EscrowError::InvalidConfig);
    require!(treasury != ops, EscrowError::DuplicateFeeAccount);
    // ... writes authority/treasury/ops to config
```

### Step 3: Confirm zero-address guard is absent from initialize_config (present only in update_config)
**Location:** v1 `update_config` at `lib.rs:82, 86, 90`; v2 `update_config` at `lib.rs:107, 111, 115`
**Finding:** `require!(a != Pubkey::default(), ...)` guards appear only in `update_config`, not in `initialize_config`. An attacker can supply `Pubkey::default()` as authority during init (though this would cripple the config rather than benefit them).

### Step 4: Confirm same gap in v2
**Location:** `programs/solshot-escrow-v2/src/lib.rs:586-600`
**Finding:** Identical pattern — `payer: Signer<'info>` unconstrained, authority/treasury/ops/fee_bps supplied as arguments.

### Step 5: Verify deploy and init are separate steps (not atomic)
**Location:** `server/scripts/init-config.mjs` and `server/scripts/init-config-v2.mjs`
**Finding:** Both scripts are standalone Node.js processes run manually AFTER `solana program deploy`. There is no bundled transaction that atomically deploys + inits. The deploy and init can be separated by any number of Solana slots.

### Step 6: Confirm current devnet instance is already initialized (race already closed)
**Source:** Project memory — GlobalConfig PDA `92wnuoauqtxkkxDu22fBWGZMBjfNmvSXfKrsJ8nrfSU4` initialized 2026-05-04. Anchor `init` constraint rejects reinit with `AccountAlreadyInitialized`.
**Finding:** This specific deployment is immune. A future redeploy or mainnet deploy restarts the race window.

## Invariant Analysis

### Target Invariant
Only the legitimate program operator should be able to set the initial `GlobalConfig.authority`.

### Enforcement Points

| Location | What It Enforces | Complete? |
|----------|-----------------|-----------|
| `v1:46-64` (initialize_config handler) | Pairwise distinctness of authority/treasury/ops | Partial — no ownership check |
| `v1:544-559` (InitializeConfig struct) | Payer must be a signer + PDA init | No — payer not bound to upgrade authority |
| `v1:80-92` (update_config) | Zero-address guard + has_one authority | Not applicable to init |

### Enforcement Gap Assessment

The invariant is NOT enforced at `initialize_config`. Solana's BPF Loader Upgradeable stores the upgrade authority separately in the program data account — the Anchor program has no built-in mechanism to read it. Binding `payer` or `authority` to the upgrade authority would require a sysvar or a manual account lookup that is absent from the struct.

---

## Blocking Factors

- **Anchor `init` blocks re-init:** `programs/solshot-escrow/src/lib.rs:546-552` — once the GlobalConfig PDA exists, `initialize_config` fails with `AccountAlreadyInitialized`. This is the single blocker: first caller wins, permanently.
- **Pairwise distinctness check:** Prevents trivially malformed configs (all-same-key) but does not block a fully-formed attacker config.

## Enabling Factors

- **Unconstrained payer:** `v1:555-556`, `v2:596-597` — any `Signer` may pay and set arguments.
- **Authority from argument:** `v1:49, 58`, `v2:67, 82` — `config.authority` is assigned from caller-supplied data with no on-chain binding to the upgrade authority.
- **Deploy and init are separate:** `server/scripts/init-config.mjs`, `server/scripts/init-config-v2.mjs` — two independent processes; any slot gap is exploitable.
- **No zero-address guard at init:** `v1:53-55`, `v2:73-75` — distinctness checks but no `!= Pubkey::default()` guard (attacker supplies valid distinct keys, so this is moot in practice).

## Exploitation Scenario

### Prerequisites
1. Attacker monitors Solana devnet/mainnet for a new SolShot escrow program deployment.
2. Attacker has a funded Solana wallet.
3. There is any gap (even one block) between `solana program deploy` completing and the operator running `node scripts/init-config.mjs`.

### Attack Steps
1. Observe the deploy TX land on-chain for the new program at a known program ID.
2. Immediately submit `initialize_config` with attacker_wallet as `authority`, `treasury`, and `ops` (using distinct addresses).
3. If this TX lands before the operator's init TX, the GlobalConfig PDA is set with attacker control.
4. Operator's init TX fails with `AccountAlreadyInitialized`.
5. Attacker now holds the `authority` key recognized by all `has_one = authority` constraints — can create/settle/cancel matches, rotate config, and drain all escrowed funds to attacker-controlled treasury/ops.

### Impact
Full protocol takeover: all subsequent match escrows are under attacker authority. Winner selection, fee destinations, and pause flag all become attacker-controlled. On mainnet with real wagers this represents total fund drainage potential up to `MAX_WAGER × MAX_PLAYERS × (active matches)`.

### PoC Transaction Sequence

```
TX 1: initialize_config
  Accounts: config (PDA, init), payer (attacker wallet, mut signer), system_program
  Args: authority=attacker_pk, treasury=attacker_treasury_pk, ops=attacker_ops_pk
  Prerequisite: Program just deployed; GlobalConfig PDA does not yet exist
  Result: GlobalConfig.authority = attacker_pk; GlobalConfig.treasury = attacker_treasury_pk

TX 2: (Operator's init attempt — FAILS)
  Returns: AccountAlreadyInitialized

TX 3: (later) create_match(match_id, players, wager)
  Accounts: config (has_one = authority enforced — attacker IS authority now), ...
  Prerequisite: TX 1 succeeded
  Result: Normal-looking match escrow created; attacker controls settlement

TX 4: settle_match(winner = attacker_alt_pk)
  Accounts: winner = attacker_alt_pk, treasury = attacker_treasury_pk, ops = attacker_ops_pk
  Result: All pot flows to attacker-controlled addresses

Final State: Attacker is the recognized authority; all new matches drain to attacker wallets.
```

## Recommended Fix

### Option A — Bind payer to upgrade authority (preferred, on-chain guarantee)

```rust
// Before (vulnerable): any signer
#[account(mut)]
pub payer: Signer<'info>,

// After (fixed): only the program's upgrade authority can pay/init
/// CHECK: Must be the BPF Loader upgrade authority for this program.
#[account(
    mut,
    constraint = payer.key() == program_data.upgrade_authority_address.ok_or(EscrowError::Unauthorized)?
        @ EscrowError::Unauthorized
)]
pub payer: Signer<'info>,

/// The program data account used to read upgrade authority.
#[account(
    seeds = [program_id.key().as_ref()],
    bump,
    seeds::program = bpf_loader_upgradeable::ID,
)]
pub program_data: Account<'info, ProgramData>,

pub program_id: Program<'info, SolshotEscrow>,
```

This requires importing `anchor_lang::solana_program::bpf_loader_upgradeable` and the `ProgramData` account type.

### Option B — Atomic deploy + init script (operational mitigation, no code change)

Combine `solana program deploy` and `initialize_config` in a single shell script that fails atomically if the init TX does not confirm. Document this as a required procedure and add a CI gate that prevents mainnet launch without verified init.

### Option C — Add zero-address guard at init (partial defense)

Add `require!(authority != Pubkey::default(), ...)` guards inside `initialize_config` (matching `update_config`). This does not close the race but prevents a degenerate-key init that bricks the protocol.

## Related Findings

- **H001** — once the race is won, the attacker holds the exact same one-step authority that H001 describes. H008 is the initial-capture vector; H001 is the ongoing-control vector.
- **H022** — H022 (reinitialization) was correctly dismissed because Anchor `init` blocks it. H008 is the complement: the `init` is only run once, but by whom is unguarded.

## Incidental Discoveries

- The init-config scripts (`server/scripts/init-config.mjs`, `server/scripts/init-config-v2.mjs`) check `getConfigState()` before calling init and abort if the PDA already exists. This is a correct defensive pattern for idempotency but does not help against a race — if the attacker wins, the script silently exits treating the existing (attacker-controlled) config as "already initialized."
