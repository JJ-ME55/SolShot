# H010 — Authority Self-Rotation Across Sequential Txs

**Category:** Tier-3 Vulnerability (multi-TX control flow)  
**Affected Versions:** v1, v2  
**Status:** NOT_VULNERABLE in isolation (distinctness check fires each step)  
**Cross-Reference:** H002 (broader multi-TX rotation chain)  

---

## Finding Summary

**Research Question:** Can authority rotate itself to a different role assignment, bypassing distinctness invariants across a sequence of two or three `update_config` calls?

Example attack:
- TX1: Authority A1 rotates `treasury` to A1, `authority` to A2 (passes distinctness: A2 ≠ A1).
- TX2: Authority A2 rotates `authority` back to A1 (now `authority == treasury` both A1).

**Result:** The distinctness re-validation at v1:96-98 / v2:125-127 fires **after each update**, preventing the final state from ever violating `authority != treasury` or `authority != ops` at settlement time.

---

## Technical Analysis

### Distinctness Check Location
- **v1:** `lib.rs:96-98` (post-update, before ConfigUpdated event)
- **v2:** `lib.rs:125-127` (post-update, before ConfigUpdated event)

### Mechanism

Each `update_config` call:
1. Applies user-supplied optional updates to authority, treasury, ops.
2. Immediately re-validates ALL three pairwise distinctness constraints:
   - `authority != treasury`
   - `authority != ops`
   - `treasury != ops`
3. If any constraint fails, **the entire TX reverts** (Solana's all-or-nothing guarantee).

### Walkthrough: TX1

**Initial state:** `{authority: A1, treasury: T1, ops: O1}` (all distinct)

**Call:** `update_config(authority=A2, treasury=A1, ops=None)`

**After updates (before re-validation):**
```
{authority: A2, treasury: A1, ops: O1}
```

**Distinctness checks fire:**
- `A2 != A1` ✓ (distinct authority, treasury)
- `A2 != O1` ✓ (distinct authority, ops)
- `A1 != O1` ✓ (distinct treasury, ops)

**TX1 commits.** New state: `{authority: A2, treasury: A1, ops: O1}`

### Walkthrough: TX2 (Attempted Authority Self-Redirect)

**Current state:** `{authority: A2, treasury: A1, ops: O1}`

**Call:** `update_config(authority=A1, treasury=None, ops=None)`

**After updates (before re-validation):**
```
{authority: A1, treasury: A1, ops: O1}
```

**Distinctness check fires at v1:96 / v2:125:**
```
require!(config.authority != config.treasury, EscrowError::InvalidConfig);
  // A1 != A1 ??  FALSE — REJECT
```

**TX2 reverts.** State remains: `{authority: A2, treasury: A1, ops: O1}`

---

## Conclusion

The distinctness check is **atomic per TX** and fires AFTER all in-TX updates are applied. There is no observable window where authority can equal treasury within the same instruction.

A would-be attacker cannot "slip through" the check via a multi-step rotation, because each TX's final state is validated before commit.

**Verdict:** **NOT_VULNERABLE in isolation.** Each step's constraints prevent the final state from violating distinctness. Authority cannot end up == treasury via sequential calls.

## Notes

- v2's per-match snapshot (at create) mitigates H002 for in-flight matches but does **not** address H010 directly — H010 is already defended by the distinctness re-check.
- No event replay / MEV ordering issues arise, since each TX is independent and all constraints fire atomically.
- The authority → treasury → authority cycle is thus **structurally impossible** on-chain.
