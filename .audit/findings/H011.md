## Executive Summary

The Feb-2026 H028 dismissal ("BPS constants are hardcoded, only a Layer-1 upgrade can change them") is **inapplicable to v2**. In v2, `fee_bps_treasury` and `fee_bps_ops` are runtime-mutable fields on `GlobalConfig`, writable by the Layer-2 application authority alone via `update_config` with no timelock, no propose/accept, and no per-match re-validation at create or settle time.

A compromised or malicious Layer-2 authority can silently ratchet the combined fee from the default 7%/3% (BPS=700/300) up to 10% combined (MAX_FEE_BPS=1000) on every NEW match created after the config change. Per-match snapshots protect in-flight matches already created, but they offer no protection against poisoning applied to future match creation. Combined with H011's documented self-redirect pattern (rotating `config.treasury` to an attacker-controlled wallet), the attacker captures the full 10% per new match silently and on-chain. The cap holds and cannot be bypassed via multi-step rotation — but the cap is itself the attack surface: up to 10% extraction per match on the current v2 program is achievable with a single Layer-2 key compromise and no program upgrade.

## Investigation Path

### Step 1: What can `update_config` mutate?

**Location:** `programs/solshot-escrow-v2/src/lib.rs:96-142`

`update_config` accepts five `Option` parameters:
- `new_authority: Option<Pubkey>`
- `new_treasury: Option<Pubkey>`
- `new_ops: Option<Pubkey>`
- `new_fee_bps_treasury: Option<u16>`
- `new_fee_bps_ops: Option<u16>`

Each `Some(...)` branch applies the new value to the live `GlobalConfig` PDA. For BPS fields, there is **no per-field validation before assignment** — the raw u16 value is written directly:

```rust
if let Some(t) = new_fee_bps_treasury {
    cfg.fee_bps_treasury = t;           // v2:118-119 — no range check here
}
if let Some(o) = new_fee_bps_ops {
    cfg.fee_bps_ops = o;                // v2:121-122 — no range check here
}
```

Validation fires **post-update** via a combined sum check:

```rust
require!(
    (cfg.fee_bps_treasury as u32 + cfg.fee_bps_ops as u32) <= MAX_FEE_BPS as u32,
    EscrowError::FeesTooHigh
);
```

**Finding:** Any BPS values are assignable if the post-update combined sum stays `≤ 1000`. No per-field cap. No timelock. No propose/accept.

---

### Step 2: Cap effectiveness analysis — single update

**Can a single `update_config` call exceed MAX_FEE_BPS=1000?**

The combined-sum check at v2:128-131 runs on the FINAL state after all five optional fields are applied. Any single call that would push `cfg.fee_bps_treasury + cfg.fee_bps_ops > 1000` is rejected with `FeesTooHigh`.

Test cases (assume initial state: treasury_bps=700, ops_bps=300):

| Call | New treasury_bps | New ops_bps | Combined | Result |
|------|-----------------|-------------|----------|--------|
| Set treasury only to 999 | 999 | 300 (unchanged) | 1299 | REJECTED (1299 > 1000) |
| Set treasury only to 700 | 700 | 300 | 1000 | ACCEPTED (exactly at cap) |
| Set treasury only to 800 | 800 | 300 | 1100 | REJECTED (1100 > 1000) |
| Set treasury to 800, ops to 0 | 800 | 0 | 800 | ACCEPTED |
| Set treasury to 900, ops to 100 | 900 | 100 | 1000 | ACCEPTED (at cap) |
| Set treasury to 1000, ops to 0 | 1000 | 0 | 1000 | ACCEPTED (100% to treasury) |

**Conclusion:** The cap fires correctly on every single-update call. No single transaction can push combined BPS above 1000.

---

### Step 3: Cap effectiveness analysis — multi-step compositional rotation

**Can sequential `update_config` calls exceed the cap across steps?**

Each call re-validates the combined sum post-update. The state after call N is the starting state for call N+1. The cap therefore holds invariantly at every possible state, not just per-call. There is no "in-between" observable state where fees exceed 1000 BPS.

Compositional attack scenario:
- Call 1: `update_config(new_treasury_bps=800, new_ops_bps=None)` → (800, 300 = 1100) → REJECTED
- Call 1': `update_config(new_treasury_bps=700, new_ops_bps=0)` → (700, 0 = 700) → ACCEPTED
- Call 2: `update_config(new_treasury_bps=None, new_ops_bps=300)` → (700, 300 = 1000) → ACCEPTED (same as default)
- Call 1'': `update_config(new_treasury_bps=900, new_ops_bps=100)` → (900, 100 = 1000) → ACCEPTED (at cap)

**Conclusion:** Multi-step rotation CANNOT exceed the cap. The cap is compositionally sound. The attack surface is not "bypass the cap" — it is "operate within the cap to the authority's advantage."

---

### Step 4: Arithmetic agent A02 — does individual BPS > MAX_FEE_BPS pose a risk?

The arithmetic agent (02-arithmetic.md, A02) flagged that individual BPS values are not separately capped. Verify:

- `fee_bps_treasury` is `u16` (max 65,535). The cap check uses `as u32` widening.
- If current `ops_bps = 0` and authority sets `new_fee_bps_treasury = 60_000`: combined = 60,000 + 0 = 60,000 > 1000 → **REJECTED**.
- If current `ops_bps = 0` and authority sets `new_fee_bps_treasury = 1000`: combined = 1000 + 0 = 1000 → ACCEPTED. `fee_bps_treasury=1000` alone means 100% of fees go to treasury (but fees are capped at 10% of pot, so winner still gets 90%).
- If current `ops_bps = 0` and authority sets `new_fee_bps_treasury = 1001`: combined = 1001 > 1000 → **REJECTED**.

**The combined cap always fires. An individual value > 1000 is only achievable if the other value is 0, and at that point the combined sum is still ≤ 1000.** The A02 concern is arithmetic-valid but does not create a bypass pathway. However it does enable an individual value of 1000 (which would send 100% of the 10% fee cap to one account). This is the "max extraction single-account" scenario, not a cap bypass.

### Step 5: Per-match snapshot atomicity verification

**Location:** `programs/solshot-escrow-v2/src/lib.rs:201-219`

```rust
let cfg = &ctx.accounts.config;
let escrow = &mut ctx.accounts.escrow;
// ... (escrow fields set) ...
escrow.treasury_snapshot = cfg.treasury;               // v2:211
escrow.ops_snapshot = cfg.ops;                         // v2:212
escrow.fee_bps_treasury_snapshot = cfg.fee_bps_treasury;  // v2:213
escrow.fee_bps_ops_snapshot = cfg.fee_bps_ops;         // v2:214
escrow.state = MatchState::AwaitingDeposits;           // v2:215
```

Both the snapshot writes and the state initialization happen within the same `create_match` instruction handler. Solana transactions are atomic — either all state writes land, or none do. There is no observable intermediate state where `escrow.state == AwaitingDeposits` but the snapshots contain default values.

**Confirmed:** Snapshot is atomic with create_match.

Grep confirms no other instruction modifies the four snapshot fields after creation:

```rust
// Only assignments in the entire file to *_snapshot fields:
escrow.treasury_snapshot = ...   // v2:211 (create_match only)
escrow.ops_snapshot = ...        // v2:212 (create_match only)
escrow.fee_bps_treasury_snapshot = ...  // v2:213 (create_match only)
escrow.fee_bps_ops_snapshot = ...       // v2:214 (create_match only)
```

**Confirmed:** Snapshots are immutable post-create.

### Step 6: settle_match reads from snapshot, not live config

**Location:** `programs/solshot-escrow-v2/src/lib.rs:396-399`

```rust
let treasury_bps = ctx.accounts.escrow.fee_bps_treasury_snapshot;  // v2:398
let ops_bps = ctx.accounts.escrow.fee_bps_ops_snapshot;            // v2:399
```

The BPS values used in settlement arithmetic come exclusively from `escrow.*_snapshot` fields.

**Location of account constraints:** `v2:715-728`

```rust
#[account(
    mut,
    constraint = treasury.key() == escrow.treasury_snapshot @ EscrowError::InvalidTreasury,
    ...
)]
pub treasury: UncheckedAccount<'info>,

#[account(
    mut,
    constraint = ops.key() == escrow.ops_snapshot @ EscrowError::InvalidOps,
)]
pub ops: UncheckedAccount<'info>,
```

The supplied `treasury` and `ops` accounts are validated against the **snapshot values**, not against live `config.treasury` / `config.ops`. An authority that rotates config AFTER a match is created cannot redirect that match's settlement — the escrow's snapshot is the source of truth.

**Confirmed:** settle_match is fully insulated from post-create config rotation for in-flight matches.

### Step 7: Why the H028 Feb dismissal does NOT apply to v2

The Feb dismissal held that "constants are hardcoded; only a Layer-1 upgrade can mutate BPS." This is true for v1 (`const u64 TREASURY_BPS: u64 = 700`, `const u64 OPS_BPS: u64 = 300` at `v1:15-16`).

In v2, these are NOT constants — they are mutable fields on the `GlobalConfig` PDA:
- Initialized via `initialize_config` args (`v2:65-91`)
- Mutated freely (within cap) via `update_config` by the Layer-2 application authority (`v2:96-142`)

The Layer-2 authority is the `HPyVPj2VH9yBirr7FMgAJeDH8xJgaMKy5UnwLkjSnovk` hot wallet — the same key that holds the Layer-1 upgrade authority. A Layer-2 compromise (hot-wallet key theft without full server access) is sufficient to rotate BPS on all future matches. No program upgrade required.

## Per-Match Snapshot Timeline (v2)

```
T0: config = {treasury: T0_treasury, ops: T0_ops, fee_bps_treasury: 700, fee_bps_ops: 300}

T1: create_match(match_id_A)
    → escrow_A.treasury_snapshot         = T0_treasury
    → escrow_A.ops_snapshot              = T0_ops
    → escrow_A.fee_bps_treasury_snapshot = 700          ← FROZEN here
    → escrow_A.fee_bps_ops_snapshot      = 300          ← FROZEN here
    → escrow_A.state                     = AwaitingDeposits
    [ATOMIC — no observable intermediate state]

T2: update_config(new_treasury=ATTACKER_WALLET, new_fee_bps_treasury=900, new_fee_bps_ops=100)
    → config.treasury         = ATTACKER_WALLET
    → config.fee_bps_treasury = 900
    → config.fee_bps_ops      = 100
    (escrow_A.* is unchanged — in-flight match is PROTECTED)

T3: settle_match(escrow_A, winner=...)
    → treasury account MUST be T0_treasury (constraint at v2:717)
    → BPS used: fee_bps_treasury_snapshot=700, fee_bps_ops_snapshot=300
    → escrow_A is unaffected by T2 change ✓

T4: create_match(match_id_B)     ← NEW match after compromise
    → escrow_B.treasury_snapshot         = ATTACKER_WALLET   ← POISONED
    → escrow_B.fee_bps_treasury_snapshot = 900               ← POISONED
    → escrow_B.fee_bps_ops_snapshot      = 100

T5: settle_match(escrow_B, winner=...)
    → 9% goes to ATTACKER_WALLET, 1% to ops
    → winner receives only 90% (instead of ~90%)
```

Matches created at T1 (before compromise) are protected. Matches created at T4 (after compromise) are poisoned. The boundary is the timestamp of the config change.

## Attack Surface (Within Cap)

| Attack parameter | Value |
|-----------------|-------|
| Max combined BPS redirect | 1000 (10% per match) |
| Default BPS (treasury=700, ops=300) | Combined 1000 — already AT the cap |
| Net redirect possible from defaults | **0 BPS** — defaults are already at the maximum |
| Redirect possible if defaults were lower | Up to (1000 - current_combined) BPS per match |
| Combined with H011 (treasury self-redirect) | Attacker captures full fee split |
| Max pot per match (v2, 10 players) | 1000 SOL × 10% = 100 SOL per match |
| Matches affected | All NEW matches after config change, indefinitely |

**Important nuance:** If the protocol deploys v2 with the DEFAULT BPS of 700/300 (combined = 1000, already at the cap), there is **zero additional extraction headroom**. The attack vector only opens meaningful headroom if the deployed default is BELOW the 1000 cap. For example, if defaults were 500/200 (combined 700), the attacker could ratchet to 700/300 (+300 BPS = +3% per match).

However, the more dangerous compound scenario is:
- Default: 700/300 (at cap)
- `update_config(new_treasury = ATTACKER_WALLET)` → treasury redirected to attacker
- BPS stays at 700/300 → attacker captures full 7% treasury + controls ops wallet → full 10%
- This is the H011 self-redirect chain, which does NOT require BPS rotation at all

## Invariant Analysis

### Target Invariant

The fee split on any match should correspond to the BPS and fee-destination wallets that were agreed to at game creation time, with the treasury and ops wallets being legitimate protocol infrastructure (not attacker-controlled).

### Enforcement Points

| Location | What It Enforces | Complete? |
|----------|-----------------|-----------|
| `v2:76-79` (initialize_config) | Combined BPS ≤ MAX_FEE_BPS=1000 at init | Yes — but allows full 10% extraction |
| `v2:128-131` (update_config) | Combined BPS ≤ MAX_FEE_BPS=1000 at update | Yes — same bound |
| `v2:211-214` (create_match) | Snapshot of config values into escrow | Yes — atomic |
| `v2:715-728` (SettleMatch constraints) | treasury/ops must match snapshot | Yes — protects in-flight |
| Distinctness check v2:125-127 | authority ≠ treasury ≠ ops (pairwise) | Yes — but attacker uses a secondary wallet |
| Authority check: `has_one = authority` | Only authority can call update_config | Yes — but authority IS the attacker under L2 compromise |

### Enforcement Gap Assessment

The invariant "treasury and ops are legitimate protocol addresses" is enforced NOWHERE. The code only enforces: treasury ≠ ops ≠ authority, combined BPS ≤ 1000, and non-zero addresses. An authority can pass any distinct non-zero Pubkeys for treasury and ops — including wallets the authority itself controls. This is the H011 family's root gap.

## Blocking Factors

- `has_one = authority @ EscrowError::Unauthorized` — blocks non-authority callers from `update_config`. `v2:603-613`
- Combined BPS cap (`MAX_FEE_BPS=1000`) — prevents >10% combined extraction. `v2:128-131`
- Per-match snapshot atomicity — protects in-flight matches. `v2:211-214`
- Distinctness check — authority cannot be treasury or ops directly. `v2:125-127`
- ConfigUpdated event — provides off-chain detection opportunity. `v2:133-139`

## Enabling Factors

- Single hot wallet holds both L1 upgrade authority AND L2 application authority — single point of compromise
- `update_config` rotates ALL config fields in one-step TX with no timelock or propose/accept — `v2:96-142`
- Distinctness check only prevents `authority == treasury` directly; a secondary wallet bypasses this — `v2:125-127`
- No per-match re-validation of BPS at settle — if snapshot was taken during a poisoned config window, no downstream guard exists — `v2:387-454`
- Per-match snapshot architecture is a defense only for already-created matches; all future matches are exposed — `v2:201-219`
- No timelock on BPS changes — rotation can happen faster than monitoring can detect and respond

## Exploitation Scenario

### Prerequisites

1. Attacker controls or compromises the `HPyVPj2VH9yBirr7FMgAJeDH8xJgaMKy5UnwLkjSnovk` hot wallet (Layer-2 application authority).
2. Attacker has a secondary wallet (`ATTACKER_TREASURY`) distinct from the authority key and the current ops wallet.
3. The deployed v2 protocol has `fee_bps_treasury + fee_bps_ops < MAX_FEE_BPS=1000`, OR the attacker is satisfied with redirecting the existing fee split to attacker-controlled wallets.

### Attack Steps

1. **TX1 — Redirect treasury to attacker wallet:**
   ```
   update_config(new_treasury=ATTACKER_TREASURY, new_fee_bps_treasury=900, new_fee_bps_ops=100)
   ```
   Combined = 1000 ≤ 1000 → ACCEPTED.

2. **Wait for server to create new matches.** The server calls `create_match` — each new match snapshots `ATTACKER_TREASURY` as treasury and BPS=900/100.

3. **TX2 — Settle each new match** (authority must sign settle anyway):
   ```
   settle_match(match_id_B, winner=ANY_LISTED_PLAYER)
   ```
   Treasury account must be `ATTACKER_TREASURY` (validated by snapshot constraint at v2:717).
   9% of pot flows to `ATTACKER_TREASURY`. 1% to ops (which attacker may also control).

4. **Persist until detected.** If undetected, attacker extracts 9-10% from every new match indefinitely.

### Impact

- **Monetary:** Up to 10% of every new match pot. At MAX_WAGER (100 SOL) × 10 players = 1000 SOL pot: 100 SOL per match. At moderate volume (e.g., 10 matches/day at 2 SOL average wager × 4 players = 8 SOL/match → 0.8 SOL/day = ~$140/day at $175/SOL, indefinitely until detected).
- **Players affected:** All players in NEW matches created after the config change.
- **Detection difficulty:** ConfigUpdated event is emitted, but if monitoring is weak or the attacker moves quickly, multiple matches may be poisoned before intervention.

- All future matches bleed 7-10% to attacker.

## Recommended Fix

### Primary: Add per-BPS-field individual cap

```rust
// Before (v2:118-123): no per-field validation
if let Some(t) = new_fee_bps_treasury {
    cfg.fee_bps_treasury = t;
}
if let Some(o) = new_fee_bps_ops {
    cfg.fee_bps_ops = o;
}

// After: validate each field individually before assignment
if let Some(t) = new_fee_bps_treasury {
    require!(t <= MAX_FEE_BPS, EscrowError::FeesTooHigh);
    cfg.fee_bps_treasury = t;
}
if let Some(o) = new_fee_bps_ops {
    require!(o <= MAX_FEE_BPS, EscrowError::FeesTooHigh);
    cfg.fee_bps_ops = o;
}
```

This closes the A02 concern (individual values cannot individually reach 100% even when combined = 1000).

### Secondary: Add timelock to BPS changes

Introduce a `pending_fee_config` with a minimum delay before taking effect (e.g., 24 hours). This gives users and monitors time to detect and respond before the change affects new matches:

```rust
// In GlobalConfig: add pending fields
pub pending_fee_bps_treasury: Option<u16>,
pub pending_fee_bps_ops: Option<u16>,
```

## Incidental Discoveries

- **BPS=1000/0 (100% to treasury, 0% to ops) is silently valid:** A single call `update_config(new_fee_bps_treasury=1000, new_fee_bps_ops=0)` passes all checks. Winner still gets 90% (the 10% cap applies), but the ops account receives nothing. This may violate operational intent if ops is a separate team. Not a security bug, but an operational edge case.
- **No rate-limiting on update_config:** The authority can call `update_config` once per block (~400ms on Solana). A ratchet-and-revert pattern across many matches in rapid succession is feasible. Consider rate-limiting BPS changes at the protocol level (e.g., minimum 1 epoch between BPS changes).
