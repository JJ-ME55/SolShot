## Executive Summary

The `update_config` instruction (lib.rs:70-89) contains no validation that prevents the authority from setting `config.treasury` equal to their own wallet (`config.authority`). Combined with the absence of any distinctness re-validation after initialization, an authority can redirect 7% of every pot settlement to their own address in a single, silent transaction. When treasury == authority in `SettleMatch`, the authority acts simultaneously as the settlement signer and the treasury fee recipient, receiving the standard 7% treasury fee in addition to the PDA rent refund (`close = authority`, lib.rs:566). There is no constraint anywhere in the `SettleMatch` account struct that requires `treasury.key() != authority.key()`.

This is a specialization of H002 (confirmed fee redirect via `update_config`), but H011 focuses on the specific scenario where the authority sets `treasury = authority's own pubkey`. The key question this investigation answers: does the `SettleMatch` account struct impose any constraint — such as `treasury.key() != authority.key()` — that would block this specific variant? The answer is: no such constraint exists. The `treasury != ops` constraint (lib.rs:588) is present, but there is no `treasury != authority` constraint. The self-redirect variant is fully viable.

---

## Hypothesis Investigated

**H011: Config Treasury Self-Redirect**

Authority can set `treasury == authority`'s own wallet via `update_config`, redirecting 7% of all settlement fees to themselves. Combined with ops redirect, authority captures 10% of all pots beyond their operational role.

*Note: H002 already confirmed fee redirect is possible. This investigates the specific treasury == authority variant and whether the SettleMatch struct has any constraint preventing it (e.g., authority and treasury being different accounts).*

## Investigation Path

### Step 1: Does update_config prevent setting treasury == authority?

**Location:** `lib.rs:70-89` (handler), `lib.rs:464-475` (account struct)

**Finding:** No. The `update_config` handler applies three optional field writes with zero validation on new values. The only guard is the account struct's `has_one = authority` (lib.rs:470), which enforces that the current authority must be the signer — but imposes no constraint on what values can be written into the config fields. There is no `require!(new_treasury != config.authority)` or equivalent.

**Evidence:**
```rust
// lib.rs:70-89
pub fn update_config(
    ctx: Context<UpdateConfig>,
    new_authority: Option<Pubkey>,
    new_treasury: Option<Pubkey>,
    new_ops: Option<Pubkey>,
) -> Result<()> {
    let config = &mut ctx.accounts.config;

    if let Some(a) = new_authority {
        config.authority = a;
    }
    if let Some(t) = new_treasury {
        config.treasury = t;   // Zero validation — t can equal config.authority
    }
    if let Some(o) = new_ops {
        config.ops = o;
    }

    Ok(())
}
```

No `require!` statement in the handler body (beyond what Anchor enforces via the account struct). No re-check of `authority != treasury`, `authority != ops`, or `treasury != ops`. The authority can set `config.treasury = ctx.accounts.authority.key()` with `new_treasury = Some(authority_pubkey)`.

---

### Step 2: Would settle_match succeed if treasury == authority?

**Location:** `lib.rs:560-610` (SettleMatch account struct), `lib.rs:284-291` (lamport transfers)

**Finding:** Yes, `settle_match` succeeds when `treasury == authority`. There is no constraint in the `SettleMatch` account struct that requires `treasury.key() != authority.key()`. The constraints that DO exist are:

1. `treasury.key() == config.treasury` — satisfied because authority set `config.treasury = authority.key()`
2. `treasury.key() != ops.key()` — satisfied as long as ops remains a different address
3. `has_one = authority` on config and escrow — satisfied because the authority signs

When the caller passes their own keypair as both `authority` (signer, lib.rs:571) and `treasury` (UncheckedAccount, lib.rs:581), both `has_one = authority` and `treasury.key() == config.treasury` resolve to the same pubkey and both pass.

**Evidence (complete SettleMatch constraints):**
```rust
// lib.rs:560-610 — SettleMatch account struct
#[derive(Accounts)]
pub struct SettleMatch<'info> {
    #[account(
        mut,
        seeds = [b"match", escrow.match_id.as_bytes()],
        bump = escrow.bump,
        has_one = authority,         // escrow.authority == signer ✓
        close = authority,           // rent goes to authority ✓
    )]
    pub escrow: Account<'info, MatchEscrow>,

    #[account(mut)]
    pub authority: Signer<'info>,    // authority signs

    /// CHECK: Constrained to escrow.player_one or escrow.player_two
    #[account(
        mut,
        constraint = winner.key() == escrow.player_one
            || winner.key() == escrow.player_two
            @ EscrowError::InvalidWinner
    )]
    pub winner: UncheckedAccount<'info>,

    /// CHECK: Constrained to config.treasury; uniqueness check vs ops
    #[account(
        mut,
        constraint = treasury.key() == config.treasury @ EscrowError::InvalidTreasury,
        // NO constraint: treasury.key() != authority.key()
        constraint = treasury.key() != ops.key() @ EscrowError::DuplicateFeeAccount,
    )]
    pub treasury: UncheckedAccount<'info>,

    /// CHECK: Constrained to config.ops
    #[account(
        mut,
        constraint = ops.key() == config.ops @ EscrowError::InvalidOps,
    )]
    pub ops: UncheckedAccount<'info>,

    #[account(
        seeds = [GlobalConfig::SEED],
        bump = config.bump,
        has_one = authority @ EscrowError::Unauthorized,  // config.authority == signer ✓
        constraint = !config.is_paused @ EscrowError::ProgramPaused,
    )]
    pub config: Account<'info, GlobalConfig>,

    pub system_program: Program<'info, System>,
}
```

Critically absent: there is no `constraint = treasury.key() != authority.key()` in the entire struct. When `config.treasury == authority.key()`, passing `authority` as both the signer account AND the treasury account in the same instruction is structurally valid.

---

### Step 3: Solana account model — can the same pubkey appear as both authority (Signer) and treasury (UncheckedAccount)?

**Finding:** Yes. In Solana, the same pubkey can appear in multiple positions in an instruction's account list. Anchor tracks account uniqueness only when both accounts are `Account<'info, T>` types with the same discriminator and both are opened for write — the framework does not prohibit the same underlying account from appearing as both a `Signer<'info>` and an `UncheckedAccount<'info>`.

In this instruction, `authority` is `Signer<'info>` (mutably referenced for the escrow close, lib.rs:570-571) and `treasury` is `UncheckedAccount<'info>` (mutably referenced for lamport credit, lib.rs:588-590). The Solana runtime permits this. The lamport debit from escrow and credit to `treasury` (which IS `authority`) succeeds. Additionally, the `close = authority` attribute on the escrow account sweeps the remaining rent to `authority` at instruction end.

**Net economic effect when treasury == authority:**
- Authority receives: `treasury_amount` (7% of pot) via explicit lamport credit (lib.rs:287-288)
- Authority receives: PDA rent (~0.00143 SOL) via Anchor `close = authority` (lib.rs:566)
- Authority does NOT receive: the `winner_amount` or `ops_amount` (these go to registered players and ops wallet respectively)

### Step 4: Can authority also capture ops (3%) for combined 10% capture?

**Location:** `lib.rs:84-86`, `lib.rs:594-597`

**Finding:** Yes. The same absence of constraints applies to `ops`. The authority can set `config.ops = authority.key()` via `new_ops = Some(authority_pubkey)`. However, doing so while also setting `config.treasury = authority.key()` creates a problem: the `SettleMatch` struct requires `treasury.key() != ops.key()` (lib.rs:588), so if both are the authority's pubkey, that constraint fails with `DuplicateFeeAccount`.

**The constraint:**
```rust
// lib.rs:585-590
#[account(
    mut,
    constraint = treasury.key() == config.treasury @ EscrowError::InvalidTreasury,
    constraint = treasury.key() != ops.key() @ EscrowError::DuplicateFeeAccount,  // <-- blocks both==authority
)]
pub treasury: UncheckedAccount<'info>,
```

**Implication:** The authority cannot simultaneously set `treasury = authority` AND `ops = authority` — the `DuplicateFeeAccount` constraint blocks that. However, the authority can:

- Set `treasury = authority` AND leave `ops` as a separate legitimate ops wallet → captures 7%
- Set `ops = authority` AND leave `treasury` as a separate legitimate treasury wallet → captures 3%
- Set `treasury = attacker_wallet_A` AND `ops = authority` → redirects 3% to self, 7% to attacker
- In the most complete self-enrichment scenario: set `treasury = authority` AND `ops = separate_attacker_wallet` → captures 7% + control of 3% (10% total, split between two authority-controlled keys)

The `treasury != ops` constraint is the ONLY constraint preventing complete consolidation to one address — and it is trivially circumvented by using two distinct authority-controlled addresses.

---

### Step 5: Confirming initialize_config's protections do not survive into update_config

**Location:** `lib.rs:53-55` (initialize_config checks)

**Finding:** `initialize_config` explicitly requires all three addresses to be distinct:
```rust
// lib.rs:53-55
require!(authority != treasury, EscrowError::InvalidConfig);
require!(authority != ops, EscrowError::InvalidConfig);
require!(treasury != ops, EscrowError::DuplicateFeeAccount);
```

None of these three `require!` statements appear in `update_config`. The invariant `authority != treasury` established at initialization is not enforced on any subsequent config update. This is the root gap that makes H011 viable.

## Invariant Analysis

### Target Invariant

The invariant this attack violates: "The authority's role is limited to determining match outcomes (winner selection) and protocol governance; the authority does not receive any portion of the wagered funds as a fee recipient beyond the PDA rent refund that compensates for match creation costs."

More precisely: `config.treasury` and `config.ops` must be addresses distinct from `config.authority`, ensuring that the authority's governance role does not include direct economic extraction from the fee stream.

### Enforcement Points

| Location | What It Enforces | Complete? |
|----------|-----------------|-----------|
| `lib.rs:53-55` | `authority != treasury`, `authority != ops`, `treasury != ops` at initialization | NO — only enforced at init, not on updates |
| `lib.rs:470` `has_one = authority` (UpdateConfig) | Only current authority can update config | YES — but this is the signer gate, not a values gate |
| `lib.rs:587` `treasury.key() == config.treasury` | Settlement sends to stored config address | YES — enforces consistency, but trusts config content |
| `lib.rs:588` `treasury.key() != ops.key()` | Treasury and ops are distinct accounts | YES — prevents complete consolidation to one address, but does NOT prevent treasury == authority |
| `lib.rs:604` `has_one = authority` (SettleMatch config) | Config authority matches settlement signer | YES — but no constraint that signer != treasury |
| `treasury.key() != authority.key()` in SettleMatch | Treasury cannot be authority's own wallet | NOT PRESENT |
| Re-validation of `authority != treasury` in `update_config` | Config remains coherent after updates | NOT PRESENT |

### Enforcement Gap Assessment

The critical missing enforcement point is `treasury.key() != authority.key()` in the `SettleMatch` account struct. The `initialize_config` checks (lib.rs:53-55) are the right model — they enforce three pairwise distinctness requirements. All three of those checks are absent from `update_config`, and the corresponding account-level constraints are absent from `SettleMatch` as well. The system correctly prevents `treasury == ops` at the settlement level (lib.rs:588), demonstrating awareness of the need for distinctness — but does not extend this pattern to `treasury vs. authority` or `ops vs. authority`.

---

## Blocking Factors

- **`has_one = authority` on UpdateConfig (lib.rs:470):** The attacker must first control the authority keypair. An external attacker without the authority private key cannot execute this attack. This is a significant real-world barrier.
- **`treasury.key() != ops.key()` in SettleMatch (lib.rs:588):** Prevents setting BOTH treasury and ops to the authority's own address. The attacker must use at least two distinct keypairs to capture the full 10% (treasury 7% + ops 3%). This is trivially satisfied by using any second keypair under attacker control, but it prevents complete consolidation to a single address.

---

## Enabling Factors

- **No `treasury != authority` constraint in SettleMatch (lib.rs:560-610):** The absence of this constraint is the direct enabler. The same pubkey can validly appear as both the authority signer and the treasury recipient.
- **No re-validation in update_config (lib.rs:70-89):** `update_config` applies writes with zero validation, allowing the post-init `authority == treasury` state to be created.
- **No event emission on config change:** The redirect is entirely silent on-chain until the next `MatchSettled` event (OC-11) reveals the new treasury address after the fact.
- **settle_match reads config at execution time:** There is no snapshot of fee destinations at match creation. All Active matches are affected immediately after the config change, not just future matches.
- **`close = authority` already credits rent to authority:** The authority already receives a rent incentive. The additional 7% treasury capture is an extension of this economic relationship with no on-chain blocker.

## Exploitation Scenario

### Prerequisites

1. Attacker controls the `config.authority` keypair (server hot wallet; single key, no multisig per ARCHITECTURE.md).
2. Attacker has a second keypair to use as ops address (to satisfy `treasury.key() != ops.key()` constraint), OR leaves the legitimate ops address unchanged (capturing only 7% for self, with 3% still going to legitimate ops).

### Attack Steps

**Variant A: Maximum stealth — capture treasury 7% only**
1. Authority calls `update_config(None, Some(authority_pubkey), None)`.
   - `config.treasury` is now set to the authority's own pubkey.
   - No event is emitted. The change is silent.
2. All subsequent `settle_match` calls proceed normally.
   - Authority passes its own pubkey as both `authority` (signer) and `treasury` (UncheckedAccount).
   - All account constraints pass (treasury == config.treasury, treasury != ops, config has_one authority).
   - Lamport transfer at lib.rs:287-288 credits 7% of each pot to authority's own wallet.
   - Additionally, `close = authority` (lib.rs:566) sweeps rent to authority, as always.
3. **Net gain per settled match:** authority receives 7% of pot (treasury fee) + PDA rent.
4. Players see their 90% winnings arrive correctly and are unlikely to investigate.

**Variant B: Full 10% capture using two controlled wallets**
1. Authority calls `update_config(None, Some(authority_pubkey), Some(attacker_ops_wallet))`.
   - `config.treasury = authority_pubkey` (self-directed 7%).
   - `config.ops = attacker_ops_wallet` (attacker-controlled separate key for 3%).
2. Settle calls: treasury (authority self) receives 7%, attacker_ops_wallet receives 3%.
   - Combined: authority-controlled addresses capture 100% of protocol fee revenue.

### Impact

**Per-match impact (at representative wager levels):**
- At 0.1 SOL wager each (0.2 SOL pot): authority captures 0.014 SOL treasury fee per match
- At 1 SOL wager each (2 SOL pot): authority captures 0.14 SOL treasury fee per match
- At 10 SOL wager each (20 SOL pot): authority captures 1.4 SOL treasury fee per match
- At max wager 100 SOL each (200 SOL pot): authority captures 14 SOL treasury fee per match

**Protocol impact:** 7% of every settled pot is continuously drained from the intended treasury. At scale, this represents the entire treasury budget for game development and operations, routed to the authority's own wallet. Players are financially unharmed (90% still goes to winner), making detection difficult without active monitoring of `MatchSettled` event `treasury_account` fields versus known legitimate treasury addresses.

**Combined with H002:** H011 is a specialization of H002 but the treasury == authority variant is more direct — it requires only one authority-controlled address (authority itself) rather than two separate attacker wallets. This means it can be executed without any pre-staged attacker infrastructure.

### Recommended Fix

**Primary fix: Add `treasury != authority` and `ops != authority` constraints to the SettleMatch account struct.**

This mirrors the pattern already used in `initialize_config` and extends the `treasury != ops` enforcement already present in the struct:

```rust
// Current (vulnerable) — lib.rs:585-590
#[account(
    mut,
    constraint = treasury.key() == config.treasury @ EscrowError::InvalidTreasury,
    constraint = treasury.key() != ops.key() @ EscrowError::DuplicateFeeAccount,
)]
pub treasury: UncheckedAccount<'info>,

// Fixed — add authority distinctness checks
#[account(
    mut,
    constraint = treasury.key() == config.treasury @ EscrowError::InvalidTreasury,
    constraint = treasury.key() != ops.key() @ EscrowError::DuplicateFeeAccount,
    constraint = treasury.key() != authority.key() @ EscrowError::InvalidConfig,  // NEW
)]
pub treasury: UncheckedAccount<'info>,
```

And symmetrically for ops:
```rust
// Current (vulnerable) — lib.rs:594-597
#[account(
    mut,
    constraint = ops.key() == config.ops @ EscrowError::InvalidOps,
)]
pub ops: UncheckedAccount<'info>,

// Fixed
#[account(
    mut,
    constraint = ops.key() == config.ops @ EscrowError::InvalidOps,
    constraint = ops.key() != authority.key() @ EscrowError::InvalidConfig,  // NEW
)]
pub ops: UncheckedAccount<'info>,
```

**Secondary fix: Re-validate all three distinctness invariants in `update_config`.**

This prevents the misconfigured state from ever being written to `GlobalConfig`, providing defense-in-depth:

```rust
// Current (vulnerable) — lib.rs:70-89
pub fn update_config(
    ctx: Context<UpdateConfig>,
    new_authority: Option<Pubkey>,
    new_treasury: Option<Pubkey>,
    new_ops: Option<Pubkey>,
) -> Result<()> {
    let config = &mut ctx.accounts.config;
    if let Some(a) = new_authority { config.authority = a; }
    if let Some(t) = new_treasury  { config.treasury = t; }
    if let Some(o) = new_ops       { config.ops = o; }
    Ok(())
}

// Fixed — post-update re-validation mirrors initialize_config
pub fn update_config(
    ctx: Context<UpdateConfig>,
    new_authority: Option<Pubkey>,
    new_treasury: Option<Pubkey>,
    new_ops: Option<Pubkey>,
) -> Result<()> {
    let config = &mut ctx.accounts.config;
    if let Some(a) = new_authority { config.authority = a; }
    if let Some(t) = new_treasury  { config.treasury = t; }
    if let Some(o) = new_ops       { config.ops = o; }
    // Re-enforce all three distinctness invariants after any update
    require!(config.authority != config.treasury, EscrowError::InvalidConfig);
    require!(config.authority != config.ops, EscrowError::InvalidConfig);
    require!(config.treasury != config.ops, EscrowError::DuplicateFeeAccount);
    Ok(())
}
```

The secondary fix alone (in `update_config`) is a strong preventive control. The primary fix (in `SettleMatch`) is a defense-in-depth guard that prevents exploitation even if a corrupted config state exists. Both should be implemented.

## Incidental Discoveries

- **`close = authority` double-dip already exists by design:** Even without H011, the authority currently receives PDA rent on every settlement via `close = authority` (lib.rs:566). This is not a vulnerability — it compensates for creation cost. However, adding the 7% treasury self-redirect on top of this creates a situation where the authority economically benefits significantly more from settlement than from cancellation. This creates a subtle incentive alignment issue: authority profits more per match by settling (rent + 7% treasury) than by cancelling (rent goes to caller, not authority). For large wagers, this incentive strongly favors settlement even when settlement may be inappropriate (e.g., disputed outcome). Suggested new hypothesis: "Does the authority's asymmetric economic benefit from settlement vs. cancellation create perverse incentive for forced settlements in disputed matches?"

- **`ops` field has the same vulnerability as `treasury`:** The investigation focused on treasury but the same absent constraint applies to `config.ops`. ### Test: what happens if same pubkey passed for authority and treasury?

Anchor does not use "duplicate account detection" for mixed account types (`Signer<'info>` vs `UncheckedAccount<'info>`). The `AccountInfo` for the same pubkey is loaded once by the runtime and shared. Lamport mutations are tracked per-account, not per-instruction-position. If `authority.pubkey() == treasury.pubkey()`:

- `close = authority` (at instruction end) credits rent to the authority's account info
- `treasury` lamport credit (lib.rs:288) credits `treasury_amount` to the same account info
- Net result: authority wallet gains `treasury_amount + rent` on the same `AccountInfo`

Solana's runtime handles this correctly (it does not double-count or error on same-pubkey multi-reference in the same instruction). The transaction succeeds.
