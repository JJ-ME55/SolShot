## Executive Summary

The hypothesis correctly identifies that at MIN_WAGER (10,000 lamports), the rent-exempt minimum for the MatchEscrow PDA (~1,430,400 lamports) exceeds the wager by a factor of 143x, creating an unusual economic ratio. However, no exploitable vulnerability exists. The rent cycle is strictly neutral for the authority (pays at creation, recovers at settlement via `close = authority`). No external party can engineer a profitable rent cycling attack because the authority controls match creation and thus controls which parties are registered as players.

The finding degrades to an **economic design concern**: the MIN_WAGER of 10,000 lamports is set approximately 143x below the rent cost to operate a single escrow account. This means the protocol is economically irrational at minimum wager—the authority subsidizes operations with rent far in excess of the wager value. This is a protocol economics warning, not a security vulnerability.

## Hypothesis Investigated

> At minimum wager (10,000 lamports ≈ $0.002), the rent-exempt minimum for the escrow PDA (~1,500,000 lamports) vastly exceeds the wager. Authority pays rent at creation and recovers it at settlement via `close = authority`. This creates unusual economics where rent dominates the economic model.
>
> Investigation:
> 1. Check who pays rent at creation (payer in CreateMatch)
> 2. Check who receives rent at close (close = X in SettleMatch, CancelMatch, PermissionlessReclaim)
> 3. Calculate: at MIN_WAGER, does authority profit from rent cycling?
> 4. Is this exploitable or just an economic design concern?

## Investigation Path

### Step 1: Who pays rent at creation?
**Location:** `lib.rs:512-513` (CreateMatch account struct)
**Finding:** The `authority` account is marked as `payer` for the escrow PDA initialization.
**Evidence:**
```rust
#[account(
    init,
    payer = authority,          // <-- authority pays rent
    space = MatchEscrow::SPACE,
    seeds = [b"match", match_id.as_bytes()],
    bump,
)]
pub escrow: Account<'info, MatchEscrow>,

#[account(mut)]
pub authority: Signer<'info>,
```
The authority (server hot wallet) pays the rent-exempt minimum at every `create_match` call.

### Step 2: Who receives rent at account close?
**Location:** `lib.rs:561-566` (SettleMatch), `lib.rs:615-619` (CancelMatch), `lib.rs:655-659` (PermissionlessReclaim)
**Finding:** The `close =` destination differs by instruction:
- `settle_match`: `close = authority` — rent returns to authority
- `cancel_match`: `close = caller` — rent goes to whoever calls cancel (may be a player)
- `permissionless_reclaim`: `close = caller` — rent goes to any caller

**Evidence:**
```rust
// SettleMatch (lib.rs:561-567)
#[account(
    mut,
    seeds = [b"match", escrow.match_id.as_bytes()],
    bump = escrow.bump,
    has_one = authority,
    close = authority,   // <-- authority recovers rent on settlement
)]
pub escrow: Account<'info, MatchEscrow>,

// CancelMatch (lib.rs:615-620)
#[account(
    mut,
    seeds = [b"match", escrow.match_id.as_bytes()],
    bump = escrow.bump,
    close = caller,      // <-- caller (player or authority) gets rent on cancel
)]
pub escrow: Account<'info, MatchEscrow>,

// PermissionlessReclaim (lib.rs:655-660)
#[account(
    mut,
    seeds = [b"match", escrow.match_id.as_bytes()],
    bump = escrow.bump,
    close = caller,      // <-- any caller gets rent after 48h
)]
pub escrow: Account<'info, MatchEscrow>,
```

### Step 3: Rent magnitude at minimum wager
**Location:** `lib.rs:29`, `lib.rs:739-753` (MatchEscrow::SPACE)
**Finding:** MatchEscrow::SPACE is 168 bytes. At current Solana rent rates, the rent-exempt minimum for 168 bytes is approximately 1,430,400 lamports (~0.00143 SOL), as documented in the token/economic context audit. MIN_WAGER_LAMPORTS is 10,000 lamports.
**Evidence:**
```rust
pub const SPACE: usize = 8 + (4 + 32) + 32 + 32 + 32 + 8 + 1 + 1 + 1 + 8 + 8 + 1; // = 168

const MIN_WAGER_LAMPORTS: u64 = 10_000;
```
Numerical comparison:
- Rent: ~1,430,400 lamports
- MIN_WAGER per player: 10,000 lamports
- Total pot at MIN_WAGER: 20,000 lamports
- **Rent-to-pot ratio: ~71.5x — rent is over 71 times larger than the total wager pot**

### Step 4: Does authority profit from rent cycling?
**Finding:** NO. For a settled match, the rent cycle is economically neutral for the authority:
- Authority pays ~1,430,400 lamports at `create_match`
- Authority recovers ~1,430,400 lamports at `settle_match` (via `close = authority`)
- Net: zero (the rent was never consumed, only temporarily held in the PDA)

The only economic gain to authority from running a match is the treasury + ops fees collected at settlement. At MIN_WAGER:
- treasury_fee = floor(20,000 * 700 / 10,000) = 1,400 lamports
- ops_fee = floor(20,000 * 300 / 10,000) = 600 lamports
- total fees = 2,000 lamports

Transaction costs to run a match (~4 transactions at ~5,000 lamports each) total ~20,000 lamports, which exceeds the 2,000 lamports in fees. The authority **loses approximately 18,000 lamports net** operating the protocol at minimum wager per settled match.

### Step 5: Is there an exploitable path?
**Finding:** No external actor can exploit the rent imbalance because of the match creation access control architecture.

The critical question is: can an attacker force the authority to create low-wager matches so that the authority hemorrhages rent? The answer is **no** — `create_match` is called by the server authority with server-controlled `player_one` and `player_two` pubkeys. The server will only create matches for players who register legitimate game sessions through the application layer.

Even if `create_match` lacks an on-chain `has_one = authority` constraint on the config account (noted as a separate finding), the PDA namespace is under server control via CSPRNG-generated match IDs (per MEMORY.md). An attacker who pre-creates a match PDA wastes their own rent, not the authority's.

The one scenario that causes a real rent loss to the authority is match cancellation, where `close = caller` sends rent to the cancelling player rather than back to the authority. This is examined in the devil's advocate section below.

## Invariant Analysis

### Target Invariant
The hypothesis suggests: "Authority should not be able to profit or be disadvantaged by rent mechanics at any wager level." A corollary concern: "No external party should be able to drain the authority's SOL via rent mechanics."

### Enforcement Points
| Location | What It Enforces | Complete? |
|----------|-----------------|-----------|
| `lib.rs:512-513` | `payer = authority` — authority funds rent | Yes, this is the design |
| `lib.rs:566` | `close = authority` — authority recovers rent on settlement | Yes, rent-neutral on success path |
| `lib.rs:619` | `close = caller` — caller gets rent on cancel | Yes, documented; authority loses rent on cancel path |
| `lib.rs:659` | `close = caller` — any caller gets rent on permissionless reclaim | Yes, by design (DCA-02 incentive) |
| `lib.rs:520-521` | `authority: Signer<'info>` — only authority can create | Partial: no `has_one = config.authority` on CreateMatch |

### Enforcement Gap Assessment
The invariant "authority cannot be drained by external parties via rent" holds because:
1. Only the authority can call `create_match` (authority must sign)
2. Players are only registered by the authority in `create_match`
3. A player calling `cancel_match` only receives the rent from a match the authority voluntarily created

The gap identified (no `has_one` linking CreateMatch to config.authority) means a non-canonical signer could create matches with themselves as authority. However, this creates an unsettleable match and the non-canonical "authority" loses their own rent — it does not drain the protocol authority's funds.

## Blocking Factors

- **Authority-gated match creation**: `create_match` requires `authority: Signer<'info>` (lib.rs:521). External parties cannot create matches that charge the canonical authority's rent.
- **Rent recovery on settlement**: `close = authority` at lib.rs:566 ensures the authority recovers rent precisely on the happy path.
- **No external profit from cycling**: Rent paid = rent recovered for authority in settle path; the math is zero-sum for rent.
- **Server-controlled player registration**: Player pubkeys are embedded by the authority at match creation (lib.rs:134-135). An attacker cannot inject themselves as a player without authority participation.
- **CSPRNG match IDs**: The server uses cryptographically random room IDs (MEMORY.md), preventing an attacker from pre-creating canonical PDAs.

## Enabling Factors

- **MIN_WAGER set 143x below rent cost**: `MIN_WAGER_LAMPORTS = 10,000` (lib.rs:29) while rent is ~1,430,400 lamports. The economic rationale for operations at minimum wager is negative.
- **Cancellation rent loss to authority**: `close = caller` in `cancel_match` (lib.rs:619) means every cancelled match costs the authority ~1,430,400 lamports in unrecovered rent.
- **No minimum wager floor relative to rent**: The program never computes `Rent::get()?.minimum_balance(MatchEscrow::SPACE)` and does not enforce wager >= rent cost. This is a design omission.

## Economic Design Concern (Primary Finding)

While not a security vulnerability, the following design concern warrants documentation:

**The MIN_WAGER (10,000 lamports) is set 143x below the rent cost (~1,430,400 lamports) to operate a single escrow account.**

Consequences:
1. At minimum wager, the authority's rent commitment (~$0.31 USD at 220 USD/SOL) dwarfs the wager pot (20,000 lamports = ~$0.004 USD). The protocol operates at an economic loss for the authority at every minimum-wager match.
2. Every cancelled match is a permanent rent loss of ~1,430,400 lamports to the authority regardless of wager size, since `close = caller` in `cancel_match` and `permissionless_reclaim` directs rent away from the authority.
3. For normal gaming at reasonable wager levels (0.1+ SOL), rent is economically insignificant (<0.15% of pot). The concern only manifests at very low wagers.
4. The intended incentive for `permissionless_reclaim` (the caller receives rent as compensation for submitting the reclaim transaction) is correct design, but it means the authority subsidizes the reclaim incentive regardless of how small the wager was.

**Recommended fix (economic, not security):** Raise `MIN_WAGER_LAMPORTS` to at least the rent-exempt minimum for MatchEscrow (approximately 1,430,400 lamports, ~0.00143 SOL). A safer bound would be 2x-5x rent to ensure the wager value economically justifies operating the escrow:

```rust
// Before
const MIN_WAGER_LAMPORTS: u64 = 10_000; // 0.00001 SOL — below rent cost

// After
const MIN_WAGER_LAMPORTS: u64 = 2_000_000; // ~0.002 SOL — ~1.4x rent cost
// Or compute dynamically (not possible as const, but could be enforced in create_match):
// require!(
//     wager_lamports >= Rent::get()?.minimum_balance(MatchEscrow::SPACE),
//     EscrowError::WagerTooSmall
// );
```

Suggested hypothesis: **H-NEW-A: Authority Rent Drain via Cancelled Matches at Scale** — investigate whether a high cancel rate (induced by e.g. server downtime or the 23-hour dead zone) could create significant ongoing rent losses for the protocol treasury.

## Raw Investigation Notes

### Rent Lifecycle per Instruction
```
create_match:       authority PAYS ~1,430,400 lamports (rent) to Solana runtime
deposit_wager:      no rent change; wager lamports added on top of rent balance
settle_match:       explicit transfers drain wager pot; rent remains; close=authority sweeps ~1,430,400 lamports to authority
cancel_match:       explicit refunds drain wager(s); rent remains; close=caller sweeps ~1,430,400 lamports to CALLER (not authority)
permissionless_reclaim: same as cancel_match; close=caller sweeps ~1,430,400 lamports to ANY CALLER
```

### Authority Rent P&L Per Match Outcome
```
Settled match:   +1,430,400 (rent back) - 1,430,400 (rent paid) = 0 net rent
Cancelled match: +0 (rent goes to caller) - 1,430,400 (rent paid) = -1,430,400 net rent loss
Reclaim match:   +0 (rent goes to any caller) - 1,430,400 (rent paid) = -1,430,400 net rent loss
```

### Arithmetic at MIN_WAGER (10,000 lamports per player)
```
pot = 20,000
treasury = floor(20,000 * 700 / 10,000) = 1,400
ops = floor(20,000 * 300 / 10,000) = 600
winner = 20,000 - 1,400 - 600 = 18,000

Authority fee income: 1,400 + 600 = 2,000 lamports
Authority tx costs: ~4 txs * 5,000 lamports = ~20,000 lamports
Authority rent cost on settle: 0 (recovered)
Authority rent cost on cancel: 1,430,400 lamports
Net on settle (best case): 2,000 - 20,000 = -18,000 lamports (LOSS)
Net on cancel (worst case): 2,000 - 20,000 - 1,430,400 = -1,448,400 lamports (SIGNIFICANT LOSS)
```

### Code Path for Rent Recovery at Settlement
```
settle_match instruction executes:
  1. lib.rs:279: escrow.state = MatchState::Settled
  2. lib.rs:284-291: explicit lamport transfers (winner, treasury, ops)
  3. After instruction: Anchor processes close = authority attribute
     - Sets escrow lamports to 0
     - Transfers remaining balance (which is ONLY rent at this point) to authority
     - Marks account for garbage collection
     - Result: authority receives ~1,430,400 lamports
```

### Why Attacker Cannot Force Authority to Burn Rent
The `create_match` instruction (lib.rs:507-532) requires `authority: Signer<'info>` (line 521). This means:
1. Only someone holding the authority private key can call `create_match`
2. Attackers cannot impersonate the authority on-chain
3. The server application layer (off-chain) determines which matches are created
4. Even if `create_match` lacks `has_one = config.authority` on the config account (a separate finding), the `authority` account must still be the actual transaction signer
5. A non-canonical "authority" creating their own matches uses their own funds for rent, not the protocol authority's funds
