# H013: Lamport Underflow on v2 N-Player Refund Loop (H012 Recheck)

**Status:** NOT VULNERABLE
**Severity:** N/A
**Confidence:** 9/10

> One-line summary: The Feb H012 dismissal holds for v2 — per-iteration bit-set gating prevents the refund loop from debiting beyond `count_ones(deposits_mask) × wager`, and `overflow-checks = true` provides a second defence layer; 10 × 100 SOL = 10^12 lamports is well within u64.

---

## Hypothesis Investigated

Re-validate the Feb H012 dismissal (lamport underflow on cancel/reclaim) against v2's u16 deposits_mask and 10-player surface. Per-iteration `escrow.lamports -= wager` operations in `cancel_match` (v2:502–518) and `permissionless_reclaim` (v2:561–577) rely on the loop invariant that the escrow holds at least `count_ones(deposits_mask) × wager` lamports.

---

## Investigation Path

### Step 1: Per-iteration bit-set gating
**Location:** `programs/solshot-escrow-v2/src/lib.rs:502–510` (cancel) and `561–569` (reclaim)

Both loops are structurally identical:

```rust
for (i, account) in ctx.remaining_accounts.iter().enumerate() {
    require!(i < max_players, EscrowError::InvalidPlayer);          // (a)
    let bit_set = (deposits_mask >> i) & 1 == 1;
    require!(bit_set, EscrowError::InvalidPlayer);                  // (b)
    require!(*account.key == players[i], EscrowError::InvalidPlayer); // (c)

    **ctx.accounts.escrow.to_account_info().try_borrow_mut_lamports()? -= wager_lamports;
    **account.try_borrow_mut_lamports()? += wager_lamports;
}
```

Check (b) at every iteration guarantees the loop body executes **at most once per set bit** in `deposits_mask`. The total number of iterations across the loop's lifetime is therefore bounded by `count_ones(deposits_mask)`. Because each iteration debits exactly `wager_lamports`, the cumulative debit is bounded by `count_ones(deposits_mask) × wager_lamports`.

The escrow PDA was funded by `deposit_wager` via `system_program::transfer`, which credited exactly `wager_lamports` per deposited player and set the corresponding bit in `deposits_mask` (`v2:286–291`). The state transition to `Cancelled` (line 498 / 558) precedes the loop. No instruction credits or debits the escrow between state-write and loop completion within the same atomic TX. Therefore the escrow holds at least `count_ones(deposits_mask) × wager_lamports` when the loop begins — the debit invariant is satisfied.

### Step 2: Overflow-checks profile
**Location:** `Cargo.toml:8–11`

```toml
[profile.release]
overflow-checks = true
```

Per context file `02-arithmetic.md` (A08) this is confirmed present and inherited by both program crates with no per-program override. A raw `u64` underflow that reaches the `-=` operator would **panic** rather than wrap silently. This is a second defence layer.

### Step 3: Max-value ceiling
**Location:** `programs/solshot-escrow-v2/src/lib.rs:31–35`

```
MAX_PLAYERS        = 10
MAX_WAGER_LAMPORTS = 100_000_000_000  // 100 SOL
```

Worst-case escrow balance: `10 × 100_000_000_000 = 10^12 lamports`. This is well below u64::MAX (`~1.8 × 10^19`). No ceiling overflow risk exists on the escrow side. The debit subtraction also has a floor of 0 (guaranteed by invariant above), so no u64 underflow can arise here.

### Step 4: v2 u16 deposits_mask surface vs v1 u8
**Location:** ARCHITECTURE.md, `programs/solshot-escrow-v2/src/lib.rs`

v2 widens `deposits_mask` from `u8` (v1, 4-player cap) to `u16` (v2, 10-player cap). The arithmetic concern would only materalise if bits beyond `max_players` could be set, allowing the loop to iterate more times than there are actual deposits. This is prevented by `deposit_wager` (`v2:261–298`): the player-index is validated `< max_players` before the bit is set, and `max_players <= MAX_PLAYERS = 10`. The u16 mask therefore can have at most 10 bits set, each corresponding to exactly one deposited wager. The larger mask type introduces no new underflow surface.

## Invariant Analysis

### Target Invariant
`escrow.lamports` never goes below 0 at any individual iteration: for each debit step k (0-indexed), `escrow.lamports_at_step_k >= wager_lamports`.

### Enforcement Points

| Location | What It Enforces | Complete? |
|----------|-----------------|-----------|
| `v2:503` | Loop index < max_players | Yes |
| `v2:504–505` | Bit i of deposits_mask must be set | Yes — prevents excess iterations |
| `v2:506` | Account must match registered player at slot i | Yes — prevents slot collisions |
| `v2:286–291` (deposit_wager) | Bit set only on confirmed system_program::transfer | Yes — escrow lamports and mask bit written atomically |
| `Cargo.toml:8–11` | overflow-checks = true panics on u64 underflow | Yes (defence-in-depth) |

### Enforcement Gap Assessment
Enforcement is complete across all v2 cancel/reclaim paths. The invariant `escrow ≥ count_ones × wager` is established by `deposit_wager` and not weakened by any other instruction before the loop runs (state is terminal `Cancelled` by the time the loop executes — no other instruction can touch the PDA after that point in the same TX, and cross-TX re-entry is blocked by the Settled/Cancelled terminal check).

| Protection | Location | How It Works |
|------------|----------|--------------|
| Bit-set gate on each iteration | `v2:504–505`, `v2:563–564` | `require!((deposits_mask >> i) & 1 == 1)` — loop body unreachable unless bit is set |
