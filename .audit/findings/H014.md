## Executive Summary

H014 investigates the specific collusion variant where the authority not only selects the winner dishonestly, but also controls one of the registered player wallets — thereby ensuring the winner is always a controlled account. This variant is **real and viable** at the on-chain level, but it is **fully encompassed by H005**, which already documented, analyzed, and scored this exact attack path including the PoC transaction sequence.

The core mechanism of H014 is enabled by two independently-verified code facts: (1) `create_match` has no `has_one = authority` constraint on `config`, meaning the authority can freely assign any `player_one` and `player_two` pubkeys — including wallets it controls — as match parameters (line 521, `lib.rs`); and (2) the `settle_match` winner constraint only requires the winner to be one of the two registered players (lines 575–580), with no on-chain verification of the actual game outcome. These two facts together mean the authority can plant a controlled wallet as player_one, register a legitimate victim as player_two, wait for the victim to deposit, then settle to the controlled wallet.

**H005 already covers this:** H005's PoC Transaction Sequence (TX 1–4) is precisely this attack. The H014 hypothesis adds no new attack surface beyond what H005 analyzed. Both findings converge on the same POTENTIAL classification, the same CVSS vector, and the same mitigations. This finding documents the overlap, confirms the mechanism through independent code analysis, and notes the one small novelty: H014 explicitly frames the authority's complete control over the player-assignment step of match creation, which H005 mentions as an incidental discovery but does not elevate to a primary finding.

## Hypothesis Investigated

> The `settle_match` winner parameter is constrained to be either player_one or player_two. If the authority controls the game server and always assigns a colluding account as one of the players, they can systematically extract 90% of every pot.

## Investigation Path

### Step 1: Can the authority freely assign any wallet as player_one or player_two?

**Location:** `lib.rs:110–152` (create_match handler), `lib.rs:507–532` (CreateMatch struct)

**Finding:** Yes. The `CreateMatch` account struct requires `authority: Signer<'info>` as the payer (line 521) but applies NO `has_one = authority` constraint on the `config` account. The config account is loaded only for the pause guard (line 527). Therefore, any signer can call `create_match` and assign arbitrary pubkeys to `player_one` and `player_two` — including wallets the authority controls.

The only constraints on the player parameters are:
- `player_one != player_two` (line 125)
- `player_one != authority.key()` (line 128 — OC-06)
- `player_two != authority.key()` (line 129 — OC-06)

OC-06 prevents the authority's own hot-wallet key from being a player. However, the authority can trivially control a second keypair that is not the `config.authority` key and register that second keypair as `player_one`. There is no on-chain verification that registered player addresses correspond to actual human players who consented to the match.

**Evidence:**
```rust
// CreateMatch struct (lib.rs:507–532)
pub struct CreateMatch<'info> {
    #[account(
        init,
        payer = authority,
        space = MatchEscrow::SPACE,
        seeds = [b"match", match_id.as_bytes()],
        bump,
    )]
    pub escrow: Account<'info, MatchEscrow>,

    #[account(mut)]
    pub authority: Signer<'info>,   // Any signer — NOT validated against config.authority

    /// Config PDA — provides pause guard (OC-04)
    #[account(
        seeds = [GlobalConfig::SEED],
        bump = config.bump,
        constraint = !config.is_paused @ EscrowError::ProgramPaused,
        // NOTE: no has_one = authority here
    )]
    pub config: Account<'info, GlobalConfig>,

    pub system_program: Program<'info, System>,
}
```

```rust
// create_match handler (lib.rs:125–135)
require!(player_one != player_two, EscrowError::SamePlayer);
require!(player_one != ctx.accounts.authority.key(), EscrowError::AuthorityAsPlayer);
require!(player_two != ctx.accounts.authority.key(), EscrowError::AuthorityAsPlayer);

let escrow = &mut ctx.accounts.escrow;
escrow.player_one = player_one;   // Set from function parameter — no other validation
escrow.player_two = player_two;   // Set from function parameter — no other validation
```

**Conclusion for Step 1:** Authority controls player assignment completely. OC-06 only prevents using the authority's own hot-wallet key; it does not prevent using a separate, authority-controlled keypair.

### Step 2: Is the winner constrained to the registered players?

**Location:** `lib.rs:573–581` (SettleMatch winner constraint)

**Finding:** Yes. The winner account constraint on `SettleMatch` enforces that the winner must be exactly `escrow.player_one` or `escrow.player_two`. This was confirmed by H005. The constraint fires before the handler body executes, making third-party winner injection impossible.

**Evidence:**
```rust
/// Winner: must be one of the registered players (OC-02 — resolves H008, H002, S001)
/// CHECK: Constrained to escrow.player_one or escrow.player_two
#[account(
    mut,
    constraint = winner.key() == escrow.player_one
        || winner.key() == escrow.player_two
        @ EscrowError::InvalidWinner
)]
pub winner: UncheckedAccount<'info>,
```

**Conclusion for Step 2:** The winner constraint is correctly enforced. Third-party wallet injection is blocked. However, if the authority controls the wallet stored as `escrow.player_one`, then `winner = attacker_wallet` passes the constraint because `attacker_wallet == escrow.player_one` is TRUE.

---

### Step 3: Is there any on-chain verification of game outcome?

**Location:** `lib.rs:228–305` (settle_match handler)

**Finding:** None whatsoever. The handler checks only:
1. Match state is `Active` (line 229–232)
2. Settlement is within the 1-hour deadline (lines 236–244)
3. The winner account satisfies the Anchor constraint (checked before handler runs)

The `winner: Pubkey` argument (line 228) is used solely to route lamports. There is no on-chain game state, no commit-reveal of outcome, no ZK proof, no dispute mechanism. The authority's choice between player_one and player_two is entirely unconstrained.

**Evidence:**
```rust
pub fn settle_match(ctx: Context<SettleMatch>, winner: Pubkey) -> Result<()> {
    require!(
        ctx.accounts.escrow.state == MatchState::Active,
        EscrowError::InvalidState
    );
    // ... settlement deadline check ...
    // NO CHECK: Is `winner` the actual game winner?
    // The program trusts the authority completely for outcome determination.
    // ...
    **ctx.accounts.winner.to_account_info().try_borrow_mut_lamports()? += winner_amount;
```

**Conclusion for Step 3:** There is a complete enforcement gap for game outcome correctness. The authority has sole, unreviewable power to select the winner between the two registered players.

## Invariant Analysis

### Target Invariant

The winner of every settled match must be the actual game winner — preventing the authority from systematically routing the 90% payout to a controlled wallet in matches where the legitimate player actually won.

### Enforcement Points

| Location | What It Enforces | Complete? |
|----------|-----------------|-----------|
| `lib.rs:575–580` | Winner must be `player_one` or `player_two` | Yes — blocks third-party injection, but does NOT block collusion |
| `lib.rs:127–129` | Authority's own key cannot be `player_one` or `player_two` | Partial — blocks authority hot wallet, not a second authority-controlled keypair |
| `lib.rs:565` | Signer must match `escrow.authority` | Yes — prevents unauthorized settlement |
| `lib.rs:604` | Signer must match `config.authority` | Yes — prevents unauthorized settlement |
| `lib.rs:228–305` | Winner is the actual game winner | **NO ENFORCEMENT** — complete gap |

### Enforcement Gap Assessment

The invariant is not enforced. The program enforces only that the winner is one of the two registered players. It cannot enforce that the winner is the correct game winner because game state does not exist on-chain. The `create_match` instruction's lack of a `has_one = authority` constraint on config (lines 524–529) means the authority can populate `player_one` with any wallet it controls, trivially satisfying the winner constraint while routing funds to a controlled address.

## Blocking Factors

- **Third-party winner injection blocked:** `lib.rs:575–580` — Anchor constraint prevents passing any winner that is not `player_one` or `player_two`. This is the constraint H005 verified as complete.
- **Authority cannot be a direct player:** `lib.rs:127–129` — OC-06. The authority's own hot-wallet key is excluded from both player slots.
- **OC-11 event emission:** `lib.rs:293–302` — `MatchSettled` event includes winner and treasury pubkeys. Systematic winner bias is detectable off-chain via event monitoring.

## Enabling Factors

- **Ungated player assignment in create_match:** `lib.rs:110–152` — Authority sets `player_one` and `player_two` as free parameters. No constraint verifies these addresses correspond to actual game participants.
- **No config authority gate on create_match:** `lib.rs:524–529` — Any signer can call `create_match`. The authority routinely creates all matches per system design (MEMORY.md: "creates escrow on joinRoom"), meaning it always controls which wallets are registered.
- **No on-chain game outcome verification:** `lib.rs:228–305` — `settle_match` has zero checks connecting the winner argument to any game state. The authority's selection is unconstrained between the two registered players.
- **OC-06 bypass via second keypair:** `lib.rs:127–129` — OC-06 only excludes `ctx.accounts.authority.key()`, not any wallet the authority happens to control. A trivially-derived secondary keypair is sufficient.
- **No dispute mechanism:** Players cannot challenge a settlement outcome on-chain. The victim's only recourse is off-chain.

## Exploitation Scenario

### Prerequisites

1. Attacker controls `config.authority` (the server keypair) — either by being the operator, or via compromise.
2. Attacker controls at least one additional wallet (call it `colluding_wallet`) that is not the authority key itself. This is trivially satisfied: any keypair the server generates serves this purpose.

### Attack Steps

1. Authority generates `colluding_wallet` (a keypair under its control that is not `config.authority`).
2. Authority calls `create_match` with `player_one = colluding_wallet`, `player_two = victim_wallet`, `wager_lamports = X`.
3. Victim receives invite to play. Victim calls `deposit_wager` for wager amount X.
4. Authority has `colluding_wallet` call `deposit_wager` for wager amount X. Match transitions to Active.
5. Authority calls `settle_match(winner = colluding_wallet)`. Anchor constraint passes: `colluding_wallet == escrow.player_one`.
6. `colluding_wallet` receives 90% of pot. Treasury/ops addresses (also authority-controlled via `update_config`) receive the remaining 10%.
7. Net: authority recovers its own deposit (X) plus victim's deposit (X). Per-match profit = X lamports.

### Impact

- Victim loses entire wager per match.
- At max wager (100 SOL), victim loses 100 SOL per match.
- Attack is repeatable with no on-chain rate limit.
- Attack leaves no on-chain distinguishing mark vs legitimate settled matches — the winner is a registered player and the constraint is satisfied.
- Detectable only by off-chain pattern analysis (the same `player_one` wallet wins in every match).

### PoC Transaction Sequence

```
TX 0 (optional): update_config
  Accounts: config (mut), authority (signer)
  Args: new_treasury = attacker_wallet, new_ops = attacker_wallet
  Prerequisite: Authority controls config.authority
  Result: Future settlements send 10% fees to attacker_wallet

TX 1: create_match
  Accounts: escrow (init), authority (signer/payer), config (pause check only)
  Args: match_id="room-abc", wager_lamports=100_000_000_000,
        player_one=colluding_wallet, player_two=victim_wallet
  Prerequisite: None (create_match has no config authority gate)
  Result: MatchEscrow PDA created; escrow.player_one = colluding_wallet;
          escrow.player_two = victim_wallet; state = AwaitingDeposits

TX 2: deposit_wager (colluding_wallet signs)
  Accounts: escrow (mut), player=colluding_wallet (signer), config
  Args: (none beyond accounts)
  Prerequisite: TX 1 complete
  Result: 100 SOL transferred from colluding_wallet to escrow;
          player_one_deposited = true

TX 3: deposit_wager (victim_wallet signs)
  Accounts: escrow (mut), player=victim_wallet (signer), config
  Args: (none beyond accounts)
  Prerequisite: TX 1 complete (order relative to TX 2 is irrelevant)
  Result: 100 SOL transferred from victim_wallet to escrow;
          player_two_deposited = true; state = Active; activated_at = now

TX 4: settle_match (within 1 hour of TX 3)
  Accounts: escrow (mut, close=authority), authority (signer),
            winner=colluding_wallet, treasury=attacker_wallet, ops=attacker_wallet,
            config
  Args: winner=colluding_wallet
  Prerequisite: Within 1h of activation; Anchor constraint:
                colluding_wallet == escrow.player_one → TRUE → passes
  Result: colluding_wallet receives 180 SOL (90%);
          attacker_wallet (as treasury) receives 14 SOL;
          attacker_wallet (as ops) receives 6 SOL;
          authority receives PDA rent (~0.00143 SOL via close=authority)
          Escrow PDA closed.

Final State: Victim lost 100 SOL. Authority net gain = +100 SOL (victim's wager).
             Repeat TX 1–4 for each new victim. No on-chain rate limiting.
```

**Verification that all steps are possible:**
- TX 0: `update_config` requires `config.authority` signer — attacker controls this. POSSIBLE.
- TX 1: `create_match` has no `has_one = authority` on config — any signer can call it. POSSIBLE.
- TX 2: `deposit_wager` requires the player to be `escrow.player_one` — `colluding_wallet` is registered. POSSIBLE.
- TX 3: `deposit_wager` requires `victim_wallet` — victim deposits voluntarily. POSSIBLE (requires victim cooperation, which is the off-chain social engineering component).
- TX 4: `settle_match` requires signer to match both `escrow.authority` and `config.authority` — both are the same authority key. `winner = colluding_wallet`, and `colluding_wallet == escrow.player_one`. POSSIBLE.

### Recommended Fix

Mitigations are identical to H005. In order of increasing implementation cost:

**1. Off-chain monitoring (Low cost):**
OC-11 `MatchSettled` event (lines 293–302) emits winner and fee destination pubkeys. Monitor for: any `update_config` transaction; the same player_one wallet winning an anomalous proportion of matches; treasury/ops address changes.

**2. Multisig authority (Medium cost):**
Replace the single server hot wallet with a multisig (e.g., Squads). Prevents single-key compromise from enabling systematic player-stuffing.

**3. Add `has_one = authority` to CreateMatch (Low code cost):**
This is the most direct mitigation for the H014-specific player-stuffing vector. Adding a `has_one = authority` constraint to the `config` account in `CreateMatch` would ensure only the legitimate server authority can create matches:

```rust
// Before (vulnerable — no config authority gate):
#[account(
    seeds = [GlobalConfig::SEED],
    bump = config.bump,
    constraint = !config.is_paused @ EscrowError::ProgramPaused,
)]
pub config: Account<'info, GlobalConfig>,

// After (gates match creation to config.authority):
#[account(
    seeds = [GlobalConfig::SEED],
    bump = config.bump,
    has_one = authority @ EscrowError::Unauthorized,
    constraint = !config.is_paused @ EscrowError::ProgramPaused,
)]
pub config: Account<'info, GlobalConfig>,
```

Note: This mitigation only constrains WHO can create matches; it does NOT prevent a malicious authority from still stuffing controlled wallets as players. A fully malicious operator can still execute this attack — the fix narrows the attack surface to only the current `config.authority`, which is the actual threat model anyway.

**4. Commit-reveal winner scheme (High code cost):**
As recommended by H005: have the server commit a winner hash at match creation or activation, then verify at settlement. Makes pre-settlement manipulation detectable after the fact but does not prevent it by a determined malicious operator.

### Why POTENTIAL and Not CONFIRMED

The attack is fully viable from a code perspective — every step can be executed with no code-level blocker. It is classified POTENTIAL (not CONFIRMED) because:
1. It requires a precondition outside the smart contract: the authority must be malicious or compromised.
2. This precondition is not trivially satisfiable by an arbitrary external adversary.
3. The protocol explicitly declares this a trust boundary ("server hot wallet" in GlobalConfig comment, line 692).

If the threat model is extended to include malicious insiders or a compromised server key, this finding upgrades to CONFIRMED.

H005's "Incidental Discoveries" section explicitly states: "Authority creates match with controlled player wallets: `lib.rs:110–151` — The `create_match` instruction has no constraint requiring the signer to match `config.authority`. This means the authority can set `player_one` to any wallet it controls." H005 then suggests this as a new hypothesis ("H005a: Create-match player stuffing").
