# H015: Lamport Credit Overflow on Destination Accounts

**Severity:** LOW  
**Status:** NOT_VULNERABLE under realistic conditions; defense-in-depth gap  
**Affected Code:** v1 `lib.rs:317-324, 408-409, 476-477`; v2 `lib.rs:434-441, 508-509, 567-568`

---

## Summary

Destination account lamport credits in `settle_match`, `cancel_match`, and `permissionless_reclaim` use bare `+=` without overflow protection. If a recipient's balance approaches u64::MAX, the operation panics (debug) or wraps (release). **Practically unreachable but not formally safe.**

---

## Technical Details

### Vulnerable Pattern (4 sites per version)

```rust
// settle_match
**dest.try_borrow_mut_lamports()? += wager_lamports;  // No checked_add

// cancel_match refund loop
**account.try_borrow_mut_lamports()? += wager_lamports;

// permissionless_reclaim refund loop
**account.try_borrow_mut_lamports()? += wager_lamports;
```

### Quantitative Analysis

| Metric | Value | Interpretation |
|--------|-------|-----------------|
| u64::MAX | 1.8 × 10^19 lamports | 1.8 × 10^10 SOL |
| Solana circulating supply | ~588M SOL | 30× smaller than max required |
| Per-match ceiling | 100 SOL × 10 players = 1000 SOL | 10^12 lamports — escrow remains safe |
| Single recipient accumulation | Many settlements | Debit side bounded; credit side across many TXs practically unreachable |

### Why Not Vulnerable

1. **Total Solana supply** is ~588M SOL. An attacker would need to accumulate **1.8 billion SOL** in a single address to trigger overflow — 30× the entire protocol's supply.
2. **Escrow account balance** is bounded: wager × max_players = 100 SOL × 10 = 1000 SOL = 10^12 lamports, well below u64::MAX.
3. **Debug builds** panic on overflow (overflow-checks=true enforced in Cargo.toml:8-11); release builds wrap silently but require u64 rollover, practically impossible.
4. **Multiple settlements across time** could theoretically accumulate lamports in a fee destination or winner wallet, but reaching 1.8 billion SOL is economically infeasible.

---

## Defense-in-Depth Recommendation

Convert bare `+=` to safe `checked_add`:

```rust
// Current (defense gap)
**dest.try_borrow_mut_lamports()? += amount;

// Recommended (defense-in-depth)
let new_balance = dest.try_borrow_mut_lamports()?
    .checked_add(amount)
    .ok_or(EscrowError::ArithmeticOverflow)?;
*dest.try_borrow_mut_lamports()? = new_balance;
```

---

## Conclusion

**Not a vulnerability under realistic conditions** — requires 1.8 billion SOL (30× protocol supply) to trigger. However, adding `checked_add` hardens the code against theoretical extreme-case scenarios and matches the mature arithmetic practices already used in BPS calculations (u128 widening + checked_* at `lib.rs:342-350`).

**Estimated effort:** Low (5 min, 4 sites per version).
