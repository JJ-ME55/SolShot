# H017: v1 Silent-Kick Attack via `start_with_depositors`

**Status:** CONFIRMED
**Severity:** HIGH
**Confidence:** 9/10
**Affects:** v1 only (v2 fixed at v2:332-339)

---

## Executive Summary

v1's `start_with_depositors` instruction (v1:493-536) contains **no timing gate**. The only preconditions are `state == AwaitingDeposits` and `deposits_mask.count_ones() >= 2`. The authority can therefore call this instruction the instant two deposits land — even if other players have broadcast deposit transactions that are still in flight across the network.

When the instruction executes, it compacts the `players[]` array to contain only the deposited players, zeros out the remaining slots (`Pubkey::default()`), and sets `state = Active`. Any in-flight `deposit_wager` from a player whose slot was just zeroed will then fail the `state == AwaitingDeposits` check at v1:196 (because state is now `Active`). That player loses their transaction fees and their wager slot; they are permanently excluded from the match.

v2 fixes this precisely: it requires `Clock::get()?.unix_timestamp >= created_at + deposit_window_secs` (v2:332-339) before compaction can run, guaranteeing players have their full advertised window to deposit.

---

## Hypothesis Investigated

> v1's `start_with_depositors` has NO timing gate (only requires `state == AwaitingDeposits` and `num_deposited >= 2`). Authority can call it the moment 2 deposits land, silently kicking late-broadcasting players whose TXs are mid-flight.
>
> Attack: 1. Match has `max_players = 4`. Players P1, P2 deposit. P3 broadcasts deposit TX (~400ms latency to leader). 2. Authority observes P3's deposit in mempool. 3. Authority front-runs with `start_with_depositors`. Compaction reduces `max_players` to 2; `players[2,3]` become `Pubkey::default()`. 4. P3's `deposit_wager` TX arrives, fails on `state == Active` check or `position()` lookup. P3 paid TX fees + lost a slot.
>
> v2 fixes this with `Clock::get >= deposit_deadline` gate at v2:336-339.

## Investigation Path

### Step 1: v1 `start_with_depositors` handler guards (v1:493-536)

**Location:** `programs/solshot-escrow/src/lib.rs:493-536`

The handler opens with exactly two `require!` guards:

```rust
// v1:494-497
require!(
    ctx.accounts.escrow.state == MatchState::AwaitingDeposits,
    EscrowError::MatchAlreadyStarted
);

// v1:499-500
let num_deposited = ctx.accounts.escrow.deposits_mask.count_ones();
require!(num_deposited >= 2, EscrowError::TooFewPlayers);
```

**Finding:** Two guards only — state check and minimum depositor count. **No `Clock::get()` call. No comparison against `created_at`, `deposit_deadline`, or any elapsed-time expression whatsoever.**

### Step 2: v1 `StartWithDepositors` account struct (v1:756-777)

**Location:** `programs/solshot-escrow/src/lib.rs:756-777`

```rust
pub struct StartWithDepositors<'info> {
    #[account(
        mut,
        seeds = [b"match", escrow.match_id.as_bytes()],
        bump = escrow.bump,
        has_one = authority,
    )]
    pub escrow: Account<'info, MatchEscrow>,

    pub authority: Signer<'info>,

    #[account(
        seeds = [GlobalConfig::SEED],
        bump = config.bump,
        has_one = authority @ EscrowError::Unauthorized,
        constraint = !config.is_paused @ EscrowError::ProgramPaused,
    )]
    pub config: Account<'info, GlobalConfig>,
}
```

**Finding:** Account-level constraints add:
- `has_one = authority` — caller must be `escrow.authority` (prevents non-authority use)
- `!config.is_paused` — pause guard
- PDA seed re-derivation — canonical PDA validation

No timing constraint exists at the struct level either. The full guard surface is: (a) not paused, (b) authority signer, (c) state == AwaitingDeposits, (d) ≥2 deposits. That is the complete list.

### Step 3: v1 compaction logic (v1:507-524)

**Location:** `programs/solshot-escrow/src/lib.rs:507-524`

```rust
let deposits_mask = escrow.deposits_mask;
let max = escrow.max_players as usize;
let mut compacted = [Pubkey::default(); 4];
let mut new_mask: u8 = 0;
let mut j = 0usize;
for i in 0..max {
    if (deposits_mask >> i) & 1 == 1 {
        compacted[j] = escrow.players[i];
        new_mask |= 1u8 << j;
        j += 1;
    }
}
escrow.players = compacted;
escrow.deposits_mask = new_mask;
escrow.max_players = j as u8;
escrow.state = MatchState::Active;
escrow.activated_at = Clock::get()?.unix_timestamp;
```

**Finding:** Compaction iterates original `players[0..max_players]`. Only entries where the deposit bit is set are copied into `compacted[]`. The remaining slots of `compacted` are initialised to `Pubkey::default()` (the Rust default). Then:
- `escrow.players` is **fully replaced** by `compacted` — non-depositors' pubkeys are **overwritten with `Pubkey::default()`**
- `escrow.max_players` is reduced to `j` (count of depositors)
- `escrow.state` is set to `Active`

Any player whose pubkey was in the original `players[i]` slot but whose deposit bit was not set is now completely gone from the escrow account. Their `Pubkey::default()` slot cannot be matched by `deposit_wager`'s `position()` lookup.

### Step 4: v1 `deposit_wager` failure path for a kicked player (v1:195-198)

**Location:** `programs/solshot-escrow/src/lib.rs:195-198`

```rust
require!(
    ctx.accounts.escrow.state == MatchState::AwaitingDeposits,
    EscrowError::InvalidState
);
```

The first check in `deposit_wager` is the state check. After `start_with_depositors` sets `state = Active`, any arriving `deposit_wager` TX for the same match immediately fails here with `InvalidState`. The SOL lamports are never transferred (state check is before the CPI). The player loses only their transaction fee (~5,000 lamports).

Notably, even if the state check were absent, the player would also fail at the `position()` lookup (v1:201-204) because their pubkey has been zeroed from `escrow.players` during compaction.

### Step 5: v2 timing gate confirmation (v2:332-339)

**Location:** `programs/solshot-escrow-v2/src/lib.rs:332-339`

```rust
// v2:332-335 — compute deposit_deadline
let deposit_deadline = ctx.accounts.escrow.created_at
    .checked_add(ctx.accounts.escrow.deposit_window_secs as i64)
    .ok_or(EscrowError::ArithmeticOverflow)?;

// v2:336-339 — enforce: window must have closed
require!(
    Clock::get()?.unix_timestamp >= deposit_deadline,
    EscrowError::DepositWindowOpen
);
```

**Finding:** v2 reads `escrow.deposit_window_secs` (a per-match configurable duration set at `create_match`) and computes `deposit_deadline = created_at + deposit_window_secs`. The `require!` macro enforces that the current on-chain clock has reached or passed this deadline. If the deposit window is still open, the instruction fails with `DepositWindowOpen`. This completely prevents premature compaction — no matter how many deposits have landed, the authority cannot kick stragglers until the deposit window expires.

The v2 comment at v2:321 makes the intent explicit: "Only callable AFTER the deposit window closes — prevents prematurely kicking stragglers."

## Attack Path Analysis

### Can the attacker...

| Step | Required Action | Possible? | Evidence |
|------|-----------------|-----------|---------|
| 1 | Create a match with `max_players = 4` and a known set of players | Yes | Authority-only instruction, no restriction on match parameters |
| 2 | Observe mempool: wait for exactly 2 deposit TXs to confirm | Yes | RPC subscription to program events; `WagerDeposited` events emitted at v1:228-232 |
| 3 | Submit `start_with_depositors` TX to compact to 2 players | Yes | No timing guard; state == AwaitingDeposits; num_deposited == 2; pause not set |

| 6 | Match proceeds as 2-player match; P3/P4 excluded | Yes | `escrow.max_players == 2`; P3/P4 pubkeys are `Pubkey::default()` |

### What does NOT happen (important for severity calibration)

- P3/P4 do NOT lose their wager (deposit CPI is after the state check, which now fails)
- P3/P4 are NOT locked into any contract
- Authority does NOT gain P3/P4's funds (there are none to gain — they never transferred)

## Invariant Analysis

### Target Invariant

"A player who deposits within their advertised time window should not be silently excluded from the match."

Equivalently: "The set of eligible depositors should remain stable for the advertised deposit window."

### Enforcement Points

| Location | What It Enforces | Complete? |
|----------|-----------------|-----------|
| v1:494-497 | State == AwaitingDeposits | Partial — correct state, not sufficient |
| v1:499-500 | num_deposited >= 2 | Partial — minimum floor, not a ceiling on timing |
| v2:332-339 | `now >= deposit_deadline` | **Complete** — time gate prevents premature compaction |

### Enforcement Gap Assessment

In v1, the invariant is NOT enforced. The only protection against premature compaction is (1) the authority acting honestly, and (2) the fact that compaction can only happen when `state == AwaitingDeposits`. There is no on-chain mechanism that prevents the authority from acting within seconds of a match being created if two deposits are available.

The gap is structural: v1's `MatchEscrow` does not even store a `deposit_window_secs` field. The field only exists in v2 (added as part of the deposit-window feature). Without this field on-chain, there is no deadline to check.

## Blocking Factors

- `config.is_paused` (`v1:774`): Not a practical blocker — authority controls the pause flag.
- `has_one = authority` (`v1:763, 773`): Limits the attack to the authority itself, not any anonymous party. This is the correct access control — but it means the attack is an **authority-initiated griefing**, not an external exploit.
- `state == AwaitingDeposits` (`v1:494-497`): The match must not already be active. Not a blocker in normal timing.

---

## Enabling Factors

- **No `deposit_window_secs` field in v1's `MatchEscrow`** (`v1:808-830`): The struct stores `created_at` and `activated_at` but no deposit-window duration. No deadline can be computed on-chain.
- **No `Clock::get()` call in v1 `start_with_depositors`** (`v1:493-536`): Even if `created_at` were available and a deposit window were defined, no clock check is performed.
- **Compaction immediately overwrites non-depositor pubkeys** (`v1:510-521`): Once the instruction runs, kicked players are unrecoverable from the match account.
- **Authority fully controls the server/mempool timing** (`v1:769`): As the entity running `start_with_depositors`, the authority can choose precisely when to submit the transaction, including immediately after seeing the second deposit.

## Exploitation Scenario

### Prerequisites

1. Authority controls the server wallet.
2. A match exists with `max_players = 4` and all four players are known.
3. At least P1 and P2 have deposited (2 deposits minimum to meet `num_deposited >= 2`).
4. P3 has broadcast (or is about to broadcast) a deposit TX.

### Attack Steps

1. Authority creates the match with `max_players = 4`, listing P1, P2, P3, P4 — all legitimate players, all expecting to participate.
2. P1 deposits. P2 deposits. Both TXs confirm. `deposits_mask = 0b0011`.
3. P3 signs and broadcasts their `deposit_wager` TX. It is now in the mempool with ~400ms typical finality.
4. Authority (server process) detects two confirmed deposits via RPC event or polling.
5. Authority immediately submits `start_with_depositors` with a competitive priority fee.
6. Authority's TX lands in the current slot (or next slot). On-chain state: `max_players = 2`, `players = [P1, P2, Pubkey::default(), Pubkey::default()]`, `state = Active`.
7. P3's in-flight `deposit_wager` arrives. Execution reaches v1:196: `state != AwaitingDeposits` → revert `InvalidState`. P3's lamports are not transferred; P3 pays ~5,000 lamports in TX fees.
8. Same for P4, if they had a TX in flight.
9. Match proceeds as a 2-player match. P1 and P2 play. Authority settles normally.

**Passive variant (no front-running required):** Even without deliberate timing manipulation, organic network latency creates a window. If P3 is on a slow RPC or a geographically distant node, their TX may naturally arrive after `start_with_depositors` lands — even if authority called it only after the deposit window the server announced informally to players. The on-chain program has no record of that informal window and cannot enforce it.

### Impact

- P3 and P4 are excluded from a match they agreed to join and planned to play.
- P3/P4 lose TX fees (~5,000 lamports ≈ $0.0008 each at current devnet rates; higher on mainnet congestion).
- P3/P4's opportunity to compete in the match is permanently lost (the slot is gone; no rejoin path exists).
- Authority can systematically disadvantage specific geographic regions (players with high-latency RPC connections are disproportionately vulnerable).
- For high-wager matches, being excluded from a match the player expected to win represents a significant indirect loss of expected value — though no funds are directly drained.

## Why v2 Fixes It

v2 introduced `deposit_window_secs` as a per-match parameter (set at `create_match`) stored on the `MatchEscrow` account. The `start_with_depositors` handler computes:

```rust
let deposit_deadline = ctx.accounts.escrow.created_at
    .checked_add(ctx.accounts.escrow.deposit_window_secs as i64)
    .ok_or(EscrowError::ArithmeticOverflow)?;
require!(
    Clock::get()?.unix_timestamp >= deposit_deadline,
    EscrowError::DepositWindowOpen
);
```

This is an on-chain, clock-verified gate. No matter how many deposits have already landed, the authority cannot compact the array until the deposit deadline has passed on Solana's clock. Players therefore have until `deposit_deadline` to submit their deposit TX. If their TX arrives before the deadline, it is valid even if `start_with_depositors` is called immediately after.

The fix requires the `deposit_window_secs` field to be present on the `MatchEscrow` struct — a structural addition that is absent from v1. A backport to v1 would require adding this field (with attendant SPACE update and migration).

## Proof of Concept Outline

1. **Setup:** Deploy a v1 match with 4 players on devnet. Two players (controlled wallets) deposit immediately. One player (P3) prepares a deposit TX but does not broadcast yet.
2. **Attack:** Authority calls `start_with_depositors` with no other arguments. Verify the instruction succeeds (no `DepositWindowOpen` error). Verify on-chain state: `max_players == 2`, `players[2] == Pubkey::default()`.
3. **Victim TX:** Broadcast P3's previously-prepared deposit TX. Verify it reverts with `InvalidState` (`0x1770` or equivalent Anchor error).
4. **Confirm damage:** P3's wallet shows no balance change (TX fee loss only). `escrow.players` does not contain P3.
5. **Result:** Confirmed — authority-initiated silent kick is possible with zero on-chain resistance.

## Recommended Fix

Add a minimum deposit window check to v1's `start_with_depositors` handler.

**Option A — Minimal backport (hardcoded minimum window):**

```rust
// Before (vulnerable) — v1:493-500
pub fn start_with_depositors(ctx: Context<StartWithDepositors>) -> Result<()> {
    require!(
        ctx.accounts.escrow.state == MatchState::AwaitingDeposits,
        EscrowError::MatchAlreadyStarted
    );
    let num_deposited = ctx.accounts.escrow.deposits_mask.count_ones();
    require!(num_deposited >= 2, EscrowError::TooFewPlayers);
    // ... (no timing check)

// After (fixed) — insert after the two require! guards:
    const MIN_DEPOSIT_WINDOW_SECS: i64 = 30; // minimum 30s for deposits to propagate
    let earliest_start = ctx.accounts.escrow.created_at
        .checked_add(MIN_DEPOSIT_WINDOW_SECS)
        .ok_or(EscrowError::ArithmeticOverflow)?;
    require!(
        Clock::get()?.unix_timestamp >= earliest_start,
        EscrowError::DepositWindowOpen  // reuse or add this error variant
    );
```

**Option B — Full v2 backport (preferred):**

Add `deposit_window_secs: u32` to `MatchEscrow` struct, update `SPACE` constant, pass `deposit_window_secs` as a parameter to `create_match`, and backport v2's full timing gate at v1:500-506. This aligns v1 and v2 behavior and is the architecturally correct fix, though it requires a program upgrade and potential account migration.

**Option A is the lower-cost mitigation.** Even a 30-second hardcoded window is sufficient to ensure in-flight TXs from any global network node have time to land before compaction can occur. The deposit timeout is already 600 seconds (v1 `TIMEOUT_SECONDS`), so a 30-second minimum window does not materially change the UX for honest operator behavior.

## Raw Investigation Notes

### Guard enumeration — v1:493-500 (complete)

```
Guard 1: v1:494-497  — state == AwaitingDeposits
Guard 2: v1:499-500  — deposits_mask.count_ones() >= 2
(no Guard 3)
```

There are zero additional `require!` macro invocations and zero `if ... { return err!(...); }` patterns between v1:500 and the start of the compaction at v1:507. The handler body is fully visible in a single read. The absence of a timing guard is certain.

### v1 MatchEscrow fields relevant to timing

```rust
pub created_at: i64,   // v1:824 — set at create_match
pub activated_at: i64, // v1:827 — set at 0, updated at activation
```

No `deposit_window_secs` field. No deposit deadline is derivable on-chain from v1 state alone (the server may have communicated an informal window off-chain, but it cannot be enforced by the program). The minimum viable fix (Option A) requires only `created_at` (already stored) plus a new hardcoded constant.

### v2 MatchEscrow fields relevant to timing (for comparison)

```rust
pub deposit_window_secs: u32,  // v2 only — set at create_match
pub created_at: i64,           // same as v1
```

The `deposit_window_secs` field is the structural addition that makes the v2 timing gate possible. Without it (v1), only a hardcoded constant can be used.

### Confidence justification (9/10)

All relevant code was read directly. The attack requires authority participation (PR=High), which is the only uncertainty — it depends on whether the authority key acts maliciously or is under adversarial control. The structural vulnerability (no timing gate) is a 10/10 certainty. The deduction from 10 to 9 reflects the single real-world precondition: the attack is only damaging if the authority uses it against players, which requires either a malicious operator or a compromised server key. Both are plausible threat models for an audited wagered protocol.
