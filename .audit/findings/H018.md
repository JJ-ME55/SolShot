# H018: Deposit-Window Edge Collision at deposit_deadline

**Status:** CONFIRMED edge case  
**Severity:** MEDIUM  
**Affected Program:** solshot-escrow-v2  
**Affected Instructions:** `deposit_wager` (v2:255-262) + `start_with_depositors` (v2:333-339)

---

## Summary

At exactly T = `deposit_deadline`, both `deposit_wager` and `start_with_depositors` are valid according to their time-window checks. This creates a race condition where the outcome (deposit succeeds vs. deposit rejected + match starts) depends on non-deterministic Solana leader ordering.

```
deposit_wager check (line 257):
  require!(Clock::get()?.unix_timestamp <= deposit_deadline, ...)
                                          ^
                                      INCLUSIVE (≤)

start_with_depositors check (line 336):
  require!(Clock::get()?.unix_timestamp >= deposit_deadline, ...)
                                          ^
                                      INCLUSIVE (≥)

At T == deposit_deadline, both pass simultaneously → race.
```

---

## Scope of Impact

**Non-deterministic outcome:** When two transactions arrive at the same block-slot with T ≈ deposit_deadline:

- **Path A wins** (leader includes deposit_wager first):
  - Player's deposit lands in AwaitingDeposits state.
  - If this is the last depositor, match activates.
  - Player correctly deposited.

- **Path B wins** (leader includes start_with_depositors first):
  - Match compacts to Active state (with N-1 depositors, excluding this slow player).
  - Subsequent deposit_wager fails: state != AwaitingDeposits.
  - Player's SOL is undeposited; they are not a participant.

**Economic consequence:** A slow network player intended to deposit but is silently excluded from the match. They incur no loss (SOL not locked) but lose the game slot they thought was reserved.

---

## Root Cause

Both bounds are **inclusive** to permit edge-case timing:

1. `deposit_wager` uses `≤` to allow deposits AT the deadline instant (not just before).
2. `start_with_depositors` uses `≥` to allow activation AT the deadline instant (not just after).

This is technically correct for their individual semantics, but creates an overlap at the boundary.

---

## Severity Justification

**MEDIUM** because:

- **Positive:** Both code paths are valid. The "losing" TX simply fails cleanly on state-transition; no fund loss or bypass of authorization.
- **Negative:** Non-deterministic outcome in a betting protocol is problematic. A player entering last (intentionally) may be excluded due to network timing, creating a griefing vector.
- **Exploitability:** Low in live devnet conditions; race window is ~1 slot (400ms). High under adversarial conditions (malicious leader or priority-fee wars).

---

## Recommended Fix

**Option 1: Tighten deposit_wager to exclusive upper bound (safer for game fairness)**

```rust
// Line 257 — change from <= to <
require!(
    Clock::get()?.unix_timestamp < deposit_deadline,  // Reject at T == deadline
    EscrowError::DepositWindowClosed
);
```

**Rationale:**
- Deposit window closes strictly AT deposit_deadline (not including it).
- Players must deposit BEFORE deadline; no overlap with start_with_depositors.
- Matches the intent of `start_with_depositors` requiring clock >= deadline.
- One-line fix; no state changes.

**Option 2: Tighten start_with_depositors to exclusive lower bound**

```rust
// Line 336 — change from >= to >
require!(
    Clock::get()?.unix_timestamp > deposit_deadline,  // Allow only strictly after deadline
    EscrowError::DepositWindowOpen
);
```

**Rationale:**
- Authority must wait for deadline to pass; small extra delay acceptable.
- Slightly looser (allows 1-slot grace), but also valid.

**Option 1 is preferred** because it gives the deposit window the full window_secs interval and then closes cleanly, rather than allowing a trailing edge-case deposit.
