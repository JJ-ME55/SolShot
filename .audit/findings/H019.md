# H019: Narrowing Cast Overflow at Hypothetical MAX_WAGER Increase

**Severity:** Low (Conditional)
**Category:** Arithmetic Safety
**Precedent:** EP-020 (Cetus flash loan arithmetic overflow, $223M)

## Summary

The `as u64` narrowing casts at lines 260, 265, and 267 in `settle_match` are safe at the current `MAX_WAGER_LAMPORTS = 100 SOL`, but would fail silently if `MAX_WAGER_LAMPORTS` were increased beyond approximately **131 trillion SOL** per wager.

## Investigation

### 1. Narrowing Casts Identified

**File:** `lib.rs:253–267` (settle_match BPS calculation)

```rust
let total_pot_128 = (wager_lamports as u128)
    .checked_mul(2)
    .ok_or(EscrowError::ArithmeticOverflow)?;

let treasury_amount = (total_pot_128
    .checked_mul(TREASURY_BPS as u128)
    .ok_or(EscrowError::ArithmeticOverflow)?
    / BPS_DENOMINATOR as u128) as u64;  // LINE 260: CAST

let ops_amount = (total_pot_128
    .checked_mul(OPS_BPS as u128)
    .ok_or(EscrowError::ArithmeticOverflow)?
    / BPS_DENOMINATOR as u128) as u64;  // LINE 265: CAST

let total_pot = total_pot_128 as u64;  // LINE 267: CAST
```

### 2. Safety Analysis at Current MAX_WAGER

- **MAX_WAGER:** 100,000,000,000 lamports (100 SOL)
- **total_pot_128:** 200,000,000,000 (safe in u128)
- **treasury_128:** 200,000,000,000 × 700 = 140,000,000,000,000 lamports
  - After division: 14,000,000,000 lamports (well under u64::MAX)
- **ops_128:** 200,000,000,000 × 300 = 60,000,000,000,000 lamports
  - After division: 6,000,000,000 lamports (well under u64::MAX)
- **total_pot:** 200,000,000,000 lamports (fits in u64 ✓)

### 3. Overflow Threshold Calculation

For the narrowest fee (7% = treasury):
- `(2 * wager * 700) / 10000 ≤ u64::MAX`
- wager ≤ (u64::MAX × 10000) / (2 × 700)
- wager ≤ **131,763,891,227,092,474 lamports** (~131 trillion SOL)

At current SOL price (~$200), this is unfeasible. But if MAX_WAGER were naively increased to, say, 1 million SOL:
- treasury_128 = 2,000,000,000,000,000 × 700 = 1,400,000,000,000,000,000
- After division: 140,000,000,000,000 lamports (still safe in u64)

**Realistic risk zone:** MAX_WAGER > ~**8.4 million SOL** (≈$1.6B per wager) would push treasury_128 toward u64::MAX.

### 4. MAX_WAGER is Compile-Time Constant

**Location:** `lib.rs:32`

```rust
const MAX_WAGER_LAMPORTS: u64 = 100_000_000_000;
```

- **Status:** Hardcoded at compile time, not configurable at runtime
- **Upgrade path:** Requires code change + recompile + new program deploy
- **Risk mitigation:** Impossible to increase MAX_WAGER without developer awareness

## Finding

**Current State:** SAFE
The narrowing casts pose no exploitable risk under current parameters (100 SOL max wager). The intermediate u128 values never exceed u64::MAX.

**Future Risk:** LOW-CONDITIONAL
If MAX_WAGER_LAMPORTS were increased to ~8+ million SOL (unlikely but conceivable), the BPS calculations would overflow silently with release builds (Cargo.toml: `overflow-checks = false` in release). The casts would truncate, causing treasury/ops to receive less than intended and the winner to receive overpayment.

**Recommendation:**
Add explicit overflow checks on the narrowing casts before deployment at higher wagers, or add a comment documenting the MAX_WAGER safety invariant.

---

**Status:** Resolved by design (compile-time bounds + conservative MAX_WAGER)
**No action required** for current parameters.
