# H020 — PDA Revival Post-Close Verification

**Status**: NOT_VULNERABLE

## Overview
Verifies that closed PDAs cannot be revived with old state via Anchor's `close` constraint in both v1 and v2 escrow programs.

## Close Patterns Verified

### Settlement (authority-close)
- **v1:665** — `settle_match` struct: `close = authority`
- **v2:696** — `settle_match` struct: `close = authority`

### Cancellation (caller-close)
- **v1:718** — `cancel_match` struct: `close = caller`
- **v2:748** — `cancel_match` struct: `close = caller`

### Permissionless Reclaim (caller-close)
- **v1:745** — `permissionless_reclaim` struct: `close = caller`
- **v2:773** — `permissionless_reclaim` struct: `close = caller`

## Anchor 0.30+ Behavior

The `close = X` constraint enforces:
1. **Data zeroing** — Account data is explicitly zeroed
2. **Discriminator update** — Account's discriminator is written to indicate uninitialized state
3. **Ownership transfer** — Account is transferred to system program
4. **Lamport drain** — Rent reserve is transferred to the close recipient

All operations are atomic within the transaction.

## Revival Attack Surface

### PDA Seed Structure
```
seeds = [b"match", match_id.as_bytes()]
```

A closed account CAN technically be revived via `init` if:
1. The same match_id is reused in future match creation
2. The lamports are refunded before the new `init` occurs

### Defense Mechanism

The `init` constraint on `create_match` (v1:546-552, v2:587-593) blocks reinitialization:
- Anchor checks: account must be uninitialized before `init` proceeds
- After `close`, the account is uninitialized and CAN be re-initialized
- BUT: Server should NEVER reuse match_id (uses CSPRNG for generation)
- If a match_id were reused, revival would require both:
  1. Fresh init in the new match creation
  2. Server misconfiguration (reused ID)

### Cross-Transaction Revival Impossibility

Even if match_id were reused in the same or subsequent transaction:
- Anchor's `close` zeros all account data
- State reverts to `AwaitingDeposits` default (no player balances, no active escrow state)
- No historical state is recoverable from a closed account
- Any new match initialized under that ID starts with fresh, empty state

## Conclusion

**NOT_VULNERABLE** — Both v1 and v2 correctly implement the close pattern. Anchor's guarantees on data zeroing + discriminator + ownership transfer prevent any meaningful state revival. The only revival scenario (reused match_id) is a server-side policy concern, not an on-chain vulnerability.
