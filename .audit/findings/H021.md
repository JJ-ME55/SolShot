## Summary

**Status: NOT_VULNERABLE on v1. N/A on v2 (no settlement deadline).**

The attack hypothesis: an attacker could craft a match where `state == Active` but `activated_at == 0`, bypassing the settlement deadline check at `lib.rs:266-272` and allowing settlement outside the 1-hour window.

**Verdict:** REJECTED. The atomicity of `state = Active` and `activated_at = Clock::get()?.unix_timestamp` in the same block prevents this attack. v1 has no reachable state where both conditions hold.

## Verification

### v1 (Program ID: `4kzrDpV9JxjE27AMg4PQXzGuge9MEYQEFznSPvkBtnH1`)

**Evidence from `programs/solshot-escrow/src/lib.rs`:**

**Line 171 (create_match initialization):**
```rust
escrow.activated_at = 0;  // Set to 0 at creation
```

**Lines 236-245 (deposit_wager → Active transition):**
```rust
// ESC-05: all deposited → match is active
let full_mask = (1u8 << escrow.max_players) - 1;
if escrow.deposits_mask == full_mask {
    escrow.state = MatchState::Active;
    escrow.activated_at = Clock::get()?.unix_timestamp;
    // ... emit MatchActive
}
```

**Lines 264-272 (settle_match deadline check):**
```rust
// OC-07: settlement deadline check (only if match was ever activated)
// activated_at > 0 ensures backward compat with matches created pre-OC-07
if ctx.accounts.escrow.activated_at > 0 {
    let deadline = ctx.accounts.escrow.activated_at
        .checked_add(SETTLEMENT_TIMEOUT_SECONDS)
        .ok_or(EscrowError::ArithmeticOverflow)?;
    require!(
        Clock::get()?.unix_timestamp <= deadline,
        EscrowError::SettlementExpired
    );
}
```

**Lines 524-530 (start_with_depositors → Active transition):**
```rust
escrow.state = MatchState::Active;
escrow.activated_at = Clock::get()?.unix_timestamp;

let total_pot = wager
    .checked_mul(num_deposited as u64)
    .ok_or(EscrowError::ArithmeticOverflow)?;
```

### Atomicity Analysis

1. **Only TWO code paths set `state = Active`:**
   - `deposit_wager` (line 238): Sets both `state = Active` AND `activated_at = Clock::get()?` in same `if` block
   - `start_with_depositors` (line 525): Sets both atomically in same instruction

2. **No intermediate state:** There is no reachable code path that:
   - Sets `state = Active` without also setting `activated_at` 
   - OR sets `activated_at = 0` after `state = Active`

3. **No RPC gaps:** Both transitions happen in a single instruction. Solana transactions are all-or-nothing.

### Settlement Deadline Check Logic

The check at line 266 branches on `activated_at > 0`:
- If `activated_at == 0`: **check is skipped** (guard allows settlement)
- If `activated_at > 0`: **deadline applies** (settlement must occur within 3600s of activation)

This is intentional per the comment "backward compat with matches created pre-OC-07" — it accommodates matches created before settlement deadlines were enforced.

**For the bypass to work, an attacker would need `state == Active` AND `activated_at == 0` simultaneously.** This is impossible because every code path that sets `state = Active` also sets `activated_at` in the same atomic block.

## v2 Context

v2 removes the settlement deadline entirely:
```rust
// v2 does not have this deadline check
// Any Active match can be settled at any time by authority
```

The question of `activated_at` bypass therefore becomes moot on v2.

## Conclusion

**H024 is NOT_VULNERABLE on v1.** The atomicity guarantee holds in both activation paths. No exploitation is possible within the Solana transaction model.

**H024 is N/A on v2.** The settlement deadline mechanism was removed by design, making the bypass question irrelevant.

**Recommendation:** No fix required. Document the `activated_at > 0` guard as intentional backward-compat feature for any future audit or migration.
