# Finding: H022 — Cancel-from-AwaitingDeposits Refund-All Per-Iteration Validation (v2)

## Status: NOT VULNERABLE
## Confidence Score: 9/10

> Confidence scale:
> - **9-10**: Certain — exhaustive code analysis, all paths verified
> - **7-8**: High — strong evidence, minor gaps in coverage
> - **5-6**: Moderate — reasonable analysis, some assumptions unverified
> - **3-4**: Low — significant uncertainty, limited code visibility
> - **1-2**: Minimal — couldn't adequately assess, treat as NEEDS MANUAL REVIEW

**One-line summary:** v2's `cancel_match` refund loop performs correct per-iteration validation (bounds, bit-set, pubkey match, fixed wager credit) but the loop as a whole does not enforce that all deposited slots are refunded — the aggregate weakness is covered by H023 (partial-refund theft) and H024 (non-contiguous mask).

---

## Executive Summary

This hypothesis is an affirmative recheck: does each individual iteration of v2's `cancel_match` refund loop validate correctly? It does. Every iteration enforces three mandatory properties before touching lamports: (1) the index is in bounds relative to `max_players`, (2) the corresponding bit in `deposits_mask` is set, and (3) the supplied account pubkey exactly matches `escrow.players[i]`. The per-iteration lamport transfer is always `wager_lamports` — the exact amount originally deposited per slot. No iteration can be spoofed to credit a wrong account or an unbounded amount.

The loop's correctness invariant holds in isolation. The structural weaknesses — that a caller can pass fewer `remaining_accounts` than the number of deposited slots (H023) and that non-contiguous `deposits_mask` bits make any valid `remaining_accounts` ordering impossible (H024) — are fully documented elsewhere and are not re-raised here. This finding exists to provide the affirmative "per-iteration validation passes" verdict required for the aggregate threat model.

---

## Hypothesis Investigated

v2's `cancel_match` refund-all flow is NEW relative to v1's similar pattern. Verify each refund iteration correctly checks `bit_set` per-iteration AND pubkey matches `escrow.players[i]`. Already partially covered by H023 (partial-refund theft) and H024 (non-contiguous mask). This finding is the affirmative "the per-iteration validation IS correct as far as it goes."

## Investigation Path

### Step 1: State guard (terminal-state check)

**Location:** `programs/solshot-escrow-v2/src/lib.rs:491-494`

**Finding:** Before any state mutation or lamport operation, the handler requires `escrow_state != MatchState::Settled && escrow_state != MatchState::Cancelled`. This prevents double-cancellation and post-settle refund.

**Evidence:**
```rust
require!(
    escrow_state != MatchState::Settled && escrow_state != MatchState::Cancelled,
    EscrowError::InvalidState
);
```

The check fires AFTER the caller-authorization check (lines 485-489) so an authorized caller who reaches line 491 is guaranteed they have not already been through a terminal state.

### Step 2: Authorization gate before the loop

**Location:** `programs/solshot-escrow-v2/src/lib.rs:485-489`

**Finding:** The instruction allows two caller classes: (a) authority, when `escrow_state == AwaitingDeposits`; (b) any registered player when `escrow_state == AwaitingDeposits` OR the match is timed out. This is evaluated before the refund loop runs.

```rust
require!(
    (is_authority && escrow_state == MatchState::AwaitingDeposits)
        || (is_player && (escrow_state == MatchState::AwaitingDeposits || is_timed_out)),
    EscrowError::Unauthorized
);
```

No anonymous caller can trigger the refund loop.

### Step 3: State write before loop (CEI compliance)

**Location:** `programs/solshot-escrow-v2/src/lib.rs:496-499`

**Finding:** `escrow.state = MatchState::Cancelled` is written inside a scoped block that drops the mutable borrow before the loop begins. This ensures the match is marked terminal before any lamports move, and re-entry (impossible on Solana but guarded defensively) would be rejected by the terminal-state check.

```rust
{
    let escrow = &mut ctx.accounts.escrow;
    escrow.state = MatchState::Cancelled;
}
```

### Step 4: Per-iteration validation — bounds check

**Location:** `programs/solshot-escrow-v2/src/lib.rs:503`

**Finding:** `require!(i < max_players, EscrowError::InvalidPlayer)` prevents the caller from passing more accounts than there are registered player slots. Since `max_players` is the count of slots initialized at `create_match` (stored as `u8`, max 10 for v2), this ensures `i` is always a valid index into `escrow.players[..max_players]`.

```rust
for (i, account) in ctx.remaining_accounts.iter().enumerate() {
    require!(i < max_players, EscrowError::InvalidPlayer);
```

### Step 5: Per-iteration validation — bit-set check

**Location:** `programs/solshot-escrow-v2/src/lib.rs:504-505`

**Finding:** `let bit_set = (deposits_mask >> i) & 1 == 1; require!(bit_set, ...)` ensures the loop only credits accounts for slots where a deposit actually occurred. An account at a slot that was never deposited produces a refund of zero entries — the require immediately reverts the instruction.

```rust
    let bit_set = (deposits_mask >> i) & 1 == 1;
    require!(bit_set, EscrowError::InvalidPlayer);
```

This prevents an attacker from padding `remaining_accounts` with arbitrary pubkeys at un-deposited slots to receive a wager credit they are not entitled to.

### Step 6: Per-iteration validation — pubkey match

**Location:** `programs/solshot-escrow-v2/src/lib.rs:506`

**Finding:** `require!(*account.key == players[i], EscrowError::InvalidPlayer)` enforces a strict equality check between the supplied account and the registered player pubkey at slot `i`. No substitution is possible: an attacker cannot pass a different account at the same index because `players[i]` is an immutable snapshot from `create_match` stored in the PDA.

```rust
    require!(*account.key == players[i], EscrowError::InvalidPlayer);
```

### Step 7: Per-iteration lamport transfer

**Location:** `programs/solshot-escrow-v2/src/lib.rs:508-509`

**Finding:** Each validated iteration transfers exactly `wager_lamports` — the fixed per-slot deposit amount stored in the PDA at `create_match`. The debit comes from the escrow PDA and the credit goes to the validated `account`. No variable amount is used.

```rust
    **ctx.accounts.escrow.to_account_info().try_borrow_mut_lamports()? -= wager_lamports;
    **account.try_borrow_mut_lamports()? += wager_lamports;
```

### Step 8: CancelMatch account struct — no pause guard (H007 fix confirmed)

**Location:** `programs/solshot-escrow-v2/src/lib.rs:743-765`

**Finding:** The `CancelMatch` struct includes `config` only to read `config.authority` for the is-authority check. There is NO `constraint = !config.is_paused` on this struct — v2's H007 fix is intact. The PDA seed derivation (`seeds = [b"match", escrow.match_id.as_bytes()], bump = escrow.bump`) is correct, and `close = caller` is the only closing directive.

## Invariant Analysis

### Target Invariant

Each refunded lamport transfer must go exactly to the registered player for that slot, for the exact deposit amount, only if that slot actually deposited.

### Enforcement Points

| Location | What It Enforces | Complete? |
|----------|-----------------|-----------|
| `v2:491-494` | No double-terminal (Settled/Cancelled re-entry blocked) | Yes |
| `v2:485-489` | Only authority or registered player may trigger | Yes |
| `v2:496-499` | State = Cancelled before any lamport moves | Yes |
| `v2:503` | Index < max_players (bounds) | Yes |
| `v2:504-505` | Bit `i` of deposits_mask must be set | Yes |
| `v2:506` | Account must equal `players[i]` exactly | Yes |
| `v2:508` | Debit = exactly `wager_lamports` | Yes |
| `v2:509` | Credit goes ONLY to the validated account | Yes |

### Enforcement Gap Assessment

Per-iteration invariant is fully enforced. The gap is at the loop-aggregate level: the program does not assert `remaining_accounts.len() == count_ones(deposits_mask)` after the loop. This gap enables the H023 attack (partial refund + rent sweep) and creates the H024 fund-lock (non-contiguous mask). Both are addressed in their respective findings.

## Blocking Factors

- **State terminal check** (`v2:491-494`): Prevents execution after Settled/Cancelled.
- **Caller authorization** (`v2:485-489`): Only authority (AwaitingDeposits only) or registered player can call.
- **CEI state write** (`v2:496-499`): State written before lamport ops; rollback yields correct prior state.
- **Index bounds** (`v2:503`): Prevents out-of-range array access and extra-account iteration.
- **Bit-set guard** (`v2:504-505`): Prevents credits for un-deposited slots.
- **Pubkey equality** (`v2:506`): Prevents substituting any account other than the exact registered player.
- **Fixed credit amount** (`v2:508-509`): No variable amount; always `wager_lamports`.

## Related Findings

- **H023** (CONFIRMED, CRITICAL) — Partial-refund theft via `close = caller` sweep: the aggregate-level gap that the per-iteration correctness cannot prevent. The loop terminates on exhausted `remaining_accounts`; Anchor's exit hook then sweeps residual lamports (un-refunded co-depositor wagers) to the caller.
- **H024** (NOT VULNERABLE verdict on the settlement-deadline bypass formulation, but the related NOVEL-CPI-01 / non-contiguous mask fund-lock concern) — Non-contiguous `deposits_mask` makes any valid `remaining_accounts` ordering impossible, permanently stranding affected deposits. Per-iteration logic cannot help here because the loop requires contiguous traversal starting at index 0.
- **H016** (LOW) — `close = caller` rent theft: a minor variant where a non-depositing observer races for the ~0.002 SOL PDA rent; distinct from per-iteration logic.

## Raw Investigation Notes

- v2 `cancel_match` handler: `programs/solshot-escrow-v2/src/lib.rs:459-519`
- `CancelMatch` account struct: `programs/solshot-escrow-v2/src/lib.rs:743-765`
- State guard at `v2:491-494` checks `!= Settled && != Cancelled` — note this uses two separate `!=` checks rather than a positive allowlist (`AwaitingDeposits || Active`). This means a hypothetical future state variant could be missed; however, the enum is sealed with exactly four variants, so the current implementation is functionally equivalent to a positive allowlist.
- `deposits_mask` in v2 is `u16` (vs `u8` in v1), supporting up to 10 players (max_players ≤ 10). The bit-shift `deposits_mask >> i` uses `u16` arithmetic; no sign-extension concern.
- `players` is `[Pubkey; 10]` in v2 (vs `[Pubkey; 4]` in v1). Slots `i ≥ max_players` hold `Pubkey::default()`. The bounds check at line 503 (`i < max_players`) fires before the pubkey check, so the zero-padding cannot be reached in normal execution.
- The `close = caller` constraint on `CancelMatch` (line 748) is an Anchor exit-hook, not inline code. It runs unconditionally after the instruction body returns `Ok(())`. This is the mechanism exploited in H023 and is not mitigated by per-iteration correctness.
- Confirmed: no post-loop assertion exists anywhere in the handler body (lines 459-519) that would enforce `remaining_accounts.len() == count_ones(deposits_mask)`.
