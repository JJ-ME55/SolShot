# Finding: H023 - PDA Account Revival After Close (Future-Transaction)

## Status: NOT VULNERABLE
## Confidence Score: 9/10

> Confidence scale:
> - **9-10**: Certain — exhaustive code analysis, all paths verified
> - **7-8**: High — strong evidence, minor gaps in coverage
> - **5-6**: Moderate — reasonable analysis, some assumptions unverified
> - **3-4**: Low — significant uncertainty, limited code visibility
> - **1-2**: Minimal — couldn't adequately assess, treat as NEEDS MANUAL REVIEW

## Executive Summary

H023 extends H004's analysis to future transactions: after an escrow PDA is closed (in TX1), can a separate `create_match` call in TX2+ re-create the account and cause financial harm? The answer is no. The PDA can be re-created—Solana and Anchor allow re-initialization of System Program-owned accounts—but the OC-10 protection ensures all funds are already distributed before close runs. The revived account is completely fresh, starting in `AwaitingDeposits` state with zero deposits and zero lamports. No funds are duplicated, no state is inherited, and the only observable issue is namespace squatting (a DoS, not a financial exploit), which is already identified in H004.

## Hypothesis Investigated

> After an escrow PDA is closed via `settle_match`, `cancel_match`, or `permissionless_reclaim`, a future `create_match` instruction with the same `match_id` can re-create the account at the same address. This future revival could allow:
> 1. Repeated rent extraction (paying rent once, recovering it multiple times)
> 2. Fund confusion (the revived escrow inheriting old match data)
> 3. Settlement bypass (re-creating a match to settle again)

## Investigation

### Step 1: Solana Account Reinitialization Rules

**Finding:** After an account is closed (owned by System Program, zero data), ANY program can re-initialize it by providing rent through the System Program's allocate instruction. Anchor's `init` constraint automatically handles this CPI.

**Code location:** `lib.rs:512` (CreateMatch, uses `init` constraint)

```rust
#[account(
    init,
    payer = authority,
    space = MatchEscrow::SPACE,
    seeds = [b"match", match_id.as_bytes()],
    bump,
)]
pub escrow: Account<'info, MatchEscrow>,
```

**Result:** A closed PDA can be re-created in a future transaction. No Anchor-level guard prevents this (cf. H004 analysis).

### Step 2: Future-TX Fund Integrity Check

**Timeline:**
```
TX1 (settled):
├─ settle_match("room-123") executes
├─ All player deposits transferred to winner/treasury/ops (lib.rs:284-291)
├─ State set to Settled before any transfer (lib.rs:279, OC-10)
├─ close = authority sweeps rent to authority
└─ Result: PDA closed, zero lamports, System-owned

[Minutes/Days/Weeks pass]

TX2 (new):
├─ create_match("room-123") executes with NEW payer
├─ System allocates fresh account, payer pays NEW rent
├─ State initialized to AwaitingDeposits (lib.rs:139)
├─ player_one_deposited = false, player_two_deposited = false (lib.rs:137-138)
└─ Result: Fresh escrow, no connection to TX1 match
```

**Financial analysis:**
- Funds from TX1 match: fully distributed, no lamports in closed account ✓
- Rent from TX1 match: swept to authority's account ✓
- Rent for TX2 match: paid by TX2 payer from their own balance ✓
- **Lamport duplication risk:** ZERO (two independent lamport movements)

### Step 3: State Inheritance Analysis

**Finding:** No state from the old match persists into the new one.

**Evidence:**
- Old account data: zeroed by `close` (all 8+160 bytes → 0x00)
- New account initialization: all fields set explicitly by `create_match` (lib.rs:131-142)
  - `state = AwaitingDeposits`
  - `player_one_deposited = false`
  - `player_two_deposited = false`
  - `activated_at = 0`
  - All player pubkeys overwritten
- **Result:** New escrow is completely independent, no old state accessible

### Step 4: Settlement Authority Verification

**Finding:** Even if the revived escrow could somehow access old funds (it can't), settlement is guarded by strict authority checks.

**Evidence:**
```rust
// lib.rs:565, 604 (SettleMatch)
#[account(
    mut,
    seeds = [b"match", escrow.match_id.as_bytes()],
    bump = escrow.bump,
    has_one = authority,        // <-- requires signer
    close = authority,
)]
pub escrow: Account<'info, MatchEscrow>,

#[account(
    ...
    has_one = authority @ EscrowError::Unauthorized,  // <-- dual check
)]
pub config: Account<'info, GlobalConfig>,
```

Settlement requires BOTH `escrow.authority` AND `config.authority` to sign, and they must match. A revived escrow created by any signer would have a different `escrow.authority` than the original. Settlement would fail unless the same server authority signs.

**Result:** Settlement of revived escrow still requires `config.authority` (server), which prevents uncontrolled fund distribution.

### Step 5: Blocking Factors (from H004 + Future-TX Specifics)

| Factor | How It Protects |
|--------|-----------------|
| OC-10 state-before-transfer | All lamports transferred OUT before close runs; none available to double-spend |
| Account zeroing on close | New escrow has zero deposits, zero balance; can't "remember" old match |
| Fresh state initialization | Every field reset by create_match; no inheritance from closed account |
| Dual authority on settle | Non-authority cannot settle; revived escrow with different authority is locked |
| Independent rent payments | Old rent swept to authority; new rent paid by TX2 payer; no duplication |

### Step 6: Unique Future-TX Scenario — PDA Namespace Exhaustion

**Finding:** The one novel attack unique to future TXs is repeated create_match calls to exhaust match_id namespace.

**Attack:** Attacker calls create_match("room-123"), then cancel_match to close. They get rent back. Later, server wants to create_match("room-123") for a legitimate room. Attacker front-runs with create_match("room-123") again (pays fresh rent), forcing server to use a different match_id. Repeated many times, this wastes the attacker's rent (recoverable after 48h) but also wastes server resources.

**Severity:** DoS only — not a financial exploit. The attacker pays rent each cycle and recovers it via `permissionless_reclaim` after 48h. No lamports are extracted from other parties.

**Already noted:** H004 incidental discoveries mention this as H-SQUAT (namespace squatting).

## Invariant Check

**Target invariant:** Each deposited wager is distributed exactly once. The PDA revival should not allow a second distribution of funds from an already-settled match.

**Enforcement:**
- Old match funds: distributed before close ✓
- New match funds: zero until new deposits ✓
- New match state: fresh, no inheritance ✓
- Settlement: requires server authority, which enforces winner selection ✓

**Result:** Invariant holds. No double-distribution possible.

## Conclusion

**H023 is NOT VULNERABLE to financial exploitation.**

Future-transaction PDA revival is theoretically possible (Solana allows System-owned accounts to be re-initialized) but provides no financial advantage to an attacker. The OC-10 protection (state-before-transfer) ensures all funds from any prior escrow are distributed before the account is closed, leaving no funds available for double-spending. The revived escrow initializes fresh state with zero deposits and cannot access funds from the old match.

The only new attack surface—namespace squatting via repeated create_match → cancel cycles—is a DoS vector (attacker wastes their own rent) and does not extract value from other users.

**Recommendation:** No code changes required for H023. The existing OC-10 pattern provides complete protection. The H-SQUAT (namespace squatting) variant is a lower-priority DoS concern already identified in H004.
