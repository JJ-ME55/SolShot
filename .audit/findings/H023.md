# H023: Partial-Refund Theft via `close = caller` Sweep

**Status:** CONFIRMED
**Severity:** CRITICAL
**Confidence:** 10/10
**Affects:** v1 AND v2 — all four refund sites

---

## Hypothesis

A malicious player (or any caller in `permissionless_reclaim`) calls `cancel_match` or `permissionless_reclaim` with a `remaining_accounts` array that is shorter than the number of deposited players. The refund loop iterates only over the supplied accounts, refunding only those players. It does NOT assert that all deposited slots were refunded. After the instruction body returns `Ok(())`, Anchor's `close = caller` exit hook runs unconditionally and transfers ALL remaining lamports in the escrow PDA — including every un-refunded wager — to the caller. The caller thereby steals the co-depositors' funds.

Worst case (v2 max match): 9 players each deposit 100 SOL. Attacker (players[0]) calls `cancel_match` with `remaining_accounts = [players[0]]`. Loop refunds 100 SOL to attacker, exits. Escrow holds 900 SOL. `close = caller` sweeps 900 SOL to attacker. Total attacker receipt: 1,000 SOL.

## Anchor 0.32.1 `close` Constraint Behavior

**Source:** `~/.cargo/registry/src/.../anchor-lang-0.32.1/src/common.rs:6–15`

```rust
pub fn close<'info>(info: AccountInfo<'info>, sol_destination: AccountInfo<'info>) -> Result<()> {
    let dest_starting_lamports = sol_destination.lamports();
    **sol_destination.lamports.borrow_mut() =
        dest_starting_lamports.checked_add(info.lamports()).unwrap();
    **info.lamports.borrow_mut() = 0;

    info.assign(&system_program::ID);
    info.resize(0).map_err(Into::into)
}
```

**Key facts confirmed from source:**

1. `close()` reads `info.lamports()` — the CURRENT balance at the moment it runs. This is whatever remains in the PDA after the instruction body has finished.
2. It adds ALL of those lamports to `sol_destination` unconditionally. There is no check whether the amount equals "just the rent reserve" or any other threshold.
3. It zeros `info.lamports` to 0.
4. It assigns the account owner to System Program and zeroes the data.
5. There is NO rejection path — `close()` never returns `Err` due to the lamport amount being larger than expected.

**Timing — confirmed from `anchor-syn-0.32.1/src/codegen/program/handlers.rs:147–162`:**

The generated handler pattern is:

```rust
// Invoke user defined handler.
let result = Program::instruction_name(
    Context::new(__program_id, &mut __accounts, __remaining_accounts, __bumps),
    ..args..
)?;

// Exit routine.
__accounts.exit(__program_id)   // ← close() runs HERE, AFTER instruction body
```

The exit routine runs only after `instruction_name(...)` returns `Ok(())`. If the instruction returns `Err`, `exit()` is never called. This means:

- The instruction body refunds however many accounts were passed.
- If the body returns `Ok(())` with un-refunded wagers still in the PDA, `exit()` runs and `close()` sweeps them ALL to the caller.

**The `exit()` implementation for `CancelMatch` — confirmed from `anchor-syn-0.32.1/src/codegen/accounts/exit.rs:31–44`:**

For any account field with `close = <target>`, the codegen produces:

```rust
anchor_lang::AccountsClose::close(
    &self.escrow,
    self.caller.to_account_info(),
).map_err(...)?;
```

Which calls `crate::common::close(escrow_account_info, caller_account_info)` — the function quoted above. No lamport-amount check. No requirement for the PDA to be empty first.

## Attack Walkthrough

### v1 `cancel_match` — Full Attack

**Setup:** 4-player match. Wager = 100 SOL each. `deposits_mask = 0b1111`. Total escrow lamports = 400 SOL + rent (~0.002 SOL). State = Active. TIMEOUT_SECONDS = 600 has elapsed.

**Attacker:** players[0]. They have signed and deposited.

**Step 1 — Gating check passes:**
```
v1:374-378 — require!(
    (is_authority && AwaitingDeposits)
    || (is_player && (AwaitingDeposits || is_timed_out))
)
```
`is_player = true` (caller == players[0]). `is_timed_out = true`. Passes.

**Step 2 — State set to Cancelled (v1:387-389):**
```rust
escrow.state = MatchState::Cancelled;
```
This runs BEFORE the loop. State is now terminal. Correct by OC-10, but not a blocker for the exploit.

**Step 3 — Refund loop (v1:393-410):**
Attacker passes `remaining_accounts = [players[0]_AccountInfo]`.

```
i=0: bounds OK (0 < 4). bit 0 set in 0b1111 ✓. account.key == players[0] ✓.
     escrow.lamports -= 100 SOL. players[0].lamports += 100 SOL.
Loop ends — no more remaining_accounts.
```

**Step 4 — Instruction returns `Ok(())`.**
Escrow now holds 300 SOL + rent. players[1], [2], [3] have not been refunded.

**Step 5 — Anchor exit hook runs (`__accounts.exit(program_id)`).**
The derived `exit()` for `CancelMatch` calls:
```rust
common::close(escrow_account_info, caller_account_info)
```
Which executes:
```rust
caller.lamports += escrow.lamports()   // += 300 SOL + rent
escrow.lamports = 0
```

**Final state:** Attacker (players[0]) has received 100 SOL (loop refund) + 300 SOL (close sweep) + rent = 400 SOL + rent. players[1], [2], [3] have received nothing. Their 300 SOL is gone.

**Net theft: 300 SOL from 3 victims in a single transaction.**

### v1 `permissionless_reclaim` — Wider Attack Population

Identical exploit. The only difference is that the caller does not need to be a registered player — **anyone** can call after `PERMISSIONLESS_RECLAIM_TIMEOUT = 1200s` (20 minutes from creation). Attack surface expands to all observers of the blockchain. A bot watching the mempool can steal from any expired match that has not yet been settled.

### v2 `cancel_match` — Maximum Damage

**Setup:** 10-player match (v2 max). Wager = 100 SOL each. `deposits_mask = 0b1111111111`. Total escrow = 1,000 SOL + rent. Match has passed `match_end_ts`.

**Attacker passes `remaining_accounts = [players[0]]`.**

Loop refunds 100 SOL to players[0]. Escrow holds 900 SOL. `close = caller` sweeps 900 SOL to attacker.

**Net theft: 900 SOL in one transaction.**

### v2 `permissionless_reclaim` — Maximum Damage, Zero Prerequisites

Same as above but the attacker does not need to be a registered player. After `match_end_ts + PUBLIC_REFUND_GRACE_SECS (86400s = 24h)`, any wallet on the network can call `permissionless_reclaim` with `remaining_accounts = []` (empty) and receive the entire escrow pot (1,000 SOL) via `close = caller` — having never deposited anything.

## Why the Loop Provides No Defense

The loop validates each entry in `remaining_accounts` correctly:
- `i < max_players` — bounds check
- `(deposits_mask >> i) & 1 == 1` — bit must be set
- `*account.key == players[i]` — pubkey must match

These checks ensure the caller cannot refund to a wrong address or claim a refund for a non-depositor. But **there is no check on `remaining_accounts.len()`**. The loop terminates when the iterator is exhausted — which is caller-controlled. The critical missing invariant is:

```
require!(
    ctx.remaining_accounts.len() == deposits_mask.count_ones() as usize,
    EscrowError::IncompleteRefund
);
```

This assertion does not exist at any of the four sites.

## Invariant Analysis

### Target Invariant

"Every player who deposited a wager must receive their wager back upon cancellation or permissionless reclaim."

Formally: `Σ(lamports refunded per deposited slot) == wager_lamports × count_ones(deposits_mask)`

### Enforcement Points

| Location | What It Enforces | Complete? |
|----------|-----------------|-----------|
| v1:395 `require!(i < max_players)` | Loop index in bounds | YES — but doesn't bound len |
| v1:398-399 `require!(bit_set)` | Only refund deposited slots | YES |
| v1:402-405 `require!(account.key == players[i])` | Refund to correct address | YES |
| POST-LOOP: (nothing) | All deposited slots were refunded | **NO — MISSING** |

The invariant is enforced on the positive path (each refund goes to the right person) but NOT on the completeness path (all deposited players receive a refund). This is the vulnerability.

## Recommended Fix

Add a single `require!` assertion **before** the refund loop in all four handlers, verifying that the caller has passed exactly as many accounts as there are deposited slots:

**v1 `cancel_match` — add at v1:391 (before the for loop):**
```rust
// Before (vulnerable):
for (i, account) in ctx.remaining_accounts.iter().enumerate() {
    // ... loop body
}

// After (fixed):
require!(
    ctx.remaining_accounts.len() == deposits_mask.count_ones() as usize,
    EscrowError::IncompleteRefund     // add this variant to EscrowError
);
for (i, account) in ctx.remaining_accounts.iter().enumerate() {
    // ... loop body unchanged
}
```

Apply the same fix to all four sites:
- v1 `cancel_match`: before v1:393
- v1 `permissionless_reclaim`: before v1:465
- v2 `cancel_match`: before v2:502
- v2 `permissionless_reclaim`: before v2:561

**Add to the error enum (both programs):**
```rust
#[error_code]
pub enum EscrowError {
    // ... existing variants ...
    #[msg("Not all deposited players were included in the refund accounts")]
    IncompleteRefund,
}
```

**Why this is the right fix:** After the fix, if the loop completes successfully, it will have processed exactly `count_ones(deposits_mask)` accounts. The PDA will hold exactly `rent_reserve` lamports (all wagers disbursed). The `close = caller` will then transfer only the rent reserve, which is the intended behavior.

**Alternative (secondary hardening):** After the loop, assert that `escrow.lamports == rent_reserve_amount`. This is a defense-in-depth assertion but requires knowing the exact rent reserve. The `len` check is simpler and sufficient.

## Raw Investigation Notes

**Counter-argument considered and refuted:**

The CPI context raised one potential blocker: "Maybe Anchor's account uniqueness check rejects `caller == remaining_accounts[0]` for the same pubkey." This concern was that when `players[0]` calls `cancel_match`, their pubkey appears twice — once as the named `caller: Signer<'info>` account, and once as `remaining_accounts[0]`.

**Resolution:** Solana's runtime allows the same pubkey to appear multiple times in an account list. Account deduplication is NOT enforced by the runtime for a mix of named accounts and `remaining_accounts`. Within a single instruction, Solana deduplicates by index position in the flat account array, but named accounts and remaining_accounts occupy different positions. The `try_borrow_mut_lamports()` calls DO require exclusive access, but since the instruction takes the escrow borrow (to debit) and the remaining_account borrow (to credit) as separate operations that don't overlap, they succeed sequentially. After the loop, the `caller` borrow for `close` is again a separate operation on the caller account. No overlapping-mut-borrow error is triggered.

Additionally: the attacker can avoid the same-key issue entirely by passing `remaining_accounts = []` (empty) and relying purely on `close = caller` to receive the full pot (all wagers). This variant requires no remaining_accounts at all. The loop body does not run, no borrows occur, and `close` sweeps everything directly. This is the simplest form of the exploit and has zero interaction with the loop.
