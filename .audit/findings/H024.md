# H024 — Non-Contiguous `deposits_mask` is Permanently Unrefundable

**Status:** CONFIRMED
**Severity:** HIGH
**Confidence:** 9/10
**Affects:** v1 + v2 (all four refund-loop sites)

## Hypothesis

If `deposits_mask = 0b0010` (only `players[1]` deposited; `players[0]` did not), no syntactically valid call sequence can refund player 1 on-chain. The `for (i, account) in remaining_accounts.iter().enumerate()` loop walks `i = 0, 1, ...` and requires `(deposits_mask >> i) & 1 == 1` AND `account.key == players[i]`. With a non-contiguous mask, the bit at position 0 is unset, so any call attempt fails at `i=0` regardless of which accounts are passed. Server explicitly tags such matches as "UNRECOVERABLE" and drops them (`server/socket-io/main.js:484-489`).

## Walkthrough — Why No Call Sequence Refunds

Setup: 4-player match, mask = `0b0010` (only player 1 deposited).

Try every possible call shape:

| Call | Loop trace | Outcome |
|---|---|---|
| `remaining_accounts = [players[1]]` | `i=0`: `(0b0010 >> 0) & 1 == 0` → fails on `InvalidPlayer` | REJECTED |
| `remaining_accounts = [players[0], players[1]]` | `i=0`: bit 0 is 0 → fails | REJECTED |
| `remaining_accounts = [players[1], players[1]]` (duplicate) | `i=0`: `players[1] != players[0]` → fails on pubkey mismatch | REJECTED |
| `remaining_accounts = []` | Loop never runs. State transitions to Cancelled. `close = caller` sweeps player 1's wager to caller (= NOVEL-CPI-02 / H023 territory) | Wager STOLEN by caller, not refunded to depositor |

Conclusion: there is no on-chain mechanism that successfully refunds player 1's wager to player 1 once mask becomes non-contiguous.

## Recovery Paths Examined

| Path | Outcome |
|---|---|
| Direct `cancel_match` | NO — fails at `i=0` |
| `permissionless_reclaim` | NO — same loop pattern, anyone can call but same failure |
| `start_with_depositors` → `cancel_match` | PARTIAL — but requires authority cooperation. Authority calls `start_with_depositors` (legal in `AwaitingDeposits` with N≥2). Compaction slides deposited slots to the front, mask becomes `0b0001`. Now contiguous, refund works after Active timeout. **However:** authority griefing or unavailability leaves funds permanently stranded; v2's deposit-window gate also delays this path. |

## Code Evidence

The four affected refund sites (each uses identical loop pattern):

- `programs/solshot-escrow/src/lib.rs:393-410` (v1 cancel_match refund loop)
- `programs/solshot-escrow/src/lib.rs:465-484` (v1 permissionless_reclaim refund loop)
- `programs/solshot-escrow-v2/src/lib.rs:502-518` (v2 cancel_match refund loop)
- `programs/solshot-escrow-v2/src/lib.rs:561-577` (v2 permissionless_reclaim refund loop)

The exact pattern at each site:

```rust
for (i, account) in ctx.remaining_accounts.iter().enumerate() {
    require!(i < max_players, EscrowError::InvalidPlayer);
    require!((deposits_mask >> i) & 1 == 1, EscrowError::InvalidPlayer);
    require!(*account.key == players[i], EscrowError::InvalidPlayer);
    ...
}
```

The loop index `i` is monotonic from 0 (via `enumerate()`). There is no skip mechanism, no caller-supplied index map, no way to refund slot k without first satisfying slots 0..k-1 with set bits.

## Off-Chain Confirmation

`server/socket-io/main.js` (lines 433-503 region) contains:
- `getEscrowDepositors()` computes `contiguous = mask === ((1 << wallets.length) - 1)`.
- `cancelEscrowSafely()` logs `"UNRECOVERABLE"` and returns `non_contiguous_deposits` without attempting the on-chain call.

The server explicitly acknowledges this state and treats the funds as lost (or pending an authority-driven `start_with_depositors` rescue).

## Production Likelihood

A non-contiguous `deposits_mask` arises any time `players[N]` deposits before `players[N-1]` for any N. Realistic causes:

- Network latency variation between players' wallet RPCs.
- A player with insufficient SOL fails their deposit; the next player's deposit lands first.
- Transient devnet RPC failures.
- Adversarial player intentionally racing deposit ordering (extremely cheap; cost = TX fee).

In a 2-player match: ~50% chance that the "later-listed" player deposits first → non-contiguous mask. In a 10-player match: any single failed deposit at slot k leaves the higher slots stranded.

## Severity Justification — HIGH

- Per-match financial exposure: `wager × N` where N = unrefundable depositors. v2 max: 9 × 100 SOL = 900 SOL.
- Combined with H023 (partial-refund theft via `close = caller`): in the empty-`remaining_accounts` case, the stranded wager flows to whoever calls reclaim. Stranded funds become attacker windfall after public grace deadline.
- Recovery requires authority (`start_with_depositors`); no permissionless escape exists.

## Recommended Fix

Rewrite the refund loop to walk player slots independently from `remaining_accounts` indexing:

```rust
// Caller passes indices explicitly:
//   refund_indices: Vec<u8>  (must equal positions of set bits in mask)
//   remaining_accounts: Vec<AccountInfo>  (one per refund_indices entry, in order)
for (j, idx) in refund_indices.iter().enumerate() {
    let i = *idx as usize;
    require!(i < max_players, EscrowError::InvalidPlayer);
    require!((deposits_mask >> i) & 1 == 1, EscrowError::InvalidPlayer);
    let account = &ctx.remaining_accounts[j];
    require!(*account.key == players[i], EscrowError::InvalidPlayer);
    ...
}
require!(
    refund_indices.len() == deposits_mask.count_ones() as usize,
    EscrowError::IncompleteRefund
);
```

This allows `refund_indices = [1]` to refund only `players[1]`, regardless of bit 0's state.

Sites to update: all 4 refund-loop sites (v1 + v2 cancel/reclaim).
