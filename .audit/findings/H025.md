**One-line summary:** Neither v1 nor v2 constrains `treasury`, `ops`, or `winner` to non-executable accounts in `SettleMatch`; a hostile authority can direct fee credits to an executable program address, burning those lamports silently per EP-106 — the single-line Feb fix still has not landed in either file.

---

## Executive Summary

Phase 1 CPI agent confirmed zero `executable` matches in both lib.rs files. This recheck verifies that status is unchanged. Both versions of `SettleMatch` declare `treasury` and `ops` as `UncheckedAccount<'info>` and validate only pubkey identity (against live `config` in v1, against the per-match snapshot in v2). No `!treasury.executable` or `!ops.executable` constraint exists in either file.

v2's per-match snapshot is an architectural improvement for the H001→H002 fee-redirect attack class: once snapshotted at `create_match`, the destinations are frozen for that match and cannot be silently rotated mid-flight. However, the snapshot mechanism does **not** validate the executable flag at snapshot time (`create_match` reads `cfg.treasury`/`cfg.ops` as raw `Pubkey` fields — no `AccountInfo` is available, so no executable check is possible there either). The snapshot therefore faithfully copies whatever pubkey is in config — executable or not.

The attack therefore shifts one step earlier in v2: rather than rotating config mid-match, a hostile authority must set `config.treasury` to an executable account **before** `create_match` is called. For in-flight matches created before the compromise, v2's snapshot genuinely protects them. For new matches created after the compromise, the executable pubkey is snapshotted and `settle_match` will credit it, burning those lamports.

Classification remains POTENTIAL (not CONFIRMED) because exploitation requires authority key compromise, which is the dominant precondition across this entire protocol's threat model, not a novel escalation path.

---

## Hypothesis Investigated

`treasury` and `ops` (and `winner`) are `UncheckedAccount`. No `!executable` constraint exists. If authority sets treasury or ops to an executable program account or sysvar, lamport credits via `try_borrow_mut_lamports` may silently succeed in-memory but be discarded at TX commit per EP-106, burning the fee lamports while the escrow debit is committed.

## Investigation Path

### Step 1: grep `executable` in both lib.rs files

**Location:** `programs/solshot-escrow/src/lib.rs`, `programs/solshot-escrow-v2/src/lib.rs`
**Finding:** Zero matches. The word `executable` does not appear anywhere in either file.
**Evidence:** grep returns no matches on both files.

### Step 2: Verify SettleMatch constraints — v1

**Location:** `programs/solshot-escrow/src/lib.rs:670-708`
**Finding:** `winner`, `treasury`, and `ops` are `UncheckedAccount`. Constraints are:
- `winner`: pubkey must be one of `escrow.players[0..max_players]` (no executable check)
- `treasury`: `treasury.key() == config.treasury` + `treasury.key() != ops.key()` (no executable check)
- `ops`: `ops.key() == config.ops` (no executable check)

```rust
// v1:684-697
#[account(
    mut,
    constraint = treasury.key() == config.treasury @ EscrowError::InvalidTreasury,
    constraint = treasury.key() != ops.key() @ EscrowError::DuplicateFeeAccount,
)]
pub treasury: UncheckedAccount<'info>,

#[account(
    mut,
    constraint = ops.key() == config.ops @ EscrowError::InvalidOps,
)]
pub ops: UncheckedAccount<'info>,
```

### Step 3: Verify SettleMatch constraints — v2

**Location:** `programs/solshot-escrow-v2/src/lib.rs:711-728`
**Finding:** Same pattern, but constraints validate against snapshot fields (`escrow.treasury_snapshot`, `escrow.ops_snapshot`) rather than live config. No executable check added.

```rust
// v2:715-728
#[account(
    mut,
    constraint = treasury.key() == escrow.treasury_snapshot @ EscrowError::InvalidTreasury,
    constraint = treasury.key() != ops.key() @ EscrowError::DuplicateFeeAccount,
)]
pub treasury: UncheckedAccount<'info>,

#[account(
    mut,
    constraint = ops.key() == escrow.ops_snapshot @ EscrowError::InvalidOps,
)]
pub ops: UncheckedAccount<'info>,
```

### Step 4: v2 snapshot creation — no executable check at create_match

**Location:** `programs/solshot-escrow-v2/src/lib.rs:201-214`
**Finding:** `create_match` copies `cfg.treasury` and `cfg.ops` directly as `Pubkey` values into `escrow.treasury_snapshot` and `escrow.ops_snapshot`. No `AccountInfo` for these fields is present in the `CreateMatch` struct — so no executable check is architecturally possible at snapshot time.

```rust
escrow.treasury_snapshot = cfg.treasury;  // v2:211 — raw Pubkey copy, no executable check
escrow.ops_snapshot = cfg.ops;            // v2:212 — same
```

### Step 5: Lamport transfer sites

**Location:** v1:`lib.rs:317-324`, v2:`lib.rs:434-441`
**Finding:** Both use the identical `try_borrow_mut_lamports()? += amount` pattern with no guard. Per EP-106, if the destination is an executable account (write-demoted by the runtime), the credit is discarded at commit while the debit from the escrow PDA is committed.

```rust
// v1:320-321 (and identical pattern in v2:437-438)
**ctx.accounts.escrow.to_account_info().try_borrow_mut_lamports()? -= treasury_amount;
**ctx.accounts.treasury.to_account_info().try_borrow_mut_lamports()? += treasury_amount;
// ↑ if treasury is executable: credit silently discarded, debit committed → lamports burned
```

### Step 6: Winner account safety

**Finding:** `winner` is constrained to one of `escrow.players[0..max_players]`. Players must sign `deposit_wager` (both v1:640, v2:672 use `pub player: Signer<'info>`), so player addresses in the escrow are always keypair-held wallets, not executable programs. The winner's 90% share is safe in practice.

## Invariant Analysis

### Target Invariant
Every lamport debited from the escrow PDA must be credited to exactly one of: winner, treasury, or ops. `winner_amount + treasury_amount + ops_amount == total_pot`.

### Enforcement Points

### Enforcement Gap Assessment
Arithmetic conservation is enforced. Physical lamport delivery is NOT verified. The gap is the absence of `!treasury.executable` and `!ops.executable` constraints in both `SettleMatch` structs, and the impossibility of adding an executable check at snapshot time (only a `Pubkey` is available at `create_match`, not an `AccountInfo`).

## Blocking Factors

- **Authority access control:** `update_config` requires current authority signature. Random user cannot execute without key compromise.
- **winner account safety:** Winner is constrained to deposit signers — non-executable wallets. 90% of pot is protected.
- **v2 snapshot for in-flight matches:** Matches created before config poisoning are immune — their snapshot holds a legitimate pubkey.
- **Behavior B uncertainty:** If the Solana runtime returns an explicit `Err` from `try_borrow_mut_lamports` on an executable account (rather than silently discarding), the TX reverts and no lamports are lost — attack reduces to settlement DoS only. This behavioral question is unresolved without a devnet test.

## Enabling Factors

- **No executable check in SettleMatch (both versions):** `UncheckedAccount` + key-identity-only constraints at `v1:680-697`, `v2:711-728`.
- **No executable check in create_match snapshot (v2):** `Pubkey` copy at `v2:211-212` — no `AccountInfo` available to inspect.
- **No executable check in update_config (both):** Authority can set treasury/ops to any pubkey including programs.
- **EP-106 write-demotion behavior:** Silent lamport burn rather than explicit error.
- **Single hot-wallet authority model:** Key compromise is the primary threat across this entire protocol (H001).

## Exploitation Scenario

### Prerequisites
1. Attacker controls the authority private key (server hot wallet compromise)
2. At least one match is in Active state (for v1) OR authority poisons config before calling `create_match` (for v2)
3. Attacker knows the pubkey of any deployed executable program (e.g., System Program `111...111`)

### Attack Steps (v1 — live config)
1. Call `update_config(new_treasury = Some(system_program_id))` — poisons live config
2. Call `settle_match` passing `treasury = system_program` — constraint at v1:686 satisfied (key identity matches)
3. Lamport transfers execute: escrow debits committed, treasury credit silently discarded
4. `treasury_amount` (7% of pot) burned; instruction returns `Ok(())`
5. Optional: restore config to hide evidence

### Attack Steps (v2 — snapshot frozen)
1. Verify no active matches yet (or accept that pre-poisoning in-flight matches are immune)
2. Call `update_config(new_treasury = Some(program_pubkey))`
3. Call `create_match` — snapshot captures the executable pubkey at `v2:211`
4. Players deposit normally
5. Call `settle_match` — treasury constraint validates against snapshot (v2:717), which holds the executable pubkey; constraint passes; lamport credit is burned

### Impact
- **Direct loss:** 7% of every pot burned (treasury) or 10% (treasury + ops). At 100 SOL max wager × 10 players = 1000 SOL pot → 70 SOL burned per match at maximum scale.
- **Under Behavior A (EP-106):** Permanent lamport destruction; invariant `winner + treasury + ops == total_pot` silently violated.
- **Under Behavior B:** Settlement permanently fails for all affected matches; players reclaim via timeout (liveness loss, no lamport loss).
- **Detection difficulty:** Instruction returns `Ok(())`; `MatchSettled` event is emitted with correct amounts; anomaly is only visible by monitoring treasury wallet balance off-chain.

### PoC Transaction Sequence

```
TX 1: update_config
  Accounts: config PDA (mut, seeds=[b"config"]), authority (signer)
  Args: new_authority=None, new_treasury=Some(11111111111111111111111111111111), new_ops=None
  Prerequisite: Attacker holds authority private key
  Result: config.treasury = System Program pubkey

TX 2: settle_match (v1) — OR — create_match then settle_match (v2)
  Accounts: escrow (mut, close=authority), authority (signer, mut),
            winner (= registered player wallet),
            treasury (= 11111111111111111111111111111111, mut),
            ops (= config.ops, real wallet),
            config (seeds=[b"config"])
  Args: match_id, winner pubkey
  Prerequisite: TX 1 committed; match Active
  Result: treasury_amount lamports debited from escrow (committed);
          credit to System Program silently discarded (EP-106);
          instruction returns Ok(()); MatchSettled event emitted;
          treasury_amount permanently burned

TX 3 (optional): update_config
  Args: new_treasury=Some(real_treasury_pubkey)
  Result: config.treasury restored; attack concealed from config state

Final State: treasury_amount burned per settled match; no on-chain error;
             settlement appears successful; economic invariant silently violated
```

## Recommended Fix

**Fix (preferred): Add `!executable` constraint to `treasury` and `ops` in SettleMatch in both v1 and v2.**

This is a one-line addition per account, surfaces at instruction execution time (where `AccountInfo` is available), and produces a clear `InvalidTreasury`/`InvalidOps` error rather than silent fund loss.

```rust
// v1:684-697 — BEFORE (vulnerable)
#[account(
    mut,
    constraint = treasury.key() == config.treasury @ EscrowError::InvalidTreasury,
    constraint = treasury.key() != ops.key() @ EscrowError::DuplicateFeeAccount,
)]
pub treasury: UncheckedAccount<'info>,

#[account(
    mut,
    constraint = ops.key() == config.ops @ EscrowError::InvalidOps,
)]
pub ops: UncheckedAccount<'info>,

// v1:684-697 — AFTER (fixed)
#[account(
    mut,
    constraint = treasury.key() == config.treasury @ EscrowError::InvalidTreasury,
    constraint = treasury.key() != ops.key() @ EscrowError::DuplicateFeeAccount,
    constraint = !treasury.executable @ EscrowError::InvalidTreasury,
)]
pub treasury: UncheckedAccount<'info>,

#[account(
    mut,
    constraint = ops.key() == config.ops @ EscrowError::InvalidOps,
    constraint = !ops.executable @ EscrowError::InvalidOps,
)]
pub ops: UncheckedAccount<'info>,
```

Apply identically at v2:715-728, replacing `config.treasury`/`config.ops` references with `escrow.treasury_snapshot`/`escrow.ops_snapshot` (already present in v2's existing constraints).

**Optional defense-in-depth:** Add the same `!executable` check for `winner` at v1:674-679 and v2:704-710, even though winner is practically safe (deposit signers cannot be programs). Provides belt-and-suspenders protection.

## Raw Investigation Notes

**Grep confirmation:** `grep "executable"` on both lib.rs files returns zero matches. The Phase 1 CPI agent assertion is verified.

**v2 snapshot nuance:** The snapshot mechanism (v2:201-214) is architecturally sound for the H001→H002 config-rotation attack class. Its limitation for this finding is structural: `create_match` receives only `config: Account<'info, GlobalConfig>` and reads `cfg.treasury` as a `Pubkey`. There is no `AccountInfo` with an `executable` flag available at that point, so adding an executable check at snapshot time would require architectural changes (passing treasury/ops as `UncheckedAccount` in `CreateMatch`, adding their `AccountInfo` to the struct). The simpler fix at `settle_match` time is sufficient and lower-risk.

**Behavioral uncertainty (Behavior A vs B):** Not re-investigated here; assessed at POTENTIAL (not CONFIRMED) in H009 with 7/10 confidence. This recheck inherits that classification and raises confidence to 8/10 based on additional Phase 1 CPI context audit corroboration confirming the same EP-106 analysis independently.
