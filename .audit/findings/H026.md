# Finding: H026 - Escrow PDA Lamport Inflation (Donation Attack)

## Status: NOT VULNERABLE
## Confidence Score: 9

> Confidence scale:
> - **9-10**: Certain — exhaustive code analysis, all paths verified
> - **7-8**: High — strong evidence, minor gaps in coverage
> - **5-6**: Moderate — reasonable analysis, some assumptions unverified
> - **3-4**: Low — significant uncertainty, limited code visibility
> - **1-2**: Minimal — couldn't adequately assess, treat as NEEDS MANUAL REVIEW

## Executive Summary

The H026 hypothesis proposes that an attacker could transfer SOL directly to the escrow PDA (bypassing the `deposit_wager` instruction) to inflate the escrow's lamport balance. On account closure, excess lamports would be swept to the authority's wallet via Anchor's `close = authority` constraint. While the mechanism is technically feasible, it is **not exploitable** because the attacker loses donated funds permanently while only the authority benefits. This creates a negative economic incentive (attacker loses money for zero gain), making the attack irrational and non-viable.

## Hypothesis Investigated

Anyone can transfer SOL to the escrow PDA via system transfer (outside the program). Extra lamports above 2*wager+rent would be swept to the `close` recipient (authority) on account close. This creates a donation → authority extraction path.

## Investigation Path

### Step 1: Understand Escrow PDA Account Lifecycle
**Location:** `lib.rs:110-152` (create_match), `lib.rs:566` (close constraint)

**Finding:** The escrow PDA is initialized with exactly one constraint from the payer (authority):
- Line 513: `payer = authority` — authority funds the account creation
- Line 516: `seeds = [b"match", match_id.as_bytes()]` — deterministic PDA
- The PDA starts with only the rent-exempt minimum lamports (no initial wager deposits)

The account is closed via Anchor's `close = authority` constraint at line 566 in `settle_match`. The `close` mechanism automatically zeros all account data and transfers remaining lamports to the `close` target.

**Evidence:**
```rust
#[account(
    mut,
    seeds = [b"match", escrow.match_id.as_bytes()],
    bump = escrow.bump,
    has_one = authority,
    close = authority,  // LINE 566
)]
pub escrow: Account<'info, MatchEscrow>,
```

### Step 2: Trace Lamport Flows Into the Escrow PDA
**Location:** `lib.rs:179-188` (deposit_wager), various other sources

**Finding:** The escrow PDA receives lamports through:
1. **Intended path:** `deposit_wager` CPI transfers (line 187) — exactly `wager_lamports` from each player
2. **Unintended path:** Direct system transfers from ANY sender to the escrow PDA address
3. **Unintended path:** Rent reclamation from closed parent accounts (if any exist)

The escrow PDA account is writable and can receive lamports from any source. There is no validation that lamports come ONLY from authorized deposit instructions.

**Evidence:**
```rust
system_program::transfer(
    CpiContext::new(
        ctx.accounts.system_program.to_account_info(),
        system_program::Transfer {
            from: ctx.accounts.player.to_account_info(),
            to: ctx.accounts.escrow.to_account_info(),  // Can receive from ANY source
        },
    ),
    wager,
)?;
```

### Step 3: Analyze Lamport Outflows During Settlement
**Location:** `lib.rs:284-291` (settle_match)

**Finding:** The settlement process deducts ONLY the calculated fee amounts from the escrow:
- Line 284: Debit `winner_amount` (exactly calculated from BPS math)
- Line 287: Debit `treasury_amount` (exactly calculated from BPS math)
- Line 290: Debit `ops_amount` (exactly calculated from BPS math)

After these three explicit transfers, the escrow PDA retains ONLY the rent-exempt minimum (which was in the account from initialization).

**Evidence:**
```rust
let total_pot_128 = (wager_lamports as u128).checked_mul(2)?;
let treasury_amount = ((total_pot_128.checked_mul(700)?)) / 10000 as u64;
let ops_amount = ((total_pot_128.checked_mul(300)?)) / 10000 as u64;
let winner_amount = total_pot.checked_sub(treasury_amount)?.checked_sub(ops_amount)?;

// Transfer amounts are DETERMINISTIC based on wager_lamports
**ctx.accounts.escrow.to_account_info().try_borrow_mut_lamports()? -= winner_amount;
**ctx.accounts.winner.to_account_info().try_borrow_mut_lamports()? += winner_amount;
// ... similar for treasury and ops
```

### Step 4: Analyze Account Closure and Rent Sweep
**Location:** `lib.rs:566`, Anchor framework behavior

**Finding:** After the explicit lamport transfers, the `close = authority` constraint is executed by Anchor's exit handler. This:
1. Transfers ALL remaining lamports in the account to the `authority` (the signer who initiated settlement)
2. Zeros out all account data
3. Changes account owner to System Program (marks as closed)

The key insight: **ALL remaining lamports go to authority**, including:
- The original rent-exempt minimum
- Any extra lamports donated by an attacker

**Evidence:**
```rust
#[account(
    mut,
    ...
    close = authority,  // Sweeps ALL remaining lamports to authority
)]
pub escrow: Account<'info, MatchEscrow>,
```

Anchor's `close` constraint is documented in the Anchor book as: "Close an account. `close = <target_account>` will set the account's lamports to 0 and transfer them to the target account."

### Step 5: Construct Attack Scenario
**Attacker goal:** Donate lamports to escrow PDA and have them swept to authority

**Attack sequence:**
1. Find an active escrow PDA address (derived from match_id)
2. Send a separate system transaction: `system_program::transfer(payer=attacker, to=escrow_pda, amount=excess_lamports)`
3. Wait for the authority to settle the match
4. Authority calls `settle_match`, which:
   - Deducts only the designed fee amounts
   - Closes the account via `close = authority`
   - Transfers all remaining lamports (original rent + donated excess) to authority

**Result:** Attacker loses `excess_lamports` permanently. Authority gains `excess_lamports` plus normal settlement fees.

### Step 6: Analyze Economic Incentives (Attack Viability)
**Question:** Why would an attacker do this?

**Analysis:**
- Attacker cannot receive the donated lamports back (they go to authority)
- Attacker loses SOL permanently with zero gain
- Authority does not solicit the donation; it's unsolicited
- Even if authority colludes with attacker, the attacker still loses money with no benefit

This is economically **irrational**. The attacker is essentially burning SOL for no return.

**Alternative interpretation (collusion):** Could the authority and attacker be cooperating?
- Authority: "Donate SOL to the escrow, I'll sweep it on settlement and give you a cut off-chain"
- Attacker: Donates SOL to escrow, authority sweeps it
- Result: Both authority and attacker lose on-chain SOL. Authority must then pay attacker off-chain to compensate, which is a net loss for both. This offers no advantage over direct off-chain value transfer.

**Conclusion:** No rational incentive exists to exploit this path.

## Invariant Analysis

### Target Invariant
**"Funds in the escrow PDA can only be extracted to designated recipients (winner, treasury, ops, authority via rent sweep) via the program's instruction handlers."**

This invariant is about **containment and authorization**, not about preventing lamport inflation per se.

### Enforcement Points

| Location | What It Enforces | Complete? | Notes |
|----------|-----------------|-----------|-------|
| `settle_match:284-291` | Only designed fee amounts leave the escrow during settlement | Yes | The three explicit transfers are the only outflow during settlement |
| `settle_match:566` | Remaining lamports go to authority on closure | Yes | Anchor's `close = authority` is enforced by the framework |
| `cancel_match:359-366` | Refunds go to depositing players only | Yes | Conditional refunds check `player_X_deposited` flags |
| `permissionless_reclaim:421-428` | Refunds go to registered players after timeout | Yes | Same refund logic as cancel_match |

### Enforcement Gap Assessment

There is NO enforcement gap in the critical path (lamports leaving the escrow). The escrow PDA's lamport balance after settlement contains:
- Original rent-exempt minimum (from initialization)
- Any unsolicited donations from external transfers

Both are swept to authority via `close = authority`. This is the design. No gap exists.

## Blocking Factors

1. **Economic Irrationality:** `lib.rs:566, Anchor framework` — Any lamports donated by an attacker go to the authority, not the attacker. The attacker has no incentive to donate SOL and receive nothing.

2. **Authority as Fixed Beneficiary:** `lib.rs:566` — The `close = authority` constraint hardcodes the authority as the sole recipient of swept lamports. The attacker cannot redirect this to themselves without gaining the authority's signing key.

3. **No Attacker Feedback Loop:** The escrow PDA has no instruction that allows an attacker to recover donated lamports or verify how much authority will receive. The attacker would be "in the dark" about the outcome.

## Enabling Factors

1. **Open Lamport Reception:** Any account can receive lamports from any sender. The escrow PDA is not blocked from accepting unsolicited transfers.

2. **No Lamport Amount Validation:** The program does not validate that the escrow PDA's lamport balance equals EXACTLY `rent + 2*wager`. It only debits the calculated amounts. Extra lamports are implicitly accepted.

3. **Automatic Rent Sweep:** `close = authority` automatically transfers all remaining lamports. There is no manual validation or cap on the sweep amount.

## Exploitation Scenario

If the attack were economically viable (which it is not), here's how it would work:

### Prerequisites
1. Active escrow PDA with deterministic address (match_id known or brute-forced)
2. Both players have deposited (escrow PDA holds 2*wager + rent)
3. Authority has not yet settled the match (within 1h window)
4. Authority is online and will settle the match eventually

### Attack Steps
1. **Transfer excess lamports to escrow PDA:**
   ```
   sender=attacker, recipient=escrow_pda_address, amount=excess_lamports
   ```
   Execution: Any signer can execute. Cost: `excess_lamports` + transaction fees (all attacker's money).

2. **Wait for authority to settle:**
   Authority calls `settle_match(winner)`. The program:
   - Reads `wager_lamports` (not affected by extra lamports)
   - Calculates `winner_amount`, `treasury_amount`, `ops_amount` (deterministic, based on wager)
   - Debits only these amounts from escrow
   - Closes account via `close = authority`, sweeping ALL remaining lamports to authority

3. **Result:**
   - Attacker loses: `excess_lamports` + transaction fees
   - Authority gains: `excess_lamports + original_rent + normal_fees`
   - Attacker gains: Nothing

### Impact
**Attacker impact:** Negative (loses SOL with zero return)
**Authority impact:** Positive (gains unsolicited lamports)
**Protocol impact:** None (escrow settlement logic unaffected)

## If NOT VULNERABLE (MANDATORY Devil's Advocate Analysis)

### Protection Analysis

| Protection | Location | How It Works |
|------------|----------|--------------|
| Economic Irrationality | `lib.rs:566, Anchor framework behavior` | Attacker donates funds but cannot retrieve them. Funds go to authority instead. |
| Deterministic Fee Calculation | `lib.rs:257-265` | Fees are computed solely from `wager_lamports`, not from escrow PDA's total balance. Extra lamports don't affect fee distribution. |
| Fixed Authority Recipient | `lib.rs:566` | Anchor's `close = authority` is hardcoded. Only the authority receives swept lamports. Attacker cannot redirect them to own wallet. |
| Transaction Atomicity | Solana runtime | If authority calls `settle_match`, all steps execute or all revert. Partial extraction impossible. No window for attacker to interleave. |

### Devil's Advocate Analysis (MANDATORY)

**Challenge 1: Flash loans could fund the donation**

*Argument:* An attacker uses a flash loan to acquire lamports, sends them to escrow, then... still loses the lamports when they're swept to authority. Flash loans don't change the economic outcome.

*Refutation:* Flash loans require repayment within the same transaction. An attacker cannot borrow SOL, send it to escrow, and wait for settlement in a later transaction. The escrow closure (which sweeps lamports) would only occur after the flash loan callback, triggering repayment. Even if the attacker could somehow avoid repayment, the lamports go to authority, not back to the attacker. The flash loan provider would see zero return.

*Confidence: HIGH* — Flash loans are intra-transaction. This attack spans multiple transactions.

---

**Challenge 2: Multiple accounts could obscure the donation source**

*Argument:* Attacker could create multiple wallets to mask their identity while donating. Then... the lamports still go to authority, not the attacker. Sybil accounts don't change the economic outcome.

*Refutation:* Even with 1000 Sybil accounts, each account that donates SOL to escrow loses that SOL with zero return. The attacker, regardless of how many identities are used, cannot retrieve the donated funds. Authority benefits instead.

*Confidence: HIGH* — Account multiplicity doesn't change incentives.

---

**Challenge 3: Attacker could donate and then replay settlement to extract lamports**

*Argument:* What if the attacker donates lamports, then somehow causes the settlement to execute multiple times, extracting excess lamports each iteration?

*Refutation:* The escrow PDA has a `state` field. After the first settlement, `state = MatchState::Settled`. The `settle_match` instruction at line 230 checks:
```rust
require!(ctx.accounts.escrow.state == MatchState::Active, EscrowError::InvalidState);
```
A second call to `settle_match` would immediately fail because the state is not `Active`. Replay is prevented by the state machine. Additionally, Solana transactions include a recent blockhash for replay protection at the network level.

*Confidence: HIGH* — State machine prevents re-settlement.

---

**Challenge 4: Attacker could front-run settlement and remove lamports they donated**

*Argument:* Attacker donates to escrow, then front-runs the authority's settlement with their own instruction to remove the lamports before the close happens?

*Refutation:* There is no instruction to remove arbitrary lamports from an active escrow. The only instructions that debit the escrow are:
- `settle_match` (debits only designed fee amounts, requires authority signer)
- `cancel_match` (debits only wagers, requires authority or player signer after timeout, requires different state)
- `permissionless_reclaim` (debits only wagers, requires timeout, requires different state)

The attacker cannot call any of these without being the authority or a player. A non-player attacker has no signer authority to debit the escrow. Lamport transfers require the account owner (the program) to debit the source. The program only debits via its three designated instructions.

*Confidence: HIGH* — No attacker-callable instruction allows lamport removal.

---

**Challenge 5: Authority and attacker could collude to launder funds off-chain**

*Argument:* Authority and attacker are the same entity (or cooperating). Attacker donates X lamports to escrow. Authority settles and sweeps X lamports to authority wallet. Authority then pays attacker off-chain. Net result: X lamports moved on-chain from attacker → authority → attacker off-chain.

*Refutation:* While technically possible, this provides NO advantage over direct off-chain value transfer and creates unnecessary on-chain footprint:
- Attacker-authority could simply exchange SOL off-chain without touching the blockchain
- On-chain execution costs transaction fees (both parties pay)
- On-chain settlement leaves a permanent record (escrow events, transfers)
- The escrow mechanism adds complexity without benefit to the colluding parties
- If the goal is to launder funds, on-chain records are counterproductive

Moreover, this is not an **exploit of the escrow program**. It's a **misuse of the escrow for off-chain economic coordination**. The program functions exactly as designed. The attacker and authority's off-chain agreement is orthogonal to the escrow logic.

*Confidence: MEDIUM* — This is possible but represents policy violation (off-chain manipulation), not a code vulnerability. The escrow program itself is not exploited; it works correctly. The attacker still "loses" on-chain SOL to authority's wallet.

---

**Overall Counterargument Confidence: HIGH**

All five devil's advocate challenges fail to establish a viable attack path. The most plausible challenge (collusion + off-chain laundering) represents a policy concern, not a code vulnerability. The escrow program itself prevents economic exploitation.

## Protection Analysis Summary

The protocol protects against this attack through a **combination of design and economics**, not through explicit code validation:

1. **Fee calculation is independent of escrow balance:** The settlement amounts depend only on `wager_lamports`, not on the total lamports in the escrow. Extra lamports are inert with respect to fees.

2. **Attacker cannot be a player:** OC-06 (`lib.rs:128-129`) prevents the authority (and by extension, anyone with control of an account) from being a player. An attacker who has only a regular wallet cannot be designated as the winner.

3. **Attacker has no signer authority on the escrow:** The escrow is owned by the program, not by the attacker. The attacker cannot directly invoke Solana runtime lamport transfers from the escrow without the program's permission (CPI from the program).

4. **No instruction allows arbitrary lamport extraction:** All instruction handlers that touch the escrow PDA either:
   - Debit only designed amounts (settlement, refunds)
   - Are gated by signer requirements (settlement requires authority, cancel requires authority/player after timeout)
   - Are time-locked (permissionless_reclaim requires 48h timeout)

5. **Economic incentive is inverted:** The attacker loses money; the authority gains money. Rational attackers do not execute strictly-losing strategies.

## Incidental Discoveries

While investigating H026, the following tangential observations were noted:

1. **Donation mechanism works as designed but is economically useless:** The escrow PDA DOES accept and sweep excess lamports to authority. This is the correct behavior for Anchor's `close` constraint. However, no one has an incentive to exploit this path.

2. **Attacker could donate to multiple escrows in sequence:** An attacker could theoretically send lamports to many escrows (burning their own SOL on transaction fees) and watch authority collect small windfall amounts across many matches. This is a denial-of-service on the attacker's own wallet, not a protocol exploit. Suggested new hypothesis: **Could there be economic incentive for authority to never settle matches with donations, allowing them to reach timeout and be reclaimable by permissionless callers?** This would be a timing-based delay tactic, not a lamport inflation attack.

3. **`close` constraint behavior is subtle:** Developers new to Anchor might not immediately grasp that `close = recipient` transfers ALL remaining lamports, not just the data space rent. This finding could inform documentation improvements in on-chain program templates.

## Raw Investigation Notes

### Code Path Trace: Donation → Sweep

```
Attacker Action:
  system_program::transfer(
    payer=attacker,
    to=escrow_pda,
    amount=excess_lamports
  )

  Escrow PDA lamports: rent + 2*wager + excess_lamports

Authority Action:
  settle_match(winner) {
    // Read wager (unchanged by donation)
    wager = escrow.wager_lamports

    // Calculate amounts (unchanged by donation)
    total_pot = wager * 2
    treasury_amount = total_pot * 700 / 10000
    ops_amount = total_pot * 300 / 10000
    winner_amount = total_pot - treasury_amount - ops_amount

    // Debit only designed amounts (donation is untouched)
    escrow.lamports -= winner_amount
    winner.lamports += winner_amount
    escrow.lamports -= treasury_amount
    treasury.lamports += treasury_amount
    escrow.lamports -= ops_amount
    ops.lamports += ops_amount

    // Escrow now holds: rent + excess_lamports

    // Close triggers Anchor exit handler:
    // close = authority transfers ALL remaining lamports
    authority.lamports += rent + excess_lamports
  }

Escrow PDA lamports after settlement: 0 (closed)
Authority net gain: normal_fees + excess_lamports (attacker donated)
Attacker net loss: excess_lamports + transaction_fees
```

### Key Constants and Calculations

```
MIN_WAGER: 10,000 lamports (~$0.002)
MAX_WAGER: 100,000,000,000 lamports (~$20 at $0.20/SOL, but MAX is 100 SOL)
Escrow rent: ~0.00143 SOL (1,430,400 lamports approx)

Example with MIN_WAGER:
  Wager: 10,000 lamports per player
  Total pot: 20,000 lamports
  Treasury (7%): 1,400 lamports
  Ops (3%): 600 lamports
  Winner (90%): 18,000 lamports
  Sum: 20,000 (correct)

  If attacker donates 1,000,000 lamports:

    After settlement transfers: 1,430,400 (rent) + 1,000,000 (donation)
    Authority sweeps: 1,430,400 + 1,000,000 = 2,430,400 lamports

    Attacker's loss: 1,000,000 + transaction_fee (~5,000) = ~1,005,000 lamports
    Attacker's gain: 0
```

### Anchor `close` Constraint Behavior

Per Anchor documentation and implementation, `close = <target_account>` performs:
1. Writes zeros to all account data (discriminator and fields)
2. Transfers account's entire lamport balance to target
3. Sets account owner to System Program

The transfer amount is the CURRENT lamport balance at the moment of closure, not a pre-calculated amount. This means any lamports in the account (intended or unintended) are swept.

This behavior is **working as designed** for Anchor programs. It's the correct way to implement account cleanup. The presence of excess lamports is not a "bug" in Anchor; it's an expected consequence of allowing any source to contribute lamports.

## Summary

H026 (Escrow PDA Lamport Inflation via Donation) is **NOT VULNERABLE**. While the escrow PDA can technically receive unsolicited lamports and these excess lamports are swept to the authority on account closure, the attack is economically irrational:

1. **Attacker loses money:** Donated lamports go to authority, not attacker.
2. **No code vulnerability:** All settlement logic remains unaffected by excess lamports.
3. **No exploitation path:** No instruction allows an attacker to extract donated funds or gain value from donation.
4. **No plausible incentive:** Rational attackers do not execute strictly-negative-return transactions.

The authority benefits from excess lamports, but this is not an exploit of the escrow—it's a direct economic consequence of the attacker's own decision to donate. The escrow program's settlement logic, fee distribution, and state machine function exactly as designed.
