## Executive Summary

The hypothesis correctly identifies that OC-06 (the authority-as-player prevention control) is **insufficient** to prevent the authority from playing matches via secondary wallets. OC-06 enforces only that the authority's signing key cannot be registered as `player_one` or `player_two` at match creation (lines 127–129 of `lib.rs`). It does NOT prevent the authority from controlling an additional keypair and registering that secondary wallet as a player.

A malicious or compromised authority can trivially execute the following attack:
1. Control a secondary keypair (call it `colluding_wallet`)
2. Call `create_match` with `player_one = colluding_wallet`, `player_two = victim_wallet`
3. Deposit from `colluding_wallet` and allow the victim to deposit from `victim_wallet`
4. Call `settle_match` with `winner = colluding_wallet`
5. Receive 90% of the pot from the victim's wager

This attack is **not new** — it is already fully documented and analyzed in H005 (Authority Winner Selection Fraud) and H014 (Authority Collusion — Settle to Controlled Winner Wallet). H027 provides independent verification that OC-06 is the specific control being bypassed, and confirms the bypass mechanism is trivial.

**Classification as POTENTIAL** (not CONFIRMED) because the attack requires a malicious or compromised authority, which is a precondition outside the smart contract code itself. The code design explicitly places trust in the authority; OC-06 fails only when that trust is violated.

## Hypothesis Investigated

> OC-06 prevents authority from being a player. But authority could use a secondary wallet to play, then always settle in their favor. The on-chain constraint only checks `authority != player_one && authority != player_two` against the signing key.

---

## Investigation Path

### Step 1: Locate OC-06 Control

**Location:** `lib.rs:127–129` (create_match handler)

**Finding:** OC-06 exists and is implemented as two explicit `require!` statements:

**Evidence:**
```rust
// OC-06: authority (server keypair) cannot be a player
require!(player_one != ctx.accounts.authority.key(), EscrowError::AuthorityAsPlayer);
require!(player_two != ctx.accounts.authority.key(), EscrowError::AuthorityAsPlayer);
```

**Analysis:**
- The checks compare `player_one` and `player_two` parameters against `ctx.accounts.authority.key()`
- `ctx.accounts.authority.key()` is the public key of the signer (the wallet calling `create_match`)
- The check prevents the **signing key** from being a player
- The check does NOT validate whether the authority controls the wallets stored as `player_one` or `player_two`

---

### Step 2: Verify OC-06 Only Blocks Direct Authority Use

**Location:** `lib.rs:114–115` (create_match parameters), `lib.rs:127–129` (OC-06 check)

**Finding:** The `player_one` and `player_two` parameters are arbitrary `Pubkey` values. No constraint validates that they correspond to addresses not controlled by the authority.

**Evidence:**
```rust
pub fn create_match(
    ctx: Context<CreateMatch>,
    match_id: String,
    wager_lamports: u64,
    player_one: Pubkey,           // Arbitrary parameter — no ownership validation
    player_two: Pubkey,           // Arbitrary parameter — no ownership validation
) -> Result<()> {
    // ...
    require!(player_one != ctx.accounts.authority.key(), EscrowError::AuthorityAsPlayer);
    require!(player_two != ctx.accounts.authority.key(), EscrowError::AuthorityAsPlayer);
    // ...
    escrow.player_one = player_one;   // Stored as-is
    escrow.player_two = player_two;   // Stored as-is
```

**Analysis:**
- The authority calls `create_match` with its own key as `authority: Signer<'info>`
- The authority can pass ANY Pubkey as `player_one` or `player_two`
- The only restriction is that these pubkeys must not equal `authority.key()`
- There is no check that the authority does not control the registered player wallets
- The authority can control multiple keypairs; registering a secondary keypair as a player is trivially possible

---

### Step 3: Verify Settlement Winner Constraint

**Location:** `lib.rs:575–580` (settle_match winner constraint)

**Finding:** The winner must be one of the two registered players (no third-party injection possible), but there is no check verifying the winner is not authority-controlled.

**Evidence:**
```rust
/// Winner: must be one of the registered players (OC-02 — resolves H008, H002, S001)
/// CHECK: Constrained to escrow.player_one or escrow.player_two
#[account(
    mut,
    constraint = winner.key() == escrow.player_one
        || winner.key() == escrow.player_two
        @ EscrowError::InvalidWinner
)]
pub winner: UncheckedAccount<'info>,
```

**Analysis:**
- If authority has registered `colluding_wallet` as `player_one`, then passing `winner = colluding_wallet` satisfies the constraint
- The constraint is correctly enforced, but OC-06 has already been bypassed at `create_match` time
- There is no on-chain mechanism to determine whether the winner is the actual game winner or a fabricated choice

---

### Step 4: Assess OC-06 Sufficiency

**Location:** Access Control analysis across `create_match` and `settle_match`

**Finding:** OC-06 is **insufficient** as a control against authority self-play.

**Evidence:**
| Scenario | OC-06 Prevents? | Authority Control | Outcome |
|----------|-----------------|-------------------|---------|
| Authority uses own key as player (`player_one = authority.key()`) | YES — blocked by line 128 | Direct (self) | Prevented ✓ |
| Authority uses secondary keypair as player (`player_one = colluding_wallet`, where colluding_wallet is authority-controlled) | **NO — not blocked** | Indirect (secondary keypair) | **Possible ✗** |
| Authority always selects secondary keypair as winner | No control (off-chain trust boundary) | Full (winner selection) | **Possible ✗** |

**Analysis:**
OC-06 treats the authority as a single entity identified by its signing key. It does not account for:
- Authority controlling multiple keypairs
- Authority registering controlled keypairs as players in matches
- Authority always settling matches to favor controlled player wallets

The control is a necessary but not sufficient protection. It requires complementary mechanisms (multisig, timelock, on-chain game state) to prevent this attack class.

## Invariant Analysis

### Target Invariant

The authority cannot play matches (using any wallet the authority controls) and systematically extract victim funds via biased winner selection.

### Enforcement Points

| Location | What It Enforces | Complete? |
|----------|-----------------|-----------|
| `lib.rs:127–129` (OC-06) | Authority's signing key cannot be a player | Partial — only blocks direct use, not secondary wallets |
| `lib.rs:575–580` (winner constraint) | Winner must be one of two registered players | Yes, blocks third-party injection |
| `lib.rs:228–305` (settle_match handler) | Winner is the actual game winner | **NO — no on-chain game state exists** |
| Off-chain (server) | Game outcome integrity | Outside smart contract scope |

### Enforcement Gap Assessment

OC-06 has a critical gap: it assumes the authority is a single, monolithic entity with one keypair. In reality, the authority is an organization that can control multiple keypairs. By registering a secondary, non-signing keypair as a player, the authority:
- Satisfies OC-06 (secondary key ≠ signing key)
- Enables self-play (authority effectively plays against legitimate players)
- Permits unilateral winner selection (authority settles to the secondary key)

The enforcement gap is **in the design**, not in the code. OC-06 enforces its constraint correctly, but the constraint is insufficient for the intended security property.

## Blocking Factors

- **Third-party winner injection blocked:** `lib.rs:575–580` — Anchor constraint prevents passing any winner that is not `player_one` or `player_two`. This is correctly enforced.
- **Authority's own signing key blocked:** `lib.rs:127–129` — OC-06 prevents using the authority's own hot-wallet key as a player.
- **OC-11 event emission:** `lib.rs:293–302` — `MatchSettled` event includes winner pubkey. Systematic single-player wins are detectable via off-chain monitoring.

## Enabling Factors

- **Authority controls multiple keypairs:** Standard capability; no on-chain validation of keypair ownership. The authority can derive any number of secondary keypairs.
- **OC-06 does not validate keypair ownership:** `lib.rs:127–129` only checks that `player_one != authority.key()` and `player_two != authority.key()`. It does not check whether the authority controls the registered player addresses.
- **Ungated player assignment in create_match:** `lib.rs:114–115` — The `player_one` and `player_two` parameters are arbitrary; no constraint validates who supplies them or who owns the registered wallets.
- **No on-chain game outcome verification:** `lib.rs:228–305` — The `settle_match` handler has zero checks connecting the winner argument to actual game state. The authority's choice between the two players is unconstrained.
- **Authority can create matches with no config gate:** `lib.rs:510–532` — The `CreateMatch` account struct has no `has_one = authority` on config (noted in H005 and H014). Any signer (not just config.authority) can create matches, but by convention, the authority creates all matches and can plant controlled wallets as players.

## Exploitation Scenario

### Prerequisites

1. Attacker controls `config.authority` (the server keypair)
2. Attacker controls at least one additional keypair (`colluding_wallet`) — trivially satisfied

### Attack Steps

1. **Setup:** Attacker generates `colluding_wallet` (a keypair under its control).
2. **Match creation:** Attacker calls `create_match` with `player_one = colluding_wallet`, `player_two = victim_wallet`, `wager_lamports = X`.
   - OC-06 check: `colluding_wallet != authority.key()` ✓ (passes, because they are different keys)
3. **Deposits:** Attacker's `colluding_wallet` deposits X lamports. Victim deposits X lamports. Match transitions to Active.
4. **Settlement:** Attacker calls `settle_match(winner = colluding_wallet)` within the 1-hour window.
   - Authority signer check: Attacker's signing key matches `escrow.authority` and `config.authority` ✓
   - Winner constraint: `colluding_wallet == escrow.player_one` ✓ (passes)
5. **Payout:** `colluding_wallet` receives 0.9 × 2X = 1.8X lamports. Attacker (via treasury/ops) receives 0.1 × 2X = 0.2X lamports.
6. **Net gain:** Attacker recovers 2X (their own X + victim's X) plus PDA rent. Net per match: +X (victim's wager).
7. **Repeat:** Attacker creates new matches with different victims, always planting `colluding_wallet` as `player_one`, always settling to it.

### Impact

- Victim loses entire wager (X) per match
- At max wager (100 SOL), victim loses up to 100 SOL per fraudulent match
- Attack is repeatable with no on-chain rate limiting or detection
- Attack leaves no on-chain evidence distinguishing it from legitimate play (winner is a registered player, constraint is satisfied)
- Detectable only via off-chain pattern analysis: the same `colluding_wallet` always wins

### PoC Transaction Sequence

```
TX 0 (optional): update_config
  Accounts: config (mut), authority (signer)
  Args: new_treasury = attacker_wallet, new_ops = attacker_wallet
  Prerequisite: Attacker controls config.authority
  Result: All future settlements send fees to attacker_wallet

TX 1: create_match
  Accounts: escrow (init), authority (signer/payer), config (pause check)
  Args: match_id="room-xyz", wager_lamports=100_000_000_000,
        player_one=colluding_wallet, player_two=victim_wallet
  Prerequisite: None
  Result: MatchEscrow PDA created; escrow.player_one = colluding_wallet;
          escrow.player_two = victim_wallet; state = AwaitingDeposits

          attacker_wallet (as treasury) receives 14 SOL (7%);
```

## Recommended Mitigations

In order of increasing implementation cost:

### 1. Off-chain Monitoring (Low cost)

The OC-11 `MatchSettled` event (lines 293–302) emits winner and fee destination pubkeys. Deploy off-chain monitoring to:
- Alert on any `update_config` transaction
- Alert when the same player wallet wins an statistically anomalous proportion of matches
- Alert on treasury/ops address changes

This does not prevent the attack but enables rapid detection and response.

### 2. Multisig Authority (Medium cost)

Replace the single server hot wallet with a multisig (e.g., Squads). This prevents a single key compromise from enabling systematic player-stuffing. A compromised single signer in a 2-of-3 multisig cannot act alone.

### 3. Timelock on Config Changes (Medium code cost)

Require a delay (e.g., 24–48 hours) between `update_config` submission and effect. This gives players time to exit or dispute before fee destinations change.

### 4. Commit-Reveal Winner Scheme (High code cost)

Have the server commit a winner hash at match creation or activation, then verify at settlement. This makes pre-settlement winner manipulation detectable after the fact.

```rust
// Conceptual fix sketch — commit-reveal pattern
// At settle_match, require winner matches committed hash:
require!(
    hash_winner(winner.key(), match_id) == escrow.winner_commitment,
    EscrowError::WinnerMismatch
);
```


### Why OC-06 is Insufficient

OC-06 is based on a faulty assumption:
- **Assumption:** Authority is a single entity with one keypair
- **Reality:** Authority can control multiple keypairs

The control tries to prevent self-play by blocking the authority's signing key. But it does not account for:
1. Authority controlling a secondary keypair
2. Authority registering that secondary key as a player
3. Authority always settling matches to favor that secondary key

The fix would require additional controls:
- Multisig (requires multiple parties to collude)
- Timelock (prevents instant decision reversal)
- On-chain game state (verifies outcome on-chain)
- Commit-reveal (makes outcome predictable)
