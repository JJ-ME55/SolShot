# Finding: H030 — H002 RECHECK — Fee Destination Hijack via update_config

## Status: CONFIRMED (v1) / EVOLVED (v2)
## Confidence Score: 9/10

> - **7-8**: High — strong evidence, minor gaps in coverage

## Executive Summary

**v1 (`programs/solshot-escrow/src/lib.rs`) — CONFIRMED, HIGH.**
`settle_match` reads `config.treasury` and `config.ops` live at execution time (`v1:686, 695`). A single `update_config` call rotates both fee destinations instantly, with no timelock, no pending/accept pattern, and no event. Any in-flight match settled after the rotation silently pays the 7%/3% fee split to attacker-controlled wallets. Players receive their correct 90% share and may not notice.

**v2 (`programs/solshot-escrow-v2/src/lib.rs`) — EVOLVED, MEDIUM.**
v2 introduces a per-match snapshot of `treasury`, `ops`, `fee_bps_treasury`, and `fee_bps_ops` captured atomically inside `create_match` (`v2:211-214`). `settle_match` validates fee-destination accounts against the frozen snapshot (`v2:717, 726`), not live config. This provides genuine defense for in-flight matches. However, `update_config` still rotates both destinations in a single TX with no timelock (`v2:96-142`), so every match created after a config rotation inherits the poisoned destinations. The attack surface is narrowed from "all settlements" to "all new matches."

The root cause — one-step authority rotation with no timelock — is unchanged in both programs and is shared with H001. The per-match snapshot in v2 is a real architectural mitigation for the in-flight class, but does not address the broader H001 exposure.

---

## Hypothesis Investigated

**H030 (H002 RECHECK):** A compromised or malicious authority can redirect all settlement fees to attacker-controlled addresses via `update_config`. v1 allows this for ALL in-flight and future matches. v2 snapshots fee destinations at create-time, mitigating in-flight matches but leaving new matches exposed.

## Investigation Path

### Step 1: Confirm v1 SettleMatch reads LIVE config

**Location:** `programs/solshot-escrow/src/lib.rs:682-697`

**Finding:** `treasury` and `ops` are constrained directly against `config.treasury` and `config.ops`. These values are read at settlement execution time; there is no snapshot or cache.

**Evidence:**
```rust
// v1:684-695
#[account(
    mut,
    constraint = treasury.key() == config.treasury @ EscrowError::InvalidTreasury,
    constraint = treasury.key() != ops.key() @ EscrowError::DuplicateFeeAccount,
)]
pub treasury: UncheckedAccount<'info>,

#[account(
    mut,
    constraint = ops.key() == config.ops @ EscrowError::InvalidOps,
)]
pub ops: UncheckedAccount<'info>,
```

Whoever controls `config.treasury` and `config.ops` at call time controls where 10% of the pot goes.

### Step 2: Confirm v1 update_config has no timelock or validation

**Location:** `programs/solshot-escrow/src/lib.rs:72-108`

**Finding:** One-step rotation. `new_treasury` and `new_ops` are applied immediately with no timelock, no pending field, and no event emitted before the change takes effect. The `ConfigUpdated` event fires after the change — reactive, not preventive.

```rust
// v1:85-91
if let Some(t) = new_treasury {
    require!(t != Pubkey::default(), EscrowError::InvalidConfig);
    config.treasury = t;   // immediate, no delay
}
if let Some(o) = new_ops {
    require!(o != Pubkey::default(), EscrowError::InvalidConfig);
    config.ops = o;        // immediate, no delay
}
```

Post-update distinctness checks at `v1:96-98` prevent degenerate collisions but do not constrain the choice of destination pubkeys.

### Step 3: Confirm v2 SettleMatch reads escrow SNAPSHOT

**Location:** `programs/solshot-escrow-v2/src/lib.rs:713-728`

**Finding:** v2 constraints bind `treasury` and `ops` to `escrow.treasury_snapshot` and `escrow.ops_snapshot`, which are immutable per-match values set at create time — not to live config.

```rust
// v2:715-727
#[account(
    mut,
    constraint = treasury.key() == escrow.treasury_snapshot @ EscrowError::InvalidTreasury,
    constraint = treasury.key() != ops.key() @ EscrowError::DuplicateFeeAccount,
)]
pub treasury: UncheckedAccount<'info>,

#[account(
    mut,
    constraint = ops.key() == escrow.ops_snapshot @ EscrowError::InvalidOps,
)]
pub ops: UncheckedAccount<'info>,
```

A post-create `update_config` cannot change where an in-flight v2 match pays fees. The snapshot is the sole authority at settle time.

### Step 4: Verify v2 snapshot atomicity

**Location:** `programs/solshot-escrow-v2/src/lib.rs:201-219`

**Finding:** The snapshot is written inside `create_match` in the same atomic block that initializes all escrow fields and sets `state = AwaitingDeposits`. There is no observable window where the escrow PDA exists with an unset (default) snapshot.

```rust
// v2:201-219 (single atomic instruction)
escrow.treasury_snapshot      = cfg.treasury;
escrow.ops_snapshot           = cfg.ops;
escrow.fee_bps_treasury_snapshot = cfg.fee_bps_treasury;
escrow.fee_bps_ops_snapshot   = cfg.fee_bps_ops;
escrow.state = MatchState::AwaitingDeposits;
// ... remaining fields
```

No instruction after `create_match` modifies any `*_snapshot` field (confirmed by grep across v2). Atomicity is sound.

### Step 5: Confirm v2 update_config still rotates in one step

**Location:** `programs/solshot-escrow-v2/src/lib.rs:96-142`

**Finding:** Same one-step pattern as v1, extended with optional `new_fee_bps_treasury` and `new_fee_bps_ops`. Combined BPS cap enforced at `v2:128-131` (≤ MAX_FEE_BPS = 1000). No timelock. No pending fields.

```rust
// v2:110-123
if let Some(t) = new_treasury { cfg.treasury = t; }   // immediate
if let Some(o) = new_ops { cfg.ops = o; }             // immediate
if let Some(t) = new_fee_bps_treasury { cfg.fee_bps_treasury = t; }
if let Some(o) = new_fee_bps_ops { cfg.fee_bps_ops = o; }
```

Any match created after this TX inherits the new (potentially poisoned) destinations and BPS values via the snapshot mechanism.

### Step 6: Half-mitigation scope

v2's snapshot is a genuine defense for in-flight matches only. The attack surface after a key compromise is:

| Match Lifecycle Phase | v1 Exposed? | v2 Exposed? |
|-----------------------|-------------|-------------|
| Active, not yet settled | YES (live read) | NO (snapshot frozen) |
| Awaiting deposits (created pre-compromise) | YES | NO (snapshot frozen) |
| Created post-compromise (new matches) | YES | YES (snapshot captures poisoned config) |

## Invariant Analysis

### Target Invariant
Fee revenue flows only to protocol-controlled destinations established through a change process that is observable and revocable before funds move.

### Enforcement Points

| Location | What It Enforces | Complete? |
|----------|-----------------|-----------|
| `v1:686, 695` | `treasury.key() == config.treasury` at settle | YES — but trusts live config |
| `v2:717, 726` | `treasury.key() == escrow.treasury_snapshot` at settle | YES — trusts frozen snapshot |
| `v2:211-214` | Snapshot written atomically at create | YES — no gap |
| `v1:96-98`, `v2:125-127` | Distinctness re-validated post-update | YES — prevents degenerate collisions only |
| Timelock | Change cannot take immediate effect | NOT PRESENT — in either version |
| Event before change | Stakeholders notified before money moves | NOT PRESENT |

### Enforcement Gap
The invariant requiring notice before effect is absent. The only gate (`has_one = authority`) is bypassed the moment the authority key is compromised or acts maliciously.

## Enabling Factors

- **No timelock** (`v1:72-108`, `v2:96-142`): treasury/ops rotation effective in the same block.
- **Singleton GlobalConfig**: one TX redirects all subsequent v1 settlements; all new v2 matches.
- **Authority = single hot wallet**: no multisig requirement.
- **v1 live read at settle** (`v1:686, 695`): in-flight match fees fully redirectable.
- **v2 snapshot from current config** (`v2:211-214`): new matches inherit poisoned destinations.

## Blocking Factors

- **`has_one = authority`** (`v1:564`, `v2:598`): only current authority can call `update_config`.
- **v2 per-match snapshot** (`v2:717, 726`): in-flight matches are immune once created.
- **MAX_FEE_BPS = 1000 (v2 only)** (`v2:78`): BPS cannot exceed 10% regardless of config state.
- **`ConfigUpdated` event** (`v1:101-105`, `v2:133-139`): exposes new addresses after the fact; enables reactive monitoring.

## Exploitation Scenario

### Prerequisites
1. Attacker holds authority private key.
2. Attacker controls two distinct wallets: `attacker_treasury`, `attacker_ops`.

### Attack Steps

**v1 (full impact):**
1. Sign and submit `update_config(None, Some(attacker_treasury), Some(attacker_ops))`.
2. All subsequent `settle_match` calls route 7%/3% to attacker wallets. No action from players required.
3. Optionally restore original config after extracting fees to erase evidence at the config level.

**v2 (partial impact):**
1. Same TX as above.
2. In-flight matches (created pre-compromise) remain honest — snapshot is frozen.
3. Every new match created after the TX captures attacker wallets in its snapshot.
4. Authority waits for high-value tournaments / large pots to be created, then harvests 10% per match.

### Impact

| Scenario | Max Per-Match Loss | Scope |
|----------|--------------------|-------|
| v1 (all in-flight + future) | 10% × MAX_POT = 10% × 400 SOL = 40 SOL | All settlements after compromise |
| v2 (new matches only) | 10% × MAX_POT = 10% × 1000 SOL = 100 SOL | All matches created after compromise |

Revenue theft scales with match volume. Players are financially unaffected (winner receives correct amount); the attack targets protocol economics.

### PoC Transaction Sequence

```
TX 1: update_config
  Accounts:
    - config: GlobalConfig PDA [b"config"] (mut)
    - authority: compromised keypair (signer)
  Args:
    - new_authority: None
    - new_treasury: Some(attacker_wallet_A)
    - new_ops: Some(attacker_wallet_B)
    - new_fee_bps_treasury: Some(1000)   // v2 only — maximize extraction
    - new_fee_bps_ops: Some(0)           // combined = 1000 ≤ MAX_FEE_BPS ✓
  Prerequisite: Attacker holds authority private key
  Result:
    - config.treasury = attacker_wallet_A
    - config.ops = attacker_wallet_B
    - (v2) config.fee_bps_treasury = 1000, fee_bps_ops = 0
    - ConfigUpdated event emitted (reveals change but doesn't prevent it)

TX 2 ... TX N (v1): settle_match for each Active match
  treasury: attacker_wallet_A (matches config.treasury — constraint passes)
  ops: attacker_wallet_B (matches config.ops — constraint passes)
  Result: 10% of every pot diverted

TX 2 ... TX N (v2): create_match for new tournaments
  Snapshot captures: treasury_snapshot = attacker_wallet_A, fee_bps_treasury_snapshot = 1000
  Result: every future settlement in those matches pays 10% to attacker

Final State:
  v1 — attacker drains 10% of all settled pots until config is restored
  v2 — attacker drains 10% of all new match pots; in-flight matches unaffected
```

## Recommended Fix

Add a timelock to treasury/ops rotation in both versions. The BPS fields in v2 should be included.

```rust
// Add to GlobalConfig:
pub pending_treasury: Option<Pubkey>,
pub pending_ops: Option<Pubkey>,
pub pending_effective_at: i64,

// Separate propose_fee_update (announces change + delay) from apply_fee_update (executes after delay)
pub fn propose_fee_update(ctx, new_treasury, new_ops) -> Result<()> {
    cfg.pending_treasury = new_treasury;
    cfg.pending_ops = new_ops;
    cfg.pending_effective_at = Clock::get()?.unix_timestamp + TIMELOCK_SECS; // e.g. 86400 = 24h
    emit!(FeeUpdateProposed { new_treasury, new_ops, effective_at });
    Ok(())
}

pub fn apply_fee_update(ctx) -> Result<()> {
    require!(Clock::get()?.unix_timestamp >= cfg.pending_effective_at, TimelockNotExpired);
    if let Some(t) = cfg.pending_treasury { cfg.treasury = t; }
    if let Some(o) = cfg.pending_ops { cfg.ops = o; }
    emit!(FeeUpdateApplied { treasury: cfg.treasury, ops: cfg.ops });
    Ok(())
}
```

Secondary: add a `ConfigUpdated` event that includes the PREVIOUS values alongside the new ones, enabling alerting on unexpected changes even without a timelock.
