# H035: Settle-vs-Cancel Priority-Fee Race (H006 Inverted)

**Status:** CONFIRMED
**Severity:** HIGH
**Confidence:** 9/10
**Affects:** v1 (50-minute race window), v2 (24-hour race window)

---

## Hypothesis

v1's constants (`TIMEOUT_SECONDS=600`, `SETTLEMENT_TIMEOUT_SECONDS=3600`) create a ~50-minute window where both `settle_match` (authority) and `cancel_match` (player) are simultaneously valid. A losing player who observes the authority's `settle_match` TX in the mempool can submit a competing `cancel_match` TX with a higher priority fee. If the cancel lands first, settle fails with `InvalidState`. The loser saves up to 100 SOL wager loss for roughly $0.10–0.30 in priority fees.

v2 removes the settlement deadline entirely: after `match_end_ts`, both `settle_match` and player `cancel_match` are simultaneously valid for the entire 24-hour reclaim grace window.

## Race Window Math

### v1 Timeline (constants at `programs/solshot-escrow/src/lib.rs:20–26`)

```
T = activated_at

T + 0s    : match goes Active
T + 601s  : player cancel_match becomes valid (TIMEOUT_SECONDS = 600)
T + 1201s : permissionless_reclaim becomes valid (TIMEOUT_SECONDS * 2 = 1200)
T + 3600s : settle_match deadline expires (SETTLEMENT_TIMEOUT_SECONDS = 3600)

Race window (settle vs cancel): T+601 → T+3600 = 2,999 seconds ≈ 50 minutes
Triple race (settle + cancel + reclaim): T+1201 → T+3600 = 2,399 seconds ≈ 40 minutes
```

**Key code — settle deadline check (`v1:264–272`):**
```rust
if ctx.accounts.escrow.activated_at > 0 {
    let deadline = ctx.accounts.escrow.activated_at
        .checked_add(SETTLEMENT_TIMEOUT_SECONDS)
        .ok_or(EscrowError::ArithmeticOverflow)?;
    require!(
        Clock::get()?.unix_timestamp <= deadline,
        EscrowError::SettlementExpired
    );
}
```

**Key code — player cancel availability check (`v1:357–378`):**
```rust
let timeout_reference = if ctx.accounts.escrow.activated_at > 0 {
    ctx.accounts.escrow.activated_at
} else {
    ctx.accounts.escrow.created_at
};
let timeout_deadline = timeout_reference
    .checked_add(TIMEOUT_SECONDS)
    .ok_or(EscrowError::ArithmeticOverflow)?;
let is_timed_out = Clock::get()?.unix_timestamp > timeout_deadline;

require!(
    (is_authority && escrow_state == MatchState::AwaitingDeposits)
    || (is_player && (escrow_state == MatchState::AwaitingDeposits || is_timed_out)),
    EscrowError::Unauthorized
);
```

Both conditions are true simultaneously from T+601 to T+3600.

### v2 Timeline (per-match `match_end_ts`, `programs/solshot-escrow-v2/src/lib.rs:387–519`)

```
match_end_ts = activated_at + duration_secs  (60s to 7 days)

After match_end_ts:
  - settle_match: NO deadline (callable any time after activation)
  - cancel_match: becomes valid when now > match_end_ts (v2:480)

Race window: match_end_ts → match_end_ts + 86400 (until permissionless_reclaim boundary)
Duration: 24 hours, for every match regardless of duration_secs
```

**Key code — v2 settle has no deadline (`v2:387–391`):**
```rust

    require!(
        ctx.accounts.escrow.state == MatchState::Active,
        EscrowError::InvalidState
    );
    // NOTE: No deadline check. Authority can settle any time after activation.
```

**Key code — v2 cancel deadline check (`v2:470–480`):**
```rust
let player_cancel_deadline = if ctx.accounts.escrow.activated_at > 0 {
    ctx.accounts.escrow.match_end_ts
} else {
    ctx.accounts.escrow.created_at
        .checked_add(ctx.accounts.escrow.deposit_window_secs as i64)
        .ok_or(EscrowError::ArithmeticOverflow)?

```

After `match_end_ts`, `is_timed_out = true` AND `settle_match` remains callable = race window open.

## Priority-Fee Mechanics

Solana validators order transactions within a block by **compute-unit price** (priority fee = microlamports per CU). Whichever transaction pays more per CU is processed first.

**Mechanics of the race:**

1. Authority broadcasts `settle_match` TX with some priority fee P1.
2. Losing player observes this TX in the mempool via RPC subscription (`getRecentBlockhash` + pending TX monitoring) or simply monitors the on-chain state for match going Active.
3. Losing player broadcasts `cancel_match` TX with priority fee P2 > P1.
4. If the leader processes cancel first, the escrow state transitions to `Cancelled`. The authority's settle TX then fails with `EscrowError::InvalidState` because state is no longer `Active`.
5. All deposited players receive their wager back. The winner receives nothing.

**Typical cost analysis (May 2026, Solana mainnet):**

| Cost component | Estimate |
|---|---|
| Base TX fee | ~5,000 lamports = ~$0.0008 |
| Priority fee (outbid P1) | 10,000–100,000 extra lamports = ~$0.0015–$0.015 |
| Practical bidding war budget | ~100,000–500,000 lamports = ~$0.015–$0.075 |
| Aggressive front-run budget | ~1,000,000 lamports = ~$0.15 |

Even at an aggressive $0.30 priority fee, the attacker saves their entire wager.

## Economic Analysis

### v1 (1v1 match, wager = W SOL)

| Party | Expected outcome (settle wins) | Outcome (cancel wins) | Delta |
|---|---|---|---|
| Winner | Receives 0.9 × 2W = 1.8W | Receives W (refund) | Loses 0.8W |
| Loser/attacker | Pays W (net zero return) | Receives W (refund) | Saves W |
| Treasury | Receives 0.07 × 2W = 0.14W | Receives 0 | Loses 0.14W |
| Ops | Receives 0.03 × 2W = 0.06W | Receives 0 | Loses 0.06W |

**Cost to attacker:** ~$0.10–$0.30 in priority fees
**Benefit to attacker:** W SOL saved (= their full wager)
**At MAX_WAGER = 100 SOL (~$15,000):** ROI = 15,000 / 0.30 = **50,000:1**

The loser does NOT "gain" — they merely recover their own wager by denying the legitimate settlement. However the winner loses 0.8W net versus the legitimate outcome. This is settlement denial, not theft, but it produces the same economic damage to the winner.

### v1 (N-player match, wager = W, N players)

- Total pot = N × W
- Loser calling cancel refunds ALL N depositors including the winner
- Winner expected to receive 0.9 × N × W; instead receives W (only their refund)
- Loser's individual saving: W
- Winner's loss: 0.9 × N × W - W = W(0.9N - 1)
- At N=4 and W=100 SOL: winner loses 260 SOL equivalent

### v2 (longer race window amplifies exposure)

- 24-hour race window instead of 50 minutes
- Attacker has much more time to observe and react
- No settlement deadline means the authority may legitimately delay settle (e.g., awaiting game result confirmation) — making it harder to distinguish lazy settle from an attack
- At MIN_DURATION_SECS=60 (1-minute match), the 24-hour race window opens 1 minute after activation

## Why H006 Inverted (the Feb Finding Context)

The **February 2026 H006** finding described a "23-hour dead zone" where:
- `TIMEOUT_SECONDS = 86400` (24h): player cancel becomes available only after T+24h
- `SETTLEMENT_TIMEOUT_SECONDS = 3600` (1h): settle deadline expires at T+1h
- Gap: from T+3601 to T+86400, NEITHER settle NOR player cancel was valid — a 23-hour period where funds were stuck

The fix was to reduce `TIMEOUT_SECONDS` from 86400 to 600. This closed the dead zone but **inverted** the problem:
- Now `TIMEOUT_SECONDS (600) < SETTLEMENT_TIMEOUT_SECONDS (3600)`
- Player cancel is available at T+601, settle deadline is T+3600
- The overlap is 50 minutes of simultaneous validity

The original H006 had a window with NO valid actions. H035 has a window with TOO MANY valid actions and Solana's priority-fee mechanism determines which action wins. The dead zone became a settlement-denial race.

## Evidence

### v1 Constants Confirm the Math (`programs/solshot-escrow/src/lib.rs:19–26`)

```rust
const TIMEOUT_SECONDS: i64 = 600;
const PERMISSIONLESS_RECLAIM_TIMEOUT: i64 = TIMEOUT_SECONDS * 2; // = 1200
const SETTLEMENT_TIMEOUT_SECONDS: i64 = 3600;
```

Note: the comment at line 22 reads "48-hour permissionless reclaim timeout" and "172800 seconds" but the actual computation is `600 * 2 = 1200` seconds (20 minutes). The comment is incorrect (separate finding; cited in timing-ordering context as HIGH stale-comment issue).

### v2 No Deadline Confirms the v2 Race (`programs/solshot-escrow-v2/src/lib.rs:384–391`)

The v2 `settle_match` function contains only a state guard (`state == Active`) and no time-based deadline check. Both settle (any time, state==Active) and cancel (after match_end_ts, state not terminal) are simultaneously valid from match_end_ts onward.

### State Guard Interaction Confirms First-TX-Wins Mechanism

Both `settle_match` and `cancel_match` require `state == Active` (settle: v1:259–262, v2:388–391) or `state != Settled && state != Cancelled` (cancel: v1:380–383, v2:491–494). Whichever TX lands first sets state to `Settled` or `Cancelled` respectively. The second TX fails on the state guard. This is a clean first-TX-wins race.

## Invariant Analysis

**Target invariant:** "Once a match is Active and the server submits a settle TX, that TX should land successfully and the winner should receive their winnings."

**Enforcement:**
- The on-chain program enforces no priority over `settle_match` vs `cancel_match`.
- There is no `pending_settle` flag or lock that would block `cancel_match` while a settle TX is in flight.
- Both instructions execute atomically on state == Active.
- The invariant is NOT enforced — it is violated by any losing player who wins the priority-fee race.

**Enforcement Gap:** No mechanism reserves the state machine for the settle path during the overlap window. This is an architectural gap: the program treats settle and cancel as peer-level instructions from T+601 to T+3600 (v1), even though the server is the only legitimately authorized settler.

## Attack Path Analysis

| Step | Required Action | Possible? | Evidence |
|---|---|---|---|
| 1 | Match goes Active | Yes | Normal gameplay flow |
| 2 | Wait for T + 601s | Yes | Trivial — attacker is losing player watching match |
| 3 | Observe authority's settle TX in mempool | Yes | Public mempool on Solana; RPC subscription trivial |
| 4 | Broadcast cancel_match TX with higher priority fee | Yes | Any wallet can submit; player qualifies (v1:372 `is_player` check) |
| 5 | cancel TX lands before settle TX | Yes (probabilistic) | Solana priority-fee ordering; higher fee = processed first |
| 6 | settle TX fails on InvalidState | Yes | State is now Cancelled; settle requires Active |
| 7 | Attacker receives full wager refund | Yes | cancel_match refund loop processes all deposited players |

**Caveat on step 5:** The race is not guaranteed to succeed — if the authority uses a very high priority fee the cancel TX may not win. However, the economic incentive (save 100 SOL vs spend $0.30) means the attacker will outbid substantially.

## Recommended Fix

### Option A — Tighten cancel deadline to align with settle deadline (v1)

Change the relationship so that player cancel is NOT available until after the settle window closes. This requires `TIMEOUT_SECONDS > SETTLEMENT_TIMEOUT_SECONDS`.

```rust
// Before (vulnerable — creates 50-minute race window)
const TIMEOUT_SECONDS: i64 = 600;           // cancel available T+601
const SETTLEMENT_TIMEOUT_SECONDS: i64 = 3600; // settle expires T+3600

// After (safe — cancel only available after settle has expired)
const TIMEOUT_SECONDS: i64 = 3600;          // cancel available T+3601
const SETTLEMENT_TIMEOUT_SECONDS: i64 = 3600; // settle still expires T+3600
// or more conservatively:
const TIMEOUT_SECONDS: i64 = 4200;          // 10-minute grace after settle expires
```

**Trade-off:** Players must wait longer before they can cancel an unsettled match.

### Option B — `pending_settle` locking flag (both v1 and v2)

Add a boolean `pending_settle: bool` to MatchEscrow. Authority sets it in a preliminary TX; `cancel_match` and `permissionless_reclaim` check `!pending_settle`. This gives the authority a way to "lock" the settle path before the TX is broadcast.

```rust
// In MatchEscrow struct
pending_settle: bool,  // set true by signal_settle instruction

// In cancel_match validation
require!(!ctx.accounts.escrow.pending_settle, EscrowError::SettlePending);
```

**Trade-off:** Requires an extra TX; adds instruction surface. The lock must timeout to prevent authority grief.

### Option C — Eliminate the race by removing the player-cancel-during-Active path (v1)

If players should only be able to cancel during `AwaitingDeposits`, remove the `is_timed_out` path for Active state and rely on `permissionless_reclaim` as the sole escape hatch for abandoned matches.

**Trade-off:** Players have no way to self-recover from a dead Active match until the permissionless window (T+1200). With PERMISSIONLESS_RECLAIM_TIMEOUT = 1200s (20 min), this is acceptable.

### Option D — v2: Add cancel grace period after settle authority signal

Since v2 has no settle deadline, the race window is theoretically infinite. A `settle_signal` instruction would give the authority an on-chain mechanism to declare intent, after which a short grace window expires and `cancel_match` is temporarily blocked.

### Recommended approach for mainnet

**Short term:** For v1, raise `TIMEOUT_SECONDS` to `>= SETTLEMENT_TIMEOUT_SECONDS` (Option A). This is a 1-line constant change. For v2, document the race as a known limitation and rely on the authority submitting settle TXs with high priority fees.

**Long term:** Option B (pending_settle lock) provides the most defense-in-depth and eliminates the race entirely at the cost of one extra TX.

## Off-Chain Mitigations and Why They Are Insufficient

**Server submits settle with high priority fee:** If the authority submits settle with priority fee F, an attacker submits cancel with F + ε. The authority can counter-escalate, but:
- The attacker's incentive (save W SOL) always dominates the authority's incentive (save TX cost)
- At MAX_WAGER=100 SOL, the attacker will pay up to ~100 SOL in fees to win the race — far above what the authority would rationally spend
- Priority-fee bidding wars end when one party's cost exceeds their benefit; for the attacker, that ceiling is their wager

**Server batches settle faster than T+601:** The server cannot guarantee sub-600s settlement for every match. Network latency, server load, and game result confirmation all introduce delays. In practice, many matches will be settled well after T+601, leaving the full race window open.
