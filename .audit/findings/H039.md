# Finding: H039 — NOVEL — v2 Unbounded duration_secs Lockup (8-Day Fund Lock)

**One-line summary:** A hostile authority can set `duration_secs = 604800` (7 days) to lock all deposited player funds for 8 days with no economic benefit to the attacker and no on-chain recourse for players until the grace window expires.

## Status: POTENTIAL
## Confidence Score: 9/10

> Confidence scale:
> - **9-10**: Certain — exhaustive code analysis, all paths verified
>
> Rating justification: All relevant constants, deadline formulas, and access-control checks were read directly from source. The only gap is the absence of a live devnet test demonstrating the full 8-day lockup in practice — hence POTENTIAL rather than CONFIRMED.

---

## Executive Summary

v2 introduces per-match configurable timing via `duration_secs` (60s – 7 days) and `deposit_window_secs` (60s – 24h), both set by the authority at `create_match`. Once a match is Active, `match_end_ts = activated_at + duration_secs` is immutable. Players may not cancel until `match_end_ts` passes. The permissionless reclaim escape hatch is gated behind `match_end_ts + PUBLIC_REFUND_GRACE_SECS` (24h). Setting `duration_secs = MAX_DURATION_SECS = 604800` (7 days) therefore creates a worst-case fund lockup horizon of **8 days** — 7 days players cannot act, plus a 24-hour grace before anyone can reclaim. The authority gains no lamports from this action; its only utility is griefing or stalling the protocol.

---

## Hypothesis Investigated

> Authority can set duration_secs up to MAX_DURATION_SECS=604800 (7 days). Plus 24h grace = 8 days fund lockup. Authority gets nothing economically but can stall the protocol.

## Investigation Path

### Step 1: Verify MAX_DURATION_SECS value

**Location:** `programs/solshot-escrow-v2/src/lib.rs:38-39`

**Finding:** Confirmed `MAX_DURATION_SECS = 7 * 24 * 3_600 = 604800`.

**Evidence:**
```rust
const MIN_DURATION_SECS: u32 = 60;                 // 1 min — supports real-time mode
const MAX_DURATION_SECS: u32 = 7 * 24 * 3_600;     // 7 days — covers 72h async + headroom
```

### Step 2: Verify reclaim deadline = match_end_ts + 24h

**Location:** `programs/solshot-escrow-v2/src/lib.rs:539-549`

**Finding:** Confirmed. When `activated_at > 0` (Active state), the reclaim deadline is `match_end_ts + PUBLIC_REFUND_GRACE_SECS`.

**Evidence:**
```rust
let reclaim_deadline = if ctx.accounts.escrow.activated_at > 0 {
    ctx.accounts.escrow.match_end_ts
        .checked_add(PUBLIC_REFUND_GRACE_SECS)
        .ok_or(EscrowError::ArithmeticOverflow)?
} else {
    ctx.accounts.escrow.created_at
        .checked_add(ctx.accounts.escrow.deposit_window_secs as i64)
        ...
        .checked_add(PUBLIC_REFUND_GRACE_SECS)
        ...
};
require!(
    Clock::get()?.unix_timestamp > reclaim_deadline,
    EscrowError::TooEarlyToReclaim
);
```

`PUBLIC_REFUND_GRACE_SECS` is defined at line 47: `const PUBLIC_REFUND_GRACE_SECS: i64 = 24 * 3_600;` — confirmed 24 hours.

### Step 3: Verify player cancel deadline = match_end_ts (no early exit during Active match)

**Location:** `programs/solshot-escrow-v2/src/lib.rs:470-487`

**Finding:** Confirmed. For an Active match (`activated_at > 0`), the player-cancel deadline is `match_end_ts` — players cannot cancel before the match ends.

**Evidence:**
```rust
let player_cancel_deadline = if ctx.accounts.escrow.activated_at > 0 {
    ctx.accounts.escrow.match_end_ts
} else {
    ctx.accounts.escrow.created_at
        .checked_add(ctx.accounts.escrow.deposit_window_secs as i64)
        ...
};
let now = Clock::get()?.unix_timestamp;
let is_timed_out = now > player_cancel_deadline;
...
require!(
    (is_authority && escrow_state == MatchState::AwaitingDeposits)
        || (is_player && (escrow_state == MatchState::AwaitingDeposits || is_timed_out)),
    EscrowError::Unauthorized
);
```

Players in an Active match are blocked from cancelling until `now > match_end_ts`.

### Step 4: Verify match_end_ts formula = activated_at + duration_secs

**Location:** `programs/solshot-escrow-v2/src/lib.rs:298-303` (deposit path) and `lib.rs:364-369` (start_with_depositors path)

**Finding:** Confirmed. Both activation paths set `match_end_ts = now + duration_secs`.

**Evidence (deposit path):**
```rust
escrow.state = MatchState::Active;
escrow.activated_at = now;
escrow.match_end_ts = now
    .checked_add(duration_secs as i64)
    .ok_or(EscrowError::ArithmeticOverflow)?;
```

### Step 5: Verify duration_secs is authority-controlled and bounded only by MAX_DURATION_SECS

**Location:** `programs/solshot-escrow-v2/src/lib.rs:161-184`

**Finding:** Confirmed. `duration_secs` is a parameter of `create_match`, callable only by the authority. The only validation is `MIN_DURATION_SECS ≤ duration_secs ≤ MAX_DURATION_SECS`. There is no per-match-type constraint or lower cap.

**Evidence:**
```rust
pub fn create_match(
    ctx: Context<CreateMatch>,
    match_id: String,
    wager_lamports: u64,
    players: Vec<Pubkey>,
    duration_secs: u32,
    deposit_window_secs: u32,
) -> Result<()> {
    ...
    require!(duration_secs >= MIN_DURATION_SECS, EscrowError::DurationTooShort);
    require!(duration_secs <= MAX_DURATION_SECS, EscrowError::DurationTooLong);
    ...
    escrow.duration_secs = duration_secs;
```

### Step 6: Compute total lockup horizon

| Phase | Duration | Formula | Max Value |
|-------|----------|---------|-----------|
| Match active (players locked) | `duration_secs` | authority-set | 604800s (7 days) |
| Player-cancel window opens | 0 | at `match_end_ts` exactly | — |
| Permissionless reclaim grace | `PUBLIC_REFUND_GRACE_SECS` | constant | 86400s (24h) |
| **Total maximum lockup horizon** | — | `duration_secs + 86400` | **691200s (8 days)** |

## Invariant Analysis

### Target Invariant

Player funds should not be locked for unreasonably long periods at the sole discretion of the authority.

### Enforcement Points

| Location | What It Enforces | Complete? |
|----------|-----------------|-----------|
| `v2:174-175` | Lower bound `duration_secs >= 60s` | Yes — but only a floor |
| `v2:175` | Upper bound `duration_secs <= 604800` (7 days) | **Partial** — 7-day cap is the attack surface itself |
| `v2:471-477` | Player cancel gated on `match_end_ts` | Yes — by design, but combines with long duration |
| `v2:539-549` | Permissionless reclaim gated on `match_end_ts + 24h` | Yes — grace period compounds the lockup |

### Enforcement Gap Assessment

The invariant is not enforced. The program correctly validates `duration_secs` against `MAX_DURATION_SECS`, but `MAX_DURATION_SECS = 604800` is the vulnerability — the cap is set too high for a real-time gaming protocol. The reclaim grace was designed as a safety valve but, at 24h, adds a material extension to an already-long lockup.

---

## Blocking Factors

- **`has_one = authority`** on `create_match`: Only the authority key can create matches — this attack requires the authority to be hostile or compromised. Not an anonymous exploit.
- **Players can cancel once `match_end_ts` passes**: `v2:480-488` — players are not permanently locked; the window is bounded by `duration_secs + 24h`.
- **`MAX_DURATION_SECS`**: The cap at 7 days prevents arbitrarily long lockup (e.g., 1 year). This is a real limit.

---

## Enabling Factors

- **`duration_secs` is uncapped below 7 days**: Authority has full discretion from 60s to 604800s per match. No per-match-type constraint.
- **No on-chain settlement deadline in v2**: Unlike v1 (`SETTLEMENT_TIMEOUT_SECONDS = 3600`), v2 imposes no deadline on the authority to settle. A hostile authority simply waits.
- **`PUBLIC_REFUND_GRACE_SECS = 86400` adds 24h**: The grace period is a fixed constant and adds to the lockup regardless of `duration_secs`.
- **Authority has no economic skin in the game**: The authority earns nothing by setting a long `duration_secs`; it can purely grief players at zero cost beyond TX fees.

## Exploitation Scenario

### Prerequisites

1. Authority wallet is compromised or the authority acts maliciously.
2. Players are willing to deposit into a match (they see a nominal `duration_secs` on-chain but may not inspect it carefully, or a frontend can obscure it).
3. No prior protocol-level enforcement of maximum practical match duration.

### Attack Steps

1. Authority calls `create_match` with `duration_secs = 604800` (7 days) and normal `wager_lamports` (e.g., 1 SOL).
2. Players deposit their wagers. Match transitions to Active; `match_end_ts = now + 604800`.
3. Authority takes no further action — does not settle, does not cancel.
4. Players attempt `cancel_match`: rejected with `Unauthorized` because `now <= match_end_ts`.
5. Days 1-7: funds are completely locked. No recourse.
6. Day 7: `now > match_end_ts`. Players can call `cancel_match`. Funds begin to refund.
   - Note: NOVEL-02 (partial `remaining_accounts`) applies here too — malicious player could also steal from co-depositors.
7. Permissionless reclaim becomes available on day 8 (`match_end_ts + 86400`).

### Impact

- **Player funds locked for 7 days minimum**, 8 days before any permissionless reclaim.
- **Protocol liveness stalled**: no new matches can proceed while the trust model is questioned.
- **Reputational damage**: even 1 incident of intentional 7-day lockup is catastrophic for a gaming product.
- **Amplified with N=10**: at 100 SOL max wager and 10 players, authority can lock 1000 SOL (~$200k+ at current prices) for 8 days.

### PoC Transaction Sequence

```
TX 1: create_match
  Accounts: authority (signer), config PDA, escrow PDA (init), system_program
  Args: match_id="grief-001", wager_lamports=100_000_000_000 (100 SOL),
        players=[A, B, C, ..., J] (10 players), duration_secs=604800, deposit_window_secs=3600
  Prerequisite: authority key controls config.authority
  Result: MatchEscrow created, state=AwaitingDeposits, duration_secs=604800 stored on-chain

TX 2–11: deposit_wager (×10 players)
  Accounts: player[i] (signer), escrow PDA, system_program
  Args: (none — player derived from signer)
  Prerequisite: TX 1 complete; called within deposit_window_secs
  Result: 100 SOL × 10 = 1000 SOL locked in escrow; state=Active; match_end_ts = now + 604800

[Authority takes NO further action for 7 days]

Players attempt TX: cancel_match
  Result: REJECTED — EscrowError::Unauthorized (now <= match_end_ts)

Day 7 (T + 604800s):
TX 12: cancel_match (any deposited player)
  Accounts: caller=player (signer), config, escrow PDA
  remaining_accounts: [player_0_account, player_1_account, ..., player_9_account]
  Prerequisite: now > match_end_ts
  Result: All players refunded (if remaining_accounts is complete and contiguous)

Day 8 (T + 604800 + 86400):
TX 12 (alternative): permissionless_reclaim
  Accounts: caller=any (signer), escrow PDA
  Prerequisite: now > match_end_ts + 86400
  Result: All deposited players refunded; PDA rent goes to caller

Final State: Players recovered funds after 7+ days. Authority achieved maximum griefing at zero economic cost.
```

## Recommended Fix

Reduce `MAX_DURATION_SECS` to 86400 (24 hours) for the initial production deployment. A 24-hour match is already generous for an async gaming product; it accommodates different time zones and turn-based async play without enabling multi-day fund lockup.

If longer matches are genuinely needed in future, introduce per-class duration caps rather than a single global maximum.

```rust
// Before (vulnerable)
const MAX_DURATION_SECS: u32 = 7 * 24 * 3_600;     // 7 days — covers 72h async + headroom

// After (fixed)
const MAX_DURATION_SECS: u32 = 24 * 3_600;          // 24 hours — prevents 8-day fund lockup
```

Optionally, add an on-chain settlement deadline to v2 (mirroring v1's `SETTLEMENT_TIMEOUT_SECONDS`) so that even a passive authority cannot stall indefinitely — players would gain cancel rights once the deadline expires, independent of `match_end_ts`. This also removes ASSUMPTION-T3 (`Authority will settle within match_end_ts`) from the unvalidated assumption list.

## Blocking Factors Summary

- This is not an anonymous exploit — it requires authority-level access (`PR:H`).
- Funds are **not permanently lost** — they are refunded after the lockup horizon.
- `MAX_DURATION_SECS = 604800` is an explicit design choice (comment says "72h async + headroom") — the cap was intentionally generous.

## Related Findings

- **H001** (authority one-step rotation): Compromise of the hot wallet that enables H039 also enables instant full drain via H001. H039's lockup attack is lower-impact but lower-barrier than H001 post-compromise.
- **NOVEL-02** (partial `remaining_accounts` theft): After the 7-day lockup expires, a malicious first player calling `cancel_match` with incomplete `remaining_accounts` could steal co-depositors' wagers, compounding the damage.
- **v2 deposit-ordering lockup** (context:08, Risk #5): Even in `AwaitingDeposits` state, authority setting `deposit_window_secs = 86400` locks the first depositor for 24h + 24h grace = 48h. Combined with `duration_secs`, total exposure can reach 8d + 48h = ~9.3 days if the authority staggers the two parameters adversarially.

## Incidental Discoveries

- **No settlement deadline in v2**: Unlike v1 (`SETTLEMENT_TIMEOUT_SECONDS = 3600`), v2 has no cap on how long after `match_end_ts` the authority can delay calling `settle_match`. An authority that is merely slow (not malicious) can sit on an expired match indefinitely — players can cancel, but the authority retains discretion to settle at any point before any player-cancel lands. This is an ASSUMPTION-T3 gap flagged in the timing audit (`08-timing-ordering.md`). Suggested new hypothesis: **H-NEW: v2 No Settlement Deadline — Authority Can Delay Settlement Indefinitely Post-match_end_ts**.
