# Finding: H040 — NOVEL — Stale 48-Hour Comment Misleads Operators

**One-line summary:** `lib.rs:22-23` claims "48-hour permissionless reclaim timeout" and trails `// 172800 seconds`, but the actual value is `TIMEOUT_SECONDS * 2 = 600 * 2 = 1200s = 20 minutes` — operators planning incident response will wait 48 hours for a window that opens in 20 minutes.

## Status: CONFIRMED
## Confidence Score: 10/10

> Confidence scale:
> - **9-10**: Certain — exhaustive code analysis, all paths verified
>
> Rating justification: The discrepancy is deterministic arithmetic. `TIMEOUT_SECONDS = 600` (v1:20); `PERMISSIONLESS_RECLAIM_TIMEOUT = TIMEOUT_SECONDS * 2 = 1200` (v1:23). The comment says "48-hour" and "172800 seconds". Neither matches. No ambiguity, no runtime variance.

---

## Executive Summary

In `programs/solshot-escrow/src/lib.rs` lines 22–23, a doc-comment and an inline comment both state that `PERMISSIONLESS_RECLAIM_TIMEOUT` is a "48-hour" window (172800 seconds). The actual value is `TIMEOUT_SECONDS * 2 = 600 * 2 = 1200 seconds = 20 minutes`. The two embedded numeric claims are factually wrong by a factor of 144. This is a documentation bug, not a code logic bug — the constant's runtime value is correct for the design intent, and no funds are at risk from the comment itself. However, any operator, incident responder, or auditor who reads the comment to plan response timelines will assume a 48-hour escape-hatch window and may miss or ignore the 20-minute reclaim window entirely.

## Investigation Path

### Step 1: Read the comment text verbatim

**Location:** `programs/solshot-escrow/src/lib.rs:19-23`

**Finding:** The doc-comment on line 22 says "48-hour permissionless reclaim timeout (2x normal timeout)" and the trailing inline comment on line 23 says `// 172800 seconds`. Both are wrong.

**Evidence:**
```rust
/// 10-minute timeout for deposit window (ESC-10 — higher no-show risk with more players)
const TIMEOUT_SECONDS: i64 = 600;

/// 48-hour permissionless reclaim timeout (2x normal timeout) — DCA-02
const PERMISSIONLESS_RECLAIM_TIMEOUT: i64 = TIMEOUT_SECONDS * 2; // 172800 seconds
```

### Step 2: Verify the actual computed value

**Location:** `programs/solshot-escrow/src/lib.rs:20, 23`

**Finding:** `TIMEOUT_SECONDS = 600` (line 20). `PERMISSIONLESS_RECLAIM_TIMEOUT = 600 * 2 = 1200`. This is 20 minutes. The comment value 172800 would require `TIMEOUT_SECONDS = 86400` (24 hours).

| Term | Source | Value |
|------|--------|-------|
| `TIMEOUT_SECONDS` | `v1:20` | 600s (10 min) |
| `PERMISSIONLESS_RECLAIM_TIMEOUT` | `v1:23` | 1200s (20 min) |
| Comment claims | `v1:22` doc-comment | 172800s (48h) |
| Inline claims | `v1:23` trailing comment | 172800s (48h) |
| **Discrepancy factor** | | **144×** |

### Step 3: Verify how the constant is used

**Location:** `programs/solshot-escrow/src/lib.rs:442-456` (permissionless_reclaim instruction body)

**Finding:** The constant is used in a `checked_add` deadline calculation. The 1200s value is what lands on-chain. The comment has zero influence on runtime behaviour; only the numeric value matters. The runtime is correct; only the documentation is wrong.

**Evidence:**
```rust
let reclaim_deadline = ctx.accounts.escrow.created_at
    .checked_add(PERMISSIONLESS_RECLAIM_TIMEOUT)  // 1200s — 20 minutes, NOT 48h
    .ok_or(EscrowError::ArithmeticOverflow)?;
require!(
    Clock::get()?.unix_timestamp > reclaim_deadline,
    EscrowError::TooEarlyToReclaim
);
```

### Step 4: Assess operational impact of the stale comment

**Finding:** The comment is dangerous in three ways:
1. **Incident response planning**: An operator reading the code to plan monitoring or alerting will set their reclaim-window alarm for T+48h. The actual window opens at T+20min. Any stranded funds become reclaim-eligible 143h 40min before the operator expects — they lose the opportunity to act first.
2. **Audit history poisoning**: The architecture document (`ARCHITECTURE.md:385`) already cites "Stale 48-hour comment" and correctly identifies `v1:22-23`, but the comment in source is unchanged. Future fresh audits of the `.rs` file encounter the same lie without the context doc.
3. **Misleading inline arithmetic**: `// 172800 seconds` is a plausible-looking sanity check that appears to confirm the doc-comment. A reader doing quick mental math sees a consistent narrative (`48h × 3600 = 172800`), never questions it, and never recomputes from `TIMEOUT_SECONDS`.

## Exploitation Scenario

### Prerequisites

1. Operator or incident responder reads `lib.rs:22-23` to understand reclaim windows.
2. Operator does not independently verify by computing `TIMEOUT_SECONDS * 2`.

### Attack Steps

1. A match enters a stranded state (server down, authority unavailable).
2. At T+1200s (20 min), `permissionless_reclaim` becomes callable. Any wallet can claim the PDA rent.
3. Operator, believing the window is T+172800 (48h), does not act until day 2.
4. A third-party bot sweeps the reclaim at T+1201s, collecting the PDA rent reserve (~0.002 SOL per match) before the operator's monitoring triggers.

### Impact

- **Operational**: Incorrect incident-response SLA. Teams planning 48h recovery windows miss the 20-min escape hatch.
- **Rent extraction**: PDA rent goes to any caller of `permissionless_reclaim`. An operator who planned for 48h loses the rent to a front-runner at 20 min.
- **Audit confidence**: Future auditors reading the comment without recomputing may carry forward the wrong 48h figure into their reports, perpetuating the incorrect threat model.

## Recommended Fix

Update both comment sites on line 22 to accurately reflect the computed value:

```rust
// Before (inaccurate)
/// 48-hour permissionless reclaim timeout (2x normal timeout) — DCA-02
const PERMISSIONLESS_RECLAIM_TIMEOUT: i64 = TIMEOUT_SECONDS * 2; // 172800 seconds

// After (accurate)
/// 20-minute permissionless reclaim timeout (2x deposit timeout = 1200s) — DCA-02
const PERMISSIONLESS_RECLAIM_TIMEOUT: i64 = TIMEOUT_SECONDS * 2; // 1200 seconds
```

Additionally, add a compile-time assertion to ensure the comment can never drift again:

```rust
const _: () = assert!(
    PERMISSIONLESS_RECLAIM_TIMEOUT == 1200,
    "PERMISSIONLESS_RECLAIM_TIMEOUT must be 1200s (20 min); update comment if value changes"
);
```

If the design intent was genuinely a 48-hour reclaim window (i.e., the constant is wrong rather than the comment), then the fix is to update `TIMEOUT_SECONDS * 2` to a hardcoded `172800i64` and restore the 48-hour framing — but this would require verifying that the current 20-minute window is intentional (the timing audit confirms it is: `08-timing-ordering.md` states 1200s is the live value and treats it as correct).
