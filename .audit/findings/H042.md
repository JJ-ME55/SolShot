# Finding: H042 — GlobalConfig Has No Close Path

**One-line summary:** No `close_config` instruction exists in either program; if the authority key is lost, GlobalConfig is permanently unrecoverable and the protocol locks forever — the only escape requires a Layer-1 program upgrade, which itself needs the same key.

## Status: CONFIRMED
## Confidence Score: 9

> **9**: Exhaustive grep of both lib.rs files. All public functions enumerated. `close = ` search confirmed only MatchEscrow accounts carry close constraints. No pending-authority field found in GlobalConfig structs. Evidence is direct and complete.

---

## Executive Summary

Neither `programs/solshot-escrow/src/lib.rs` (v1, 962 LOC) nor `programs/solshot-escrow-v2/src/lib.rs` (v2, 1020 LOC) contains a `close_config` instruction, a `pending_authority` field, or any mechanism to rotate authority without the current authority signing. GlobalConfig is a permanent singleton PDA seeded `[b"config"]`; once initialized it can only be mutated (not closed) by whoever currently holds `config.authority`.

If that key is lost — due to hardware failure, seed-phrase loss, or key rotation error — there is no on-chain path to recover. `update_config` requires the old authority to sign. No guardian, no social recovery, no time-delayed escape hatch. The only remediation path is a Layer-1 program upgrade introducing a new recover instruction, which requires the upgrade authority key — currently the same hot wallet (`HPyVPj2VH9yBirr7FMgAJeDH8xJgaMKy5UnwLkjSnovk`) that holds application authority. Losing this key loses both layers simultaneously.

This compounds directly with H001 (no `pending_authority` two-step flow): H001 means a compromised key can instantly seize the protocol; H042 means a *lost* key permanently locks it. Together they represent the full blast radius of single-key dependency.

---

## Hypothesis Investigated

> No `close_config` instruction exists. If authority key is lost AND H001 stays open, GlobalConfig is permanently locked. Recovery requires Layer-1 program upgrade introducing a recover instruction — which itself requires upgrade-key access.

## Invariant Analysis

### Target Invariant
The protocol must always have a live, reachable authority capable of creating matches, settling disputes, and rotating config. GlobalConfig is the sole source of this authority.

### Enforcement Points

| Location | What It Enforces | Complete? |
|----------|-----------------|-----------|
| `v1:568, v2:608` | `has_one = authority` on `update_config` | Yes — but blocks recovery if key lost |
| `v1:82, v2:107` | `a != Pubkey::default()` prevents burn to zero-address | Yes — but doesn't provide recovery |
| `v1:787-798, v2:810-818` | GlobalConfig struct — no recovery field | Yes — gap confirmed |

### Enforcement Gap Assessment

The invariant "authority is always reachable" is NOT enforced. The program guarantees the authority field is non-zero (Pubkey::default() guard), but it does not guarantee the holder of that key is alive or accessible. A lost key permanently satisfies "non-zero" while being completely unreachable.

---

## Enabling Factors

- **Single-key design:** Both application authority and upgrade authority resolve to the same hot wallet (`HPyVPj2VH9yBirr7FMgAJeDH8xJgaMKy5UnwLkjSnovk`). One event (key loss) disables both recovery paths.
- **No pending_authority:** H001 documents the absence of a two-step flow. The same structural gap that makes instant takeover possible also makes recovery impossible.
- **GlobalConfig is permanent:** Seeds `[b"config"]` produce a deterministic singleton with no close path. The PDA exists forever.
- **`update_config` requires live authority signature:** There is no "fallback authority" or "guardian" bypass.

## Blocking Factors

None. There is no on-chain mechanism preventing permanent protocol lockup on key loss.

## Exploitation Scenario

### Prerequisites
1. The hot wallet key (`HPyVPj2VH9yBirr7FMgAJeDH8xJgaMKy5UnwLkjSnovk`) is lost (hardware failure, seed-phrase loss, operational error during rotation, or wiped from CI secrets).

### What Happens
1. All new match creation stops — `create_match` requires authority signature.
2. All settlement stops — `settle_match` requires authority signature.
3. All config rotation stops — `update_config` requires authority signature.
4. Players with active matches can still cancel/reclaim via `cancel_match` (Active state, after timeout) or `permissionless_reclaim` (after grace period) — these paths do NOT require config.authority. Funds are not permanently frozen.
5. The protocol is **dead** for new business. GlobalConfig still exists on-chain with the old (unreachable) authority forever.

### What Cannot Happen (mitigating factors)
- Player funds in existing active matches are NOT permanently frozen — `cancel_match` and `permissionless_reclaim` are available without authority signature.
- The protocol can be replaced by deploying a NEW program at a different address if upgrade-key is somehow recovered separately.

### Impact
- **Operational shutdown**: No new matches can be created. No settlement possible.
- **Reputational damage**: Protocol publicly dead on-chain with no recovery path visible.
- **No direct player fund loss** (permissionless reclaim is the safety net), but all new wagering stops.
- If upgrade-key is also lost (same wallet): no Layer-1 recovery possible. GlobalConfig PDA occupies its address forever as dead state.


## Recommended Fix

Introduce a key-recovery mechanism before mainnet. Two options in ascending robustness:

**Option A (Minimal — guardian wallet):** Add a `guardian` field to `GlobalConfig` and a `guardian_recover` instruction with a time-delay (e.g. 48–72 hours) that allows the guardian to rotate `config.authority` without the old authority signing. The delay provides a window to detect and cancel fraudulent use.

```rust
// Before: GlobalConfig has no recovery path
pub struct GlobalConfig {
    pub authority: Pubkey,
    ...
}

// After: add guardian + optional pending recovery
pub struct GlobalConfig {
    pub authority: Pubkey,
    pub guardian: Pubkey,           // cold wallet / multisig
    pub pending_authority: Option<Pubkey>,
    pub pending_authority_ts: i64,  // when recovery was initiated
    ...
}

// New instruction: guardian initiates recovery (no authority sig needed)
pub fn initiate_recovery(ctx: ..., new_authority: Pubkey, delay_secs: i64) -> Result<()> {
    // requires guardian signature, not authority
    config.pending_authority = Some(new_authority);
    config.pending_authority_ts = Clock::get()?.unix_timestamp + delay_secs;
}

// New instruction: anyone finalizes after delay
pub fn finalize_recovery(ctx: ...) -> Result<()> {
    require!(now >= config.pending_authority_ts, EscrowError::RecoveryNotReady);
    config.authority = config.pending_authority.unwrap();
    config.pending_authority = None;
}
```

**Option B (Recommended — multisig upgrade authority):** Transfer the Solana-level upgrade authority to a multisig (e.g., Squads) before mainnet. A multisig upgrade authority means key loss of any single key cannot prevent recovery via Layer-1 upgrade. This also addresses the H001 + H042 compound risk.

**Minimum viable pre-mainnet action:** Separate the upgrade authority key from the application authority key. Even if both remain hot wallets, two distinct keys mean single-key loss does not simultaneously close both recovery paths.

## Related Findings

- **H001** (STILL OPEN): No `pending_authority` two-step flow. H001 and H042 are complementary faces of the same structural gap — H001 = compromised key seizes everything; H042 = lost key locks everything. A fix for H001 (`pending_authority` + timelock) partially mitigates H042 if the pending-authority mechanism allows a third party to complete rotation.
- **Upgrade-admin context finding #4:** Documents this as "HIGH — No `close_config` instruction; key loss permanent without upgrade." This investigation confirms that finding with direct code evidence.
- **Layer-1 upgrade authority co-location:** Both v1 and v2 use the same hot wallet for upgrade authority and application authority. Fixing H042 in isolation (add guardian) does not address the Layer-1 risk; the guardian mechanism must also cover the upgrade-authority path or a malicious upgrade can bypass it.
