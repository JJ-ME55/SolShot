# Finding: H044 — NOVEL — Single Hot Wallet for Layer 1 + Layer 2

## Status: CONFIRMED (operational, by design)
## Confidence Score: 10/10

> Confidence scale:
> - **9-10**: Certain — exhaustive code analysis, all paths verified
>
> *Live verification via `solana program show` on 2026-05-06 confirmed both layers resolve to the same key. JJ has acknowledged as intentional pre-mainnet posture.*

---

**One-line summary:** The single hot wallet `HPyVPj2VH9yBirr7FMgAJeDH8xJgaMKy5UnwLkjSnovk` holds both Solana-level upgrade authority (Layer 1) and application-level `config.authority` (Layer 2) for both v1 and v2 — a single private-key compromise enables total protocol drainage AND malicious bytecode deployment simultaneously.

---

## Executive Summary

Both SolShot Anchor programs (`4kzr...nH1` v1, `BVKX...G7N` v2) are deployed under BPF Loader Upgradeable with upgrade authority = `HPyVPj2VH9yBirr7FMgAJeDH8xJgaMKy5UnwLkjSnovk`. The same wallet is stored as `GlobalConfig.authority` in both programs. This is confirmed live via `solana program show` (2026-05-06) and corroborated by `Anchor.toml` (`wallet = "~/.config/solana/solshot-dev.json"`) and project memory.

The colocation of Layer 1 and Layer 2 authority in a single hot wallet is not a code-level vulnerability — no on-chain instruction is incorrectly permissioned. It is an operational risk: one compromised key immediately unlocks both the ability to drain all in-flight `MatchEscrow` PDAs via the application layer (H001 attack chain) AND the ability to silently deploy malicious replacement bytecode that bypasses all application-layer checks. These attack vectors are additive, not redundant. Industry precedent places this pattern in the $1M–$40M loss range.

JJ has documented this as an explicit pre-mainnet decision (see `OC-13` marker at `v1:1` and `Docs/PRIOR_AUDIT_DELTA.md`). The finding is recorded here for the audit report and as a mainnet gate item.

## Hypothesis Investigated

Single-key compromise = total protocol drainage AND ability to deploy malicious replacement bytecode. Pre-mainnet posture per JJ. Document for the report.

## Investigation Path

### Step 1: Confirm program IDs and upgrade authority
**Location:** `Anchor.toml:7-12`, `.audit/context/07-upgrade-admin.md:19-21`
**Finding:** Both programs are registered in Anchor.toml under devnet with their respective program IDs. The Phase 1 Upgrade/Admin agent verified live via `solana program show` on 2026-05-06 that upgrade authority = `HPyVPj2VH9yBirr7FMgAJeDH8xJgaMKy5UnwLkjSnovk` for both.

### Step 2: Confirm application authority matches
**Location:** `.audit/context/07-upgrade-admin.md:28`, `programs/solshot-escrow/src/lib.rs:787-798`, `programs/solshot-escrow-v2/src/lib.rs:810-818`
**Finding:** `GlobalConfig.authority` for both programs is set to the same hot wallet. This is the same key stored in `~/.config/solana/solshot-dev.json` (the `Anchor.toml` provider wallet). JJ confirmed this as the pre-mainnet posture.

### Step 3: Characterise Layer 1 powers
**Location:** Solana BPF Loader Upgradeable documentation; `.audit/context/07-upgrade-admin.md:22-24`
**Finding:** Upgrade authority can: (a) deploy arbitrary new bytecode replacing any instruction logic, (b) close the program and reclaim ~1.77 SOL rent, (c) transfer upgrade authority to another key. No timelock, no on-chain notice period, no governance. `OC-13` at `v1:1` marks this as a known pre-mainnet gap.

### Step 4: Characterise Layer 2 powers
**Location:** `programs/solshot-escrow/src/lib.rs:72-108` (v1 `update_config`), `programs/solshot-escrow-v2/src/lib.rs:96-142` (v2 `update_config`)
**Finding:** Application authority can: settle any match (pick any winner), cancel any `AwaitingDeposits` match, rotate treasury/ops fee destinations in a single TX (H001), pause both programs, v2 additionally rotate fee BPS. All one-step with no propose/accept.

### Step 5: Confirm no on-chain check separates the two layers
**Finding:** No instruction validates that `upgrade_authority != config.authority`. The separation is purely operational. A single leaked or compromised key unlocks both layers simultaneously. This is not a code gap — it is by design.

## Invariant Analysis

### Target Invariant
Only the legitimate operator can change program logic or drain in-flight match escrows.

### Enforcement Points
| Location | What It Enforces | Complete? |
|----------|-----------------|-----------|
| `has_one = authority` (v1 and v2, all privileged paths) | Correct application-layer key | Yes — for Layer 2 operations |
| BPF Loader Upgradeable runtime | Correct upgrade-authority key | Yes — for Layer 1 operations |
| (none) | Separation between the two layers | **No — by design** |

### Enforcement Gap Assessment
The invariant "only the legitimate operator can drain funds" is correctly enforced assuming the operator key is not compromised. The gap is not in the on-chain code; it is in the operational model: there is no key-separation, no multisig threshold, and no timelock that would slow down or detect a compromise before funds are lost.

## Exploitation Scenario

### Prerequisites
1. Attacker obtains the private key for `HPyVPj2VH9yBirr7FMgAJeDH8xJgaMKy5UnwLkjSnovk` (e.g. server breach, `.env` leak, CI/CD secret, social engineering)
2. In-flight `MatchEscrow` PDAs hold wager funds

### Attack Steps — Layer 2 (application) path
1. Call `update_config(new_treasury = attacker_wallet)` — rotates fee destination instantly
2. Call `settle_match(winner = attacker_wallet)` for each active match — drains all pots
3. Full treasury/ops cut redirected; winner amount also to attacker-controlled key

### Attack Steps — Layer 1 (bytecode) path
1. Deploy replacement `.so` that replaces `settle_match` with an unconditional drain-all instruction
2. Call the new instruction once — all `MatchEscrow` PDAs drained in a single TX
3. No `has_one` check applies because the check itself was replaced

### Why both paths matter
Layer 2 alone is recoverable in theory — pause + rebuild. Layer 1 replacement is silent; it can mimic normal program behaviour while exfiltrating funds across many matches with no on-chain evidence until forensic bytecode comparison.

### PoC Transaction Sequence

```
TX 1 (Layer-2 path): update_config
  Accounts: config (GlobalConfig PDA), authority (attacker holding HPyV...nokv)
  Args: new_treasury = attacker_wallet_A, new_ops = attacker_wallet_B
  Prerequisite: Attacker holds HPyV...nokv private key
  Result: All future settle_match calls pay 7% to attacker_wallet_A, 3% to attacker_wallet_B

TX 2..N (Layer-2 path): settle_match (repeated per active match)
  Accounts: escrow (any MatchEscrow PDA in Active state), winner (attacker_wallet_C),
            treasury (attacker_wallet_A), ops (attacker_wallet_B), config, authority
  Args: winner pubkey = attacker_wallet_C
  Prerequisite: TX 1 landed; escrow.state == Active
  Result: 90% of pot → attacker_wallet_C; 7% → attacker_wallet_A; 3% → attacker_wallet_B

Final State: All match pots drained; protocol operator has no recourse without a new deploy
             (which itself requires the same compromised upgrade key).
```

### Impact
- **All in-flight wager pots** across both programs drained
- **Upgrade authority** prevents any on-chain recovery without attacker cooperation
- **Layer 1 path** is forensically invisible until bytecode comparison
- **No timelock or on-chain alert** — loss is immediate and irreversible

## Recommended Fix

**Before mainnet launch**, the following two changes are required:

1. **Transfer program upgrade authority to a Squads multisig** (or freeze it with `solana program set-upgrade-authority --final`):
   ```bash
   # Transfer to Squads multisig (recommended for operational flexibility)
   solana program set-upgrade-authority <PROGRAM_ID> --new-upgrade-authority <SQUADS_MULTISIG_PUBKEY>

   # OR: permanently freeze (no further upgrades possible)
   solana program set-upgrade-authority <PROGRAM_ID> --final
   ```

2. **Rotate `GlobalConfig.authority` to a separate Squads multisig** (different from the upgrade authority multisig, or same with a different threshold):
   ```
   update_config(new_authority = <SQUADS_MULTISIG_PUBKEY>)
   ```
   This ensures Layer 1 and Layer 2 authorities are separate keys. A Layer 2 compromise no longer enables bytecode replacement; a Layer 1 compromise no longer enables winner-pick fraud without a full program upgrade cycle.

**Additional mitigations to consider:**
- Add a `pending_authority` propose/accept pattern to `update_config` (addresses H001, which this finding amplifies)
- Emit an on-chain event when upgrade authority is transferred
- Use a time-locked governance program for BPS mutations (v2)

## Blocking Factors
- **Pre-mainnet devnet only:** No significant user funds at risk currently
- **Hot wallet physically secured:** Risk is operational; no code flaw enables anonymous exploit
- **`OC-13` documented:** JJ has formally acknowledged the gap

## Enabling Factors
- **Same key, both layers:** No architectural separation between upgrade and application authority
- **No timelock:** Layer 2 drainage executes in a single TX with no on-chain delay
- **H001 also open:** Authority rotation is one-step; combined with Layer 1 = no recovery path
- **Server hot wallet:** Key lives on internet-connected server, expanding attack surface
