# H045 — Snapshot Drift Across update_config Calls

## Finding

Per-match fee splits (treasury/ops pubkeys and BPS rates) are **snapshot-atomically** at `create_match` into the `MatchEscrow` account, decoupling in-flight matches from subsequent `update_config` calls. However, **no on-chain audit trail links snapshot values to specific config state versions**. Different matches may be created with different live config snapshots; off-chain monitoring cannot easily verify "this match was created with valid vs. poisoned config."

## Verification

**create_match emits MatchCreated event at v2:225–234 with all snapshot values:**
- `treasury` (Pubkey)
- `ops` (Pubkey)
- `fee_bps_treasury` (u16)
- `fee_bps_ops` (u16)

✓ Event is emitted atomically with PDA init (same instruction, no observable window for partial state).
✓ Snapshots are immutable per-match (read from config BEFORE mutable borrow at create_match).
✓ settle_match validates treasury/ops pubkeys against snapshots via account constraints (v2:717, 726).

## Audit Trail Gap

The `ConfigUpdated` event (emitted by `update_config` at v2:133–139) records new config state but does **not** include a version number or timestamp correlation to link with future MatchCreated events. Monitoring tools must correlate events manually:
1. See MatchCreated event at block N with treasury T, ops O, BPS = B.
2. See ConfigUpdated event at block N+k with treasury T', ops O'.
3. Cannot directly verify whether T/O/B were "live" config values at block N (requires off-chain state tree reconstruction).

## Impact

- **Severity**: LOW (operational/metadata concern, not correctness).
- **In-flight matches are protected** (snapshot mechanism is atomic and immutable).
- **Concern**: Off-chain auditing workflows (compliance, treasury tracking) require additional tooling or timestamp-based heuristics to confidently map a match to a specific config version.

## Recommendation

**Emit a config version/sequence number** in both `ConfigUpdated` and `MatchCreated` events:
```rust
pub struct ConfigUpdated {
    pub version: u32,  // incremented each call
    ...
}

pub struct MatchCreated {
    pub config_version: u32,  // snapshot source identifier
    ...
}
```

This allows auditors to deterministically link "match M was created with config version V" and correlate to the exact `ConfigUpdated(V)` event at match-creation time.
