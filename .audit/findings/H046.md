# Finding: H046 — NOVEL — Layer-1 Bytecode Replacement Risk

**One-line summary:** The hot wallet that holds Solana-level upgrade authority for both programs can deploy arbitrary replacement bytecode — with no timelock, no multisig, and no on-chain governance — and drain every live `MatchEscrow` PDA in a single transaction.

## Status: CONFIRMED (operational)
## Confidence Score: 10/10

> Confidence scale:
> - **9-10**: Certain — exhaustive code analysis, all paths verified
>
> *Both programs are live on devnet under `BPFLoaderUpgradeab1e11111111111111111111111` with a single hot-wallet upgrade authority. Verified live via `solana program show` (2026-05-06). No timelock or governance program wraps the upgrade key.*

---

## Executive Summary

Both `solshot-escrow` (v1, `4kzrDpV9JxjE27AMg4PQXzGuge9MEYQEFznSPvkBtnH1`) and `solshot-escrow-v2` (`BVKXLUnukU9cyTAWojsQPfLWHq4CyJY7CLG59bBVSG7N`) are deployed under Solana's `BPFLoaderUpgradeab1e11111111111111111111111`. The upgrade authority for both is `HPyVPj2VH9yBirr7FMgAJeDH8xJgaMKy5UnwLkjSnovk` — the same hot wallet used as the application-level `config.authority` (H044 / H001). There is no timelock, no multisig guard, no notice period, and no on-chain governance program wrapping the upgrade key.

An attacker who compromises this one key can in a single atomic transaction deploy replacement bytecode that calls `try_borrow_mut_lamports` on every live `MatchEscrow` PDA and transfers all accumulated lamports to an attacker-controlled wallet. Every in-flight wager on both programs is drained simultaneously. The only defense is operational: the private key must never be leaked. For a public mainnet launch, a stolen key is game-over with no on-chain escape hatch.

---

## Hypothesis Investigated

Upgrade authority can deploy malicious replacement bytecode that drains all MatchEscrow PDAs in one TX. EP-083 pattern. No timelock, no notice period, no on-chain governance. Compounds with H044 (same key as application authority).

### Step 3: Document blast radius of a malicious upgrade

A replacement program deployed to `4kzr...nH1` or `BVKX...G7N` retains the same program ID and is trusted by all existing `MatchEscrow` PDAs (which are owned by those program IDs). The replacement can:

1. Iterate every `MatchEscrow` PDA derived from `["match", match_id]` using `remaining_accounts`.
2. Call `try_borrow_mut_lamports()` on each PDA and zero their balances, crediting the attacker wallet.
3. Optionally close the `GlobalConfig` PDA to recover ~890 bytes of rent.
4. Execute in a single transaction limited only by Solana's CU cap (~1.4M per TX). Multiple TXs are possible in the same block for larger scale.

The v2 per-match snapshot mechanism (`ARCHITECTURE.md` Mechanism 1) provides NO protection here — it defends against Layer-2 config rotation, not Layer-1 bytecode replacement. Any logic in the current programs can be completely overwritten.

**v1 hardcoded BPS constants** (`lib.rs:15-16`, `const TREASURY_BPS: u64 = 700; const OPS_BPS: u64 = 300`) are irrelevant in a replacement scenario — the replacement binary is not constrained by the original source.

## Invariant Analysis

### Target Invariant
"Only authorized `settle_match` / `cancel_match` / `permissionless_reclaim` calls following the current program logic can remove lamports from a `MatchEscrow` PDA."

### Enforcement Points

| Location | What It Enforces | Complete? |
|----------|-----------------|-----------|
| `programs/solshot-escrow/src/lib.rs` — all instructions | Anchor constraints, `has_one`, state checks | Against the deployed bytecode only |
| BPFLoaderUpgradeable runtime | Upgrade requires authority signature | Yes — but authority is a single hot wallet |
| No timelock / governance wrapping upgrade key | — | NOT PRESENT — enforcement gap |

### Enforcement Gap Assessment

The invariant is enforced by the **current bytecode**. The BPF Loader enforces that upgrades require the upgrade authority signature — but it provides no constraint on what the replacement bytecode may do. Once new bytecode is deployed, all previous instruction-level invariants are void. The single hot-wallet upgrade authority creates a direct path from "key compromised" to "all PDA funds drained."

## Exploitation Scenario

### Prerequisites
1. Attacker compromises private key for `HPyVPj2VH9yBirr7FMgAJeDH8xJgaMKy5UnwLkjSnovk`.
2. Attacker has enough SOL to fund a buffer account (~2× program size in rent).

### PoC Transaction Sequence

```
TX 1: BpfLoaderUpgradeable::Write (buffer account)
  Accounts: buffer_account (attacker-funded), upgrade_authority = HPyV...nokv
  Args: malicious_bytecode (drain program targeting MatchEscrow PDAs)
  Prerequisite: attacker holds upgrade authority private key
  Result: buffer account loaded with drain bytecode

TX 2: BpfLoaderUpgradeable::Upgrade
  Accounts: program = 4kzr...nH1 (v1), program_data, buffer, upgrade_authority = HPyV...nokv
  Args: (none)
  Prerequisite: TX 1 complete
  Result: v1 program now executes drain bytecode; all existing MatchEscrow PDAs (owner = 4kzr...nH1) are now drainable

TX 3: drain_all (new instruction in replacement bytecode)
  Accounts: all live MatchEscrow PDAs via remaining_accounts, attacker_wallet
  Args: (none)
  Prerequisite: TX 2 complete; at least one MatchEscrow PDA exists with lamports > 0
  Result: every MatchEscrow PDA zeroed; attacker_wallet credited all wager pots

TX 4 (optional): BpfLoaderUpgradeable::Upgrade on v2 (BVKX...G7N)
  Same pattern, drains all v2 MatchEscrow PDAs

Final State: attacker holds all in-flight wager lamports from both programs; players have no recourse; no on-chain transaction to challenge.
```

### Impact

- **All in-flight wagers** on both programs lost simultaneously.
- At MAX_WAGER (100 SOL) × MAX_PLAYERS (10) = 1000 SOL per match × N concurrent matches.
- Devnet: first wagered match settled 2026-05-04 at 0.2 SOL wager. Mainnet at any meaningful TVL = potentially millions USD.
- No on-chain recovery path; `permissionless_reclaim` is also under the new bytecode.

## Recommended Fix

**Primary:** Transfer upgrade authority for both programs to a Squads multisig wallet before any mainnet deployment. Require M-of-N signatures (e.g., 3-of-5) for any program upgrade. This decouples the hot-wallet application authority from the Solana-level bytecode authority.

```bash
# Transfer upgrade authority to Squads multisig (SQUAD_MULTISIG_ADDRESS)
solana program set-upgrade-authority 4kzrDpV9JxjE27AMg4PQXzGuge9MEYQEFznSPvkBtnH1 \
  --new-upgrade-authority <SQUADS_MULTISIG_ADDRESS>

solana program set-upgrade-authority BVKXLUnukU9cyTAWojsQPfLWHq4CyJY7CLG59bBVSG7N \
  --new-upgrade-authority <SQUADS_MULTISIG_ADDRESS>
```

**Secondary (post-mainnet stabilization):** Freeze the upgrade authority entirely once the programs are battle-tested and no further upgrades are anticipated.

```bash
# Freeze — irreversible; only after extensive audit and mainnet stability
solana program set-upgrade-authority 4kzrDpV9JxjE27AMg4PQXzGuge9MEYQEFznSPvkBtnH1 \
  --final
```

**Interim (immediate):** Separate the upgrade authority key from the application hot wallet. Even if the application key (`config.authority`) is compromised (H001/H044), an attacker should not automatically hold Layer-1 upgrade power. Use a hardware-wallet-backed key (Ledger) for upgrade authority.
