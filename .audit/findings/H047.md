## Summary

**`remaining_accounts` writability is NOT enforced in-program; the Solana runtime enforces it implicitly.**

The refund loops in `cancel_match` and `permissionless_reclaim` accept caller-supplied `remaining_accounts` and perform direct lamport crediting via `**account.lamports += wager_lamports`. The program does not check `account.is_writable` before mutation. However, the Solana runtime would reject the instruction if any of these accounts were not marked writable in the transaction.

## Status

**NOT_VULNERABLE.** Runtime-enforced. Defense-in-depth improvement recommended.

## Analysis

### Vulnerability Surface

- **Lines affected:** v1:317-324, v1:408-409, v1:476-477; v2:434-441, v2:508-509, v2:567-568
- **Operation:** Direct lamport credit: `**account.lamports += amount`
- **Account source:** Caller-provided `remaining_accounts` (cancel_match, permissionless_reclaim)
- **Validation gap:** No `require!(account.is_writable, ...);` before mutation

### Why Not Vulnerable

The Solana runtime performs writability enforcement at the account-slot level during instruction execution:
1. Client (off-chain) marks accounts as writable/read-only in the transaction AccountMeta
2. Runtime validates account metadata before CPI or direct mutation
3. Any attempt to write to a read-only account fails **immediately** with a runtime error
4. The instruction rolls back atomically; lamports are **not** transferred

Server-side (`server/services/escrow.js:459`) confirms: `isWritable: true` is set on all refund destinations.

### Mitigation Gap

While runtime-protected, explicit in-program validation (`require!(account.is_writable, ...);`) provides:
- **Defense-in-depth:** Fail-fast at the program boundary rather than relying on runtime
- **Auditability:** Code intent is explicit; future reviewers see the check in the source
- **Clarity:** Defensive programming removes assumption that the runtime will catch all cases

## Recommendation

Add a writability check immediately before lamport mutation:

```rust
for (i, account) in ctx.remaining_accounts.iter().enumerate() {
    require!(i < max_players, EscrowError::InvalidPlayer);
    require!((deposits_mask >> i) & 1 == 1, EscrowError::InvalidPlayer);
    require!(*account.key == players[i], EscrowError::InvalidPlayer);
    
    // Explicit writability check (defense-in-depth)
    require!(account.is_writable, EscrowError::InvalidAccount);
    
    **escrow.lamports -= wager_lamports;
    **account.lamports += wager_lamports;
}
```

This is a **one-line addition** (already done in equivalent form for settle_match fee destinations in some versions). Apply to both programs (v1 + v2) and all four iteration sites.

---

**Conclusion:** Runtime-enforced writability provides security. Explicit check improves code clarity and follows defense-in-depth principles.
