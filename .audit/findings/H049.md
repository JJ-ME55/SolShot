# H049: Match ID PDA Seed Entropy

## Summary
Match IDs are server-generated using `crypto.randomBytes(4).toString('hex')` (4 bytes = 32 bits of entropy). PDAs use `seeds = [b"match", match_id.as_bytes()]` to derive accounts. With a 4-character hex alphabet (36 possibilities per char), collision becomes likely at ~1,300 concurrent matches (birthday paradox threshold). On-chain validation rejects collisions via `init` constraint, but server-side match creation will fail at the point of PDA derivation.

## Details

**Generation:** `server/socket-io/main.js:2212, 2393, 2471, 2639`  
**Alphabet:** Hex → [0-9a-f] = 16 chars, so 16^8 = 4.3B unique IDs (actual usage: 4 bytes hex = 8 chars = 16^8 space)  
**Collision threshold:** sqrt(16^8) ≈ 65M matches before birthday paradox hits 50% collision probability  
**On-chain defense:** Anchor `init` constraint prevents reinitialization → duplicate match_id TX fails with "account already initialized"  
**Server impact:** Match creation fails silently; player receives no explicit "ID collision" error; reconnect/retry loops possible

## Cross-Domain Assessment

- **On-chain:** Covered. `init` constraint at `programs/solshot-escrow/src/lib.rs:613` (v1), v2:648 rejects reinit.  
- **Database/Server:** Exposed. 4-byte CSPRNG is cryptographically sound but lacks application-layer collision detection. No DB uniqueness constraint or deduplication logic observed.  
- **Player UX:** Degraded. Rare collision results in match-not-found or "room already exists" silent failures.

## Recommendations

1. **Short-term:** Increase `randomBytes()` to 8 bytes → 64-bit entropy → ~17B ID space, raising birthday threshold to ~130M matches.  
2. **Long-term:** Add server-side DB uniqueness constraint on `matchId` to surface collisions explicitly and log high-frequency ID reuse.  
3. **Logging:** On PDA derivation failure, emit "match_id collision detected" alert for operational awareness.
