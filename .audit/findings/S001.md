## Executive Summary

A single server authority key compromise enables a three-step chain attack that extracts 100% of all active match deposits plus permanent protocol governance. The chain is: (1) redirect treasury and ops fee destinations to attacker-controlled wallets via `update_config` (no timelock, no re-validation, instant effect); (2) settle all active matches with a colluding registered player as winner, routing 90% of each pot to the attacker; (3) lock out the original team by rotating `config.authority` to an attacker-controlled key. Combined, the attacker extracts up to 100% of all deposited funds, redirects all future fee revenue indefinitely, and permanently forecloses governance recovery without a program upgrade.

The chain is CONFIRMED because each individual step is independently CONFIRMED (H001: authority takeover, H002: fee redirect), and the combination step — winner selection fraud — is CONFIRMED as POTENTIAL at the individual level (H005) but becomes CONFIRMED within this chain because the preconditions for H005 (authority control + registered player control) are trivially satisfied by the setup steps of S001. The winner constraint (`winner.key() == escrow.player_one || escrow.player_two`) provides only the minor partial mitigation identified in H001 and H005: it requires the attacker to control one of the two registered player wallets. Since the authority creates matches and sets both player pubkeys as unvalidated parameters, this constraint is trivially satisfied by the attacker pre-registering an owned wallet as `player_one`.

The score is 9/10 rather than 10/10 because the 100% extraction path requires the attacker to have pre-registered as a player in active matches OR to wait for new matches where they register themselves — slightly constraining instantaneous full extraction of matches already in-progress at compromise time where no attacker wallet is a registered player.

## Investigation Path

### Step 1: Verify TX0 — Can attacker redirect treasury/ops instantly?

**Location:** `lib.rs:70-89` (update_config handler), `lib.rs:464-475` (UpdateConfig account struct)

**Finding:** Fully confirmed by H002. The `update_config` handler applies treasury and ops changes with zero validation — no timelock, no re-validation of distinctness, no event emission. The sole gate is `has_one = authority` on the config account, which the attacker passes because they hold the authority key. The change takes effect immediately.

**Evidence:**
```rust
// lib.rs:70-89
pub fn update_config(
    ctx: Context<UpdateConfig>,
    new_authority: Option<Pubkey>,
    new_treasury: Option<Pubkey>,
    new_ops: Option<Pubkey>,
) -> Result<()> {
    let config = &mut ctx.accounts.config;
    if let Some(a) = new_authority {
        config.authority = a;      // lib.rs:79 — one-step, immediate, irreversible
    }
    if let Some(t) = new_treasury {
        config.treasury = t;       // lib.rs:82 — zero validation on new value
    }
    if let Some(o) = new_ops {
        config.ops = o;            // lib.rs:85 — zero validation on new value
    }
    Ok(())
}
```

**Chain link status:** PASSES. Attacker can redirect 10% fees in a single transaction. No obstacle.

### Step 2: Verify TX1-N — Can attacker settle matches with a controlled player as winner?

**Location:** `lib.rs:228-305` (settle_match handler), `lib.rs:560-610` (SettleMatch account struct)

**Finding:** The settle_match instruction contains two constraints that interact with this chain:

**Constraint A — Winner must be a registered player (lib.rs:575-580):**
```rust
/// Winner: must be one of the registered players (OC-02 — resolves H008, H002, S001)
/// CHECK: Constrained to escrow.player_one or escrow.player_two
#[account(
    mut,
    constraint = winner.key() == escrow.player_one
        || winner.key() == escrow.player_two
        @ EscrowError::InvalidWinner
)]
pub winner: UncheckedAccount<'info>,
```

Note the developer comment explicitly references S001 as a concern this constraint addresses. The constraint blocks routing the winner payout to an arbitrary third-party address.

**Constraint B — Both escrow.authority and config.authority must match the signer (lib.rs:565, 604):**
```rust
// lib.rs:565
has_one = authority,  // signer must equal escrow.authority (stored at create_match)

// lib.rs:604
has_one = authority @ EscrowError::Unauthorized,  // signer must equal config.authority
```

**Chain link assessment:** The winner constraint provides a PARTIAL blocker, not a complete one. The attacker cannot route the 90% winner payout to a fresh third-party address. However, the attacker CAN route it to a registered player wallet they control, because:

1. `create_match` lacks `has_one = authority` on config (confirmed in context/01-access-control.md, ARCHITECTURE.md). Any signer can call it — including the attacker.
2. `create_match` accepts `player_one` and `player_two` as arbitrary `Pubkey` parameters with no validation beyond `player_one != player_two` and `authority != player_one/two`.
3. Therefore, the attacker creates matches where `player_one = attacker_controlled_wallet`.
4. When the attacker then calls `settle_match(winner=player_one)`, the winner constraint passes because `attacker_controlled_wallet == escrow.player_one`.

**For pre-existing matches at time of compromise:** If any active match has a registered player the attacker controls (trivially possible if attacker was already playing), they can extract those. For matches with no attacker-controlled player, they must wait for new matches or accept that those 90% shares go to the winning player. However, the 10% fee redirect (TX0) and governance lockout (TX_final) still apply to pre-existing matches.

**Chain link status:** PASSES with one qualifier: 90% extraction from each match requires the attacker to control a registered player wallet in that match. For new matches created after the compromise, this is trivially satisfied. For pre-existing matches, depends on whether attacker wallet is registered.

### Step 5: Verify the chain is executable end-to-end in one transaction bundle

**Finding:** All four steps can be bundled into a single Solana transaction with multiple instructions, or spread across two transactions. Solana's transaction model allows multiple instructions that all execute atomically if bundled together. The optimal attack order:

1. Instruction 1: `update_config(None, Some(attacker_wallet_A), Some(attacker_wallet_B))` — redirect fees
2. Instructions 2-N: `settle_match(winner=attacker_player_one)` for each active match the attacker controls a player in
3. Instruction N+1: `update_config(Some(attacker_key2), None, None)` — lock out governance

If all instructions fit in a single transaction, the entire chain is atomic. If not, individual transactions from the same compromised key achieve the same result with negligible additional risk window.

**Chain link status:** PASSES. The attack is executable in a single transaction bundle.

The constraints address the most naive version of the attack (direct third-party extraction) but do not prevent the complete chain attack described in this finding.

## Invariant Analysis

### Target Invariant

For this chain attack: "A single key compromise cannot simultaneously enable (a) arbitrary winner selection, (b) fee destination redirection, and (c) permanent governance transfer in a single transaction."

This is actually THREE related invariants that all fail together:

- I-A: "Winner payouts flow only to the legitimate match winner." — Violated because authority controls winner selection with no on-chain game verification.
- I-B: "Fee revenue flows to the protocol-controlled treasury and ops addresses." — Violated because update_config has no timelock.
- I-C: "Authority can only be transferred via a process that requires the new authority's acceptance." — Violated because there is no two-step pattern.

### Enforcement Points

| Location | What It Enforces | Complete? |
|----------|-----------------|-----------|
| `lib.rs:470` `has_one = authority` on UpdateConfig | Only current authority can update config | Yes — but falls entirely upon key compromise |
| `lib.rs:575-580` winner constraint | Winner must be player_one or player_two | YES — but only blocks THIRD-PARTY injection, not colluding player |
| `lib.rs:587` treasury constraint | Treasury must match config.treasury | YES — but trusts config values (which attacker already changed in TX0) |
| `lib.rs:596` ops constraint | Ops must match config.ops | YES — same as above |
| `lib.rs:604` `has_one = authority` on SettleMatch config | Only config.authority can settle | YES — falls upon key compromise |
| Timelock on update_config | Config changes cannot take immediate effect | NOT PRESENT |
| Two-step authority transfer | New authority must accept to confirm key control | NOT PRESENT |
| Distinctness re-validation in update_config | Config addresses remain coherent after updates | NOT PRESENT |
| On-chain event for config changes | Change is logged for monitoring | NOT PRESENT |

### Enforcement Gap Assessment

All three invariants have complete enforcement gaps at the code level: they are 100% predicated on the authority key remaining under legitimate control. There is no second factor, no timelock, no multisig, and no on-chain mechanism that slows or prevents the chain once the key is compromised. The developer's OC-02 and OC-03 annotations on the constraints indicate awareness of the concern, but the implemented mitigations address only the simplest form of the attack.

## Blocking Factors

The following factors limit but do not prevent the attack:

- **Winner must be a registered player (`lib.rs:575-580`):** The attacker cannot route the 90% winner share to a fresh arbitrary address. They must control one of the two registered player wallets for each match. This is easily satisfied: the attacker can create new matches with an owned wallet as player_one. For pre-existing matches where the attacker has no registered player, the 90% goes to a legitimate player, not the attacker — though fees are still captured.

- **Authority cannot be a player in the same match (`lib.rs:127-129`):** OC-06 prevents the server authority wallet itself from being registered as a player. The attacker must use a SECOND wallet to receive the 90% winner payout. This is a minor inconvenience — any attacker with the authority key likely controls multiple wallets.

- **Treasury and ops must be distinct (`lib.rs:588`):** The fee redirect requires two distinct attacker addresses, not one. Minor inconvenience only.

- **1-hour settlement deadline (`lib.rs:236-244`):** For existing Active matches at time of compromise, the attacker must settle within 1 hour of match activation. This does not prevent the attack — it creates a time constraint on the existing-match portion of TX1-N. New matches created by the attacker have their own 1-hour windows.

## Enabling Factors

- **Single hot wallet authority with no multisig:** The server keypair is a single private key documented as a hot wallet (ARCHITECTURE.md, context/01-access-control.md). No second factor.
- **One-step authority transfer (`lib.rs:79`):** A single `update_config` transaction permanently rotates governance.
- **No timelock on treasury/ops changes (`lib.rs:70-88`):** Fee redirect takes effect immediately.
- **`create_match` not gated by config authority (`lib.rs:510-532`):** Any signer can create matches and register arbitrary player pubkeys.
- **No on-chain game outcome verification (`lib.rs:228-305`):** Authority's winner choice is unconstrained between the two registered players.
- **No event for config changes:** The fee redirect is silent until the next MatchSettled event reveals the new treasury/ops addresses post-facto.
- **Settlement reads config at execution time:** No snapshot of fee destinations at match creation — TX0's redirect immediately affects all subsequent TX1-N.

## Exploitation Scenario

### Prerequisites

1. Attacker controls the server authority keypair (via phishing, malware, leaked `.env`, or insider threat)
2. At least one active match exists OR the attacker can create new matches (the latter is always true since `create_match` is ungated)
3. Attacker controls two wallet addresses for fee destinations (to satisfy treasury != ops constraint)
4. Attacker controls a third wallet (to register as player_one in new matches)

### Attack Steps

1. Attacker prepares: `attacker_player` (to register as player_one), `attacker_treasury` (fee destination A), `attacker_ops` (fee destination B), `attacker_key2` (new governance key).

2. Execute TX0: `update_config(None, Some(attacker_treasury), Some(attacker_ops))` — All future settlements redirect 10% fees to attacker. Silent, no event.

3. Execute TX1 (for each active match where attacker controls player_one): `settle_match(winner=attacker_player)` — 90% payout to attacker_player, 10% to attacker_treasury/attacker_ops. Total: 100% of pot to attacker.

4. Execute new-match cycle for future victims:
   - `create_match(match_id, wager, player_one=attacker_player, player_two=victim_wallet)`
   - victim deposits their wager
   - `settle_match(winner=attacker_player)` — attacker receives 90%+10% = 100%
   - Repeat indefinitely.

5. Execute TX_final: `update_config(Some(attacker_key2), None, None)` — Original team permanently locked out. No recovery path without program upgrade.

6. Optional: `pause_program` (with attacker_key2) — blocks all player cancellations, forcing 48h wait for permissionless reclaim.

### Impact

- **Direct fund theft:** 90% of each match pot where attacker controls a registered player wallet. At max wager (100 SOL each, 200 SOL pot), attacker gains 180 SOL per match.
- **Fee revenue theft:** 10% of every settled pot directed to attacker_treasury/attacker_ops. This is ongoing and silent until monitoring detects MatchSettled events with unexpected addresses.
- **Complete extraction when attacker is player:** If attacker controls player_one and has set treasury/ops to self, 100% of the pot (180 + 14 + 6 = 200 SOL) flows to attacker accounts. Net profit per match: victim's 100 SOL wager (attacker's own 100 SOL is returned to themselves as player_one winner).
- **Permanent governance loss:** Authority rotation with no recovery path.
- **At scale (10 concurrent matches, 10 SOL wager each):** 900 SOL stolen from existing matches in TX1 bundle, plus indefinite future extraction from new matches and fees.

### Recommended Fix

The root cause is a single hot wallet with unrestricted, instant power over winner selection, fee destinations, and governance transfer. The complete fix has three mandatory layers:

**Layer 1 — Two-step authority transfer (CRITICAL, addresses H001 and the TX_final step):**

```rust
// Add to GlobalConfig:
pub struct GlobalConfig {
    pub authority: Pubkey,
    pub pending_authority: Option<Pubkey>,  // NEW
    pub treasury: Pubkey,
    pub ops: Pubkey,
    pub is_paused: bool,
    pub bump: u8,
}

// propose_authority: current authority nominates new authority
pub fn propose_authority(ctx: Context<UpdateConfig>, proposed: Pubkey) -> Result<()> {
    require!(proposed != Pubkey::default(), EscrowError::InvalidConfig);
    ctx.accounts.config.pending_authority = Some(proposed);
    emit!(AuthorityProposed { proposed });
    Ok(())
}

// accept_authority: new authority must sign to accept
pub fn accept_authority(ctx: Context<AcceptAuthority>) -> Result<()> {
    let config = &mut ctx.accounts.config;
    // AcceptAuthority requires: pending_authority == Some(signer.key())
    config.authority = ctx.accounts.new_authority.key();
    config.pending_authority = None;
    emit!(AuthorityTransferred { new: ctx.accounts.new_authority.key() });
    Ok(())
}
```

**Layer 2 — Timelock on treasury/ops changes (CRITICAL, addresses H002 and the TX0 step):**

```rust

pub pending_ops: Option<Pubkey>,
pub pending_config_effective_at: i64,
```

### False Positive Check

Per the common-false-positives guide:
- This is NOT FP-003 (the `has_one = authority` signer check is correctly implemented — it just falls when the key is compromised).
- This is NOT FP-018 (the constraints are not redundant; the issue is their insufficiency, not their presence).
- This is NOT FP-013 (the global PDA is correct for a singleton config).
- The vulnerability is ARCHITECTURAL (no propose/accept, no timelock) not a code defect in the constraint logic itself.

### Confidence Justification (9/10)

Score 9 rather than 10 because:
- The 100% per-match extraction path requires the attacker to control a registered player wallet. For pre-existing Active matches at the moment of compromise where no attacker wallet is registered, the 90% winner payout goes to a legitimate player (though 10% fees are still captured).

- A score of 10 would require ZERO conditions under which extraction is partial; the 90%-path partial limitation warrants a 9.
