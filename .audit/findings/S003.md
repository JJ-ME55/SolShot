## Executive Summary

S003 hypothesizes a distinct attack variant from H011: it asks whether `treasury == authority` works at the `SettleMatch` constraint level specifically because H003 revealed that `treasury == ops` causes a constraint contradiction (settlement DoS), while `treasury == authority` might not have the same blocker. The investigation confirms this reasoning is correct in its initial framing — there is no `treasury.key() != authority.key()` constraint in the `SettleMatch` struct — but S003's conclusion is NOT VULNERABLE for a specific reason: this vulnerability has already been confirmed and fully documented in **H011** ("Config Treasury Self-Redirect"), which is a prior finding from this same audit.

S003 is the third investigation covering the same `update_config` + `SettleMatch` constraint gap family. H003 covers `treasury == ops` (DoS variant). H011 covers `treasury == authority` (fee capture variant). S003 was generated from H003's incidental discovery section and asks the same question H011 investigates. The underlying vulnerability is CONFIRMED (see H011, confidence 9/10), but S003 as a new finding is a duplicate, not a new vulnerability. This file documents the deduplication analysis, verifies the S003 hypothesis independently, and cross-references the existing confirmed findings.

## Hypothesis Investigated

**S003: Authority == Treasury Economic Consolidation**

Authority sets `treasury == authority_wallet` via `update_config`. Unlike treasury == ops (which breaks settlement per H003), treasury == authority may succeed because the `SettleMatch` struct has separate constraints for treasury and authority accounts. This silently redirects 7% of all pots to the authority, creating hidden fee capture.

**Attack Vector:**
1. `update_config(new_treasury=authority_wallet)` — passes because update_config has no distinctness checks
2. `settle_match` passes treasury=authority_wallet — constraint `treasury.key() == config.treasury` passes
3. Authority receives 7% fee on top of normal operational role

**Target Code:** `lib.rs:70-89`, `lib.rs:583-598` (SettleMatch constraints)
**Requires:** [token-economic-findings, access-control-findings]

## Investigation Path

### Step 1: Does update_config prevent treasury == authority?

**Location:** `lib.rs:70-89` (handler), `lib.rs:464-475` (account struct)

**Finding:** No. The `update_config` handler applies three optional field writes with zero validation on new values beyond the `has_one = authority` signer gate.

**Evidence:**
```rust
// lib.rs:70-89
pub fn update_config(
    ctx: Context<UpdateConfig>,
    new_authority: Option<Pubkey>,
    new_treasury: Option<Pubkey>,
    new_ops: Option<Pubkey>,
) -> Result<()> {
    let config = &mut ctx.accounts.config;

    if let Some(a) = new_authority {
        config.authority = a;
    }
    if let Some(t) = new_treasury {
        config.treasury = t;   // No require!(t != config.authority)
    }
    if let Some(o) = new_ops {
        config.ops = o;
    }

    Ok(())
}
```

The `UpdateConfig` account struct:
```rust
// lib.rs:464-475
#[derive(Accounts)]
pub struct UpdateConfig<'info> {
    #[account(
        mut,
        seeds = [GlobalConfig::SEED],
        bump = config.bump,
        has_one = authority @ EscrowError::Unauthorized,
    )]
    pub config: Account<'info, GlobalConfig>,

    pub authority: Signer<'info>,
}
```

There is no `require!(new_treasury != config.authority)` or any equivalent. The authority can set `config.treasury = authority.key()` by passing `new_treasury = Some(authority_pubkey)`.

### Step 2: What constraints exist in SettleMatch for treasury vs. authority?

**Location:** `lib.rs:560-610`

**Finding:** The `SettleMatch` struct contains the following constraints relevant to treasury and authority:

1. `has_one = authority` on escrow (line 565): `escrow.authority == signer`
2. `has_one = authority` on config (line 604): `config.authority == signer`
3. `treasury.key() == config.treasury` (line 587): treasury account must match stored config address
4. `treasury.key() != ops.key()` (line 588): treasury and ops must be distinct
5. `ops.key() == config.ops` (line 596): ops account must match stored config address

**Critically absent:** There is no `constraint = treasury.key() != authority.key()` anywhere in the struct.

**Evidence:**
```rust
// lib.rs:560-610 — SettleMatch account struct
#[derive(Accounts)]
pub struct SettleMatch<'info> {
    #[account(
        mut,
        seeds = [b"match", escrow.match_id.as_bytes()],
        bump = escrow.bump,
        has_one = authority,
        close = authority,         // rent goes to authority on close
    )]
    pub escrow: Account<'info, MatchEscrow>,

    #[account(mut)]
    pub authority: Signer<'info>,

    /// CHECK: Constrained to escrow.player_one or escrow.player_two
    #[account(
        mut,
        constraint = winner.key() == escrow.player_one
            || winner.key() == escrow.player_two
            @ EscrowError::InvalidWinner
    )]
    pub winner: UncheckedAccount<'info>,

    /// CHECK: Constrained to config.treasury; uniqueness check vs ops
    #[account(
        mut,
        constraint = treasury.key() == config.treasury @ EscrowError::InvalidTreasury,
        constraint = treasury.key() != ops.key() @ EscrowError::DuplicateFeeAccount,
        // NOTE: NO constraint = treasury.key() != authority.key()
    )]
    pub treasury: UncheckedAccount<'info>,

    /// CHECK: Constrained to config.ops
    #[account(
        mut,
        constraint = ops.key() == config.ops @ EscrowError::InvalidOps,
        // NOTE: NO constraint = ops.key() != authority.key()
    )]
    pub ops: UncheckedAccount<'info>,

    #[account(
        seeds = [GlobalConfig::SEED],
        bump = config.bump,
        has_one = authority @ EscrowError::Unauthorized,
        constraint = !config.is_paused @ EscrowError::ProgramPaused,
    )]
    pub config: Account<'info, GlobalConfig>,

    pub system_program: Program<'info, System>,
}
```

### Step 3: Would settle_match succeed if treasury == authority?

**Location:** `lib.rs:284-291` (lamport transfers)

**Finding:** Yes. When `config.treasury == authority.key()`, the caller passes their own pubkey for both `authority` (Signer) and `treasury` (UncheckedAccount). The constraints resolve as follows:

- `treasury.key() == config.treasury`: authority.key() == authority.key() → PASS
- `treasury.key() != ops.key()`: authority.key() != ops.key() (ops is a different address) → PASS
- `has_one = authority` on config: config.authority == signer → PASS
- `has_one = authority` on escrow: escrow.authority == signer → PASS

All constraints pass. The instruction executes. At `lib.rs:287-288`, the `treasury_amount` (7% of pot) is credited to the treasury account, which IS the authority's account. The `close = authority` at line 566 additionally sweeps PDA rent to the authority. Net result: authority receives 7% of pot + PDA rent on every settlement.

### Step 5: Confirm the H003/S003 distinction is correctly framed

**Location:** `lib.rs:585-598` (SettleMatch constraints)

**Finding:** The strategy brief correctly identifies the asymmetry between `treasury == ops` and `treasury == authority` at the constraint level:

- `treasury == ops`: CAUSES SETTLEMENT DOS. The constraint `treasury.key() != ops.key()` (line 588) creates a logical contradiction when `config.treasury == config.ops`. Settlement becomes impossible because no valid account combination can satisfy both `treasury == config.treasury`, `ops == config.ops`, AND `treasury != ops` simultaneously. (Documented in H003.)

- `treasury == authority`: ENABLES SILENT FEE CAPTURE. No constraint prevents `treasury.key() == authority.key()`. Settlement succeeds, and the authority receives the treasury fee in addition to their normal role. (Documented in H011.)

The strategy brief's insight that these are distinct outcomes at the constraint level is correct. The distinction is real and material. S003's hypothesis is valid and confirmed — it is simply that the confirmation already exists in H011.

## Invariant Analysis

### Target Invariant

"The authority's fee-collection role is limited to PDA rent reclaim (`close = authority`); the authority does not receive a percentage of wagered funds as a fee recipient."

More precisely: `config.treasury != config.authority` should hold at all times, mirroring the check in `initialize_config`.

### Enforcement Points

| Location | What It Enforces | Complete? |
|----------|-----------------|-----------|
| `lib.rs:53-55` (initialize_config) | `authority != treasury`, `authority != ops`, `treasury != ops` | NO — only at init, not on updates |
| `lib.rs:70-89` (update_config) | Nothing — no re-validation | NO — gap identified |
| `lib.rs:587` `treasury.key() == config.treasury` | Settlement goes to configured treasury | YES — enforces consistency, trusts config content |
| `lib.rs:588` `treasury.key() != ops.key()` | Treasury and ops are distinct | YES — blocks `treasury == ops`, but NOT `treasury == authority` |
| `lib.rs:604` `has_one = authority` on config | Config authority matches signer | YES — wrong purpose, does not block treasury == signer |
| `treasury.key() != authority.key()` | Treasury cannot equal authority's wallet | NOT PRESENT |

### Enforcement Gap Assessment

The invariant is enforced exactly once (initialize_config) and not re-enforced in update_config. The `SettleMatch` struct enforces `treasury != ops` (preventing H003-class DoS) but does not enforce `treasury != authority` (not preventing S003/H011-class fee capture). The enforcement is incomplete and the gap is the root of both H011 and S003.

## Blocking Factors

- **`has_one = authority` on UpdateConfig (lib.rs:470):** Requires the current authority key to sign. An external attacker without the authority private key cannot execute this attack. This is a significant prerequisite, though it represents insider-threat or key-compromise scenarios.
- **`treasury.key() != ops.key()` in SettleMatch (lib.rs:588):** Prevents setting both treasury AND ops to the authority's address simultaneously. The attacker cannot consolidate 10% of every pot to a single address; they must use two distinct keys to capture treasury (7%) and ops (3%) separately. This is trivially circumvented using any second key.

---

## Enabling Factors

- **No re-validation in update_config (lib.rs:70-89):** All three distinctness invariants from initialize_config are absent.
- **No `treasury != authority` constraint in SettleMatch (lib.rs:560-610):** The absence of this constraint directly enables the attack. The program demonstrates awareness of the need for fee-account distinctness via the `treasury != ops` constraint at line 588 but does not extend this logic to `treasury vs. authority`.
- **`close = authority` already credits rent to authority (lib.rs:566):** The design pattern of sending value to the authority already exists; adding treasury redirect extends this without structural inconsistency.
- **No event emission on update_config:** Config changes are silent on-chain; treasury self-redirect is undetectable without monitoring the `treasury_account` field in `MatchSettled` events.

This is a more sophisticated attack variant that H011 does not explicitly model, but the underlying mechanism is the same confirmed vulnerability.

### Single-TX Atomic Variant: New Hypothesis Suggestion

While investigating S003, the following nuance was identified that H011 does not explicitly address and may warrant a targeted investigation or a supplementary note in H011:

**The atomic single-TX redirect:** Because `update_config` and `settle_match` can both be inner instructions within the same Solana transaction, an authority could:
1. Call `update_config(None, Some(authority_pubkey), None)` (TX instruction 0)
2. Call `settle_match(...)` with treasury = authority (TX instruction 1 — reads updated config)
3. Call `update_config(None, Some(legitimate_treasury_pubkey), None)` (TX instruction 2 — restores config)

The `MatchSettled` event would record `treasury_account = authority.pubkey()` (still detectable by monitoring), but the config state at transaction end would show the legitimate treasury address, obscuring the redirect in direct config state inspection. This is a stealth enhancement of H011, not a new vulnerability, but it should be noted in H011's documentation.

### Complete constraint survey for SettleMatch (lib.rs:560-610)

```
escrow:
  - seeds = [b"match", escrow.match_id.as_bytes()]    (PDA derivation)
  - bump = escrow.bump                                 (canonical bump)
  - has_one = authority                                (escrow.authority == signer)

winner:
  - winner.key() == escrow.player_one
    || winner.key() == escrow.player_two               (player-only winner)

treasury:
  - treasury.key() == config.treasury                 (matches stored config)
  - treasury.key() != ops.key()                        (treasury != ops)
  [ABSENT: treasury.key() != authority.key()]

ops:
  - ops.key() == config.ops                            (matches stored config)
  [ABSENT: ops.key() != authority.key()]

config:
  - seeds = [GlobalConfig::SEED]                       (singleton PDA)
  - bump = config.bump
  - has_one = authority @ EscrowError::Unauthorized    (config.authority == signer)
```

Three pairwise distinctness checks at `initialize_config` (lines 53-55):
- `authority != treasury`: PRESENT at init, ABSENT in update_config, ABSENT in SettleMatch
- `authority != ops`: PRESENT at init, ABSENT in update_config, ABSENT in SettleMatch
- `treasury != ops`: PRESENT at init, ABSENT in update_config, PRESENT in SettleMatch (line 588)

Only one of the three invariants (`treasury != ops`) is re-enforced at the settlement level. The other two (`authority != treasury` and `authority != ops`) are not enforced anywhere outside of initialization. This is the structural gap that enables both H011 and the S003 hypothesis.

### Verification: initialize_config versus update_config

```
initialize_config (lib.rs:53-55):
  require!(authority != treasury, EscrowError::InvalidConfig)      -> PRESENT
  require!(authority != ops, EscrowError::InvalidConfig)           -> PRESENT
  require!(treasury != ops, EscrowError::DuplicateFeeAccount)      -> PRESENT

update_config (lib.rs:70-89):
  require!(authority != treasury ...)                              -> ABSENT
  require!(authority != ops ...)                                   -> ABSENT
  require!(treasury != ops ...)                                    -> ABSENT
```

All three checks present at initialization; none re-validated in update_config. The SettleMatch struct re-enforces only one (`treasury != ops`). The asymmetry creates two exploitable gaps: (1) H003 cannot be exploited because SettleMatch enforces `treasury != ops`, blocking the DoS at settlement time — but the config can still be poisoned, requiring the fix to be in update_config. (2) H011/S003 can be fully exploited because SettleMatch does NOT enforce `treasury != authority`, meaning the redirected settlement proceeds normally.

### Solana account model: same pubkey as Signer and UncheckedAccount

Anchor does not enforce uniqueness across different account types (`Signer<'info>` vs `UncheckedAccount<'info>`). The Solana runtime permits the same pubkey to appear in multiple positions in an instruction's account list. When authority and treasury share the same pubkey:
- `authority` account: `Signer<'info>`, marked `mut` (receives escrow rent via `close = authority`)
- `treasury` account: `UncheckedAccount<'info>`, marked `mut` (receives treasury_amount via lamport credit)

Both are `AccountInfo` references to the same underlying account. Lamport operations on both are valid. The transaction succeeds. This was verified in H011 Step 3.
