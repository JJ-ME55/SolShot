# H001 — Balance-Check-Fail-Open Wager Bypass

**Status:** CONFIRMED
**Severity:** HIGH
**Confidence:** HIGH
**Origin:** KB

## Summary

Both `joinRoom` and `createRoom` handlers wrap the `verifyBalance()` call in a try/catch that silently swallows any exception and allows execution to continue. The comment at line 980 explicitly designates this as "best-effort — skip if RPC unavailable." A wallet with zero SOL can enter a wagered match whenever the Solana RPC call throws an unhandled exception rather than resolving normally. The `getBalance()` function in `solana.js` (line 262–272) is a separate code path and is not used in the wager-check flow; the actual vulnerability is in the outer try/catch in `main.js` around `verifyBalance()`.

## Evidence

### `server/services/solana.js` — `verifyBalance` (lines 122–143)

`verifyBalance` has its own internal try/catch and returns `{ sufficient: false }` on RPC error:

```js
// lines 122–143
export async function verifyBalance(walletAddress, wagerSOL) {
    try {
        const lamports = await getCachedLamports(walletAddress);
        ...
        return { sufficient: balance >= required, balance, required };
    } catch (err) {
        console.error('[Solana] Balance check error:', err.message);
        return {
            sufficient: false,   // <-- safe return on inner error
            balance: 0,
            required: wagerSOL + 0.01,
        };
    }
}
```

`getCachedLamports` (lines 102–113) does NOT have its own try/catch — `new PublicKey()` or `conn.getBalance()` can throw synchronously or reject in a way that escapes `verifyBalance`'s inner catch if, for example, the Connection object is null/malformed, or if `getConnection()` itself throws.

### `server/services/solana.js` — `getBalance` (lines 262–272)

This function is separate and IS fail-open (returns `0` on error), but it is used only by gold.js, NOT in the wager-check path:

```js
// lines 262–272
export async function getBalance(walletAddress) {
    const conn = getConnection();
    try {
        const pubkey = new PublicKey(walletAddress);
        const lamports = await conn.getBalance(pubkey);
        return lamports / LAMPORTS_PER_SOL;
    } catch (err) {
        console.error('[Solana] Balance error:', err.message);
        return 0;   // <-- explicit fail-open
    }
}
```

### `server/socket-io/main.js` — `joinRoom` handler (lines 980–993)

The outer try/catch around `verifyBalance()` is explicitly labeled as intentional fail-open:

```js
// lines 980–993
// Verify joiner has enough balance (best-effort — skip if RPC unavailable)
try {
    const balanceCheck = await verifyBalance(joinerWallet, roomWager)
    // H027: Fix fail-open — reject if insufficient, regardless of balance amount
    if (!balanceCheck.sufficient) {
        client.emit('joinRoomError', {
            reason: `Insufficient SOL balance. Need ${balanceCheck.required.toFixed(3)}, have ${balanceCheck.balance.toFixed(3)}`
        })
        return
    }
} catch (err) {
    console.warn('[Solana] Balance check skipped:', err.message)
    // <-- NO return. Execution falls through and the player joins the room.
}
```

### `server/socket-io/main.js` — `createRoom` handler (lines 1135–1148)

Identical pattern:

```js
// lines 1135–1148
// H038: Verify creator has sufficient balance for wager
if (wagerAmount > 0 && walletAddress) {
    try {
        const balanceCheck = await verifyBalance(walletAddress, wagerAmount)
        if (!balanceCheck.sufficient) {
            client.emit('createRoomError', {
                reason: `Insufficient SOL balance. Need ${balanceCheck.required.toFixed(3)}, have ${balanceCheck.balance.toFixed(3)}`
            })
            return
        }
    } catch (err) {
        console.warn('[Solana] Creator balance check skipped:', err.message)
        // <-- NO return. Execution falls through and the room is created.
    }
}
```

### Comment at line 980 confirms intentional design

`// Verify joiner has enough balance (best-effort — skip if RPC unavailable)`

This is not an oversight — the fail-open behavior is deliberate. The prior fix tag `H027` at line 983 attempted to fix the fail-open only for the normal (non-throwing) code path but left the exception path unclosed.

## Root Cause

Two distinct but compounding issues:

1. **`verifyBalance` in `solana.js` (lines 122–143):** The internal try/catch catches errors from `getCachedLamports`, but `getCachedLamports` (lines 102–113) calls `new PublicKey(walletAddress)` and `conn.getBalance(pubkey)` without its own guard. If `getConnection()` returns an uninitialized or stale connection object that throws synchronously on `.getBalance()`, or if the RPC endpoint is unreachable and the `@solana/web3.js` client throws a non-Promise-rejecting error, the exception propagates out of `verifyBalance`'s catch block to the outer handler.

2. **`main.js` outer catch (lines 990–992 and 1145–1147):** The catch block issues a `console.warn` and does not `return`. Execution continues unconditionally into room join / room creation logic. The comment "best-effort — skip if RPC unavailable" documents this as an intentional availability trade-off, but it creates a security bypass window during any RPC outage.

## Impact

An attacker can exploit this in two ways:

**Passive exploitation (opportunistic):** During a natural Solana RPC outage or devnet instability, a zero-balance wallet can join any wagered room or create a wagered room. Once in the match, the escrow deposit phase requires the attacker to actually sign a deposit transaction — however, if the attacker simply never signs, the deposit timeout cancels the escrow (DCA-01 at line 1059). The attacker incurs no cost and can repeatedly occupy wager slots, denying legitimate players access.

**Active exploitation (RPC exhaustion):** An attacker who can exhaust or delay the RPC endpoint (e.g., flooding devnet with requests, supplying a malicious/slow SOLANA_RPC URL via environment configuration) can reliably trigger the catch path and enter wagered matches without a balance check. If the escrow deposit phase is also bypassed (see FIN-02 / FIN-03 in the LOGIC-02 context), the attacker can participate in and win a match without ever depositing — the server would then call `settleMatchEscrow()` against an escrow PDA that was never funded by the attacker, resulting in theft of the legitimate player's deposited funds.

**Severity is HIGH (not CRITICAL):** The escrow deposit phase acts as a secondary control — the attacker must sign a real on-chain transaction to lock funds before the match starts. The balance check bypass alone does not result in immediate fund loss in the normal escrow flow; it becomes critical only when combined with FIN-02 or FIN-03.

## Recommendation

Remove the fail-open behavior. Replace the silent catch with a hard rejection:

```js
// joinRoom — replace lines 990–992
} catch (err) {
    console.error('[Solana] Balance check failed:', err.message)
    client.emit('joinRoomError', { reason: 'Unable to verify balance. Please try again.' })
    return
}
```

```js
// createRoom — replace lines 1145–1147
} catch (err) {
    console.error('[Solana] Balance check failed:', err.message)
    client.emit('createRoomError', { reason: 'Unable to verify balance. Please try again.' })
    return
}
```

Additionally, add a try/catch inside `getCachedLamports` so that RPC errors are caught at the lowest level and surfaced as structured errors to `verifyBalance`'s catch, rather than propagating as unstructured throws:

```js
async function getCachedLamports(walletAddress) {
    const now = Date.now();
    const cached = balanceCache.get(walletAddress);
    if (cached && now < cached.expiresAt) {
        return cached.lamports;
    }
    const conn = getConnection();
    const pubkey = new PublicKey(walletAddress);  // can throw on bad address
    const lamports = await conn.getBalance(pubkey); // can reject on RPC error
    balanceCache.set(walletAddress, { lamports, expiresAt: now + BALANCE_CACHE_TTL_MS });
    return lamports;
}
```

This is already structured correctly — the fix belongs exclusively in `main.js`'s outer catch blocks. Fail-closed is the correct posture for any financial gate.
