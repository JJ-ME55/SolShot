# H002 — Double Settlement via Disconnect+Fire TOCTOU Race

**Status:** POTENTIAL
**Severity:** HIGH
**Confidence:** MEDIUM
**Origin:** KB

## Summary

The `fire` handler and `cleanupRoom` (disconnect path) both call `withLock('settle:${roomId}')` to serialize settlement, but the `fire` handler calls `transitionState(ms, MATCH_STATES.SETTLING)` at line 2081 **outside** the lock before entering it at line 2085. A concurrent `disconnect` event that arrives between those two lines will be turned away by the early guard at line 566 (`if (ms.status === MATCH_STATES.SETTLING)`) — not because it lost a lock race, but because the state was already flipped. That guard causes an early return **without** settlement, so no double-settlement occurs on that specific path. However, a third, completely unlocked settlement path exists in the turn-timer forfeit callback (`startTurnTimer`, lines 326–393), which calls `transitionState` and `settleMatch` with **no lock at all**, creating a genuine window where it can race the `fire` handler's TOCTOU gap.

## Evidence

### Path A — `fire` handler (lines 2079–2085, `server/socket-io/main.js`)

```js
// line 2079
if (matchResult.isOver) {
    // H068/H020: Transition to SETTLING — if fails, another handler already settled
    const transitioned = transitionState(ms, MATCH_STATES.SETTLING)  // line 2081 — OUTSIDE lock
    if (!transitioned) return                                          // line 2082

    // H020: Use lock to prevent concurrent settlement
    await withLock(`settle:${this.roomId}`, async () => {             // line 2085 — lock acquired HERE
        // Re-check state inside lock
        if (ms.status !== MATCH_STATES.SETTLING) return               // line 2087
        ...
        const sResult = await settleMatch(winnerWallet, loserWallet, ws.amount, roomId)  // line 2102
```

The TOCTOU window is the span between line 2081 (state written to SETTLING) and line 2085 (lock acquired). Any concurrent handler that runs between those two `await`-free synchronous lines will observe status = SETTLING.

### Path B — `cleanupRoom` / disconnect (lines 558–685, `server/socket-io/main.js`)

```js
// line 566 — early guard
if (ms && ms.status === MATCH_STATES.SETTLING) {
    client.leave(roomId)
    io.sockets.in(roomId).emit('opponentLeft', {})
    client.roomId = null
    client.isHost = false
    return                              // exits WITHOUT settlement
}

// line 575 — wager forfeit path (only reached if not SETTLING)
if (ws && ws.amount > 0 && ms) {
    const room = findRoom(roomId)
    if (room && (ms.status === MATCH_STATES.BATTLE || ms.status === MATCH_STATES.WEAPON_SHOP)) {
        await withLock(`settle:${roomId}`, async () => {              // line 579 — lock acquired
            const currentMs = matchStates[roomId]
            if (!currentMs || currentMs.status === MATCH_STATES.SETTLING ||
                currentMs.status === MATCH_STATES.COMPLETE) return   // line 581 — inner guard
            transitionState(currentMs, MATCH_STATES.SETTLING)        // line 583 — inside lock
```

For the `fire`+`disconnect` pairing specifically, if `disconnect` arrives **after** line 2081 (status is now SETTLING), the guard at line 566 fires and returns early — no double settlement. If `disconnect` arrives **before** line 2081 (status is still BATTLE), `cleanupRoom` enters `withLock` at line 579, flips to SETTLING at line 583, and calls `settleMatch` at line 654. When the `fire` handler then reaches line 2081, `transitionState` returns `false` (SETTLING → SETTLING is not a valid transition per the state machine), and `fire` returns at line 2082 without ever entering `withLock`. In both orderings the `fire`+`disconnect` pair is safe.

### Path C — turn-timer forfeit (lines 326–393, `server/socket-io/main.js`) — NO LOCK

```js
// line 326 — OUTSIDE any lock, no guard on current state
transitionState(ms, MATCH_STATES.SETTLING)

// line 341 — direct settleMatch call, no withLock
const result = await settleMatch(winnerWallet, loserWallet, wsState.amount, roomId)
```

The turn-timer callback in `startTurnTimer` is module-level and has no access to `cleanupRoom`'s `withLock` call site. It transitions and settles with zero synchronization. The timer callback can run during the TOCTOU window in the `fire` handler (between lines 2081 and 2085), or concurrently with `cleanupRoom`'s lock-protected path.

Concretely for `fire` + turn-timer:
1. Turn timer fires (callback scheduled via `setTimeout`).
2. Timer callback: `transitionState(ms, SETTLING)` succeeds (state was BATTLE) → line 326.
3. Timer callback: `await settleMatch(...)` — yields to event loop at the RPC call → line 341.
4. `fire` handler runs: `transitionState(ms, SETTLING)` returns `false` (already SETTLING) → line 2082 — fire returns safely.
5. **No double settlement on this ordering.**

Alternative ordering where both succeed:
1. `fire` handler: `transitionState(ms, SETTLING)` succeeds → line 2081. **No `await` yet.**
2. Turn timer callback cannot interleave here — we are still in the same synchronous tick. The timer callback only runs after a `await` yields control.
3. `fire` handler: enters `withLock` at line 2085 — first `await`, event loop yields.
4. Timer callback: `transitionState(ms, SETTLING)` returns `false` → timer path bails at line 326 only if it checks the return value... **it does not check the return value** of `transitionState`.

```js
// line 326 — return value of transitionState is DISCARDED
transitionState(ms, MATCH_STATES.SETTLING)   // no `if (!transitioned) return`

// line 341 — settleMatch called regardless
const result = await settleMatch(winnerWallet, loserWallet, wsState.amount, roomId)
```

So if the timer fires after the `fire` handler has already flipped to SETTLING at line 2081 but before `settleMatch` resolves inside the lock (lines 2085–2102), the timer will call `settleMatch` a second time for the same room — double settlement.

### `transitionState` return value check comparison

| Path | Checks `transitionState` return value? | Safe? |
|------|----------------------------------------|-------|
| `fire` handler (line 2081–2082) | YES — `if (!transitioned) return` | Yes |
| `cleanupRoom` inside lock (line 583) | NO — but lock + inner guard at 581 protect it | Yes |
| turn-timer forfeit (line 326) | NO — discards return value, proceeds to `settleMatch` | **VULNERABLE** |

## Root Cause

Two independent defects combine:

1. The turn-timer forfeit path (`startTurnTimer`, lines 326–393) does not use `withLock`, does not check the return value of `transitionState`, and therefore cannot be blocked by concurrent settlement from the `fire` handler or `cleanupRoom`. It is a third settlement path that the mutex in `guards.js` was never applied to.

2. The `fire` handler performs `transitionState` outside the lock (line 2081), creating a TOCTOU window. While the `disconnect` path is accidentally safe because its outer guard (line 566) observes the already-set state, the turn-timer path does not have an equivalent gate and proceeds unconditionally.

## Impact

A malicious or unlucky scenario: player fires the killing blow, causing `matchResult.isOver = true` in the `fire` handler. Simultaneously, the turn timer for that same round fires (e.g., because the shot processing took longer than the turn window). The timer calls `settleMatch` while `fire` is awaiting the lock and its own `settleMatch` RPC. Both calls reach the on-chain escrow program (or the `solana.js` settlement function) concurrently. Depending on escrow implementation:

- If the on-chain program enforces single-settlement (idempotent), the second call fails silently — the `failedSettlements` queue absorbs it and logs an error, but no funds are double-paid.
- If `settleMatch` in `solana.js` does not check on-chain program state before dispatching (and the program does not guard against re-settlement), the winner could receive two payouts from the escrow account, draining funds that should have gone to treasury/ops, or causing the escrow to error in a partially-settled state.

The financial impact per occurrence is bounded by the wager amount (up to the High Roller tier). The probability is non-trivial for any wagered match where turn timers are active during the final shot.

## Recommendation

**Primary fix — apply `withLock` to the turn-timer forfeit path:**

```js
// In startTurnTimer callback, replace lines 326–393 with:
transitionState(ms, MATCH_STATES.SETTLING)   // keep outside for early-exit signal

await withLock(`settle:${roomId}`, async () => {
    const currentMs = matchStates[roomId]
    if (!currentMs || currentMs.status !== MATCH_STATES.SETTLING) return
    // ... rest of settlement logic ...
})
```

**Secondary fix — check `transitionState` return value in the turn-timer path:**

```js
const transitioned = transitionState(ms, MATCH_STATES.SETTLING)
if (!transitioned) {
    // Another path already settled — skip
    io.sockets.in(roomId).emit('opponentLeft', {})
    await removeRoom(roomId)
    return
}
```

Both fixes together fully close the race. The lock ensures mutual exclusion against the `fire` handler's lock-protected path; the return-value check provides a fast exit when the state machine has already moved on.

**Tertiary fix — move `transitionState` inside the lock in the `fire` handler** (closes the TOCTOU gap used to block the `disconnect` path, which currently relies on the outer guard rather than lock ordering):

```js
// fire handler — move transitionState INSIDE withLock:
await withLock(`settle:${this.roomId}`, async () => {
    const transitioned = transitionState(ms, MATCH_STATES.SETTLING)
    if (!transitioned) return
    ...
})
```

This makes the fire+disconnect combination formally correct under the lock rather than accidentally safe via a coincidentally observed state value.
