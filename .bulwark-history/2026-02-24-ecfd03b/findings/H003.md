# H003 — Prestige Burn Double-Unlock via Concurrent Socket Events

**Status:** CONFIRMED
**Severity:** HIGH
**Confidence:** HIGH
**Origin:** KB

## Summary

The `prestigeBurn` socket handler in `main.js` calls `verifyBurnTransaction()` with `await`, which performs a remote RPC call before adding the transaction signature to the replay-protection Set. Two concurrent `prestigeBurn` events carrying the same `txSignature` will both pass the `verifiedBurnTxs.has()` check before either one reaches `verifiedBurnTxs.add()`, causing both to return `valid: true` and both to call `prestigeBurn(wallet)` — advancing the prestige tier twice and deducting the burn cost twice from a single on-chain burn.

## Evidence

**`server/services/shot-token.js` — replay guard check (line 465), async gap (lines 471–547), and late add (line 549):**

```js
// Line 465 — replay protection check
if (verifiedBurnTxs.has(txSignature)) {
    return { valid: false, reason: 'Transaction already used for prestige' };
}

try {
    // Line 471 — ASYNC SUSPENSION POINT (network I/O, may take 200–2000ms)
    const tx = await connection.getParsedTransaction(txSignature, {
        commitment: 'confirmed',
        maxSupportedTransactionVersion: 0,
    });

    // ... (lines 476–546: validation logic, more return paths) ...

    // Line 549 — add() is only reached AFTER the await resolves
    verifiedBurnTxs.add(txSignature);
    persistBurnTx(txSignature);

    return { valid: true };
```

**`server/socket-io/main.js` — socket handler (lines 1611–1644):**

```js
// Line 1611
client.on('prestigeBurn', async (data) => {
    const wallet = authenticatedWallets[client.id] || null
    // ...

    // Line 1626 — await yields; a second concurrent handler for the same
    // txSignature can now execute and also pass the has() check above
    const verification = await verifyBurnTransaction(txSignature, wallet, burnAmount)

    if (!verification.valid) {
        client.emit('prestigeResult', { success: false, reason: verification.reason || 'Burn verification failed' })
        return
    }

    // Line 1634 — both concurrent handlers reach this when both return valid: true
    const result = prestigeBurn(wallet)
    // ...
    client.emit('prestigeResult', result)
})
```

**Interleaving timeline (same wallet, same `txSignature`, two rapid socket events):**

```
Handler A: verifiedBurnTxs.has("sigX")  → false  (line 465)
Handler A: await getParsedTransaction()  → SUSPENDS
Handler B: verifiedBurnTxs.has("sigX")  → false  (line 465, Set still empty)
Handler B: await getParsedTransaction()  → SUSPENDS
Handler A: resumes, validates, reaches line 549: verifiedBurnTxs.add("sigX")
Handler A: returns { valid: true }
Handler A: prestigeBurn(wallet) called → tier advanced, balance debited
Handler B: resumes, validates, reaches line 549: verifiedBurnTxs.add("sigX") (no-op, already present)
Handler B: returns { valid: true }
Handler B: prestigeBurn(wallet) called → tier advanced AGAIN, balance debited AGAIN
```

The `verifiedBurnTxs.add()` on Handler B's path is a no-op — the signature is already in the Set — but the damage is already done: `prestigeBurn()` has been called twice.

## Root Cause

JavaScript's event loop provides within-tick atomicity but not across `await` boundaries. The window between the synchronous `verifiedBurnTxs.has()` check (line 465) and the synchronous `verifiedBurnTxs.add()` call (line 549) contains at least one `await` (line 471, the RPC call to Solana). Any number of concurrent handlers can enter that window simultaneously and all pass the `has()` guard before any one of them completes the `add()`. There is no per-wallet lock, no in-flight tracking Set, and no atomic check-and-set operation protecting this critical section.

## Impact

An attacker with a single valid on-chain burn transaction can advance their prestige tier multiple times (bounded by how many concurrent events the server accepts before the first handler's `add()` executes, typically one or two extra advances) with only one burn's worth of SHOT tokens destroyed on-chain. In concrete terms:

- Burn 200 SHOT (Tier 1 cost) on-chain once, send two concurrent `prestigeBurn` events → reach Tier 2 (Silver) unlocking Cruiser, costing only 200 SHOT instead of 700.
- With careful timing, an attacker targeting Diamond could skip several tiers, unlocking weapons (Homing Missile, Cruiser, Tommy Gun, Chain Reaction, Pineapple) at a fraction of the required 8,400 SHOT cumulative burn.
- The off-chain `state.balance` is debited for each successful `prestigeBurn()` call, so if the attacker does not have enough balance the second call to `prestigeBurn()` will fail with "insufficient balance" — but if the player has accumulated enough SHOT (e.g., balance >= 700 but only burned 200 on-chain) the second advance also succeeds, leaking both balance and tier integrity.

## Recommendation

Add an in-flight tracking Set to make the guard synchronous and atomic across the check-fetch-add sequence. Before the `await`, optimistically mark the signature as "in-flight" and bail on any concurrent attempt:

```js
// In shot-token.js, alongside verifiedBurnTxs
const pendingBurnTxs = new Set();   // signatures currently being verified

export async function verifyBurnTransaction(txSignature, walletAddress, expectedAmount) {
    if (!SHOT_MINT) {
        return { valid: true };
    }

    // Synchronous replay + in-flight check (no await between these two lines)
    if (verifiedBurnTxs.has(txSignature) || pendingBurnTxs.has(txSignature)) {
        return { valid: false, reason: 'Transaction already used or pending verification' };
    }
    pendingBurnTxs.add(txSignature);   // claim the slot before any await

    try {
        const tx = await connection.getParsedTransaction(txSignature, { ... });

        // ... existing validation ...

        verifiedBurnTxs.add(txSignature);
        pendingBurnTxs.delete(txSignature);
        persistBurnTx(txSignature);
        return { valid: true };
    } catch (err) {
        pendingBurnTxs.delete(txSignature);   // release slot on error
        return { valid: false, reason: 'Failed to verify burn transaction' };
    }
}
```

All early-return paths that currently return `{ valid: false }` after the `await` must also call `pendingBurnTxs.delete(txSignature)` to avoid permanently blocking legitimate future retries on a signature that failed for transient reasons (e.g., RPC timeout, tx not yet confirmed). Alternatively, the `prestigeBurn` socket handler in `main.js` can implement a per-wallet mutex using the existing `withLock()` pattern (already used for settlement) keyed on `prestige:<walletAddress>` to serialize concurrent attempts at the handler level.
