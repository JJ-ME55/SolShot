# H010 — Deposit-Confirmation Race Double-EscrowActive
**Status:** CONFIRMED
**Severity:** MEDIUM
**Confidence:** HIGH
**Origin:** KB

## Summary

The `escrowDepositConfirm` handler in `server/socket-io/main.js` contains a classic async race condition. Because the handler suspends at multiple `await` points (an RPC call and an optional 2-second sleep) before writing the deposit flag, two concurrent handler invocations — one for the host and one for the joining player — can both pass verification and then interleave on the shared `ws.deposits` object. In the worst-case ordering, both handlers evaluate `hostDeposited && playerDeposited` as `true` and both emit `escrowActive` to the room. There is no idempotency guard on emission and no client-side handler that de-duplicates the event.

A secondary consequence is that `depositTimers[rid]` is cleared by whichever handler fires first, while the second handler attempts `clearTimeout` on an already-deleted timer — a benign no-op in isolation, but evidence that the cleanup path was not designed for concurrent execution.

## Evidence

**Handler entry point — shared mutable state captured before awaits:**

```js
// server/socket-io/main.js  line 1736
const ws = wagerStates[rid]
if (!ws) return
```

`ws` is a reference to the live `wagerStates[rid]` object. Both handlers for the host and the joining player capture the same reference.

**Suspension point 1 — RPC call (line 1743):**

```js
let escrowState = await getEscrowState(rid)
```

Node.js yields the event loop here. The second `escrowDepositConfirm` handler (from the other player's socket) can now start executing up to and including this same `await`.

**Suspension point 2 — conditional 2-second sleep (lines 1746-1747):**

```js
await new Promise(r => setTimeout(r, 2000))
escrowState = await getEscrowState(rid)
```

This is a 2-second window during which the second handler can advance through its own verification logic all the way to the write phase.

**Non-atomic read-modify-check sequence (lines 1782-1790):**

```js
// line 1782
if (!ws.deposits) ws.deposits = {}
ws.deposits[client.id] = txSignature          // write own flag

const hostDeposited   = ws.deposits[room.host?.socketId]   // line 1785
const playerDeposited = ws.deposits[room.player?.socketId] // line 1786

if (hostDeposited && playerDeposited) {        // line 1790
    // Both handlers can reach here independently
    if (depositTimers[rid]) {
        clearTimeout(depositTimers[rid])       // line 1794
        delete depositTimers[rid]              // line 1795
    }
    io.sockets.in(rid).emit('escrowActive', { // line 1798
        roomId: rid,
        escrowPDA: room.escrowPDA,
        totalPot: ws.amount * 2,
    })
}
```

There is no lock, no guard flag, and no post-write re-check before the `emit`. After Handler A writes its flag and Handler B writes its flag, each then reads `ws.deposits` and sees both flags set. Each independently passes the `if (hostDeposited && playerDeposited)` branch.

**No client-side deduplication:**

A search of the entire codebase confirms `escrowActive` is only emitted — it has no registered listener anywhere in the client:

```
grep -rn "escrowActive" client/src/   → (no results)
```

The event is therefore silently dropped twice by the client, but any future handler that is added (e.g., transitioning match state or enabling the start button) will fire twice.

**`withLock` exists but is not applied here:**

The `withLock` async mutex used to guard settlement (lines 579, 2085) is imported and available but not used for the deposit-confirmation path:

```js
// guards.js line 120 — already used for H020 (settlement race)
export async function withLock(key, fn, timeoutMs = LOCK_TIMEOUT_MS) { ... }
```

## Root Cause

The `escrowDepositConfirm` handler performs async I/O (Solana RPC) before writing to shared state. Node.js's single-threaded event loop does not protect against concurrent `async` handler invocations. Two sockets belonging to the same room each invoke the handler; both handlers park at `await` and, upon resumption, operate on the same `ws.deposits` object without mutual exclusion. The final read-check-emit sequence is not atomic and can be entered by both handlers when the second handler resumes after the first has already written its flag.

This is the same class of bug as H020 (double settlement), which was fixed with `withLock`. The deposit-confirmation path replicates the pattern but was not given the same fix.

## Impact

1. **Double `escrowActive` emission (today):** Both sockets in the room receive `escrowActive` twice per match start. Currently harmless because the client has no handler for the event. If a handler is added — for example, to display a "wager locked" banner, enable the match-start flow, or trigger on-chain settlement — it will execute twice, potentially corrupting client state or sending duplicate transactions.

2. **Timer double-clear:** The second handler executes `clearTimeout` on a timer that the first handler already cleared and deleted. `clearTimeout(undefined)` is a no-op in Node.js, so this does not currently crash, but the `delete depositTimers[rid]` on line 1795 attempts to delete a key that no longer exists — again a silent no-op, but masking the race.

3. **Future regression surface:** The unguarded emission creates a latent trap. Any developer who adds a client listener for `escrowActive` must simultaneously discover and mitigate this server-side race, which is non-obvious.

Severity is rated MEDIUM (not HIGH) because `escrowActive` currently has no client handler; no funds are at risk from the double emission as the on-chain escrow state is already correct after both RPC verifications succeed. The risk escalates to HIGH the moment a client listener is wired.

## Recommendation

Apply `withLock` to the entire post-verification write-and-emit sequence, consistent with the existing pattern used for settlement:

```js
// server/socket-io/main.js — escrowDepositConfirm handler
// Replace lines 1781-1803 with:

await withLock(`deposit:${rid}`, async () => {
    // Re-read ws inside lock to get latest state
    const wsLocked = wagerStates[rid]
    if (!wsLocked) return

    // Idempotency: if this player already confirmed, do nothing
    if (wsLocked.deposits && wsLocked.deposits[client.id]) return

    if (!wsLocked.deposits) wsLocked.deposits = {}
    wsLocked.deposits[client.id] = txSignature

    const hostDeposited   = wsLocked.deposits[room.host?.socketId]
    const playerDeposited = wsLocked.deposits[room.player?.socketId]

    console.log(`[Escrow] Deposit confirmed: ${client.id} for room ${rid} (TX: ${txSignature})`)

    if (hostDeposited && playerDeposited) {
        if (depositTimers[rid]) {
            clearTimeout(depositTimers[rid])
            delete depositTimers[rid]
        }
        console.log(`[Escrow] Both deposits confirmed for room ${rid} — match is escrowed`)
        io.sockets.in(rid).emit('escrowActive', {
            roomId: rid,
            escrowPDA: room.escrowPDA,
            totalPot: wsLocked.amount * 2,
        })
    }
})
```

Key changes:
- `withLock('deposit:rid', ...)` serialises the write-check-emit section for a given room.
- Re-read `wagerStates[rid]` inside the lock for a fresh reference.
- Early-return idempotency guard (`if (wsLocked.deposits[client.id]) return`) prevents duplicate processing if a client retransmits the event.
- The on-chain verification (the `await getEscrowState` calls) runs outside the lock to avoid holding the lock during slow RPC round-trips.
