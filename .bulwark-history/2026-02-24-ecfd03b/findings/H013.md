# H013 — Single Authority Hot-Wallet Full Fund Drain

**Status:** CONFIRMED
**Severity:** CRITICAL
**Confidence:** HIGH
**Origin:** KB

---

## Summary

A single server-side hot-wallet keypair (`_escrowKeypair` in `server/services/keys.js`) holds
unilateral authority over every privileged operation in the escrow program: `create_match`,
`settle_match`, `cancel_match`, `pause_program`, `unpause_program`, and `update_config`.
There is no multi-sig, no timelock, and no secondary signer requirement on any of these
instructions.

Compromise of this key does **not** permit the attacker to route `settle_match` winner funds to
an arbitrary address in one step — the on-chain `winner` constraint is correctly bound to
`escrow.player_one || escrow.player_two`. However, the attacker can execute a two-step drain:

1. Call `update_config` to redirect `config.treasury` and `config.ops` to attacker wallets.
2. Call `settle_match` on every active escrow, naming either registered player as winner.
   The 7% treasury and 3% ops shares (total 10% of every pot) flow to attacker wallets.

Additionally, `update_config` accepts an optional `new_authority` field with no
propose/accept handshake and no timelock. The attacker can permanently transfer protocol
authority to a key they control in a single transaction, locking out the original operator.

The combined exposure is: **all active escrow pots (10% drain on every match via fee
redirection) plus permanent loss of protocol control**.

## Evidence

### 1. Single keypair for all operations (`server/services/keys.js`)

```js
// keys.js line 17
let _escrowKeypair = null;

// line 72-74
export function getEscrowKeypair() {
    return _escrowKeypair;
}
```

`getEscrowKeypair()` is called in `escrow.js` for every privileged instruction:
`createMatchEscrow`, `settleMatchEscrow`, `cancelMatchEscrow`, `pauseProgram`,
`unpauseProgram`, `updateConfig`, and `initializeConfig`. There is no second key, no
threshold, and no hardware security module referenced.

### 2. `settle_match` winner is constrained to registered players, limiting direct drain

```rust
// lib.rs lines 575-581
#[account(
    mut,
    constraint = winner.key() == escrow.player_one
        || winner.key() == escrow.player_two
        @ EscrowError::InvalidWinner
)]
pub winner: UncheckedAccount<'info>,
```

The winner account must match one of the two players stored in the escrow PDA at creation
time. A compromised authority key alone cannot route the 90% winner share to an attacker
wallet in a single step.

### 3. Treasury and ops are validated against config PDA — but config is mutable by the same key

```rust
// lib.rs lines 585-598
#[account(
    mut,
    constraint = treasury.key() == config.treasury @ EscrowError::InvalidTreasury,
    constraint = treasury.key() != ops.key() @ EscrowError::DuplicateFeeAccount,
)]
pub treasury: UncheckedAccount<'info>,

#[account(
    mut,
    constraint = ops.key() == config.ops @ EscrowError::InvalidOps,
)]
pub ops: UncheckedAccount<'info>,
```

`update_config` can change `config.treasury` and `config.ops` with only the authority key
as signer:

```rust
// lib.rs lines 70-89
pub fn update_config(
    ctx: Context<UpdateConfig>,
    new_authority: Option<Pubkey>,
    new_treasury: Option<Pubkey>,
    new_ops: Option<Pubkey>,
) -> Result<()> {
    let config = &mut ctx.accounts.config;
    if let Some(a) = new_authority { config.authority = a; }
    if let Some(t) = new_treasury  { config.treasury = t; }
    if let Some(o) = new_ops       { config.ops = o; }
    Ok(())
}
```

No timelock. No require-then-execute pattern. No secondary signer. The authority field itself
can be updated in the same call, completing a full authority hijack.

### 4. `UpdateConfig` account struct — `has_one = authority` on the config PDA is the sole guard

```rust
// lib.rs lines 465-475
#[derive(Accounts)]
pub struct UpdateConfig<'info> {
    #[account(
        mut,
        seeds = [GlobalConfig::SEED],
        bump = config.bump,
        has_one = authority @ EscrowError::Unauthorized,
    )]
    pub config: Account<'info, GlobalConfig>,
    pub authority: Signer<'info>,
}
```

The only check is that the transaction signer matches `config.authority`. No second factor,
no on-chain governance, no time delay.

### 5. Architecture audit confirms the risk

From `.audit/ARCHITECTURE.md` (executive summary, line 13):

> "The authority's total economic control without timelock or multisig."
> "one-step authority transfer enabling instant takeover"

The architecture document explicitly records this as a known concern but it has not been
mitigated in the current codebase.

### 6. No multi-sig or timelock anywhere in the codebase

Searching `server/services/escrow.js`, `server/services/keys.js`, and `programs/solshot-escrow/src/lib.rs`
finds zero references to any multi-signature scheme, Squads, Serum governance, timelock
instruction, or two-step authority transfer pattern.

## Root Cause

The protocol was designed with a single centralized operator model. The server hot-wallet
keypair is the only signer required for all administrative and settlement instructions. While
the on-chain program correctly validates winner addresses against stored player pubkeys
(preventing the simplest drain path), the `update_config` instruction allows the same key to
silently redirect all fee destinations and permanently transfer authority in a single
transaction with no delay, no confirmation window, and no secondary approval.

The root cause is **architectural**: a single private key is both the operational credential
(used in every match) and the governance credential (used to change protocol parameters).
These two roles are not separated.

---

## Impact

**Immediate on compromise:**

- Attacker calls `update_config` with their own wallets as `new_treasury` and `new_ops`, and
  their own key as `new_authority`. This is one transaction, irreversible.
- Attacker calls `settle_match` on every active escrow. 10% of every active pot (7% + 3%
  fee share) is routed to attacker wallets. At 100 SOL max wager per match, 20 concurrent
  High Roller matches = 200 SOL pot × 10% = 20 SOL per batch of 20 matches.
- The 90% winner share still goes to a registered player (not the attacker), limiting
  direct SOL theft from that portion.
- After `update_config` transfers authority, the original operator loses all ability to
  pause, cancel, or reclaim protocol control.

**Availability impact:**

- Attacker can call `pause_program` to halt all new deposits, freezing player funds in
  `AwaitingDeposits` state until the 24h player-cancel timeout or the 48h permissionless
  reclaim window elapses.

**Key exposure vectors:**

- Server process memory dump
- Plaintext keypair file on disk (`SOLANA_KEYPAIR_PATH`)
- Plaintext `SOLANA_KEYPAIR_JSON` environment variable exposed via process listing,
  container introspection, or logging
- Insider threat (any party with server access)

---

## Recommendation

**Minimum for mainnet:**

1. **Separate operational and governance keys.** The settlement key (used per-match) should
   be a distinct keypair from the governance key (used for `update_config`,
   `pause_program`). Store the governance key in cold storage or a hardware wallet; the
   operational key is the only one that needs to be online.

2. **Implement a two-step authority transfer for `update_config`.** Add a
   `proposed_authority` field to `GlobalConfig`. `propose_update_config` sets the field
   (requires current authority). A separate `accept_config` instruction requires the
   **new** authority to sign, confirming they hold the key. This eliminates instant
   takeover from a single compromised key.

3. **Add a timelock on treasury/ops address changes.** Even without a second key,
   requiring a 24–48 hour delay between proposing and applying a fee destination change
   gives operators time to detect and respond to unauthorized changes before funds are
   redirected.

**Recommended for mainnet (stronger):**

4. **Use a multi-sig (e.g., Squads v4) as the protocol authority.** Replace the single
   server keypair as `config.authority` with a Squads multisig PDA. Require M-of-N
   approval for `update_config` and authority transfers. The operational settlement key
   can remain a single hot-wallet signer for `settle_match` only, limited to that role.

5. **Consider a governance instruction that allows setting a settlement-only role** distinct
   from the admin authority, so the hot wallet has no power over `update_config` at all.

**Operational mitigations (not code-level but reduce exposure):**

- Store `SOLANA_KEYPAIR_JSON` in a secrets manager (Vault, AWS Secrets Manager) with
  short TTL leases; never write the raw key to disk or environment variables in production.
- Implement alert monitoring on `update_config` and `pause_program` on-chain events.
- Minimize hot-wallet SOL balance to the minimum required for transaction fees.
