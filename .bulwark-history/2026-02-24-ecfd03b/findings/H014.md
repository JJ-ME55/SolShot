# H014 — Incomplete Key Zeroing Enables Heap Dump Key Extraction
**Status:** CONFIRMED
**Severity:** MEDIUM
**Confidence:** HIGH
**Origin:** KB

## Summary

`server/services/keys.js` contains a documented KM-04 mitigation that only partially zeroes the secret key material. The code correctly zeroes the intermediate `Uint8Array` (`bytes.fill(0)`) after calling `Keypair.fromSecretKey()`, but the original parsed JSON array (`secretKeyArray` — a plain JS `Array` of 64 numbers) is never zeroed. That array holds the same raw secret key bytes and remains live in the V8 heap from the time `JSON.parse()` returns until the garbage collector eventually reclaims it. A heap snapshot taken at any point in that window — including after `initKeys()` returns — can recover the full 64-byte secret key. The code comment at line 11 ("Keypair object is the only in-memory copy of the secret") is therefore factually incorrect.

## Evidence

Full source of the relevant section (`server/services/keys.js`, lines 41–63):

```js
// keys.js lines 41–63
try {
    let secretKeyArray;                                    // line 42

    if (keypairJson) {
        secretKeyArray = JSON.parse(keypairJson);          // line 45 — plain Array<number>
    } else {
        const resolved = keypairPath.replace('~', ...);
        secretKeyArray = JSON.parse(fs.readFileSync(resolved, 'utf-8')); // line 48
    }

    const bytes = Uint8Array.from(secretKeyArray);         // line 51 — copy into typed array
    _escrowKeypair = Keypair.fromSecretKey(bytes);         // line 52 — Keypair takes its own slice

    // KM-04: Zero the input array — secret now lives only inside the Keypair object
    bytes.fill(0);                                         // line 55 — only bytes is zeroed

    // secretKeyArray is never zeroed; it still holds the 64 key bytes
    console.log(`[Keys] Escrow authority: ...`);
    return true;
} catch (err) { ... }
```

Two copies of the secret key material exist simultaneously after line 51:

| Variable | Type | Contains secret? | Zeroed? |
|---|---|---|---|
| `secretKeyArray` | `Array<number>` (64 elements) | Yes — full 64 bytes | No |
| `bytes` | `Uint8Array` (64 bytes) | Yes — full 64 bytes | Yes, line 55 |

`secretKeyArray` goes out of lexical scope at the end of the `try` block, but exiting scope in JavaScript does not zero or free memory. The array object persists in the V8 heap until the GC chooses to collect it. Because Node.js runs a generational GC and `initKeys()` is called once at startup, the array may survive in the old-object heap for the lifetime of the process.

A V8 heap snapshot (obtained via `--inspect` + Chrome DevTools, `v8.writeHeapSnapshot()`, `process.report.writeReport()`, or a native heap dump from a compromised process) would show the `Array` object containing the 64 raw integer values of the secret key.

## Root Cause

`JSON.parse()` on a Solana keypair file (which has the format `[byte0, byte1, ..., byte63]`) produces a standard JavaScript `Array`. Unlike `Uint8Array`, a JS `Array` has no `fill()` method that overwrites its backing store in a predictable way that zeroes physical memory — but more importantly, the code does not call `fill()` on it at all. The author applied the zeroing discipline only to the `Uint8Array` intermediate, not to the upstream source from which it was built.

## Impact

1. **Heap dump key recovery.** Any party who can obtain a V8 heap snapshot of the server process — including the server operator themselves under coercion, a cloud provider with memory access, or an attacker who achieves RCE — can search the snapshot for an `Array` of 64 small integers (0–255) and recover the escrow authority secret key. The escrow authority can sign settlement and cancel instructions, allowing a full drain of all active escrow PDAs.

2. **False security guarantee.** The comment on line 11 ("Keypair object is the only in-memory copy of the secret") and the KM-04 annotation give a misleading assurance that the zeroing is complete. Code reviewers and auditors reading this file may incorrectly conclude the mitigation is fully effective.

3. **Process report / core dump exposure.** Node.js `--report-on-signal` and OS-level core dumps on crash will capture heap state. On cloud platforms (e.g., Lambda, Cloud Run, Fly.io), crash reports may be stored and accessible to support staff.

Severity is rated MEDIUM rather than HIGH because exploitation requires the ability to read process heap memory, which implies significant prior access. However, because the stated and documented intent of this code is to defend against exactly that scenario, the partial implementation represents a meaningful security gap relative to the security property it claims to provide.

## Recommendation

Zero `secretKeyArray` immediately after `Uint8Array.from()` converts it, before any `await` or other suspension point:

```js
const bytes = Uint8Array.from(secretKeyArray);

// Zero the source array first — JS Array has no typed fill, iterate manually
for (let i = 0; i < secretKeyArray.length; i++) secretKeyArray[i] = 0;

_escrowKeypair = Keypair.fromSecretKey(bytes);
bytes.fill(0);
```

Note that calling `secretKeyArray.fill(0)` would also work for a plain `Array` in V8 (it writes 0 into each element slot), but the semantics are weaker than `Uint8Array.fill` because V8 may optimize sparse or holey arrays differently. The explicit `for` loop above is unambiguous.

Update the comment on line 11 to reflect the two-step zeroing:

```js
 *   - Source JSON array and input Uint8Array both zeroed after Keypair construction (KM-04)
 *   - Keypair object is the only in-memory copy of the secret after initKeys() returns
```

Additionally consider loading the keypair from an environment variable as a base58 or hex string (rather than a JSON array of numbers), and using `Buffer.from()` directly into a `Uint8Array` to avoid ever creating the intermediate `Array<number>`.
