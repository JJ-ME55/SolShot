# H015 — SOLANA_KEYPAIR_JSON Env Var Leak via Crash Reporter
**Status:** POTENTIAL
**Severity:** HIGH
**Confidence:** MEDIUM
**Origin:** KB

## Summary

`SOLANA_KEYPAIR_JSON` holds the raw 64-byte server escrow authority private key as a
JSON byte-array string in `process.env` for the entire lifetime of the process. The
env var is **never deleted** after the key is loaded. No crash reporter or APM agent
is currently integrated, and the `uncaughtException` / `unhandledRejection` handlers
do not dump `process.env`. However, the structural risk is real: any future addition
of an APM agent (Sentry, Datadog, New Relic) that captures process environment by
default would silently exfiltrate the private key.

## Evidence

### 1. Env var read but never cleared (`server/services/keys.js` lines 33–55)

```js
// line 33
const keypairJson = process.env.SOLANA_KEYPAIR_JSON;
// ...
if (keypairJson) {
    secretKeyArray = JSON.parse(keypairJson);
}
const bytes = Uint8Array.from(secretKeyArray);
_escrowKeypair = Keypair.fromSecretKey(bytes);
// KM-04: Zero the input array
bytes.fill(0);
```

The code zeros the intermediate `Uint8Array` (KM-04) — a good practice — but
`process.env.SOLANA_KEYPAIR_JSON` still contains the original JSON string with all 64
bytes in plaintext. There is no `delete process.env.SOLANA_KEYPAIR_JSON` anywhere in
the codebase (confirmed by full-repo grep).

### 2. No crash reporter / APM present (but pino is)

`server/package.json` lists `pino` and `pino-pretty`. The pino logger in
`server/services/logger.js` has a `redact` configuration that censors wallet addresses,
but does **not** redact `SOLANA_KEYPAIR_JSON` or any env var keys:

```js
redact: {
    paths: [
        'walletAddress', 'wallet', 'winner', 'loser', 'player',
        'p1wallet', 'p2wallet', 'winnerAddress', 'loserAddress',
        '*.walletAddress', '*.wallet',
    ],
    censor: '[REDACTED]',
},
```

If a future developer passes `process.env` as a log context object (e.g.,
`logger.info({ env: process.env }, 'startup')`), the private key would appear in
plaintext log output.

### 3. Crash handlers do not dump env — but provide no protection against future integrations

`server/index.js` lines 177–183:

```js
process.on('uncaughtException', (err) => {
    console.error('[FATAL] Uncaught exception:', err);
});
process.on('unhandledRejection', (reason) => {
    console.error('[FATAL] Unhandled rejection:', reason);
});
```

These only log the error/reason object, not `process.env`. This is safe today. The
risk materialises the moment any APM SDK is `npm install`-ed, because many (Sentry
Node SDK, Datadog APM, New Relic) capture `process.env` as part of their crash
context by default.

### 4. Deployment uses Render secret injection (`render.yaml` line 37–38)

```yaml
- key: SOLANA_KEYPAIR_JSON
  sync: false
```

`sync: false` prevents the value from being stored in the render.yaml committed to
source control, which is correct. However, once injected, the value lives in
`process.env` for the entire process lifetime without any clearing.

### 5. No existing code to clear the env var

Confirmed by full-repo grep: the string `delete process.env.SOLANA_KEYPAIR_JSON` does
not appear anywhere in the codebase. The `SOLANA_KEYPAIR_PATH` alternative is also
never deleted, though it is lower-risk (it exposes a file path, not the key itself).

## Root Cause

`initKeys()` in `keys.js` reads `SOLANA_KEYPAIR_JSON`, constructs the keypair, and
zeros the intermediate byte array (good), but omits the symmetrical step of deleting
the source env var. Because `process.env` is a global, mutable namespace readable
from any module at any time, the private key remains accessible for the full process
lifetime after the keypair is loaded.

## Impact

- **If an APM/crash-reporter SDK is added** without explicit env-var filtering, the
  full 64-byte private key is captured and transmitted to the APM vendor's cloud
  infrastructure on the first unhandled exception or periodic environment snapshot.
- **Render log streaming**: if a developer ever adds `console.log(process.env)` for
  debugging (common during outage triage), the key appears in Render's log drain.
- **Node.js `--inspect` / `--inspect-brk`**: attaching a debugger to the production
  process allows inspection of `process.env`, exposing the key interactively.
- The escrow authority keypair controls match settlement. Compromise allows an attacker
  to settle all active escrow accounts to arbitrary winner addresses, draining the
  entire wager pool.

## Recommendation

**Primary fix — delete the env var immediately after reading (one line):**

```js
// keys.js — inside initKeys(), after keypairJson is parsed
if (keypairJson) {
    secretKeyArray = JSON.parse(keypairJson);
    delete process.env.SOLANA_KEYPAIR_JSON;   // ← add this line
}
```

This mirrors the existing KM-04 `bytes.fill(0)` hygiene and extends it to the source.

**Secondary fix — add `SOLANA_KEYPAIR_JSON` to pino redact paths as a defensive measure:**

```js
redact: {
    paths: [
        // existing paths ...
        'SOLANA_KEYPAIR_JSON',   // guard against accidental env log dumps
    ],
}
```

Note: pino redaction only protects structured log calls where the key appears as a
field name in the log object. It does not protect against `process.env` being passed
directly or against external APM environment capture.

**Tertiary — document APM onboarding requirement:**

Add a note to deployment/ops documentation that any APM SDK must be configured with
an env-var denylist including `SOLANA_KEYPAIR_JSON`, `ADMIN_API_KEY`, `JWT_SECRET`,
and `MONGODB_URI` before being enabled in production.
