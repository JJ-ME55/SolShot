# H017 — giveTurn Unauthorized Turn Relay Attack

**Status:** CONFIRMED (Partially Mitigated — Critical Attack Vector Neutralized by Client Change, Server Exposure Remains)
**Severity:** MEDIUM (downgraded from hypothesized CRITICAL — see Analysis section)
**Confidence:** HIGH
**Origin:** AUTH-03 / API-03 — Unauthorized state mutation via relay event
**Date:** 2026-02-23

---

## Summary

The `giveTurn` socket event handler on the server has **zero authorization controls**: no `requireAuth` check, no turn-ownership check, no match-state guard, and no size validation on the relayed `terrainData` field. Any socket in a room — including unauthenticated sockets in free rooms — can emit `giveTurn` with arbitrary payloads and the server will relay them to the opponent verbatim.

However, the **actual game impact is substantially reduced** because the canonical client has been updated to no longer listen for the `recieveTurn` event for any gameplay-authoritative logic. Turns are now driven entirely by `turnResult.nextTurn` (server-authoritative). The `giveTurn` pathway is therefore a dead relay in the current client.

The residual risks are:
1. **Unbounded `terrainData` amplification** — a player can relay arbitrarily large objects to their opponent at 30 events/second, up to the 1 MB Socket.IO default.
2. **Dead server code surface** — the handler remains armed and will process any `giveTurn` event from any socket in any room, representing ongoing attack surface that could be activated by a custom client.
3. **Legacy relay still in `match.js` VALID_ACTIONS** — `giveTurn` is explicitly listed as a permitted BATTLE-state action in the state machine, providing a false signal that it is an active and intended game mechanic.

## Evidence

### 1. The handler — no auth, no state guard, unbounded relay

**File:** `server/socket-io/main.js`, lines 2478–2483

```js
// LEGACY: turn relay (still works)
client.on('giveTurn', (data) => {
    if (!data || typeof data !== 'object') return
    const { terrainData, pos1, pos2, rotation1, rotation2 } = data
    client.to(client.roomId).emit('recieveTurn', {terrainData, pos1, pos2, rotation1, rotation2})
})
```

**Missing controls (compared to neighboring handlers):**

| Control | `stepLeft` (line 2409) | `fire` (line ~1830) | `giveTurn` (line 2479) |
|---------|----------------------|---------------------|------------------------|
| `requireAuth` | YES | YES (inline) | **NO** |
| `validateAction` state guard | YES | YES | **NO** |
| Turn ownership check | YES (`ms.currentTurn !== client.id`) | YES | **NO** |
| Payload size cap | N/A (no payload) | YES (`validateFireParams`) | **NO** |

The handler's own inline comment acknowledges it is legacy (`// LEGACY: turn relay (still works)`), yet it carries no guards and is not blocked.

### 2. `terrainData` is relayed without any size limit

The `terrainData` field from the client payload is extracted and re-emitted directly to the opponent socket. The Socket.IO server has no `maxHttpBufferSize` configured in `server/index.js` (confirmed by API-03 auditor finding WS-06), so the default 1 MB limit applies. An attacker can send a `terrainData` payload approaching 1 MB at the global rate limit of 30 events/second, causing the server to allocate and forward up to ~30 MB/second of traffic to the victim socket.

**File:** `server/index.js`, lines 31–36 (no `maxHttpBufferSize` key present):

```js
const io = new socket.Server(server, {
    cors: {
        origin: CORS_ORIGINS,
        methods: ["GET", "POST"]
    }
})
```

### 3. `giveTurn` is listed as a valid BATTLE-state action in the state machine

**File:** `server/services/match.js`, line 66:

```js
[MATCH_STATES.BATTLE]: ['fire', 'move', 'angleChange', 'powerChange', 'weaponChange',
                         'stepLeft', 'stepRight', 'giveTurn', 'requestTurn', 'shoot'],
```

`giveTurn` appears alongside `fire` and `stepLeft` as an explicitly sanctioned BATTLE action. This is misleading because the `giveTurn` handler itself does **not** call `validateAction`, so this entry has no practical effect on the handler's execution — but it signals to future developers that `giveTurn` is an active mechanic, discouraging its removal.

### 4. The `recieveTurn` event is no longer processed by the canonical client

**File:** `client/src/scenes/main/index.js`, line 143:

```js
// Legacy turn relay handlers (recieveTurn, opponentRequestTurn) REMOVED.
// Turns are now managed server-side via turnResult.nextTurn.
```

Turn assignment is now driven exclusively by `turnResult.nextTurn` from server-authoritative fire physics resolution:

**File:** `client/src/scenes/main/index.js`, lines 604–613:

```js
const isMyTurn = (nextTurn === socket.id);
if (isMyTurn) {
    this.tank1.active = true;
    this.activeTank = 1;
    this.tank1.movesRemaining = 4;
} else {
    this.tank1.active = false;
    this.activeTank = 2;
    this.tank2.movesRemaining = 4;
}
```

The `activeTank` value (which controls which player can fire) is set only via `terrainGenerated.firstTurn` and `turnResult.nextTurn` — both of which are server-generated and contain the socket ID of the authorized turn holder. There is no code path in the current client where `recieveTurn` payload fields influence `activeTank` or enable firing.

### 5. Server-side turn ownership is fully enforced on `fire`

**File:** `server/socket-io/main.js`, lines 1843–1847:

```js
// Validate it's this player's turn
if (ms.currentTurn && ms.currentTurn !== this.id) {
    this.emit('fireRejected', { reason: 'Not your turn' })
    return
}
```

`ms.currentTurn` is set only by `getNextTurn()` (called from the `fire` result handler and `requestTerrain`), the turn timer expiry path, and `rejoinRoom`. The `giveTurn` handler does **not** mutate `ms.currentTurn`. This means that even if a custom client listens to `recieveTurn` and attempts to fire out of turn, the server-side ownership check will reject the `fire` event regardless.

## Attack Scenarios

### Scenario A — Turn-Steal Attack (NEUTRALIZED against canonical client)

**Hypothetical:** Attacker sends `giveTurn` with a fabricated payload hoping the opponent's client will believe it is the attacker's turn, allowing the attacker to fire twice in a row.

**Reality:** The canonical client does not register any `recieveTurn` listener. Turn assignment comes only from `turnResult.nextTurn` (server-generated). Even if a victim client receives the `recieveTurn` event, it is silently discarded. Furthermore, even if a modified client processed it, the server's `fire` handler enforces `ms.currentTurn !== this.id` and would reject the out-of-turn fire.

**Verdict:** Neutralized for canonical client. A victim running a non-standard or outdated client build that still listens to `recieveTurn` could experience UI-level turn confusion but could not lose funds because the server rejects unauthorized fires at the `fire` handler level.

### Scenario B — Targeted Bandwidth Exhaustion Against Opponent (ACTIVE)

**Attack steps:**
1. Attacker joins any room (authentication not required for free rooms where `joinRoom` wager is 0; in wagered rooms, attacker is an authenticated participant).
2. In a loop at the global rate limit of 30 events/second, attacker emits `giveTurn` with a near-maximum `terrainData` payload (~900 KB string).
3. The server extracts and re-emits `terrainData` to the opponent socket with no truncation or validation.
4. The opponent receives up to approximately 30 × 900 KB = ~27 MB/second of inbound WebSocket frames.

**Impact:** Targeted bandwidth exhaustion against a specific in-match opponent. In a wagered match, a losing player could use this to force-disconnect the winning opponent before the match resolves, potentially disrupting settlement. The turn timer's 3-consecutive-timeout forfeit rule (line 309) would eventually settle the match in the attacker's favor if the victim appears to disconnect.

**Mitigations present:** The 30 events/second global rate limit caps the event rate. The 1 MB Socket.IO frame default caps per-event size. The escalating disconnect (90 events/5 seconds) would eventually disconnect the attacker too, but not before significant traffic has been relayed.

### Scenario C — Opponent UI Disruption via Position/Rotation Fields (LOW RISK)

The `pos1`, `pos2`, `rotation1`, `rotation2` fields are relayed alongside `terrainData`. Historical versions of the client used these to update the opponent tank's visual position without server validation. This path is fully dead in the current canonical client.

## Root Cause

The `giveTurn` handler is a legacy relay that predates server-authoritative turn management. It was never updated with authorization guards when the rest of the turn-management infrastructure was hardened. The comment `// LEGACY: turn relay (still works)` confirms developer awareness that it is obsolete, but the handler was not deleted or guarded.

The fix for client-side turn management (removing `recieveTurn` listeners) was applied without the corresponding server-side cleanup (removing the `giveTurn` emission). The handler also escaped the authorization hardening pass that added `requireAuth` to `stepLeft`, `stepRight`, `requestTurn`, `playAgainRequest`, and the `fire` event — all handlers in the same code block.

Note: In `server/middleware/guards.js` the `Fixes: H017` annotation refers to `sanitizeName` (oversized player name broadcast), a different issue that reused this ID. The `giveTurn` authorization gap was catalogued separately in the AUTH-03 and API-03 context files.

## Recommendations

### P1 — Delete the handler entirely (preferred fix)

The handler is explicitly labeled legacy, the canonical client no longer processes `recieveTurn`, and there is no functional use case for it. Deletion is the safest and cleanest resolution.

**File:** `server/socket-io/main.js`, lines 2478–2483 — delete these lines entirely:

```js
// LEGACY: turn relay (still works)
client.on('giveTurn', (data) => {
    if (!data || typeof data !== 'object') return
    const { terrainData, pos1, pos2, rotation1, rotation2 } = data
    client.to(client.roomId).emit('recieveTurn', {terrainData, pos1, pos2, rotation1, rotation2})
})
```

### P2 — Remove `giveTurn` from `match.js` VALID_ACTIONS

**File:** `server/services/match.js`, line 66:

```js
// Before
[MATCH_STATES.BATTLE]: ['fire', 'move', 'angleChange', 'powerChange', 'weaponChange',
                         'stepLeft', 'stepRight', 'giveTurn', 'requestTurn', 'shoot'],

// After
[MATCH_STATES.BATTLE]: ['fire', 'move', 'angleChange', 'powerChange', 'weaponChange',
                         'stepLeft', 'stepRight', 'requestTurn', 'shoot'],
```

### P3 — Set `maxHttpBufferSize` on the Socket.IO server (mitigates Scenario B independently)

**File:** `server/index.js`, lines 31–36:

```js
const io = new socket.Server(server, {
    cors: { origin: CORS_ORIGINS, methods: ["GET", "POST"] },
    maxHttpBufferSize: 64 * 1024,  // 64 KB covers all legitimate payloads
})
```

This setting also mitigates the bandwidth amplification vector of other unauthenticated relay events (`weaponPick`, `weaponChange`, `angleChange`, `powerChange`).

### P4 — If the handler cannot be deleted immediately, add minimal guards

```js
client.on('giveTurn', (data) => {
    if (!requireAuth(client, 'giveTurn')) return
    if (!data || typeof data !== 'object') return
    if (!client.roomId) return
    const ms = matchStates[client.roomId]
    if (!ms || !validateAction(ms.status, 'giveTurn')) return
    // Only the current turn holder may relay
    if (ms.currentTurn && ms.currentTurn !== client.id) return
    // Drop terrainData entirely — terrain is server-generated via requestTerrain
    const { pos1, pos2, rotation1, rotation2 } = data
    if (![pos1, pos2, rotation1, rotation2].every(v => typeof v === 'number' && isFinite(v))) return
    client.to(client.roomId).emit('recieveTurn', { pos1, pos2, rotation1, rotation2 })
})
```
