# H019 — Room Join Capacity Overflow via Concurrent Joins

**Strategy ID:** H019
**Categories:** ERR-02 (Race Conditions), API-03 (WebSocket Security)
**Verdict:** CONFIRMED
**Severity:** MEDIUM (downgraded from Tier 1 CRITICAL — see Impact Assessment)
**File:** `server/socket-io/main.js`
**Lines:** 955–1093 (`joinRoom` handler)
**Date:** 2026-02-23

---

## Summary

The `joinRoom` handler reads `room.active` to enforce the one-player-per-room cap, but assigns `room.active = true` only AFTER one or two async yield points. Two concurrent join requests for the same room can both pass the `room.active === true` guard before either sets the flag, causing the second joiner to overwrite the first inside `room.player`. The room ends up with two sockets that believe they are `room.player`, but only the second socket's identity is recorded in the room object. The first socket's data is silently discarded.

---

## Evidence

### Capacity Check (Line 962) — No Sentinel Set Here

```js
// server/socket-io/main.js, lines 961-962
var room = findRoom(roomId)
if (!room || room.active === true) return
```

`room.active` is read here. At this point it is `false` (set during `createRoom` at line 1195: `active: false`). No sentinel, no lock, no flag is set to claim the slot at this point. The event loop is free to run another handler.

### First Async Yield Point — Wagered Rooms (Line 982)

```js
// server/socket-io/main.js, lines 980-992
try {
    const balanceCheck = await verifyBalance(joinerWallet, roomWager)
    if (!balanceCheck.sufficient) {
        client.emit('joinRoomError', { ... })
        return
    }
} catch (err) {
    console.warn('[Solana] Balance check skipped:', err.message)
}
```

`verifyBalance` calls `getCachedLamports` which calls `conn.getBalance(pubkey)` — an HTTP RPC call via `@solana/web3.js`. This is a genuine async I/O operation. The call takes roughly 50–500 ms depending on RPC latency. During this entire window, the event loop is idle for this handler and can process any other incoming socket events — including a second `joinRoom` for the same `roomId` from a different socket.

`verifyBalance` implementation in `server/services/solana.js`, lines 122–143:
```js
export async function verifyBalance(walletAddress, wagerSOL) {
    try {
        const lamports = await getCachedLamports(walletAddress);  // HTTP RPC — yields here
        // ...
    }
}
```

### Second Async Yield Point — Any Room (Line 997)

```js
// server/socket-io/main.js, lines 995-998
if (client.roomId !== null) {
    client.leave(client.roomId)
    await removeRoom(client.roomId)  // MongoDB I/O — yields here
}
```

`removeRoom` at line 213 calls `Match.findByIdAndUpdate(...)` — a Mongoose/MongoDB async operation — if the room has a `_matchId`. This is a second yield point that exists even for free (non-wagered) rooms when the joining socket was previously in another room. The same race window applies here.

### Slot Assignment — After Both Yield Points (Lines 1012-1013)

```js
// server/socket-io/main.js, lines 1012-1013
room.player = {name: sanitizeName(name), color: color, socketId: client.id, isReady: false, playAgain: false}
room.active = true
```

`room.active = true` is set only here — after both yield points. No intermediate sentinel is set at line 962 or anywhere between the guard and the assignment.

### No Lock at the Join Site

```js
// grep: withLock usage in main.js
// Line 579:  await withLock(`settle:${roomId}`, async () => {   ← cleanupRoom/disconnect
// Line 2085: await withLock(`settle:${this.roomId}`, async () => { ← fire/match end
```

`withLock` is used exclusively for settlement. There is no `withLock('join:${roomId}', ...)` or equivalent for the join handler. No sentinel flag (such as `room._joining = true`) is set before the first yield.

## Impact Assessment

### What Actually Happens (Not a 3-Player Room)

The hypothesis posited "3 players in a 2-player room." The actual outcome is different and in some ways less severe, in other ways more confusing:

- `room.player` is a single object reference, not an array. The second write at line 1012 **overwrites** the first — the room contains exactly 2 socket references (host + the last writer to `room.player`).
- The first joiner's socket has `client.roomId = roomId` set (line 1001) and has joined the Socket.IO room channel (line 1000). It will receive all room broadcasts (e.g., `startPick`, `terrainGenerated`, `turnResult`) because it is subscribed to the Socket.IO room.
- However, `room.player.socketId` points to the **second** joiner. Game logic that resolves player identities via `room.player.socketId` will address the second joiner; the first joiner's socket is effectively a ghost — it receives broadcasts but the server does not recognize its socket ID as a valid player slot.
- The first joiner's `client.roomId` is set, so their `disconnect` handler will fire `cleanupRoom` referencing this room — potentially corrupting or cancelling a live match.

### Wagered Match Consequences

For a wagered room (wager > 0), the escrow path at line 1021 runs ONCE per `joinRoom` invocation, not once per room. If both handlers complete, escrow is created **twice** for the same `roomId` — two `createMatchEscrow` calls with the same `roomId` PDA seed. The second Anchor CPI will fail (PDA already initialized), and the server logs `[Match] Escrow creation failed`. The match proceeds without an escrow for the second invocation's data path.

The deposit transactions emitted at lines 1041–1057 are sent to both sockets independently. The first joiner receives a deposit request and may sign and send to chain. When they send `escrowDepositConfirm`, `room.player.socketId` does not match `client.id`, so `ws.deposits[client.id]` is written but the `hostDeposited && playerDeposited` check at line 1785 will never complete — the expected `room.player.socketId` is the second joiner's ID. This can result in a deposit timeout cancel despite a legitimate on-chain deposit, causing the depositing player to lose access to the refund flow without the 48h Anchor reclaim.

### Severity Justification: MEDIUM

The original Tier 1 (CRITICAL) estimate was based on the hypothesis of "3 players in a room." The actual mechanics are an **overwrite race**, not an additive one. The result is:

- Match integrity: HIGH concern — the ghost socket receives all game events and can still emit relay events (weaponPick, giveTurn, etc.) that affect the opponent.
- Financial impact: MEDIUM — escrow double-creation fails gracefully on-chain, but the first joiner's deposit is at risk of the timeout cancel path.
- Denial of service: MEDIUM — the ghost socket's eventual disconnect triggers room cleanup, which could cancel an in-progress match.
- Exploit reliability: MEDIUM — requires precise timing or network conditions (race window is 50–500ms for wagered rooms, potentially sub-ms for free rooms with MongoDB I/O).

This aligns with ERR-02 context document rating of RC-05 as **MEDIUM**.

## Exploit Scenario

### Scenario 1: Wagered Room Disruption

1. Attacker observes a room ID via `broadcastRooms` / `getRooms` (both are unauthenticated read events). Room is open with `room.active === false`.
2. Attacker controls two sockets (or uses a single client that sends two rapid `joinRoom` frames before the first is processed — feasible because Socket.IO can have multiple events queued before the event loop processes them).
3. Both `joinRoom` handlers pass the `room.active === true` guard at line 962.
4. Both call `await verifyBalance(...)` — both yield. Whichever completes second will overwrite `room.player`.
5. The first joiner (whose data was overwritten) still receives `startPick` and all game events via the Socket.IO room channel. This socket can now influence the match through unauthenticated relay events (`weaponPick`, `angleChange`, `powerChange`, `giveTurn`) without being recognised as a legitimate player.
6. If the attacker's first socket deposited into escrow and was then overwritten, the deposit confirmation will stall and timeout, triggering `cancelMatchEscrow` — potentially cancelling the match and stranding the legitimate player's deposit in the 48h Anchor reclaim window.

### Scenario 2: Free Room Ghost Injection

1. Attacker creates two sockets, both previously in other rooms (so `client.roomId !== null` for each).
2. Both send `joinRoom` for the same free room simultaneously.
3. For free rooms, `roomWager === 0` so there is no `verifyBalance` await — but if `client.roomId !== null`, there is an `await removeRoom(client.roomId)` at line 997.
4. Both pass the capacity guard, both yield at `await removeRoom(...)`. Whichever `removeRoom` finishes last has its socket overwrite `room.player`.
5. The overwritten socket is a ghost in the Socket.IO room. It can emit relay events to the opponent without the server recognizing it as a slot holder.

## Recommendations

### Fix 1 — Synchronous Sentinel Before First Yield (Minimal, Correct)

Set `room.active = true` **synchronously immediately after the capacity check**, before any `await`. This claims the slot atomically within a single event-loop tick.

```js
// server/socket-io/main.js — joinRoom handler

var room = findRoom(roomId)
if (!room || room.active === true) return

// CLAIM THE SLOT IMMEDIATELY — prevents concurrent joinRoom from passing guard
room.active = true   // ← add this line here, before any await

// ... balance check, removeRoom, etc. ...

// At line 1012 — keep the player assignment, remove the redundant active = true
room.player = { name: sanitizeName(name), color: color, socketId: client.id, isReady: false, playAgain: false }
// room.active = true ← remove or leave (idempotent now)
```

If the balance check subsequently fails or any other guard rejects the join, reset the flag:

```js
try {
    const balanceCheck = await verifyBalance(joinerWallet, roomWager)
    if (!balanceCheck.sufficient) {
        room.active = false  // ← release the slot
        client.emit('joinRoomError', { ... })
        return
    }
} catch (err) {
    // On RPC error, the slot remains claimed (conservative) OR:
    room.active = false  // ← release if you want fail-open behavior
    console.warn('[Solana] Balance check skipped:', err.message)
}
```

This is the same pattern recommended in ERR-02 context document RC-05 recommendation (P1, item 4).

### Fix 2 — Per-Room Join Lock (Robust)

Use `withLock` (already imported at line 15) around the entire join critical section:

```js
await withLock(`join:${roomId}`, async () => {
    var room = findRoom(roomId)
    if (!room || room.active === true) return

    // ... all join logic including verifyBalance ...

    room.player = { ... }
    room.active = true
})
```

This is more defensive but serialises all joins to the same room. Given a room can only have one joiner, contention will be rare, and the lock will be short-lived.

### Fix 3 — Re-check After Yield (Defense in Depth)

After each `await`, re-validate that the room slot is still available:

```js
const balanceCheck = await verifyBalance(joinerWallet, roomWager)
// Re-check room state after async yield
const roomAfterBalanceCheck = findRoom(roomId)
if (!roomAfterBalanceCheck || roomAfterBalanceCheck.active === true) {
    client.emit('joinRoomError', { reason: 'Room is no longer available' })
    return
}
```

This does not fully close the window (two handlers can still pass both checks if interleaved symmetrically) but provides a meaningful reduction in the race window without requiring a sentinel flag.
