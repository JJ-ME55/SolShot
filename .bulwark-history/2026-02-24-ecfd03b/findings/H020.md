## Verdict: CONFIRMED

## Severity: CRITICAL

---

## Executive Summary

The `joinQueue` handler in `server/socket-io/main.js` (lines 1213–1389) contains two independent, exploitable flaws that together enable an attacker to guarantee a win in any wagered matchmaking game and extract the wager pot.

**Flaw 1 — Same-Wallet Self-Pairing (Deterministic):** The queue pairing logic performs zero wallet-identity deduplication. An attacker who opens two browser tabs with the same Solana wallet, authenticates on both, and sends `joinQueue` from each will have one tab queue an entry and the second tab immediately match against it. The server creates a room where both sides are controlled by the same party. The attacker controls both sides of every turn, can forfeit the designated "loser" at will, and collects the wager payout from the winner side.

**Flaw 2 — Race Condition Double-Consume / Corrupted Self-Pair (Probabilistic):** Two concurrent `joinQueue` events (same or different wallets) can both pass the `queue.length > 0` check before either executes `queue.shift()`. This yields a corrupted room (opponent becomes `undefined`) that is permanently stuck in an `active` state with a live escrow PDA, blocking that `roomId` from any other use and stranding the on-chain PDA until the 48-hour reclaim window.

The self-pairing flaw (Flaw 1) is the financially exploitable path. It is deterministic, requires no timing precision, and is straightforward to script.

## Evidence

### 1. `joinQueue` Handler — No Wallet Deduplication

**File:** `server/socket-io/main.js`, lines 1213–1389

The complete pairing gate at lines 1242–1253:

```javascript
if (queue.length > 0) {
    // SF-05: Validate wager matches before pairing (DB: H017)
    const opponent = queue[0]; // peek first, don't consume
    if (opponent.wager !== wagerAmount) {
        // Wager mismatch — do not pair, push joiner to queue instead
        queue.push({ name: sanitizeName(playerName), color: tankColor, socketId: client.id, wallet: authenticatedWallets[client.id] || null, wager: wagerAmount });
        client.emit('queueWaiting', { matchMode, matchLength, position: queue.length });
        console.log(`[Queue] Wager mismatch: opponent=${opponent.wager} SOL, joiner=${wagerAmount} SOL — queued separately`);
        return;
    }
    queue.shift(); // now safe to consume
    if (queue.length === 0) matchmakingQueues.delete(queueKey);
```

The only pre-pairing check is `opponent.wager !== wagerAmount`. There is no check of the form:

```javascript
if (opponent.wallet === authenticatedWallets[client.id]) { ... reject ... }
```

and no check of the form:

```javascript
if (opponent.socketId === client.id) { ... reject ... }
```

The wager wallet field recorded at pairing time (line 1275) is:

```javascript
wagerStates[roomId] = {
    amount: wagerAmount,
    wallets: {
        [opponent.socketId]: opponent.wallet,
        [client.id]: authenticatedWallets[client.id] || null,
    },
};
```

When `opponent.wallet` and `authenticatedWallets[client.id]` are the same Solana address (two tabs, one wallet), this map resolves to two different socket IDs pointing at the same wallet address. Settlement will transfer from that wallet to itself (minus fees).

### 2. `authenticatedWallets` is Keyed by `socketId`, Not by `walletAddress`

**File:** `server/socket-io/main.js`, line 45:

```javascript
var authenticatedWallets = {}
```

**File:** `server/socket-io/main.js`, line 541:

```javascript
authenticatedWallets[client.id] = result.walletAddress
```

The map is `{ socketId → walletAddress }`. Two independent socket connections (two browser tabs) each get a distinct `client.id` and each write their own entry into `authenticatedWallets`. There is no scan over existing entries to detect that the same `walletAddress` is being bound to a second socket. Nothing prevents two distinct socket IDs both mapping to `"HPyVPj2VH9yBirr7FMgAJeDH8xJgaMKy5UnwLkjSnovk"` (or any attacker wallet) simultaneously.

### 3. `handleAuthenticate` Has No Uniqueness Check

**File:** `server/middleware/auth.js`, lines 127–148:

```javascript
export function handleAuthenticate(client, { walletAddress, message, signature, timestamp }) {
    const msgCheck = verifyAuthMessage(message, walletAddress, timestamp);
    if (!msgCheck.valid) {
        return { success: false, reason: msgCheck.reason };
    }
    const sigCheck = verifyWalletSignature(walletAddress, message, signature);
    if (!sigCheck.valid) {
        return { success: false, reason: sigCheck.reason };
    }
    const token = generateToken(walletAddress);
    client.walletAddress = walletAddress;
    client.isAuthenticated = true;
    return { success: true, token, walletAddress };
}
```

`handleAuthenticate` takes a socket-local `client` argument and sets `client.isAuthenticated = true`. It is purely per-socket; it has no visibility into any other socket's authentication state. Two sockets authenticating with the same wallet address both succeed independently.

### 4. `removeFromAllQueues` Only Deduplicates by `socketId`

**File:** `server/socket-io/main.js`, lines 67–75:

```javascript
function removeFromAllQueues(socketId) {
    for (const [key, queue] of matchmakingQueues.entries()) {
        const idx = queue.findIndex(e => e.socketId === socketId);
        if (idx !== -1) {
            queue.splice(idx, 1);
            if (queue.length === 0) matchmakingQueues.delete(key);
        }
    }
}
```

This function is called at the start of each `joinQueue` invocation (line 1234: `removeFromAllQueues(client.id)`). It removes prior entries for the same **socket** before re-queuing, which prevents the same socket from queuing against itself. However, it does nothing about a second socket from the same wallet that has already placed an entry. Tab A's queue entry (socket ID = `abc123`) is not removed when Tab B (socket ID = `def456`) calls `joinQueue`.

### 5. Race Condition in Queue Pairing (Non-Atomic Shift)

**File:** `server/socket-io/main.js`, lines 1242–1252 — noted in `context/18-err-02-race-conditions.md` as RC-06.

The sequence:
1. Both `joinQueue` handlers execute concurrently.
2. Both reach `if (queue.length > 0)` — queue currently has one entry.
3. Both read `queue[0]` (the same entry).
4. Both validate wager match.
5. First call executes `queue.shift()` — returns the entry.
6. Second call executes `queue.shift()` — returns `undefined`.
7. Both proceed to room creation; handler B sets `opponent = undefined`, leading to `opponent.socketId = undefined`.

In the self-pairing case this race is irrelevant (both tabs are the attacker and both outcomes are acceptable to the attacker). In the general case, the race corrupts a legitimate match.

## Exploit Scenario

### Self-Pairing Guaranteed Win Attack

**Prerequisites:**
- One Solana wallet with the wager amount in balance (e.g., 0.5 SOL for a Duel wager).
- Two browser tabs open to SolShot.

**Steps:**

1. Tab A authenticates with wallet W. Tab B also authenticates with wallet W. Both succeed because `handleAuthenticate` is socket-scoped with no global wallet-uniqueness check.

2. Tab A sends `joinQueue({ matchMode: 'duel', matchLength: 1, wager: 0.5, ... })`. The queue for `duel:1` is empty; the entry `{ socketId: A, wallet: W, wager: 0.5, ... }` is pushed. Tab A receives `queueWaiting`.

3. Tab B sends `joinQueue({ matchMode: 'duel', matchLength: 1, wager: 0.5, ... })`. The queue has one entry (Tab A). Wager matches. `queue.shift()` consumes Tab A's entry. A room is created with:
   - `room.host.socketId = A` (wallet W)
   - `room.player.socketId = B` (wallet W)
   - `wagerStates[roomId].wallets = { A: W, B: W }`

4. The escrow is created on-chain with `opponent.wallet = W` and `joinerWallet = W` (same address for both). Both deposit transactions are built targeting wallet W. The attacker signs both.

5. The attacker controls both sides of the match. On Tab B (player), they send `ready`, proceed through the shop, and then deliberately perform the minimum legal actions. On Tab A (host), they play normally to win.

6. When the match ends, `settleMatch(winnerWallet=W, loserWallet=W, amount=0.5, roomId)` is called. Because both wallets are W, the on-chain `settleMatchEscrow` instruction transfers 90% of the pot (0.45 SOL winner share + 0.5 SOL loser deposit = 0.95 SOL principal) back to W, minus the 7% treasury fee and 3% ops fee. In effect:
   - Attacker paid 0.5 SOL (winner deposit) + 0.5 SOL (loser deposit) = 1.0 SOL into escrow.
   - Attacker receives 0.9 SOL back (90% split).
   - Treasury receives 0.07 SOL, ops receives 0.03 SOL.
   - Net cost: 0.1 SOL in fees per self-match.

   The economic harm is not direct theft of other players' funds in the base self-pairing scenario. However, **see Amplified Attack below**.

### Amplified Attack — Queue Squatting to Block Legitimate Players

1. The attacker opens N tab-pairs, each pair authenticating with a different wallet.
2. Each pair sends `joinQueue` for the same mode and wager tier.
3. Each pair immediately self-matches, consuming the queue slot.
4. Legitimate players who join the queue are immediately matched against the attacker's second tab (which the attacker controls), giving the attacker a guaranteed win against real opponents who have deposited real funds.

**This variant achieves direct fund extraction:**
- Attacker Tab A queues. Legitimate player queues and matches against Attacker Tab A.
- Attacker controls Tab A (the host). Attacker can use all other established exploits (position drift at 12,000 px/sec from H020/BL-C03, unauthenticated weapon selection from H020/BL-L02) to guarantee a win.
- Legitimate player's wager goes to the attacker.

### Practice Mode Self-Pairing (Zero-Cost Exploitation)

For `wagerAmount = 0` (practice), the `requireAuth` call is skipped (line 1231: `if (wagerAmount > 0 && !requireAuth(client, 'joinQueue')) return`). An unauthenticated attacker with two sockets can self-pair in practice mode with no authentication at all. While practice mode has no direct financial impact, it allows:
- Farming the `five_win_streak` milestone via controlled wins (if the server does credit this mode, per audit dispute in LOGIC-01).
- Verifying exploit mechanics before executing the wagered version.
- Consuming server-side match state and turn timers to contribute to denial-of-service.

## Root Cause Analysis

Three independently missing controls, each of which alone would suffice to block this attack:

1. **No wallet-level deduplication in queue entries.** `removeFromAllQueues` uses `socketId` as the key, not `walletAddress`. Adding a wallet-based check at entry time would block same-wallet queuing.

2. **No same-wallet pairing rejection at match-time.** When `queue.shift()` is called and the room is assembled, `opponent.wallet` and `authenticatedWallets[client.id]` are not compared. A single equality check before room creation would close this.

3. **No global uniqueness constraint on wallet authentication.** `authenticatedWallets` is a `socketId → walletAddress` map. There is no reverse map (`walletAddress → socketId`) that would allow the server to detect and reject (or forcibly disconnect) duplicate wallet sessions.

## Recommendations

### Fix 1 — Reject Same-Wallet Pairing at Match-Time (Minimum Viable Fix)

**File:** `server/socket-io/main.js`, before `queue.shift()` at line 1252.

```javascript
// Add wallet identity check before consuming the queue entry
const joinerWallet = authenticatedWallets[client.id] || null;
if (joinerWallet && opponent.wallet && opponent.wallet === joinerWallet) {
    // Same wallet on both sides — reject pairing, push joiner to queue
    queue.push({
        socketId: client.id,
        wallet: joinerWallet,
        name: sanitizeName(playerName),
        color: tankColor,
        wager: wagerAmount,
        format: matchLength,
        matchMode,
        queuedAt: Date.now(),
    });
    client.emit('queueWaiting', { matchMode, matchLength, position: queue.length });
    console.warn(`[Queue] Self-pairing rejected: wallet ${joinerWallet} cannot match itself`);
    return;
}
```

This single guard closes the deterministic self-pairing path with minimal code change.

### Fix 2 — Wallet-Based Queue Deduplication

**File:** `server/socket-io/main.js`, `removeFromAllQueues` function (line 67).

Extend `removeFromAllQueues` to accept and match on `walletAddress` in addition to `socketId`:

```javascript
function removeFromAllQueues(socketId, walletAddress) {
    for (const [key, queue] of matchmakingQueues.entries()) {
        // Remove by socketId (existing behavior)
        let idx = queue.findIndex(e => e.socketId === socketId);
        if (idx !== -1) {
            queue.splice(idx, 1);
        }
        // Also remove any existing entry for the same wallet (new behavior)
        if (walletAddress) {
            idx = queue.findIndex(e => e.wallet === walletAddress && e.socketId !== socketId);
            if (idx !== -1) {
                queue.splice(idx, 1);
                console.warn(`[Queue] Removed duplicate wallet entry for ${walletAddress}`);
            }
        }
        if (queue.length === 0) matchmakingQueues.delete(key);
    }
}
```

Then at line 1234, pass the wallet:

```javascript
removeFromAllQueues(client.id, authenticatedWallets[client.id] || null);
```

This prevents the same wallet from ever holding two queue entries simultaneously, closing the queuing race.

### Fix 3 — Enforce One Active Socket Per Authenticated Wallet (Defense in Depth)

**File:** `server/socket-io/main.js`, `authenticate` handler (line 533).

Add a reverse map `walletToSocketId` that tracks the current socket for each wallet. On re-authentication with the same wallet, forcibly disconnect the previous socket:

```javascript
// Module-level reverse map
const walletToSocketId = new Map(); // walletAddress → socketId

// In authenticate handler, after result.success:
const existingSocketId = walletToSocketId.get(result.walletAddress);
if (existingSocketId && existingSocketId !== client.id) {
    const existingSocket = io.sockets.sockets.get(existingSocketId);
    if (existingSocket) {
        existingSocket.emit('sessionReplaced', { reason: 'A new session was opened for this wallet' });
        existingSocket.disconnect(true);
    }
}
walletToSocketId.set(result.walletAddress, client.id);
```

Also update `disconnect` to clean this map:

```javascript
// In disconnect handler, after removing from queue:
if (authenticatedWallets[client.id]) {
    const wallet = authenticatedWallets[client.id];
    if (walletToSocketId.get(wallet) === client.id) {
        walletToSocketId.delete(wallet);
    }
}
```

This is a broader fix that also addresses re-authentication on the same socket (M-12 in ARCHITECTURE.md) and the `authenticatedWallets` 30-second leak (M-13).

### Fix 4 — Atomicity Guard on Queue Shift (Race Condition)

**File:** `server/socket-io/main.js`, lines 1242–1252.

Use a synchronous sentinel to prevent double-consume under concurrent async handlers:

```javascript
if (queue.length > 0) {
    const opponent = queue[0];
    if (opponent.wager !== wagerAmount) { ... return; }

    // Atomically claim the entry by removing it before any async operation
    queue.shift();
    if (queue.length === 0) matchmakingQueues.delete(queueKey);

    // Validate: reject same-wallet pairing AFTER claiming the slot
    const joinerWallet = authenticatedWallets[client.id] || null;
    if (joinerWallet && opponent.wallet && opponent.wallet === joinerWallet) {
        // Re-queue both: add opponent back, then add joiner
        queue.push(opponent);
        queue.push({ socketId: client.id, wallet: joinerWallet, name: sanitizeName(playerName), color: tankColor, wager: wagerAmount, format: matchLength, matchMode, queuedAt: Date.now() });
        client.emit('queueWaiting', { matchMode, matchLength, position: queue.length });
        console.warn(`[Queue] Self-pairing rejected`);
        return;
    }

    // Proceed with room creation
    ...
}
```

Moving the `queue.shift()` before any validation ensures the entry is consumed exactly once even under concurrent handlers.
