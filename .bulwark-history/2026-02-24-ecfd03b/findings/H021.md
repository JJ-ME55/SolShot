# H021 — Reconnect State Migration Duplication

**Strategy:** H021
**Category:** ERR-02 (Race Conditions) / AUTH-01 (Authentication)
**Verdict:** NOT VULNERABLE (in the nominal dual-reconnect scenario) / POTENTIAL (in the timer-race sub-scenario)
**Severity:** LOW–MEDIUM (see sub-scenarios below)
**Estimated Priority:** Tier 3 (downgraded from hypothesised Tier 1)
**Investigator:** Dinh's Bulwark — H021
**Date:** 2026-02-23

---

## Summary

The hypothesis is that two rapid `rejoinRoom` emissions from the same wallet can both find
`pendingReconnects[wallet]` populated, both proceed through state migration, and corrupt or duplicate
match state. After full code tracing, the **primary hypothesis is NOT CONFIRMED** in its strongest form:
the code deletes `pendingReconnects[walletAddress]` at line 826 before any `await` is reached, and both
`verifyAuthMessage` and `verifyWalletSignature` are fully synchronous (no yield points). As a result, the
second of two simultaneous `rejoinRoom` events will reach line 805 after the first has already deleted the
entry and will receive `rejoinError: No active match to rejoin`.

However, two **weaker but real** race conditions in the same code path are confirmed:

1. **POTENTIAL** — Timer-fires-during-migration: the `disconnectTimers` entry is cleared at line 822–824
   **after** `pendingReconnects` is read at line 805. If the 30-second timer fires between those two
   lines, `cleanupRoom` runs concurrently with the migration, destroying the room state that the
   `rejoinRoom` handler is in the middle of writing.

2. **POTENTIAL** — Stale `oldSocketId` in the migration: the migration block re-uses `oldSocketId` from
   the `pending` snapshot captured before migration began. If a prior successful reconnect had already
   advanced `room.host.socketId` or `room.player.socketId` to a different ID (e.g., via a race between
   the first reconnect's migration and the second's read at line 811–812), the migration will try to
   remap a socket ID that no longer exists in the state stores, silently leaving the state half-migrated.

## Investigation

### Step 1 — Identify all yield points in `rejoinRoom`

The `rejoinRoom` handler (lines 776–924) is declared `async`. Yield points (suspension via `await`) are
where a second concurrent invocation can interleave. The full handler was traced for `await` keywords:

| Line range | Operation | Synchronous? |
|------------|-----------|-------------|
| 792 | `verifyAuthMessage(...)` | YES — pure computation, no await |
| 799 | `verifyWalletSignature(...)` | YES — NaCl in-process, no await |
| 805 | `pendingReconnects[walletAddress]` read | YES — plain property access |
| 815 | `findRoom(roomId)` / `matchStates[roomId]` | YES — Map/object lookup |
| 822–826 | Timer clear + `delete pendingReconnects[wallet]` | YES — synchronous |
| 829 | `client.join(roomId)` | YES — in-memory adapter `addAll()` is synchronous (confirmed in `socket.io-adapter/dist/index.js` lines 41–56: no Promise returned, pure Set mutations) |
| 836–888 | All state store migrations | YES — synchronous object property reads and writes |
| 896, 900 | `emit(...)` calls | YES — synchronous in Socket.IO 4.x (queued; not awaited) |

**Finding:** There is NO `await` anywhere in the handler after the initial signature checks. The entire
`pendingReconnects` check, timer cancellation, deletion, and all state migration is synchronous within a
single Node.js event loop tick. Once a `rejoinRoom` handler begins executing past line 803 (after
`sigCheck` returns), it runs to completion without yielding to the event loop.

### Step 2 — Trace the dual-reconnect scenario

**Scenario:** Wallet `W` disconnects from socket `S_old`. Within the 30s window, two rapid `rejoinRoom`
events arrive from two new sockets `S_1` and `S_2`.

**Event loop ordering (inevitable, because JS is single-threaded):**

```
Tick A: S_1 rejoinRoom handler starts
  - verifyAuthMessage(...) → valid (sync)
  - verifyWalletSignature(...) → valid (sync)
  - pendingReconnects["W"] → { roomId, isHost, oldSocketId: S_old, ... }   [LINE 805: FOUND]
  - delete pendingReconnects["W"]                                           [LINE 826: DELETED]
  - clearTimeout / delete disconnectTimers["W"]                            [LINES 822-824]
  - client.join(roomId)                                                     [LINE 829: SYNC]
  - All state migration: S_old → S_1.id                                    [LINES 839-889: SYNC]
  - emitReconnected, emitRejoinSuccess                                      [LINES 896-923: SYNC]
  --- handler completes ---

Tick B: S_2 rejoinRoom handler starts
  - verifyAuthMessage(...) → valid (sync)
  - verifyWalletSignature(...) → valid (sync)
  - pendingReconnects["W"] → undefined                                      [LINE 805: NOT FOUND]
  - client.emit('rejoinError', { reason: 'No active match to rejoin' })    [LINE 807: EMITTED]
  --- handler returns ---
```

The `delete pendingReconnects[walletAddress]` at line 826 is the effective guard. Since there is no
`await` between line 805 (read) and line 826 (delete), the guard is atomic within a single tick.
**The primary hypothesis is NOT CONFIRMED.**

### Step 3 — Identify the real race: timer fires during migration

The ERR-02 context report (RC-07, lines 265–278) identified this window, and code inspection confirms it.

**Precise window (lines 822 vs 805):**

```js
// Line 805
const pending = pendingReconnects[walletAddress]    // A: READ pending
if (!pending) { ... return }

const { roomId, isHost, oldSocketId, name, color } = pending  // B: DESTRUCTURE
const room = findRoom(roomId)                                   // C: room lookup
const ms = matchStates[roomId]                                  // D: ms lookup

if (!room || !ms) {
    delete pendingReconnects[walletAddress]          // E: delete on bad room
    client.emit('rejoinError', ...)
    return
}

// Line 822
if (disconnectTimers[walletAddress]) {
    clearTimeout(disconnectTimers[walletAddress])   // F: CLEAR TIMER
    delete disconnectTimers[walletAddress]
}
delete pendingReconnects[walletAddress]             // G: LINE 826
```

The `disconnectTimers` callback (set at line 737) fires after exactly 30,000 ms. It does:

```js
disconnectTimers[walletAddress] = setTimeout(async () => {
    delete pendingReconnects[walletAddress]      // Line 738
    delete disconnectTimers[walletAddress]       // Line 739
    ...
    await cleanupRoom(fakeClient, io, 'reconnect_timeout')  // Line 758
    delete authenticatedWallets[client.id]       // Line 759
}, RECONNECT_WINDOW_MS)
```

`cleanupRoom` calls `removeRoom(roomId)` which deletes `wagerStates[roomId]`, `goldStates[roomId]`,
`weaponInventories[roomId]`, `matchStates[roomId]`, and removes the room from the `rooms` Map.

**The race window:** If the `rejoinRoom` handler has completed step A (line 805: read `pending`,
confirmed non-null) and the 30-second timer fires between step A and step F (line 822: `clearTimeout`),
then:

1. The timer callback fires.
2. `delete pendingReconnects[walletAddress]` at line 738 runs (no-op for the value but the key is
   deleted from the object).
3. `await cleanupRoom(...)` runs — this is async and calls `removeRoom()`, which deletes all room state.
4. The `rejoinRoom` handler, which suspended at nothing (all sync) but the timer ran in between ticks,
   now proceeds through the migration at lines 839–888. However:
   - `findRoom(roomId)` at line 812 already returned the room object reference by value. The local `room`
     variable still holds the stale object reference.
   - `matchStates[roomId]` at line 813 already returned the stale `ms` reference.
   - The migration writes to `ws.wallets[client.id]` — but `wagerStates[roomId]` has been deleted by
     `removeRoom()`. `ws` was captured at line 841 as a local reference to the deleted object, so writes
     go to a detached object no longer in `wagerStates`.
   - `room.host.socketId = client.id` at line 865 — writes to the stale `room` object, not the `rooms`
     Map entry (which was deleted). These writes are invisible to future lookups.
5. `client.emit('rejoinSuccess', ...)` fires — the client navigates to BattleScreen with stale state.
   The room no longer exists on the server. Any subsequent game event (shoot, fire, etc.) will fail
   room lookups and be silently dropped or errored.

**Trigger probability:** This window is exactly 0 milliseconds wide in practice because no `await`
exists between line 805 (read pending) and line 822 (clear timer) within the handler. The timer fires
asynchronously as a separate event loop task — it CANNOT interrupt the synchronous execution of the
`rejoinRoom` handler between those lines. The timer is a separate macrotask and will only execute after
the current call stack (the full `rejoinRoom` handler) returns.

**Revised assessment:** The timer race is NOT exploitable by a concurrent `rejoinRoom` during normal
execution. The JS event loop single-thread guarantee means the timer callback cannot interrupt the
synchronous handler mid-execution. The window would only be relevant if any `await` existed between
lines 805 and 822 — and none does.

However, there is one subtle residual concern: `client.join(roomId)` at line 829 is synchronous
in the in-memory adapter but the Socket.IO documentation states it "may return a Promise or nothing,
depending on the adapter". If a distributed adapter (e.g., Redis adapter for horizontal scaling) were
introduced, `client.join()` would become `await client.join()`, opening a yield point between lines
826 (delete pendingReconnects) and 836 (authenticate state writes). In that future state, the timer
could fire during the `await`, and `cleanupRoom` would destroy the room while migration is in progress.
This is a latent architectural risk.

### Step 4 — Stale `oldSocketId` migration error

A separate correctness gap exists when two `rejoinRoom` events from different sockets process sequentially
(first succeeds, second gets `rejoinError` as shown above). But consider a different scenario:

**Scenario:** A player reconnects successfully (S_old → S_1). The match continues. The player
disconnects again (S_1 disconnects). A new `pendingReconnects["W"]` is created with
`oldSocketId: S_1`. The player reconnects again (S_1 → S_2).

In this scenario the migration correctly uses `oldSocketId = S_1` and migrates to `S_2`. This is the
intended case and works correctly.

**However**, the `wagerStates` migration at line 842–844 has a silent-fail pattern:

```js
const ws = wagerStates[roomId]
if (ws && ws.wallets[oldSocketId]) {        // Only migrates if old key EXISTS
    ws.wallets[client.id] = ws.wallets[oldSocketId]
    delete ws.wallets[oldSocketId]
}
```

If `ws.wallets[oldSocketId]` is falsy (e.g., the wager was set up with a different key, or the wallet
entry was already cleared), no wallet entry is created for `client.id`. Settlement at line 2216 in
`main.js` falls through to `wsState?.wallets?.[winnerId]` — if the wallet is not present under the
new socket ID, settlement wallet resolution fails silently and the winner's wallet address is
`undefined`. This causes an `UncheckedAccount` violation at the on-chain level (invalid pubkey) and
the settlement transaction fails, triggering `handleSettlementFailure` (cancel/refund). The winner
loses their winnings.

This is not a race condition — it is a correctness bug in the migration logic that can manifest
if `wagerStates` entry structure differs from what the migration assumes.

## Verdict

**NOT VULNERABLE** to the specific hypothesis (dual rapid reconnect corrupting state).

**POTENTIAL** for two narrower issues:
1. Latent timer-race if `client.join()` ever becomes async (distributed adapter, future refactor).
2. Silent wager wallet migration failure if `ws.wallets[oldSocketId]` is absent, causing settlement
   wallet resolution to fail and the winner to lose winnings.

---

## Severity

**Overall: LOW–MEDIUM**

- Primary hypothesis: NOT VULNERABLE (guard is correctly placed; synchronous handler prevents interleaving)
- Latent distributed-adapter risk: LOW (not present in current single-server deployment)
- Wager wallet migration silent-fail: MEDIUM (can cause winner to lose winnings on second reconnect in a wagered match if state is inconsistent)

## Recommendations

### R1 — Document the adapter assumption (LOW priority)

Add an inline comment at line 829 explaining the synchrony assumption:

```js
// client.join() is synchronous with the in-memory adapter (default).
// If a distributed adapter (Redis etc.) is introduced, this becomes async
// and a 'await client.join(roomId)' would create a yield point between
// the pendingReconnects delete (line 826) and authentication state writes (line 836).
// In that case, move the delete to AFTER client.join() completes.
client.join(roomId)
```

### R2 — Harden the wager wallet migration (MEDIUM priority)

The conditional migration at lines 841–845 silently skips creating the new wallet entry if the old
key is absent. Replace with an unconditional write using the wallet address from `authenticatedWallets`
as a fallback:

```js
const ws = wagerStates[roomId]
if (ws) {
    // Migrate wallet entry: prefer old key; fall back to authenticatedWallets
    const existingWallet = ws.wallets[oldSocketId] || authenticatedWallets[oldSocketId] || walletAddress
    ws.wallets[client.id] = existingWallet
    if (ws.wallets[oldSocketId]) delete ws.wallets[oldSocketId]
}
```

Apply the same pattern to the `room.player` branch at lines 867–871.

### R3 — Move timer cancel before pendingReconnects read (LOW priority, defence-in-depth)

Currently the order is: read pending (L805) → guard on null (L806–809) → room validity check
(L811–819) → cancel timer (L822–824) → delete pending (L826).

For maximum clarity and to prevent any future confusion if an `await` is ever introduced between lines
805 and 826, reorder to: cancel timer first (immediately after signature verification), then read and
delete pending:

```js
// Cancel timer FIRST — before reading pending — to eliminate any theoretical
// window where the timer callback runs between the read and the delete.
if (disconnectTimers[walletAddress]) {
    clearTimeout(disconnectTimers[walletAddress])
    delete disconnectTimers[walletAddress]
}

const pending = pendingReconnects[walletAddress]
if (!pending) {
    client.emit('rejoinError', { reason: 'No active match to rejoin' })
    return
}
delete pendingReconnects[walletAddress]
```

This reordering has no effect in current single-server Node.js but makes the code's intent
explicit and safe against future async refactors.
