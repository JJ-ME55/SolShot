# H022 — maxHttpBufferSize Unbounded Payload DoS

**Hypothesis ID:** H022
**Category:** API-03 (WebSocket Security), ERR-03 (Rate Limiting)
**Status:** CONFIRMED
**Verdict:** REAL VULNERABILITY — LOW-MEDIUM severity (downgraded from Tier 1 hypothesis)
**Auditor:** Dinh's Bulwark Hypothesis Investigator
**Date:** 2026-02-23

---

## Verdict Summary

The hypothesis is confirmed: `maxHttpBufferSize` is not configured on the Socket.IO server,
leaving the default of **1 MB per WebSocket frame** in effect. This is a real gap. However, the
Tier 1 CRITICAL classification in the hypothesis requires downgrade to **LOW-MEDIUM** because:

1. The largest legitimate inbound client payload is the `giveTurn` event's `terrainData` field,
   which is legacy/unused but still accepted. All other inbound client events are small (< 1 KB).
2. The 1 MB default is not "arbitrarily large" — it is already a fixed ceiling. An attacker
   cannot send a 10 MB payload; they can send at most 1 MB per frame.
3. Per-socket event rate limiting (30 events/second) and per-IP connection limiting (100
   connections/IP) substantially constrain the aggregate throughput of the attack.
4. The most dangerous amplification vector — `giveTurn` relaying unbounded `terrainData` — is
   a separate and more severe finding (WS-01) that subsumes the worst-case for this issue.

The residual risk is: a single socket sending 1 MB frames at 30 frames/second = 30 MB/s of
inbound data that the server must buffer and parse before rejecting or processing. With 100
sockets per IP (100 connections/IP limit) at 30 events/second each, one IP can push 3 GB/s
worth of data through the server's parse path — well beyond what Node.js can absorb.

In practice, the per-socket event rate limiter catches the volume before memory is exhausted.
But the combination of no `maxHttpBufferSize` + the unauthenticated `giveTurn` relay creates a
compounded path that is more dangerous than either issue alone.

## Evidence

### 1. Socket.IO Server Initialization — `maxHttpBufferSize` Not Set

**File:** `server/index.js`, lines 31–36

```js
const io = new socket.Server(server, {
    cors: {
        origin: CORS_ORIGINS,
        methods: ["GET", "POST"]
    }
})
```

No `maxHttpBufferSize` option is present. The Socket.IO constructor passes options directly to
engine.io, which sets the default.

### 2. Engine.io Default Confirmed from Installed Source

**File:** `server/node_modules/engine.io/build/server.js`, line 30 (installed: engine.io 6.2.0,
which ships with socket.io 4.5.1)

```js
maxHttpBufferSize: 1e6,
```

The default is exactly `1,000,000` bytes (1 MB) per WebSocket frame and per HTTP polling body.
This value is then threaded into the underlying `ws` module as `maxPayload`:

```js
// engine.io/build/server.js line 297
maxPayload: this.opts.maxHttpBufferSize
```

This means the `ws`-level WebSocket frame limit is also 1 MB — the cap applies uniformly across
the WebSocket and HTTP long-polling transports.

**Installed versions:**
- `socket.io`: 4.5.1 (from `server/package.json` line 29: `"socket.io": "^4.4.1"`)
- `engine.io`: 6.2.0 (resolved dependency)

### 3. The Unauthenticated `giveTurn` Relay — Primary Amplification Vector

**File:** `server/socket-io/main.js`, lines 2478–2483

```js
// LEGACY: turn relay (still works)
client.on('giveTurn', (data) => {
    if (!data || typeof data !== 'object') return
    const { terrainData, pos1, pos2, rotation1, rotation2 } = data
    client.to(client.roomId).emit('recieveTurn', {terrainData, pos1, pos2, rotation1, rotation2})
})
```

Key observations:
- No `requireAuth` call — any socket including unauthenticated ones can emit this event.
- `terrainData` is destructured and forwarded wholesale. If the client sends
  `{ terrainData: "A".repeat(900000) }` (900 KB string), the server:
  1. Allocates a buffer to receive the 900 KB WebSocket frame (permitted by the 1 MB default).
  2. Parses the JSON, creating a 900 KB string in the V8 heap.
  3. Re-serializes the object and emits it to the opponent's socket (another 900 KB allocation).
- The relay is per-event, not per-room. Any socket with `client.roomId` set — including sockets
  that joined a free/unranked room without authentication — can trigger this.

### 4. Per-Socket Rate Limiter Parameters

**File:** `server/socket-io/main.js`, lines 444–528

```js
const RL_MAX_EVENTS = 30          // max events per second
const RL_DISCONNECT_MULT = 3      // disconnect at 3x limit (90 events/sec)
const RL_DISCONNECT_WINDOW = 5000 // sustained for 5 seconds
```

At 30 events/second with 1 MB frames:
- **Per socket inbound:** 30 MB/s
- **Per socket outbound (via giveTurn relay):** 30 MB/s
- **Per IP (100 sockets):** 3 GB/s inbound + 3 GB/s outbound relay

The rate limiter counts events, not bytes. A single event consuming 1 MB counts the same as a
1-byte event. The volume cap on bytes is entirely absent.

### 5. Legitimate Payload Envelope (Context for Severity Calibration)

The largest server-generated payloads are:

| Event | Direction | Payload content | Approx size |
|-------|-----------|-----------------|-------------|
| `terrainGenerated` | Server → Client | 1200-element heightmap array + path + metadata | ~12 KB |
| `turnResult` | Server → Client | 1200-element `terrainUpdate` + trajectory + metadata | ~12–30 KB |
| `rejoinSuccess` | Server → Client | Full match state including heightmap | ~20 KB |

The largest legitimate **inbound** client payloads are:

| Event | Direction | Payload content | Approx size |
|-------|-----------|-----------------|-------------|
| `fire` | Client → Server | `{ weaponId, angle, power, seq, pos }` | ~50 bytes |
| `authenticate` | Client → Server | `{ walletAddress, message, signature, timestamp }` | ~200 bytes |
| `createRoom` | Client → Server | `{ name, color, wager, matchMode }` | ~100 bytes |
| `giveTurn` | Client → Server | `{ terrainData: <any>, pos1, pos2, rotation1, rotation2 }` | **up to 1 MB** |

All inbound events except `giveTurn` are well under 1 KB. The 1 MB default is only reachable
through `giveTurn`'s unbounded `terrainData` field.

### 6. Express Body-Parser Limit Is Irrelevant for WebSocket Traffic

**File:** `server/index.js`, lines 109–111

```js
// H008: Reduce body parser limit from 30mb to 1mb — no endpoint needs 30mb
app.use(express.json({limit: "1mb", extended: true}))
app.use(express.urlencoded({limit: "1mb", extended: true}))
```

The Express body-parser limit applies only to HTTP request bodies (REST endpoints). Socket.IO
WebSocket frames bypass Express middleware entirely — they are handled at the `http.Server` level
by engine.io's `upgrade` handler. The 1 MB body-parser limit provides no protection for
WebSocket frame sizes.

### 7. Architecture Document Corroboration

**File:** `.bulwark/ARCHITECTURE.md`, lines 93–94

```
- express-rate-limit on HTTP (not WS events)
- maxHttpBufferSize NOT configured
```

This was already flagged during Phase 1 synthesis. The finding is corroborated by 2 auditors
(API-03 and ERR-03) and appears in the architecture document's trust boundary analysis.

## Attack Scenario

### Scenario A: Large-Frame Memory Pressure (Direct)

1. Attacker opens `N` WebSocket connections from the same IP (up to 100 per IP limit).
2. Each socket emits `giveTurn` with `{ terrainData: <~950 KB string> }` at 30 events/second.
3. Per socket: 2 allocations × 950 KB × 30/s = ~57 MB/s of heap churn.
4. Per IP (100 sockets): 5.7 GB/s of heap allocation — guaranteed OOM on any standard Node.js
   deployment within seconds.
5. No authentication required. Attacker does not even need a Solana wallet.

**Mitigation interaction:** The global 30 events/second rate limiter fires before the socket can
send more than 30 frames. But each frame is still 950 KB. The rate limiter counts events, not
bytes — it does not slow down the data rate per event.

### Scenario B: `giveTurn` Relay Amplification

1. Attacker opens a socket, joins a free/unranked room (no auth required for `wager=0`).
2. Emits `giveTurn` with 950 KB `terrainData` at 30 events/second.
3. Server receives 950 KB, allocates it, then re-emits the same 950 KB to the opponent's socket.
4. Net effect: server doubles the allocation per event (receive + re-emit buffer).
5. If attacker creates 100 free rooms with 100 sockets, each pair generates 57 MB/s × 2 = 114
   MB/s of heap churn per pair, or 11.4 GB/s total.

### Scenario C: Active Wagered Match Disruption

1. Attacker identifies a player mid-match via `broadcastRooms` (global broadcast reveals lobby).
2. Creates a separate socket and floods `giveTurn` from a different IP (no per-IP coordination
   needed since the attack targets server heap, not a specific victim socket).
3. Server OOM or GC pause disrupts the event loop.
4. In-progress wagered match state is lost — no persistence. If the server crashes during a
   settling match, the winner loses their payout (escrow state is in-memory).

## Severity Assessment

**Severity: LOW-MEDIUM** (downgraded from hypothesis Tier 1 CRITICAL)

| Factor | Assessment |
|--------|------------|
| Exploitability | Easy — no auth required, no cryptographic overhead |
| Payload ceiling | Fixed at 1 MB by engine.io default — not "arbitrarily large" |
| Rate limit interaction | 30 events/second per socket limits burst, not byte rate |
| Amplification factor | ~2x via `giveTurn` relay; ~100x via IP connection limit |
| Independent mitigations | Per-IP 100-connection limit constrains total sockets from one IP |
| Financial impact | Indirect — server OOM disrupts in-memory wagered match state |
| Practical OOM threshold | Requires multiple IPs to sustain; single-IP attack is meaningful but bounded |
| Convergence | 2 auditors flagged independently (API-03 WS-06, ERR-03 F02) |

The "Tier 1 CRITICAL" classification in the hypothesis overstates the severity because:
- The 1 MB default is not unlimited — it is a fixed ceiling
- The per-socket event rate limiter (30/s) caps event throughput
- The `giveTurn` relay issue (WS-01, which this partially overlaps) is the actual dangerous
  amplification path and should be tracked as the primary finding

The combined `maxHttpBufferSize` + unauthenticated `giveTurn` relay path is the most dangerous
intersection and elevates the combined risk above either finding alone.

## Recommendations

### Fix 1 — Set `maxHttpBufferSize` on Socket.IO constructor (PRIMARY)

**File:** `server/index.js`, lines 31–36

Change from:
```js
const io = new socket.Server(server, {
    cors: {
        origin: CORS_ORIGINS,
        methods: ["GET", "POST"]
    }
})
```

Change to:
```js
const io = new socket.Server(server, {
    cors: {
        origin: CORS_ORIGINS,
        methods: ["GET", "POST"]
    },
    maxHttpBufferSize: 64 * 1024,  // 64 KB — covers all legitimate payloads (largest is ~30 KB)
})
```

**Rationale:** 64 KB covers the largest legitimate server-generated payload (`turnResult` with
full `terrainUpdate` ~30 KB) with a 2x safety margin. It reduces the per-frame allocation ceiling
from 1 MB to 64 KB — a 16x reduction in the maximum per-event memory impact.

Note: `maxHttpBufferSize` controls inbound frames only. The server-generated `terrainGenerated`
and `turnResult` outbound payloads (~12–30 KB) are unaffected by this setting.

### Fix 2 — Delete or sanitize the `giveTurn` legacy relay (PRIMARY — addresses amplification)

**File:** `server/socket-io/main.js`, lines 2478–2483

`terrainData` in `giveTurn` is the only inbound field that can approach the 1 MB limit. The
`requestTerrain`/`terrainGenerated` flow supersedes `giveTurn` entirely. The legacy relay should
be removed:

```js
// DELETE the entire giveTurn handler:
// client.on('giveTurn', (data) => { ... })
```

If backward compatibility is required for old clients during a transition period, replace the
relay with a numeric-fields-only version that drops `terrainData`:

```js
client.on('giveTurn', (data) => {
    if (!requireAuth(client, 'giveTurn')) return
    if (!data || typeof data !== 'object') return
    const pos1 = typeof data.pos1 === 'number' ? data.pos1 : null
    const pos2 = typeof data.pos2 === 'number' ? data.pos2 : null
    const rotation1 = typeof data.rotation1 === 'number' ? data.rotation1 : null
    const rotation2 = typeof data.rotation2 === 'number' ? data.rotation2 : null
    // terrainData intentionally omitted — use requestTerrain/terrainGenerated instead
    client.to(client.roomId).emit('recieveTurn', { pos1, pos2, rotation1, rotation2 })
})
```

### Fix 3 — Reduce per-IP connection limit (DEFENSE IN DEPTH)

**File:** `server/index.js`, line 41

Change:
```js
const MAX_CONNECTIONS_PER_IP = 100;
```
To:
```js
const MAX_CONNECTIONS_PER_IP = 10;  // Appropriate for a 1v1 game
```

A 1v1 game has no legitimate use case for 100 simultaneous connections from the same IP. Reducing
to 10 limits the per-IP attack multiplier from 100x to 10x.
