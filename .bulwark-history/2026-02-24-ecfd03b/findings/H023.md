# H023 — Client NPM Critical Vulnerability Exploitation

**Strategy ID:** H023
**Category:** DEP-01 (Dependencies)
**Hypothesis Tier:** 1 (CRITICAL) — as assigned by strategize phase
**Investigator:** Dinh's Bulwark Phase 3
**Date:** 2026-02-23

---

## Verdict

**PARTIALLY CONFIRMED — Downgraded to HIGH (not CRITICAL)**

The three npm-reported "critical" vulnerabilities in the client are **not directly exploitable** in a deployed production context: two are build-time-only tools (`loader-utils`, `form-data`) and one (`webpack` DOM clobbering) is mitigated by the react-scripts static `publicPath` configuration. There is no known CVE that enables direct client-side RCE or XSS from these specific packages in this deployment.

However, the underlying attack surface this hypothesis targets — XSS escalation via `window.socket` and wallet signing functions — is **real and unmitigated**. The absence of any Content Security Policy on the Vercel-served client (confirmed by WEB-02 auditor, Finding W7) means that *any* XSS vector (including future ones, third-party script compromise, or the marginal webpack DOM-clobbering risk if `publicPath` ever changes) has a clear and severe escalation path: `window.socket` is a confirmed global with full Socket.IO access to the live server connection.

The `window.solWallet` global cited in the hypothesis **does not exist** in the current codebase — wallet signing functions were refactored to React Context hooks (CS-04 remediation, evidenced by comments throughout). This removes one arm of the escalation path but does not eliminate the risk.

## Evidence

### 1. The Three Client Critical CVEs — Actual Exploitability

**Source:** `C:/Users/johnk/SolShot-clean/.bulwark/context/16-dep-01-dependencies.md`, Section 3.1

| CVE | Package | Runtime Exploitable? | Reason |
|-----|---------|----------------------|--------|
| GHSA-4vvj-4cpr-p986 | `webpack` 5.73.0 — DOM Clobbering XSS gadget | LOW (currently) | Gadget only injected when `output.publicPath: 'auto'`; react-scripts uses a static path. Not active in current build. Fixed in webpack >=5.94.0. |
| GHSA-76p3-8jx3-jpfq | `loader-utils` 2.0.2 — Prototype Pollution | NO | Build-time only; not in production bundle. Requires attacker-controlled webpack config at build time. |
| GHSA-fjxv-7rqg-78g4 | `form-data` 3.0.1 — Math.random() MIME boundary | NO | Test/build transitive dependency; not in production bundle. Requires observing outgoing multipart requests. |

The npm audit labels all three as CRITICAL, but this rating is misleading for this specific deployment. Neither `loader-utils` nor `form-data` ship to browsers. The `webpack` DOM-clobbering gadget is architecture-dependent and is not active given the current react-scripts configuration.

The DEP-01 auditor explicitly confirmed: "the CRITICAL webpack rating is partially justified... the react-scripts static publicPath configuration prevents the vulnerable code path from being exercised."

### 2. window.socket — Confirmed Global

**Source:** `C:/Users/johnk/SolShot-clean/client/src/App.js:20`

```javascript
// Keep socket on window for Phaser + WalletContext access
window.socket = socket;
```

This assignment is unconditional at module load time. Every screen and Phaser scene accesses the live Socket.IO connection via `window.socket`. This is confirmed by 50+ usage sites across the codebase:

```
client/src/App.js:20         window.socket = socket;  (assignment)
client/src/screens/LobbyScreen.js:423   window.socket.emit('createRoom', ...)
client/src/screens/LobbyScreen.js:443   window.socket.emit('joinRoom', ...)
client/src/screens/LobbyScreen.js:467   window.socket.emit('joinQueue', ...)
client/src/scenes/main/index.js:589     window.socket.emit('positionUpdate', ...)
client/src/classes/Tank.js:145          window.socket.emit('stepLeft', ...)
client/src/wallet/WalletContext.js:147  const socket = window.socket;
```

Any JavaScript executing in the page context (via XSS, malicious third-party script, or browser extension) has immediate access to `window.socket` and can:
- Emit arbitrary socket events including `shoot`, `giveTurn`, `positionUpdate`, `createWeaponArray`, `weaponPick` (all of which lack server-side authentication per AUTH-03 finding C-7 and C-8)
- Emit `leaveRoom`, `playAgainRequest`, `deleteRoom` to disrupt active matches
- Listen on all server-emitted events including `escrowDeposit`, `matchEnd`, `shotInfo`

### 3. window.solWallet — Does NOT Exist in Current Codebase

**Source:** Grep of `window.solWallet =` across all client source files returned zero matches.

The hypothesis assumed `window.solWallet` is set globally. The MEMORY.md entry for this project states: "signAndSendEscrowDeposit is exposed on both context value AND window.solWallet for Phaser access." However, the CS-04 remediation (documented via comments in at least 5 files) removed this global assignment. Instead:

- `signAndSendEscrowDeposit` is accessible only via the React Context hook `useSolShotWallet()`
- `signAndBurnShot` is similarly context-only
- Phaser scenes access the wallet indirectly through `BattleScreen.js` (which is a React component with hook access)

Confirming comments in source:
```
BattleScreen.js:100:    // CS-04: Use context hook instead of window.solWallet
LobbyScreen.js:292:     // CS-04: Use context hook instead of window.solWallet
PrestigeScreen.js:192:  // CS-04: Use context hook instead of window.solWallet
App.js:26:              // CS-04: Use wallet adapter hook directly for rejoin logic (avoids window.solWallet)
```

This means injected scripts cannot call `window.solWallet.signAndSendEscrowDeposit()` — that path is closed. Wallet signing requires access to the React Context tree, which is not trivially accessible from arbitrary injected JavaScript.

### 4. No CSP on Client — The Actual Amplifier

**Source:** `C:/Users/johnk/SolShot-clean/client/vercel.json` (WEB-02 Finding W7)

```json
{
  "headers": [
    {
      "source": "/static/(.*)",
      "headers": [
        { "key": "Cache-Control", "value": "public, max-age=31536000, immutable" }
      ]
    }
  ]
}
```

The `client/vercel.json` sets **only** `Cache-Control` on static assets. There is no:
- `Content-Security-Policy`
- `X-Frame-Options`
- `X-Content-Type-Options`
- `Permissions-Policy`

This means any XSS that does execute in the page has zero browser-level containment. The CSP on the Express server (`server/index.js:70-95`) protects only the API server's own responses, not the Vercel-served client. These are two separate deployments with separate header configurations.

### 5. Production-Reachable HIGH Vulnerability: bigint-buffer

**Source:** DEP-01 context, Section 3.2

```
bigint-buffer 1.1.5  GHSA-3gc7-fjrx-p6mg  Buffer Overflow via toBigIntLE()
Path: @solana/spl-token -> @solana/buffer-layout-utils -> bigint-buffer
```

This is the only client-side dependency vulnerability with a genuine production execution path. It triggers during on-chain token account deserialization (e.g., SHOT token operations). In the browser the native addon is absent so the impact is reduced (pure-JS fallback), but no upgrade is available as 1.1.5 is the latest version on npm.

## Attack Scenario Analysis

### Scenario A: webpack DOM-Clobbering XSS (Currently Low Risk)

The `webpack` 5.73.0 DOM Clobbering gadget (GHSA-4vvj-4cpr-p986) would inject a script into the production bundle if `publicPath` is set to `'auto'`. The react-scripts webpack configuration currently uses `paths.publicUrlOrPath` (a build-time static value). This prevents the gadget from being active in the current build.

**Risk condition:** If a developer runs `npm run eject` or switches to a custom webpack config that sets `publicPath: 'auto'`, the gadget activates. If this happens without also deploying a CSP, an attacker who can influence DOM object names (e.g., via a stored XSS in any user-controlled field, or via a compromised CDN asset) could execute arbitrary JavaScript.

If such XSS were achieved, the escalation path is:
1. Injected script reads `window.socket` (confirmed global)
2. Emits `shoot`, `giveTurn`, `positionUpdate` events with crafted payloads (all unauthenticated per server)
3. Manipulates active wagered match outcome
4. Cannot directly trigger wallet signing (window.solWallet removed by CS-04)
5. Can listen on `escrowDeposit` events to intercept the base64-encoded transaction, but cannot sign it without wallet adapter access

### Scenario B: Third-Party Script Compromise (Supply Chain XSS)

No third-party script CDN includes are found in the client build. The app is a self-contained CRA bundle. This narrows the XSS surface considerably — the only external JavaScript loaded is from the Vercel edge itself plus any wallet adapter browser extensions.

### Scenario C: Future Vulnerability in Phaser 3.55.2

`phaser` 3.55.2 is approximately 2 years behind current (3.87.x). No CVEs are currently reported but this is a large game engine (~3MB) with significant DOM/canvas interaction surface. A future Phaser vulnerability would have direct access to `window.socket`.

## Recommendations

### Immediate (before mainnet)

**R1 — Add CSP to client/vercel.json (HIGH priority)**

This is the primary missing control. Without it, any XSS — regardless of source — has zero browser containment. Add to `client/vercel.json`:

```json
{
  "headers": [
    {
      "source": "/(.*)",
      "headers": [
        { "key": "X-Frame-Options", "value": "DENY" },
        { "key": "X-Content-Type-Options", "value": "nosniff" },
        { "key": "Referrer-Policy", "value": "strict-origin-when-cross-origin" },
        {
          "key": "Content-Security-Policy",
          "value": "default-src 'self'; script-src 'self'; connect-src 'self' https://api.devnet.solana.com wss://api.devnet.solana.com https://solshot-server.onrender.com wss://solshot-server.onrender.com; img-src 'self' data: blob:; style-src 'self' 'unsafe-inline'; font-src 'self' https://fonts.gstatic.com; frame-src 'none'; object-src 'none';"
        }
      ]
    },
    {
      "source": "/static/(.*)",
      "headers": [
        { "key": "Cache-Control", "value": "public, max-age=31536000, immutable" }
      ]
    }
  ]
}
```

Note: `'unsafe-inline'` in `style-src` may be necessary for Phaser canvas styling. `'unsafe-eval'` must NOT be added.

**R2 — Upgrade webpack via react-scripts (MEDIUM priority)**

The DOM-clobbering gadget in webpack 5.73.0 (GHSA-4vvj-4cpr-p986) is currently inactive but becomes active if `publicPath` is ever set to `'auto'`. Upgrade to webpack >=5.94.0 when react-scripts 6.x becomes available, or use `CRACO` / `react-app-rewired` to override the webpack version without ejecting.

**R3 — Document the window.socket global as a security boundary (LOW priority)**

Add a comment in `App.js` near `window.socket = socket` noting that this is an intentional architectural decision for Phaser access, and that the server must treat all socket events as unauthenticated unless explicitly verified. This surfaces the assumption to future developers who might add sensitive server-side event handlers.

**R4 — Upgrade server socket.io and express (HIGH priority)**

The server-side `ws` 8.2.3 DoS (GHSA-3h5v-q93c-6h6q) and express 4.18.1 advisories are separately exploitable and production-reachable. Move `nodemon` to `devDependencies` and regenerate the server lock file to pull express 4.21.x and socket.io 4.8.x, resolving approximately 20 server vulnerabilities in a single operation (per DEP-01-S01, DEP-01-S02, DEP-01-S03).

### Medium-term

**R5 — Upgrade Phaser from 3.55.2 to current (3.87.x)**

Phaser is a large, complex game engine that is 2 years behind current. No CVEs exist today, but this is the highest-risk "unknown future CVE" surface in the client bundle. A Phaser XSS would have direct `window.socket` access in a context with no CSP containment.
