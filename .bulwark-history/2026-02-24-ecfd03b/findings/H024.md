# H024 — Server Authority Settles Fabricated Match Outcomes

**Status:** CONFIRMED
**Severity:** CRITICAL
**Confidence:** HIGH
**Category:** CHAIN-01 (Transaction Construction), SOS Cross-Boundary
**Origin:** Strategy H024

---

## Summary

The on-chain `settle_match` instruction has zero knowledge of game outcomes. It accepts any
winner address supplied by the server authority, provided only that the address matches one
of the two registered players. The server alone determines who won — through server-side
physics computation, a match state machine in memory, and a winner lookup in an in-memory
Map. No game state is committed to the blockchain at any point during a match. A compromised
or malicious server operator can call `settle_match` with either player's address as winner
for any active escrow, regardless of actual match outcome.

The on-chain program's `winner` constraint (`winner.key() == escrow.player_one ||
winner.key() == escrow.player_two`) is a correct anti-theft guard against *arbitrary*
addresses — but it explicitly permits the server to designate either registered player as
winner. By design, the program delegates all outcome determination to the off-chain server.

---

## Verdict

**CONFIRMED CRITICAL — Architectural trust model places unverified match outcomes entirely
in server hands.**

This is not a code defect that can be patched with a one-line fix. It is an intentional
architectural design that accepts the server as a trusted oracle for game outcomes. The
finding is confirmed as critical because:

1. The server authority keypair is a single hot wallet with no multisig protection (see H013).
2. Six gameplay events accept unauthenticated input from any connected socket (see
   ARCHITECTURE.md Invariant I-7), meaning match outcomes can be manipulated before the
   server ever calls `settle_match`.
3. The match outcome (winner socketId → winner wallet address lookup) is computed entirely
   from ephemeral in-memory state that is never persisted to the database, audited, or
   verifiable after the fact.
4. There is no on-chain audit trail of the game state that produced the settlement decision.

The combination of (1) key compromise → fabricated `settle_match` call, and (2) server
manipulation via unauthenticated gameplay events → legitimate `settle_match` call with
attacker-controlled outcome, gives two distinct attack surfaces for the same root cause.

## Evidence

### 1. On-Chain Program: `settle_match` Winner Constraint (`lib.rs:575–581`)

```rust
/// Winner: must be one of the registered players (OC-02 — resolves H008, H002, S001)
/// CHECK: Constrained to escrow.player_one or escrow.player_two
#[account(
    mut,
    constraint = winner.key() == escrow.player_one
        || winner.key() == escrow.player_two
        @ EscrowError::InvalidWinner
)]
pub winner: UncheckedAccount<'info>,
```

This is the totality of on-chain winner verification. The constraint enforces only that the
winner is *a registered player*, not *the player who won the game*. There is no on-chain
game state, no score, no HP record, no kill count, no round result. The program has no
mechanism to know or verify who actually won.

### 2. On-Chain Program: `settle_match` Instruction Signature (`lib.rs:228`)

```rust
pub fn settle_match(ctx: Context<SettleMatch>, winner: Pubkey) -> Result<()> {
```

The `winner` is a caller-supplied argument (`Pubkey`). The instruction body reads:
- `ctx.accounts.escrow.state == MatchState::Active` (state guard only)
- `ctx.accounts.escrow.activated_at` (settlement deadline only)
- `wager_lamports` (arithmetic only)

Zero game-state fields are read. The on-chain program stores no scores, HP, turn count,
round wins, or any gameplay data. The entire state machine lives off-chain.

### 3. IDL Confirms No Game State Parameters (`server/idl/solshot_escrow.json:521–526`)

```json
"args": [
  {
    "name": "winner",
    "type": "pubkey"
  }
]
```

`settle_match` takes exactly one argument: the winner's public key. No score, no proof,
no game state hash, no round result.

### 4. `MatchEscrow` Account Has No Game State Fields (`lib.rs:712–736`)

The full `MatchEscrow` struct contains:
- `match_id` (String)
- `authority` (Pubkey)
- `player_one` (Pubkey)
- `player_two` (Pubkey)
- `wager_lamports` (u64)
- `player_one_deposited` (bool)
- `player_two_deposited` (bool)
- `state` (MatchState enum: AwaitingDeposits/Active/Settled/Cancelled)
- `created_at` (i64)
- `activated_at` (i64)
- `bump` (u8)

No HP fields. No score fields. No round wins. No turn count. No game outcome data of any
kind is stored in the PDA.

### 5. Server Determines Winner: `settleMatchEscrow` Call Chain

The full winner determination chain, all off-chain and all in ephemeral memory:

**Step A — Physics determines HP damage (`server/services/physics.js`):**
Server processes shots, reduces HP values stored in `matchState.hp[playerId]`.

**Step B — `isMatchOver` determines winner by socketId (`server/services/match.js:165–188`):**
```js
export function isMatchOver(matchState, hostId, playerId) {
    const hostWins = matchState.roundWins[hostId] || 0;
    const playerWins = matchState.roundWins[playerId] || 0;
    const winsNeeded = Math.ceil(matchState.maxRounds / 2);

    if (hostWins >= winsNeeded) {
        return { isOver: true, winner: hostId };   // socketId
    }
    if (playerWins >= winsNeeded) {
        return { isOver: true, winner: playerId };  // socketId
    }
    // ... score tiebreak ...
    return { isOver: true, winner: hostId };         // tiebreak always favors host
}
```

`hostId` and `playerId` are **socket IDs**, not wallet addresses. The match outcome is a
socket ID, stored in `matchResult.winner` in memory.

**Step C — Winner socketId resolved to wallet address (`server/socket-io/main.js:2093`):**
```js
const winnerWallet = ws.wallets[matchResult.winner] || null
```

`ws.wallets` is a plain JS object keyed by socketId, populated at room join time from the
`authenticatedWallets` Map. This is in-memory, never persisted, never committed to chain.

**Step D — Settlement called with winner wallet address (`server/socket-io/main.js:2102`):**
```js
const sResult = await settleMatch(winnerWallet, loserWallet, ws.amount, roomId)
```

**Step E — `settleMatch` delegates to `settleMatchEscrow` (`server/services/solana.js:201`):**
```js
const result = await settleMatchEscrow(matchId, winnerAddress);
```

**Step F — `settleMatchEscrow` passes winner to on-chain program (`server/services/escrow.js:400–411`):**
```js
const tx = await program.methods
    .settleMatch(winner)           // <-- server-supplied Pubkey, on-chain accepts it
    .accounts({
        escrow: escrowPDA,
        authority: getEscrowKeypair().publicKey,
        winner: winner,
        treasury: treasury,
        ops: ops,
        config: configPDA,
        systemProgram: PublicKey.default,
    })
    .rpc();
```

The winner address flows from a server-computed in-memory value to the on-chain program as a
caller-supplied instruction argument. No checkpoint, hash, signature, or proof is required.

### 6. Unauthenticated Events Allow Match Outcome Manipulation Without Key Compromise

Even without compromising the server authority keypair, the match outcome that feeds into
`settle_match` can be manipulated via unauthenticated socket events. From ARCHITECTURE.md,
Invariant I-7 and Section 4 (API Surface Map):

| Event | Authentication | Impact on Match Outcome |
|-------|---------------|------------------------|
| `shoot` | **NONE** | Directly triggers physics computation |
| `giveTurn` | **NONE** | Passes turn to opponent, affects sequence |
| `weaponPick` | **NONE** | Controls weapon selection for current pool |
| `weaponChange` | **NONE** | Controls which weapon is fired |
| `angleChange` | **NONE** | Controls shot trajectory |
| `powerChange` | **NONE** | Controls shot power |

Any connected socket (not just authenticated players) can emit these events. Combined with
the `positionUpdate` 400px/event tolerance (12,000 px/sec drift possible per ARCHITECTURE.md
Invariant I-8), an adversary can:

1. Connect to a wagered room without authenticating
2. Emit `angleChange` and `powerChange` to control firing parameters
3. Emit `shoot` to trigger server-side physics with those parameters
4. Influence HP damage, round outcomes, and ultimately which player `isMatchOver` returns as
   winner
5. The server legitimately calls `settle_match` with the manipulated winner address

This is outcome manipulation without needing key compromise at all.

### 7. No Persistent Audit Trail (`server/socket-io/main.js:2212–2228`)

```js
if (isDbConnected()) {
    const winnerId = matchResult.winner
    // ...
    if (winnerAddr) {
        await User.findOneAndUpdate(
            { walletAddress: winnerAddr },
            { $inc: { 'stats.wins': 1, ... } },
            { upsert: true }
        )
    }
```

Match results are written only as stat increments (`wins++`, `matchesPlayed++`) via
fire-and-forget DB calls. From ARCHITECTURE.md (H-7):

> `winner` and `settlementTx` fields are permanently null in the DB.

There is no persistent record of which players were in which match, what the outcome was, or
what transaction settled it. Disputes cannot be investigated retrospectively. The on-chain
`MatchSettled` event contains the winner address but not the match state that justified it.

### 8. Cross-Reference: H013 (Single Authority Hot-Wallet)

H013 established that the `_escrowKeypair` in `server/services/keys.js` is the sole
authority for all privileged on-chain operations. H024 adds the settlement vector: once the
server keypair is compromised (via memory dump, plaintext keypair file, container
introspection, or insider threat), the attacker can:

1. Query all active escrow PDAs on-chain (PDAs are public)
2. For each active escrow, identify `player_one` and `player_two` from the PDA data
3. Call `settle_match` with either player as winner (both are valid per the on-chain constraint)
4. The chosen "winner" receives 90% of the pot

The attacker cannot route funds to an arbitrary wallet in one step (on-chain constraint
blocks this), but they can designate the colluding player of their choice as winner for every
active wagered match.

## Attack Scenarios

### Scenario A: Direct Key Compromise

**Prerequisite:** Attacker obtains the server authority keypair.
**Path:**
1. Read `SOLANA_KEYPAIR_JSON` from server environment (exposed via logs, process listing,
   container introspection) or read keypair file at `SOLANA_KEYPAIR_PATH`.
2. Query Solana for all PDAs with seeds `["match", *]` created by program
   `CqvRC6mSJe2CrBtENVfCEPkgRW3WwxLSL9C1hgXz7GtD` where `state == Active`.
3. For each active escrow, construct and sign a `settle_match` transaction naming
   `player_one` (or `player_two`) as winner — whichever is the attacker's colluding wallet.
4. 90% of each active pot flows to the designated "winner".

**On-chain guard response:** None. Both player addresses are valid winners. The authority
signature check passes because the attacker holds the key.

**Impact:** 90% of all concurrent active wagered pots. At max wager (100 SOL per match),
20 concurrent High Roller matches = 200 SOL pots × 90% × attacker-controlled winner share.

### Scenario B: Gameplay Manipulation (No Key Compromise Required)

**Prerequisite:** Attacker controls a socket connection to a wagered match room.
**Path:**
1. Player A enters a wagered match via `joinQueue` (no balance check per Invariant I-1 gap).
2. Player B (legitimate opponent) deposits their wager.
3. Attacker (Player A or a separate socket) emits unauthenticated `weaponChange`,
   `angleChange`, `powerChange`, and `shoot` events to control Player B's shot parameters.
4. Attacker causes Player B to deal minimal damage while Player A deals maximum damage.
5. `isMatchOver` returns Player A as winner.
6. Server legitimately calls `settle_match(playerAWallet, playerBWallet, ...)`.
7. Player A collects 90% of the pot.

**On-chain guard response:** None. `settle_match` is called by the legitimate server with the
legitimate authority key. The winner is Player A, who is a registered player. All on-chain
constraints pass. The settlement is indistinguishable from a legitimate win.

**Impact:** Systematic wagered match theft with no on-chain evidence of manipulation.

### Scenario C: Insider Malicious Operator

**Prerequisite:** Operator has access to running server (legitimate deployment access).
**Path:**
1. Operator creates two colluding wallets: Wallet-A and Wallet-B.
2. Wallet-B enters wagered matches with legitimate opponents.
3. When the match would naturally result in a loss for Wallet-B, operator directly calls
   `settleMatchEscrow(matchId, walletBAddress)` from server code or a direct RPC call.
4. Wallet-B "wins" every match regardless of outcome.

**On-chain guard response:** None. The on-chain program cannot detect operator fraud.

## Root Cause Analysis

The root cause is a deliberate architectural decision to use a trusted oracle model:

> The on-chain program trusts the server authority to determine winners. The server trusts
> its own physics engine and match state machine to compute the correct winner. Neither
> layer verifies the other's correctness.

This is a standard pattern for off-chain game servers with on-chain settlement, and it is
not inherently wrong — but it requires the off-chain server to be as secure as the on-chain
program. The current off-chain server fails this requirement:

| Required Property | Current State |
|------------------|---------------|
| Authority key is protected | Single hot wallet, no multisig (H013) |
| Gameplay events are authenticated | 6 events have no auth check (I-7) |
| Match outcomes are auditable | Winner never written to DB (H-7) |
| Server process is hardened | No evidence of HSM, key rotation, or isolation |
| Client cannot influence physics | Position spoofing at 12K px/sec (I-8) |

## Severity Rationale

**CRITICAL.** The vulnerability enables direct financial theft of player funds:

- **Confidentiality:** Settlement decisions are not auditable (winner/tx fields null in DB).
- **Integrity:** Match outcomes can be fabricated without on-chain detection.
- **Availability:** Not directly affected.
- **Financial impact:** 90% of every active wagered pot at risk under key compromise; 90% of
  individual matches at risk under gameplay manipulation.
- **Attack complexity:** Scenario A (key compromise) requires server access but is a known
  Solana hot-wallet threat. Scenario B requires only a valid socket connection.
- **Existing mitigations:** The on-chain `InvalidWinner` constraint prevents routing funds to
  arbitrary wallets but permits either registered player to be named winner. This is not a
  mitigation for the stated hypothesis — it only limits the *shape* of the theft, not its
  possibility.

## Recommendations

### Immediate (Pre-Mainnet Required)

**R1. Implement multisig or timelock for authority key operations.**
The server keypair should not be a single hot wallet for `settle_match`. Minimum: use a
Squads v4 multisig as the `config.authority`, with the hot-wallet settlement key having only
`settle_match` rights (requires a separate governance instruction). See H013 for full
multisig recommendation.

**R2. Authenticate all gameplay events that affect match state.**
Events `shoot`, `giveTurn`, `weaponPick`, `weaponChange`, `angleChange`, `powerChange` must
require a valid authenticated session before processing. Without this, match outcomes fed
into `settle_match` are manipulable by unauthenticated actors. See ARCHITECTURE.md I-7.

**R3. Persist match outcome to database before calling `settle_match`.**
Write a match result record (`matchId`, `winner`, `loser`, `wallets`, `roundWins`, `scores`,
`timestamp`) to MongoDB **before** initiating the on-chain settlement call. This creates an
auditable record for dispute resolution. Currently `winner` and `settlementTx` are
permanently null (H-7).

### Medium Term (Reduces Trust Surface)

**R4. Commit match state hash to chain at key transitions.**
At round end, compute a hash of `{ roundWins, scores, hp, roomId }` and include it as a
memo instruction in the settlement transaction. This does not prevent the attack but creates
a cryptographic audit trail that would expose inconsistent settlement decisions post-hoc.

**R5. Implement server-side replay log for wagered matches.**
Maintain an append-only log of all gameplay events (shots, damage, HP changes) with
timestamps and socket IDs for every wagered match. Store this log to durable storage (S3,
IPFS) before settlement. This enables retrospective verification that the declared winner
actually won the game.

**R6. Rate-limit and authenticate position-affecting events.**
Enforce per-event rate limiting (not just HTTP-level rate limiting) on `positionUpdate`,
`shoot`, `angleChange`, and `powerChange`. Require authentication on all gameplay events.
This reduces the ease of Scenario B gameplay manipulation.

### Long Term (Architectural)

**R7. Consider a commit-reveal scheme for match outcomes.**
Before settlement, both players sign a message attesting to the match result. The server
submits both signatures with the `settle_match` transaction as memo data. This requires
player collusion or coercion to fabricate outcomes, rather than only server compromise.

**R8. Evaluate ZK-based outcome verification for high-value matches.**
For High Roller matches (up to 100 SOL wager), a zero-knowledge proof of the physics
computation could be submitted with the settlement transaction, enabling on-chain
verification of the outcome without revealing all game state. This is complex but eliminates
the trusted oracle dependency entirely.
