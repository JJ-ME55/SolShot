# H025 — Treasury/Ops UncheckedAccount Misdirection

**Status:** REFUTED (Hypothesis Incorrect as Stated)
**Verdict:** NOT_VULNERABLE via direct per-call redirection; RESIDUAL RISK absorbed by H013
**Severity:** N/A (direct attack path does not exist; see H013 for the indirect path)
**Confidence:** HIGH
**Category:** CHAIN-01 (Transaction Construction), SOS Cross-Boundary
**Origin:** Strategy H025
**Related:** H013 (Single Authority Hot-Wallet Full Fund Drain — CONFIRMED CRITICAL)

---

## Summary

The hypothesis states that `settle_match` accepts treasury and ops as unconstrained
`UncheckedAccount` values, and that a compromised server can redirect the 7%/3% fee
shares to attacker-controlled wallets on a per-settlement basis. This is **incorrect**.

The on-chain program constrains both treasury and ops accounts against the on-chain
`GlobalConfig` PDA on every `settle_match` call. A server calling `settle_match` with
attacker wallets as treasury/ops will be rejected by the program with
`EscrowError::InvalidTreasury` (6012) or `EscrowError::InvalidOps` (6013). There is no
per-call override of these destinations.

The true attack path for fee redirection is indirect and requires a prior `update_config`
call to rewrite the config PDA — a finding already fully documented in H013. H025 as
originally hypothesized is subsumed by H013 and does not represent an independent
vulnerability.

## Evidence

### 1. On-chain constraints in `SettleMatch` account struct

`programs/solshot-escrow/src/lib.rs`, lines 558–610:

```rust
/// SettleMatch — distribute pot to winner, treasury, ops (OC-02, OC-03, OC-04)
#[derive(Accounts)]
pub struct SettleMatch<'info> {
    #[account(
        mut,
        seeds = [b"match", escrow.match_id.as_bytes()],
        bump = escrow.bump,
        has_one = authority,
        close = authority,
    )]
    pub escrow: Account<'info, MatchEscrow>,

    #[account(mut)]
    pub authority: Signer<'info>,

    /// Winner: must be one of the registered players (OC-02)
    /// CHECK: Constrained to escrow.player_one or escrow.player_two
    #[account(
        mut,
        constraint = winner.key() == escrow.player_one
            || winner.key() == escrow.player_two
            @ EscrowError::InvalidWinner
    )]
    pub winner: UncheckedAccount<'info>,

    /// Treasury: validated against config PDA (OC-03)
    /// CHECK: Constrained to config.treasury; uniqueness check vs ops
    #[account(
        mut,
        constraint = treasury.key() == config.treasury @ EscrowError::InvalidTreasury,
        constraint = treasury.key() != ops.key() @ EscrowError::DuplicateFeeAccount,
    )]
    pub treasury: UncheckedAccount<'info>,

    /// Ops: validated against config PDA (OC-03)
    /// CHECK: Constrained to config.ops
    #[account(
        mut,
        constraint = ops.key() == config.ops @ EscrowError::InvalidOps,
    )]
    pub ops: UncheckedAccount<'info>,

    /// Config PDA — provides validated treasury/ops/authority pubkeys + pause guard (OC-04)
    #[account(
        seeds = [GlobalConfig::SEED],
        bump = config.bump,
        has_one = authority @ EscrowError::Unauthorized,
        constraint = !config.is_paused @ EscrowError::ProgramPaused,
    )]
    pub config: Account<'info, GlobalConfig>,

    pub system_program: Program<'info, System>,
}
```

The `treasury` and `ops` accounts are typed `UncheckedAccount`, meaning Anchor does
not enforce account ownership or discriminator. However, they are subject to two
explicit `constraint` attributes each:

- `treasury.key() == config.treasury` — treasury must equal the pubkey stored in the
  on-chain config PDA.
- `ops.key() == config.ops` — ops must equal the pubkey stored in the on-chain config
  PDA.
- `treasury.key() != ops.key()` — treasury and ops must be distinct.

These constraints are evaluated by the Anchor framework before any instruction logic
executes. Passing an attacker-controlled wallet as `treasury` or `ops` when those
addresses differ from `config.treasury` and `config.ops` will cause the instruction
to abort with error code 6012 (`InvalidTreasury`) or 6013 (`InvalidOps`).

The use of `UncheckedAccount` here is correct Anchor practice: the account type
annotation (`UncheckedAccount`) indicates that Anchor skips the discriminator/ownership
check (appropriate for externally-owned wallets that are not program accounts), while
the value constraint in the attribute macro provides the actual security guarantee.
The `/// CHECK:` comments document this pattern.

### 3. Server-side: treasury/ops sourced from environment variables, passed per-call

`server/services/escrow.js`, lines 43–44 and 384–411:

```js
const TREASURY_WALLET = process.env.TREASURY_WALLET;
const OPS_WALLET = process.env.OPS_WALLET;

export async function settleMatchEscrow(matchId, winnerAddress) {
    // ...
    if (!TREASURY_WALLET || !OPS_WALLET) {
        return { success: false, error: 'Treasury/Ops wallets not configured' };
    }

    const treasury = new PublicKey(TREASURY_WALLET);
    const ops = new PublicKey(OPS_WALLET);
    // ...
    const tx = await program.methods
        .settleMatch(winner)
        .accounts({
            escrow: escrowPDA,
            authority: getEscrowKeypair().publicKey,
            winner: winner,
            treasury: treasury,
            ops: ops,
            config: configPDA,
            systemProgram: PublicKey.default,
        })
        .rpc();
}
```

The server reads `TREASURY_WALLET` and `OPS_WALLET` from environment variables at module
load time and uses those values for every settlement call. There is no runtime parameter
that allows a caller to inject different treasury/ops addresses into `settleMatchEscrow`.

If the environment variables hold correct addresses that match the on-chain config PDA,
settlements succeed. If they do not match (e.g., because the env was tampered with but
the on-chain config was not updated, or vice versa), `settle_match` will be rejected
by the on-chain constraint.

The env variable values are used only to construct the account keys passed to the
instruction — they are not trusted by the program itself. The program independently
validates these keys against its own stored config. This is the correct security model:
the off-chain caller provides candidate accounts, the on-chain program verifies them.

### 4. GlobalConfig stores treasury/ops on-chain

`programs/solshot-escrow/src/lib.rs`, lines 690–708:

```rust
#[account]
pub struct GlobalConfig {
    pub authority: Pubkey,
    pub treasury: Pubkey,   // 7% destination — validated in settle_match
    pub ops: Pubkey,        // 3% destination — validated in settle_match
    pub is_paused: bool,
    pub bump: u8,
}
```

`GlobalConfig` is a PDA (seeds `[b"config"]`) initialized once by the deployer via
`initialize_config`. The treasury and ops addresses are stored durably on-chain and
are not per-match or per-call state. Every `settle_match` call reads this account and
enforces that the provided treasury/ops accounts match stored pubkeys.

### 5. Cross-reference with H013: the indirect path

H013 (CONFIRMED CRITICAL) documents that `update_config` can change `config.treasury`
and `config.ops` with only the server authority key as signer, with no timelock, no
second signer, and no confirmation window:

```rust
pub fn update_config(
    ctx: Context<UpdateConfig>,
    new_authority: Option<Pubkey>,
    new_treasury: Option<Pubkey>,
    new_ops: Option<Pubkey>,
) -> Result<()> {
    let config = &mut ctx.accounts.config;
    if let Some(a) = new_authority { config.authority = a; }
    if let Some(t) = new_treasury  { config.treasury = t; }
    if let Some(o) = new_ops       { config.ops = o; }
    Ok(())
}
```

The attack path for fee redirection therefore exists — but it requires two steps and
passes through `update_config`, not `settle_match`:

1. Attacker calls `update_config(None, Some(attacker_wallet_A), Some(attacker_wallet_B))`
   using the compromised authority key.
2. Attacker calls `settle_match` on active escrows, now passing `attacker_wallet_A` and
   `attacker_wallet_B` as treasury/ops — these will now match the on-chain config and
   the constraints will pass.

This two-step path is entirely covered by H013. The original H025 hypothesis (direct
per-call injection without `update_config`) does not hold.

## Architecture Assessment

The treasury/ops constraint architecture is correctly implemented. The design pattern
— `UncheckedAccount` type with explicit `constraint = field.key() == config.field` — is
idiomatic Anchor for validating externally-owned wallet destinations. It correctly
separates the concern of "what type of account is this" (an externally-owned wallet,
not a program account — hence `UncheckedAccount`) from "which specific address must
it be" (enforced by the constraint attribute).

The on-chain program is a correct and robust backstop against direct fee misdirection.
Any `settle_match` call with treasury/ops accounts that differ from the on-chain config
state will be rejected at the Solana runtime level before any lamports move.

The ARCHITECTURE.md note ("Treasury/ops destinations unconstrained (UncheckedAccount)")
in the on-chain audit cross-reference table (section 8, Boundary Crossing Vulnerabilities)
is **technically imprecise**. The accounts are `UncheckedAccount` in Anchor type terms,
but they are substantively constrained via the `constraint` attribute. The note should
be interpreted as "unconstrained to a specific account type" (i.e., can be any wallet
address), not "unconstrained in destination value" (the value is fully constrained).

## Residual Risk

There is no residual risk specific to H025 that is not already captured by H013.

The fee redirection attack path exists as a consequence of:
- `update_config` allowing immediate treasury/ops changes with a single key (H013)
- No timelock or secondary signer on governance operations (H013)
- The server authority key being a hot-wallet with no operational/governance role
  separation (H013)

All three of these are documented, evidenced, and remediated in H013. H025 does not
add any new exploitable surface beyond what H013 identifies.

---

## Verdict

**REFUTED.** The specific mechanism described in the H025 hypothesis — a compromised
server directly redirecting treasury/ops fees by passing attacker-controlled accounts
as arguments to `settle_match` — does not work. The on-chain program enforces
`constraint = treasury.key() == config.treasury` and `constraint = ops.key() == config.ops`
on every `settle_match` call. These constraints cannot be bypassed by the server.

The indirect path (rewrite config via `update_config`, then settle with updated
destinations) is real and is fully documented in H013. H025 as stated is a
false-positive variant of H013.

**Recommended action:** No new remediation required for H025. Refer to H013
recommendations (separate operational/governance keys, two-step authority transfer
for `update_config`, timelock on treasury/ops address changes).
