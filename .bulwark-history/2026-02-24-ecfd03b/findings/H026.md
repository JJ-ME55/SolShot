# H026 — Hardcoded Program ID Prevents Emergency Migration

**Hypothesis:** H026
**Category:** SEC-02 (Secret Management) / CHAIN-01 (Transaction Construction)
**Verdict:** CONFIRMED — PARTIALLY MITIGATED
**Severity:** HIGH (downgraded from Tier 1 CRITICAL — see Severity Rationale)
**Date:** 2026-02-23
**Auditor:** Hypothesis Investigator (Phase 3)

---

## Summary

The escrow program ID `CqvRC6mSJe2CrBtENVfCEPkgRW3WwxLSL9C1hgXz7GtD` is hardcoded
as a string literal in `server/services/escrow.js` despite a corresponding environment
variable (`MATCH_ESCROW_PROGRAM_ID`) being declared in `server/.env.example` and
`render.yaml`. The env var is never read by the server. On the client side the program
ID is correctly read from `REACT_APP_ESCROW_PROGRAM_ID`, but that value is baked into
the Vercel build artifact and cannot be changed without a full client redeploy.

The hypothesis that a post-exploit program migration would leave old and new program
states inconsistent is **confirmed**. However, the operational severity is lower than
initially estimated because the scenario requires an on-chain program vulnerability,
and the current devnet deployment poses no mainnet fund risk yet. The finding is HIGH,
not CRITICAL, because no funds are at imminent risk from the hardcoding alone.

---

## Evidence

### 1. Server — Hardcoded Literal (`server/services/escrow.js:39`)

```javascript
// Line 37-39
// Program ID — must match deployed program
// NOTE: This ID will change after fresh deploy — see OC-14 deploy checklist
const PROGRAM_ID = new PublicKey('CqvRC6mSJe2CrBtENVfCEPkgRW3WwxLSL9C1hgXz7GtD');
```

`PROGRAM_ID` is defined as a module-level constant from a string literal. It is used
in four places within the same file:

- `escrow.js:111` — `getEscrowPDA()`: PDA derivation for every match
- `escrow.js:124` — `getConfigPDA()`: GlobalConfig PDA derivation
- `escrow.js:83` — startup log
- `escrow.js:543` — exported as `export { PROGRAM_ID }`

### 2. The Env Var Exists But Is Never Read

`server/.env.example:23`:
```
MATCH_ESCROW_PROGRAM_ID=CqvRC6mSJe2CrBtENVfCEPkgRW3WwxLSL9C1hgXz7GtD
```

`render.yaml:25-26`:
```yaml
- key: MATCH_ESCROW_PROGRAM_ID
  value: CqvRC6mSJe2CrBtENVfCEPkgRW3WwxLSL9C1hgXz7GtD
```

A full grep of `server/services/escrow.js` for `process.env` returns no match for
`MATCH_ESCROW_PROGRAM_ID`. The env var is declared in both the example and the Render
deployment config but is dead configuration — it has no effect on the running server.

This is confirmed by context auditor SEC-02 finding SC-11 (INFO):
> "MATCH_ESCROW_PROGRAM_ID env var declared in .env.example and render.yaml but never
> read by escrow.js"

### 3. Client — Correctly Uses Env Var But Is Build-Baked

`client/src/wallet/WalletContext.js:35-37`:
```javascript
// CS-01: Escrow program ID for TX validation
const ESCROW_PROGRAM_ID = process.env.REACT_APP_ESCROW_PROGRAM_ID
    ? new PublicKey(process.env.REACT_APP_ESCROW_PROGRAM_ID)
    : null;
```

The client reads from `REACT_APP_ESCROW_PROGRAM_ID` correctly. However, Create React
App (CRA) inlines all `REACT_APP_*` environment variables at build time into the
JavaScript bundle. Once the client is deployed to Vercel, the program ID is baked into
the static JS artifact. Updating `REACT_APP_ESCROW_PROGRAM_ID` requires a full client
rebuild and redeploy.

`client/.env.example:11`:
```
REACT_APP_ESCROW_PROGRAM_ID=CqvRC6mSJe2CrBtENVfCEPkgRW3WwxLSL9C1hgXz7GtD
```

### 4. On-Chain — `declare_id!` Is Inherently Static

`programs/solshot-escrow/src/lib.rs:7`:
```rust
declare_id!("CqvRC6mSJe2CrBtENVfCEPkgRW3WwxLSL9C1hgXz7GtD");
```

`Anchor.toml:7,10`:
```toml
[programs.localnet]
solshot_escrow = "CqvRC6mSJe2CrBtENVfCEPkgRW3WwxLSL9C1hgXz7GtD"

[programs.devnet]
solshot_escrow = "CqvRC6mSJe2CrBtENVfCEPkgRW3WwxLSL9C1hgXz7GtD"
```

`declare_id!` is a compile-time macro. Redeploying the program to a new address
produces a new binary with a new `declare_id!`. The old binary (at the old address)
remains on-chain and immutable unless the upgrade authority closes it.

### 5. IDL — Also Embeds the Program ID

`server/idl/solshot_escrow.json:2`:
```json
{
  "address": "CqvRC6mSJe2CrBtENVfCEPkgRW3WwxLSL9C1hgXz7GtD",
```

Anchor 0.32 constructs the `Program` object by reading `idl.address` from the loaded
JSON file. The `Program` instance uses the IDL's embedded address as its program ID
for all instruction builds. The constant `PROGRAM_ID` at line 39 and the IDL address
at `server/idl/solshot_escrow.json:2` must therefore remain in sync. If only one is
updated during a migration, the server constructs instructions targeting a different
address than its own `PROGRAM_ID` constant, producing silent breakage.

## Complete Migration Surface

The following files would all require manual updates in an emergency program migration.
All are in production-deployed artifacts (server code on Render, client bundle on
Vercel, IDL on server filesystem):

| File | Location | Update Required | Deploy Required |
|------|----------|-----------------|-----------------|
| `server/services/escrow.js:39` | `PROGRAM_ID` string literal | Yes — change literal | Yes — server redeploy |
| `server/idl/solshot_escrow.json:2` | `"address"` field | Yes — copy new IDL | Yes — server redeploy |
| `client/src/wallet/WalletContext.js:35-37` | `REACT_APP_ESCROW_PROGRAM_ID` | Yes — update `.env` | Yes — client rebuild + deploy |
| `client/.env.example:11` | `REACT_APP_ESCROW_PROGRAM_ID` | Yes — docs only | No |
| `server/.env.example:23` | `MATCH_ESCROW_PROGRAM_ID` | Yes — docs only | No |
| `render.yaml:26` | `value: CqvRC6mSJe2...` | Yes — git commit + PR | Yes — server redeploy |
| `programs/solshot-escrow/src/lib.rs:7` | `declare_id!()` | Yes — compile-time | Yes — program redeploy |
| `Anchor.toml:7,10` | Both `[programs.*]` entries | Yes | Yes — program redeploy |

**Total production artifacts requiring coordinated update: 4 (server code, server IDL,
client bundle, on-chain program binary).** All four must be updated and deployed before
any new match should be created.

## Attack Scenario: Post-Exploit Migration Window

```
T+0:    Vulnerability discovered in on-chain escrow program.
        Active matches: N in-flight (wagers escrowed at old PDA addresses).

T+1:    New program deployed at new_id. Old program at old_id still live.

T+2:    render.yaml updated (git commit, PR, merge, Render build).
        Server redeploys with new IDL + updated PROGRAM_ID string.
        BUT: Because PROGRAM_ID is hardcoded (not env var), the env var
        MATCH_ESCROW_PROGRAM_ID=new_id in render.yaml has NO EFFECT.
        The developer must also update escrow.js:39 and idl/address.
        If the developer only updates render.yaml, the server still
        talks to old_id. This is the trap the dead env var creates.

T+3:    Client rebuild started. CRA bakes old_id into JS bundle.
        Deploy to Vercel takes 2-5 minutes.
        During this window: clients use old_id, server may use new_id.

T+4:    Migration complete. But in-flight matches from T+0 to T+4:
        - Escrow PDAs were created at old_id.
        - If server now uses new_id, getEscrowPDA() derives addresses
          under new program — different PDAs for the same matchId.
        - settleMatch() targets wrong PDAs → TX fails.
        - handleSettlementFailure() calls cancelMatchEscrow() → also
          targets wrong PDAs → TX fails.
        - failedSettlements queue exhausts 5 retries → discarded.
        - In-flight match wagers permanently locked in old PDAs with
          no server-side path to settle or cancel them.
        - Players must use permissionlessReclaim (48h timeout) to
          recover funds — if they are even aware it exists.
```

The key risk: the false configurability created by the dead `MATCH_ESCROW_PROGRAM_ID`
env var means an operator under pressure may update only `render.yaml` and redeploy,
believing the change is complete, while the server code continues targeting the old
program.

## Severity Rationale

**Why HIGH and not CRITICAL:**

The original hypothesis estimated Tier 1 (CRITICAL). After evidence review, HIGH is
more accurate for the following reasons:

1. **No direct exploit path.** The hardcoding does not enable an attacker to steal
   funds directly. It is an operational deficiency that amplifies the blast radius of
   a hypothetical on-chain vulnerability during incident response.

2. **Devnet only.** The program is currently on devnet. No real funds are at stake
   until mainnet deployment.

3. **Both layers require code changes.** Server and client both require code changes
   and deploys for any migration, with or without the env var fix. The env var fix
   reduces this to one fewer code change on the server side (env update vs. code
   change), which is meaningful but does not change the fundamental multi-deploy
   requirement.

**Why still HIGH and not MEDIUM:**

1. **The dead env var creates false confidence.** `MATCH_ESCROW_PROGRAM_ID` is present
   in `render.yaml` and `.env.example`, signaling to operators that the program ID is
   configurable via environment. An operator who trusts this will fail to update the
   source code during migration. This is an active mislead, not just a missing feature.

2. **In-flight matches at migration time.** Any matches active during a migration
   window will have their escrow PDAs derived against the old program ID. A server
   that has been updated to a new program ID cannot settle those matches. With the
   current error-handling pattern (settlement failure → refund → refund failure →
   abandoned), winner funds for those matches are lost.

3. **IDL address and PROGRAM_ID constant divergence risk.** The server program
   instance is constructed from the IDL's `address` field, while `PROGRAM_ID` is a
   separate constant. If these diverge during a partial update, PDA derivation (using
   `PROGRAM_ID`) and instruction construction (using `program.programId` from IDL)
   target different addresses. This silent inconsistency would cause all escrow
   operations to fail with cryptic errors rather than clear configuration errors.

## Recommendations

### R1 — Wire the existing env var (immediate, low-effort)

`server/services/escrow.js` should read `MATCH_ESCROW_PROGRAM_ID` from the
environment. The env var already exists in `render.yaml` and `.env.example`; only
the server code needs to change:

```javascript
// Replace line 39:
// const PROGRAM_ID = new PublicKey('CqvRC6mSJe2CrBtENVfCEPkgRW3WwxLSL9C1hgXz7GtD');

// With:
const programIdEnv = process.env.MATCH_ESCROW_PROGRAM_ID;
if (!programIdEnv) {
    throw new Error('[Escrow] MATCH_ESCROW_PROGRAM_ID not configured — set in .env');
}
const PROGRAM_ID = new PublicKey(programIdEnv);
```

This converts a code change + redeploy into an env var update + redeploy for server-
side migrations. It also eliminates the dead-configuration trap.

### R2 — Derive IDL address from env var (same change, same file)

The IDL `address` field is currently read from `server/idl/solshot_escrow.json:2`.
After wiring the env var, patch the IDL at init time to ensure consistency:

```javascript
export function initEscrow() {
    const idl = JSON.parse(fs.readFileSync(IDL_PATH, 'utf-8'));
    // Override IDL address from env to keep PROGRAM_ID and program.programId in sync
    idl.address = PROGRAM_ID.toBase58();
    program = new Program(idl, provider);
    // ...
}
```

This prevents the divergence scenario where `PROGRAM_ID` and `idl.address` disagree
after a partial update.

### R3 — Document the migration checklist

Add a `MIGRATION.md` or extend the existing `OC-14 deploy checklist` to enumerate all
files requiring update when the program ID changes:

```
Program ID Migration Checklist:
[ ] Set MATCH_ESCROW_PROGRAM_ID=<new_id> in render.yaml (and Render dashboard)
[ ] Set REACT_APP_ESCROW_PROGRAM_ID=<new_id> in client .env / Vercel env vars
[ ] Copy new IDL: cp target/idl/solshot_escrow.json server/idl/
[ ] Update declare_id!() in lib.rs (required by Anchor build system)
[ ] Update Anchor.toml [programs.*] entries
[ ] WAIT for all in-flight matches to settle before deploying new server
[ ] Verify: new server logs "[Escrow] Program ID: <new_id>"
[ ] Verify: new client JS bundle references <new_id> (check network tab)
```

### R4 — Handle in-flight matches during migration

Before deploying a server with a new program ID, drain all active escrow matches:
pause the on-chain program via `pauseProgram` (which blocks new `createMatch`
instructions), wait for all active matches to settle, then deploy. The `permissionless
Reclaim` instruction (48h timeout) provides a backstop for any matches that cannot be
settled during the drain period.
