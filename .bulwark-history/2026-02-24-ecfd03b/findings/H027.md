# H027 — Escrow Creation Failure Silently Ignored; Match Proceeds Without On-Chain Escrow

**Status:** CONFIRMED
**Severity:** HIGH
**Confidence:** HIGH
**Categories:** ERR-01 (Error Handling), LOGIC-02 (Financial Logic)
**Origin:** Strategy investigation

---

## Summary

When `createMatchEscrow()` fails in either the `joinRoom` or `joinQueue` handler, the error
is caught (or the `else` branch is taken), a log line is emitted, and execution continues
unconditionally to the `startPick` / `queueMatched` / `startPick` emissions that begin the
match. The match enters the weapon-pick phase, plays to completion, and the fire handler's
settlement code path then calls `settleMatchEscrow()` against a PDA that was never created.

The on-chain call fails with `AccountNotFound`. `handleSettlementFailure()` is invoked, which
attempts `cancelMatchEscrow()` — which also fails (the PDA never existed). After 5 retry
attempts, the `failedSettlements` entry is deleted. Both players receive no `matchSettled`
event. If `startPick` was reached, the players played a match they believed was wagered, with
no actual on-chain escrow backing the wager.

**The hypothesis in H027 is confirmed in full.** The match proceeds without an escrow
account, players are prompted to deposit into a non-existent PDA (if escrow is enabled),
and the downstream settlement logic eventually exhausts all retries and silently discards
the match result.

## Evidence

### 1. `joinRoom` — escrow creation failure is non-blocking (lines 1024–1092)

```js
// server/socket-io/main.js lines 1021–1092
if (roomWager > 0 && isEscrowEnabled()) {
    const hostWallet = ws?.wallets[room.host.socketId]
    if (hostWallet && joinerWallet) {
        try {
            const escrowResult = await createMatchEscrow(roomId, roomWager, hostWallet, joinerWallet)
            if (escrowResult.success) {
                room.escrowPDA = escrowResult.escrowPDA          // line 1027
                // ... build deposit TXs, emit escrowDeposit to both players ...
            } else {
                console.error(`[Match] Escrow creation failed for ${roomId}:`, escrowResult.error)
                // line 1084 — NO return, NO abort, execution falls to line 1092
            }
        } catch (err) {
            console.error(`[Match] Escrow error for ${roomId}:`, err.message)
            // line 1087 — NO return, NO abort, execution falls to line 1092
        }
    }
    // NOTE: if hostWallet || joinerWallet is null, the entire block is skipped silently
}

// line 1092 — reached regardless of escrow success or failure
io.sockets.in(client.roomId).emit('startPick', {host: room.host, player: room.player, wager: roomWager})
```

`startPick` at line 1092 is emitted unconditionally after the escrow block. It does not
check whether `room.escrowPDA` was set. The match proceeds into the weapon-pick phase
with `room.escrowPDA === undefined`.

### 2. `joinQueue` — identical pattern (lines 1304–1370)

```js
// server/socket-io/main.js lines 1304–1352
if (wagerAmount > 0 && isEscrowEnabled() && opponent.wallet && joinerWallet) {
    try {
        const escrowResult = await createMatchEscrow(roomId, wagerAmount, opponent.wallet, joinerWallet);
        if (escrowResult.success) {
            roomData.escrowPDA = escrowResult.escrowPDA;         // line 1308

        } else {

    }
}

// line 1370 — reached regardless of escrow success or failure
io.sockets.in(roomId).emit('startPick', { host: hostEntry, player: playerEntry, wager: wagerAmount });
```

Exact same non-blocking pattern. `startPick` at line 1370 fires unconditionally after the
escrow block.

### 3. `createMatchEscrow` in `escrow.js` — always returns, never throws (lines 281–313)

```js
// server/services/escrow.js lines 281–313
export async function createMatchEscrow(matchId, wagerSOL, playerOneAddress, playerTwoAddress) {
    if (!program) {
        return { success: false, error: 'Escrow not initialized' };  // line 283
    }
    try {
        // ... Anchor .rpc() call ...
        return { success: true, txSignature: tx, escrowPDA: escrowPDA.toBase58() };
    } catch (err) {
        console.error(`[Escrow] createMatch failed for ${matchId}:`, err.message);
        return { success: false, error: err.message };              // line 312
    }
}
```

`createMatchEscrow` never throws — it catches all Anchor/RPC errors and returns
`{ success: false }`. This means the `catch (err)` in `main.js` at lines 1086–1088 and
1349–1351 can only be triggered by bugs external to `escrow.js` (e.g., `walletAddress`
being a non-string that causes `new PublicKey()` to throw before entering the function).
In practice, the failure path is the `else` branch at lines 1083–1085 and 1346–1348.
Either way, the outcome is identical: the match proceeds without an escrow PDA.

### 4. Settlement failure cascade when `room.escrowPDA` is undefined

At match end, the fire handler calls `settleMatch()` in `solana.js`:

```js
// server/services/solana.js lines 200–213 (approximate)
if (isEscrowEnabled() && matchId) {
    const result = await settleMatchEscrow(matchId, winnerAddress);
    ...
}
```

`settleMatchEscrow` calls `getEscrowPDA(matchId)` to derive the PDA address
deterministically from the `matchId`. The derived address is correct in form but the
account does not exist on-chain (creation failed). The Anchor `.rpc()` call throws
`AccountNotFound`. `settleMatchEscrow` catches this and returns `{ success: false }`.

`settleMatch` then propagates the failure back to the fire handler, which calls:

```js
// server/socket-io/main.js lines 107–136
async function handleSettlementFailure(roomId, room, ws, error) {
    // ...
    const cancelResult = await cancelMatchEscrow(roomId, p1wallet, p2wallet);
    // cancelMatchEscrow also fails — PDA never existed
    // ...
    failedSettlements.set(roomId, { ... attempts: 1 ... });
}
```

The retry loop (lines 82–104) calls `cancelMatchEscrow` up to 5 more times. All fail.
After 5 attempts, the entry is deleted from `failedSettlements`. The match result is
permanently discarded. Neither player receives a `matchSettled` event from inside the
settlement success branch.

### 5. No guard anywhere in match progression checks for escrow creation success

A search for `escrowPDA` across `main.js` shows it is set (lines 1027, 1308) and read
(lines 110, 338, 593, 1044, 1053, 1316, 1319, 1800, 2099) — but never checked before
settlement for truthiness. The settlement call site at line 2091 is:

```js
const ws = wagerStates[this.roomId]
if (ws && ws.amount > 0) {
    // No check: if (room.escrowPDA) ...
    const sResult = await settleMatch(winnerWallet, loserWallet, ws.amount, roomId)
```

`ws.amount > 0` is the only predicate. A room where escrow creation failed will have
`ws.amount > 0` (the wager was configured) and `room.escrowPDA = undefined`. Settlement
is attempted regardless.

## Failure Modes

### Mode A — RPC error / Anchor error during `createMatchEscrow`

`createMatchEscrow` returns `{ success: false, error: 'rpc error...' }`. The `else` branch
logs the error (line 1084 / 1347). `startPick` fires. The match runs to completion. At
settlement, `settleMatchEscrow` fails with `AccountNotFound`. `handleSettlementFailure`
calls `cancelMatchEscrow` — also `AccountNotFound`. Five retries, all fail. Match result
discarded. No `matchSettled` emitted.

**Funds at risk:** None — the deposit instructions were never emitted to clients (they are
only emitted inside the `escrowResult.success` branch, line 1040–1057 / 1315–1320). Neither
player was asked to deposit, so no SOL is locked in any PDA.

**Operational impact:** Both players played a wagered match with no on-chain backing.
Both believe wager was live. Server never confirms or denies the settlement to either player
(no `matchSettled` event from within the failed settlement path in the normal success branch).
Match record is lost. SHOT milestones may still fire (they are in the post-settlement emit
block which is only reached on `sResult.success`, so they are NOT emitted — but the match
state is also not cleaned up cleanly). Room leaks in `matchStates` until some cleanup path
runs.

### Mode B — `!program` guard fires (`escrow.js` line 282)

If `SOLANA_SERVER_KEYPAIR_PATH` or `MATCH_ESCROW_PROGRAM_ID` is not set, `program` is null,
and `createMatchEscrow` returns `{ success: false, error: 'Escrow not initialized' }`
immediately. Identical outcome to Mode A. The match proceeds with no escrow and no deposit
prompts. In this configuration, `isEscrowEnabled()` would return false, preventing the block
from being entered at all — so this specific sub-case is likely unreachable in practice.

### Mode C — `hostWallet || joinerWallet` is null (lines 1022–1023)

```js
const hostWallet = ws?.wallets[room.host.socketId]
if (hostWallet && joinerWallet) {
    // entire escrow block skipped silently
}
```

If either wallet is null (unauthenticated player in a wagered match — a separate
vulnerability), the escrow block is silently skipped. `room.escrowPDA` remains undefined.
`startPick` fires. Settlement is attempted at match end against a non-existent PDA.

This is a second, independent path to the same outcome. It is noted here because it means
the "guard" at lines 1022–1023 appears to be a safety check but is actually a second silent
failure path. The caller has no notification that escrow was not set up.

## Severity Assessment

**Severity: HIGH** (not CRITICAL, for the reasons below).

The finding is **HIGH** rather than CRITICAL because in the primary failure path (Mode A),
no funds are actually lost: the deposit instructions are never sent to clients, so no SOL
is locked in a non-existent PDA. Players are not asked to deposit and do not deposit.

However, the finding reaches CRITICAL severity under two conditions:

1. **If a deposit instruction is sent before the escrow creation result is known** — this
   does not currently occur because deposit instruction building happens inside the
   `escrowResult.success` branch. But if that control flow is ever refactored, the deposit
   could be sent against a non-existent PDA.

2. **Combined with H004 (settlement without deposit verification):** If an adversary can
   cause the escrow creation to fail (e.g., by exploiting a Solana RPC error or by providing
   invalid data at join time), the match proceeds with `wagerStates.amount > 0` but
   `room.escrowPDA = undefined`. When settlement runs, it calls `settleMatchEscrow` on a
   non-existent PDA. The failure triggers `handleSettlementFailure`, which calls
   `cancelMatchEscrow` — also on a non-existent PDA. All recovery attempts fail. Match
   result is silently discarded. This is a reliable way to deny a legitimate winner their
   payout in a wagered match.

**Impact summary:**
- Match outcome permanently lost on escrow creation failure
- No notification to either player that the match was not backed by escrow
- Settlement retry loop exhausted (5 attempts × both `settle` and `cancel` failing on missing
  PDA) generating spurious error log noise
- Operational: server operator has no insight into how many matches ran without escrow backing
- Financial: no direct SOL loss in the current deposit flow, but winner is denied payout

## Relationship to Existing Findings

- **H001 (Balance Check Fail-Open):** H001 covers the outer `try/catch` around `verifyBalance`
  that allows zero-SOL players into wagered matches. H027 is a separate, independent failure
  point in the same `joinRoom` handler that occurs later in the flow (after balance check
  passes). Both contribute to the pattern of fail-open behavior in the financial entry path.

- **H004 (Settlement Without Deposit Verification):** H004 documents that settlement is called
  regardless of whether both deposits were confirmed. H027 is a more extreme variant: the
  escrow PDA itself does not exist, making any settlement or cancellation call certain to fail
  rather than merely inadvisable.

- **ERR-01 context (EH-F02):** The ERR-01 auditor identified this issue at lines 1083–1090
  (joinRoom) and 1346–1353 (joinQueue) and rated it HIGH. This investigation confirms those
  line numbers, adds the Mode C silent-skip path (lines 1022–1023), and validates the full
  downstream failure cascade through `handleSettlementFailure` and the retry loop.

## Recommendations

### Fix 1 — Abort match start on escrow creation failure (primary fix)

In both `joinRoom` (line 1083) and `joinQueue` (line 1347), replace the log-and-continue
behavior with a hard abort:

```js
// joinRoom — replace lines 1083–1085
} else {
    console.error(`[Match] Escrow creation failed for ${roomId}:`, escrowResult.error)
    client.emit('joinRoomError', { reason: 'Escrow setup failed. Please try again.' })
    await removeRoom(roomId)
    broadcastRooms(io)
    return   // <-- prevents startPick from firing
}
```

```js
// joinRoom catch block — replace lines 1086–1088
} catch (err) {
    console.error(`[Match] Escrow error for ${roomId}:`, err.message)
    client.emit('joinRoomError', { reason: 'Escrow setup error. Please try again.' })
    await removeRoom(roomId)
    broadcastRooms(io)
    return   // <-- prevents startPick from firing
}
```

Apply the same pattern in `joinQueue` at lines 1347–1351, emitting `queueError` instead of
`joinRoomError`.

### Fix 2 — Gate `startPick` emission on escrow PDA being set

As a defense-in-depth measure, add a guard before the unconditional `startPick` emit:

```js
// joinRoom — before line 1092
if (roomWager > 0 && isEscrowEnabled() && !room.escrowPDA) {
    // Escrow was expected but not created — do not start the match
    client.emit('joinRoomError', { reason: 'Match could not be started: escrow not ready.' })
    await removeRoom(roomId)
    broadcastRooms(io)
    return
}
io.sockets.in(client.roomId).emit('startPick', { ... })
```

### Fix 3 — Null-wallet guard should be a hard rejection, not a silent skip

At lines 1022–1023 (`joinRoom`) and 1304 (`joinQueue`), the condition
`if (hostWallet && joinerWallet)` silently skips escrow creation if either wallet is null.
For wagered matches, a null wallet means the player is not authenticated, which should have
been rejected earlier by `requireAuth`. Add a defensive assertion:

```js
if (roomWager > 0 && isEscrowEnabled()) {
    const hostWallet = ws?.wallets[room.host.socketId]
    if (!hostWallet || !joinerWallet) {
        // This should never occur if requireAuth is working — treat as abort
        console.error(`[Match] Null wallet in wagered room ${roomId} — aborting`)
        client.emit('joinRoomError', { reason: 'Authentication required for wagered matches.' })
        await removeRoom(roomId)
        return
    }
    // ... escrow creation ...
}
```

### Fix 4 — Settlement guard: check for escrowPDA existence before calling settleMatchEscrow

At all three `settleMatch()` call sites (lines 2091–2102, 331–341, 591–654), add a check:

```js
const ws = wagerStates[this.roomId]
if (ws && ws.amount > 0) {
    // H027: If escrow was expected but PDA was never created, skip settlement
    if (isEscrowEnabled() && !room.escrowPDA) {
        console.error(`[Settlement] Room ${this.roomId} has wager but no escrowPDA — skipping settlement`)
        // No funds to settle; notify both players that match is void
        io.sockets.in(this.roomId).emit('matchVoided', { reason: 'Escrow was not established for this match.' })
        return
    }
    // ... proceed to settleMatch ...
}
```

This does not fix the root cause but prevents the retry loop from being exhausted on a
guaranteed-to-fail PDA lookup.
