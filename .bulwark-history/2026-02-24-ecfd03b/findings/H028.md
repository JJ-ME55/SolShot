# H028 — 30-Second Balance Cache TOCTOU: Stale Balance Admits Wallet-Drained Players

**Status:** CONFIRMED — Partially Mitigated by On-Chain Deposit Enforcement
**Verdict:** REAL VULNERABILITY — exploitable for griefing and time-of-deposit races; on-chain escrow
is the only practical backstop, and that backstop itself has gaps documented in FIN-02/FIN-03
**Severity:** HIGH (down from hypothesized CRITICAL — on-chain deposit requirement limits direct SOL
theft in the escrow-enabled path; griefing impact is HIGH regardless)
**Confidence:** HIGH
**Categories:** CHAIN-02 (RPC Client), LOGIC-02 (Financial Logic)
**Related Findings:** H001 (fail-open balance check), FIN-02 (settlement without deposit verification),
FIN-03 (partial deposit attack), FIN-08 (joinQueue no balance check)

---

## Summary

The `getCachedLamports()` function in `server/services/solana.js` caches on-chain balance query
results for 30 seconds per wallet address. The balance check at `joinRoom` and `createRoom` reads
from this cache. An attacker who has their balance checked and cached at T=0 can transfer their SOL
to another wallet within the 30-second window and then join or create a wagered room at T=10 to T=29.
The server returns `sufficient: true` from stale data and admits them to the match.

The real TOCTOU window is significantly wider than 30 seconds, because the balance check is only the
first gate. Once admitted, the attacker's wallet is not re-checked at: (a) escrow deposit signing,
(b) the `ready` event transition to the shop phase, or (c) the settlement step. The deposit signing
step on-chain is the only enforcement point, and only when the escrow program is live. In dev mode
there is no enforcement at all. Even with escrow live, the deposit timeout is 2 minutes, during which
a legitimate opponent has committed to the match.

## Evidence

### 1. Balance Cache Definition

**File:** `server/services/solana.js`, lines 94–113

```js
// solana.js:94-96
const balanceCache = new Map(); // walletAddress → { lamports, expiresAt }
const BALANCE_CACHE_TTL_MS = 30_000; // 30 seconds

// solana.js:102-113
async function getCachedLamports(walletAddress) {
    const now = Date.now();
    const cached = balanceCache.get(walletAddress);
    if (cached && now < cached.expiresAt) {
        return cached.lamports;   // ← stale balance returned for up to 30s
    }
    const conn = getConnection();
    const pubkey = new PublicKey(walletAddress);
    const lamports = await conn.getBalance(pubkey);
    balanceCache.set(walletAddress, { lamports, expiresAt: now + BALANCE_CACHE_TTL_MS });
    return lamports;
}
```

The cache is keyed by wallet address and shared globally across all callers. There is no per-room
invalidation, no invalidation on match entry, and no mechanism to evict a wallet's cache entry when
that wallet joins a wagered match.

### 2. Balance Check at joinRoom (single check point)

**File:** `server/socket-io/main.js`, lines 980–992

```js
// main.js:980-992
// Verify joiner has enough balance (best-effort — skip if RPC unavailable)
try {
    const balanceCheck = await verifyBalance(joinerWallet, roomWager)
    // H027: Fix fail-open — reject if insufficient, regardless of balance amount
    if (!balanceCheck.sufficient) {
        client.emit('joinRoomError', {
            reason: `Insufficient SOL balance. Need ${balanceCheck.required.toFixed(3)}, have ${balanceCheck.balance.toFixed(3)}`

} catch (err) {
    console.warn('[Solana] Balance check skipped:', err.message)
    // ← no return — fail-open path still present (separate from TOCTOU issue)
}
```

`verifyBalance()` delegates to `getCachedLamports()`. If a cache entry exists and is not expired,
the RPC is never called; the 30-second-old balance value is returned as current.

### 4. No Re-Check at the ready Event

**File:** `server/socket-io/main.js`, lines 1399–1481

The `ready` handler transitions the match from LOBBY to WEAPON_SHOP. This is the last server-side gate
before the match actively begins. The handler contains zero balance verification and zero deposit
confirmation check:

```js
// main.js:1399-1481
client.on('ready', () => {
    if (!requireAuth(client, 'ready')) return
    var room = findRoom(client.roomId)
    if (!room) return

    const msReady = matchStates[client.roomId]
    if (msReady && !validateAction(msReady.status, 'ready')) {
        client.emit('readyError', { reason: `Cannot ready during ${msReady.status}` })
        return
    }

    // Track readiness
    if (client.isHost === true) {
        room.host.isReady = true
    } else {
        if (!room.player) return
        room.player.isReady = true
    }

    // Both players ready — start shop phase
    if (room.host.isReady && room.player && room.player.isReady) {
        // ... (no wagerStates deposit check here)
        transitionState(ms, MATCH_STATES.WEAPON_SHOP)
        io.sockets.in(client.roomId).emit('shopPhase', { ... })
        // match now active
    }
})
```

There is no line reading `ws.deposits` before `transitionState(WEAPON_SHOP)` is called. Both players
can mark themselves ready and start the match entirely independently of whether their deposits have
been confirmed on-chain.

### 5. Settlement Also Does Not Check Deposits

**File:** `server/socket-io/main.js`, lines 2091–2102

```js
// main.js:2091-2102
const ws = wagerStates[this.roomId]
if (ws && ws.amount > 0) {
    const winnerWallet = ws.wallets[matchResult.winner] || null
    const loserId = matchResult.winner === hostId ? playerId : hostId
    const loserWallet = ws.wallets[loserId] || null
    if (winnerWallet && loserWallet) {
        // No check for ws.deposits here
        const sResult = await settleMatch(winnerWallet, loserWallet, ws.amount, roomId)
```

Settlement reads `ws.amount` and `ws.wallets` but never checks `ws.deposits`. The only on-chain
enforcement is inside the Anchor program's `settle_match` instruction, which will fail if not both
players have deposited — but this failure is caught by `handleSettlementFailure` and converted to a
refund (see FIN-09 in the LOGIC-02 context).

### 6. The Full TOCTOU Timeline

The actual window between balance snapshot and on-chain enforcement is not 30 seconds — it is the
entire match duration:

```
T=0s    Player A's balance is checked by getCachedLamports() → 0.26 SOL cached for 30s
        verifyBalance() returns { sufficient: true }
        joinRoom (or createRoom) proceeds

T=5s    Player A transfers 0.25 SOL to another wallet
        On-chain balance is now 0.01 SOL (below wager + fee requirement of 0.26 SOL)

T=10s   Another player joins / is matched
        createMatchEscrow() called (server pays creation fee from authority wallet)
        buildDepositTransaction() called for both players

T=15s   escrowDeposit events emitted — Player A receives deposit TX to sign
        Player A either ignores it or signs a TX that will fail (insufficient funds)

T=15s–2m15s  Deposit window open
             If Player A never sends escrowDepositConfirm:
               → 2-minute timer fires, cancelMatchEscrow() called, both refunded
               → Opponent waited 2+ minutes for nothing
             If Player A submits a failing deposit TX and somehow the confirmation
             path is reached (via the escrowDepositConfirm single-retry vulnerability,
             FIN-03), match could proceed with only one deposit

T=x     If match somehow started: settlement called on escrow with only one deposit
        → On-chain settle_match fails (Anchor checks both playerOneDeposited and
          playerTwoDeposited before transferring)
        → handleSettlementFailure fires, cancelMatchEscrow called
        → Opponent who deposited is refunded (correct behavior)
        → But if cancelMatchEscrow also fails (FIN-09 interaction), funds are stuck
```

### 7. Cache Shared Across Connections — Amplifies the Window

**File:** `server/services/solana.js`, line 95

The `balanceCache` Map is module-level and shared across all socket connections:

```js
const balanceCache = new Map(); // module-level — shared globally
```

This means:

- If Player A authenticated and had their balance checked on a previous socket connection (e.g.,
  during browsing rooms), and then re-joins with a fresh socket within 30 seconds, the cached value
  from their prior connection is used.
- Two different rooms checking the same wallet address concurrently will both read the same stale
  value.
- An attacker who knows about the 30-second TTL can deliberately time their fund transfer to happen
  immediately after triggering a balance check (e.g., by browsing rooms on the lobby screen), then
  quickly join a wagered match.

## Root Cause

Two independent design decisions compound:

1. **`getCachedLamports()` has a fixed 30-second TTL with no invalidation on match entry.**
   `server/services/solana.js`, line 96: `const BALANCE_CACHE_TTL_MS = 30_000`
   The comment at line 94 says "Cuts RPC costs nearly in half for wagered games" — the cache was
   added as a performance optimization without security scoping. The cache is correct for read-heavy
   non-financial paths (e.g., displaying lobby balance) but inappropriate as the sole gate for wager
   entry.

2. **Balance is never re-verified after the initial check.**
   `server/socket-io/main.js`, `ready` handler (lines 1399–1481): no deposit or balance check.
   `server/socket-io/main.js`, settlement block (lines 2091–2102): no deposit check.
   The design assumes the initial balance check is sufficient. It is not, because the window between
   check and on-chain deposit enforcement spans the entire match lobby phase.

## Attack Scenarios

### Scenario 1: Wallet Drain Between joinRoom and Deposit (Griefing)

Precondition: Attacker has exactly enough SOL to pass the wager threshold (e.g., 0.26 SOL for a
0.25 SOL wager). Attacker does not need to be technically sophisticated.

1. Attacker calls `joinRoom` for a 0.25 SOL room. Balance check passes (0.26 SOL). Cache set.
2. Attacker immediately transfers 0.25 SOL to another wallet. Balance is now 0.01 SOL.
3. Escrow created. Attacker receives `escrowDeposit` event with pre-signed TX.
4. Attacker's deposit TX fails on-chain (insufficient SOL for transfer).
5. Legitimate opponent deposited and is waiting.
6. 2-minute deposit timer expires. `cancelMatchEscrow` fires.
7. Opponent's deposit refunded (assuming cancel succeeds — if not, FIN-09 applies).
8. Opponent lost 2+ minutes, paid deposit TX gas fees, and received no match.
9. Attack can be repeated indefinitely with a wallet holding a small recycled SOL buffer.

**Cost to attacker:** Near-zero (one transfer out, one transfer back). Transaction fees only.
**Cost to opponent per iteration:** Gas for deposit TX + gas for refund TX + 2+ minutes wait.

### Scenario 2: Cache-Primed Fast Window Exploit

Attacker has previously browsed the lobby and triggered a balance check (e.g., via `broadcastRooms`
callback or any action that called `verifyBalance`). Cache entry primed with high balance.

1. Attacker transfers out most of their SOL, retaining the minimum to authenticate.
2. Within 30 seconds of the cached balance read, `joinRoom` fires.
3. Cached balance is returned as sufficient. Match joined.
4. Same outcome as Scenario 1.

### Scenario 3: Dev Mode (No Escrow) — Full Financial Impact

With `SHOT_TOKEN_MINT` or `MATCH_ESCROW_PROGRAM_ID` not configured, `isEscrowEnabled()` returns
false. In this mode:

1. `settleMatch()` falls through to the logging stub (returns `{ success: true, txSignature: null }`).
2. There is no on-chain deposit step at all — no `escrowDeposit` event emitted, no deposit required.
3. The balance check at `joinRoom` is the **only** guard.
4. A 30-second TOCTOU window means an attacker who transfers funds out within that window plays a
   wagered match with zero SOL backing, and the settlement succeeds as a no-op log.
5. In this mode, the TOCTOU vulnerability has **zero mitigating controls** — it is the complete
   attack surface.

**Note:** The MEMORY.md project notes indicate the escrow program is "awaiting devnet deploy." If the
server is running in dev mode (common for development), this scenario is the active one.

## Severity Assessment

### Why HIGH and not CRITICAL

The hypothesis rated this CRITICAL. After reading the actual code, the severity is downgraded to HIGH:

- **With escrow enabled:** The on-chain `deposit_wager` instruction is the actual financial gate. If
  the attacker's wallet lacks funds, the deposit TX fails on-chain and the escrow is cancelled after
  2 minutes. No SOL is directly stolen from the opponent in the normal flow. The harm is griefing
  (wasted time, opponent gas fees).
- **With escrow disabled (dev mode):** No on-chain backstop. The TOCTOU is the complete attack
  surface. However, there is also no real SOL at stake in dev mode.

The rating is HIGH because:
- The griefing attack is trivially executable at zero cost to the attacker and non-trivial cost to
  the victim (gas fees + time + friction).
- The 2-minute deposit timeout means an attacker can lock an opponent's escrow deposit and
  participation for 2 minutes per attempt, with no limit on rate (joinRoom has only HTTP-level rate
  limiting, which applies to the HTTP upgrade, not socket events).
- Combined with FIN-02 (settlement called without deposit verification), if the match somehow
  starts before the deposit timeout fires, the TOCTOU elevates to direct fund exposure.
- Combined with FIN-03 (partial deposit attack), the slot-mapping vulnerability means an adversary
  with both sockets could confirm only one deposit and still potentially start the match.
- In dev mode, there is no escrow and the only gate is this stale-cache check.

### Financial Impact Quantification

| Scenario | Cost Per Attack | Repeatability | Requires Escrow Live? |
|----------|----------------|---------------|----------------------|
| Griefing (Scenario 1) | ~0 SOL to attacker; opponent pays ~0.001 SOL gas × 2 | Unlimited | No |
| High Roller griefing | ~0 SOL to attacker; opponent locks 1.0 SOL for 2 min/attempt | Unlimited | Yes |
| Dev mode financial bypass | Full wager (no actual SOL enforced) | Per session | No (dev mode) |
| Combined FIN-02+TOCTOU | Full pot exposure (up to 2.0 SOL on High Roller) | Per match | Yes, partially |

## Recommendations

### Recommendation 1 (PRIMARY — Immediate): Invalidate Balance Cache on Match Entry

The balance cache should be invalidated when a wallet joins or creates a wagered match. This forces a
fresh RPC read at the moment of decision, eliminating the TOCTOU window for the cache itself:

```js
// In getCachedLamports, add an invalidate function:
export function invalidateBalanceCache(walletAddress) {
    balanceCache.delete(walletAddress);
}

// In joinRoom handler, before calling verifyBalance:
// server/socket-io/main.js, before line 982
invalidateBalanceCache(joinerWallet);
const balanceCheck = await verifyBalance(joinerWallet, roomWager)
```

This is a one-line change per call site and eliminates the stale-read vector entirely at the cost
of one additional RPC call per match join. The performance comment on line 94 ("cuts RPC costs nearly
in half") does not apply to the wager-entry path, which executes once per match.

### Recommendation 2 (PRIMARY): Re-check Balance at the ready Event

Even with a fresh check at joinRoom, an attacker can drain their wallet between the `joinRoom`
check and the `ready` event. The `ready` handler should verify deposit status before transitioning
to the shop phase:

```js
// server/socket-io/main.js, in ready handler, before transitionState()
if (room.host.isReady && room.player && room.player.isReady) {
    // For wagered matches: require both deposits confirmed before shop starts
    const wsReady = wagerStates[client.roomId]
    if (wsReady && wsReady.amount > 0 && isEscrowEnabled()) {
        const hostDep = wsReady.deposits && wsReady.deposits[room.host.socketId]
        const playerDep = wsReady.deposits && wsReady.deposits[room.player.socketId]
        if (!hostDep || !playerDep) {
            client.emit('readyError', { reason: 'Waiting for escrow deposits to confirm before match can start' })
            // Reset ready flags — both players must re-ready after deposits land
            room.host.isReady = false
            if (room.player) room.player.isReady = false
            return
        }
    }
    // ... rest of ready handler
}
```

This also closes the FIN-02 gap (settlement without deposit verification) at the source by preventing
the match from starting until deposits are confirmed.

### Recommendation 3 (SECONDARY): Reduce Cache TTL for Wager-Gated Paths

If invalidation at match entry is not immediately feasible, reducing the TTL from 30 seconds to
3–5 seconds substantially narrows the attack window:

```js
// server/services/solana.js, line 96
const BALANCE_CACHE_TTL_MS = 5_000; // 5 seconds (down from 30s) for wager checks
```

This is a weaker fix than invalidation because a determined attacker could still execute the drain
within a 5-second window, but it makes the attack significantly harder in practice.

### Recommendation 4 (SECONDARY): Scope Cache to Non-Financial Paths

Split the cache into two tiers — one for display (30-second TTL acceptable) and one for financial
gating (no cache or 5-second TTL):

```js
async function getBalanceForDisplay(walletAddress) {
    // Use full 30s cache — only for UI/stats display
    return getCachedLamports(walletAddress, 30_000);
}

async function getBalanceForWager(walletAddress) {
    // Fresh RPC call — financial gate
    balanceCache.delete(walletAddress);  // force fresh read
    return getCachedLamports(walletAddress, 5_000);
}
```

### Recommendation 5 (DEFENSE-IN-DEPTH): Fix the Fail-Open Catch Block

Both `joinRoom` (line 990–992) and `createRoom` (line 1145–1147) have a `catch` block that
`console.warn` and fall through on any `verifyBalance` exception. This is the H001/FIN-01 bug and is
a separate but compounding vulnerability. The TOCTOU fix must not be undermined by the fail-open
path. Replace:

```js
// Current — fail-open:
} catch (err) {
    console.warn('[Solana] Balance check skipped:', err.message)
}

// Fix — fail-closed:
} catch (err) {
    console.error('[Solana] Balance check failed:', err.message)
    client.emit('joinRoomError', { reason: 'Balance verification unavailable. Please try again.' })
    return
}
```

## Precise TOCTOU Window Measurement

```
T=0          verifyBalance() called, getCachedLamports() returns fresh RPC value
             Cache entry: { lamports: 260_000_000, expiresAt: T+30_000 }

T=0 to T+30  Attack window for cache: any call to verifyBalance() for same wallet
             returns stale 260_000_000 lamports regardless of on-chain state

T+30         Cache entry expires; next call triggers fresh RPC

--- but the match continues beyond T+30: ---

T+30 to T+120+  Deposit window (2-minute DEPOSIT_TIMEOUT_MS)
                ready event can fire at any point in this window
                No balance re-check at ready (lines 1399-1481)
                No deposit check at ready (confirmed above)

T+(2-5 min)  Match gameplay begins
             No balance check during gameplay
             No deposit check before settlement (lines 2091-2102)
             Settlement finally hits on-chain Anchor program as the last gate
```

**Effective TOCTOU window:** From T=0 (balance check) to whenever the Anchor `deposit_wager`
instruction executes on-chain — which is T=0 + cache TTL + lobby time + player ready time +
any async lag. In practice, this is 1–5 minutes after the initial balance check, not 30 seconds.
The 30-second cache is only the first part of a much wider window.
