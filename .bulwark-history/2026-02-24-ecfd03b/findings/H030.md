# H030 — Signature Replay Within 5-Minute Window

**Status:** CONFIRMED
**Verdict:** REAL VULNERABILITY — any observed auth signature tuple is replayable on new socket
connections until the 5-minute timestamp window expires; no consumed-signature store exists anywhere
in the codebase
**Severity:** CRITICAL
**Confidence:** HIGH (confirmed by direct code inspection; hypothesis description is accurate in every
detail)
**Categories:** AUTH-01 (Authentication), CRYPTO-01 (Cryptography)
**Related Findings:** C5 (JWT never consumed — auth system is socket-flag only), M12 (re-auth swap
on same socket), AUTH-01 context auditor finding C2, ARCHITECTURE.md Section 3 trust boundary note
"Signature replay possible within 5-min window (no nonce)"

---

## Summary

The `authenticate` socket event accepts a four-field payload:
`{ walletAddress, message, signature, timestamp }`.

The server verifies two things: (1) the message string matches the expected format
`"SolShot Auth: <walletAddress> at <timestamp>"` and the timestamp is within AUTH_TIMEOUT of
`Date.now()`; (2) the Ed25519 signature over that message is valid for the claimed wallet.

Neither check is destructive. The signature is not stored after verification. No nonce, no replay
set, no Map, no database write. An attacker who captures a valid
`(walletAddress, message, signatureBase64)` tuple — by any means — can replay it verbatim on any
number of new socket connections for up to 5 minutes after the original timestamp, and each replay
will pass both checks and produce a fully authenticated session attributed to the victim's wallet.

## Evidence

### 1. Message Format — Timestamp Only, No Nonce

**File:** `server/middleware/auth.js`, lines 75–88

```js
// auth.js:75-88
export function verifyAuthMessage(message, walletAddress, timestamp) {
    const expected = `SolShot Auth: ${walletAddress} at ${timestamp}`;
    if (message !== expected) {
        return { valid: false, reason: 'Invalid message format' };
    }

    // Check timestamp is recent
    const age = Date.now() - timestamp;
    if (age > AUTH_TIMEOUT || age < -60000) {
        return { valid: false, reason: 'Auth message expired' };
    }

    return { valid: true };
}
```

The message contains exactly two fields: the wallet address (public, non-secret) and the timestamp
(a Unix millisecond integer). There is no random nonce, no session ID, no connection ID, and no
server-generated challenge included in the message. The timestamp determines whether the signature
is "fresh" but does not make it unique — the same timestamp value is valid for any connection that
calls `authenticate` before `AUTH_TIMEOUT` elapses.

### 2. AUTH_TIMEOUT is 5 Minutes — Hard-Coded, Not Configurable

**File:** `server/middleware/auth.js`, line 28

```js
const AUTH_TIMEOUT = 5 * 60 * 1000; // 5 minutes — signature must be recent
```

`AUTH_TIMEOUT` is a `const` in module scope. It is not exported from the module and has no call
sites outside `auth.js`. It cannot be overridden via environment variable. There is no documentation
of any intent to make it configurable. The .env.example (line 31) configures only `JWT_SECRET`, not
`AUTH_TIMEOUT`.

The window is 300,000 milliseconds — 300 seconds. A round-trip WebSocket auth takes less than
500 ms in practice. The 300-second window is nominally for clock-skew tolerance but exceeds any
realistic clock-skew requirement by two orders of magnitude.

### 3. No Consumed-Signature Store Exists Anywhere

A comprehensive search of the server source for any data structure that would track or invalidate
used signatures:

```
Pattern searched: usedAuthSig, seenSig, replayProtect, nonceSig, authHistory,
                  usedNonce, seenNonce, usedSigs, authNonce
Result: No matches found (server/*, confirmed)
```

The only nonce-like variable in `main.js` is `ms.turnSequence` (match turn counter), which is
entirely unrelated to authentication.

The `verifiedBurnTxs` Set (used for prestige burn replay protection in `main.js:~43`) demonstrates
that the development team was aware of the replay-protection pattern for other transaction types,
but this pattern was not applied to authentication signatures.

### 4. The authenticate Handler — No Guard Against Replay

**File:** `server/socket-io/main.js`, lines 533–553

```js
// main.js:533-553
client.on('authenticate', async (data) => {
    // H015: Null payload guard
    if (!data || typeof data !== 'object') {
        client.emit('authResult', { success: false, reason: 'Missing payload' })
        return
    }
    const result = handleAuthenticate(client, data)
    if (result.success) {
        authenticatedWallets[client.id] = result.walletAddress
        logger.info({ socketId: client.id }, '[Auth] Socket authenticated')
        try {
            await loadMilestoneState(result.walletAddress)
        } catch (err) {
            console.warn(`[Auth] Failed to load milestone state:`, err.message)
        }
    }
    client.emit('authResult', result)
})
```

The handler calls `handleAuthenticate`, which calls `verifyAuthMessage` + `verifyWalletSignature`
and returns success. If success, `authenticatedWallets[client.id] = result.walletAddress` is set.
There is no lookup against any "used signatures" store before or after this sequence.

### 5. handleAuthenticate — Verification Without Consumption

**File:** `server/middleware/auth.js`, lines 127–148

```js
// auth.js:127-148
export function handleAuthenticate(client, { walletAddress, message, signature, timestamp }) {
    // Verify message format
    const msgCheck = verifyAuthMessage(message, walletAddress, timestamp);
    if (!msgCheck.valid) {
        return { success: false, reason: msgCheck.reason };
    }

    // Verify signature
    const sigCheck = verifyWalletSignature(walletAddress, message, signature);
    if (!sigCheck.valid) {
        return { success: false, reason: sigCheck.reason };
    }

    // Generate JWT
    const token = generateToken(walletAddress);

    // Mark socket as authenticated
    client.walletAddress = walletAddress;
    client.isAuthenticated = true;

    return { success: true, token, walletAddress };
}
```

`verifyWalletSignature` (lines 38–65) decodes the base64 signature, verifies the Ed25519 signature
over the message bytes using NaCl, and returns `{ valid: true }` or `{ valid: false }`. It does not
record that this signature was used. Calling `handleAuthenticate` twice with identical arguments
will produce `{ success: true }` both times.

### 6. rejoinRoom — Same Vulnerability

**File:** `server/socket-io/main.js`, lines 776–803

The `rejoinRoom` handler also verifies an Ed25519 signature to restore a disconnected session. It
calls the same `verifyAuthMessage` + `verifyWalletSignature` pair (lines 792–803) with no consumed-
signature check. A captured rejoin tuple is equally replayable within the timestamp window.

```js
// main.js:792-803
const msgCheck = verifyAuthMessage(message, walletAddress, timestamp)
if (!msgCheck.valid) { ... return }

const sigCheck = verifyWalletSignature(walletAddress, message, signature)
if (!sigCheck.valid) { ... return }
// No: if (usedSigs.has(signature)) return  ← this line does not exist
```

## Attack Scenarios

### Scenario 1: Network Interception on Shared Infrastructure

**Precondition:** Attacker and victim share a network segment (e.g., public WiFi, coffee shop,
conference, LAN party).

1. Victim opens SolShot and authenticates. The `authenticate` event is transmitted as a WebSocket
   frame over the TLS connection.
2. With TLS, direct capture requires a MITM position. However, WebSocket traffic observed via a
   browser extension, debugging proxy (Charles, Burp, mitmproxy), or compromised extension leaks
   the plaintext after TLS termination.
3. Attacker captures `{ walletAddress, message, signature, timestamp }`.
4. Within 5 minutes of the victim's `timestamp`, attacker opens a new WebSocket connection to the
   SolShot server and emits `authenticate` with the captured tuple.
5. `verifyAuthMessage`: timestamp age is within AUTH_TIMEOUT — passes.
6. `verifyWalletSignature`: the Ed25519 signature is valid over the message — passes.
7. Attacker's socket receives `authResult: { success: true, token: ..., walletAddress: victim }`.
8. `authenticatedWallets[attacker.socketId] = victim.walletAddress`.

Attacker now has a server-authenticated socket attributed to the victim wallet.

### Scenario 2: XSS-Assisted Replay (Most Realistic Vector)

The ARCHITECTURE.md Section 3 confirms: "No Content Security Policy headers configured" and
`window.socket` is exposed as a global. If any XSS is achieved in the client (no CSP, so any
injected script runs freely):

1. Injected script intercepts `socket.emit` by wrapping the function.
2. When the victim's legitimate `authenticate` emission fires, the interceptor captures the payload.
3. Injected script sends the captured payload via `fetch` or WebSocket to attacker-controlled
   server.
4. Attacker replays the tuple on a new socket within 5 minutes.

This vector requires no network-layer access — only JavaScript execution in the victim's browser
tab. Combined with the absence of CSP, the XSS surface in a React app with external dependencies
is non-trivial.

### Scenario 3: Compromised Client Machine / Shared Session

If a user authenticates on a shared or compromised machine, the authentication payload logged by
any monitoring tool (DevTools, browser extension, proxy) is replayable by anyone with access to
that machine within the 5-minute window.

## What an Attacker Can Do With a Replayed Session

### Direct (Off-Chain) Capabilities

With a replayed session attributed to victim's wallet:

1. **SHOT milestone farming:** The session can emit events that trigger SHOT milestone checks
   (`recordMatchPlayed`). Milestone state is in-memory, keyed by wallet address. Farming milestones
   on the victim's behalf corrupts their milestone state.

2. **Prestige tier manipulation:** The `prestigeBurn` handler uses `authenticatedWallets[client.id]`
   to identify the wallet (main.js line 1612). With a replayed session, `prestigeBurn` is attributed
   to the victim. Combined with H001 (burnAmount=0 bypass), an attacker can advance the victim's
   prestige tier without the victim burning any SHOT.

3. **Room creation and queue entry in victim's name:** All wagered room and queue events use
   `authenticatedWallets[client.id]` as the wallet source (confirmed at main.js lines 1124, 1247,
   1276, 1303, 1378). An attacker creating a wagered room under the victim's identity causes the
   victim's wallet address to appear in `wagerStates`, which is the wallet used for on-chain escrow
   creation. The attacker cannot steal SOL from the escrow (Anchor program enforces on-chain wallet
   ownership for deposits), but they can create fraudulent escrow PDAs chargeable to the server's
   authority wallet.

4. **Stats poisoning:** Match results written to MongoDB use
   `authenticatedWallets[winnerId]` (main.js line 2216). A replayed session participating in a
   match will have its outcome attributed to the victim's wallet address in persistent storage.

5. **Re-auth wallet swap compound:** Combined with M12 (re-authentication on same socket not
   blocked), an attacker who holds the replay can authenticate as victim, then immediately re-
   authenticate as themselves. This creates a brief window where the victim's wallet is associated
   with the attacker's socket for milestone/prestige side effects before the swap.

### Why Direct SOL Theft is Not Achievable

SOL wager theft is blocked by the Anchor escrow program, which enforces on-chain ownership:

- The `deposit_wager` instruction requires the player to sign the transaction with their private
  key. An attacker who has replayed the off-chain auth cannot sign on-chain transactions as the
  victim — that requires the victim's private key, not the auth signature.
- The `settle_match` instruction pays to the on-chain `winner` account, not to whatever address the
  server provides. If the attacker has manipulated server state to name themselves winner, the
  settlement requires their actual wallet — which would be correct for them.

The severity is therefore CRITICAL for session impersonation and off-chain state corruption, but
does not extend to direct SOL theft from the victim in the escrow-enabled path.

## Severity Assessment

### Why CRITICAL

The hypothesis rated this CRITICAL. This rating is **confirmed**, for the following reasons:

1. **The vulnerability is real and complete.** No consumed-signature store exists. The message
   contains no nonce. The 5-minute window is 300 seconds. The attack requires only possession of
   a previously-captured valid auth tuple.

2. **The attack vector is practical.** XSS-assisted interception (Scenario 2) is the primary
   realistic vector. The client has no CSP, exposes `window.socket` as a global, and is a React
   app loading external NPM packages. Any XSS-susceptible dependency achieves full interception.

3. **The broader auth context amplifies the impact.** The JWT is never consumed (C5/ARCHITECTURE).
   Session identity rests entirely on the in-memory `client.isAuthenticated` flag, which is set
   by the replayed authentication. There is no secondary verification layer to catch the replay.

4. **Off-chain state consequences are financial.** Prestige tiers have monetary cost (SHOT burns
   to advance). Corrupting or fraudulently advancing a victim's prestige tier has direct economic
   value. The `verifiedBurnTxs` replay-protection Set for burns proves the team understands the
   value of consumed-state protection — it simply was not applied to authentication.

5. **Multiple entry points share the vulnerability.** Both `authenticate` and `rejoinRoom` are
   vulnerable. A replayed `rejoinRoom` for an active wallet (during its 30-second reconnect window)
   would steal the victim's active match session, including their in-progress wager position.

### Scope Limitation

The CRITICAL rating is bounded: it covers off-chain session impersonation, SHOT/prestige
manipulation, and stats poisoning. Direct SOL theft from escrow is not achievable via this vector
alone because the Anchor program requires on-chain signing with the victim's actual private key.

## Root Cause

The message format `"SolShot Auth: <walletAddress> at <timestamp>"` was designed with the timestamp
as an implicit nonce — the assumption being that the same timestamp would never be reused because
the client generates a fresh timestamp per auth attempt. This assumption is valid for the original
client, but it fails under adversarial replay because:

1. The timestamp is public information (included in the plaintext message, not derived from a
   server secret).
2. The window is 300 seconds, not 1 second. A one-second freshness window would make replay nearly
   impractical; 300 seconds makes it comfortably exploitable.
3. No state is maintained on the server to detect that a specific signature has already been used.
4. The NaCl `detached.verify` function is stateless by design — it verifies cryptographic
   correctness, not freshness. The application layer must handle freshness and uniqueness.

## Recommendations

### Recommendation 1 (PRIMARY — Immediate): Add Consumed-Signature Store

Maintain a `Map<sigHash, expiresAt>` of recently-used auth signatures in `auth.js`. On each
successful verification, check the Map before accepting; add to it after accepting. Evict expired
entries periodically.

**File:** `server/middleware/auth.js`

```js
// Add at module level, after AUTH_TIMEOUT (line 28):
const usedAuthSigs = new Map(); // sha256(signatureBase64) → expiresAt (ms)

// Periodic eviction to prevent unbounded growth (~every 30s):
setInterval(() => {
    const now = Date.now();
    for (const [hash, expiresAt] of usedAuthSigs) {
        if (now > expiresAt) usedAuthSigs.delete(hash);
    }
}, 30_000);

// In verifyWalletSignature(), after the nacl.sign.detached.verify() call succeeds (after line 55):
const sigHash = crypto.createHash('sha256').update(signatureBase64).digest('hex');
if (usedAuthSigs.has(sigHash)) {
    return { valid: false, reason: 'Signature already used' };
}
usedAuthSigs.set(sigHash, Date.now() + AUTH_TIMEOUT);
// NOTE: Add() must happen here, before returning { valid: true }, not in the caller.
// If placed in the caller, a concurrent replay that reaches verifyWalletSignature
// before the caller's .set() fires will pass both checks (same race that affects
// verifiedBurnTxs in the prestige burn handler).
```

**Memory cost:** Each entry is a 64-char hex string + 8-byte timestamp. At 1 auth/second (high
load), the Map holds at most 300 entries. Negligible.

**Correctness:** The sha256 hash of the base64 signature is deterministic and effectively unique
per signature (Ed25519 signatures are 64 bytes; collision probability is negligible for practical
purposes).

### Recommendation 2 (PRIMARY — Immediate): Reduce AUTH_TIMEOUT to 60 Seconds

**File:** `server/middleware/auth.js`, line 28

```js
// Before:
const AUTH_TIMEOUT = 5 * 60 * 1000; // 5 minutes

// After:
const AUTH_TIMEOUT = 60 * 1000; // 60 seconds — sufficient for clock-skew tolerance
```

This is a defense-in-depth reduction independent of the consumed-signature store. Even with
Recommendation 1 in place, reducing the window from 300s to 60s limits the replay utility of any
captured signature that bypasses the store (e.g., on server restart, which clears in-memory state).

**Impact on legitimate users:** Negligible. The client signs and transmits the auth message in
under 500 ms. A 60-second clock-skew allowance covers any realistic browser/server clock divergence.
The only user-visible effect would be if a user signs the message and then waits 60 seconds before
submitting — which does not occur in the current client flow.

### Recommendation 3 (SECONDARY): Include a Server-Generated Challenge in the Message

The most robust mitigation is to require a server-generated random nonce in the auth message,
making replay impossible even for an attacker who stores signatures long-term:

**Server side — before `authenticate` event:**
```js
// Expose a challenge endpoint or add a socket event:
client.on('requestAuthChallenge', () => {
    const nonce = crypto.randomBytes(16).toString('hex');
    pendingChallenges.set(client.id, { nonce, expiresAt: Date.now() + 60_000 });
    client.emit('authChallenge', { nonce });
});
```

**Message format change:**
```
"SolShot Auth: <walletAddress> at <timestamp> nonce:<nonce>"
```

**Server verification — in verifyAuthMessage:**
```js
const challenge = pendingChallenges.get(client.id);
if (!challenge || challenge.nonce !== nonce || Date.now() > challenge.expiresAt) {
    return { valid: false, reason: 'Invalid or expired challenge' };
}
pendingChallenges.delete(client.id); // consume
```

This eliminates the replay surface entirely. The nonce is:
- Server-generated (attacker cannot predict it in advance)
- Single-use (consumed on verification)
- Connection-scoped (bound to the specific socket `client.id`)

The trade-off is one additional round-trip before authentication. For a WebSocket flow this is
acceptable. This is the standard secure challenge-response pattern and is the correct long-term
architecture.

### Recommendation 4 (DEFENSE-IN-DEPTH): Apply Same Fix to rejoinRoom

The `rejoinRoom` handler (main.js lines 792–803) uses the same `verifyAuthMessage` +
`verifyWalletSignature` pair without replay protection. The consumed-signature store from
Recommendation 1 would protect this path automatically if `verifyWalletSignature` is the insertion
point. Confirm that the store is checked before both `authenticate` and `rejoinRoom` pathways.
