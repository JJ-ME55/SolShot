# H034 — Settlement Timeout Too Short (1h) for Griefing / Fund Lockup

**Hypothesis ID:** H034
**Investigator:** Dinh's Bulwark Pipeline — Phase 3 Hypothesis Investigation

**Category:** CHAIN-06 (PDA Interaction Patterns), LOGIC-02 (Financial Logic)
**Origin:** CHAIN-06 FINDING-C06-01 (Settlement Timeout), ARCHITECTURE.md M-8, `.audit/ARCHITECTURE.md` Area 3 "23-Hour Dead Zone"

## Verdict: CONFIRMED — PARTIALLY OVERSTATED

**Severity: MEDIUM**

The hypothesis is confirmed in its structural claim: the 1-hour settlement deadline (`SETTLEMENT_TIMEOUT_SECONDS = 3600`) is real, enforced on-chain, and shorter than the litepaper's stated 24-hour auto-refund. A genuine fund lockup window of 23 hours exists between settlement expiry and the earliest player-initiated cancel. However, the hypothesis overstates the severity as a deliberate griefing tool. The 23-hour dead zone is primarily an **operational reliability risk** (server fails to settle a slow BO5 match in time, creating accidental lockup) rather than an attacker-controlled griefing path. An attacker who deliberately triggers the dead zone gains no direct financial benefit; the net result is inconvenience and temporary fund lockup, not theft. Severity is therefore MEDIUM, not HIGH.

The hypothesis also incorrectly states the timeout is 1 hour versus a litepaper claim of 24 hours. The litepaper's 24-hour figure refers to the player **cancel** timeout (TIMEOUT_SECONDS = 86400), not the settlement window. These are two different constants serving two different purposes — the confusion between them is what created the "1h vs 24h" framing in the hypothesis.

## Exact Timeout Values in the On-Chain Program

Three distinct timeout constants are defined in `programs/solshot-escrow/src/lib.rs`:

```rust
/// 24-hour timeout for auto-refund after match activation (in seconds)
const TIMEOUT_SECONDS: i64 = 86400;

/// 48-hour permissionless reclaim timeout (2x normal timeout) — DCA-02
const PERMISSIONLESS_RECLAIM_TIMEOUT: i64 = TIMEOUT_SECONDS * 2; // 172800 seconds

/// 1-hour settlement deadline after match activation (OC-07)
const SETTLEMENT_TIMEOUT_SECONDS: i64 = 3600;
```

**File:** `C:/Users/johnk/SolShot-clean/programs/solshot-escrow/src/lib.rs` lines 19–26

These three constants govern three separate operations:

| Constant | Value | What it controls |
|----------|-------|-----------------|
| `SETTLEMENT_TIMEOUT_SECONDS` | 3600 (1h) | Maximum time from `activated_at` within which server can call `settle_match` |
| `TIMEOUT_SECONDS` | 86400 (24h) | Minimum time from `activated_at` before a player can call `cancel_match` |
| `PERMISSIONLESS_RECLAIM_TIMEOUT` | 172800 (48h) | Minimum time before anyone can call `permissionless_reclaim` |

The constants do not conflict — they are deliberately staggered. The 1-hour settlement window is for the server (normal case). The 24-hour cancel is the earliest player escape hatch. The 48-hour reclaim is the last-resort recovery.

`is_timed_out` is computed against `TIMEOUT_SECONDS` (24h), not `SETTLEMENT_TIMEOUT_SECONDS` (1h):


**File:** `C:/Users/johnk/SolShot-clean/programs/solshot-escrow/src/lib.rs` lines 321–333

**Summary of cancel_match permissions:**

| Caller | State = AwaitingDeposits | State = Active, < 24h | State = Active, >= 24h |
|--------|--------------------------|----------------------|----------------------|
| Authority (server) | YES | NO (OC-05) | NO |
| Player (p1 or p2) | YES | NO | YES |
| Anyone else | NO | NO | NO |

The authority is explicitly blocked from cancelling an Active match (OC-05 constraint), regardless of elapsed time. This is a deliberate design decision to prevent the server from reclaiming funds from Active matches (which could otherwise be exploited to steal a legitimate winner's payout by cancelling instead of settling).

## The 23-Hour Dead Zone

When `settle_match` fails with `SettlementExpired` and the match is in `Active` state with less than 24 hours elapsed:

- **Authority cannot settle:** `SettlementExpired` blocks `settle_match`
- **Authority cannot cancel:** OC-05 blocks `cancel_match` on Active state
- **Players cannot cancel:** `is_timed_out` is false (< 24h elapsed)
- **Permissionless reclaim:** Not available until 48h

This creates a window of **1h to 24h** (23 hours maximum) where no party can act on the escrow. The `.audit/ARCHITECTURE.md` calls this "Area 3: 23-Hour Dead Zone" (confirmed by the SOS on-chain audit).

```
Timeline from activated_at:
  0h      settle_match available (server can settle)
  1h      settle_match expires (SettlementExpired)     <-- dead zone starts
  24h     cancel_match available (player can cancel)   <-- dead zone ends
  48h     permissionless_reclaim available (anyone)
```

**File:** `C:/Users/johnk/SolShot-clean/.audit/ARCHITECTURE.md` lines 288–298

During the dead zone, both players' wager lamports are locked in the escrow PDA. Neither player can access them. They are not permanently lost — the player cancel at 24h rescues the funds — but the lockup is real and unexpected.

## Off-Chain Settlement Error Handling: Does the Server Handle SettlementExpired?

The server's settlement failure path in `main.js` calls `handleSettlementFailure`, which attempts `cancelMatchEscrow`:

```js
// server/socket-io/main.js lines 107–137
async function handleSettlementFailure(roomId, room, ws, error) {
    ...
    try {
        const cancelResult = await cancelMatchEscrow(roomId, p1wallet, p2wallet);
        if (cancelResult.success) {
            console.log(`[Recovery] Immediate cancel succeeded for ${roomId}`);
            return;
        }
    }
    // Store for retry (also calls cancelMatchEscrow in the retry loop)
}
```

**File:** `C:/Users/johnk/SolShot-clean/server/socket-io/main.js` lines 107–137

When `settle_match` fails with `SettlementExpired`, the server calls `cancelMatchEscrow` (authority cancel). But the on-chain `cancel_match` will **also fail** — because the authority is blocked from cancelling Active matches (OC-05). The result:

1. `settle_match` fails: `SettlementExpired`
2. `handleSettlementFailure` calls `cancelMatchEscrow`
3. `cancelMatchEscrow` also fails: `Unauthorized` (authority + Active state not permitted)
4. Failure is stored in `failedSettlements` for retry (up to 5 retries, 60s each)
5. All 5 retries also fail with `Unauthorized`
6. After retry exhaustion, the entry is removed from `failedSettlements`
7. The server has no further recovery mechanism
8. Funds remain locked until the 24h player cancel or 48h permissionless reclaim

The server does **not** distinguish between `SettlementExpired` and other settlement failure reasons. It applies the same cancel-based recovery logic regardless, and that recovery logic is structurally incapable of rescuing an Active escrow that has passed the settlement deadline.

## Can an Attacker Deliberately Trigger the Dead Zone?

The hypothesis frames this as a "deposit, disconnect, and lock opponent's funds for 1h" griefing attack. This framing is imprecise — the real mechanism requires specific conditions.

### The Actual Precondition for the Dead Zone

The dead zone is reached only when ALL of the following are true simultaneously:
1. Both players have deposited (escrow is Active, not AwaitingDeposits)
2. The match has been running for more than 1 hour from `activated_at`
3. The server attempts `settle_match` after the 1-hour deadline

An attacker who deposits and immediately disconnects does **not** trigger the dead zone — this puts the escrow into AwaitingDeposits (if only one player deposited) or Active (if both deposited). For AwaitingDeposits: the server's 2-minute deposit timeout fires `cancelMatchEscrow`, which succeeds (authority cancel of AwaitingDeposits is permitted). Funds are refunded within 2 minutes.

For the dead zone to activate, the attacker needs the match to actually become Active (both players deposit) and then continue for over 1 hour without the server settling it.

### Realistic Path to the Dead Zone: BO5 Match Duration

A BO5 match with maximum turn timer usage:
- 5 rounds × (turn timer: 60s × 2 players × ~10 turns per round) = 5 × 20 min = 100 minutes

A slow BO5 match legitimately exceeds the 1-hour window. This is the primary operational risk: not malicious triggering, but normal gameplay in a long format exceeding the settlement deadline.

### Could an Attacker Deliberately Stall?

Yes, but with constraints:
- The turn timer is 60 seconds per turn (`TURN_TIMEOUT_MS = 60_000` in `main.js` line 141)
- If a player consistently takes 60 seconds per turn and the match goes to 5 rounds, the match takes ~100 minutes
- A deliberate staller must actually play the match (turns expire via forfeit, which triggers settlement — settlement would succeed if it fires within 1h)
- If the staller uses the full 60s per turn without a disconnect, the match stays active and may exceed 1h

The forfeit path in `main.js` also calls `settleMatch` or `cancelMatchEscrow` depending on timing — if forfeit happens before 1h expires, settlement succeeds. If the staller reaches the 1h mark while the match is still nominally Active on the server, and then the server attempts settlement, it will fail.

**Conclusion on griefing viability:** The dead zone is primarily an accidental operational risk from long matches. Deliberate triggering requires active participation in a slow match for 60+ minutes, which is a high-effort, low-reward attack (the attacker also loses their wager if they forfeit, or plays a real match for an hour to achieve a 23h fund lockup with no financial gain).

## The Deposit-and-Disconnect Scenario (What the Hypothesis Described)

The hypothesis specifically describes: "attacker deposits, disconnects, and locks opponent's funds for 1h."

This scenario does not actually produce a 1h lockup. The mechanism:

1. Attacker joins wagered room, both players deposit → escrow is Active
2. Attacker disconnects
3. Server detects disconnect → starts 30s reconnect timer (`RECONNECT_WINDOW_MS = 30000`)
4. After 30s with no reconnect, the server forfeits the disconnected player (opponent wins by forfeit)
5. `settleMatch` is called by the forfeit path, within the 1-hour window (disconnect → 30s → forfeit → settle takes ~35s total)
6. Settlement succeeds; opponent receives their winnings

The opponent's funds are locked for approximately **30–60 seconds** (reconnect window + forfeit processing), not 1 hour. This is the existing disconnect/forfeit behavior and is within the intended design.

For the full 23-hour lockup to materialize, the match must reach the 1-hour mark while still Active (no disconnect forfeit, no turn timer forfeit, both players playing slowly but continuously).

## Financial Impact

**In the accidental (slow BO5) scenario:**
- Both players' funds locked for up to 23 hours (from settlement deadline expiry until 24h player cancel)
- At High Roller (1.0 SOL each), this is a 2.0 SOL lockup for up to 23 hours
- Players receive full refund at 24h player cancel — no permanent loss

**In the deliberate stalling scenario:**
- Same fund lockup, but attacker must play 60+ minutes to achieve it
- Attacker's own funds are also locked (they deposited too)
- No financial gain for the attacker — it is mutual inconvenience
- The attacker loses the match if they forfeit to end the stall early

**Total exposure per incident:** up to 2.0 SOL (High Roller) locked for up to 23 hours. No permanent loss if players trigger cancel at 24h.

**Risk of players not knowing to cancel:** A legitimate user who does not understand the on-chain mechanics may not know to manually call `cancel_match` at the 24h mark. The server has no automated notification or recovery mechanism for this state — `failedSettlements` exhausts its retries and the entry is silently discarded. Players receive no on-chain or off-chain notification that they need to manually cancel.

## Severity Assessment

**Severity: MEDIUM**

The finding confirms a real structural issue — a 23-hour dead zone between settlement expiry and player cancel, with no automated server recovery and no player notification. However, several factors prevent this from being HIGH:

1. **No financial theft:** Funds are temporarily locked, not permanently lost. Players who know the system can cancel at 24h and receive full refunds.

2. **Not an attacker-controlled griefing path with leverage:** An attacker cannot use this to lock *only the opponent's funds* — both players deposit to activate the escrow, and both are equally affected by the lockup. An attacker who triggers the dead zone also traps their own funds.

3. **Requires 60+ minutes of active match play to trigger deliberately:** This is a high-effort, zero-gain attack. The attacker spends 60 minutes playing a wagered match only to achieve mutual 23-hour inconvenience.

4. **Primary risk is operational, not adversarial:** The most likely trigger is a slow legitimate BO5 match that organically exceeds 1 hour — particularly at BO5 with the 60s turn timer.

5. **The 48h permissionless reclaim is the final backstop:** Even if neither player calls cancel at 24h, anyone (including the server, players, or a third party) can call `permissionless_reclaim` at 48h to recover funds.

**Severity rationale: MEDIUM** — confirmed structural gap with real UX/operational impact, bounded fund lockup risk at max 2.0 SOL (High Roller) for max 23 hours, no direct theft path. Upgrades to HIGH if High Roller matches become common and players are not informed of the manual cancel requirement.

## Attack Scenarios

### Scenario A: Accidental Dead Zone — Slow BO5 Match (Primary Risk)

**Prerequisites:** Two legitimate players in a High Roller BO5 match. Both consistently use close to the full 60s turn timer across all 5 rounds.

**Path:**
1. Both players deposit into escrow → `activated_at` set
2. Match proceeds slowly — players use full turn timers
3. At T+60 minutes: `settle_match` deadline expires on-chain
4. Match ends at T+75 minutes (e.g., end of round 4 or 5)
5. Server calls `settleMatchEscrow` → returns `SettlementExpired`
6. `handleSettlementFailure` calls `cancelMatchEscrow` → returns `Unauthorized` (Active state, < 24h)
7. All 5 retries (at 60s intervals) also return `Unauthorized`
8. `failedSettlements` entry expires silently
9. Both players' funds (2.0 SOL) locked for up to 23 hours
10. At T+24h from `activated_at`, either player can call `cancel_match` to recover funds
11. Server has no automated notification to players

**Net result:** Winner does not receive their winnings. Both players receive full refunds at 24h. Winner loses 0.8 SOL net (90% of 2.0 SOL pot minus their 1.0 SOL deposit = 0.8 SOL winnings lost). For a High Roller match this is significant.

**Likelihood:** Low-Medium. Requires a specific slow match format. More likely at BO5 + High Roller than at Quick Match BO1.

### Scenario B: Deliberate Stalling (Attacker-Triggered)

**Prerequisites:** Attacker has 1.0 SOL for High Roller. Attacker is willing to spend 60+ minutes playing.

**Path:**
1. Attacker joins High Roller BO5 match and deposits
2. Attacker deliberately takes the full 60s per turn across all rounds
3. At T+60 minutes, the settlement deadline expires
4. Attacker continues playing until the match ends naturally after T+60 minutes
5. Server settlement fails; funds locked until 24h player cancel

**Net result:** Both players' 1.0 SOL locked for up to 23h. Attacker's own funds are also locked. Attacker has no financial gain — this is mutual inconvenience only. Attacker could just as well have forfeited at T+30min (before deadline), which would cause the server to settle the match normally in favor of the leading player.

**Threat actor motivation:** Essentially nil. Griefing requires the attacker to spend 60+ minutes actively playing, lock their own funds, and gain nothing. A more effective griefing tool already exists (H030, joinQueue with zero balance creates a 2-minute deposit timeout for the opponent with zero attacker cost).

## Recommendations

### R1 — Increase SETTLEMENT_TIMEOUT_SECONDS to Cover Maximum Match Duration (PRIMARY)

The cleanest fix, identified by the CHAIN-06 auditor:

```rust
// programs/solshot-escrow/src/lib.rs line 26
// CHANGE:
const SETTLEMENT_TIMEOUT_SECONDS: i64 = 3600;  // 1 hour
// TO:
const SETTLEMENT_TIMEOUT_SECONDS: i64 = 28800;  // 8 hours (covers worst-case BO5)
```

**Justification:** A BO5 match with 60s turn timers, 30s shop phases, and network delays has a realistic maximum of approximately 100 minutes. An 8-hour settlement window provides a 5x safety margin while still enforcing an upper bound that prevents indefinite fund locking. The 24-hour player cancel remains unchanged, so the dead zone shrinks from 23 hours to 16 hours in the pathological case, but more importantly eliminates the dead zone for all realistic match durations.

This requires a program upgrade and redeployment (the timeout is a compile-time constant, not a config parameter). The config PDA could be extended to make it a governance-updateable parameter if runtime flexibility is needed.

### R2 — Add Server-Side Settlement Deadline Monitoring (SECONDARY)

Add a proactive check that warns operators before the deadline expires:

```js
// server/socket-io/main.js or a new monitoring service
// When escrowActive is confirmed, schedule a warning at T+50min:
const warningTimer = setTimeout(() => {
    const escrowState = await getEscrowState(roomId);
    if (escrowState && escrowState.state === 'active') {
        // Telegram alert: "Room X approaching 1h settlement deadline — settle soon"
        await sendTelegramAlert(`[WARNING] Room ${roomId} approaching settlement deadline`);
    }
}, 50 * 60 * 1000);  // warn at 50 minutes
```

This does not fix the underlying issue but gives operators 10 minutes to intervene (e.g., manually trigger settlement if the match is nearly complete).

### R3 — Notify Players When Funds Enter the Dead Zone (SECONDARY)

If settlement fails with `SettlementExpired`, notify both players via the socket that their funds are locked and will be releasable at 24h:

```js
// server/socket-io/main.js — in handleSettlementFailure, when cancelMatchEscrow also fails
// after checking that the failure reason is Unauthorized (Active state):
io.sockets.in(roomId).emit('escrowDeadZone', {
    roomId,
    activatedAt: ws.activatedAt,
    cancelAvailableAt: ws.activatedAt + 86400000,  // 24h from activation
    message: 'Settlement window expired. Your wagers will be refundable at 24h from match start.'
});
```

Players should also be informed in the client UI with a countdown to the 24h cancel window.

### R4 — Consider Making SETTLEMENT_TIMEOUT_SECONDS a Config Parameter (LONG-TERM)

Embedding the timeout as a compile-time constant means any adjustment requires a program upgrade. Adding it to the `GlobalConfig` PDA would allow governance-controlled updates via `update_config`, enabling operators to tune the window without a full redeployment:

```rust
// GlobalConfig (future version)
pub struct GlobalConfig {
    pub authority: Pubkey,
    pub treasury: Pubkey,
    pub ops: Pubkey,
    pub is_paused: bool,
    pub settlement_timeout_seconds: i64,  // governance-updateable
    pub bump: u8,
}
```

This is a non-trivial change that affects account space and all instructions that use the timeout — appropriate as a mainnet-readiness improvement.
