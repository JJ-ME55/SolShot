# H038 — Unbounded In-Memory Growth Across Multiple Stores

**Status:** CONFIRMED
**Severity:** MEDIUM
**Confidence:** HIGH
**Origin:** Hypothesis investigation

---

## Summary

The server maintains at least six in-memory data structures that grow without any upper bound, eviction policy, or TTL mechanism. The primary target of this hypothesis — `verifiedBurnTxs` (a module-level `Set` in `shot-token.js`) — is confirmed unbounded. However, the investigation reveals that `verifiedBurnTxs` is the least dangerous of the unbounded stores in isolation. The more significant risks are:

1. `playerShotState` object in `shot-token.js` accumulates one entry per unique authenticated wallet address and is **never pruned on disconnect or at any other lifecycle event**.
2. `claimedMatchIds` is a per-player `Set` that grows with every completed match and is also never pruned.
3. `verifiedBurnTxs` grows with every confirmed prestige burn, but at 5 tiers maximum per user its absolute growth rate is the most bounded of the three.

None of these stores contributes to OOM on their own at devnet scale. The risk becomes material only at sustained production scale (thousands of distinct wallets connecting over a long uptime), or if the server is not restarted periodically. Given the current single-dyno Render deployment with no persistence restart strategy, this is a **low-urgency medium severity** issue today, but requires a fix before production launch.

---

## Evidence

### 1. `verifiedBurnTxs` — the primary hypothesis target

**File:** `server/services/shot-token.js`, line 42

```js
// Track verified burn tx signatures to prevent replay
const verifiedBurnTxs = new Set();
```

**Lifecycle analysis:**

- Entries are added at line 549 (`verifiedBurnTxs.add(txSignature)`) after a successful on-chain burn verification.
- Entries are loaded from MongoDB on server startup at line 100–103 (`state.verifiedBurnTxs.forEach(tx => verifiedBurnTxs.add(tx))`).
- No removal path exists anywhere in the codebase. There is no TTL, no size cap, no compaction.

**Bounding analysis:**

Each prestige tier can only be unlocked once per wallet (the prestige state machine prevents going backward). There are 5 tiers. Therefore, in the normal game flow, the maximum number of entries contributed by any single wallet is 5. At N wallets, the Set grows to at most 5N entries.

At 88 bytes per Solana base58 signature string plus JavaScript Set overhead (~100 bytes per entry total), 10,000 wallets contributes ~5 MB. This is not OOM-threatening at any realistic scale for a devnet deployment.

**Persistence dual-write:** The Set is also mirrored into the `ServerState.verifiedBurnTxs` MongoDB array (`server/models/ServerState.js`, line 16). The MongoDB document has a hard 16 MB limit. At 88 bytes per signature, the document limit is reached at approximately 181,818 entries, or ~36,364 distinct Diamond-tier users. The DB document risk (noted independently as DB-3 in the DATA-01 context audit) is the more pressing concern for this store than in-process OOM.

**Verdict on primary hypothesis:** CONFIRMED but LOW impact at current scale. The Set is definitively unbounded and has no pruning mechanism. OOM from this store alone requires an implausible number of distinct prestige-burning users without a server restart. The bigger risk is the MongoDB document size limit, which is a separate finding (DB-3).

### 2. `playerShotState` — the more serious unbounded store

**File:** `server/services/shot-token.js`, line 85

```js
// In-memory player SHOT state (keyed by walletAddress)
// Persisted to MongoDB — loaded on authenticate, saved after each match
const playerShotState = {};
```

**Lifecycle analysis:**

- New entries are created lazily by `getPlayerShotState(walletAddress)` (line 128) on first access.
- `getPlayerShotState` is called from `loadMilestoneState`, `recordMatchPlayed`, `prestigeBurn`, `getPrestigeInfo`, `getShotBalance`, and the `prestigeBurn` socket handler — i.e., on every player authentication and every match completion.
- **Zero removal paths exist.** A full-text search of `server/services/shot-token.js` and `server/socket-io/main.js` for `delete playerShotState` returns no results. The `disconnect` handler in `main.js` (lines 705–765) deletes `authenticatedWallets[client.id]` but does NOT touch `playerShotState`.

**Size per entry:**

Each `playerShotState[wallet]` entry contains:
- Numeric scalars: `balance`, `totalMatchesPlayed`, `wageredMatchesPlayed`, `wageredWins`, `consecutiveWins`, `totalBurned`, `lastRewardAt`, `matchesPlayed` — ~8 fields × 8 bytes = ~64 bytes
- `milestonesEarned` array: max 8 strings × ~25 bytes each = ~200 bytes
- `prestigeTier`: scalar
- `claimedMatchIds`: a `Set` (see below)

The `claimedMatchIds` Set within each player entry grows with every match:

**File:** `server/services/shot-token.js`, line 339

```js
if (matchId) state.claimedMatchIds.add(matchId);
```

Match IDs have the form `${roomId}:${round}:${timestamp}` — approximately 35 characters = ~35 bytes per entry. There is no eviction of old match IDs from this Set. After 1,000 matches played, a single player's `claimedMatchIds` Set holds ~35 KB. After 10,000 matches, ~350 KB.

**Aggregate growth at scale:**

| Players (unique wallets) | Matches per player | playerShotState RAM (approx) |
|---|---|---|
| 1,000 | 100 | ~35 MB |
| 1,000 | 1,000 | ~350 MB |
| 10,000 | 100 | ~350 MB |
| 10,000 | 1,000 | ~3.5 GB |

At 1,000 active wallets each playing 1,000 matches, heap usage from this store alone reaches ~350 MB — a serious concern for a single-dyno Render instance with a typical 512 MB–1 GB memory limit.

**Compounding factor — `claimedMatchIds` is also persisted to MongoDB:**

`saveMilestoneState()` (line 214) writes `[...state.claimedMatchIds]` to `User.stats.claimedMatchIds` as a plain array. With 10,000 match IDs per user, each user document approaches 350 KB. MongoDB enforces a 16 MB document limit, which is reached at approximately 457,000 match IDs per user — unlikely in practice, but the growth has no floor.

### 3. `authenticatedWallets` — bounded by active sockets, safe

**File:** `server/socket-io/main.js`, line 45

```js
var authenticatedWallets = {}
```

This object is keyed by `client.id` (Socket.IO socket ID) and is deleted on disconnect (lines 759 and 764). It is bounded by the number of concurrent active sockets, which is itself capped at `MAX_CONNECTIONS_PER_IP * number_of_IPs`. This store does not contribute to long-term growth.

**One edge case noted:** During a 30-second reconnect window, the old `client.id` key is deleted by the deferred cleanup timer (line 759), but a new entry is immediately created for the new socket at rejoin (line 836). The brief window where both entries exist is minor and bounded.

### 4. Other session-scoped stores — bounded, safe

The following stores are all keyed by `roomId` or `socketId` and are cleaned up by `removeRoom()` (lines 213–237) or the disconnect handler:

- `matchStates` — deleted by `removeRoom()` (line 216)
- `goldStates` — deleted by `removeRoom()` (line 217)
- `weaponInventories` — deleted by `removeRoom()` (line 218)
- `shopReady` — deleted by `removeRoom()` (line 219)
- `wagerStates` — deleted by `removeRoom()` (line 220)
- `shopTimers` — cleared by `removeRoom()` (lines 222–225)
- `depositTimers` — cleared by `removeRoom()` (lines 226–228)
- `turnTimers` — cleared by `clearTurnTimer()` called from `removeRoom()` (line 221)
- `pendingReconnects` — deleted at line 738 (timeout fires) and line 826 (successful rejoin)
- `disconnectTimers` — deleted at lines 738 and 824

These stores are not contributing to unbounded growth. The `failedSettlements` Map (line 78) is bounded by the retry logic — entries are deleted after 5 retries (line 86) or on success (line 94). Maximum concurrent entries equals the number of simultaneously-failing match settlements, which is operationally bounded.

### 5. `matchmakingQueues` — bounded under normal operation, weak under abuse

**File:** `server/socket-io/main.js`, line 61

```js
const matchmakingQueues = new Map();
```

Under normal operation, queue entries are consumed when players are matched or removed on disconnect (`removeFromAllQueues`). However, the ERR-03 audit found that `removeFromAllQueues` only removes the first occurrence per socket per queue bucket, allowing a single socket to accumulate multiple entries. This is an abuse scenario that creates transient growth, bounded by the number of concurrent abusive sockets. It does not create permanent unbounded growth.

## Root Cause

The root cause is a missing eviction strategy for `playerShotState`. The design correctly persists state to MongoDB on match end and reloads it on authenticate, but there is no corresponding step to **unload** the in-memory copy when the player disconnects. The `disconnect` handler removes `authenticatedWallets[client.id]` but does not invoke any cleanup of the wallet-keyed `playerShotState[walletAddress]`.

The rationale for keeping state in memory (fast access during matches) is valid. The missing piece is unloading it after the match session ends and the player has disconnected, since the MongoDB copy is the durable source of truth.

The `verifiedBurnTxs` Set has a separate root cause: it is intentionally global (shared across all player sessions) and has no natural per-player lifecycle event that could trigger eviction. Pruning requires a TTL-based approach or migration to a dedicated collection.

## Growth Rate Estimates

### `verifiedBurnTxs` Set

| Distinct Diamond-tier users | In-memory size | MongoDB document size |
|---|---|---|
| 1,000 | ~500 KB | ~440 KB |
| 10,000 | ~5 MB | ~4.4 MB |
| 36,000 | ~18 MB | ~15.8 MB (near 16 MB doc limit) |
| 100,000 | ~50 MB | exceeds MongoDB doc limit |

Growth rate: 5 entries × 88 bytes = 440 bytes per new Diamond-tier user. Not a realistic OOM vector unless the game reaches tens of thousands of Diamond players without a server restart.

### `playerShotState` object (including `claimedMatchIds`)

| Unique wallets ever seen | Matches per wallet | In-memory size |
|---|---|---|
| 100 | 100 | ~3.5 MB |
| 1,000 | 100 | ~35 MB |
| 1,000 | 1,000 | ~350 MB |
| 5,000 | 500 | ~875 MB (OOM on 1 GB dyno) |

This is the actual OOM risk. A production server running for weeks without restart, serving thousands of distinct wallets, will accumulate hundreds of MB of `playerShotState` heap that will never be reclaimed.

## Recommendations

### Fix 1 (PRIMARY): Evict `playerShotState` entries on disconnect

In `server/socket-io/main.js`, in the `disconnect` handler, after `saveMilestoneState` has been called (or can be confirmed to have fired), delete the in-memory entry:

```js
// In disconnect handler, after cleanupRoom():
const walletAddress = authenticatedWallets[client.id];
if (walletAddress) {
    // State is already persisted to MongoDB via saveMilestoneState() at match end.
    // Safe to evict from in-memory cache. Will be reloaded on next authenticate.
    delete playerShotState[walletAddress];
    delete authenticatedWallets[client.id];
}
```

This requires importing or re-exporting `playerShotState` from `shot-token.js`, or adding an explicit `evictPlayerState(walletAddress)` export function. The latter is cleaner:

```js
// shot-token.js — add export:
export function evictPlayerState(walletAddress) {
    if (walletAddress && playerShotState[walletAddress]) {
        delete playerShotState[walletAddress];
    }
}
```

**Caution:** The 30-second reconnect window means the eviction must be deferred until the reconnect window expires (same timing as `delete authenticatedWallets[client.id]` at line 759). During the reconnect window the state must remain in memory for fast rejoin. This is already the correct place to add the eviction call — line 759 in `main.js`.

### Fix 2: Prune `claimedMatchIds` to a rolling window

In `recordMatchPlayed()`, limit `claimedMatchIds` to the most recent N entries. Since the 30-second cooldown already prevents rapid double-claiming, the dedup window only needs to span the cooldown plus a reasonable safety margin (e.g., 24 hours):

```js
// After adding matchId to claimedMatchIds:
if (state.claimedMatchIds.size > 1000) {
    // Convert to array, drop oldest 200 entries, rebuild Set
    const arr = [...state.claimedMatchIds];
    state.claimedMatchIds = new Set(arr.slice(arr.length - 800));
}
```

Also apply the same pruning before writing to MongoDB in `saveMilestoneState()`.

### Fix 3: Migrate `verifiedBurnTxs` to a dedicated MongoDB collection

Move burn transaction replay protection out of the singleton `ServerState` document (which risks hitting the 16 MB document limit) into a dedicated `BurnTx` collection with a TTL index:

```js
// New model: server/models/BurnTx.js
const burnTxSchema = new mongoose.Schema({
    signature: { type: String, required: true, unique: true, index: true },
    walletAddress: { type: String, required: true },
    createdAt: { type: Date, default: Date.now, expires: '365d' }  // TTL: 1 year
});
```

The in-memory `verifiedBurnTxs` Set can remain as a fast first-pass check (populated on startup from the collection). Entries older than 365 days can be allowed to fall out of the Set on the next restart since Solana transactions are immutable and their finality is deterministic within seconds — re-verifying a 1-year-old TX against the chain is acceptable as a fallback.

### Fix 4: Add a global `playerShotState` size monitor

Add a periodic log statement (or Telegram alert if over threshold) to detect heap growth before it causes an OOM crash:

```js
setInterval(() => {
    const walletCount = Object.keys(playerShotState).length;
    if (walletCount > 5000) {
        logger.warn({ walletCount }, '[SHOT] playerShotState growing large — consider restart or eviction policy');
    }
}, 60_000);
```

## Severity Rationale

**MEDIUM** (not HIGH) because:

1. At current devnet scale (dozens to hundreds of concurrent users), none of these stores will cause OOM within a normal deployment cycle.
2. The server is restarted on every Render deploy, which provides a natural (if unintentional) eviction mechanism.
3. The `verifiedBurnTxs` Set growth is practically bounded by the finite number of prestige tiers (5 max per user) and the total user count.
4. No active attacker can directly force accelerated growth of `verifiedBurnTxs` — they can only burn once per signature. They can force `playerShotState` growth by rapidly authenticating many wallets (each `authenticate` call creates a `playerShotState` entry), but this is bounded by the 100-connections-per-IP limit and the 30-events/second ring buffer.

The finding is upgraded from LOW to MEDIUM because:

1. `playerShotState` + `claimedMatchIds` growth is genuinely unbounded and will cause OOM at production scale (thousands of wallets, weeks of uptime).
2. The fix is straightforward and low-risk.
3. The MongoDB document size risk for `verifiedBurnTxs` (DB-3) compounds with the in-memory risk to create two independent failure modes from the same root pattern.
