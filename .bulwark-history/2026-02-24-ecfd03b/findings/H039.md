# H039 — Settlement Data Logged Verbatim: Information Disclosure via console.log Bypassing Pino Redaction

**Audit:** Dinh's Bulwark — Off-Chain Security Audit
**Hypothesis ID:** H039
**Verdict:** CONFIRMED
**Severity:** LOW-MEDIUM (context-dependent; see analysis)
**Status:** Open
**Date:** 2026-02-23
**Auditor:** Hypothesis Investigator
**Sources:**
- `server/socket-io/main.js` — primary

---

## Hypothesis

> Settlement data (wallets, amounts, tx sigs) logged via console.log bypassing pino redaction.

---

## Verdict Summary

**CONFIRMED — with precision adjustment.** Settlement-path `console.log` calls do bypass the pino redaction layer and do emit financial data verbatim to stdout. However, the specific claim that *wallet addresses* appear in the settlement dumps is **partially incorrect**: the two primary settlement log objects (`settlementInfo` at line 2119, `settlementResult` at line 662) do not include wallet addresses in their object shape. Wallet addresses are consumed by `settleMatch()` internally but are not returned in its result object.

What IS confirmed:
1. Settlement financial amounts (wager, totalPot, winnerPayout, treasuryFee, opsFee) logged as verbatim object dumps via `console.log`, bypassing pino.
2. Transaction signatures (Solana txids) logged in the same object dumps.
3. A broader pattern of ~49 raw `console.*` calls throughout `main.js` alone — versus only 3 structured `logger.*` calls — means the pino redaction configuration is effectively decorative for the vast majority of operational logging.
4. Player in-game names correlated with wager amounts in matchmaking logs.

## Evidence

### 1. Pino Infrastructure Is Configured but Marginally Applied

**File:** `server/services/logger.js` (lines 1–26)

```js
const logger = pino({
    level: process.env.LOG_LEVEL || 'info',
    redact: {
        paths: [
            'walletAddress', 'wallet', 'winner', 'loser', 'player',
            'p1wallet', 'p2wallet', 'winnerAddress', 'loserAddress',
            '*.walletAddress', '*.wallet',
        ],
        censor: '[REDACTED]',
    },
    transport: process.env.NODE_ENV !== 'production'
        ? { target: 'pino-pretty' }
        : undefined,
});
```

The logger is imported in four files:

| File | Structured `logger.*` calls | Raw `console.*` calls |
|---|---|---|
| `server/services/escrow.js` | 1 (line 413) | ~20 |
| `server/services/solana.js` | 3 (lines 203, 216, 251) | ~5 |
| `server/services/shot-token.js` | 3 | ~5 |
| `server/socket-io/main.js` | 3 (lines 542, 1638, 2238) | ~49 |

Redaction is applied to 10 calls. Approximately 79 calls emit raw unstructured text or object dumps to stdout/stderr without any field-level redaction.

### 2. Normal Settlement Path — Financial Object Dump (main.js:2111–2119)

**File:** `server/socket-io/main.js`, lines 2111–2119

```js
settlementInfo = {
    wager: ws.amount,
    totalPot: ws.amount * 2,
    winnerPayout: sResult.settlement.winner,
    treasuryFee: sResult.settlement.treasury,
    opsFee: sResult.settlement.ops,
    txSignature: sResult.txSignature
}
console.log('[Solana] Match settled:', settlementInfo)
```

`settlementInfo` is constructed immediately before the `console.log` call and contains:

- `wager` — the per-player SOL wager amount (e.g., `0.5`)
- `totalPot` — `wager * 2` (e.g., `1.0`)
- `winnerPayout` — 90% of pot in SOL (e.g., `0.9`)
- `treasuryFee` — 7% of pot in SOL (e.g., `0.07`)
- `opsFee` — 3% of pot in SOL (e.g., `0.03`)
- `txSignature` — the confirmed Solana transaction ID string (base58, ~88 chars)

All six fields are emitted verbatim to stdout as a Node.js object dump. This call is on the success branch of the normal match-end settlement path — it fires for every successfully wagered match.

**Wallet addresses are NOT present in this object.** `settleMatch()` accepts `winnerAddress` and `loserAddress` as parameters but its return shape (`{ success, settlement: { winner, treasury, ops }, txSignature }`) does not echo them back.

### 3. Forfeit/Disconnect Settlement Path — Raw Result Object Dump (main.js:662)

**File:** `server/socket-io/main.js`, line 662

```js
const settlementResult = await settleMatch(winnerWallet, loserWallet, ws.amount, roomId)
// ...
console.log(`[Solana] Forfeit settlement (${reason}):`, settlementResult)
```

`settlementResult` here is the complete return value of `settleMatch()`:

```js
{
    success: true,
    settlement: { winner: <SOL amount>, treasury: <SOL amount>, ops: <SOL amount> },
    txSignature: <base58 string>
}
```

This is the unfiltered return object from `solana.js:settleMatch()`, logged via `console.log` on the disconnect/forfeit path. The `reason` parameter is a string tag (e.g., `'reconnect_timeout'`, `'leave'`) that is also interpolated into the log prefix.

Same data class as finding 2: financial amounts and txSignature, no wallet addresses, bypasses pino entirely.

### 4. On-Chain Settlement Success Path Uses Structured Logger (solana.js:203)

**File:** `server/services/solana.js`, line 203

```js
logger.info({ matchId, txSignature: result.txSignature }, '[Solana] On-chain settlement');
```

This is the one settlement log call that correctly routes through pino. `matchId` and `txSignature` are not in the redact list (they are not wallet fields), so they still appear in the JSON output — but this is by design and acceptable for auditability. The key observation is that this structured call exists alongside the `console.log` calls: the escrow-enabled production path uses pino, the fallback dev path also uses pino (line 216), but the caller in `main.js` adds its own redundant `console.log` after the fact.

### 5. Escrow Service Startup Logs Treasury/Ops Wallet Addresses (escrow.js:82–86)

**File:** `server/services/escrow.js`, lines 82–86

```js
console.log(`[Escrow] Initialized — authority: ${escrowKeypair.publicKey.toBase58()}`);
console.log(`[Escrow] Program ID: ${PROGRAM_ID.toBase58()}`);
console.log(`[Escrow] Config PDA: ${configPDA.toBase58()}`);
console.log(`[Escrow] Treasury: ${TREASURY_WALLET || 'NOT SET'}`);
console.log(`[Escrow] Ops: ${OPS_WALLET || 'NOT SET'}`);
```

`TREASURY_WALLET` and `OPS_WALLET` are env-var values (wallet addresses) logged at startup. These are not secret — they are the platform's receiving addresses that appear on every settlement transaction on-chain — but their presence in server logs provides a correlation anchor: any log aggregator or log breach reveals the platform's treasury and ops wallet addresses in plaintext, enabling targeted chain surveillance of those addresses.

The escrow authority public key (line 82) is likewise not a secret but is logged here rather than via pino.

## Root Cause

The architecture has two tiers of logging that are used inconsistently:

1. **Pino structured logger** — configured with redaction, used for a small set of high-value events (authentication confirmation, prestige burn, stats persist, on-chain settlement success, dev-mode settlement fallback). 10 call sites total across 4 files.

2. **Raw `console.*`** — used for all other operational logging, including the majority of error paths, recovery paths, settlement success/failure messages, and debug output. ~79 call sites across the same 4 files.

The pino redact configuration works correctly for the calls that pass through it. The problem is that the settlement path in `main.js` constructs its own log object (`settlementInfo`) and emits it via `console.log` **after** the underlying `settleMatch()` call has already logged through pino. This means the settlement event is logged twice: once correctly (pino, in `solana.js`) and once verbatim (console.log, in `main.js`). The `main.js` layer adds no new information — it re-derives the same amounts — but bypasses redaction entirely.

## Severity Assessment

**LOW-MEDIUM.**

The severity is bounded by what the logged data actually discloses:

**Lower bound (LOW):** Transaction signatures are public on the Solana ledger. Financial amounts (wager, payout, fees) are revealed on-chain for every settlement transaction. Anyone monitoring the escrow program's on-chain activity can derive all of these values independently. The server logs add a correlation layer (linking settlement events to timestamps and roomIds) but do not reveal anything that is cryptographically private.

**Upper bound (MEDIUM):** The concern is log infrastructure, not direct secret exposure. If server logs are shipped to a third-party aggregator (Datadog, Logtail, Papertrail — common on Render), the log aggregator receives:
- A financial activity trail for every wagered match (wager amounts, payout breakdown, txSignature per match)
- Treasury and ops wallet addresses (startup log)
- Name-to-wager correlations (matchmaking logs)

This is meaningful for two reasons:
1. **Log aggregator as attack surface.** If the aggregator is compromised or misconfigured, all financial activity is exposed in a searchable, indexed form that is easier to mine than the Solana chain.
2. **Regulatory/compliance.** If the platform later handles higher-value wagers under a jurisdiction with financial data handling requirements, unstructured financial data in third-party logs becomes a compliance issue.

The finding does not represent an active exploit path. It is an information exposure risk that becomes more significant as wager values and player volume increase, and as the log pipeline matures.

---

## Impact

- **Confidentiality:** Financial amounts and transaction IDs for all wagered matches appear in stdout unstructured. Severity increases if logs are externally aggregated.
- **Auditability:** The dual-logging pattern (pino + console.log for the same event) creates redundant log entries that complicate incident reconstruction — the pino entry is structured and searchable; the console.log entry is not.
- **Operational reconnaissance:** Treasury and ops wallet addresses logged at every server startup allow any actor with log access to identify and monitor the platform's receiving addresses on-chain.
- **Privacy (minor):** Player display names correlated with wager amounts in matchmaking logs. Not wallet addresses, but creates a financial profile linkable to community identity.

## Recommendations

**Recommendation 1 (Primary): Remove the redundant console.log at main.js:2119.**

The successful settlement event is already logged correctly at `solana.js:203` via `logger.info`. The `console.log` at `main.js:2119` adds no new information and bypasses redaction. Remove it entirely. If a caller-level log is desired, use `logger.info({ roomId, txSignature: settlementInfo.txSignature }, '[Match] Settlement complete')` — referencing only the txSignature and roomId, not the full financial breakdown.

```js
// Remove this:
console.log('[Solana] Match settled:', settlementInfo)

// If any caller-level log is needed, use:
logger.info({ roomId, txSignature: settlementInfo.txSignature }, '[Match] Settlement complete')
```

**Recommendation 2: Remove the verbatim dump at main.js:662.**

Replace with a structured pino call logging only the txSignature:

```js
// Remove this:
console.log(`[Solana] Forfeit settlement (${reason}):`, settlementResult)

// Replace with:
logger.info({ roomId, reason, txSignature: settlementResult.txSignature }, '[Match] Forfeit settlement complete')
```

**Recommendation 3: Remove or environment-gate the startup wallet address logs in escrow.js:85–86.**

```js
// Remove or gate behind DEBUG level:
console.log(`[Escrow] Treasury: ${TREASURY_WALLET || 'NOT SET'}`);
console.log(`[Escrow] Ops: ${OPS_WALLET || 'NOT SET'}`);
```

These addresses do not need to appear in runtime logs. They are configuration values verifiable through env inspection. If operational confirmation is needed, log only their presence/absence:

```js
console.log(`[Escrow] Treasury: ${TREASURY_WALLET ? 'SET' : 'NOT SET'}`);
console.log(`[Escrow] Ops: ${OPS_WALLET ? 'SET' : 'NOT SET'}`);
```

**Recommendation 4: Remove unconditional per-shot debug logs at main.js:1932 and 1944.**

Gate them behind a debug environment variable:

```js
if (process.env.LOG_LEVEL === 'debug') {
    console.log('[Fire] tanks:', tanks.map(t => ({ id: t.id.slice(0,8), x: Math.round(t.x), y: Math.round(t.y) })))
}
// ...
if (process.env.LOG_LEVEL === 'debug') {
    console.log('[Fire] impact:', result.impact, 'damage:', result.damage)
}
```

**Recommendation 5: Remove financial amounts from matchmaking correlation logs (main.js:1372, 1387).**

Replace per-player name+wager log lines with aggregate/redacted versions:

```js
// Instead of logging names + amounts:
console.log(`[Queue] Matched: ${opponent.name} vs ${sanitizeName(playerName)} in ${matchMode} (${roundType}) @ ${wagerAmount} SOL — room ${roomId}`);

// Log only non-identifying operational data:
console.log(`[Queue] Matched: ${matchMode} (${roundType}) — room ${roomId}`);
```

**Recommendation 6 (Systemic): Establish a logging policy and audit all console.* call sites.**

The ~79 raw `console.*` calls versus 10 structured `logger.*` calls indicates pino was added as an afterthought rather than adopted as the primary logging instrument. A one-time audit pass should:
- Replace financial/identity-containing `console.*` calls with `logger.*` calls using structured fields
- Remove debug-only logs that are unconditionally active
- Ensure no wallet address string interpolation appears anywhere (pino redact only catches object field names, not interpolated strings — see `shot-token.js:184,222`)

## Conclusion

The hypothesis is **confirmed**. Settlement data (wager amounts, payout breakdown, transaction signatures) is logged verbatim via `console.log` at `main.js:2119` and `main.js:662`, bypassing pino redaction entirely. The pino infrastructure exists and is correctly configured but is applied to only ~11% of logging call sites across the settlement path. The specific claim about wallet addresses appearing in these dumps is **not confirmed** for the primary settlement log objects — wallet addresses are not echoed in the return shape of `settleMatch()`. However, wallet addresses do appear in other bypassed-redaction contexts (startup logs for treasury/ops, string interpolation in shot-token.js error logs). The severity is LOW-MEDIUM: no cryptographic secrets are exposed, but financial activity records in unstructured form in external log aggregators represent a meaningful operational disclosure risk.
