# H046 — RPC Fails Open Default Behavior

**Status:** CONFIRMED
**Severity:** HIGH
**Confidence:** HIGH
**Origin:** Hypothesis Investigation

---

## Summary

A comprehensive audit of all RPC-dependent error handlers across `server/services/solana.js`, `server/services/escrow.js`, `server/services/shot-token.js`, and the calling code in `server/socket-io/main.js` reveals a mixed posture: some calls fail correctly closed, but three significant fail-open patterns exist with direct financial consequences. Additionally, several nominally fail-closed paths contain second-order fail-open fallthrough that nullifies the intended protection.

The hypothesis is **CONFIRMED** but requires important precision: the individual service functions in `escrow.js` and `shot-token.js` are generally well-structured (they catch and return `{ success: false }`). The critical fail-open behaviors are concentrated in two places:

1. The outer catch blocks in `main.js` around `verifyBalance()` calls (the established H001 pattern — wager bypass on outer exception)
2. The `refundWager()` function in `solana.js`, which silently falls through to `{ success: true, txSignature: null }` whenever the on-chain cancel fails or is missing arguments
3. The standalone `getBalance()` utility function in `solana.js`, which returns `0` on RPC error — fail-open for any caller that uses `0` as a permissive sentinel

A fourth structural problem — `getConfigState()` in `escrow.js` returning `null` silently on any error — is fail-open for the operational state of the entire escrow program but has no current callers that act on the result.

## Key Findings

### Finding 1 — CONFIRMED HIGH: `refundWager()` Fail-Open Fallthrough (solana.js:241–253)

The `refundWager()` function in `solana.js` has a structural fail-open. When the on-chain cancel fails (or when called with missing arguments from `main.js:690`), it falls through to the dev-mode log path and returns `{ success: true, txSignature: null }`. Callers receive a success signal even though the on-chain cancel did not execute. Funds remain locked in the PDA until the 48-hour permissionless reclaim window.

This is the *second-order fail-open*: `cancelMatchEscrow()` in `escrow.js` correctly returns `{ success: false }`, but `refundWager()` in `solana.js` ignores that failure and promotes it to `success: true`.

```js
// solana.js lines 241–253
if (isEscrowEnabled() && matchId && playerOneAddress && playerTwoAddress) {
    const result = await cancelMatchEscrow(matchId, playerOneAddress, playerTwoAddress);
    if (result.success) {
        return { success: true, txSignature: result.txSignature };
    }
    console.error('[Solana] On-chain cancel failed:', result.error);
    // ← NO RETURN. Falls through.
}

// Fallback: log refund (dev mode)
logger.info({ amount: wagerSOL }, '[Solana] Refund (off-chain)');
return { success: true, txSignature: null };  // ← Caller sees success
```

Additionally, the call at `main.js:690` passes only 2 of 5 required arguments:

```js
// main.js line 688–691 — LOBBY disconnect
const wallet = ws.wallets[client.id]
if (wallet && ws.amount > 0) {
    await refundWager(wallet, ws.amount)  // matchId, p1Addr, p2Addr = undefined
}
```

The `isEscrowEnabled() && matchId && playerOneAddress && playerTwoAddress` guard evaluates to `false` because `matchId` is `undefined`. The function falls directly to `return { success: true }` with no cancel attempted. Neither the return value check nor the missing arguments are flagged anywhere in the call chain.

### Finding 2 — CONFIRMED HIGH: Balance Check Outer Catch Fails Open (main.js:990–992, 1145–1147)

Documented in H001. Reproduced here for completeness. The `verifyBalance()` function in `solana.js` has its own inner catch that returns `{ sufficient: false }` — making it fail-closed for normal RPC errors. However, `getCachedLamports()` (which `verifyBalance` calls) does not have its own try/catch. If `getConnection()` returns a stale or null connection object that throws synchronously on `.getBalance()`, or if `new PublicKey(walletAddress)` throws on a null/invalid address, the exception escapes `verifyBalance`'s inner catch and propagates to `main.js`'s outer catch — which is explicitly labeled "best-effort — skip if RPC unavailable" and contains no `return` statement.

```js
// main.js lines 980–992 (joinRoom)
try {
    const balanceCheck = await verifyBalance(joinerWallet, roomWager)
    if (!balanceCheck.sufficient) {
        client.emit('joinRoomError', { ... })
        return
    }
} catch (err) {
    console.warn('[Solana] Balance check skipped:', err.message)
    // ← NO return. Player joins wagered room.
}
```

### Finding 3 — CONFIRMED MEDIUM: `getBalance()` Returns 0 on Error (solana.js:268–271)

The standalone `getBalance()` utility function returns `0` on any RPC error:

```js
// solana.js lines 262–272
export async function getBalance(walletAddress) {
    const conn = getConnection();
    try {
        const pubkey = new PublicKey(walletAddress);
        const lamports = await conn.getBalance(pubkey);
        return lamports / LAMPORTS_PER_SOL;
    } catch (err) {
        console.error('[Solana] Balance error:', err.message);
        return 0;  // ← Fail-open sentinel value
    }
}
```

This function is currently exported from `solana.js` but not imported by any active server-side module (`main.js` imports `getBalance` from `gold.js`, not `solana.js`). It is therefore latent rather than active. However, it represents a footgun: any future code path that imports and uses this function to make a financial gating decision, treating `0` as "wallet is empty" rather than "balance unknown," would fail open during RPC degradation. The function should either throw on error or return a typed result that distinguishes failure from a genuine zero balance.

### Finding 4 — CONFIRMED MEDIUM: Deposit Timeout Cancel Has No Recovery Path (main.js:1072–1076, 1336–1340)

When the 2-minute deposit timeout fires and `cancelMatchEscrow()` fails:

```js
// main.js lines 1071–1076
if (p1wallet && p2wallet && isEscrowEnabled()) {
    try {
        await cancelMatchEscrow(roomId, p1wallet, p2wallet)
    } catch (err) {
        console.error(`[Escrow] Deposit timeout cancel failed for ${roomId}:`, err.message)
        // ← No entry added to failedSettlements. No retry.
    }
}
io.sockets.in(roomId).emit('escrowDepositTimeout', { roomId })
await removeRoom(roomId)
```

The room is torn down and `escrowDepositTimeout` is emitted regardless of whether the cancel succeeded. If `cancelMatchEscrow` threw (RPC error), any funds deposited by the single player who completed their deposit remain frozen in the PDA until the 48-hour permissionless reclaim. This is in contrast to the settlement failure path, which correctly routes to `handleSettlementFailure` and the retry queue.

### Finding 5 — INFO: `getConfigState()` and `getEscrowState()` Return Null on Error (escrow.js:262–265, 537–540)

Both `getConfigState()` and `getEscrowState()` return `null` for both "account not found" and "RPC error." The comment on `getConfigState` says "Config not initialized or account doesn't exist" — but an RPC timeout also returns `null`, which is indistinguishable from the legitimate "not yet initialized" state. For `getEscrowState()`, the `main.js` call site correctly handles `null` as a failure (emits `escrowError` to client). For `getConfigState()`, there are no current callers in the match lifecycle, so operational impact is bounded to admin/monitoring use.

## Verdict

**H046 is CONFIRMED.** The fail-open pattern is real, confirmed by direct code inspection, and is not limited to the one pattern in H001. Five distinct fail-open behaviors exist:

| # | Location | Behavior | Severity | Financial Impact |
|---|----------|----------|----------|-----------------|
| F1 | `main.js:990–992`, `1145–1147` | Balance check outer catch proceeds without return | HIGH | Zero-SOL wallets enter wagered matches |
| F2 | `solana.js:241–253` | `refundWager()` falls through on cancel failure, returns `success: true` | HIGH | Deposited funds frozen in PDA; caller unaware |
| F3 | `main.js:690` | `refundWager()` called with 2 of 5 args; escrow cancel guard evaluates false | HIGH | LOBBY disconnect never cancels on-chain escrow |
| F4 | `main.js:1072–1076`, `1336–1340` | Deposit timeout cancel failure swallowed, no recovery entry added | MEDIUM | Partial deposit frozen in PDA with no retry path |
| F5 | `solana.js:262–272` | `getBalance()` returns `0` on RPC error | MEDIUM (latent) | Any future caller making a gating decision treats failure as empty balance |

The fail-closed behaviors are functioning correctly for: `verifyBurnTransaction()`, `settleMatchEscrow()`, `createMatchEscrow()`, `buildDepositTransaction()`, `cancelMatchEscrow()`, `escrowDepositConfirm` on-chain verify, and `prestigeBurn` verification. These represent the majority of call sites by count. The fail-open patterns are concentrated in the financial recovery and refund paths, which is where the consequences are highest.

## Evidence

### Primary Evidence — `refundWager()` Fallthrough (F2)

`server/services/solana.js` lines 235–253:

```js
export async function refundWager(playerAddress, wagerSOL, matchId, playerOneAddress, playerTwoAddress) {
    if (wagerSOL === 0) {
        return { success: true, txSignature: null };
    }

    if (isEscrowEnabled() && matchId && playerOneAddress && playerTwoAddress) {
        const result = await cancelMatchEscrow(matchId, playerOneAddress, playerTwoAddress);
        if (result.success) {
            console.log('[Solana] On-chain refund:', { matchId, txSignature: result.txSignature });
            return { success: true, txSignature: result.txSignature };
        }
        console.error('[Solana] On-chain cancel failed:', result.error);
        // ← MISSING RETURN — falls through to success
    }

    logger.info({ amount: wagerSOL }, '[Solana] Refund (off-chain)');
    return { success: true, txSignature: null };  // Reached on both: missing args AND cancel failure
}
```

### Primary Evidence — LOBBY Disconnect Missing Args (F3)

`server/socket-io/main.js` lines 686–691:

## Relationship to H001

H046 extends H001. H001 identified the `verifyBalance()` outer catch fail-open specifically. H046 confirms that pattern (F1) and identifies four additional fail-open behaviors (F2–F5). The `refundWager()` fallthrough (F2 + F3) is the most severe new finding because it causes an active `{ success: true }` return value on a failed on-chain operation — a silent lie propagated to callers that have no way to detect the failure.

## Recommendations

**F2 — Add explicit return on `refundWager()` cancel failure (`solana.js:247`):**

```js
if (isEscrowEnabled() && matchId && playerOneAddress && playerTwoAddress) {
    const result = await cancelMatchEscrow(matchId, playerOneAddress, playerTwoAddress);
    if (result.success) {
        console.log('[Solana] On-chain refund:', { matchId, txSignature: result.txSignature });
        return { success: true, txSignature: result.txSignature };
    }
    console.error('[Solana] On-chain cancel failed:', result.error);
    return { success: false, error: result.error };  // ADD THIS — do not fall through
}
```

**F3 — Pass all required arguments to `refundWager()` at `main.js:690`:**

```js
} else if (ms.status === MATCH_STATES.LOBBY) {
    const wallet = ws.wallets[client.id]
    const p1w = ws.wallets[room.host?.socketId]
    const p2w = ws.wallets[room.player?.socketId]
    if (wallet && ws.amount > 0) {
        await refundWager(wallet, ws.amount, roomId, p1w, p2w)
    }
}
```

**F4 — Add deposit timeout cancel failure to `failedSettlements` (`main.js:1072–1076`, `1336–1340`):**

```js
try {
    await cancelMatchEscrow(roomId, p1wallet, p2wallet)
} catch (err) {

    failedSettlements.set(roomId, {
        matchId: roomId,
        p1wallet,
        p2wallet,
        wagerSOL: wsCheck.amount || 0,
        failedAt: Date.now(),

```

**F1 — Close the outer catch in `main.js` (see H001 recommendation for full fix):**

```js
} catch (err) {
    console.error('[Solana] Balance check failed:', err.message)
    client.emit('joinRoomError', { reason: 'Unable to verify balance. Please try again.' })

```

**F5 — Replace `getBalance()` silent zero with explicit error propagation:**

```js
export async function getBalance(walletAddress) {
    const conn = getConnection();
    const pubkey = new PublicKey(walletAddress);
    const lamports = await conn.getBalance(pubkey);  // Let callers handle rejection
```

Or use a typed return: `return { sol: lamports / LAMPORTS_PER_SOL, error: null }` vs `return { sol: null, error: err.message }`.
