# H050 — trust proxy Not Configured: HTTP Rate Limiter Bypassed on Render

**Status:** CONFIRMED
**Severity:** MEDIUM
**Confidence:** HIGH
**Origin:** Hypothesis Investigation
**Categories:** WEB-02 (Security Headers / Infrastructure), ERR-03 (Rate Limiting)

---

## Summary

`app.set('trust proxy', ...)` is absent from `server/index.js`. Express defaults to `trust proxy: false`. The server is deployed on Render, a reverse-proxy infrastructure that injects `X-Forwarded-For` on every inbound HTTP request.

`express-rate-limit` v8 ships a built-in validation that throws `ERR_ERL_UNEXPECTED_X_FORWARDED_FOR` when `X-Forwarded-For` is present in the request headers AND `trust proxy` is `false`. The throw is caught by the library's own `handleAsyncErrors` wrapper, which calls `next(error)`. Express's default error handler responds `500 Internal Server Error` and the rate-limit middleware returns without incrementing any counter or enforcing any limit.

**The practical effect on production Render deployment:** the HTTP rate limiter (`httpLimiter`, 100 req / 15 min) never enforces anything against any client. Every HTTP request that carries `X-Forwarded-For` — which is every request on Render — causes the middleware to error out before the counter is incremented. Rate limiting is silently non-functional on all HTTP endpoints.

The Socket.IO connection-per-IP limiter is **not affected** because it reads `x-forwarded-for` manually from the handshake headers and does not use `req.ip` or `express-rate-limit`.

### 5. `handleAsyncErrors` Routes the ValidationError to `next(error)`

```js
// express-rate-limit dist/index.mjs lines 794-800
var handleAsyncErrors = (fn) => async (request, response, next) => {
    try {
        await Promise.resolve(fn(request, response, next)).catch(next);
    } catch (error) {
        next(error);
    }
};
```

The thrown `ValidationError` propagates up through `keyGenerator`, exits the `rateLimit` middleware body, and is caught here. `next(error)` is called. The rate-limit counter is never incremented and no `429` response is ever sent.

Render's routing layer is a multi-tenant reverse proxy. Per Render's infrastructure documentation, `X-Forwarded-For` is set on all inbound requests to Web Service instances. There is no opt-out. The header is always present in production.

The comment at line 39-40 explicitly states:

The Socket.IO connection limiter is correctly written for the Render proxy environment. The HTTP rate limiter is not.

## Impact Analysis

### Primary Impact: HTTP Rate Limiter Non-Functional in Production

The `httpLimiter` never fires a `429`. Any client on Render (which is every client in production) can send unlimited requests to all HTTP endpoints. The 100 req/15 min limit that the developer configured and believes is active is silently not enforced.

### Secondary Impact: Brute-Force Path to Admin Endpoints

`POST /api/admin/reload-keys` and `GET /stats` require an `ADMIN_API_KEY` header. The key is a randomly generated value (Render `generateValue: true` for `JWT_SECRET`, but `ADMIN_API_KEY` is `sync: false` — set manually). Without rate limiting, an attacker can attempt unlimited guesses at the `ADMIN_API_KEY` header value. The key format and entropy are not documented in the codebase, so the actual brute-force difficulty is unknown, but the rate limiter is the only throttle between the attacker and the key.

If `ADMIN_API_KEY` is guessed or leaked:
- `POST /api/admin/reload-keys` triggers `process.kill(process.pid, 'SIGHUP')` on Linux/Render, forcing a credential reload from disk. If the attacker can influence the credentials file (a separate attack), this provides a trigger.
- `GET /stats` returns financial metrics and internal server state.

### Third Impact: DoS Surface on All Endpoints

Without a functional rate limiter, a single attacker can send sustained high-volume requests to `/health` or `/` to generate server load with no throttling. The per-IP Socket.IO connection limit (100 connections/IP) still applies to WebSocket connections, but HTTP requests are unthrottled.

### Scope Limitation

The Socket.IO connection limiter, the per-socket ring-buffer event rate limiter, and the per-socket `createRoom` throttle are all unaffected. Only the `express-rate-limit` HTTP middleware is broken. The financial wager paths (createRoom, joinRoom, fire, etc.) all go through Socket.IO, not HTTP. The financial impact is therefore constrained to the admin endpoint brute-force vector rather than the core wagered match flow.

## Relationship to Architecture Document

The architecture document (`.bulwark/ARCHITECTURE.md`) listed this as M-7 (MEDIUM, Infrastructure) with the description "trust proxy not configured for Render." The WEB-02 context auditor flagged it as Finding W9 (MEDIUM) and the ERR-03 auditor flagged it as ERR-03-F01 (MEDIUM) noting "trust proxy not confirmed; HTTP rate limiter may key on proxy IP." Both prior assessments treated this as an IP-bucketing problem — the rate limiter keys on the proxy IP instead of the client IP, meaning all clients share one bucket.

That assessment understated the actual severity. The behavior is not that all clients share a bucket and exhaust it faster — it is that no bucket is ever incremented because the validation throws before any counting occurs. The rate limiter does not degrade to proxy-IP-level accuracy; it fails entirely.

## Verdict

**CONFIRMED.** The hypothesis is confirmed and the impact is worse than originally hypothesized. The rate limiter does not group all users under one proxy-IP bucket — it throws an error on every request and never counts anything. The HTTP rate limiter is completely non-functional in the Render production deployment.

Severity is maintained at MEDIUM (not elevated to HIGH) because:
1. The financial wager paths operate over Socket.IO, not HTTP, and have independent rate limiting via the ring-buffer system.
2. The admin endpoints (`/stats`, `/api/admin/reload-keys`) have a secondary `requireAdminKey` auth guard that remains effective.
3. The bug is a configuration omission with a one-line fix, not a deep architectural flaw.

The finding would be HIGH if the admin key were weak or predictable, because the rate limiter is the only brute-force control on that endpoint. That is a compounding risk that should be noted.

## Recommendations

### Fix 1 — Add `trust proxy` Setting (Required)

Add the following immediately after `const app = express()` in `server/index.js`:

```js
// Trust Render's single reverse-proxy hop so req.ip reflects the real client IP
// and express-rate-limit can correctly bucket requests per user.
if (process.env.NODE_ENV === 'production') {
    app.set('trust proxy', 1);
}
```

Using `1` (number) rather than `true` (boolean) is deliberate and important:
- `app.set('trust proxy', 1)` trusts exactly one hop — the Render load balancer. `req.ip` becomes the first `X-Forwarded-For` value, which is the real client IP.
- `app.set('trust proxy', true)` trusts all proxies unconditionally, which express-rate-limit v8 explicitly forbids (it throws `ERR_ERL_PERMISSIVE_TRUST_PROXY`) because it allows spoofing `req.ip` via a crafted `X-Forwarded-For` header.

The `NODE_ENV === 'production'` guard ensures local development (no proxy) is unaffected. In dev, `req.ip` is the direct socket address, which is correct.

### Fix 2 — Verify express-rate-limit Validates the Setting (No Further Change Needed)

With `app.set('trust proxy', 1)`, Express will:
1. Set `req.ip` to the leftmost `X-Forwarded-For` value (the real client IP, stripped of the Render proxy hop).
2. Return `1` (not `false`, not `true`) from `app.get('trust proxy')`.

The express-rate-limit validation in `xForwardedForHeader` checks `request.app.get("trust proxy") === false`. With the setting at `1`, this check is `false` and no error is thrown. The `trustProxy` check at line 317-323 only throws for `=== true`. The value `1` passes both checks. No additional library configuration is needed.

### Fix 3 — Audit ADMIN_API_KEY Entropy (Separate, Compounding Risk)

The `ADMIN_API_KEY` is set as `sync: false` in `render.yaml`, meaning it is entered manually by the operator. There is no documentation on its required length or format in `server/.env.example` (which does not include `ADMIN_API_KEY` at all — a separate gap noted in W12). If the key is short or follows a predictable pattern, the absence of rate limiting creates a meaningful brute-force window. This should be audited and documented independently of the trust proxy fix.
