# H051 — txSignature No Format Validation

**Audit:** Dinh's Bulwark — Off-Chain Security
**Hypothesis ID:** H051
**Date:** 2026-02-23
**Investigator:** Hypothesis Investigator (Phase 3)
**Status:** CONFIRMED (PARTIAL)
**Verdict:** MEDIUM — `txSignature` is accepted without base58 format or length validation in both the `prestigeBurn` and `escrowDepositConfirm` handlers. A malformed signature passed to `getParsedTransaction` does not crash the server (the catch block absorbs the RPC rejection) and cannot produce a false positive verification — malformed input causes `verifyBurnTransaction` to return `{ valid: false }` via the catch path, not a bypass. However, the unvalidated string is stored in `ws.deposits[client.id]` (a persistent in-memory record), is logged to console, and in `escrowDepositConfirm` the deposit is accepted in dev-mode (escrow not enabled) regardless of the signature value. The practical attack surface is low for prestige burns; it is higher for escrow deposit confirmation where the field is used to record "which player deposited" even though the signature content is never re-examined.

---

## 1. Summary

Two socket handlers accept `txSignature` from the client:

1. `prestigeBurn` (`main.js:1611`) passes it to `verifyBurnTransaction()` (`shot-token.js:457`) which calls `connection.getParsedTransaction(txSignature, ...)`. No format check precedes the RPC call.
2. `escrowDepositConfirm` (`main.js:1722`) accepts it via a `typeof txSignature !== 'string'` gate only, then stores it in `ws.deposits[client.id]` and logs it to console.

The hypothesis asks three questions:

- **Is the signature validated as base58? Length checked?** No, in either handler.
- **What happens when malformed input hits `getParsedTransaction`?** The RPC call rejects (or returns null), the `catch` block in `verifyBurnTransaction` absorbs the error, and the function returns `{ valid: false }`. No crash, no false positive.
- **Could it cause a crash or false positive?** No crash — the try/catch is correctly placed. No false positive for prestige burns — the function returns invalid. For escrow deposit, no RPC call is made at all against `txSignature`; the deposit acceptance is gated on the on-chain escrow PDA state, not the signature string. However, the raw client string is stored and logged without sanitisation.

## 2. Vulnerability Detail

### 2.1 prestigeBurn handler — no format validation before RPC call

**File:** `server/socket-io/main.js`
**Lines:** 1611–1645

```javascript
// Line 1618
const { txSignature, burnAmount } = data || {}
if (!txSignature) {                              // only truthy check
    client.emit('prestigeResult', { success: false, reason: 'No burn transaction provided' })
    return
}

try {
    // Line 1626
    const verification = await verifyBurnTransaction(txSignature, wallet, burnAmount)
    // ...
} catch (err) {
    console.error('[Prestige] Burn verification error:', err.message)
    client.emit('prestigeResult', { success: false, reason: 'Burn verification error' })
}
```

The check at line 1619 only confirms `txSignature` is not falsy. Any non-empty string proceeds directly to `verifyBurnTransaction`. There is no base58 character-set check, no length enforcement (a valid Solana signature is exactly 88 base58 characters encoding 64 bytes), and no attempt to decode it before passing it to the RPC layer.

### 2.2 verifyBurnTransaction — RPC call with unvalidated input

**File:** `server/services/shot-token.js`
**Lines:** 457–558

```javascript
// Line 465
if (verifiedBurnTxs.has(txSignature)) {
    return { valid: false, reason: 'Transaction already used for prestige' }
}

try {
    // Line 471 — txSignature passed directly to RPC
    const tx = await connection.getParsedTransaction(txSignature, {
        commitment: 'confirmed',
        maxSupportedTransactionVersion: 0,
    });

    if (!tx) {
        return { valid: false, reason: 'Transaction not found or not confirmed' }
    }
    // ...
} catch (err) {
    // Line 554
    console.error('[SHOT] Burn verification error:', err.message);
    return { valid: false, reason: 'Failed to verify burn transaction' };
}
```

`@solana/web3.js` `Connection.getParsedTransaction` constructs a JSON-RPC request with the signature as a string parameter. If the string is not valid base58 or is the wrong length, the behaviour depends on the RPC endpoint:

- **Devnet / Mainnet RPC (standard):** The RPC returns an HTTP 400 or a JSON-RPC error response. `@solana/web3.js` throws a `SendTransactionError` or parses the response as null/undefined. Either path lands in the `catch` block at line 554.
- **Some RPC implementations:** Return `null` (signature not found), which hits the `if (!tx)` check at line 476 and returns `{ valid: false }`.
- **Pathological inputs (very long strings, Unicode, binary):** Cause the JSON-RPC serialisation to throw before any network call, again landing in the `catch` block.

In all cases the function returns `{ valid: false }`. There is no code path through which a malformed signature produces `{ valid: true }`.

**No crash risk:** The `catch` at line 554 is correctly placed around the entire async block including the RPC call. An unhandled rejection is not possible from `getParsedTransaction` alone. The outer `try/catch` in `main.js` lines 1624/1641 provides a second layer.

**No false-positive risk for prestige burns:** The verification function requires an affirmative `burnFound = true` inside parsed instruction data. A malformed signature that causes `getParsedTransaction` to throw or return null never reaches the instruction-parsing loop.

### 2.3 escrowDepositConfirm handler — signature stored and logged without validation

**File:** `server/socket-io/main.js`
**Lines:** 1722–1804

```javascript
// Line 1726
if (!rid || !txSignature || typeof txSignature !== 'string') return

// ...on-chain escrow state verified if escrow is enabled (correct)...

// Line 1783
ws.deposits[client.id] = txSignature          // stored as-is

// Line 1788
console.log(`[Escrow] Deposit confirmed: ${client.id} for room ${rid} (TX: ${txSignature})`)
```

Two observations:

1. **Stored without validation:** The raw client-supplied `txSignature` is stored in `ws.deposits[client.id]`. This value is used only to confirm "this client has deposited" (truthiness check at lines 1785–1786: `hostDeposited && playerDeposited`). The signature content itself is never re-examined, verified, or used in any downstream operation. A client can store an arbitrary string of any length here.

2. **Logged without sanitisation:** `txSignature` is interpolated directly into a `console.log` at line 1788. A string containing newlines or carriage returns can produce multi-line log entries that forge apparent log output — a log-injection vector. This is a low-severity cosmetic issue for a console logger (Pino is bypassed here) but is worth noting.

3. **Dev-mode is the critical case:** When `isEscrowEnabled()` returns false (lines 1740–1778 block is skipped), the handler accepts any non-empty string as a valid deposit confirmation. In production this is gated by on-chain state verification, but in any dev or staging environment without `MATCH_ESCROW_PROGRAM_ID` set, the `txSignature` value is completely irrelevant to whether the deposit is considered confirmed. A client in that environment can pass `"FAKE"` and receive an `escrowActive` event.

### 2.4 Replay protection interaction

The `verifiedBurnTxs.has(txSignature)` check at line 465 runs before the RPC call. If an attacker repeatedly submits malformed signatures that all fail verification, none of them are added to `verifiedBurnTxs` (the `.add()` at line 549 is only reached after `burnFound = true`). There is no denial-of-service concern from replay protection being exhausted by malformed input.

However, the inverse case matters: if an attacker submits the same valid signature simultaneously from two concurrent sockets (the race condition in C-10), both pass the `.has()` check before either lands at `.add()`. This interaction is a separate finding (C-10 in ARCHITECTURE.md) and is not introduced by the format validation gap — it would exist regardless of whether format validation were added.

## 3. Attack Scenarios

### Scenario A: Prestige burn — malformed signature (no practical impact)

**Actor:** Authenticated player.

**Steps:**
1. Emit `prestigeBurn` with `{ txSignature: "not-base58!!!", burnAmount: 200 }`.
2. Server calls `verifyBurnTransaction("not-base58!!!", wallet, 200)`.
3. RPC call throws or returns null/error.
4. `verifyBurnTransaction` returns `{ valid: false, reason: 'Failed to verify burn transaction' }`.
5. Server emits `prestigeResult: { success: false }`.

**Outcome:** No prestige advancement. No crash. No state corruption.

**Finding:** No practical exploit. The existing error handling correctly closes this path. The gap is cosmetic (unnecessary RPC call, noisier error logs).

### Scenario B: Prestige burn — DoS via RPC flooding with unique malformed signatures

**Actor:** Attacker.

**Steps:**
1. Generate a large number of unique non-base58 strings.
2. Emit `prestigeBurn` events in rapid succession with each string.
3. Each event makes an RPC call to `getParsedTransaction` that fails (or returns null).
4. The RPC connection object (`connection` at `shot-token.js:36`) accumulates pending requests.

**Outcome:** No per-event rate limiting exists on `prestigeBurn` (ARCHITECTURE.md H-28 / no per-event rate limit). At sufficient volume, pending RPC requests can delay or time out legitimate RPC calls made by other handlers. The impact is liveness degradation, not fund loss or state corruption.

**Severity contribution:** Low-to-medium. This path requires flooding, and the server's global `safeHandler` and socket-level disconnect protection bound the worst case. However, the absence of format validation means the RPC call is made for every single emission rather than being short-circuited at the handler boundary.

### Scenario C: Escrow deposit — arbitrary string stored in wager state (dev mode only)

**Actor:** Attacker in a dev/staging environment where escrow is not enabled.

**Steps:**
1. Connect to a wagered match in dev mode (no `MATCH_ESCROW_PROGRAM_ID` set).
2. Emit `escrowDepositConfirm` with `{ roomId: rid, txSignature: "FAKE_DEPOSIT" }`.
3. Server skips on-chain verification (lines 1740–1778).
4. `ws.deposits[client.id] = "FAKE_DEPOSIT"` is stored.
5. If both players do this, server emits `escrowActive`.

**Outcome:** In dev mode, fake deposit confirmations advance the match to the escrow-active state without any real on-chain deposit. This is consistent with the documented dev-mode bypass behaviour (dev-mode is explicitly not production), so the practical risk is limited to test environments. In production with escrow enabled, the on-chain PDA state check correctly rejects this.

### Scenario D: Log injection via crafted txSignature

**Actor:** Attacker with an authenticated socket in any match.

**Steps:**
1. Emit `escrowDepositConfirm` with `txSignature` containing `\n[FAKE] Settlement confirmed: winner=<attacker_wallet>`.
2. Server logs `[Escrow] Deposit confirmed: <socketId> for room <rid> (TX: <injected content>)`.

**Outcome:** The `console.log` at line 1788 produces a forged log line. In a development or staging environment where console output is reviewed, this could mislead an operator. In production where Pino is the primary logger (console is bypassed per ARCHITECTURE.md M-4), impact is minimal. Still, log injection via unvalidated user input is a code quality concern.

## 4. Severity Assessment

**Verdict: MEDIUM**

The original hypothesis feared a crash or false positive from malformed input reaching `getParsedTransaction`. Neither materialises: the try/catch correctly absorbs all error paths and the function returns `{ valid: false }` in every failure mode. There is no false-positive prestige advancement possible from a malformed signature alone (ignoring the separate C-10 race condition).

The residual concerns are:

| Sub-finding | Severity | Rationale |
|-------------|----------|-----------|
| No base58/length check before RPC call (prestige burn) | Low | RPC error correctly absorbed; no exploit possible; creates unnecessary RPC noise |
| Raw signature stored in wager state map without sanitisation | Low | Content never re-examined; no downstream injection into DB or chain |
| Console log injection via `txSignature` (escrow handler) | Low | Console only (Pino bypassed); no structured log injection into Pino |
| Dev-mode deposit acceptance with arbitrary txSignature | Low | Dev-only; on-chain gate present in production; consistent with documented dev-mode bypass |
| Potential liveness impact from RPC flooding (prestige burn) | Medium | No per-event rate limit on `prestigeBurn`; each malformed sig makes a live RPC call; at volume this adds latency to the shared `connection` object |

**Aggregate: MEDIUM.** The finding is confirmed but at lower severity than the hypothesis implies. The primary real-world issue is the missing format check causing unnecessary RPC calls on every malformed submission, with liveness implications under flood. The false-positive and crash paths are not present.

## 7. Recommendations

### R1 — Add base58 format and length validation before RPC calls (Primary fix)

Insert a lightweight validation function at the handler boundary, before any async RPC call is made. A valid Solana transaction signature is a 64-byte value encoded as base58, which always produces exactly 87 or 88 characters (88 for the vast majority of signatures). The base58 character set is `[1-9A-HJ-NP-Za-km-z]`.

```javascript
// Utility function (add to server/middleware/guards.js or a shared util)
const BASE58_REGEX = /^[1-9A-HJ-NP-Za-km-z]{87,88}$/;

function isValidTxSignature(sig) {
    return typeof sig === 'string' && BASE58_REGEX.test(sig);
}
```

Apply in `prestigeBurn` handler (`main.js:1619`):

```javascript
// Replace:
if (!txSignature) { ... }

// With:
if (!isValidTxSignature(txSignature)) {
    client.emit('prestigeResult', { success: false, reason: 'Invalid transaction signature format' })
    return
}
```

Apply in `escrowDepositConfirm` handler (`main.js:1726`):

```javascript
// Replace:
if (!rid || !txSignature || typeof txSignature !== 'string') return

// With:
if (!rid || !isValidTxSignature(txSignature)) return
```

**Benefit:** Short-circuits before the RPC call, eliminating unnecessary network traffic for malformed inputs. Prevents log injection. Provides clearer error feedback to clients.

### R2 — Sanitise txSignature before log interpolation

```javascript
// Replace line 1788:
console.log(`[Escrow] Deposit confirmed: ${client.id} for room ${rid} (TX: ${txSignature})`)

// With:
const safeSig = typeof txSignature === 'string' ? txSignature.replace(/[\r\n]/g, '') : '(invalid)'
console.log(`[Escrow] Deposit confirmed: ${client.id} for room ${rid} (TX: ${safeSig})`)
```

If R1 is implemented (format validation before handler logic runs), this sanitisation is redundant — a validated base58 string cannot contain `\n` or `\r`. R2 is only necessary if R1 is not implemented or if the log line is moved to a position before the validation check.

### R3 — Add per-event rate limiting to prestigeBurn

The `prestigeBurn` handler makes a live RPC call on every event. Without a per-event rate limit, an attacker can flood the handler and add latency to the shared `connection` object used by other handlers. Add a per-socket throttle (e.g., one `prestigeBurn` per 5 seconds) using the existing rate-limiter infrastructure in `guards.js`. This is distinct from R1 but complementary: R1 eliminates the RPC call for malformed sigs, R3 limits the rate of valid-format submissions.

---

## 8. Verdict

**CONFIRMED MEDIUM.**

`txSignature` is accepted in both `prestigeBurn` and `escrowDepositConfirm` without base58 format or length validation. The crash and false-positive paths hypothesised in H051 are not present — `verifyBurnTransaction`'s try/catch correctly absorbs all RPC failures, and no malformed signature can produce a `{ valid: true }` result. The actual risks are: unnecessary live RPC calls on every malformed submission (liveness under flood), storage of unvalidated client strings in the wager state map, and console log injection. The prestige burn path is protected by both the on-chain verification and the error-absorbing catch. The escrow deposit path is protected in production by the on-chain PDA state check; the format gap is exploitable only in dev mode where the escrow gate is disabled. The master risk register entry M-19 correctly categorises this as MEDIUM.
