# H054 — ws / express / socket.io Known CVE Exploitation

**Hypothesis:** Server npm audit shows 30 vulns (18 high). Known CVEs may be exploitable.
**Verdict:** CONFIRMED (versions are pinned to ranges that include known-vulnerable releases)
**Severity:** HIGH (Denial of Service / Request Smuggling)

---

## Summary

`server/package.json` pins three core networking packages to version ranges that include releases with known CVEs. The `express` pin at `^4.17.3` is below the patched `4.21.2`; the `socket.io` pin at `^4.4.1` is well below current; and `ws` is not a direct dependency but arrives transitively through `socket.io`. Given that `^` ranges resolve to the latest compatible minor/patch at install time, the actual installed versions depend on when `npm install` was last run. If the lock file is stale or absent, vulnerable versions may be in use. The most directly applicable published CVEs for these version ranges are detailed below.

`ws` is not a direct dependency (line not present) but is a transitive dependency of `socket.io`. The `socket.io` 4.4.1 floor resolves to `engine.io` 6.x, which depends on `ws` 8.2.x — the range flagged by the architecture audit.

## CVE Assessment by Package

### express `^4.17.3`

| CVE | Affected | Fixed | Type | Exploitability |
|-----|----------|-------|------|---------------|
| CVE-2024-29041 | < 4.19.2 | 4.19.2 | Open Redirect via malformed Host header | Low (requires specific routing) |
| CVE-2024-43796 | < 4.19.2 | 4.19.2 | XSS via `res.redirect()` with unsanitized input | Medium (server must call `res.redirect()` with user input) |
| CVE-2024-45590 | body-parser < 1.20.3 | 1.20.3 | ReDoS in URL-encoded body parsing | HIGH — see below |

**CVE-2024-45590 (body-parser ReDoS) — Highest Applicable Risk:**

`body-parser` ships as a bundled dependency of `express`. Versions of `body-parser` below `1.20.3` (bundled with express < 4.19.2) contain a Regular Expression Denial of Service (ReDoS) vulnerability in the URL-encoded body parser. A crafted request body with deeply nested bracket notation (e.g., `a[b][c][d]...=1`) causes catastrophic backtracking.

**Applicability to SolShot server:**
- The SolShot server uses Express for its `/api/auth/verify` and `/api/telegram/webhook` HTTP endpoints.
- `/api/auth/verify` accepts `Content-Type: application/json` (JSON body, not URL-encoded). Body-parser's JSON parser is not affected by this ReDoS.
- `/api/telegram/webhook` also likely uses JSON. However, if Express's default `urlencoded` middleware is mounted globally (common pattern), a `Content-Type: application/x-www-form-urlencoded` request with a crafted body can trigger the ReDoS regardless of the route's intended content type.
- **Attack:** Attacker sends a POST to any endpoint with a crafted URL-encoded body. The event loop blocks for seconds. This is effectively a single-request DoS against a single-process Node.js server.

**Floor version risk:** `^4.17.3` resolves at minimum to 4.17.3, which bundles `body-parser` well below the patched version. The express package itself was not patched to update its bundled body-parser until 4.19.2.

### socket.io `^4.4.1`

| CVE / Advisory | Affected | Fixed | Type |
|---------------|----------|-------|------|
| GHSA-xfhh-g9f5-x4m4 | socket.io < 4.6.2 | 4.6.2 | engine.io DoS via malformed HTTP upgrade request |
| GHSA-r7qp-cfhv-p84w | engine.io < 6.4.2 | 6.4.2 | HTTP request smuggling via malformed upgrade headers |

**GHSA-xfhh-g9f5-x4m4 (engine.io HTTP request DoS):**

`socket.io` 4.4.1 uses `engine.io` 6.2.x. This version of `engine.io` does not properly validate the HTTP upgrade request, allowing an attacker to send a specially crafted HTTP request that causes the server to crash or loop indefinitely. Fixed in `engine.io` 6.4.2 (bundled with `socket.io` 4.6.2+).

**Applicability:** The SolShot server exposes Socket.IO directly. The entire game and financial flow runs over Socket.IO. A DoS against the Socket.IO server terminates all active wagered matches, triggering `handleSettlementFailure` paths and potentially causing fund loss (see H-11 / H-6 in the architecture). This is an amplified impact — the DoS itself is bad, but the secondary financial effect (see Architecture Section 10, Attack 6) is the critical concern.

**Floor version:** `^4.4.1` resolves to at minimum 4.4.1, which is below the 4.6.2 fix. Whether the currently installed version is at or above 4.6.2 depends entirely on when `npm install` was last run against the lock file.

### ws (transitive via socket.io / engine.io)

The architecture audit identified `ws 8.2.3` as the flagged version. `ws` has had several DoS advisories in the 7.x and 8.x range:

| CVE | Affected | Fixed | Type |
|-----|----------|-------|------|
| CVE-2024-37890 | ws < 8.17.1 | 8.17.1 | ReDoS in HTTP upgrade header parsing |

**CVE-2024-37890 (ws ReDoS):**

`ws` versions below 8.17.1 are vulnerable to a ReDoS in the HTTP upgrade handshake header processing. A crafted `Sec-WebSocket-Protocol` header value causes catastrophic backtracking in `ws`'s header validation regex. For a Socket.IO server, every WebSocket upgrade request (i.e., every player connecting) passes through this code path.

**Applicability:** Every SolShot client establishes a WebSocket connection. An attacker can send upgrade requests with crafted `Sec-WebSocket-Protocol` headers before authenticating, freezing the event loop for each crafted request. This is unauthenticated DoS at the connection layer — no valid game session required.

**Transitive chain:** `socket.io 4.4.1` → `engine.io 6.2.x` → `ws 8.2.x` → vulnerable to CVE-2024-37890 (patched in ws 8.17.1, which arrived via engine.io 6.5.x, bundled in socket.io 4.7.x+).

---

## Combined Attack Scenario

An attacker can chain two of these in sequence with minimal effort:

1. **Phase 1 (ws ReDoS):** Send a batch of WebSocket upgrade requests with crafted `Sec-WebSocket-Protocol` headers to saturate the event loop. Existing players experience lag/disconnection. Match timers fire, potentially triggering forfeit or disconnect-settlement paths.

2. **Phase 2 (body-parser ReDoS, if URL-encoded body parsing is enabled):** Send crafted POST bodies to `/api/auth/verify` to sustain the DoS during the settlement window, preventing the server from processing settlement transactions and triggering `handleSettlementFailure` → `cancelMatchEscrow` → winner loses winnings.

Neither phase requires authentication or a game session.

## Recommendations

1. **Update express to >= 4.21.2.** This pulls in the patched body-parser (1.20.3+) and fixes all known express CVEs in the `^4.x` range:

```json
"express": "^4.21.2"
```

2. **Update socket.io to >= 4.7.5.** This transitively updates `engine.io` to a version that bundles `ws >= 8.17.1`, resolving both the engine.io DoS and the ws ReDoS:

```json
"socket.io": "^4.7.5"
```

3. **Commit an up-to-date `package-lock.json`.** The lock file ensures reproducible installs and prevents `^` ranges from resolving to older versions in CI/CD or on new deployments.

4. **Add `npm audit --audit-level=high` to the CI pipeline** as a failing gate. This catches new advisories before they reach production.

5. **Explicitly limit `maxHttpBufferSize` on the Socket.IO server** (also flagged as H-28 in the architecture). This is a complementary defense that limits the payload size an attacker can use in WebSocket upgrade and message DoS attempts:

```js
const io = new Server(server, { maxHttpBufferSize: 1e6 }); // 1MB cap
```
