# H056 — Shop Phase Double-Trigger Race (endShopPhase Double Gold Distribution)

**Hypothesis:** Two concurrent ready events both trigger endShopPhase, causing double gold distribution.
**Verdict:** NOT VULNERABLE (state machine guard prevents double-trigger)
**Severity:** N/A — but a latent logic gap in the `ready` handler is noted as a POTENTIAL issue

---

## Summary

The `endShopPhase` function is protected by a state machine check that prevents it from executing more than once per shop phase. The check at line 257 (`if (ms.status !== MATCH_STATES.WEAPON_SHOP) return`) ensures that only the first invocation transitions the state to BATTLE — subsequent calls from the `shopDone` handler or the shop timer find the state already transitioned and return early without distributing gold or emitting `shopEnd` a second time.

However, the `ready` handler (which initiates a shop phase) has a structural vulnerability: when both players send `ready` simultaneously, both can pass the `room.host.isReady && room.player.isReady` check before either resets the readiness flags. This can double-initialize gold and the shop, though not double-distribute gold on *exit* from the shop phase.

## Evidence

### endShopPhase guard (lines 243–286)

**File:** `C:/Users/johnk/SolShot-clean/server/socket-io/main.js`

```js
function endShopPhase(io, roomId) {
    // Clear timer
    if (shopTimers[roomId]) {                    // line 245
        clearTimeout(shopTimers[roomId]);
        delete shopTimers[roomId];
    }

    const room = findRoom(roomId)
    if (!room) return                             // line 251

    const ms = matchStates[roomId]
    if (!ms) return                               // line 254

    // Only transition if we're still in weapon_shop      ← KEY GUARD
    if (ms.status !== MATCH_STATES.WEAPON_SHOP) return   // line 257

    transitionState(ms, MATCH_STATES.BATTLE)     // line 259 — state changes here
    // ... gold distribution and shopEnd emit ...
}
```

The state check at line 257 is the critical guard. `transitionState` at line 259 sets `ms.status = MATCH_STATES.BATTLE`. A second call to `endShopPhase` for the same room will hit line 257, find `ms.status === 'battle'` (not `'weapon_shop'`), and return immediately. No gold is distributed a second time, no `shopEnd` is emitted a second time.

**Node.js atomicity:** Because there is no `await` between the status check (line 257) and the status mutation (line 259), the event loop cannot yield to process a second invocation of `endShopPhase` mid-execution. The check-then-set is atomic.

### shopDone triggering endShopPhase (lines 1553–1572)

```js
client.on('shopDone', () => {
    if (!requireAuth(client, 'shopDone')) return         // line 1554
    const room = findRoom(client.roomId)
    if (!room) return

    const ms = matchStates[client.roomId]
    if (ms && !validateAction(ms.status, 'shopDone')) return  // line 1559
    // validateAction allows 'shopDone' only in WEAPON_SHOP state

    const ready = shopReady[client.roomId]
    if (!ready) return                                    // line 1562

    ready[client.id] = true                              // line 1564

    const hostId = room.host ? room.host.socketId : null
    const playerId = room.player ? room.player.socketId : null

    if (hostId && playerId && ready[hostId] && ready[playerId]) {  // line 1570
        endShopPhase(io, client.roomId)                  // line 1571
    }
})
```

Two concurrent `shopDone` events:

```
Event 1 (host): ready[hostId] = true
    → ready[hostId]=true, ready[playerId]=false → condition false → no endShopPhase

Event 2 (player): ready[playerId] = true
    → ready[hostId]=true, ready[playerId]=true → condition true → endShopPhase()
    → endShopPhase: ms.status === WEAPON_SHOP → transitions to BATTLE → distributes gold

Hypothetical Event 3 (duplicate shopDone from host):
    → validateAction(ms.status, 'shopDone') → ms.status is now BATTLE → 'shopDone' not in BATTLE allowlist → return
    → endShopPhase never reached
```

The `validateAction` guard at line 1559 uses `allowedActions[MATCH_STATES.WEAPON_SHOP] = ['buyWeapon', 'shopDone']` (from `match.js` line 65). Once the state transitions to BATTLE, `shopDone` is not in the BATTLE allowlist, so duplicate events are silently dropped.

## Potential Issue in `ready` Handler (Double Shop Initialization)

The `ready` handler at lines 1399–1482 has a structural race that the hypothesis does not precisely target but is worth documenting here.

**File:** `C:/Users/johnk/SolShot-clean/server/socket-io/main.js`, lines 1399–1482

```js
client.on('ready', () => {
    if (!requireAuth(client, 'ready')) return
    var room = findRoom(client.roomId)
    if (!room) return

    // H019: Validate ready is allowed in current state
    const msReady = matchStates[client.roomId]
    if (msReady && !validateAction(msReady.status, 'ready')) {
        client.emit('readyError', ...)
        return
    }

    // Track readiness
    if (client.isHost === true) {
        room.host.isReady = true       // line 1413
    } else {
        if (!room.player) return
        room.player.isReady = true     // line 1416
    }

    // Both players ready — start shop phase
    if (room.host.isReady && room.player && room.player.isReady) {  // line 1420
        // ...
        goldStates[client.roomId] = initGold(hostId, playerId)      // line 1433 — OVERWRITES gold
        // ...
        shopReady[client.roomId] = { ... }                          // line 1443 — OVERWRITES readiness
        // ...
        transitionState(ms, MATCH_STATES.WEAPON_SHOP)               // line 1450

        room.player.isReady = false    // line 1479 — reset AFTER the block
        room.host.isReady = false      // line 1480 — reset AFTER the block
    }
})
```

**Race scenario (between-round ready):**

If both players simultaneously send `ready` during the `ROUND_END` state:

```
Event 1 (host): room.host.isReady = true
  → room.host.isReady=true, room.player.isReady=false → block not entered → returns

Event 2 (player): room.player.isReady = true
  → room.host.isReady=true, room.player.isReady=true → block entered
  → initGold() (on isBetweenRounds=false path) OR carries over (isBetweenRounds=true)
  → transitionState → WEAPON_SHOP
  → room.player.isReady = false, room.host.isReady = false

(Event 1 already returned before event 2; no double trigger.)
```

Because Node.js processes events sequentially, one `ready` event always executes to completion before the other starts. This prevents the double-trigger entirely: event 1 sets `host.isReady=true` and returns (block not entered). Event 2 sets `player.isReady=true`, finds both ready, enters the block, resets both flags at the end.

**The only path to double-initialization** would be if a single player sent `ready` twice rapidly with both `isReady` flags already true from a prior round. The `validateAction` check at line 1406 uses `allowedActions[MATCH_STATES.LOBBY] = ['join', 'leave', 'ready']` and `allowedActions[MATCH_STATES.ROUND_END] = ['ready', 'playAgainRequest']`. Once the state transitions to `WEAPON_SHOP` (line 1450), `validateAction` for `'ready'` in `WEAPON_SHOP` state returns `false`, blocking re-entry. This correctly prevents double-initialization.

## Gold Distribution in endShopPhase

`endShopPhase` does not distribute gold. It only:
1. Transitions state to BATTLE (line 259)
2. Builds weapon lists from existing inventories (lines 267–274)
3. Emits `shopEnd` with current gold balances (line 277) and resets `shopReady` (line 284)

Gold is distributed during battle (in the `fire` handler via `earnGold`, `awardKillBonus`, `awardRoundWinBonus`). Gold is initialized in the `ready` handler via `initGold()` (line 1433). The hypothesis that double-triggering `endShopPhase` causes double gold distribution is structurally incorrect — `endShopPhase` emits balances but does not mutate them.

---

## Verdict Rationale

The hypothesis is **NOT VULNERABLE** because:
- `endShopPhase` contains a synchronous state machine guard (line 257) that prevents double execution.
- The `shopDone` handler uses `validateAction` to block `shopDone` events after the state leaves `WEAPON_SHOP`.
- Node.js's single-threaded event loop prevents concurrent execution of the handler.
- `endShopPhase` does not distribute or mutate gold balances.

The `ready` handler's readiness flag reset (lines 1479–1480) could theoretically be a TOCTOU if an `await` existed between line 1420 and line 1479, but no such `await` is present.

---

## Recommendations

While no vulnerability is confirmed for the specific hypothesis, the following hardening is suggested:

1. **Add a `shopInitialized` flag** (or check `ms.status !== MATCH_STATES.LOBBY && ms.status !== MATCH_STATES.ROUND_END`) at the top of the shop-start block inside the `ready` handler (line 1420), as a defense-in-depth guard. This makes the idempotency explicit rather than relying solely on event sequencing.

2. **Move `room.player.isReady = false` and `room.host.isReady = false` (lines 1479–1480) to the top of the block** immediately after the condition is confirmed true (before any mutations). This is a cleaner TOCTOU guard even though no `await` is currently present.
