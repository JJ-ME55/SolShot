# H059 — Deposit Timer vs Confirmation Race

**Verdict:** NOT VULNERABLE (timer cleared correctly, but with a narrow residual gap)

**Severity:** LOW (theoretical; requires precise millisecond timing)

**Hypothesis:** The deposit timeout fires while a confirmation is being processed, triggering a refund for an already-confirmed deposit.

---

## Evidence

### Timer Initialization

The deposit countdown is started at two sites in `server/socket-io/main.js`:

- **Line 1059** (inside `joinRoom` handler, after escrow creation for manual room join):
  ```js
  depositTimers[roomId] = setTimeout(async () => {
      delete depositTimers[roomId]
      ...
      if (hostDep && playerDep) return   // Line 1067
      // Cancel escrow and refund
  ```

- **Line 1322** (inside `joinQueue` handler, after escrow creation for queue-matched room):
  ```js
  depositTimers[roomId] = setTimeout(async () => {
      delete depositTimers[roomId]
      ...
      if (hostDep && playerDep) return   // Line 1330
      // Cancel escrow and refund
  ```

Both timeout callbacks check the current deposit state at the time they fire, not at the time the timer was set. Crucially, both self-delete via `delete depositTimers[roomId]` as their **first action** before the deposit check.

### Timer Clearance on Confirmation

In the `escrowDepositConfirm` handler at **lines 1790–1796**:

```js
if (hostDeposited && playerDeposited) {
    // DCA-01: Clear deposit countdown — both players deposited in time
    if (depositTimers[rid]) {
        clearTimeout(depositTimers[rid])
        delete depositTimers[rid]
    }
    ...
    io.sockets.in(rid).emit('escrowActive', { ... })
}
```

The timer is cleared **only when both players have deposited**. After the first player confirms, the timer is still running. It is not cleared after the first deposit — only after the second.

---

## Analysis

### The Normal Race Scenario

The hypothesized race is: the timer fires while a `escrowDepositConfirm` event is mid-processing.

JavaScript's single-threaded event loop prevents true simultaneous execution. A `setTimeout` callback is queued as a macrotask. The `escrowDepositConfirm` handler is already executing as a macrotask. Therefore:

- If `escrowDepositConfirm` is executing, the timer callback cannot interrupt it.
- The timer callback will only run after the current macrotask completes.
- By the time the timer fires, `ws.deposits[client.id]` will already be set if confirmation was successful.

This makes the race benign: the timer callback at lines 1065–1067 (and 1328–1330) explicitly re-reads `wagerStates[roomId]` and returns early if both deposits are present:

```js
const hostDep = wsCheck.deposits && wsCheck.deposits[roomCheck.host?.socketId]
const playerDep = wsCheck.deposits && wsCheck.deposits[roomCheck.player?.socketId]
if (hostDep && playerDep) return
```

### The Residual Gap

There is one narrow scenario where this protection is insufficient:

The timer fires **between the first and second deposit confirmation**. The timer callback checks `hostDep && playerDep` — this is false if only one player has deposited. The timer then proceeds to cancel the escrow even though one deposit is already on-chain and confirmed in-memory.

This means: if Player A's timeout fires 1ms before Player B calls `escrowDepositConfirm`, and Player A has already confirmed but Player B has not, the escrow is cancelled. Player A's on-chain funds are refunded, but both players lose the match setup. This is a **correctness bug** (premature cancellation griefs Player B's game setup) rather than a fund-loss bug (the refund returns funds correctly).

The timer check at lines 1065–1067 should be `hostDep || playerDep` (cancel only if *neither* deposited) to allow partial-deposit grace:

```js
// Current (partial-deposit cancellation):
if (hostDep && playerDep) return

// Safer (only cancel if truly no deposits):
if (hostDep || playerDep) return
```

---

## Recommendations

1. **Fix the partial-deposit timer guard.** Change the timer early-return condition from `hostDep && playerDep` to `hostDep || playerDep` at both timer sites (lines 1067 and 1330). This prevents cancellation when one player has already deposited, which is the aggressive and user-unfriendly behavior in the current code.

2. **Clear the timer after first confirmed deposit**, not just after both. Move the `clearTimeout(depositTimers[rid])` block to run when either deposit is confirmed — start a second, shorter grace timer for the second deposit at that point. This provides a better UX signal and eliminates the partial-deposit race entirely.

3. **Log timer cancellation decisions** with deposit state at the time of firing, to aid operational debugging.
