# H060 — joinQueue No Balance Check

**Verdict:** CONFIRMED

**Severity:** HIGH

**Hypothesis:** `joinQueue` doesn't verify SOL balance before placing a player in a wagered matchmaking queue.

---

## Evidence

### joinQueue Handler — `server/socket-io/main.js`, lines 1213–1389

The `joinQueue` handler performs the following checks in order:

1. **Line 1214:** Null payload guard
2. **Line 1218:** Rejects `custom_challenge` mode
3. **Line 1224:** Calls `validateMatchMode(matchMode, wagerAmount, matchLength)` — validates the *mode and wager tier are legal*, not that the wallet holds sufficient funds
4. **Line 1231:** Requires authentication for wagered matches (`wagerAmount > 0 && !requireAuth(...)`)

After authentication, the handler proceeds directly to queue logic:

```js
// Lines 1233–1240:
removeFromAllQueues(client.id);
const queueKey = getQueueKey(matchMode, matchLength);
if (!matchmakingQueues.has(queueKey)) {
    matchmakingQueues.set(queueKey, []);
}
const queue = matchmakingQueues.get(queueKey);
```

There is **no call to `verifyBalance()`** anywhere in the `joinQueue` handler. The player is placed in the queue (or immediately matched and a room created) without any SOL balance verification.

### Contrast with createRoom and joinRoom

Both `createRoom` and `joinRoom` call `verifyBalance()` for wagered matches:

- **`createRoom`, lines 1136–1148:**
  ```js
  if (wagerAmount > 0 && walletAddress) {
      try {
          const balanceCheck = await verifyBalance(walletAddress, wagerAmount)
          if (!balanceCheck.sufficient) {
              client.emit('createRoomError', { ... })
              return
          }
      } catch (err) {
          console.warn('[Solana] Creator balance check skipped:', err.message)
      }
  }
  ```

- **`joinRoom`, lines 980–992:**
  ```js
  try {
      const balanceCheck = await verifyBalance(joinerWallet, roomWager)
      if (!balanceCheck.sufficient) {
          client.emit('joinRoomError', { ... })
          return
      }
  } catch (err) {
      console.warn('[Solana] Balance check skipped:', err.message)
  }
  ```

The queue path is an explicitly different code path that omits this check entirely.

---

## Attack Scenario

A zero-SOL wallet can exploit this gap as follows:

1. Authenticate with any valid Solana wallet (zero SOL balance).
2. Emit `joinQueue` with `matchMode: 'high_roller'` and a large `wager`.
3. The server validates the mode and authentication, then queues the attacker.
4. A legitimate opponent joins the queue; both are matched. The server creates a room and an on-chain escrow PDA (spending server transaction fees).
5. Both players receive `escrowDeposit` events with pre-built deposit transactions.
6. The legitimate opponent deposits their SOL on-chain and calls `escrowDepositConfirm`.
7. The attacker's deposit transaction fails silently (no SOL to spend). The attacker never calls `escrowDepositConfirm`.
8. After 2 minutes, the deposit timer fires. Only one deposit is confirmed. The server cancels the escrow and refunds the legitimate player.

**Impact per iteration:**
- Attacker: zero cost (no SOL required, just authenticated socket)
- Legitimate player: gas fees on the deposit transaction + gas fees on the refund + 2 minutes wasted
- Server: escrow PDA creation transaction fee (paid from server authority wallet)

**Amplification:** With multiple sockets from different IP ranges, an attacker can systematically poison every matchmaking queue, making wagered queue-based matchmaking unusable. The per-IP connection limit (100) in `server/index.js` at line 41 slows this but does not prevent it — 100 connections per IP can each independently queue for different wager tiers.

The ARCHITECTURE.md already identifies this as a Critical finding (C-2) with convergence from 3 auditors (AUTH-03, LOGIC-01, LOGIC-02).

## Recommendations

1. **Add a balance check in `joinQueue` before queuing the player**, mirroring the existing pattern in `createRoom`:

   ```js
   // After requireAuth check, before queue insertion:
   if (wagerAmount > 0) {
       const joinerWallet = authenticatedWallets[client.id] || null;
       if (!joinerWallet) {
           client.emit('queueError', { reason: 'Wallet required for wagered matches' });
           return;
       }
       try {
           const balanceCheck = await verifyBalance(joinerWallet, wagerAmount);
           if (!balanceCheck.sufficient) {
               client.emit('queueError', {
                   reason: `Insufficient SOL balance. Need ${balanceCheck.required.toFixed(3)}, have ${balanceCheck.balance.toFixed(3)}`
               });
               return;
           }
       } catch (err) {
           // H027 pattern: fail closed — reject if balance cannot be verified
           client.emit('queueError', { reason: 'Balance verification unavailable. Try again shortly.' });
           return;
       }
   }
   ```

2. **Consider fail-closed behavior on RPC error in `joinQueue`**, unlike the fail-open pattern in `createRoom`/`joinRoom`. Since the queue path already lacks a balance check entirely, the bar for exploitation is lower. Failing closed (rejecting the queue entry on RPC error) is appropriate here.

3. **Add a rate limit to `joinQueue`** separate from `createRoom`. Currently `joinQueue` is subject only to the global per-socket event rate limit (same as all other events), which is insufficient to prevent griefing amplification. A dedicated `joinQueue` rate limit (e.g., max 5 per 60s per socket) would reduce the scale of the griefing attack.
