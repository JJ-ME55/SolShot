# H061 — No Global Room Cap Resource Exhaustion

**Verdict:** POTENTIAL

**Severity:** MEDIUM

**Hypothesis:** No maximum room limit allows an attacker to create thousands of rooms, consuming all server memory.

---

## Evidence

### Per-Socket createRoom Rate Limit

A per-socket rate limit exists in `server/socket-io/main.js`, lines 450–522:

```js
// Lines 450–454:
const RL_MAX_CREATES = 3
const RL_CREATE_WINDOW = 60000
const createRing = new Float64Array(RL_MAX_CREATES + 1)
let createHead = 0

// Lines 515–522 (inside onevent interceptor):
if (eventName === 'createRoom') {
    const createCount = ringCount(createRing, createHead, createRing.length, now, RL_CREATE_WINDOW)
    if (createCount >= RL_MAX_CREATES) {
        return  // Drop excess room creations
    }
    createRing[createHead % createRing.length] = now
    createHead++
}
```

This limits each individual socket to **3 room creations per 60 seconds**. The `createRing` is declared per-socket (inside the `io.on('connection', ...)` callback), so each new socket connection gets a fresh ring buffer.

### No Global Room Cap

A search across `server/socket-io/main.js` for global room count enforcement yields no results. There is no check of the form `rooms.size >= MAX_ROOMS` before creating a new room. The `rooms` Map declared at **line 24** has no enforced size ceiling:

```js
const rooms = new Map()
```

### Room Cleanup

Rooms are removed in several places:
- `removeRoom(roomId)` called on disconnect, `leaveRoom`, `deleteRoom`, `createRoom` (when rejoining), and `joinRoom` (when rejoining)
- Rooms are **not** auto-cleaned after a timeout if they remain in the `LOBBY` state (waiting for a second player to join)

A room created by `createRoom` that never receives a `joinRoom` event will persist in the `rooms` Map, in `matchStates`, and in `wagerStates` indefinitely — until the creating socket disconnects or the server restarts.

### Attack Vector Across Multiple Sockets

The per-socket limit of 3 per 60 seconds is scoped to each socket instance. The per-IP connection limit in `server/index.js` line 41 caps connections at **100 per IP**:

```js
const MAX_CONNECTIONS_PER_IP = 100;
```

With 100 connections per IP, the sustained room creation rate from a single IP is:
- 100 sockets × 3 rooms/min = **300 rooms/minute** from one IP address.

However, an attacker using multiple IP addresses (e.g., a residential VPN or botnet) faces no aggregate cap. Each IP can sustain 300 rooms/minute independently.

### Memory Cost Per Room

Each room in memory includes:
- `rooms` Map entry: room object with host/player data
- `matchStates[roomId]`: match state object (status, turns, round data)
- `wagerStates[roomId]`: wager object
- Socket.IO internal room membership data

Estimated memory cost: ~1–5 KB per room (conservative). At 10,000 rooms, that is 10–50 MB of structured objects in the V8 heap. More significant is the associated overhead in Socket.IO's internal room tracking and in Node.js GC pressure from many small, long-lived objects.

---

## Analysis

This is a **mitigated but incomplete** defense. The per-socket rate limit is meaningful but does not constitute a global room cap. The missing safeguards are:

1. **No global limit on total open rooms.** The `rooms.size` is never checked before creating a new room.
2. **No orphan room timeout.** A lobby room waiting for a second player has no expiry timer.
3. **Per-socket limit is per-connection**, so opening 100 connections (within the IP limit) multiplies the rate by 100x.

The ARCHITECTURE.md note at line 176 references process-level crash protection (uncaughtException/unhandledRejection) but does not address OOM exhaustion. A Node.js process dying from OOM results in all in-memory match state — including active wagered matches and their wager data — being lost permanently.

The severity is MEDIUM rather than HIGH because: (a) the per-socket rate limit raises the bar compared to no limit at all; (b) the per-IP connection limit constrains single-source amplification; and (c) the process-level exception handlers prevent a crash from a single malformed request, though they do not prevent OOM.

---

## Recommendations

1. **Add a global room cap.** Before creating a new room in the `createRoom` handler (line 1163), check:
   ```js
   const MAX_GLOBAL_ROOMS = 500;  // tune to server capacity
   if (rooms.size >= MAX_GLOBAL_ROOMS) {
       client.emit('createRoomError', { reason: 'Server at capacity. Try again later.' });
       return;
   }
   ```

2. **Add an orphan room timeout.** Start a lobby expiry timer when a room is created. If no second player joins within a reasonable window (e.g., 5 minutes), call `removeRoom()` automatically. This reclaims memory from rooms that never progressed past lobby.

3. **Expose `rooms.size` in the `/stats` monitoring endpoint** so operational alerting can detect abnormal room accumulation before it becomes an OOM event.

4. **Consider tightening the per-socket create limit** for wagered modes (e.g., 1 wagered room per 60s per socket). A legitimate player rarely needs to create 3 wagered rooms per minute.
