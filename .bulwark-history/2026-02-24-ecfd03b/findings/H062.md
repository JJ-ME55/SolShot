# H062 — 32-bit Room ID Space Collision Probability

**Verdict:** POTENTIAL

**Severity:** LOW (birthday paradox collision risk; no collision check exists)

**Hypothesis:** Room IDs have limited entropy, and the birthday paradox makes collisions likely at scale.

---

## Evidence

### Room ID Generation — Three Sites

Room IDs are generated at three locations in `server/socket-io/main.js`:

1. **Line 1163** (`createRoom` handler):
   ```js
   const roomId = crypto.randomBytes(4).toString('hex')
   ```

2. **Line 1256** (`joinQueue` handler, when two queue entries are matched):
   ```js
   const roomId = crypto.randomBytes(4).toString('hex');
   ```

3. **Line 2293** (`requestTerrain` handler, terrain seed — different purpose):
   ```js
   const fullSeed = crypto.randomBytes(16).toString('hex');
   ```

Room IDs specifically use `crypto.randomBytes(4)` — 4 bytes = 32 bits of entropy. Formatted as hex, this produces an 8-character string in the range `00000000` to `ffffffff` (4,294,967,296 possible values).

### No Collision Check

There is no check after generation to verify that the new `roomId` does not already exist in the `rooms` Map. The generated ID is used immediately:

```js
// Line 1163–1165:
const roomId = crypto.randomBytes(4).toString('hex')
client.join(roomId)
client.roomId = roomId
```

If `rooms.has(roomId)` were true at this point, the new room would **overwrite** the existing room's state — destroying an in-progress match.

---

## Analysis

### Birthday Paradox Probability

The birthday problem formula gives the probability of at least one collision among `n` rooms with space `N = 2^32 ≈ 4.3 billion`:

```
P(collision) ≈ 1 - e^(-n²/2N)
```

| Active rooms (n) | Collision probability |
|-----------------|----------------------|
| 1,000           | ~0.012% (negligible) |
| 10,000          | ~1.2% (low)          |
| 30,000          | ~10%                 |
| 93,000          | ~66%                 |

At typical game server scale (hundreds of simultaneous rooms), the probability is negligible in absolute terms. However, the lack of a collision check means that if a collision *does* occur — however unlikely — it silently overwrites an active match's state without any error or warning.

### Significance

The practical risk is low at current scale. However, two compounding issues raise the concern:

1. **No uniqueness verification:** The code makes no attempt to check `rooms.has(roomId)` before use. This is trivially fixable and should be a baseline correctness guarantee.

2. **Rooms are long-lived if orphaned:** As noted in H061, rooms without a second player are never cleaned up. This means the active room count can grow over time, increasing the birthday probability window.

3. **ARCHITECTURE.md M-11 classification:** The architecture document already catalogues this as M-11 (Medium, randomness category), confirming prior auditor awareness.

### RNG Quality

The use of `crypto.randomBytes()` (Node.js CSPRNG) is correct — there is no weak PRNG involved. The problem is exclusively the size of the ID space, not the quality of the random number generation.

---

## Recommendations

1. **Increase the Room ID to 8 bytes (64 bits).** Change all three generation sites from `crypto.randomBytes(4)` to `crypto.randomBytes(8)`. This increases the space to `2^64 ≈ 1.8 × 10^19` values, making birthday collisions cosmologically improbable at any realistic server scale, with negligible extra storage cost (8 hex chars more per ID).

   ```js
   // Before:
   const roomId = crypto.randomBytes(4).toString('hex')
   // After:
   const roomId = crypto.randomBytes(8).toString('hex')
   ```

2. **Add a collision check with re-generation at all creation sites:**

   ```js
   let roomId;
   let attempts = 0;
   do {
       roomId = crypto.randomBytes(8).toString('hex');
       attempts++;
   } while (rooms.has(roomId) && attempts < 10);
   if (rooms.has(roomId)) {
       client.emit('createRoomError', { reason: 'Room creation failed. Try again.' });
       return;
   }
   ```

   The retry loop is O(1) in practice given sufficient ID space but provides a correctness guarantee regardless of space size.

3. **Apply the same fix to the `joinQueue` auto-room creation at line 1256**, which uses the same 4-byte pattern.
