# H063 — verifyWalletSignature Error Message Information Leak

**Verdict:** POTENTIAL

**Severity:** LOW

**Hypothesis:** Authentication error messages in `auth.js` expose NaCl/Node.js internal details to clients.

---

## Evidence

### The catch block — `server/middleware/auth.js`, lines 62–64:

```js
} catch (err) {
    return { valid: false, reason: `Verification error: ${err.message}` };
}
```

The raw `err.message` from any exception thrown inside the `try` block is interpolated directly into the `reason` string and returned to the caller.

### Exceptions that can propagate to this catch block

The `try` block (lines 39–64) contains three operations, each of which can throw:

1. **`new PublicKey(walletAddress)` (line 41):** If `walletAddress` is not a valid base58 string, `@solana/web3.js` throws a descriptive error. Example message: `"Invalid public key input"`. This is benign.

2. **`Uint8Array.from(atob(signatureBase64), ...)` (line 47):** If `signatureBase64` is not valid base64, `atob()` throws a `DOMException` or `InvalidCharacterError`. Example messages: `"The string to be decoded contains invalid characters"`. These are benign.

3. **`nacl.sign.detached.verify(messageBytes, signature, publicKey.toBytes())` (line 51–55):** TweetNaCl is a pure JavaScript library that does not throw on malformed input — it returns `false`. However, if `signature` or `publicKey.toBytes()` returns a `Uint8Array` of unexpected length, TweetNaCl's internal type checks may throw. Example message: `"unexpected type"` or a V8-level RangeError.

### How `reason` is surfaced to clients

The `reason` field is returned by `handleAuthenticate()` (line 127) which returns `{ success: false, reason: ... }`. In `main.js` the authenticate handler emits this back:

```js
// main.js authenticate handler (not shown in excerpt but standard pattern):
client.emit('authError', { reason: result.reason })
```

This means `err.message` — verbatim — reaches the client socket.

---

## Analysis

### Actual Leakage Assessment

The current messages that can be returned are:

| Source | Example `err.message` | Sensitive? |
|--------|----------------------|------------|
| Invalid base58 wallet address | `"Invalid public key input"` | No |
| Invalid base64 signature | `"The string to be decoded contains invalid characters"` | No |
| NaCl length mismatch | `"unexpected type"` or `"bad length"` | Marginal |
| V8 RangeError | `"Invalid typed array length: X"` | Marginal |

None of these messages expose server internals such as stack traces, file paths, environment variables, keypair material, or internal state identifiers. The library names involved (NaCl, web3.js) are already public knowledge since the client ships open-source code.

The information leakage is therefore **marginal** in practice. An attacker can probe which input caused which error message, but cannot extract anything operationally useful for escalation.

### Why POTENTIAL Rather Than NOT VULNERABLE

The catch-all interpolation pattern `\`Verification error: ${err.message}\`` is a code smell that *could* become a higher-severity issue if:

1. The `try` block is extended with new operations (e.g., database lookups, RPC calls) that throw messages containing internal context such as MongoDB connection strings, environment variable names, or internal IDs.
2. A dependency update changes what `err.message` contains for a given error condition.

The pattern is a fragile approach to error reporting. Controlled, enumerated error messages are a security hygiene baseline.

### Controlled Messages Already Used (Comparison)

Lines 43 and 58 in `auth.js` already use controlled messages:

```js
return { valid: false, reason: 'Invalid wallet address' };
return { valid: false, reason: 'Signature verification failed' };
```

The `catch` block's verbatim interpolation is inconsistent with this pattern and should be replaced with a controlled message.

---

## Recommendations

1. **Replace the verbatim `err.message` interpolation with a controlled message:**

   ```js
   } catch (err) {
       // Log the real error server-side for diagnostics
       console.error('[Auth] verifyWalletSignature exception:', err.message);
       return { valid: false, reason: 'Signature verification failed' };
   }
   ```

   This eliminates all external leakage regardless of what `err.message` contains in the future.

2. **Log the original error server-side** (as shown above) to preserve debuggability without client exposure.

3. **Apply the same principle to `verifyAuthMessage`.** While that function currently uses only string comparisons and `Date.now()` (no throw path), any future additions should follow the controlled-message pattern from the start.

4. **Audit `handleAuthenticate`'s caller in `main.js`** to confirm the `reason` field is emitted only as a string and not as a structured object that could inadvertently expose additional context through JSON serialization.
