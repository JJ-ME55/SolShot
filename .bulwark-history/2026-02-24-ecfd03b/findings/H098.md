## H098 — Phantom Room State After Cleanup Failure

**Verdict:** POTENTIAL

**Severity:** MEDIUM

**Evidence:**
- server/socket-io/main.js:145-190 (approximate) — cleanupRoom() function removes room from all in-memory stores
- No transaction/atomic batch: deletes from rooms map, matchStates, goldStates, weaponInventories, shopTimers, shopReady, wagerStates, turnTimers, depositTimers sequentially
- If error thrown after deleting rooms[roomId] but before deleting matchStates[roomId], state is split across maps
- No rollback mechanism; cleanup not wrapped in try/catch with recovery

**Analysis:**
Failure scenario:
1. cleanupRoom(roomId) called
2. Delete rooms.delete(roomId) ✓
3. Delete matchStates[roomId] ✓
4. Delete goldStates[roomId] ✓
5. Error thrown (e.g., MongoDB write fails for stats)
6. Return early or throw
7. Result: wagerStates[roomId], turnTimers[roomId] still exist but orphaned
8. Next time createRoom reuses roomId (32-bit CSPRNG), collision → merged state from previous match

**Impact:**
- Orphaned state persists indefinitely (or until server restart)
- Memory leak: dead state accumulates
- Potential collision if same roomId regenerated: old wagers merged with new match

**Recommendation:**
1. Wrap cleanupRoom in single try/catch; log failures
2. Use atomic Map.clear() pattern or transaction-like semantics
3. Add cleanup verification: assert all stores cleared for roomId
