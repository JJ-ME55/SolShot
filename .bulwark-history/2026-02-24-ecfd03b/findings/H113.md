## H113 — Multi-Wallet Collusion for Matchmaking Wins

**Verdict:** POTENTIAL

**Severity:** MEDIUM

**Evidence:**
Server tracks max 100 connections per IP via x-forwarded-for (server/index.js:41-67). However, the matchmaking queue and room creation logic do not verify that the same wallet/user is not on both sides of a match. In a wagered game on devnet (low-cost griefing), a single user on multiple sockets from the same IP could:

1. Queue with wallet A via socket 1
2. Queue with wallet B via socket 2
3. Match themselves automatically via `matchPlayers()` (server/socket-io/main.js:~1306-1320)
4. Control both tanks to guarantee a win for wallet A
5. Settle the wager in their favor

**Recommendation:** Add intra-match validation that both players' wallets are distinct; reject matches where player_one === player_two or both map to same user account.

---

**Notes:** Partially covered by H020 (same-IP limit works at connection level, but not at game logic level). The 100-connection IP limit prevents obvious bot farms but does not prevent a single attacker controlling two wallets on two distinct Socket.IO connections from the same IP.
