## H119 — Match ID Collision in Room ID Space

**Verdict:** CONFIRMED

**Severity:** MEDIUM

**Evidence:**
Room IDs are generated as 4-byte crypto.randomBytes (socket-io/main.js:1163, 1256):

```javascript
const roomId = crypto.randomBytes(4).toString('hex')
```

This produces 32-bit IDs (values 0x00000000–0xFFFFFFFF = 4.3 billion possible values). Room ID is passed directly as matchId to escrow.js:createMatch() (solana.js line 277, socket-io/main.js:1025):

```javascript
const escrowResult = await createMatchEscrow(roomId, roomWager, hostWallet, joinerWallet)
```

On-chain PDA seed is `["match", match_id.as_bytes()]` (escrow.js:290, IDL:114-129). Two issues:

1. **Birthday paradox collision**: With 4.3B space, collision risk is significant after ~65K rooms created
2. **No collision detection**: Server does not check if room ID already exists before creating new escrow

Attack: After ~100K matches, attacker finds roomId collision and attempts to reuse existing PDA.

**Recommendation:** Use 8-byte or 16-byte random IDs. Or: check `rooms.has(roomId)` before assignment.

---

**Notes:** On-chain constraints prevent double-settlement (PDA close on Settled state), but the collision creates fork in off-chain room logic.
