# S003 — Ghost Player DoS via Join Race + Unauthenticated Relay Events

**Finding ID:** S003
**Type:** Supplemental — Attack Chain
**Investigator:** Dinh's Bulwark — Phase 3 Supplemental Strategies
**Date:** 2026-02-23
**Constituent Findings:** H019 (join race ghost socket), H016 (unauthenticated relay events)
**Category:** ERR-02 (Race Conditions), AUTH-01/AUTH-03 (Authentication/Authorization), API-03 (WebSocket DoS)

---

## Verdict: CONFIRMED

**Severity: HIGH**

The join race condition (H019) and the unauthenticated relay events (H016) are independently confirmed vulnerabilities. When chained, the ghost socket created by the race overwrite has all the properties required to exploit the unauthenticated relay surface. The ghost socket retains a live Socket.IO room subscription, has `client.roomId` set to the target room, and can continuously emit `giveTurn`, `weaponPick`, `angleChange`, `powerChange`, `weaponChange`, and `shoot` events — all of which the server processes without any authentication check. The combined effect is a reliable, targeted disruption attack against any active wagered match where the attacker wins the join race.

## Chain Analysis

### Step 1 — H019: Create the Ghost Socket

The `joinRoom` handler in `server/socket-io/main.js` (lines 955–1093) reads the capacity guard `room.active === true` at line 962 but does not set `room.active = true` until after one or two async yield points (RPC balance check at line 982, or MongoDB `removeRoom` at line 997). Two concurrent `joinRoom` invocations for the same room both pass the guard before either sets the flag.

The final state:
- `room.player` points to the **second** joiner's socket (the overwrite at line 1012)
- The **first** joiner's socket has `client.roomId = roomId` set (line 1001) and has joined the Socket.IO room channel (line 1000)
- The first joiner's socket is **not** recorded as `room.player.socketId` — the server no longer considers it a legitimate player slot
- The first joiner's socket is the **ghost**: it receives all room broadcasts but is not recognized by game logic

The ghost socket condition is stable until the ghost socket disconnects. It does not expire on its own, has no server-side detection, and emits no warning to the legitimate occupant.

### Step 2 — H016: Ghost Socket Has Full Relay Event Access

The six unauthenticated relay events identified in H016 are:

| Event | Line | Auth Check | Effect on Ghost Socket |
|-------|------|-----------|------------------------|
| `weaponPick` | 1650 | NONE | Ghost emits → `opponentWeaponPick` relayed to victim |
| `shoot` | 1697 | NONE | Ghost emits → `opponentShoot` relayed; partial state guard |
| `weaponChange` | 2348 | NONE | Ghost emits → `opponentWeaponChange` relayed to victim |
| `angleChange` | 2356 | NONE | Ghost emits → `opponentAngleChange` relayed to victim |
| `powerChange` | 2364 | NONE | Ghost emits → `opponentPowerChange` relayed to victim |
| `giveTurn` | 2479 | NONE | Ghost emits → `recieveTurn` relayed; unbounded `terrainData` |

The relay check in each handler uses `client.to(client.roomId).emit(...)`. Since the ghost socket has `client.roomId` set, this targeting succeeds. The server routes the relay to all other sockets in the room — including the legitimate opponent.

### Step 3 — The Combination: Sustained Targeted Relay Spam

The ghost socket does not need to authenticate. It does not need to be `room.player.socketId`. It only needs `client.roomId` to be set — which the join race guarantees.

Combined capability of the ghost socket:
1. Receive all room broadcasts (`startPick`, `terrainGenerated`, `turnResult`, `matchSettled`) because it is subscribed to the Socket.IO room channel. This gives the attacker perfect knowledge of game state without being a recognized participant.
2. Emit unlimited relay events to disrupt the opponent's UI state.
3. Emit `giveTurn` with up to ~1 MB `terrainData` payload (H028: `maxHttpBufferSize` not configured), which the server relays verbatim to the victim — potentially triggering client-side deserialization of a large object.
4. Ghost socket disconnect eventually triggers `cleanupRoom`, which may cancel an active wagered match.

## Attack Scenario

### Prerequisites

- An active or just-created wagered room visible via `broadcastRooms` or `getRooms`
- Attacker controls two sockets (two browser tabs or a scripted client)
- Target room has `room.active === false` (waiting for a second player)

### Execution

1. **Race the join:** Attacker Socket A sends `joinRoom` for the target room. Attacker Socket B immediately sends a second `joinRoom` for the same room before Socket A's `verifyBalance` call completes (50–500 ms window for wagered rooms, sub-millisecond for free rooms with MongoDB I/O). One socket wins the race and becomes `room.player`. The other becomes the ghost. The attacker does not need to know which outcome occurred — both sockets receive `startPick` notifications regardless; the ghost receives them because it is in the Socket.IO room channel.

2. **Maintain the ghost:** The attacker does not disconnect the ghost socket. The ghost receives all game events, giving the attacker full match-state visibility without holding a recognized player slot.

3. **Relay spam the opponent:** During the opponent's turn, the ghost emits a burst of `angleChange` events with rapidly oscillating `rotation` values:
   ```
   for each tick at 30/sec:
       ghostSocket.emit('angleChange', { rotation: Math.random() * 360 })
   ```
   The server relays each as `opponentAngleChange` to the victim. The victim's aiming indicator flickers continuously. In a 60-second turn timer, this sustained disruption degrades the victim's ability to aim accurately.

4. **`giveTurn` large-payload relay bomb:** The ghost emits:
   ```
   ghostSocket.emit('giveTurn', {
       terrainData: 'A'.repeat(900000),
       pos1: 0, pos2: 0, rotation1: 0, rotation2: 0
   })
   ```
   The server allocates and relays a 900 KB object to all room members. At 30 events/sec, this is 27 MB/sec of relay traffic directed at the victim's browser connection. Combined with no per-event rate limit on `giveTurn`, this is a targeted bandwidth exhaustion attack on the victim specifically.

5. **Match termination via ghost disconnect:** If the attacker wants to force match cancellation (e.g., after the victim is ahead), the ghost socket disconnects. The ghost's `disconnect` handler fires with `client.roomId` set. If the match is in BATTLE or WEAPON_SHOP state and `authenticatedWallets[client.id]` is set (the ghost will have this if it joined via a free-room path after calling `createRoom` without auth), the disconnect triggers `cleanupRoom` which calls `handleSettlementFailure` and cancels the escrow PDA — denying the victim their winnings.

## Severity Assessment

**HIGH** (slightly below CRITICAL because the attack requires winning the join race, which reduces reliability compared to the individual CRITICAL-rated constituents in some scenarios, but the impact to a targeted victim is severe):

- **DoS impact:** Sustained relay spam degrades victim gameplay in timed wagered matches. Turn forfeiture from UI confusion results in financial loss.
- **Information leak:** Ghost receives all game events without being a recognized participant.
- **Bandwidth attack:** `giveTurn` large-payload relay directed at victim at 30/sec = 27 MB/sec.
- **Match cancellation:** Ghost disconnect triggers room cleanup, potentially cancelling the escrow and denying the winner their payout.
- **Reliability:** For wagered rooms, the race window is 50–500 ms (RPC latency). Scripted clients can synchronize the two join events reliably. For free rooms with MongoDB I/O, the window may be sub-millisecond but still exploitable with sufficient volume.
- **No fix for relay events needed from H016 to close this:** Fixing H019 (adding a sentinel) eliminates the ghost socket. Fixing H016 (adding `requireAuth`) eliminates the relay spam vector. Both are required for full remediation of this chain.

## Recommendations

### Primary — Fix H019: Set `room.active` as Sentinel Before First Yield

```js
// server/socket-io/main.js — joinRoom handler
var room = findRoom(roomId)
if (!room || room.active === true) return

// CLAIM SLOT SYNCHRONOUSLY before any await
room.active = true  // add this line immediately after the guard
```

This closes the race window. The second concurrent `joinRoom` handler will now see `room.active === true` and return without creating a ghost socket.

### Secondary — Fix H016: Add `requireAuth` to All Six Relay Events

Even if the join race is fixed, the relay events remain accessible to any socket with `client.roomId` set (e.g., legitimate authenticated players can still misuse them). Adding `requireAuth` is the correct defense-in-depth:

```js
client.on('giveTurn', (data) => {
    if (!requireAuth(client, 'giveTurn')) return  // add this
    // ...
})
// Repeat for: weaponPick, shoot, weaponChange, angleChange, powerChange
```

### Tertiary — Add Room Membership Validation to Relay Events

Beyond authentication, verify that the emitting socket is one of the two recognized players (`room.host.socketId` or `room.player.socketId`):

```js
client.on('angleChange', (data) => {
    if (!requireAuth(client, 'angleChange')) return
    const room = findRoom(client.roomId)
    if (!room) return
    const isRecognizedPlayer = room.host?.socketId === client.id || room.player?.socketId === client.id
    if (!isRecognizedPlayer) return  // ghost sockets rejected here
    // ...
})
```

This directly closes the chain: even if a ghost socket exists, it cannot emit relay events because it is not `room.host.socketId` or `room.player.socketId`.

### Quaternary — Cap `giveTurn` Payload

Regardless of other fixes, strip or cap `terrainData` from the `giveTurn` relay to prevent large-payload relay amplification:

```js
client.on('giveTurn', (data) => {
    // ...
    const { pos1, pos2, rotation1, rotation2 } = data  // drop terrainData entirely
    client.to(client.roomId).emit('recieveTurn', {pos1, pos2, rotation1, rotation2})
})
```
