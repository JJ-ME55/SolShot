# S004 — Self-Pair Wager Farming via Matchmaking + Position Control

**Finding ID:** S004
**Type:** Supplemental — Attack Chain
**Investigator:** Dinh's Bulwark — Phase 3 Supplemental Strategies
**Date:** 2026-02-23
**Constituent Findings:** H020 (self-pairing via concurrent queue), H018 (non-host weapon manipulation), H047 (positionUpdate drift)
**Category:** LOGIC-01 (Business Logic), ERR-02 (Race Conditions), Financial

---

## Verdict: CONFIRMED

**Severity: CRITICAL**

Each constituent finding is independently confirmed. Self-pairing (H020) is trivially exploitable with two browser tabs; it gives the attacker full bilateral control of a wagered match. Non-host weapon manipulation (H018) allows the attacker to control the weapon array regardless of which tab was assigned the host role. Position drift (H047) allows the attacker's winning tab to guarantee maximum damage output. Together, these three findings constitute a complete, deterministic pipeline for winning wagered matches against legitimate opponents — either by squatting the queue to intercept real players or by farming the wager pool against itself.

The escrow mechanics do not protect against self-pairing: the Anchor program performs no check that `player_one` and `player_two` are distinct wallet addresses.

## Chain Analysis

### Flaw 1 — H020: Same-Wallet Self-Pairing (Deterministic)

**File:** `server/socket-io/main.js`, lines 1242–1253

The `joinQueue` handler's pairing gate checks only wager amount equality before consuming the queue entry:

```js
if (queue.length > 0) {
    const opponent = queue[0];
    if (opponent.wager !== wagerAmount) {
        // Wager mismatch — push to queue separately
        queue.push({ ... });
        return;
    }
    queue.shift(); // now safe to consume
```

There is no check of the form `opponent.wallet !== authenticatedWallets[client.id]`. Two sockets authenticating with the same wallet address both succeed (line 541: `authenticatedWallets[client.id] = result.walletAddress` is socket-scoped; line 109 in auth.js: `handleAuthenticate` is purely per-socket). Tab A enters the queue; Tab B immediately matches against Tab A.

The resulting `wagerStates` entry:

```js
// main.js:1268-1280
wagerStates[roomId] = {
    amount: wagerAmount,
    wallets: {
        [opponent.socketId]: opponent.wallet,   // wallet W
        [client.id]: authenticatedWallets[client.id] || null,  // also wallet W
    },
}
```

Both socket IDs map to the same wallet address. The attacker controls both sides of the match.

### Flaw 2 — H018: Non-Host Weapon Manipulation

**File:** `server/socket-io/main.js`, lines 1666–1691

```js
client.on('createWeaponArray', (data) => {
    if (!requireAuth(client, 'createWeaponArray')) return
    // NO host check here — compare to deleteRoom at line 927 which has if (!client.isHost) return
    // ...
    room.randomArray = randomArray  // unconditional overwrite
    io.sockets.in(client.roomId).emit('setWeaponArray', {randomArray: room.randomArray})
})
```

In the self-pairing scenario, the attacker knows which tab was assigned host role (both are controlled). If the non-host tab (Tab B) also needs weapon array control, it can call `createWeaponArray` without restriction. In practice, for the self-pairing scenario this flaw is redundant — the attacker controls both tabs. Its significance in this chain is for the Amplified Attack variant where the attacker's Tab A (host) is matched against a legitimate opponent: the attacker can still control the weapon array even if Tab A was assigned the non-host role by queue ordering.

### Flaw 3 — H047: positionUpdate Position Drift

**File:** `server/socket-io/main.js`, lines 2371–2402

The attacker's "winning" tab drifts its server-stored tank position to the optimal firing location using `positionUpdate` at 30 events/sec with 400 px per event (12,000 px/sec):

```js
client.on('positionUpdate', (data) => {
    if (!requireAuth(client, 'positionUpdate')) return
    // NO turn ownership check (compare stepLeft line 2414: ms.currentTurn !== client.id)
    // NO moveCounts gate (compare stepLeft line 2420: ms.moveCounts[client.id] >= 4)
    // ...
    if (dx > 400 || dy > 200) return  // only check: 400px per event, unchained
    room.host.pos.x = clampedX  // unconditional write
})
```

The attacker pre-positions their tank directly above the "losing" tab's tank, ensuring every shot is a direct hit.

### Combined Attack Flow

When chained with the Amplified Attack variant from H020:

1. **Queue squatting:** Attacker opens N socket pairs. Each pair self-matches, filling available queue slots. When a legitimate player joins, they are matched against the attacker's Tab A (which the attacker controls as a pre-positioned, weapon-manipulating adversary).

2. **Escrow interaction with self-pairing:** The server calls `createMatchEscrow(roomId, wagerAmount, walletA=W, walletB=W)`. The Anchor program initializes the escrow PDA with both `player_one` and `player_two` set to wallet W. The on-chain program has no constraint preventing this — its code at `lib.rs` line 101 only checks `player_one != player_two` if such a constraint were present, which it is not. Both deposit transactions target wallet W. The attacker signs both, paying from the same wallet.

3. **Self-pairing settlement math:** Settlement calls `settleMatchEscrow(winner=W, loser=W, amount)`. The Anchor program transfers 90% of the pot to `winner_account` — which is wallet W — and sends 7% to treasury and 3% to ops. Net cost to attacker: 10% of wager amount per self-paired match, all extracted from the attacker's own funds. No other player is harmed in pure self-pairing.

4. **Amplified variant with legitimate victim:**
   - Attacker Tab A enters queue.
   - Legitimate player matches against Tab A.
   - Attacker uses `positionUpdate` drift (H047) to guarantee maximum damage every turn.
   - Attacker can also use `createWeaponArray` (H018) to re-roll the weapon array until favorable weapons appear.
   - Attacker wins. Settlement sends 90% of combined wager pot (0.9 × 2 × wager) to attacker wallet.
   - Legitimate player loses their full wager deposit.

## Escrow Does Not Protect Against Same-Wallet Settlement

A critical amplifier of this chain: the on-chain escrow program is correctly implemented for its documented scope but does not validate distinct wallet addresses. Confirmed from the Anchor program (`programs/solshot-escrow/src/lib.rs`):

The `settle_match` instruction at line 555 uses:
```rust
#[account(
    has_one = authority,
    constraint = winner_account.key() == escrow.player_one ||
                 winner_account.key() == escrow.player_two
                 @ SolshotError::InvalidWinner,
)]
```

This constraint ensures the winner is one of the two registered players. When both `player_one` and `player_two` are wallet W, any `winner_account` equal to W satisfies the constraint. The settlement succeeds. There is no `player_one != player_two` invariant in the Anchor program.

The SOS (on-chain) audit confirmed this structure. The off-chain server is the only layer that could enforce wallet uniqueness — and it does not.

## Severity Assessment

**CRITICAL.** The chain is:
- **Deterministic:** Self-pairing requires no timing precision. Two browser tabs, one wallet, one queue entry — guaranteed to match.
- **Financially impactful:** In the Amplified Attack, the attacker extracts a legitimate player's full wager deposit every match.
- **Low complexity:** No binary patching, no RCE, no Solana interaction required beyond normal client operation.
- **Composed of three independently CRITICAL/HIGH findings:** Each constituent is exploitable alone; together they form a complete, undetectable win-guarantee system.
- **On-chain program provides no protection:** Same-wallet settlement succeeds. The only defense layer is the off-chain server.

## Recommendations

### Fix 1 — Reject Same-Wallet Pairing at Match-Time (Closes H020, Closes Chain)

```js
// server/socket-io/main.js, before queue.shift() at line 1252
const joinerWallet = authenticatedWallets[client.id] || null;
if (joinerWallet && opponent.wallet && opponent.wallet === joinerWallet) {
    queue.push({ socketId: client.id, wallet: joinerWallet, ... });
    client.emit('queueWaiting', { matchMode, matchLength, position: queue.length });
    console.warn(`[Queue] Self-pairing rejected: ${joinerWallet}`);
    return;
}
```

### Fix 2 — Add Host-Only Guard to `createWeaponArray` (Closes H018)

```js
client.on('createWeaponArray', (data) => {
    if (!requireAuth(client, 'createWeaponArray')) return
    if (!client.isHost) {
        client.emit('createWeaponArrayError', { reason: 'Only host can create weapon array' })
        return
    }
    // ...
})
```

### Fix 3 — Restrict `positionUpdate` to Post-Blast Context (Closes H047)

Remove the general-purpose `positionUpdate` position write. Make knockback server-authoritative: have the server physics engine write the post-blast position directly rather than accepting a client-reported position. If client reporting is required, bind each accepted `positionUpdate` to a server-issued knockback token that expires after one use.

### Fix 4 — Add Server-Side Same-Wallet Uniqueness Constraint

Maintain a reverse map `walletToSocketId` to enforce one active socket per wallet:

```js
const walletToSocketId = new Map();
// On authenticate: reject or disconnect prior socket for same wallet
// On disconnect: remove wallet from map
```

This closes the self-pairing prerequisite entirely at the authentication layer.
