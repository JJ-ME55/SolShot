# S005 — positionUpdate Drift Injection via Unauthenticated Relay Chain

**Finding ID:** S005
**Type:** Supplemental — Attack Chain
**Investigator:** Dinh's Bulwark — Phase 3 Supplemental Strategies
**Date:** 2026-02-23
**Constituent Findings:** H016 (unauthenticated relay events), H047 (positionUpdate 12K px/sec exploit)
**Category:** AUTH-01 (Authentication), LOGIC-01 (Business Logic), Financial

---

## Verdict: POTENTIAL

**Severity: MEDIUM**

The strategy hypothesized that `positionUpdate` might be one of the unauthenticated relay events from H016, enabling an unauthenticated socket to spoof tank positions. The code investigation reveals this is **not the case**: `positionUpdate` requires authentication (`requireAuth` at line 2371). However, the chain is partially realized through a different mechanism — the conditional authentication gap in room entry events (`createRoom`/`joinRoom`/`joinQueue`) allows an unauthenticated socket to obtain `client.roomId`, after which it can emit the six unauthenticated relay events including `giveTurn` with spoofed `pos1`/`pos2`/`rotation1`/`rotation2` fields. This relay injects false position data into the opponent's client-side rendering state, not the server's authoritative state. The verdict is POTENTIAL because the real-world financial impact depends on whether the client's rendering layer uses `recieveTurn` position data for game logic versus display only.

## Chain Analysis

### Investigation: Is positionUpdate Unauthenticated?

**File:** `server/socket-io/main.js`, line 2371–2372

```js
client.on('positionUpdate', (data) => {
    if (!requireAuth(client, 'positionUpdate')) return   // AUTHENTICATION IS PRESENT
```

`positionUpdate` is **not** in the list of unauthenticated events. The full authentication inventory from H016 confirms:

| Event | Auth Check | Result |
|-------|-----------|--------|
| `positionUpdate` | `requireAuth` | AUTHENTICATED — not unauthenticated |
| `weaponPick` | NONE | Unauthenticated |
| `shoot` | NONE | Unauthenticated |
| `weaponChange` | NONE | Unauthenticated |
| `angleChange` | NONE | Unauthenticated |
| `powerChange` | NONE | Unauthenticated |
| `giveTurn` | NONE | Unauthenticated |

The hypothesis as stated — "unauthenticated socket spoof positions via positionUpdate" — is NOT CONFIRMED.

### What Is Confirmed: Partial Chain via giveTurn Position Injection

`giveTurn` at line 2479 relays `pos1`, `pos2`, `rotation1`, `rotation2` verbatim to the opponent:

```js
// server/socket-io/main.js:2479-2483
client.on('giveTurn', (data) => {
    if (!data || typeof data !== 'object') return
    const { terrainData, pos1, pos2, rotation1, rotation2 } = data
    client.to(client.roomId).emit('recieveTurn', {terrainData, pos1, pos2, rotation1, rotation2})
})
```

No authentication check. No validation of `pos1`/`pos2`/`rotation1`/`rotation2` values. An unauthenticated socket with `client.roomId` set (achieved via the conditional auth gap on `createRoom`/`joinRoom`/`joinQueue` for free/zero-wager rooms) can emit `giveTurn` with arbitrary position values:

```js
// Attack payload:
ghostSocket.emit('giveTurn', {
    terrainData: null,
    pos1: 9999,    // fake position for player 1
    pos2: -500,    // fake position for player 2
    rotation1: 180,
    rotation2: 0
})
```

The server relays `recieveTurn` with these attacker-supplied coordinates to all room members including the victim.

### What the Client Does with recieveTurn

The critical question for impact assessment is whether the client uses `recieveTurn` position data for game logic (collision, hit detection, physics) or only for display (animating tank positions on screen).

Based on the architecture:
- The server is intended to be authoritative on tank positions. Server physics (`processShot` in `server/services/physics.js`) uses `room.host.pos` and `room.player.pos` — not anything from `recieveTurn`.
- The `fire` handler at line 1881 uses `serverPos` (the server-stored position), not any client-relayed position from `giveTurn`.
- `recieveTurn` likely drives the client's Phaser canvas animation of where the opponent's tank is rendered.

If the client ONLY uses `recieveTurn` for display rendering, then injecting false positions causes visual desynchronization (the victim sees tank positions that don't match the server-authoritative values) but does not alter physics outcomes. This is a display-layer attack.

If any legacy client code uses `recieveTurn` `pos1`/`pos2` values to update a local game-state model that is then used for aiming assistance or hitbox calculations, the impact escalates to a physics manipulation attack.

**Assessment:** Based on the available codebase, this appears to be a display-layer attack. The server does not consume `recieveTurn`; it only emits it. Server physics uses `room.host.pos`/`room.player.pos` exclusively. The financial impact is therefore indirect (confusion leading to poor shots in timed turns) rather than direct physics manipulation.

### Access Path for Unauthenticated Socket

The conditional auth gap from H016 enables an unauthenticated socket to obtain a room ID:

```js
// server/socket-io/main.js:1121 — createRoom (wagerAmount > 0 condition only)
if (wagerAmount > 0 && !requireAuth(client, 'createRoom')) return
// → free room creation: zero auth required

// server/socket-io/main.js:970-972 — joinRoom
if (roomWager > 0) {
    if (!requireAuth(client, 'joinRoom')) return
// → free room join: zero auth required

// server/socket-io/main.js:1231 — joinQueue
if (wagerAmount > 0 && !requireAuth(client, 'joinQueue')) return
// → free queue: zero auth required
```

After creating or joining a free room, the unauthenticated socket has `client.roomId` set. It can then emit `giveTurn` with arbitrary position data, and the server will relay it to the room.

For a wagered match, the unauthenticated socket CANNOT join (auth is required when `wagerAmount > 0`). To reach a wagered match with an unauthenticated socket, the attacker would need to combine this with H019 (join race ghost socket), which provides a mechanism to get a socket into a room without completing a valid join.

## Scenarios

### Scenario A: Free Room Relay Confusion (Confirmed)

1. Attacker creates a free room without authenticating (wagerAmount = 0).
2. A legitimate player joins the free room.
3. During the match, the attacker emits rapid `giveTurn` events with scrambled `pos1`, `pos2`, `rotation1`, `rotation2` values.
4. The victim's client receives `recieveTurn` events with false tank positions.
5. The victim's aiming display shows the opponent's tank at incorrect locations. In a timed game, this visual confusion can lead to missed shots.
6. No financial impact (free game). Impact: disrupted user experience.

### Scenario B: Wagered Match via Ghost Socket (Chain with H019)

1. Attacker wins the join race (H019) to place a ghost socket in a wagered room.
2. The ghost socket is unauthenticated but has `client.roomId` set.
3. Ghost socket emits `giveTurn` with false position data targeting the legitimate opponent.
4. Opponent's display shows incorrect tank positions. Combined with `angleChange` and `powerChange` relay spam (also unauthenticated), the opponent's entire visual game state is corrupted.
5. Potential financial impact if the opponent's AI or client-side prediction uses `recieveTurn` position data for shot calculation.

### Scenario C: Authenticated Player Injecting False Positions (Confirmed, Different Vector)

An authenticated player in a wagered match can also emit `giveTurn` with false position data — this requires no unauthenticated access. The attacker is legitimately in the match and injects `recieveTurn` events with arbitrary `pos1`/`pos2` to confuse the opponent's display during the opponent's own turn. This is a pure H016 exploitation and not dependent on H047.

## Verdict Justification

**POTENTIAL** because:
1. The specific hypothesis (`positionUpdate` via unauthenticated socket) is not realized — `positionUpdate` requires auth.
2. The chain that IS realized (unauthenticated `giveTurn` position injection via free room or ghost socket) affects the client-side display layer, not server-authoritative physics. Financial impact is indirect (user confusion) rather than direct (physics manipulation).
3. The impact escalates to CONFIRMED HIGH if any client code uses `recieveTurn` position fields for game logic beyond display rendering. This cannot be excluded without full client-side analysis of the `recieveTurn` handler in the Phaser scene.

The chain is real and the components interact as described. The POTENTIAL rating reflects that the ultimate impact depends on a client-side behavior that this server-side audit cannot definitively confirm.

## Recommendations

### Fix 1 — Add `requireAuth` to `giveTurn` (Closes the Position Injection Path)

```js
client.on('giveTurn', (data) => {
    if (!requireAuth(client, 'giveTurn')) return  // add this
    // ...
})
```

### Fix 2 — Validate `pos1`/`pos2`/`rotation1`/`rotation2` in `giveTurn`

If the event is retained with authentication, add bounds validation:

```js
client.on('giveTurn', (data) => {
    if (!requireAuth(client, 'giveTurn')) return
    if (!data || typeof data !== 'object') return
    const { pos1, pos2, rotation1, rotation2 } = data
    if (!Number.isFinite(pos1) || !Number.isFinite(pos2)) return
    if (!Number.isFinite(rotation1) || !Number.isFinite(rotation2)) return
    // Drop terrainData entirely — server terrain is authoritative
    client.to(client.roomId).emit('recieveTurn', {pos1, pos2, rotation1, rotation2})
})
```

### Fix 3 — Delete `giveTurn` and `recieveTurn` Entirely

Server terrain is generated server-side via `requestTerrain`. The `recieveTurn`/`giveTurn` pair is described as "LEGACY: turn relay." If the client no longer needs to pass terrain data between turns (because it fetches from the server), removing these events eliminates both the position injection vector and the large-payload DoS vector from H016.

### Fix 4 — Remove Conditional Auth from Free Room Entry

Require authentication for all room participation regardless of wager amount. This closes the unauthenticated-socket-gets-roomId prerequisite.
