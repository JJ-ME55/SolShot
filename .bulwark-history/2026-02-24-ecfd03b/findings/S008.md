# S008 — Refund Failure + PlayAgain Permanent Fund Lock

**Finding ID:** S008
**Type:** Supplemental — Attack Chain
**Investigator:** Dinh's Bulwark — Phase 3 Supplemental Strategies
**Date:** 2026-02-23
**Constituent Findings:** H007 (refundWager wrong parameters — silent failure), H012 (playAgainRequest wagerless rematch)
**Category:** LOGIC-02 (Financial Logic), ERR-01 (Error Handling), Financial

---

## Verdict: CONFIRMED

**Severity: CRITICAL**

H007 and H012 are independently confirmed vulnerabilities. When chained, they create a specific scenario where deposited funds are permanently stranded with no automatic recovery path: a player disconnects during the LOBBY phase of a wagered match before the game starts, the `refundWager` call silently fails (H007), the escrow PDA remains active and funded, the server's match state is destroyed by cleanup, and the opponent — or either player — subsequently triggers `playAgainRequest` on the now-dead room or creates a new match. The original escrow PDA is now orphaned: the server has lost its `roomId`-to-PDA association, `refundWager` never issued the on-chain `cancel_match`, and the 48-hour Anchor permissionless reclaim window is the only remaining recovery path.

Even without the lobby disconnect path, H012 alone creates a fund-lock scenario on the rematch: original escrow PDA closed after first match, rematch proceeds with phantom wager, settlement of rematch fails on the closed PDA, `failedSettlements` exhausts retries, match result is permanently lost. The two findings together add a second fund-lock path that operates earlier in the match lifecycle.

## Chain Analysis

### H007: refundWager Silent Failure on Lobby Disconnect

**File:** `server/socket-io/main.js`, lines 686–691

```js
} else if (ms.status === MATCH_STATES.LOBBY) {
    // Not started yet — refund if applicable
    const wallet = ws.wallets[client.id]
    if (wallet && ws.amount > 0) {
        await refundWager(wallet, ws.amount)   // line 690 — ONLY 2 ARGS
    }
}
```

`refundWager` has the signature (file: `server/services/solana.js`, lines 235–253):

```js
export async function refundWager(playerAddress, wagerSOL, matchId, playerOneAddress, playerTwoAddress) {
    if (wagerSOL === 0) return { success: true, txSignature: null };

    if (isEscrowEnabled() && matchId && playerOneAddress && playerTwoAddress) {  // line 241
        const result = await cancelMatchEscrow(matchId, playerOneAddress, playerTwoAddress);
        // ...
    }
    // Fallback: log refund — always reached when matchId/addresses are undefined
    logger.info({ amount: wagerSOL }, '[Solana] Refund (off-chain)');
    return { success: true, txSignature: null };   // spurious success
}
```

With only 2 arguments at the call site, `matchId`, `playerOneAddress`, `playerTwoAddress` are all `undefined`. The guard on line 241 evaluates to `false`. No `cancelMatchEscrow` call is made. The function returns `{ success: true }` despite performing no on-chain action. The escrow PDA created at match initialization remains live and funded on-chain.

### H012: playAgainRequest Creates Wagerless Rematch

**File:** `server/socket-io/main.js`, lines 2516–2534

```js
matchStates[client.roomId] = createMatchState(client.roomId, paRoundType)
delete goldStates[client.roomId]
delete weaponInventories[client.roomId]
delete shopReady[client.roomId]
// H037: Don't delete wagerStates — cleaned up by removeRoom or next createRoom
```

`playAgainRequest` resets match state but:
- Does NOT call `createMatchEscrow`
- Does NOT call `buildDepositTransaction`
- Does NOT emit `escrowDeposit` to clients
- Does NOT reset `ws.deposits`
- Leaves `room.escrowPDA` pointing to the original (now-closed) PDA

The first match's PDA was closed by Anchor's `close = authority` constraint on `settle_match`. The rematch runs without any on-chain escrow. When the rematch ends and `settleMatchEscrow(roomId, winnerWallet)` is called, the Anchor program rejects it (`AccountNotInitialized` or equivalent). `handleSettlementFailure` is triggered, which attempts `cancelMatchEscrow` (also fails — PDA doesn't exist), appends to `failedSettlements`, exhausts 5 retries over 5× exponential backoff, and eventually gives up. The rematch winner receives nothing.

### The Combined Chain: Orphaned Escrow + Phantom Rematch

The two findings interact across the match lifecycle to create a scenario where funds are locked at two different points with no recovery path:

**Phase 1 — Initial match creation (correct behavior):**
1. Both players join a wagered room.
2. `createMatchEscrow(roomId, wagerAmount, hostWallet, playerWallet)` is called.
3. Escrow PDA is initialized on-chain with `roomId` as the seed.
4. Both players receive `escrowDeposit` events and sign/submit their deposit transactions.
5. `wagerStates[roomId].deposits` records both deposit confirmations.

**Phase 2 — Lobby disconnect triggers H007 (fund lock point 1):**
6. One player disconnects while `ms.status === MATCH_STATES.LOBBY`.
7. The cleanup code at line 686–691 calls `refundWager(wallet, ws.amount)` — only 2 args.
8. `refundWager` silently returns `{ success: true }` without calling `cancelMatchEscrow`.
9. The escrow PDA remains live on-chain with deposited funds.
10. `cleanupRoom` continues to execute, deleting `rooms[roomId]`, `matchStates[roomId]`, `wagerStates[roomId]` from server memory.
11. The server has now lost all knowledge of the escrow PDA for `roomId`. The PDA exists on-chain but the server can no longer reference it by any in-memory state.

**Phase 3 — playAgainRequest on a new/existing room triggers H012 (fund lock point 2):**
12. The remaining player (or a new session) creates a new room with the same players.
13. A new match runs to completion. The server calls `settleMatchEscrow(newRoomId, winnerWallet)`.
14. This succeeds (new room, new PDA). First match is over.
15. Both players trigger `playAgainRequest`.
16. `playAgainRequest` preserves `wagerStates[newRoomId]` but creates no new escrow.
17. Second match (rematch) runs to completion. `settleMatchEscrow(newRoomId, winnerWallet)` is called on the closed first-match PDA.
18. Transaction fails. `handleSettlementFailure` runs. 5 retries. Permanent failure.
19. Rematch winner receives nothing.

**The Fund-Lock State:**
- Phase 2 leaves the original lobby-phase escrow PDA live on-chain with no server-side reference. Funds are locked until the 48-hour Anchor permissionless reclaim window. No automated recovery is possible because the server lost `roomId`, `playerOneAddress`, and `playerTwoAddress`.
- Phase 3 leaves the rematch winner without their winnings. No on-chain funds are at risk (no new escrow was funded), but the financial harm to the winner (they played a real wagered game with no payout) is the same as a theft.

## Attack Scenario

An adversarial player (the loser) can deliberately trigger this chain:

1. Enter a wagered match (Quick Match or Duel).
2. Both players complete deposits.
3. Loser waits until `ms.status === MATCH_STATES.LOBBY` (before `startPick` fires — the window after joining but before the shop phase begins).
4. Loser disconnects (closes browser tab). `refundWager` is called with 2 args → silent failure. Escrow PDA is orphaned.
5. If the winner was the host, they receive `reconnectExpired` after 30s and the match is cleaned up (via `cleanupRoom` / `cleanupRoom_timeout`). The winner never receives their funds. The loser's deposit is also locked in the PDA.
6. The loser (if they intend to exploit further) waits for the 48-hour Anchor reclaim window and uses `permissionlessReclaimEscrow` to recover their deposit. The winner cannot recover theirs without knowing the PDA address (which the server no longer has).

### Deliberate playAgain Abuse

Separately, a player who loses match 1 can deliberately trigger `playAgainRequest` knowing that the rematch will be played without escrow, and the winner will receive nothing. The loser has nothing to lose — they already forfeited their wager in match 1. The winner is denied their match-2 winnings.

## Severity Assessment

**CRITICAL:**
- **Direct fund loss:** The lobby-disconnect path (H007) leaves deposited SOL locked in the escrow PDA with no server-side recovery path. The server lost the PDA reference when it cleaned up the room state. Only the 48-hour Anchor reclaim window provides any escape.
- **Rematch fund denial:** The playAgainRequest path (H012) denies the rematch winner their winnings with no on-chain recourse.
- **Triggerable by the loser intentionally:** A losing player can deliberately trigger both paths to deny the winner any payout while minimizing their own losses.
- **No error surfaced:** Both failures return or cause `{ success: true }`. No alert is sent. No admin notification occurs. The team does not know funds are locked.
- **Compounded by in-memory state loss:** Server restart destroys `failedSettlements`, erasing any retry context for the playAgain settlement failure.

## Recommendations

### Primary Fix for H007 — Supply All Required Arguments

```js
// server/socket-io/main.js:686-691
} else if (ms.status === MATCH_STATES.LOBBY) {
    const wallet = ws.wallets[client.id]
    if (wallet && ws.amount > 0) {
        const p1wallet = ws.wallets[room.host?.socketId]
        const p2wallet = ws.wallets[room.player?.socketId]
        await refundWager(wallet, ws.amount, roomId, p1wallet, p2wallet)  // all 5 args
    }
}
```

All needed values (`roomId`, `room.host`, `room.player`, `wagerStates`) are available at the point of the call.

### Primary Fix for H012 — Re-initialize Escrow on playAgainRequest

```js
// server/socket-io/main.js — inside playAgainRequest, before emitting playAgain
const ws = wagerStates[client.roomId]
if (ws && ws.amount > 0 && isEscrowEnabled()) {
    ws.deposits = {}  // reset deposit tracking for new match
    const hostWallet = ws.wallets[room.host.socketId]
    const playerWallet = ws.wallets[room.player.socketId]
    const escrowResult = await createMatchEscrow(client.roomId, ws.amount, hostWallet, playerWallet)
    if (!escrowResult.success) {
        io.sockets.in(client.roomId).emit('playAgainError', { reason: 'Escrow creation failed' })
        return
    }
    room.escrowPDA = escrowResult.escrowPDA
    // Build and emit deposit transactions for both players
    // Start depositTimers[client.roomId] countdown
    return  // wait for escrowActive before emitting playAgain
}
```

### Secondary Fix — Add refundWager Validation Guard

Add a warning log inside `refundWager` when called with escrow enabled but missing parameters:

```js
// server/services/solana.js — inside refundWager
if (isEscrowEnabled() && (!matchId || !playerOneAddress || !playerTwoAddress)) {
    console.warn('[Solana][CRITICAL] refundWager called without escrow params — fund lock possible');
    // Optionally: throw to prevent silent failure rather than returning success
}
```

### Tertiary Fix — Gate ready on Deposit State

```js
// server/socket-io/main.js:1420 — ready handler
if (room.host.isReady && room.player && room.player.isReady) {
    const ws = wagerStates[client.roomId]
    if (ws && ws.amount > 0 && isEscrowEnabled()) {
        const hostDep = ws.deposits?.[room.host.socketId]
        const playerDep = ws.deposits?.[room.player.socketId]
        if (!hostDep || !playerDep) {
            client.emit('readyError', { reason: 'Escrow deposit not confirmed' })
            return
        }
    }
    // proceed with shopPhase / startGame
}
```

This closes the H012 path where the match starts before deposits are confirmed.
