# H004 — Settlement Without Deposit Verification

**Status:** CONFIRMED
**Severity:** HIGH
**Confidence:** HIGH
**Origin:** KB

## Summary

All three settlement code paths in `server/socket-io/main.js` (normal match-end, turn-timeout forfeit, and disconnect forfeit) call `settleMatch()` conditioned only on `wagerStates[roomId].amount > 0` — never on whether `wagerStates[roomId].deposits` shows that both players actually deposited. The on-chain `settle_match` instruction provides a partial backstop by requiring `escrow.state == Active`, which only becomes true when both on-chain deposits have landed. However, a race window exists — and in dev mode (escrow disabled) the vulnerability is fully exploitable with no on-chain protection at all.

### Deposit tracking state — only used by deposit timeout check and `escrowActive` emit

`ws.deposits` is set in `escrowDepositConfirm` (lines 1782–1783):

The `ws.deposits` object is checked in two places: the `DCA-01` deposit countdown timeout (lines 1065–1067 and 1328–1330) and the `escrowActive` emit (line 1790). It is **never checked** before any of the three `settleMatch()` call sites.

### On-chain backstop in `settle_match` (`programs/solshot-escrow/src/lib.rs` lines 228–232)

```rust
// lines 228–232
pub fn settle_match(ctx: Context<SettleMatch>, winner: Pubkey) -> Result<()> {
    require!(
        ctx.accounts.escrow.state == MatchState::Active,
        EscrowError::InvalidState
    );
```

`MatchState::Active` is only set after both players deposit on-chain (lines 206–207):

```rust
// lines 206–207
if escrow.player_one_deposited && escrow.player_two_deposited {
    escrow.state = MatchState::Active;
```

This means `settleMatchEscrow()` will revert with `InvalidState` if only one (or zero) players deposited — **but only when escrow is enabled**. In dev mode (`isEscrowEnabled()` returns false), `settleMatch()` in `solana.js` falls through to the off-chain logging path and returns `{ success: true }` unconditionally, with no on-chain guard whatsoever.

## Root Cause

The server settlement logic treats `wagerStates[roomId].amount > 0` as the sole predicate for attempting settlement. The `ws.deposits` field, which tracks which players have confirmed their on-chain deposits (populated by `escrowDepositConfirm` at line 1782), is never consulted at any of the three settlement call sites. The design assumes that the match cannot reach the end (BATTLE state completion, turn-timeout forfeit, or disconnect forfeit) before both deposits are confirmed — but this assumption is not enforced. The `escrowActive` event that signals "both deposited" is advisory and client-directed; the server has no hard gate that prevents match progression or settlement without confirmed deposits.

The on-chain program provides a partial runtime defense (`require!(state == Active)`), but this is absent in dev mode and does not protect against the race window between a single player depositing and match-end being triggered before the second deposit arrives.

## Impact

**In dev mode (escrow disabled):** Full exploit. If only one player deposits (or neither does), the server calls `settleMatch()` at match end, which returns `{ success: true }` and logs a fake settlement. No SOL moves, but the match result is recorded and SHOT milestones are emitted as though a real wagered match occurred. Attacker can farm wagered-match rewards without depositing.

**In production (escrow enabled) — race window:** If a match ends (by forfeit, turn-timeout, or normal completion) between the time player 1 deposits and player 2 deposits, the server calls `settleMatchEscrow()` against an escrow PDA in `AwaitingDeposits` state. The on-chain call reverts with `InvalidState`. The server catches the error, calls `handleSettlementFailure()`, and queues the match in `failedSettlements` (an in-memory array lost on restart). Player 1's deposited SOL is now stuck in the `AwaitingDeposits` escrow PDA until the 48-hour `permissionless_reclaim` window opens. The player has no immediate recovery path.

**In production (escrow enabled) — intentional exploit:** A malicious player can forfeit (disconnect) immediately after winning the first round — before their opponent has completed the deposit TX. The server calls `settleMatch()` for the forfeiting-player's opponent as winner. The on-chain call reverts. Legitimate player's deposited funds are locked. Attacker loses nothing (never deposited).

## Recommendation

Add an explicit deposit-status guard at each of the three settlement call sites. Before calling `settleMatch()`, check whether both players have confirmed deposits:

```js
// Guard to add before all three settleMatch() call sites
const hostDeposited = ws.deposits && ws.deposits[room.host?.socketId]
const playerDeposited = ws.deposits && ws.deposits[room.player?.socketId]
const bothDeposited = hostDeposited && playerDeposited

if (!bothDeposited) {
    // Cancel escrow and refund whoever deposited
    await refundWager(null, ws.amount, roomId,
        ws.wallets[room.host?.socketId],
        ws.wallets[room.player?.socketId])
    transitionState(ms, MATCH_STATES.CANCELLED)
    // Notify both players of cancellation
    return
}
// Only then call settleMatch(...)
```

Additionally, the `DCA-01` deposit countdown timer (lines 1059–1080 and 1321–1346) is the correct mechanism for handling cases where deposits are never confirmed — but it only fires after a 2-minute window. The settlement paths must also be hardened to refuse settlement when deposit tracking is incomplete, independent of that timer. The on-chain `require!(state == Active)` check is a necessary defense-in-depth measure but should not be the primary safeguard.
