# H005 — burnAmount=0 Dust Burn Prestige Bypass

**Status:** CONFIRMED
**Severity:** HIGH
**Confidence:** HIGH
**Origin:** KB

## Summary

The `prestigeBurn` socket handler extracts `burnAmount` directly from the client-supplied payload and passes it unvalidated to `verifyBurnTransaction`. Inside `verifyBurnTransaction`, the expected amount is derived solely from this client-controlled value via `BigInt(expectedAmount) * BigInt(1_000_000_000)`. When `burnAmount` is `0`, `expectedRaw` resolves to `0n`, and the on-chain comparison `BigInt(ixAmount) >= 0n` is trivially true for any real burn instruction — including a 1-lamport dust burn for a completely different SPL token operation. An attacker who can produce any valid confirmed transaction containing a burn instruction against the SHOT mint signed by their wallet can satisfy the amount check regardless of how much they actually burned.

## Evidence

**main.js line 1618** — `burnAmount` extracted from raw client payload with no type check or range validation:

```js
const { txSignature, burnAmount } = data || {}
if (!txSignature) {
    client.emit('prestigeResult', { success: false, reason: 'No burn transaction provided' })
    return
}
```

`burnAmount` has no guard — it can be `0`, `undefined`, negative, or any non-numeric type. There is no check for `burnAmount > 0` or `typeof burnAmount === 'number'`.

**main.js line 1626** — raw client value forwarded directly as the expected amount:

```js
const verification = await verifyBurnTransaction(txSignature, wallet, burnAmount)
```

**shot-token.js lines 508-512** — the expected amount is computed entirely from the client-supplied parameter:

```js
// Verify amount (expectedAmount is in whole tokens, on-chain is raw with 9 decimals)
const expectedRaw = BigInt(expectedAmount) * BigInt(1_000_000_000);
if (BigInt(ixAmount) < expectedRaw) {
    return { valid: false, reason: `Burned ${ixAmount} raw but need ${expectedRaw} for prestige` };
}
```

When `expectedAmount` is `0`: `BigInt(0) * BigInt(1_000_000_000) === 0n`. Any `ixAmount >= 0` satisfies the check.

**shot-token.js lines 74-81** — the correct expected amounts live in the server-side tier table, which is never consulted during verification:

```js
export const PRESTIGE_TIERS = [
    { tier: 0, name: 'Unranked',  burnCost: 0,    ... },
    { tier: 1, name: 'Bronze',    burnCost: 200,  ... },
    { tier: 2, name: 'Silver',    burnCost: 500,  ... },
    { tier: 3, name: 'Gold',      burnCost: 1200, ... },
    { tier: 4, name: 'Platinum',  burnCost: 2500, ... },
    { tier: 5, name: 'Diamond',   burnCost: 4000, ... },
];
```

`verifyBurnTransaction` never references `PRESTIGE_TIERS`. The `burnCost` values in this table are the ground truth but are bypassed entirely.

**shot-token.js lines 358-376** — the `prestigeBurn` function that runs after verification does check `state.balance >= nextTier.burnCost`:

```js
if (state.balance < nextTier.burnCost) {
    return {
        success: false,
        reason: `Need ${nextTier.burnCost} SHOT, have ${state.balance}`,
        ...
    };
}
```

However `state.balance` is the server's in-memory SHOT balance, which is accumulated by playing matches. This is a meaningful backstop only if the attacker has never earned any SHOT. An attacker who has played enough matches to accumulate the requisite SHOT balance in-game (and who therefore would legitimately qualify for the tier anyway) can bypass the on-chain burn cost entirely, keeping their on-chain SHOT while still receiving the prestige tier.

## Root Cause

`verifyBurnTransaction` accepts `expectedAmount` as a caller-supplied parameter rather than deriving it from the server-authoritative `PRESTIGE_TIERS` table. The function was designed to be generic (caller specifies the expected amount), but the only caller is the socket handler, which passes the client payload field directly. Because `burnAmount` is never validated as a positive integer before the `BigInt()` coercion, a client-supplied value of `0` makes the amount comparison a no-op. The server derives the correct expected burn amount (`nextTier.burnCost`) in `prestigeBurn()` after verification, but it is never passed into the verification step.

## Impact

An attacker can advance to any prestige tier (Bronze through Diamond) without burning the required SHOT tokens (200–4000 SHOT per tier) by:

1. Producing any valid, confirmed Solana transaction containing a `burn` or `burnChecked` instruction targeting the SHOT mint (`4NnYBycLLo8acgbkLz2SyCXd3KU8jgHQLEmrVypi5VLd`), signed by their wallet. A dust burn of 1 raw unit (0.000000001 SHOT) suffices.
2. Emitting a `prestigeBurn` socket event with `{ txSignature: "<that tx>", burnAmount: 0 }`.
3. The on-chain check passes (`0 >= 0n`). The server-side balance check in `prestigeBurn()` then gates on whether the attacker's in-memory SHOT balance meets `nextTier.burnCost`. If they have accumulated that balance through match play (which they would ordinarily need to have done to afford the burn legitimately), the tier is unlocked without burning any meaningful tokens.

The net effect is that attackers can retain their on-chain SHOT supply while obtaining prestige tiers and the associated locked weapons (Homing Missile, Cruiser, Tommy Gun, Chain Reaction, Pineapple). Because the in-memory balance check still runs, this is not a complete free bypass for players with zero SHOT balance — but it is a complete bypass of the on-chain burn requirement, which is the economic invariant the feature is meant to enforce.

## Recommendation

Replace the client-supplied `burnAmount` with the server-authoritative tier cost derived from `PRESTIGE_TIERS` before calling `verifyBurnTransaction`. The handler already knows the player's current tier from `getPrestigeInfo(wallet)` or equivalently via `getPlayerShotState(wallet).prestigeTier`. The fix has two parts:

**1. Derive `expectedAmount` on the server before calling verification:**

```js
// In main.js prestigeBurn handler, after authenticating wallet:
const state = getPlayerShotState(wallet)   // already imported
const currentTier = state ? state.prestigeTier : 0
const nextTier = PRESTIGE_TIERS[currentTier + 1]
if (!nextTier) {
    client.emit('prestigeResult', { success: false, reason: 'Already at max prestige' })
    return
}
const expectedAmount = nextTier.burnCost   // server-authoritative, never from client

const verification = await verifyBurnTransaction(txSignature, wallet, expectedAmount)
```

**2. Validate `burnAmount` if it is kept at all (e.g., for logging):**

```js
// Optionally keep burnAmount for client-side logging but never use it for security decisions
if (typeof burnAmount !== 'number' || !Number.isInteger(burnAmount) || burnAmount <= 0) {
    client.emit('prestigeResult', { success: false, reason: 'Invalid burn amount' })
    return
}
```

This ensures the amount checked against the on-chain transaction is always the value from `PRESTIGE_TIERS[n].burnCost` rather than a value the client controls.
