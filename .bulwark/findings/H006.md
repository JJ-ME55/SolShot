# H006 — Turn-Timer Forfeit Bypasses Settlement Lock

**Status:** NOT VULNERABLE
**Severity:** N/A (mitigated)
**Confidence:** HIGH
**Origin:** Novel

## Summary

The hypothesis asserts that `startTurnTimer`'s forfeit branch calls `settleMatch` without acquiring the `settle:${roomId}` mutex (implemented via `withLock`), creating a double-settlement race with the fire handler. After tracing both paths, the hypothesis does not hold. The timer's forfeit path is protected by a different, but equally effective, guard: an atomic `transitionState(ms, MATCH_STATES.SETTLING)` call that acts as a CAS-like gate before `settleMatch` is invoked. Because Node.js is single-threaded and the state mutation is synchronous, only one concurrent path can observe `status === BATTLE` and win the transition. The fire handler uses `withLock` as an additional, belt-and-suspenders guard, but the `transitionState` gate it checks inside the lock (`if (ms.status !== MATCH_STATES.SETTLING) return`) is the same mechanism the timer path relies on, meaning the two paths cannot race to a double-settlement outcome.

`transitionState` (match.js lines 41–53) performs the mutation synchronously:

```js
export function transitionState(matchState, newState) {
    const currentState = matchState.status;
    const validTransitions = TRANSITIONS[currentState];
    if (!validTransitions || !validTransitions.includes(newState)) {
        console.warn(`Invalid state transition: ${currentState} → ${newState}`);
        return false;   // rejected if already SETTLING/COMPLETE/CANCELLED
    }
    matchState.status = newState;  // committed atomically in the JS event loop
    matchState.stateChangedAt = Date.now();
    return true;
}
```

The TRANSITIONS table (match.js lines 23–32) only allows `BATTLE → SETTLING` once; a second call from any other path (timer or fire) when `status` is already `SETTLING` will return `false` and the caller will not proceed to `settleMatch`.

## Root Cause

The forfeit branch in `startTurnTimer` (lines 309–403) does not call `withLock`. This was intentional or an oversight depending on perspective. However, it is not exploitable because:

1. **Node.js event-loop atomicity.** The `setTimeout` callback and socket event handlers (fire, disconnect) are all async functions executed in the single-threaded Node.js event loop. Two of them cannot execute concurrently; they interleave at `await` points only. The `transitionState` call at line 326 is a synchronous, non-awaited mutation. No other handler can run between the status check at line 293 (`ms.status !== MATCH_STATES.BATTLE`) and the state write inside `transitionState` at match.js line 50. The transition is therefore effectively atomic.

2. **`transitionState` is an idempotent gate.** `BATTLE → SETTLING` is a one-way, one-shot transition. The TRANSITIONS table allows it only from `BATTLE`. Once the timer path commits `SETTLING`, any subsequent concurrent attempt by the fire handler to call `transitionState(ms, MATCH_STATES.SETTLING)` will receive `false` (because `SETTLING → SETTLING` is not in the table) and exit at line 2082 before ever reaching `settleMatch` or acquiring the lock.

3. **The fire handler has belt-and-suspenders.** Even if the fire handler somehow slipped through `transitionState`, it re-checks `ms.status !== MATCH_STATES.SETTLING` inside the lock at line 2087 before calling `settleMatch`.

4. **The disconnect handler also guards inside the lock.** It checks `currentMs.status === MATCH_STATES.SETTLING` at line 581 and returns early.

The guards.js file header comment lists "H006" as one of the issues that `withLock` fixes, but the fix description there refers to the original hypothesis ticket's `requireAuth` guard (the comment `// Fixes: H006 — auth bypass` at line 38). The `withLock` export comment at line 115 cites H020 (double settlement race). The timer path's lack of `withLock` is a style inconsistency, not a vulnerability, given the state-machine gate.

## Impact

No impact. The `transitionState` guard prevents double-settlement across all three settlement paths (fire, timer forfeit, disconnect). A race between the timer's forfeit branch and a simultaneous `fire` event cannot produce two calls to `settleMatch` for the same room.

## Recommendation

While not a vulnerability, adding `withLock` to the timer forfeit path would make the protection symmetric and easier to reason about during future audits. A belt-and-suspenders pattern consistent with the fire and disconnect handlers would be:

```js
// Proposed: wrap the forfeit settlement in withLock for consistency
await withLock(`settle:${roomId}`, async () => {
    // Re-check inside lock
    if (ms.status !== MATCH_STATES.SETTLING) return
    if (wsState && wsState.amount > 0) {
        ...await settleMatch(...)
    }
})
```

This would make the absence of double-settlement immediately obvious to a future auditor without requiring knowledge of Node.js's event-loop atomicity guarantees.
