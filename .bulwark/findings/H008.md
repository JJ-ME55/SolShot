# H008 — SHOT Milestone Double-Claim via Concurrent Matches

**Status:** NOT VULNERABLE
**Severity:** N/A
**Confidence:** HIGH
**Origin:** KB

## Summary

The hypothesis predicts that two concurrent `recordMatchPlayed` calls for the same wallet can both pass the `claimedMatchIds.has(matchId)` check before either adds the matchId, enabling double SHOT emission for a single match. This race window does not exist. `recordMatchPlayed` is a fully synchronous function — there is no `await` between the `has()` guard and the `add()` call. Node.js single-threaded execution means no two calls for the same wallet can interleave. Additionally, the two per-match call sites use distinct wallets (host vs. player), and both share the same `matchId`, but each wallet's `claimedMatchIds` is a separate Set — so no cross-wallet dedup collision is possible either.

## Evidence

### `recordMatchPlayed` is entirely synchronous

`server/services/shot-token.js` lines 247–350:

```js
// Line 247
export function recordMatchPlayed(walletAddress, matchInfo = {}) {
    const state = getPlayerShotState(walletAddress);   // synchronous
    // ...
    // Line 272 — guard check
    if (matchId && state.claimedMatchIds && state.claimedMatchIds.has(matchId)) {
        return { earned: 0, newBalance: state.balance, reason: 'Match already claimed' };
    }
    // ... all synchronous state mutations ...
    // Line 338-339 — add happens in same tick, no await between has() and add()
    if (!state.claimedMatchIds) state.claimedMatchIds = new Set();
    if (matchId) state.claimedMatchIds.add(matchId);

    saveMilestoneState(walletAddress);   // fire-and-forget (does NOT await)
    // ...
}
```

There is no `await` anywhere in `recordMatchPlayed`. The entire function body — from the `has()` check at line 272 to the `add()` at line 339 — executes atomically within a single JavaScript turn of the event loop. No other code can run between these two lines.

### Call site uses the same `matchId` for both players but distinct wallets

`server/socket-io/main.js` lines 2156–2185:

```js
// Line 2156 — single matchId generated once per match end
const matchId = `${this.roomId}:${ms.currentRound}:${Date.now()}`

// Line 2163-2172 — host wallet call
if (hostWallet) {
    shotResults[hostId] = recordMatchPlayed(hostWallet, {
        matchId,
        // ...
    })
}
// Line 2175-2185 — player wallet call (different wallet address, own claimedMatchIds Set)
if (playerWallet) {
    shotResults[playerId] = recordMatchPlayed(playerWallet, {
        matchId,
        // ...
    })
}
```

Both calls use the same `matchId` string, but `claimedMatchIds` is stored per-wallet inside `playerShotState[walletAddress]` (line 139 of shot-token.js). Host and player have independent Sets, so sharing a matchId does not cause cross-wallet dedup — which is correct behaviour (both players legitimately earn milestones from the same match).

### `claimedMatchIds` is per-wallet, not global

`server/services/shot-token.js` lines 128–146:

```js
// Line 85 — top-level map keyed by walletAddress
const playerShotState = {};

// Lines 128-146 — each wallet gets its own state object with its own Set
if (!playerShotState[walletAddress]) {
    playerShotState[walletAddress] = {
        // ...
        claimedMatchIds: new Set(),   // line 139 — per-wallet Set
        // ...
    };
}
```

There is no global `claimedMatchIds` Set shared across wallets. Two different wallets calling `recordMatchPlayed` with the same `matchId` each consult their own independent Set — this is not a race condition, it is correct design.

## Root Cause

The hypothesis assumed either (a) an `await` exists between the dedup `has()` check and the `add()` call, or (b) `claimedMatchIds` is a shared global Set. Neither is true. The function is synchronous end-to-end and the Set is per-wallet.

## Impact

None. The described double-claim race condition cannot occur under the current implementation.

## Recommendation

No code change required for this specific hypothesis. Two related concerns are documented separately and remain valid:

1. **Same-wallet double-fire** (e.g., disconnect/reconnect triggering `matchEnd` twice for the same socket): the synchronous dedup does protect against this correctly because the first call adds the matchId before returning, so a second call to `recordMatchPlayed` with the same `matchId` and same wallet will hit the `has()` guard and return early.

2. **`saveMilestoneState` is fire-and-forget** (line 342): the in-memory `claimedMatchIds` Set is authoritative during the server's lifetime, but a crash between the `add()` at line 339 and the MongoDB write completing would drop the dedup record. On restart, `loadMilestoneState` (line 175) restores `claimedMatchIds` from MongoDB — but any matchId that was added to the Set but not yet flushed to MongoDB would be lost, allowing replay. This is a separate, lower-severity concern (H-adjacent, persistence gap) and is outside the scope of H008.
