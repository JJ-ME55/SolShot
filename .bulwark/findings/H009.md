# H009 — SHOT Supply Cap Race Condition Bypass

**Status:** NOT VULNERABLE
**Severity:** N/A
**Confidence:** HIGH
**Origin:** Novel

## Summary

The hypothesis predicts that concurrent match settlements can both read `totalShotEmitted` below the cap, both emit tokens, and together exceed the 7,000,000 SHOT reward pool. Investigation shows this scenario cannot occur in practice. Node.js's single-threaded event loop guarantees that `recordMatchPlayed` — a fully synchronous function — runs to completion without interleaving. The supply cap check and the increment happen in the same synchronous tick with no `await` between them. Additionally, the per-match `matchId` deduplication guard provides a second layer of protection within each match's own calls. No over-emission is possible through concurrency. The one real (but bounded) weakness — the debounced MongoDB persist — does not create over-emission; it only risks under-counting across restarts, which is separately addressed.

## Evidence

### Supply cap check and increment are atomic within Node.js's event loop

`server/services/shot-token.js`, lines 277–331:

```js
// H034: Check global supply cap before emitting
if (totalShotEmitted >= SHOT_TOKEN_CONFIG.rewardPool) {
    return { earned: 0, newBalance: state.balance, reason: 'Reward pool exhausted' };
}

// ... milestone loop (synchronous) ...

// H034: Clamp earned to remaining supply
if (totalShotEmitted + totalEarned > SHOT_TOKEN_CONFIG.rewardPool) {
    const allowed = SHOT_TOKEN_CONFIG.rewardPool - totalShotEmitted;
    const excess = totalEarned - allowed;
    state.balance -= excess;
    totalEarned = allowed;
}

// H034: Track global emissions
totalShotEmitted += totalEarned;
```

There is no `await` anywhere between line 277 (the cap check) and line 331 (the increment). The entire function is declared as:

```js
export function recordMatchPlayed(walletAddress, matchInfo = {}) {
```

Not `async`. JavaScript's event loop cannot preempt synchronous execution. A second call to `recordMatchPlayed` from any concurrent match cannot interleave with this function.

### Both calls within the same match are sequential and synchronous

`server/socket-io/main.js`, lines 2163–2185:

```js
if (hostWallet) {
    shotResults[hostId] = recordMatchPlayed(hostWallet, {   // line 2164
        ...
        matchId,
        ...
    })
}
if (playerWallet) {
    shotResults[playerId] = recordMatchPlayed(playerWallet, {  // line 2176
        ...
        matchId,
        ...
    })
}
```

These two calls are back-to-back synchronous calls. Call 1 completes fully (including incrementing `totalShotEmitted`) before call 2 begins. Call 2 therefore reads the already-updated `totalShotEmitted`.

### matchId deduplication provides defense-in-depth

The `matchId` is constructed as:

```js
const matchId = `${this.roomId}:${ms.currentRound}:${Date.now()}`   // line 2156
```

Both players receive the same `matchId` string. Within `recordMatchPlayed`, lines 272–274:

```js
if (matchId && state.claimedMatchIds && state.claimedMatchIds.has(matchId)) {
    return { earned: 0, newBalance: state.balance, reason: 'Match already claimed' };
}
```

Since host and player have separate `playerShotState` entries (keyed by wallet address), this check does not prevent the second player from claiming — nor should it. But it does prevent the same player from claiming the same match twice if the settlement path fires more than once, e.g. via a forfeit+normal-end overlap.

### Debounced persist does not create over-emission

`server/services/shot-token.js`, lines 109–116:

```js
function persistEmissionCount() {
    if (savePending) return;
    savePending = true;
    setTimeout(async () => {
        savePending = false;
        await saveServerState(totalShotEmitted);
    }, 1000);
}
```

The debounce coalesces rapid saves. The in-memory `totalShotEmitted` variable is always the authoritative value. The debounce only affects how quickly it is written to MongoDB. Under-persistence (e.g. a crash within the 1-second window) means the saved counter lags behind the true value, causing the server to re-allow some emissions after restart — but this is a restart-persistence gap, not a concurrency over-emission bug. It is bounded by the number of matches played within the debounce window (typically 1–2 matches per second at most).

### Emission is in-memory SHOT balance only — no SPL token transfers

The `recordMatchPlayed` function increments `state.balance` (an in-memory integer) and persists to MongoDB. It does not trigger any SPL token transfer. The burned mint authority means no on-chain minting is possible regardless. Over-emission would inflate players' in-game balances, not create new on-chain tokens.

## Root Cause

No root cause applies — the system is not vulnerable to this race condition. The design correctly relies on JavaScript's single-threaded event loop to provide implicit mutual exclusion for synchronous counter operations. The two-layer protection (single-thread atomic increment + matchId dedup) is sound within a single process.

## Impact

None from this specific hypothesis. The supply cap is effectively enforced by Node.js's execution model for the concurrency scenario described. The restart-persistence lag from the debounced save is a separate, lower-severity issue (risk: a crash within 1 second of emissions could allow a small number of tokens to be re-emitted after restart, bounded to the 7M pool total).

## Recommendation

No fix required for the concurrency race described in H009. The existing design is correct.

Two adjacent notes for completeness:

1. The 1-second debounced persist (`persistEmissionCount`) means a server crash in that window causes `totalShotEmitted` to be under-counted in MongoDB. On restart, `initShotState()` loads the stale value, allowing slightly more SHOT to be emitted than the cap should permit. This is bounded and self-correcting once the next successful save occurs, but it is worth acknowledging. Mitigation: reduce debounce to 0ms (fire immediately, or use `$inc` atomically in Mongo).

2. If the server is ever horizontally scaled (multiple Node.js processes behind a load balancer), the in-memory `totalShotEmitted` would diverge across instances and the single-thread guarantee would no longer apply. The current architecture assumes a single process and would require a distributed atomic counter (e.g. Redis `INCR` or MongoDB `$inc` with `findAndModify`) before scaling.
