# H011 — failedSettlements Recovery Loop Race with Active Settlement
**Status:** NOT VULNERABLE
**Severity:** LOW
**Confidence:** HIGH
**Origin:** Novel

## Summary

The `failedSettlements` retry interval does not use `withLock` and does not inspect live match state before issuing a `cancelMatchEscrow` call. However, analysis of when entries are placed into `failedSettlements` versus how they interact with active settlement paths reveals that a meaningful double-settlement race is not achievable. Entries only enter `failedSettlements` after a `settleMatch` or `cancelMatchEscrow` call has already **failed** — meaning the on-chain escrow account is still in an unresolved (Active/Deposited) state, never in a Settled or Cancelled state. The retry loop then calls `cancelMatchEscrow`, which is a different operation from `settleMatch`. An overlapping `settleMatch` call on an already-cancelled escrow would fail at the Solana program level (wrong account state discriminant), so no fund duplication can occur. The actual risk is a narrower conflict: the retry loop and the normal-path settlement running concurrently for the same match, one issuing `settle_match` and the other issuing `cancel_match`, racing to mutate the on-chain account. This race is real but self-resolves: exactly one instruction will succeed and one will fail (Anchor's state guard rejects the second), with no double-payout outcome. The confirmed risk is operational (a settle could lose to a cancel, or vice versa), not a fund-duplication vulnerability.

## Evidence

**failedSettlements is populated only on settlement failure (lines 107–136, main.js):**

```js
// handleSettlementFailure — called only when settleMatch() returns { success: false }
// or throws, meaning the on-chain escrow is still in Active/Deposited state.
failedSettlements.set(roomId, {
    matchId: roomId,
    escrowPDA,
    p1wallet,
    p2wallet,
    wagerSOL: ws?.amount || 0,
    failedAt: Date.now(),
    attempts: 1,
    error: error || 'unknown',
});
```

`handleSettlementFailure` is called from three sites:
1. Turn-timeout forfeit (line 346, 351) — after `settleMatch()` fails or throws.
2. Disconnect/reconnect-timeout forfeit inside `cleanupRoom` (lines 660, 679) — after `settleMatch()` fails or throws.
3. Normal match-end inside the `fire` handler's `withLock` block (lines 2109, 2129) — after `settleMatch()` fails or throws.

In every case, the on-chain escrow remains in its pre-settlement state (funds locked, account not yet closed). No case adds a match to `failedSettlements` when settlement has already succeeded.

**The retry loop issues cancelMatchEscrow, not settleMatch (lines 82–104):**

```js
setInterval(async () => {
    for (const [matchId, data] of failedSettlements.entries()) {
        if (data.attempts >= 5) {
            failedSettlements.delete(matchId);
            continue;
        }
        try {
            const result = await cancelMatchEscrow(matchId, data.p1wallet, data.p2wallet);
            if (result.success) {
                failedSettlements.delete(matchId);   // removed AFTER success
            } else {
                data.attempts++;
            }
        } catch (err) {
            data.attempts++;
        }
    }
}, 60_000);
```

The retry path always cancels (refunds), never settles. It does not re-attempt the original `settleMatch`. The intended recovery semantics are: "settlement failed — refund both players rather than leave funds locked."

**No `withLock` on the retry loop; no match-state check before issuing cancel:**

The interval body reads `failedSettlements` and fires the RPC call with no inspection of `matchStates[matchId]`. This means the retry can issue `cancel_match` for a room that:
- Has already been removed from memory (no `matchStates` entry) — harmless, the on-chain call either succeeds (refunds) or fails.
- Is currently inside a `withLock('settle:${roomId}')` block from the disconnect handler retrying the settlement — possible race described below.

**Settle/cancel conflict window:**

Suppose settlement fails, `handleSettlementFailure` stores the entry, and within the 60-second window the disconnect handler retries via `cleanupRoom` (this does not happen — `cleanupRoom` calls `settleMatch` once and delegates failure to `handleSettlementFailure`; it does not retry on its own). The realistic overlap is narrower: the interval fires at T+60s while a concurrent socket event (a second disconnect or a late `fire` event) is inside `withLock('settle:roomId')` calling `settleMatch`. In this window:

- `withLock('settle:roomId')` path calls `settleMatch` → `settleMatchEscrow` → on-chain `settle_match`.
- Simultaneously, the interval calls `cancelMatchEscrow` → on-chain `cancel_match`.

Both target the same PDA. The Anchor program's `settle_match` instruction requires the escrow account to be in `Active` state; `cancel_match` also requires `Active` state. One instruction will land first, close or transition the account, and the second will fail with an account-state error. No double disbursement is possible because the account can only be settled once — the program closes it after the first successful instruction.

**Entries removed only after a successful cancel (line 94):**

```js
if (result.success) {
    failedSettlements.delete(matchId);
}
```

If the cancel fails (because `settle_match` won the race and closed the account), `data.attempts++` increments and the entry remains. On the next 60-second tick, `cancelMatchEscrow` will fail again (account already closed), incrementing until it hits the 5-attempt limit and the entry is silently deleted. This means a failed settlement whose funds were actually distributed via `settle_match` will still appear in `failedSettlements` for up to ~5 minutes, logging spurious cancel failures but causing no financial harm.

**On-chain program state machine is the ultimate guard (escrow.js lines 400–411):**

```js
const tx = await program.methods
    .settleMatch(winner)
    .accounts({ escrow: escrowPDA, ... })
    .rpc();
```

Anchor's `settle_match` instruction requires `escrow.state == MatchState::Active` (or equivalent). After settlement or cancellation, the PDA is closed/state-changed. Any subsequent instruction targeting it fails with a Solana account-validation error, not a fund leak.

## Root Cause

The `failedSettlements` interval was designed as a best-effort recovery mechanism for on-chain escrow accounts that failed to settle. It does not use `withLock` and does not consult in-memory match state before issuing the RPC call. The architectural decision to use `cancelMatchEscrow` (refund) as the recovery action — rather than retrying `settleMatch` — avoids the double-settlement scenario explicitly. The residual risk is a settle-vs-cancel race within the 60-second retry window, which the Anchor on-chain program resolves atomically.

## Impact

**Financial impact:** None. The on-chain program enforces single-execution semantics; one of the two concurrent instructions will succeed and the other will fail. Funds cannot be double-disbursed.

**Operational impact (Low):**
- If the retry cancel wins the race against a legitimate settle, the wrong party may receive funds (both players refunded instead of winner receiving payout). This is a correctness concern but not a double-spend.
- If the settle wins the race, the entry persists in `failedSettlements` for up to ~5 minutes (5 × 60s), generating noisy log errors but no financial harm.
- Silent 5-attempt exhaustion: after 5 failed cancel retries against an already-settled account, the entry is deleted with no operator alert. An operator cannot distinguish "account was settled successfully via race-win" from "account is genuinely stuck."

The 60-second retry window is wide enough that the scenario where a second normal-path settlement caller appears for the same match is nearly impossible in practice — the normal-path callers (disconnect and fire) are each guarded by `withLock` and operate on match state that transitions to `SETTLING`/`COMPLETE`/`CANCELLED` before the 60-second mark.

## Recommendation

The vulnerability class (double settlement) is not exploitable due to on-chain program guards. The following lower-priority hardening measures address the operational correctness risk:

**1. Check match state before retrying cancel (eliminates stale-entry noise):**

```js
setInterval(async () => {
    for (const [matchId, data] of failedSettlements.entries()) {
        if (data.attempts >= 5) {
            console.error(`[Recovery] Giving up on settlement recovery for ${matchId}`);
            failedSettlements.delete(matchId);
            continue;
        }
        // Skip if match is now settled or complete in memory
        const ms = matchStates[matchId];
        if (ms && (ms.status === MATCH_STATES.COMPLETE || ms.status === MATCH_STATES.CANCELLED)) {
            console.log(`[Recovery] Match ${matchId} already resolved in memory — dropping retry`);
            failedSettlements.delete(matchId);
            continue;
        }
        // ... rest of retry logic
    }
}, 60_000);
```

Note: `matchStates` may no longer contain the entry if the room was removed. The check is useful but not sufficient — an absent entry should not be treated as evidence of resolution.

**2. Use `withLock` around the cancel attempt to serialize against any concurrent normal-path settlement:**

```js
await withLock(`settle:${matchId}`, async () => {
    const result = await cancelMatchEscrow(matchId, data.p1wallet, data.p2wallet);
    if (result.success) {
        failedSettlements.delete(matchId);
    } else {
        data.attempts++;
    }
});
```

This ensures the cancel call does not interleave with a concurrent `settleMatch` inside the disconnect or fire handlers, producing a deterministic winner rather than relying on on-chain atomic ordering alone.

**3. Alert on 5-attempt exhaustion** rather than silently deleting. Emit a monitoring event so operators can manually investigate whether funds remain locked on-chain.
