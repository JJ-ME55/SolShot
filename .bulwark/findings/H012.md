# H012 — playAgainRequest Creates Wagerless Wagered Match
**Status:** CONFIRMED
**Severity:** HIGH
**Confidence:** HIGH
**Origin:** KB

## Summary

The `playAgainRequest` handler in `server/socket-io/main.js` resets match state, gold, and weapon inventories for a new game while explicitly preserving `wagerStates[roomId]` intact (comment: "H037: Don't delete wagerStates"). It does not call `createMatchEscrow`, does not call `buildDepositTransaction`, does not emit `escrowDeposit` to the clients, and does not verify any new deposits before the rematch begins. The room's `room.escrowPDA` still points to the on-chain PDA from the completed (now closed/settled) match.

After both players send `playAgainRequest` and `playAgain` fires, each player sends `ready`. The `ready` handler at line 1420 checks only that both players have `isReady === true` — it has no gate on deposit state. The game proceeds directly to `shopPhase` / `startGame` for the second match with no funds locked on-chain, regardless of wager amount.

## Evidence

**playAgainRequest handler — no escrow reset, no deposit trigger (lines 2516–2534):**

```js
// server/socket-io/main.js  lines 2521-2526
// Reset match state, Gold, and inventories for new game
matchStates[client.roomId] = createMatchState(client.roomId, paRoundType)
delete goldStates[client.roomId]
delete weaponInventories[client.roomId]
delete shopReady[client.roomId]
// H037: Don't delete wagerStates — cleaned up by removeRoom or next createRoom
```

No call to `createMatchEscrow`, `buildDepositTransaction`, or any escrow-related function appears anywhere in the handler. The `room.escrowPDA` field on the room object is never cleared or replaced.

**`ready` handler — no deposit gate (lines 1420–1481):**

```js
// server/socket-io/main.js  line 1420
if (room.host.isReady && room.player && room.player.isReady) {
    // ... initializes gold, inventories, emits shopPhase + startGame
    // No check on wagerStates[roomId].deposits
    // No check on escrowActive flag
}
```

A search for `deposit`, `escrow`, or `wagerState` in the range lines 1395–1481 returns zero results.

**Original match creation does create escrow and request deposits (lines 1020–1084, 1304–1341):**

```js
// joinRoom (line 1025) and joinQueue (line 1306)
if (wagerAmount > 0 && isEscrowEnabled() && hostWallet && joinerWallet) {
    const escrowResult = await createMatchEscrow(roomId, wagerAmount, ...)
    // ... emits escrowDeposit to both clients
    // ... starts depositTimers[roomId] 2-minute countdown
}
```

This entire block is absent from `playAgainRequest`.

**Escrow PDA is closed after settlement — `close = authority` attribute (lib.rs line 566):**

```rust
// programs/solshot-escrow/src/lib.rs  line 560-568
#[account(
    mut,
    seeds = [b"match", escrow.match_id.as_bytes()],
    bump = escrow.bump,
    has_one = authority,
    close = authority,    // PDA is closed; rent returned to authority after settle_match
)]
pub escrow: Account<'info, MatchEscrow>,
```

The PDA keyed on `matchId` (which equals `roomId`) is destroyed by the Anchor `close` constraint when `settle_match` executes. The room's `room.escrowPDA` field therefore points to a non-existent account for the duration of the rematch.

**PDA seed is the roomId (escrow.js line 110):**

```js
// server/services/escrow.js  line 108-113
export function getEscrowPDA(matchId) {
    return PublicKey.findProgramAddressSync(
        [Buffer.from('match'), Buffer.from(matchId)],
        PROGRAM_ID
    );
}
```

Because `roomId` does not change across `playAgain`, a new `createMatch` call for the same room would attempt to re-initialize the same PDA address. Anchor's `init` constraint would reject this with `AccountAlreadyInitialized` if the account still existed — but since `close = authority` destroys it after settlement, re-initialization is technically possible. However, this path is never exercised because `createMatchEscrow` is never called from `playAgainRequest`.

**`wagerStates[roomId]` is deliberately preserved with stale `deposits` entries:**

After match 1 settles, `wagerStates[roomId]` still contains:
- `amount`: the original wager (e.g. 0.5 SOL)
- `wallets`: the socket-id-to-wallet-address map (valid as long as sockets haven't changed)
- `deposits`: `{ [hostSocketId]: <tx1>, [playerSocketId]: <tx2> }` — signatures from the completed match

The `ready` handler never consults `wagerStates`. The `escrowDepositConfirm` handler is never triggered again. No new SOL is locked.

## Root Cause

The `playAgainRequest` handler was designed to reuse an existing room to avoid re-matchmaking overhead. It resets all per-match ephemeral state but does not treat the wager as ephemeral. There is no "replay the escrow funding flow" step. The comment `// H037: Don't delete wagerStates — cleaned up by removeRoom or next createRoom` documents a deliberate choice to preserve the wager amount for room-listing purposes, but the consequence is that the escrow creation and deposit request steps are never re-run for the rematch.

The `ready` handler, which is the effective game-start gate, has no guard that requires `wagerStates[roomId].deposits` to be populated or `room.escrowPDA` to refer to a live on-chain account.

## Impact

**Financial impact — real SOL at risk:**

When two players complete a wagered match and both click "Play Again", the second (and all subsequent) match(es) in the room are played without any SOL locked on-chain. The `settleMatch` call at the end of rematch will invoke `settleMatchEscrow(roomId, winnerAddress)`, which attempts to call `settle_match` on the Anchor program. The Anchor program will fail with `AccountNotInitialized` (or equivalent) because the PDA was closed after match 1 settled. The `settleMatch` function propagates this as a failure (`result.success === false`), transitions the match to `CANCELLED`, and calls `handleSettlementFailure`. No SOL is paid to the winner. The loser also receives nothing because no escrow was funded.

In practice: both players risked their wager amount in a game whose outcome has no financial consequence, defeating the entire purpose of wagered play. A malicious player who loses match 1 can deliberately trigger `playAgainRequest` knowing that the rematch is effectively free.

**Secondary impacts:**

1. `handleSettlementFailure` logs a failed settlement and appends to the in-memory `failedSettlements` store. Under repeated play-again abuse this store grows without bound (no eviction).
2. The stale `deposits` entries in `wagerStates[roomId]` from match 1 can confuse any future diagnostic tooling or monitoring that inspects deposit state to infer "is this match escrowed?"
3. If escrow is disabled (dev/staging environment), `settleMatch` falls through to the off-chain logging path and silently reports a "successful" settlement with `txSignature: null` — making the bug invisible in non-production testing.

## Recommendation

**Primary fix — re-run the escrow funding flow inside `playAgainRequest`:**

When both players agree to play again and the room has a non-zero wager, the handler must:

1. Call `createMatchEscrow(roomId, ws.amount, hostWallet, joinerWallet)` to re-initialize the on-chain PDA (valid because the prior PDA was closed).
2. Call `buildDepositTransaction` for each player and emit `escrowDeposit` to their sockets, with a fresh `depositDeadline`.
3. Reset `ws.deposits` to `{}` so the old match-1 signatures do not satisfy the match-2 deposit gate.
4. Start a new `depositTimers[roomId]` countdown.
5. Prevent `ready` from starting the shop phase until both deposits are confirmed (either gate the `ready` handler on `ws.deposits` being fully populated when `ws.amount > 0`, or block `startGame` emission until `escrowActive` fires for the new PDA).

```js
// server/socket-io/main.js — inside playAgainRequest, after both players agree
// (replace the direct emit of playAgain with an async sequence)

const ws = wagerStates[client.roomId]
if (ws && ws.amount > 0) {
    // Reset deposit tracking for the new match
    ws.deposits = {}

    // Re-initialize on-chain escrow (PDA was closed after previous settlement)
    const hostWallet = ws.wallets[room.host.socketId]
    const playerWallet = ws.wallets[room.player.socketId]
    if (isEscrowEnabled() && hostWallet && playerWallet) {
        const escrowResult = await createMatchEscrow(client.roomId, ws.amount, hostWallet, playerWallet)
        if (escrowResult.success) {
            room.escrowPDA = escrowResult.escrowPDA
            const [hostDeposit, playerDeposit] = await Promise.all([
                buildDepositTransaction(client.roomId, hostWallet),
                buildDepositTransaction(client.roomId, playerWallet),
            ])
            const depositDeadline = Date.now() + DEPOSIT_TIMEOUT_MS
            const hostSocket = io.sockets.sockets.get(room.host.socketId)
            const playerSocket = io.sockets.sockets.get(room.player.socketId)
            if (hostSocket && hostDeposit.success) {
                hostSocket.emit('escrowDeposit', { roomId: client.roomId, transaction: hostDeposit.transaction, escrowPDA: escrowResult.escrowPDA, wager: ws.amount, depositDeadlineMs: depositDeadline })
            }
            if (playerSocket && playerDeposit.success) {
                playerSocket.emit('escrowDeposit', { roomId: client.roomId, transaction: playerDeposit.transaction, escrowPDA: escrowResult.escrowPDA, wager: ws.amount, depositDeadlineMs: depositDeadline })
            }
            depositTimers[client.roomId] = setTimeout(async () => {
                // ... same deposit-timeout cancel logic as initial match creation
            }, DEPOSIT_TIMEOUT_MS)
            // Delay emitting playAgain until escrowActive confirms both deposits
            // (escrowDepositConfirm handler already emits escrowActive when both confirm)
            return
        }
        // If escrow creation fails, abort play-again
        io.sockets.in(client.roomId).emit('playAgainError', { reason: 'Escrow creation failed for rematch' })
        return
    }
}

// Wagerless path — safe to proceed immediately
io.sockets.in(client.roomId).emit('playAgain', {})
```

**Gate `ready` on deposit state (defence-in-depth):**

```js
// server/socket-io/main.js — ready handler, line 1420
if (room.host.isReady && room.player && room.player.isReady) {
    const ws = wagerStates[client.roomId]
    if (ws && ws.amount > 0 && isEscrowEnabled()) {
        const hostDep = ws.deposits && ws.deposits[room.host.socketId]
        const playerDep = ws.deposits && ws.deposits[room.player.socketId]
        if (!hostDep || !playerDep) {
            client.emit('readyError', { reason: 'Wager deposit not confirmed — cannot start match' })
            return
        }
    }
    // ... proceed with shopPhase / startGame
}
```

This dual-layer fix (re-fund on play-again + gate on deposits in `ready`) ensures no wagered match can start without confirmed on-chain funds, regardless of whether the match is the first in a room or a subsequent rematch.
