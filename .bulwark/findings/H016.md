# H016 — Unauthenticated Socket Event Exploitation (6 Events)

**Hypothesis ID:** H016
**Investigator:** Dinh's Bulwark Pipeline — Phase 3 Hypothesis Investigation
**Date:** 2026-02-23
**Category:** AUTH-01 (Authentication), AUTH-03 (Authorization)
**Origin:** KB — Missing authentication check on sensitive events

---

## Verdict: CONFIRMED

**Severity: CRITICAL**

Six gameplay-affecting socket events in `server/socket-io/main.js` have no authentication check whatsoever. An unauthenticated WebSocket connection can send these events directly and the server will process and relay them without restriction. Additionally, a seventh event (`fire`) uses an inline `isAuthenticated` check rather than `requireAuth`, but is correctly authenticated. Three additional events (`createRoom`, `joinRoom`, `joinQueue`) use conditional authentication (wagered matches only), leaving free/practice-mode paths fully open. The hypothesis is fully confirmed and the impact extends slightly beyond the initial 6-event estimate.

## Evidence: Exact Code

### Event 1: `weaponPick` — Line 1650

```js
client.on('weaponPick', (data) => {
    if (!data || typeof data !== 'object') return
    const { arrayIndex } = data
    client.to(client.roomId).emit('opponentWeaponPick', {arrayIndex})
})
```

**File:** `server/socket-io/main.js:1650-1654`

No `requireAuth` call. No `client.isAuthenticated` check. No match-state guard. Any socket with `client.roomId` set — including one that never called `authenticate` — can emit `weaponPick` and the server will broadcast `opponentWeaponPick` with the attacker's `arrayIndex` value to the opponent.

### Event 6: `giveTurn` — Line 2479 (Most Severe)

```js
// LEGACY: turn relay (still works)
client.on('giveTurn', (data) => {
    if (!data || typeof data !== 'object') return
    const { terrainData, pos1, pos2, rotation1, rotation2 } = data
    client.to(client.roomId).emit('recieveTurn', {terrainData, pos1, pos2, rotation1, rotation2})

```

**File:** `server/socket-io/main.js:2479-2483`

No `requireAuth` call. No match-state guard. No room membership check beyond `client.roomId` being non-null. The `terrainData` field is relayed verbatim to all room members with no size cap. This is the most dangerous of the six events:

1. `terrainData` can be any arbitrary object — up to the 1 MB Socket.IO default (`maxHttpBufferSize` is also not configured per H028)
2. If the client-side physics engine uses `terrainData` from `recieveTurn` for collision/height calculations, this is a physics injection vector
3. `pos1`, `pos2`, `rotation1`, `rotation2` can be spoofed to inject false positional data into the opponent's rendering state

**Note:** The `recieveTurn` event name contains a typo ("recieve" instead of "receive") that propagates to client-side listeners.

### Conditional Auth Gap: `createRoom`, `joinRoom`, `joinQueue`

These three events include `requireAuth` only when `wagerAmount > 0`:

```js
// main.js:1121
if (wagerAmount > 0 && !requireAuth(client, 'createRoom')) return

// main.js:970-972
if (roomWager > 0) {
    if (!requireAuth(client, 'joinRoom')) return

// main.js:1231
if (wagerAmount > 0 && !requireAuth(client, 'joinQueue')) return;
```

An unauthenticated socket can create a free room, join a free room, and enter the matchmaking queue for free matches. Once `client.roomId` is set by the server (via `createRoom`/`joinRoom`/`joinQueue` matchmaking), that unauthenticated socket gains access to all six unauthenticated relay events. It then hits `requireAuth` only at `ready`, `buyWeapon`, and `shopDone` — creating an inconsistency where an unauthenticated socket occupies a room slot and can spam relay events but cannot proceed to gameplay.

## Attack Scenarios

### Scenario A: Unauthenticated UI Disruption in Wagered Match

**Prerequisites:** An active wagered match is in progress. The attacker knows (or guesses) the target room's Socket.IO room channel.

**Mechanism:** An attacker connects a raw WebSocket without authenticating. The attacker does not need to join the room via `joinRoom` — `client.roomId` is only checked by `client.to(client.roomId)`, which broadcasts to nothing useful if null. However, if the attacker can first join the target room (possible if it has not been filled), their `client.roomId` is set by the server.

**If attacker has a socket in the room (e.g., joined a free room with matching ID — extremely unlikely with 32-bit IDs but possible in a targeted attack):**

1. During the opponent's turn, attacker sends rapid `angleChange` events: `{ rotation: <random values> }`
2. Opponent client receives continuous `opponentAngleChange` events, causing their aiming display to flicker
3. Attacker sends `weaponChange` events to spoof fake weapon selection display on opponent's screen
4. Attacker sends `giveTurn` with crafted `pos1`, `pos2` to inject false tank positions into `recieveTurn`
5. Attacker sends `shoot` with `power`, `rotation` during battle state, injecting phantom shot visuals

**Impact:** Visual desynchronization, UI confusion, disruption of the opponent's ability to aim. In a timed match (60s turn timer), sustained disruption can cause turn forfeiture.

### Scenario B: `giveTurn` Large-Payload Relay (DoS)

**Prerequisites:** Attacker has `client.roomId` set (joined any free room).

**Attack:**
```js
socket.emit('giveTurn', {
    terrainData: 'A'.repeat(900000),  // 900 KB — within 1 MB Socket.IO default
    pos1: 0, pos2: 0, rotation1: 0, rotation2: 0
})
```

Server receives 900 KB payload, allocates it in memory, and broadcasts the same 900 KB to all room members via `client.to(client.roomId).emit('recieveTurn', ...)`. At 30 events/second (global rate limit), this is 27 MB/second of relay traffic. Multiple sockets doing this simultaneously creates amplified load. Since `maxHttpBufferSize` is not configured (H028), the full 1 MB default applies.

**Impact:** Server memory pressure, elevated CPU for serialization/deserialization, network bandwidth exhaustion for victims in the room. This is compounded by the fact that `giveTurn` has no per-event rate limit (only the global 30/s applies).

### Scenario C: Authentication Bypass Chain — Free Match to Relay Spam

**Prerequisites:** None.

**Attack path:**
1. Connect socket without authenticating
2. Emit `createRoom` with `player.wager = 0` — succeeds because `createRoom` only requires auth when `wagerAmount > 0`
3. Server sets `client.roomId` to the new room ID
4. Now emit any of the 6 unauthenticated relay events freely
5. If a second authenticated player joins (they will be blocked from wagering, but can join free), the attacker can spam all relay events targeting that player's session

**Impact:** Any unauthenticated socket can occupy a free-game room slot and spam relay events at whoever joins. Combined with `giveTurn` large-payload attack, this is a targeted DoS against a specific player.

### Scenario D: Impersonation via Relay Injection (Wagered Match Integrity)

**Prerequisites:** Attacker has a legitimate authenticated socket in a wagered match as one player.

**Attack:**
1. Attacker is Player 1, authenticated and in a wagered match
2. During Player 2's turn, attacker emits `weaponPick` with arbitrary `arrayIndex` values
3. Player 2's client renders `opponentWeaponPick` — spoofing what weapon they see Player 1 "selecting"
4. Attacker emits `angleChange` with false rotation values during Player 1's own turn (no turn-ownership check on relay)
5. No server-side enforcement prevents Player 1's relay from firing during Player 2's turn

**Note:** The `shoot` legacy relay has a `validateAction` state guard (`!validateAction(ms.status, 'shoot')`) which provides partial mitigation by blocking relay during non-battle states. However this guard is absent on `weaponChange`, `angleChange`, `powerChange`, and `giveTurn`.

**Impact:** Match integrity degraded. Visual state on opponent's screen can be manipulated by either player at any time, not just during their own turn.

## Root Cause Analysis

The 6 unauthenticated events fall into two categories:

**Category 1: Legacy relay events never updated during security hardening pass**

Events `giveTurn`, `weaponPick`, `weaponChange`, `angleChange`, `powerChange`, and `shoot` are described in comments as "LEGACY" or inherited from a prior client-side physics architecture. The auth hardening pass (which added `requireAuth` to `ready`, `buyWeapon`, `shopDone`, `fire`, `requestTerrain`, `positionUpdate`, `stepLeft`, `stepRight`, `requestTurn`, `playAgainRequest`, `createWeaponArray`, `escrowDepositConfirm`, `deleteRoom`) focused on high-value financial events and server-authoritative gameplay events. The legacy relay events were assessed as "low-value visual relays" and left unguarded.

Evidence of this assessment: The `shoot` handler has a comment `// H024: Add state validation + sanitize relayed fields` showing it received partial hardening (numeric sanitization + state guard) but the auth check itself was not added. The comment for `giveTurn` says `// LEGACY: turn relay (still works)` — treated as backward-compat infrastructure rather than a security surface.

**Category 2: Conditional auth on room entry events**

`createRoom`, `joinRoom`, and `joinQueue` have conditional auth (`wagerAmount > 0 only`) that was a deliberate design decision to allow guest/practice play. This creates the prerequisite condition for Category 1 exploitation: an unauthenticated socket can get `client.roomId` set, enabling all relay events.

## Severity Assessment

**Overall: CRITICAL** (matching hypothesis estimate)

**Severity rationale:**

- Financial impact in wagered matches: Relay injection can disrupt a player's UI during a wagered match, potentially causing turn forfeiture (60s timer) or incorrect aim. While the server-authoritative `fire` event is protected, the visual disruption path to forcing errors is real.
- The `giveTurn` event relays an unbounded `terrainData` object — without `maxHttpBufferSize` configuration, this is a 1 MB relay bomb amplifiable at 30/s.
- Zero authentication barrier: requires no credentials, no wallet, no Solana interaction. A raw WebSocket connection with no prior authentication is sufficient to exercise all 6 events.
- The conditional auth on `createRoom`/`joinRoom`/`joinQueue` means the attack surface is accessible without even an authenticated socket — just a free-room join.
- The 6 events individually rate as MEDIUM (relay disruption) but collectively rate CRITICAL because `giveTurn` enables a DoS vector, and the combination of all 6 can fully manipulate the opponent's visual game state in a wagered match.

## Recommendations

### Immediate Fix — Add `requireAuth` to all 6 events

The fix is a single-line addition to each handler. Apply consistently using the existing `requireAuth` guard from `server/middleware/guards.js`:

```js
// weaponPick — main.js:1650
client.on('weaponPick', (data) => {
    if (!requireAuth(client, 'weaponPick')) return  // ADD THIS LINE
    if (!data || typeof data !== 'object') return
    const { arrayIndex } = data
    client.to(client.roomId).emit('opponentWeaponPick', {arrayIndex})
})

// shoot (legacy relay) — main.js:1697
client.on('shoot', (data) => {
    if (!requireAuth(client, 'shoot')) return  // ADD THIS LINE
    if (!data || typeof data !== 'object') return
    const ms = matchStates[client.roomId]
    if (ms && !validateAction(ms.status, 'shoot')) return
    ...
})

// weaponChange — main.js:2348
client.on('weaponChange', (data) => {
    if (!requireAuth(client, 'weaponChange')) return  // ADD THIS LINE
    ...
})

// angleChange — main.js:2356
client.on('angleChange', (data) => {
    if (!requireAuth(client, 'angleChange')) return  // ADD THIS LINE
    ...
})

// powerChange — main.js:2364
client.on('powerChange', (data) => {
    if (!requireAuth(client, 'powerChange')) return  // ADD THIS LINE
    ...
})

// giveTurn — main.js:2479
client.on('giveTurn', (data) => {
    if (!requireAuth(client, 'giveTurn')) return  // ADD THIS LINE
    if (!data || typeof data !== 'object') return
    const { terrainData, pos1, pos2, rotation1, rotation2 } = data
    client.to(client.roomId).emit('recieveTurn', {terrainData, pos1, pos2, rotation1, rotation2})
})
```

### Secondary Fix — Add match-state guards to relay events

Beyond authentication, relay events should only process during valid match states. Add `validateAction` checks to prevent relays outside of their intended phases:

- `weaponPick`, `weaponChange`: Only valid during `WEAPON_SHOP` state
- `angleChange`, `powerChange`, `shoot`: Only valid during `BATTLE` state
- `giveTurn`: Only valid during `BATTLE` state (or delete entirely — see below)

### Tertiary Fix — Delete `giveTurn` entirely

`giveTurn` is marked as a "LEGACY: turn relay" but terrain is now server-generated via `requestTerrain`. The `recieveTurn` event (note typo) is not necessary if the server is authoritative on terrain. Deleting both `giveTurn` and `recieveTurn` eliminates the unbounded-payload relay vector entirely and removes dead legacy infrastructure.

If backward compatibility with legacy clients is required, strip `terrainData` from the relay entirely and only forward numeric fields (`pos1`, `pos2`, `rotation1`, `rotation2`) with explicit `Number.isFinite` guards.

### Quaternary Fix — Require auth for free room entry

Remove the conditional `wagerAmount > 0` auth check from `createRoom`, `joinRoom`, and `joinQueue`. All room participation should require authentication. The wagered/free distinction should only affect escrow logic, not authentication. This removes the unauthenticated-socket-gets-roomId prerequisite for relay event exploitation:

```js
// createRoom — main.js:1121 — CHANGE:
if (wagerAmount > 0 && !requireAuth(client, 'createRoom')) return
// TO:
if (!requireAuth(client, 'createRoom')) return
```

Apply equivalently to `joinRoom` (line 972) and `joinQueue` (line 1231).

### Combined Fix Priority

1. **P1 — giveTurn deletion or stripping** (eliminates DoS vector immediately)
2. **P2 — `requireAuth` on all 6 relay events** (closes the core auth gap)
3. **P3 — State guards on relay events** (defense-in-depth against authenticated-but-wrong-state abuse)
4. **P4 — Unconditional auth on room entry** (removes unauthenticated-socket prerequisite)
5. **P5 — `maxHttpBufferSize: 64 * 1024`** (caps payload size regardless of auth — see H028)
