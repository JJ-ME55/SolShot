# H018 — createWeaponArray Non-Host Manipulation

**Strategy ID:** H018
**Categories:** AUTH-03 (Authorization), LOGIC-01 (Business Logic)
**Verdict:** CONFIRMED
**Severity:** HIGH
**Status:** Open

---

## Summary

The `createWeaponArray` socket event handler on the server is callable by any authenticated player in a room — including the non-host (player 2). There is no host-only guard. Any authenticated socket in the room can overwrite `room.randomArray` at any time, causing the server to broadcast a new weapon randomization array to both players via `setWeaponArray`.

The handler also performs zero match-state validation: it can be called during any match phase (LOBBY, WEAPON_SHOP, BATTLE, ROUND_END). A non-host player can call it repeatedly, including mid-match, to continually reset the shared weapon array.

---

## Evidence

### Handler Code

**File:** `server/socket-io/main.js`, lines 1666–1691

```javascript
client.on('createWeaponArray', (data) => {
    if (!requireAuth(client, 'createWeaponArray')) return
    // H015: Null payload guard
    if (!data || typeof data !== 'object') return
    const { count, max } = data

    var room = findRoom(client.roomId)
    if (!room) return

    // H013: Validate and cap count to prevent memory exhaustion
    if (typeof count !== 'number' || typeof max !== 'number') return
    const safeCount = Math.min(Math.max(0, Math.floor(count)), 100)
    const safeMax = Math.max(1, Math.floor(max))

    // O9: Use crypto.randomBytes for better entropy (wagered game integrity)
    const randomBytes = crypto.randomBytes(safeCount * 4)
    var randomArray = []
    for (let index = 0; index < safeCount; index++) {
        const val = randomBytes.readUInt32LE(index * 4)
        randomArray.push(val % safeMax)
    }

    room.randomArray = randomArray          // <-- unconditional overwrite
    persistRoom(room);
    io.sockets.in(client.roomId).emit('setWeaponArray', {randomArray: room.randomArray})
})
```

**Missing check (compare to `deleteRoom` at lines 927–934):**

```javascript
client.on('deleteRoom', async () => {
    if (!requireAuth(client, 'deleteRoom')) return
    if (client.roomId !== null) {
        // H003: Only host can delete the room
        if (!client.isHost) {                          // <-- HOST CHECK PRESENT HERE
            client.emit('deleteRoomError', { reason: 'Only host can delete room' })
            return
        }
        ...
    }
})
```

`deleteRoom` has an explicit `if (!client.isHost)` guard. `createWeaponArray` has no equivalent.

### `client.isHost` Is Reliably Set

`client.isHost` is set server-side at room creation and join time and cannot be spoofed by the client:

- `main.js:1166`: `client.isHost = true` (for the creating player in `createRoom`)
- `main.js:1002`: `client.isHost = false` (for the joining player in `joinRoom`)
- `main.js:1293`: `client.isHost = false` (for queue-matched non-host player in `joinQueue`)

The value is available and correct. It is simply not consulted in the `createWeaponArray` handler.

### No State-Machine Guard

The `validateAction` table in `server/services/match.js` (lines 63–71) does not include `createWeaponArray` in any allowed-action set:

```javascript
export function validateAction(currentState, action) {
    const allowedActions = {
        [MATCH_STATES.LOBBY]:       ['join', 'leave', 'ready'],
        [MATCH_STATES.WEAPON_SHOP]: ['buyWeapon', 'shopDone'],
        [MATCH_STATES.BATTLE]:      ['fire', 'move', 'angleChange', 'powerChange', 'weaponChange',
                                     'stepLeft', 'stepRight', 'giveTurn', 'requestTurn', 'shoot'],
        [MATCH_STATES.ROUND_END]:   ['ready', 'playAgainRequest'],
        [MATCH_STATES.SETTLING]:    [],
        [MATCH_STATES.COMPLETE]:    ['playAgainRequest'],
        [MATCH_STATES.CANCELLED]:   []
    };
    ...
}
```

The handler itself does not call `validateAction` at all. `room.randomArray` can be overwritten during any state including BATTLE.

### room.randomArray Scope of Use

`room.randomArray` is:
- Generated by `createWeaponArray` (lines 1681–1686)
- Stored on the room object and persisted to MongoDB via `persistRoom` (line 1689)
- Broadcast to both players via `setWeaponArray` (line 1690)
- Re-fetched on demand via `getWeaponArray` (lines 1658–1662)
- Included in the `persistRoom` update payload (line 186)
- Deleted on rematch reset (lines 2517, 2541)

The client-side code in `client/src/` contains no references to `createWeaponArray`, `getWeaponArray`, `setWeaponArray`, or `randomArray`. These are legacy server-side handlers. The current client-side weapon selection logic (the shop with `buyWeapon`) does not depend on `room.randomArray` for server-authoritative enforcement — weapons purchased via `buyWeapon` are validated against the weapon catalog and the player's gold balance, not against the `randomArray`.

However, the server broadcasts the `setWeaponArray` event to all room members each time `createWeaponArray` is called. Any connected legacy client that listens to `setWeaponArray` would update its weapon display. In a match with a legacy-connected client (e.g., old browser tab, Phaser-side legacy code in scenes), this directly manipulates the weapon selection interface presented to both players.

## Exploit Scenario

### Scenario A: Legacy Client — Direct Weapon Pool Influence

**Prerequisites:** Either player's client still uses `setWeaponArray` to populate the weapon selection UI (legacy Phaser flow).

1. Non-host player (player 2) authenticates normally and joins a wagered match.
2. When the weapon pick phase begins, instead of waiting for the host to send `createWeaponArray`, player 2 immediately emits:
   ```javascript
   socket.emit('createWeaponArray', { count: 15, max: 15 })
   ```
3. The server generates a new `randomArray` from `crypto.randomBytes` (uncontrolled) and broadcasts it to both players.
4. Player 2 can repeat this call in rapid succession (no rate limit, no state guard), replacing the array repeatedly until the resulting weapon pool contains favorable weapons. Since `count` and `max` control the array length and index range, a patient adversary can statistically bias the draw by repeatedly resetting it.
5. Player 2 observes which `setWeaponArray` result arrives (their own call returns it immediately to both) and stops when favorable weapons are at the front of the array.

**Impact:** Player 2 controls the weapon randomization in a wagered match. Financial advantage in matches where weapon selection is meaningful.

### Scenario B: Overwrite During Active Battle (Any Client)

**Prerequisites:** None beyond authentication and room membership.

1. During the BATTLE phase of a multi-round match, the non-host player emits `createWeaponArray`.
2. The server overwrites `room.randomArray` on a live match and broadcasts `setWeaponArray`.
3. Any legacy client logic that re-reads weapon array data mid-battle receives a new array, potentially desynchronizing weapon display state.
4. More concretely: if `requestTerrain` is called in round 2 (see finding BL-H01 / H019) and the terrain reset also re-reads `room.randomArray`, the new array takes effect for the fresh round.

### Scenario C: Repeated Calls — Informational Advantage via Timing

Even if the client ignores `setWeaponArray` updates in modern code, the non-host player can call `createWeaponArray` N times rapidly:

```javascript
for (let i = 0; i < 50; i++) {
    socket.emit('createWeaponArray', { count: 20, max: 20 })
}
```

Each call overwrites `room.randomArray` server-side and calls `persistRoom` — triggering 50 synchronous MongoDB writes from a single socket event burst. There is no per-event rate limiting on this handler. This is a low-cost DoS on the persistence layer.

## Limitations and Downgrade Notes

The current React client (`client/src/`) has no references to `createWeaponArray`, `getWeaponArray`, `setWeaponArray`, or `randomArray`. This indicates the weapon selection mechanism in the active client does not rely on `room.randomArray` for the weapon shop. The `buyWeapon` handler independently validates weapon IDs against the catalog.

This reduces the direct competitive impact from CRITICAL to HIGH in the current deployment: the weapon shop presented to players is not determined by `room.randomArray` in the active client. However:

1. The server-side `setWeaponArray` broadcast still occurs and will affect any legacy or alternative client connected to the room.
2. The `persistRoom` write amplification DoS is active regardless of client behavior.
3. The missing host check is a structural authorization defect that is one client-side usage away from being fully weaponized.
4. The LOGIC-01 auditor noted `room.randomArray` as a "legacy field" where "server-authoritative terrain takes precedence" — but this assessment applies to terrain, not to weapon selection specifically.

The AUTH-03 auditor rated this CRITICAL. Given that the active client does not consume `setWeaponArray`, this investigation rates it HIGH with the caveat that any client-side update restoring `setWeaponArray` consumption would immediately elevate impact to CRITICAL.

## Root Cause

The `createWeaponArray` handler was written with only an authentication guard (`requireAuth`) and input-size caps, but no host-only role check and no state-machine validation. The pattern for host-only operations exists in the codebase (`deleteRoom`) but was not applied here.

---

## Recommendations

### Fix 1: Add Host-Only Guard (Primary Fix)

Add the following check immediately after `requireAuth`, mirroring the `deleteRoom` pattern:

```javascript
client.on('createWeaponArray', (data) => {
    if (!requireAuth(client, 'createWeaponArray')) return
    // Only the host should generate the shared weapon randomization array
    if (!client.isHost) {
        client.emit('createWeaponArrayError', { reason: 'Only host can create weapon array' })
        return
    }
    if (!data || typeof data !== 'object') return
    ...
})
```

### Fix 2: Add State-Machine Guard

Prevent calls outside of the legitimate pre-game phases:

```javascript
const ms = matchStates[client.roomId]
if (!ms || !['lobby', 'weapon_shop'].includes(ms.status)) return
```

This ensures the array cannot be overwritten during an active battle round.

### Fix 3: Add Once-Per-Match Guard (Defense in Depth)

If the weapon array is intended to be set once per match, add a guard that rejects overwrites once `room.randomArray` is already set:

```javascript
if (room.randomArray && room.randomArray.length > 0) {
    client.emit('createWeaponArrayError', { reason: 'Weapon array already set for this match' })
    return
}
```

### Fix 4: Consider Server-Initiated Generation

For wagered matches, remove the client-triggered flow entirely. Generate `room.randomArray` server-side at match creation time (in `createRoom`/`joinRoom`/`joinQueue`), removing the client attack surface completely. Broadcast via `setWeaponArray` at the start of the weapon pick phase.
