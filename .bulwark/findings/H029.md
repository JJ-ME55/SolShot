# H029 — JWT Dead Code Creates Future Auth Bypass Surface

**Verdict:** CONFIRMED
**Severity:** HIGH
**Category:** Authentication / Dead Code
**Auditor Convergence:** 3 independent auditors (AUTH-01, SEC-01, DATA-05) — cross-domain agreement that auth is decorative
**Hypothesis Accuracy:** FULLY CONFIRMED. Both sub-claims are true: `verifyToken()` has zero call sites, and `generateToken()` IS called — tokens are actively issued but never consumed.

---

## Summary

`server/middleware/auth.js` defines two JWT functions: `generateToken()` (line 96) and `verifyToken()` (line 110). `generateToken()` is called on every successful authentication and its output is transmitted to the client. `verifyToken()` is defined but has **zero call sites anywhere in the application**. The issued JWT is received by the client and immediately discarded — never stored, never re-sent. The `jsonwebtoken` library occupies the dependency tree for zero security benefit. Session identity rests entirely on the in-memory `client.isAuthenticated` boolean flag, which lives only for the duration of a single socket connection. The primary risk is developer confusion and future misuse: any developer who adds an HTTP endpoint and reaches for `verifyToken()` will consume a function that has never been exercised in integration and may have subtle misuse bugs.

## Evidence

### 1. `generateToken()` is called on every successful auth

**File:** `server/middleware/auth.js`, lines 96–102, 140–147

```js
// Line 96-102
export function generateToken(walletAddress) {
    return jwt.sign(
        { wallet: walletAddress },
        JWT_SECRET,
        { expiresIn: '24h' }
    );
}

// Line 140-147 — called inside handleAuthenticate()
    // Generate JWT
    const token = generateToken(walletAddress);

    // Mark socket as authenticated
    client.walletAddress = walletAddress;
    client.isAuthenticated = true;

    return { success: true, token, walletAddress };
```

The token is included in the `authResult` payload returned to the socket caller.

### 2. Server emits the token to the client

**File:** `server/socket-io/main.js`, lines 539–552

```js
const result = handleAuthenticate(client, data)
if (result.success) {
    authenticatedWallets[client.id] = result.walletAddress
    // ...
}
client.emit('authResult', result)   // result contains { success, token, walletAddress }
```

The `token` field is present in every `authResult` emission on successful authentication.

### 3. Client receives the token and discards it

**File:** `client/src/wallet/WalletContext.js`, lines 303–313

```js
const handler = (result) => {
    if (result.success) {
        console.log('[SolShot] Auth confirmed by server');
        setIsAuthenticated(true);    // <-- only this is acted upon
    } else {
        console.warn('[SolShot] Auth rejected:', result.reason);
        setIsAuthenticated(false);
    }
};
socket.on('authResult', handler);
```

`result.token` is never read, stored in `localStorage`/`sessionStorage`, or re-sent on any subsequent request. The token is transmitted over the wire to the client and immediately falls out of scope.

### 4. `verifyToken()` has ZERO call sites — confirmed by exhaustive grep

**File:** `server/middleware/auth.js`, lines 110–117 (definition only)

```js
export function verifyToken(token) {
    try {
        const decoded = jwt.verify(token, JWT_SECRET);
        return { valid: true, wallet: decoded.wallet };
    } catch (err) {
        return { valid: false, reason: err.message };
    }
}
```

Grep result for `verifyToken` across all `.js` files in the project (excluding node_modules):

```

server/middleware/auth.js:112:        const decoded = jwt.verify(token, JWT_SECRET);
```

**Zero callers.** The function is defined and exported but never imported or invoked by any socket handler, HTTP middleware, or route.

### 5. The import in main.js confirms `verifyToken` is NOT imported

**File:** `server/socket-io/main.js`, line 10

```js
import { handleAuthenticate, verifyAuthMessage, verifyWalletSignature } from '../middleware/auth.js';
```

`verifyToken` and `generateToken` are not included in the named import. Only the signature-verification functions are consumed.

### 6. No HTTP route exists that could use JWT

**File:** `server/index.js` — complete HTTP route inventory:

```js

app.get('/health',    healthCheck)                     // monitoring
app.get('/stats',     requireAdminKey, getStats)       // admin key, NOT JWT
```

The ARCHITECTURE.md reference to a `/api/auth/verify` HTTP endpoint does not exist in code. No `express.Router`, no `/api/auth` route handler, no JWT `Authorization: Bearer` header check anywhere in the application.

### 7. `requireAdminKey` (the only HTTP auth guard) does not use JWT

## Root Cause Analysis

The JWT infrastructure was added during a security hardening pass, anticipating future REST endpoints that would use stateless token-based auth (e.g., `/stats`, `/armory`, `/leaderboard`). The pattern was partially implemented: token generation and issuance work correctly, but the consumption side — `verifyToken()` being called on HTTP request middleware — was never built. The existing HTTP endpoints that were added later used a simpler `requireAdminKey` pattern instead. No developer ever wired `verifyToken()` into a route. The code comment in `auth.js` (line 10) explicitly says "Server issues JWT **or** marks socket as authenticated", indicating the implementer knew the JWT path was aspirational.

## Security Impact Assessment

### Direct impact (current state): LOW-MEDIUM
- The JWT infrastructure does not create an active vulnerability in isolation.
- Session security is maintained by `client.isAuthenticated` on the socket object — this is appropriate for a WebSocket-only architecture where sessions are socket-lifetime.
- No active bypass is possible solely because of the dead JWT code.

### Future-risk impact: HIGH
The dead code creates three forward-looking risks:

**Risk 1 — Misuse of `verifyToken()` in a future HTTP endpoint**
If a developer adds a REST endpoint and calls `verifyToken()` to protect it, they will be calling a function that has never been exercised in integration with the rest of the auth stack. The 24h `expiresIn` setting is never tested against actual server behavior. The `JWT_SECRET` rotation pattern (random bytes in dev, env var in prod) has never been exercised in a verify path. Subtle misuse is likely.

**Risk 2 — JWT_SECRET in client/.env (separate confirmed finding H010)**
`JWT_SECRET` is currently committed to `client/.env`. Since `verifyToken()` is never called, this has no immediate impact. If `verifyToken()` is ever wired up, a client-side secret exposure becomes a direct authentication bypass: an attacker who knows `JWT_SECRET` can forge valid JWTs for any wallet address.

**Risk 3 — Developer confusion about the trust model**
`auth.js` has a comment stating "Server issues JWT or marks socket as authenticated." A developer reading this may believe session security relies partly on JWT validation when in fact it relies entirely on the in-memory socket flag. This misunderstanding could lead to incorrect assumptions about session persistence across reconnects (JWT would survive reconnect; socket flag does not — but `rejoinRoom` handles this correctly with a fresh Ed25519 signature).

**Risk 4 — Unnecessary attack surface from `jsonwebtoken` dependency**
`jsonwebtoken@9.0.2` is in production dependencies. JWT libraries have historically been targets for algorithm confusion attacks (`alg: "none"`, RS256/HS256 confusion). Since `verifyToken()` is never called, these vulnerabilities are currently unexploitable, but the dependency remains in the attack surface for supply chain compromise.

## Recommendations

### Option A — Remove JWT entirely (RECOMMENDED)
Remove `generateToken()`, `verifyToken()`, and the `jsonwebtoken` import from `auth.js`. Remove `JWT_SECRET` from all `.env` files. Remove `jsonwebtoken` from `server/package.json`. Document explicitly in `auth.js` that authentication is socket-lifetime only, enforced by `client.isAuthenticated`.

```js
// auth.js — REMOVE these sections entirely:
import jwt from 'jsonwebtoken';                    // line 15
const JWT_SECRET = process.env.JWT_SECRET || ...; // lines 19-27
export function generateToken(walletAddress) {...} // lines 96-102
export function verifyToken(token) {...}           // lines 110-117
// In handleAuthenticate, remove:
const token = generateToken(walletAddress);        // line 141
// Change return to:
return { success: true, walletAddress };           // line 147
```

**Benefit:** Eliminates the `jsonwebtoken` attack surface, removes `JWT_SECRET` confusion, eliminates the H008/H010 risk surface, and makes the actual trust model explicit.

### Option B — Activate JWT for future HTTP endpoints (if REST API is planned)
If REST endpoints for player stats, leaderboard, or armory are planned, wire `verifyToken()` into Express middleware:

```js
// server/middleware/guards.js
export function requireJwt(req, res, next) {
    const auth = req.headers['authorization'];
    if (!auth || !auth.startsWith('Bearer ')) {
        return res.status(401).json({ error: 'Missing token' });
    }
    const result = verifyToken(auth.slice(7));
    if (!result.valid) {
        return res.status(401).json({ error: result.reason });
    }
    req.wallet = result.wallet;
    next();
}
```

Store the token client-side in `sessionStorage` (not `localStorage`) after `authResult`. Re-send as `Authorization: Bearer <token>` on every HTTP call. Remove `JWT_SECRET` from `client/.env` immediately — the secret must remain server-side only.

### Immediate action regardless of option chosen:
Remove `JWT_SECRET` from `client/.env` (finding H010). The secret being on the client is dangerous whether or not JWT is ever used. This must be done before production launch.
