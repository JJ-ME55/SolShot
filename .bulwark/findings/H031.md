# H031 — No Account-Change Handler Enables Wallet Switch Attack

**Hypothesis:** Client doesn't listen for wallet account changes. Wallet switch during match creates identity mismatch between socket auth and wallet signer.
**Severity:** HIGH
**Status:** CONFIRMED
**Category:** Wallet Integration / Identity
**Auditor:** CHAIN-03
**Files:**
- `client/src/wallet/WalletContext.js`
- `client/src/App.js`
- `server/socket-io/main.js`
- `server/services/shot-token.js`

---

## Verdict

CONFIRMED — HIGH severity. The client has no mechanism to detect or respond to a wallet account switch. When a user switches accounts inside Phantom (or Solflare) without disconnecting, `isAuthenticated` remains `true` for the old wallet's session. The auto-authenticate effect's early-return guard on `isAuthenticated === true` prevents re-authentication for the new public key. The server's `authenticatedWallets[socket.id]` entry continues to hold the old wallet address for the lifetime of the socket connection.

The identity mismatch this creates diverges across three independent attack surfaces, each with different exploitation characteristics. The most severe path is prestige burn fraud, where the mismatch between the server's stale auth record and the wallet that actually signed the burn transaction allows a low-SHOT wallet to credit burns to a high-tier wallet's account.

---

## Evidence

### 1. The Account-Switch Gap in WalletContext.js

The effect responsible for clearing `isAuthenticated` on wallet disconnect is at lines 136–143:

```js
// WalletContext.js lines 136–143
useEffect(() => {
    if (connected && publicKey) {
        refreshBalance();
    } else {
        setBalance(0);
        setIsAuthenticated(false);
    }
}, [connected, publicKey, refreshBalance]);
```

When a user switches accounts inside Phantom's UI (using the account switcher, not the disconnect button), the wallet adapter updates `publicKey` to the new account's `PublicKey` object but `connected` remains `true`. The `if (connected && publicKey)` branch fires — it calls `refreshBalance()` for the new key, but it does **not** call `setIsAuthenticated(false)`. The `else` branch, which contains the authentication reset, is never reached.

There is no `useRef` tracking the previous `publicKey` value. There is no `wallet.on('accountChanged')` listener. There is no `onAccountChange` subscription to the wallet adapter. A comprehensive search of `client/src/` finds zero occurrences of `onAccountChange`, `accountChanged`, `accountChange`, or `prevPublicKey`.

### 2. Auto-Authenticate Effect Guards Prevent Re-Auth on Switch

The auto-authenticate effect runs after every render where its dependencies change:

```js
// WalletContext.js lines 326–342
useEffect(() => {
    if (!connected || !publicKey || isAuthenticated) return;
    // ...
    authenticate();
    // ...
}, [connected, publicKey, isAuthenticated, authenticate]);
```

When `publicKey` changes to the new account, this effect fires because `publicKey` is in its dependency array. However, the guard `if (!connected || !publicKey || isAuthenticated) return` exits immediately because `isAuthenticated` is still `true` from the old wallet. `authenticate()` is never called. The server is never notified of the account switch.

### 3. Server's authenticatedWallets Holds the Stale Address

After a switch, the server's in-memory map retains the old binding:

```js
// server/socket-io/main.js line 45
var authenticatedWallets = {}
// ...
// Set at auth time (line 541):
authenticatedWallets[client.id] = result.walletAddress  // OLD wallet address
```

This binding is only updated on:
- A new `authenticate` event (which is never sent after a switch — see above)
- A `rejoinRoom` event (only on reconnect after disconnect)
- Socket disconnect (cleans it up entirely)

For the duration of the session after a switch, `authenticatedWallets[client.id]` maps to the old wallet address.

### 4. divergence of Socket Auth State vs. Actual Signer

After the switch, the server's `authenticatedWallets[client.id]` holds Wallet A's address. The wallet adapter's `publicKey` is now Wallet B. Every subsequent signing operation — `signMessage`, `signAndSendEscrowDeposit`, `signAndBurnShot` — will use Wallet B as the signer.

The CHAIN-03 context report (section 4) documented this exactly:

> "Subsequent socket events (`createRoom`, `joinRoom`, `prestigeBurn`) will carry the new wallet address in their payloads, which the server uses as the authoritative address. The escrow deposit confirmation (`escrowDepositConfirm`) will be attributed to the new wallet. The prestige burn verification (`verifyBurnTransaction`) will verify against a transaction signed by the new wallet while the server's auth record references the old wallet."

## Attack Scenarios

### Scenario A — Prestige Burn Cross-Account Fraud (Most Severe)

**Precondition:** Attacker controls two wallets: Wallet A (high SHOT balance, high prestige tier already), Wallet B (low SHOT balance).

**Execution:**
1. Connect Wallet B to SolShot. Authenticate — server sets `authenticatedWallets[socket.id] = WalletB`.
2. Switch to Wallet A inside Phantom's account switcher (no disconnect/reconnect). `publicKey` is now Wallet A. `isAuthenticated` remains `true`. Server still holds `WalletB`.
3. Navigate to PrestigeScreen. The `signAndBurnShot` callback uses `publicKey` (Wallet A) and calls `sendTransaction`, which prompts Wallet A to sign. The burn transaction is submitted on-chain by Wallet A.
4. The server's `prestigeBurn` handler at line 1612 reads `const wallet = authenticatedWallets[client.id] || null` — this returns `WalletB`.
5. `verifyBurnTransaction(txSignature, WalletB, burnAmount)` is called. The on-chain transaction has `info.authority === WalletA`. Line 504 checks `if (ixAuthority !== walletAddress)` — `WalletA !== WalletB` — and returns `{ valid: false, reason: 'Burn was not signed by your wallet' }`.

**Result (benign side):** The prestige burn is correctly rejected. Wallet B does not gain tier. The burn cost from Wallet A is permanently lost — the tokens are gone but no tier was granted. **This is a financial loss for the attacker.**

**Result (adversarial variant):** Switch wallets in the opposite direction.
1. Connect Wallet A (high SHOT balance). Authenticate. Server holds `WalletA`.
2. Switch to Wallet B. `isAuthenticated` still `true`. Server still holds `WalletA`.
3. PrestigeScreen now shows Wallet B's balance (which is low) but the tier advancement logic `getPrestigeInfo(WalletA)` runs on the server. If Wallet A had sufficient SHOT balance accumulated, `prestigeBurn(WalletA)` succeeds and deducts from Wallet A's in-memory state — but the actual on-chain burn transaction was signed and executed by Wallet B.
4. **The result is Wallet A's prestige tier advancing without Wallet A's tokens being burned, because Wallet B's tokens (or any tokens belonging to Wallet B) were burned instead.**

The degree of exploitation depends on which direction the switch occurs and what balances each wallet holds.

### Scenario B — Match Escrow Identity Mismatch (Financial Path)

**Setup:** A wagered match is in progress. Player switches wallet mid-match.

1. Player authenticated as Wallet A. Server: `authenticatedWallets[socket.id] = WalletA`. `wagerStates[roomId].wallets[socket.id] = WalletA`.
2. Player switches to Wallet B. Client still holds the active match session. `isAuthenticated` remains `true`.
3. When the match ends and `settleMatch` is called (line 341), it uses `authenticatedWallets[winnerId]` to identify the winner's destination wallet — still `WalletA`.
4. Settlement proceeds: SOL is sent to Wallet A, not Wallet B.
5. If the player intended to receive winnings into Wallet B (e.g., they switched to a fresh wallet for financial isolation), settlement sends funds to the wrong address. The player may not immediately notice if both wallets are theirs.

**Financial damage:** Winnings go to the wrong wallet. In a High Roller match, this could be a material amount.

### Scenario C — Escrow Deposit Signer Mismatch (Transaction Failure Path)

**Setup:** Player is in lobby phase, switches wallet after the server sends `escrowDeposit` but before signing.

1. Server sends `escrowDeposit` with a pre-built transaction targeting `wagerStates[roomId].wallets[socket.id]` — Wallet A.
2. Player switches to Wallet B. The `signAndSendEscrowDeposit` callback executes with `publicKey = WalletB`.
3. Wallet B signs and submits the deposit transaction. The on-chain escrow PDA was created with Wallet A as `player_one` or `player_two`. The deposit from Wallet B will fail the Anchor program's signer/owner checks — the PDA expects a deposit from Wallet A's ATA.
4. Transaction fails on-chain. Client's `connection.confirmTransaction()` throws. The `catch` at line 247 returns `null`. `escrowDepositConfirm` is never emitted.
5. Server never receives deposit confirmation for this player. After the deposit timeout, the server cancels the escrow and refunds both players. The opponent (who deposited correctly) is refunded minus the gas they paid.

**Impact:** Denial of match start. Opponent wastes gas. Attacker can trigger this deliberately by switching wallets at the precise moment after the escrow deposit event arrives.

## Root Cause

The React effect dependency array on the balance/auth-reset effect (`[connected, publicKey, refreshBalance]`) reacts to `publicKey` changes but only clears `isAuthenticated` in the `else` branch, which only fires when `connected` becomes `false`. The effect branch taken on a `publicKey` change where `connected` remains `true` only refreshes the balance — it does not invalidate authentication.

The auto-authenticate effect correctly includes `publicKey` as a dependency and would re-trigger authentication on a switch — but the `isAuthenticated` guard at line 327 short-circuits it before `authenticate()` is reached.

The two effects together form a logical contradiction:
- Effect 1 (lines 136–143): "If connected and publicKey exist, refresh balance. Only clear auth on disconnect."
- Effect 2 (lines 326–342): "Only auto-authenticate if not already authenticated."

When `publicKey` changes without `connected` going `false`, Effect 1 refreshes balance and leaves `isAuthenticated = true`, and Effect 2 sees `isAuthenticated = true` and returns early. The new public key is never authenticated.

## Absence of Any Mitigation

Searched `client/src/` exhaustively:
- **Zero occurrences** of `onAccountChange`
- **Zero occurrences** of `accountChanged`
- **Zero occurrences** of `prevPublicKey` or any `useRef` for tracking public key changes
- **No wallet event listeners** (`wallet.on(...)`) registered anywhere outside the standard adapter-react hooks
- **No server-side detection** of wallet change — the server only sees socket events; it has no way to know the wallet changed unless the client emits a new `authenticate` event

---

## Severity Rationale

**HIGH** (not CRITICAL) because exploitation requires:
1. The attacker to have control of two wallets (not just one), OR
2. The user to accidentally switch wallets in a specific window during a match

The most damaging variant (cross-account prestige burn) requires precise control of both wallets and sufficient SHOT balance in one of them. For random users accidentally switching wallets, the most likely outcome is a broken match flow rather than financial theft. The financial theft path (Scenario A adversarial variant) is specific enough to require intentional setup.

Elevated from MEDIUM because:
- The prestige burn cross-account path has a direct financial impact (tokens burned from wrong wallet)
- The escrow settlement sends funds to the stale wallet address (wrong recipient)
- There is a plausible accidental user harm scenario (wallet switch during deposit, causes match cancellation and opponent gas loss)
- No mitigation of any kind exists — not even a comment acknowledging the gap

## Recommendations

### Fix 1 — Detect Account Switch with publicKey Comparison (Minimal Fix)

Add a `useRef` to track the previous `publicKey` and force re-authentication when it changes while `connected` remains `true`:

```js
// WalletContext.js — add after line 114 (existing state declarations)
const prevPublicKeyRef = useRef(null);

// Detect account switch (publicKey changed while still connected)
useEffect(() => {
    if (!publicKey) {
        prevPublicKeyRef.current = null;
        return;
    }
    if (prevPublicKeyRef.current && !publicKey.equals(prevPublicKeyRef.current)) {
        // Account switched — invalidate authentication so auto-auth fires for new key
        setIsAuthenticated(false);
    }
    prevPublicKeyRef.current = publicKey;
}, [publicKey]);
```

This causes `isAuthenticated` to become `false` when `publicKey` changes, which unblocks the auto-authenticate effect at line 327, triggering a fresh `authenticate()` call for the new public key. The server will update `authenticatedWallets[socket.id]` to the new wallet.

### Fix 2 — Force Disconnect on Account Switch (Stronger)

More defensive: treat an account switch identically to a disconnect. Force the socket to disconnect and reconnect, wiping all match-in-progress state client-side and triggering the server's reconnect window:

```js
useEffect(() => {
    if (!publicKey) {
        prevPublicKeyRef.current = null;
        return;
    }
    if (prevPublicKeyRef.current && !publicKey.equals(prevPublicKeyRef.current)) {
        // Account switched — treat as a full disconnect to prevent identity mismatch
        setIsAuthenticated(false);
        if (window.socket && window.socket.connected) {
            window.socket.disconnect();
            // Socket will reconnect automatically; App.js attemptRejoin will fire
        }
    }
    prevPublicKeyRef.current = publicKey;
}, [publicKey]);
```

This is stronger because it fully invalidates the server session, but it also means any in-progress match is disrupted. This is the correct behavior — a wallet switch mid-match should not be silently tolerated.

### Fix 3 — Lock Wallet During Active Match (UX Constraint)

Display a blocking overlay in BattleScreen if `walletAddress` changes from the value present at match start:

```js
// BattleScreen.js — store match-start wallet address
const [matchWalletAddress] = useState(() => walletAddress);

useEffect(() => {
    if (walletAddress && matchWalletAddress && walletAddress !== matchWalletAddress) {
        // Wallet switched during match — show warning and prevent actions
        setWalletMismatch(true);
    }
}, [walletAddress, matchWalletAddress]);
```

This does not fix the server-side identity mismatch but prevents the user from accidentally taking actions (firing, depositing, burning) with the wrong wallet.

### Fix 4 — Server-Side: Validate Wallet in prestigeBurn Against TX Signer Only

As a defense-in-depth measure independent of the client fix, the `prestigeBurn` handler should not use `authenticatedWallets[client.id]` as the wallet parameter for `verifyBurnTransaction`. Instead, the client should include the wallet address that signed the burn in the payload, and the server should verify that address is the signer:

This would not fix the core identity mismatch but would prevent the adversarial Scenario A variant: if the payload wallet and the TX signer always agree (both come from the current `publicKey`), the cross-account burn becomes harder to construct without explicit intent.
