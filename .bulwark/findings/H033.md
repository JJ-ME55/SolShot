# H033 — autoConnect Without Auth Gate Enables Pre-Auth Actions

**Hypothesis ID:** H033
**Investigator:** Dinh's Bulwark Pipeline — Phase 3 Hypothesis Investigation
**Date:** 2026-02-23
**Category:** AUTH-01 (Authentication), CHAIN-03 (Wallet Adapter Integration)
**Origin:** CHAIN-03-F07 (autoConnect race condition), AUTH-01 (unauthenticated event surface)

---

## Verdict: CONFIRMED — PARTIALLY OVERSTATED

**Severity: MEDIUM**

The hypothesis is confirmed in its core structural claim: `autoConnect` on the wallet adapter and unconditional socket establishment at module load do create a window where the socket is connected and the wallet is known before the server has authenticated the session. However, the practical impact is lower than the hypothesis implies, because the pre-auth window is a **latency race, not a persistent bypass path**. The real risk is not that an attacker exploits the race deliberately — it is that the design has no client-side auth gate on lobby actions, which combines with the already-confirmed H016 unauthenticated server events to produce a compounding exposure. The finding is a real gap at MEDIUM severity on its own, but it amplifies CRITICAL finding H016 and HIGH finding CHAIN-03-F03.

## Component Sequencing: What Happens on Page Load

### Execution Order (cold start, autoConnect enabled)

The following sequence is determined by the module evaluation order and React render lifecycle:

```
1. App.js module evaluated
   -> socket/index.js imported: io(serverUrl, { auth: ... }) executes immediately
   -> WebSocket TCP connection initiated to server
   -> window.socket = socket (line 20 of App.js)

2. React renders App -> SolShotWalletProvider -> SolShotWalletInner
   -> WalletProvider with autoConnect={true} mounts
   -> Wallet adapter reads localStorage for last-used wallet (e.g. Phantom)
   -> Adapter requests connection to Phantom extension silently
   -> publicKey and connected become available (NO user action required)

3. WalletContext auto-auth useEffect fires (WalletContext.js lines 326–342):
   -> Conditions checked: connected=true, publicKey set, isAuthenticated=false
   -> polls window.socket.connected every 1000ms
   -> When socket connects: calls authenticate()
   -> authenticate() calls signMessage() -> wallet extension signs
   -> socket.emit('authenticate', { walletAddress, message, signature, timestamp })

4. Server processes authenticate event
   -> handleAuthenticate() verifies Ed25519 signature
   -> client.isAuthenticated = true
   -> socket.emit('authResult', { success: true, ... })

5. WalletContext receives 'authResult'
   -> setIsAuthenticated(true)
```

### The Pre-Auth Window

Between step 2 (wallet connected) and step 5 (server confirmation received), the following conditions hold simultaneously:

- `window.socket.connected === true`
- `connected === true`, `publicKey` is set, `walletAddress` is derivable
- `isAuthenticated === false` (WalletContext state)
- `client.isAuthenticated === false` on the server

This window typically lasts **300ms to 2000ms** depending on socket latency, `signMessage` response time, and the 1-second polling interval in the auto-auth effect. On mobile browsers where wallet popups may require explicit user interaction, this window can extend indefinitely if the user dismisses the popup.

### Socket Established Before Any Auth Gate

The socket is created unconditionally in `client/src/socket/index.js`:

```js
// client/src/socket/index.js
export const socket = io(serverUrl, {
  auth: tgInitData ? { telegramInitData: tgInitData } : {},
})
```

This module is imported at the top of `App.js`. There is no lazy initialization, no wallet-connected guard, and no authentication check before the WebSocket connection is established. The socket connects to the server the moment the JavaScript bundle executes, before any wallet state is known.

**File:** `client/src/socket/index.js` lines 1–10
**File:** `client/src/App.js` line 20

## Can Pre-Auth Actions Be Sent?

### Client-Side: No Guard on Lobby Actions

`LobbyScreen.js` provides `createRoom`, `joinRoom`, and `joinQueue` as callbacks. None of these check `isAuthenticated` before emitting:

```js
// client/src/screens/LobbyScreen.js lines 416–435
const createRoom = useCallback(() => {
    if (!window.socket) return;  // only guard: socket existence
    // NO isAuthenticated check
    window.socket.emit('createRoom', {
        player: {
            walletAddress: walletAddress || null,
            wager: wagerToSend,
            ...
        },
    });
}, [..., walletAddress]);
```

```js
// client/src/screens/LobbyScreen.js lines 462–475
const joinQueue = useCallback(() => {
    if (!window.socket) return;  // only guard: socket existence
    // NO isAuthenticated check
    window.socket.emit('joinQueue', { matchMode, matchLength, wager: wagerToSend, ... });
}, [...]);
```

A user with autoConnect enabled who navigates quickly from LoadingScreen to LobbyScreen during the pre-auth window — or on a return visit where LoadingScreen completes before `signMessage` is resolved — can click "Create Room" or "Join Queue" before `isAuthenticated` becomes `true`.

### Server-Side: Conditional Auth Allows Pre-Auth Room Entry for Free Matches

As confirmed by H016, the server only enforces authentication for wagered matches:

```js
// server/socket-io/main.js line 1121
if (wagerAmount > 0 && !requireAuth(client, 'createRoom')) return

// server/socket-io/main.js line 1231
if (wagerAmount > 0 && !requireAuth(client, 'joinQueue')) return;
```

A pre-auth `createRoom` or `joinQueue` event with `wager: 0` (free/practice match) is accepted by the server and `client.roomId` is set. The socket is now inside a room before authentication completes.

For **wagered matches** (`wager > 0`), the server correctly blocks the event — `requireAuth` returns false and emits `createRoomError`. The client does not check `isAuthenticated` before sending, but the server rejects it. So the financial path is gated at the server level.

### The Compounding Path: Pre-Auth Room Entry Enables H016 Relay Events

Once `client.roomId` is set (via pre-auth free room entry), the socket has access to all 6 unauthenticated relay events from H016:

```
Pre-auth socket
  -> emits createRoom(wager: 0)          <- accepted (no auth required for free)
  -> server sets client.roomId           <- socket is now "in a room"
  -> emits weaponPick, angleChange,
     powerChange, weaponChange,
     shoot, giveTurn                     <- all accepted with NO auth check (H016)
```

This is the key compounding path. The autoConnect race does not directly enable a financial attack, but it directly feeds the H016 attack surface by providing a fast path to `client.roomId` being set before auth completes.

## Evidence: Auto-Authenticate Race

```js
// client/src/wallet/WalletContext.js lines 326–342
useEffect(() => {
    if (!connected || !publicKey || isAuthenticated) return;
    // Poll for socket availability (may not exist on first render)
    const tryAuth = () => {
        if (window.socket && window.socket.connected) {
            console.log('[SolShot] Auto-authenticating wallet...');
            authenticate();
            return true;
        }
        return false;
    };
    if (tryAuth()) return;
    const timer = setInterval(() => {
        if (tryAuth()) clearInterval(timer);
    }, 1000);
    return () => clearInterval(timer);
}, [connected, publicKey, isAuthenticated, authenticate]);
```

The effect polls `window.socket.connected` every 1 second. When both the socket connects and the wallet is available (both enabled by autoConnect), `authenticate()` is called — which calls `signMessage()`. The server processes the signature asynchronously. Between the `tryAuth()` call and the receipt of `authResult`, `isAuthenticated` is still `false`.

On a fast connection, this window is sub-second. However, the `signMessage` call involves the wallet extension's UI, which can stall on mobile or when the user is not focused on the tab. There is no timeout on the auth attempt — if `signMessage` never resolves (extension crash, popup blocked), `authenticate()` silently returns `null` (line 196–199 of WalletContext.js), `isAuthenticated` stays `false` permanently, and the socket stays connected. The user can still navigate to the lobby and interact with the pre-auth socket.

grep -r "isAuthenticated" client/src/screens/MenuScreen.js
-> No matches found

The `LoadingScreen` only checks `window.socket.connected` — not authentication state — before calling `navigate('menu')`:

```js
// client/src/screens/LoadingScreen.js lines 87–107
function checkSocket() {
    return new Promise((resolve) => {
        const socket = window.socket;
        if (socket.connected) { resolve(); return; }
        // Wait up to 3s for connection
        const timeout = setTimeout(resolve, 3000);
        socket.on('connect', () => { clearTimeout(timeout); resolve(); });

```

The LoadingScreen transitions to MenuScreen once the socket is connected — this may be before the wallet adapter has reconnected (autoConnect) and before `signMessage` has been called. There is no "waiting for auth" stage in the loading sequence.

## The rejoinRoom Pre-Auth Hazard

`App.js` also emits `rejoinRoom` on socket connect:

```js
// client/src/App.js lines 56–94
const attemptRejoin = async () => {
    const walletAddress = publicKey?.toBase58();
    if (!walletAddress || !signMessage) {
        // Wallet not ready — retry in 2s
        if (!attemptRejoin._retried) {
            attemptRejoin._retried = true;
            setTimeout(attemptRejoin, 2000);
        }
        return;
    }
    const timestamp = Date.now();
    const message = `SolShot Auth: ${walletAddress} at ${timestamp}`;
    const encodedMessage = new TextEncoder().encode(message);
    const signature = await signMessage(encodedMessage);
    window.socket.emit('rejoinRoom', { walletAddress, message, signature, timestamp });
};

// Fires on every socket connect event:
window.socket.on('connect', attemptRejoin);
```

This fires on every `connect` event with autoConnect. Because autoConnect reconnects the wallet silently and the socket connects unconditionally, `attemptRejoin` will attempt `signMessage` and emit `rejoinRoom` on page load without any user action. This is the intended reconnect flow — but it means wallet signatures are generated silently and automatically on every page reload when a wallet is connected. The silent signature generates a timestamp-bound credential with the same 5-minute replay window identified in AUTH-01-C2 (C-6 in ARCHITECTURE.md).

Each page reload by an autoConnect user silently generates and transmits a fresh replayable auth credential over the WebSocket.

## Severity Assessment

**Severity: MEDIUM**

The hypothesis is confirmed with the following qualification: the autoConnect race does not itself create a new financial exploit path beyond what already exists. Its contribution is:

1. **It ensures the pre-auth window always exists** — there is no deliberate "require user action before connecting" design, so the window is structural, not accidental.
2. **It feeds H016 directly** — the fastest path to `client.roomId` being set without authentication is: autoConnect restores wallet -> socket connects -> user navigates to lobby -> `createRoom(wager:0)` is sent before `authResult` arrives.
3. **It generates silent replayable credentials** on every page reload via `attemptRejoin`, amplifying AUTH-01-C2 (C-6).
4. **It enables persistent pre-auth socket state** when `signMessage` fails or is blocked — the socket stays connected with a wallet address derivable by the server from payload, but `isAuthenticated` never becomes `true`.

The finding does not reach HIGH or CRITICAL on its own because:
- Wagered match creation is blocked server-side before auth
- The pre-auth free-room path is only financially harmful when combined with the existing H016 relay events
- The relay events were already rated CRITICAL in H016 independent of this finding
- No direct fund loss path is uniquely enabled by autoConnect that is not already covered by H016

**Severity rationale: MEDIUM** — confirmed structural gap that amplifies existing CRITICAL and HIGH findings without itself being a standalone financial exploit path.

## Exact Race Window Measurement

The race window duration depends on three independent timers:

| Timer | Typical Duration | Notes |
|-------|-----------------|-------|
| Socket TCP connect | 20–200ms | Network-dependent |
| Wallet adapter autoConnect | 50–300ms | Phantom extension response |
| `signMessage` in `authenticate()` | 100ms–indefinite | User action required on mobile; silent on desktop if already approved |
| Server `authResult` round-trip | 10–50ms after signature send | NaCl verify is fast |

On a fast desktop with Phantom pre-approved, the total window from page load to `isAuthenticated = true` is approximately **200–600ms**. This is fast enough that accidental pre-auth room entry is unlikely in normal use.

However, on mobile, or when the wallet popup is dismissed or blocked, `signMessage` may never complete, leaving the socket in a permanent pre-auth state with `connected = true` and `publicKey` available.

## Attack Scenarios

### Scenario A: Accidental Pre-Auth Free Room Entry (Race)

**Prerequisites:** User has Phantom connected via autoConnect. Fast click on "Play Free" before auth completes.

**Path:**
1. Page loads: socket connects (20ms), wallet reconnects (100ms)
2. LoadingScreen passes at ~500ms (socket connected)
3. User navigates to lobby quickly
4. Auto-auth poll fires at 1000ms interval — `authenticate()` called, `signMessage` pending
5. User clicks "Create Room" (free) at 800ms — before `signMessage` resolves
6. `createRoom(wager:0)` sent pre-auth
7. Server accepts — `client.roomId` set
8. Auth completes at 1200ms — `isAuthenticated` becomes true on both sides
9. Player is now in a room and is "authenticated" — no anomaly detected

**Net result:** A legal free match started during the pre-auth window. No financial harm. Race condition is typically invisible to the user and benign in practice.

### Scenario B: Persistent Pre-Auth Socket (Mobile / Blocked Popup)

**Prerequisites:** Mobile browser, wallet popup blocked by browser permissions.

**Path:**
1. autoConnect reconnects wallet silently (no user action)
2. Socket connects
3. `authenticate()` is called, `signMessage` throws (popup blocked)
4. `catch` block sets `isAuthenticated(false)` and returns null
5. `isAuthenticated` stays `false` permanently — no retry logic
6. Socket remains connected with `publicKey` and `walletAddress` available in context
7. User navigates to lobby — `walletAddress` is present in context, lobby renders
8. User creates free room or joins queue — `createRoom(wager:0)` accepted by server
9. Once in a room, all 6 H016 unauthenticated relay events are accessible
10. User cannot proceed past `ready` (requires auth) but occupies a room slot indefinitely

**Net result:** A socket with a known wallet address (but not server-authenticated) occupies a room and has access to relay event injection. For free matches, this represents a persistent unauthenticated participant. Financial matches are blocked at `ready` but the slot is occupied.

### Scenario C: Silent Replay Credential Generation on Page Reload

**Prerequisites:** User has autoConnect enabled (default). Normal page reload.

**Path:**
1. Page reload — socket connects, wallet reconnects
2. `attemptRejoin` fires on `connect` event
3. `signMessage("SolShot Auth: <wallet> at <timestamp>")` executes silently
4. Signed credential transmitted as `rejoinRoom` event
5. If no active match: server ignores rejoin (no pending reconnect)
6. But the signed credential `{ walletAddress, message, signature, timestamp }` is on the wire

If the WebSocket is on plaintext (dev environment — `http://localhost:5001` fallback, or REACT_APP_SERVER_URL unset), this credential is visible to any network observer. The credential is replayable for 5 minutes (AUTH-01-C2).

Each page reload silently generates and transmits a fresh replayable wallet signature. A user who reloads their page 12 times in an hour generates 12 potentially replayable credentials.

**Net result:** Amplifies the AUTH-01-C2 signature replay window. Not a unique vulnerability but autoConnect makes it systematic rather than occasional.

## Root Cause Analysis

Three independent design decisions combine to produce this finding:

1. **`autoConnect` enabled without explicit user re-consent on each session** — `WalletProvider wallets={wallets} autoConnect` in `WalletContext.js` line 375. The intent is UX convenience (returning users skip the connect step). The security cost is that wallet state and socket state are both established before the user takes any deliberate action.

2. **Socket initialized unconditionally at module load** — `socket/index.js` creates the Socket.IO connection on import. `App.js` imports this module at startup. The socket is not lazy-initialized after auth; it connects immediately on page load.

3. **No client-side auth gate on lobby actions** — `LobbyScreen.createRoom`, `LobbyScreen.joinRoom`, and `LobbyScreen.joinQueue` check only `window.socket` existence, not `isAuthenticated`. The UI does not disable these buttons during the pre-auth window, nor does it block navigation to the lobby until auth completes.

The server-side partial mitigation (auth required for waged matches) means the financial critical path is gated, but the free-match path and relay event surface remain accessible before auth.

## Relationship to H016

H033 and H016 form a compounding pair:

- **H016** established that 6 relay events are accessible to any socket with `client.roomId` set, regardless of authentication.
- **H033** establishes that any socket can get `client.roomId` set (via free room entry) before authentication completes, because there is no client-side auth gate and the server allows unauthenticated free room creation.

The combined attack path is:

```
autoConnect (H033) -> socket connects before auth
  -> createRoom(wager:0) sent pre-auth (H033)
  -> client.roomId set on server
  -> weaponPick/angleChange/powerChange/giveTurn accessible (H016)
```

Without H033, H016 still exists (an attacker can always connect without autoConnect and send `createRoom(wager:0)` before authenticating). Without H016, H033 produces only a benign race condition. Together, they mean the pre-auth race is not just a curiosity — it is a reliable entry point into the H016 relay event surface.

## Recommendations

### R1 — Add client-side auth gate on lobby actions (PRIMARY)

Add `isAuthenticated` check in `LobbyScreen` before emitting financial or room-entry events:

```js
// client/src/screens/LobbyScreen.js
const { isAuthenticated } = useSolShotWallet();

const createRoom = useCallback(() => {
    if (!window.socket) return;
    if (!isAuthenticated) {
        // Show "Connecting wallet..." UI state instead of silently failing
        console.warn('[SolShot] Cannot create room: not authenticated');
        return;
    }
    window.socket.emit('createRoom', { ... });
}, [..., isAuthenticated, walletAddress]);
```

Apply the same guard to `joinRoom` and `joinQueue`. This eliminates the accidental pre-auth room entry race.

### R2 — Require authentication unconditionally on server for all room entry (SECONDARY)

Remove the `wagerAmount > 0` condition from the `requireAuth` calls in `createRoom`, `joinRoom`, and `joinQueue`:

```js
// server/socket-io/main.js line 1121 — CHANGE:
if (wagerAmount > 0 && !requireAuth(client, 'createRoom')) return
// TO:
if (!requireAuth(client, 'createRoom')) return
```

This ensures that even if the client-side guard is bypassed (direct socket manipulation, XSS), the server rejects all unauthenticated room creation regardless of wager amount. This directly removes the prerequisite for H016 Scenario C (unauthenticated relay via free room entry).

### R3 — Add retry / persistent auth state for mobile (TERTIARY)

The current auto-auth `useEffect` does not retry if `signMessage` fails. On mobile, the popup may be blocked without any user notification. Add a retry mechanism and surface an auth state indicator in the UI:

```js
// WalletContext.js — add retry on auth failure
const authenticate = useCallback(async () => {
    ...
    try {
        const signature = await signMessage(encodedMessage);
        ...
    } catch (err) {
        console.error('[SolShot] Auth error:', err.message);
        setIsAuthenticated(false);
        // Schedule retry after 3s to handle transient popup failures
        setTimeout(() => {
            if (!isAuthenticated) {
                console.log('[SolShot] Retrying authentication...');
                authenticate();
            }
        }, 3000);
        return null;
    }
}, [...]);
```

### R4 — Consider disabling autoConnect in favor of explicit connect (OPTIONAL)

Disabling `autoConnect` and requiring the user to click "Connect Wallet" eliminates the race entirely:

```js
// WalletContext.js line 375 — CHANGE:
<WalletProvider wallets={wallets} autoConnect>
// TO:
<WalletProvider wallets={wallets}>
```

This is a UX tradeoff — returning users must click "Connect Wallet" on each visit. For a game involving real SOL wagers, explicit wallet connection is arguably the correct UX signal (the user should always consciously connect before playing for money).

If autoConnect is retained, at minimum add a loading state in the UI that shows "Authenticating..." and disables lobby actions until `isAuthenticated` is true.

### R5 — Include socket ID in auth message to bind credential to connection (AMPLIFICATION MITIGATION)

Addresses the silent credential generation problem from Scenario C (amplifies AUTH-01-C2):

```js
// WalletContext.js authenticate()
const message = `SolShot Auth: ${walletAddress} at ${timestamp} session:${window.socket.id}`;
```

Including `socket.id` in the signed message binds the credential to the specific connection. A replayed credential on a different socket will have a mismatched socket ID in the message, which the server can detect during `verifyAuthMessage`. This requires a server-side change to also include `socket.id` in the expected message format.
