# H035 — broadcastRooms Amplification DoS

**Hypothesis ID:** H035
**Investigator:** Dinh's Bulwark Pipeline — Phase 3 Hypothesis Investigation
**Date:** 2026-02-23
**Category:** API-03 (WebSocket Security), ERR-03 (Rate Limiting / Resource Exhaustion)
**Origin:** ARCHITECTURE.md M-20 (broadcastRooms to ALL sockets), WS-05 (API-03 auditor), ERR-03-F04/F06

---

## Verdict: CONFIRMED — PARTIALLY MITIGATED

**Severity: LOW**

The hypothesis is confirmed: `broadcastRooms` uses `io.emit` (global broadcast) and is called on every room create, join, destroy, and deposit-timeout event, meaning all connected sockets — including sockets inside active matches — receive lobby updates they do not need. However, the impact is substantially lower than the hypothesis implies. The function has a 100ms debounce that hard-limits the broadcast rate to 10 broadcasts per second regardless of how many room-change events are generated, the payload is minimal (at most 5 rooms, safe lobby-only fields, no wallet addresses or match state), and the `createRoom` per-socket throttle (3 creates per 60 seconds) limits the rate at which any single attacker can generate new room-change events. The attack surface exists but the combination of debounce and per-socket create throttle keeps it in the low-severity range under realistic conditions. The finding is real and worth fixing, but it is not a high-impact availability vulnerability at current scale.

## Code Under Investigation

### broadcastRooms (main.js lines 143–151)

```js
// O2: Debounced room broadcast — batch multiple room changes within 100ms
let broadcastTimer = null;
function broadcastRooms(io) {
    if (broadcastTimer) return; // already scheduled
    broadcastTimer = setTimeout(() => {
        broadcastTimer = null;
        io.emit('setRooms', { rooms: getOpenRooms() });
    }, 100);
}
```

**File:** `server/socket-io/main.js`, lines 143–151

### getOpenRooms (main.js lines 160–178)

```js
function getOpenRooms() {
    const result = [];
    for (const room of rooms.values()) {
        if (!room.active) {
            result.push({
                roomId: room.roomId,
                host: room.host ? {
                    name: room.host.name,
                    color: room.host.color,
                } : null,
                wager: room.wager || 0,
                matchMode: room.matchMode || null,
                totalRounds: room.totalRounds || 1,
            });
            if (result.length >= 5) break;
        }
    }
    return result;
}
```

**File:** `server/socket-io/main.js`, lines 160–178

## Debounce Analysis: Is the Hypothesis Mitigation Effective?

### What the Debounce Does

The `if (broadcastTimer) return` guard ensures that once a broadcast is scheduled (timer set), all subsequent calls within the 100ms window are silently ignored. Only one `io.emit` fires per 100ms window. After the timer fires, `broadcastTimer = null` resets, allowing the next call to schedule a new broadcast.

**Maximum theoretical broadcast rate:** 10 broadcasts per second (one every 100ms), regardless of how many `createRoom`, `leaveRoom`, or `joinRoom` events are generated during that window.

### Attack Scenario: Single-Socket Rapid Room Create/Destroy

**Per-socket `createRoom` rate limit:** 3 per 60 seconds (from the `createRing` ring buffer at lines 450–523).

A single socket can create at most 3 rooms per minute. Destroying each room (via `leaveRoom`) is not separately rate-limited — `leaveRoom` just calls `cleanupRoom` at the global 30-events/sec cap. But with only 3 rooms per minute to create, the attacker can generate at most 6 room-change broadcasts per minute from a single socket (3 creates + 3 destroys), well below the debounce ceiling.

**At 3 creates per minute, the attacker generates roughly 1 broadcast every 10 seconds from room-change events alone — far below the 10/second debounce cap.**

### Attack Scenario: Multi-Socket Coordinated Burst

With multiple sockets (up to 100 per IP per the `ipConnectionCounts` limit), the scenario changes:

- 100 sockets × 3 creates per 60 seconds = 300 room creates per minute from one IP
- 300 creates per 60 seconds = 5 creates per second
- Plus 5 destroys per second = 10 room-change events per second from one IP

At this rate, the attacker's events arrive fast enough to trigger the debounce continuously. The debounce means only 10 broadcasts per second escape regardless — the burst is absorbed.

**However:** All 10 broadcasts per second go to every connected socket via `io.emit`. If there are 200 connected sockets (players + in-game + lobby), that is 200 × 10 = 2,000 `setRooms` messages per second being dispatched by the server. Each `setRooms` payload is small (~200 bytes for 5 rooms), so the total bandwidth is ~400 KB/s — manageable, but wasteful.

The more significant concern is CPU: `getOpenRooms()` iterates `rooms.values()` on every broadcast, and at the worst-case coordinated attack of 300 rooms per minute (from ERR-03-F06, the unbounded `rooms` Map), each `getOpenRooms()` call may scan hundreds of room entries before finding 5 inactive ones. This is O(rooms.size) per broadcast, not O(1).

### Attack Scenario: Deposit Timeout Cascade

The deposit timeout callback fires after 2 minutes for each wagered room where deposits are incomplete. If an attacker creates rooms (via `createRoom` with a non-zero wager) and never deposits, each room generates a `broadcastRooms(io)` call at the 2-minute mark when the timeout fires. This is not a rapid burst but a sustained drip of broadcasts 2 minutes after creation.

At 3 creates per 60 seconds per socket, a socket creates 3 rooms in 60 seconds. Two minutes later, 3 deposit timeouts fire in rapid succession, each calling `broadcastRooms`. The debounce collapses these into 1 broadcast. Not a significant amplification.

## What the Broadcast Sends to All Sockets

`getOpenRooms()` serializes only these fields per room:
- `roomId` (hex string, non-sensitive)
- `host.name` (sanitized player name, max 20 chars)
- `host.color` (hex color string)
- `wager` (number)
- `matchMode` (string)
- `totalRounds` (number)

No wallet addresses, no socket IDs, no match state, no financial transaction data, no HP or weapon inventory. The payload is lobby-safe by design.

**Result:** The information disclosure surface of `broadcastRooms` is LOW. The risk is performance amplification, not data exposure.

---

## Who Receives the Broadcast

`io.emit` sends to every socket in the Socket.IO server, including:
- Sockets in the lobby (`LobbyScreen`)
- Sockets in active matches (`BattleScreen`, `BATTLE` state)
- Sockets in the weapon shop (`WEAPON_SHOP` state)
- Sockets in any other state (authenticating, spectating, idle)

Only lobby-screen clients actually use the `setRooms` event. In-game clients receive and likely ignore it. This wastes bandwidth and client-side event processing for every in-game socket.

The ARCHITECTURE.md audit noted the correct fix (M-20): segregate lobby sockets into a Socket.IO channel or namespace and change `io.emit` to `io.to('lobby').emit`. This would ensure only lobby-state clients receive room broadcasts.

## Severity Factors

**Amplification coefficient:** Modest. The debounce prevents more than 10 broadcasts/second regardless of event rate. The per-socket create throttle limits the attacker to 3 creates per minute. Even a 100-socket coordinated attack from one IP stays within the debounce ceiling.

**Payload size:** Minimal (~200 bytes per broadcast). Not a bandwidth attack vector.

**Receiver scope:** Excessive. All sockets receive what only lobby clients need. This wastes server-side emit processing and client-side event handler CPU for in-game players.

**`getOpenRooms()` cost:** Linear scan of `rooms.values()`. If the unbounded `rooms` Map (ERR-03-F06) is exploited to fill the map with hundreds of inactive rooms, each `getOpenRooms()` call may scan all of them before finding 5. Under the ERR-03-F06 attack scenario (300+ inactive rooms from a multi-IP campaign), each broadcast call runs an O(rooms.size) loop. At 10 broadcasts/second, this is 3,000 map iterations per second — still negligible for current JS engine performance, but it compounds with ERR-03-F06.

**Financial impact:** None. The broadcast does not affect match outcomes, settlement, or escrow state.

**Combined risk with ERR-03-F06:** The interaction between the unbounded `rooms` Map and `getOpenRooms()` is the only non-trivial compounding scenario. If an attacker achieves a large `rooms` Map (via ERR-03-F06), each broadcast scan becomes more expensive. But this interaction is already fully described by ERR-03-F06 (no global room count cap) — the broadcast overhead is an additional cost, not the primary attack.

**Severity: LOW** — confirmed amplification vector, mitigated to low impact by the 100ms debounce and the `createRoom` per-socket throttle. Becomes a meaningful nuisance only in combination with ERR-03-F06 (unbounded room map).

## Root Cause

Three independent design choices combine to produce the finding:

1. **`io.emit` (global broadcast) instead of scoped emit** — `io.emit('setRooms', ...)` at line 149 sends to all connected sockets. The correct scope is clients in a `'lobby'` channel. This is the primary fix.

2. **`getOpenRooms()` iterates the full rooms Map** — The function scans `rooms.values()` until it finds 5 inactive rooms. If the rooms Map grows large (ERR-03-F06), this scan becomes more expensive per broadcast. An early-exit index or a maintained `openRooms` Set would make this O(1).

3. **No lobby channel segregation** — No mechanism tracks which sockets are currently on the lobby screen. Without a channel, the server cannot scope the broadcast to interested parties.

The debounce is a correct and effective partial mitigation that was clearly added intentionally (the comment "O2: Debounced room broadcast — batch multiple room changes within 100ms" is present). The finding exists above the debounce, not instead of it.

## Recommendations

### R1 — Scope broadcast to lobby channel (PRIMARY)

Replace the global `io.emit` with a scoped emit to a `'lobby'` Socket.IO room. Have clients join the `'lobby'` channel when entering `LobbyScreen` and leave when navigating away.

**Server (`server/socket-io/main.js`):**
```js
// Change line 149:
io.emit('setRooms', { rooms: getOpenRooms() });
// TO:
io.to('lobby').emit('setRooms', { rooms: getOpenRooms() });
```

**Client (LobbyScreen mount/unmount):**
```js
// client/src/screens/LobbyScreen.js
useEffect(() => {
    window.socket.emit('joinLobbyChannel');
    return () => { window.socket.emit('leaveLobbyChannel'); };
}, []);
```

**Server (new handlers):**
```js
client.on('joinLobbyChannel', () => { client.join('lobby'); });
client.on('leaveLobbyChannel', () => { client.leave('lobby'); });
```

This ensures only clients actively viewing the lobby receive room updates. In-game players receive no spurious broadcasts.

### R2 — Replace getOpenRooms() scan with maintained open-rooms index (SECONDARY)

Instead of iterating `rooms.values()` on every broadcast, maintain a small Set or ordered array of inactive room IDs that is updated on room creation, activation, and deletion:

```js
const openRoomIds = new Set(); // maintained alongside rooms Map

// On createRoom:
openRoomIds.add(roomId);

// On joinRoom (room becomes active):
openRoomIds.delete(roomId);

// On removeRoom:
openRoomIds.delete(roomId);

function getOpenRooms() {
    const result = [];
    for (const id of openRoomIds) {
        const room = rooms.get(id);
        if (room && !room.active) {
            result.push({ roomId: room.roomId, host: { name: room.host.name, color: room.host.color }, wager: room.wager || 0, matchMode: room.matchMode || null, totalRounds: room.totalRounds || 1 });
            if (result.length >= 5) break;
        }
    }
    return result;
}
```

This makes `getOpenRooms()` O(1) in practice (iterates only up to the number of open rooms, typically 0–5) and eliminates the interaction with the ERR-03-F06 unbounded rooms Map attack.

### R3 — Address in conjunction with ERR-03-F06 (COMPOUND FIX)

The `getOpenRooms()` linear scan cost is only meaningful if ERR-03-F06 (unbounded rooms Map) is exploited. Fixing ERR-03-F06 with a global room cap (`MAX_TOTAL_ROOMS = 500`) eliminates the O(rooms.size) worst case independent of the open-rooms index optimization. Both fixes are beneficial; they address different root causes.
