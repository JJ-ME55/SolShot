# H036 — Match Result Never Written to DB

**Hypothesis ID:** H036
**Investigator:** Dinh's Bulwark Pipeline — Phase 3 Hypothesis Investigation
**Date:** 2026-02-23
**Category:** DATA-01 (Data Persistence), LOGIC-02 (Financial Logic)
**Origin:** DB-6 (DATA-01 auditor), H-7 (ARCHITECTURE.md deduplicated finding)

---

## Verdict: CONFIRMED — FULLY ACCURATE

**Severity: HIGH**

The hypothesis is confirmed without qualification. After `settleMatch()` succeeds, no code writes the outcome to any persistent store. The Match document's `winner`, `settlementTx`, `settledAt`, and `status: 'complete'` fields exist in the schema but are permanently null/`'lobby'` in production. The only post-match write to the database is an incremental `$inc` on two `User.stats` documents (fire-and-forget, no match reference). There is no matches collection record that proves a specific match was won by a specific wallet, settled for a specific amount, or confirmed by a specific on-chain transaction. This means there is no off-chain forensic trail for any completed wagered match.

---

## What the Schema Declares vs. What the Code Writes

### Match Schema (`server/models/Match.js`)

The schema defines all the fields needed for a complete forensic record:

```js
// server/models/Match.js
const matchSchema = new mongoose.Schema({
    roomCode:     { type: String, required: true, unique: true },
    status:       { type: String, default: 'lobby',
                    enum: ['lobby', 'weapon_shop', 'battle',
                           'settling', 'complete', 'cancelled'] },
    escrowPDA:    String,
    rounds:       [roundSchema],
    winner:       String,          // <- never written
    settlementTx: String,          // <- never written
    settledAt:    Date             // <- never written
}, { timestamps: true });
```

Fields `winner`, `settlementTx`, `settledAt`, and the `'complete'` status value are defined and correctly typed. The `escrowPDA` field is also present. None are populated in the code.

### All `Match.findByIdAndUpdate` Call Sites (`server/socket-io/main.js`)

A full search across the file finds exactly two call sites:

**Call site 1 — `persistRoom()` (line 206):**

```js
// main.js lines 180–210
async function persistRoom(room) {
    if (!room || !room._matchId || !isDbConnected()) return;
    const update = {
        active: room.active,
        randomArray: room.randomArray,
    };
    if (room.host)   update.host   = { username, socketId, color, isReady, playAgain };
    if (room.player) update.player = { username, socketId, color, isReady, playAgain };
    await Match.findByIdAndUpdate(room._matchId, update);
}
```

This writes connection metadata only. `winner`, `settlementTx`, `settledAt`, and `status` are untouched.

**Call site 2 — `removeRoom()` (line 232):**

```js
// main.js lines 212–237
async function removeRoom(roomId) {
    rooms.delete(roomId);
    // ... state cleanup ...
    if (room && room._matchId && isDbConnected()) {
        await Match.findByIdAndUpdate(room._matchId, { status: 'cancelled' });
    }
}
```

`removeRoom()` is the **only** function that writes `status` to the Match document — and it hardcodes `'cancelled'`. Every match termination path (normal win, forfeit, disconnect, turn timeout) eventually calls `removeRoom()`. The result is that every completed Match document carries `status: 'cancelled'` regardless of whether the match was won legitimately and settled on-chain.

There is no third call site. `Match.findOneAndUpdate`, `Match.updateOne`, `Match.replaceOne`, and `Match.save()` are entirely absent from `main.js`.

### The Settlement Success Path (main.js lines 2085–2244)

Following the full success branch of `withLock('settle:roomId', ...)`:

```js
// main.js lines 2101–2122
const sResult = await settleMatch(winnerWallet, loserWallet, ws.amount, roomId)
if (!sResult.success) {
    // ... failure path: handleSettlementFailure ...
} else {
    settlementInfo = {
        wager:        ws.amount,
        totalPot:     ws.amount * 2,
        winnerPayout: sResult.settlement.winner,
        treasuryFee:  sResult.settlement.treasury,
        opsFee:       sResult.settlement.ops,
        txSignature:  sResult.txSignature          // <- captured here, then discarded
    }
    console.log('[Solana] Match settled:', settlementInfo)  // <- logged only
    transitionState(ms, MATCH_STATES.COMPLETE)             // <- in-memory only
}
```

`sResult.txSignature` is captured into `settlementInfo`, then logged to the console and emitted to clients in the `matchEnd` payload. It is never passed to a `Match.findByIdAndUpdate` call. The `MATCH_STATES.COMPLETE` transition updates the in-memory `matchStates[roomId]` object, not the database.

Subsequent code in the same lock block:

```js
// main.js lines 2212–2243
if (isDbConnected()) {
    const winnerId   = matchResult.winner
    const winnerAddr = authenticatedWallets[winnerId] || wsState?.wallets?.[winnerId]
    const loserAddr  = authenticatedWallets[loserId]  || wsState?.wallets?.[loserId]
    const persistStats = async () => {
        await User.findOneAndUpdate(
            { walletAddress: winnerAddr },
            { $inc: { 'stats.matchesPlayed': 1, 'stats.wins': 1,
                      'stats.totalSolWon': solWonAmt, ... } },
            { upsert: true }
        )
        await User.findOneAndUpdate(
            { walletAddress: loserAddr },
            { $inc: { 'stats.matchesPlayed': 1, 'stats.losses': 1,
                      'stats.totalSolLost': wagerAmt, ... } },
            { upsert: true }
        )
    }
    persistStats()  // fire-and-forget — don't await
}
```

`persistStats()` writes aggregate counters to two `User` documents — `matchesPlayed`, `wins`, `losses`, `totalSolWon`, `totalSolLost`, `totalShotEarned`. These are running totals with no reference to which match produced them, no `roomCode` linkage, no `txSignature`, and no `winner` wallet address stored on the match record itself. The `User` document records that *a* win happened; it does not record *which* match it was, *who* the opponent was, or *what* the on-chain transaction signature is.

Control then falls through to `removeRoom(roomId)` which, as shown above, writes `{ status: 'cancelled' }` to the Match document.

### What `escrowPDA` Is and Is Not Stored

The `escrowPDA` is stored in memory on the `roomData` object:

```js

room.escrowPDA = escrowResult.escrowPDA

// main.js line 1308 (createRoom / joinQueue path)
roomData.escrowPDA = escrowResult.escrowPDA
```

It is passed into `roomSnapshot` objects for failure recovery:

```js

    host: roomSnap.host,
    player: roomSnap.player,
    escrowPDA: roomSnap.escrowPDA  // <- in memory snapshot only
```

It is **never written** to the Match document's `escrowPDA: String` field. `Match.create()` at line 1185–1196 does not include `escrowPDA`. No subsequent `findByIdAndUpdate` writes it. The on-chain PDA address — which is the sole link between the Match document and the Anchor escrow account — exists only in the in-memory `rooms` Map and is lost when `removeRoom()` clears that Map.

## Impact Analysis

### No Forensic Trail for Wagered Matches

After a wagered match completes and the server restarts (or even after `removeRoom()` is called in the normal lifecycle), the following information is permanently lost:

| Data | Schema Field | Written? | Lost After |
|------|-------------|---------|-----------|
| Winner wallet address | `Match.winner` | Never | removeRoom() |
| Settlement tx signature | `Match.settlementTx` | Never | removeRoom() |
| Settlement timestamp | `Match.settledAt` | Never | removeRoom() |
| On-chain escrow PDA | `Match.escrowPDA` | Never | removeRoom() |
| Match status (complete vs cancelled) | `Match.status` | Overwritten with 'cancelled' | removeRoom() |
| Turn-by-turn history | `Match.rounds` | Never (always empty) | removeRoom() |

What IS left in the database after any completed match:

- `Match.status = 'cancelled'` (same for legitimate wins and actual cancellations)
- `Match.roomCode` (the room ID, allowing blockchain correlation if the match ID was used in the escrow PDA seeds)
- `User.stats.$inc` counters for both players (wins, losses, SOL amounts — no match reference)

### Dispute Resolution Is Impossible

If a player disputes a match outcome — claiming they won but did not receive payment, or that the wrong winner was recorded — there is no server-side record to resolve the dispute. The on-chain escrow settlement is authoritative for whether funds moved, but:

1. The on-chain record only shows lamport transfers; it does not record who the "winner" was by game logic.
2. Without `settlementTx` in the Match document, correlating the Solana transaction to the specific game outcome requires manually searching the chain with only the room code (which was used in PDA seeds) as a hint.
3. Without `Match.status: 'complete'`, a database query for all completed matches returns zero results — every match appears cancelled.

### `User.stats` Integrity Cannot Be Verified

The `User.stats.wins` counter cannot be audited against match records because no match record links to a win. If a logic bug double-increments wins, or if the in-memory state diverges from on-chain reality, there is no way to reconcile the user's stats against actual match outcomes.

### The False Status Problem

Every Match document ends with `status: 'cancelled'` because `removeRoom()` is the only post-match DB writer. This creates a systematic false record. A future analytics query of `Match.find({ status: 'complete' })` will return zero documents even though hundreds of matches may have been played and settled. Conversely, a query of `Match.find({ status: 'cancelled' })` will return all matches — both legitimately cancelled and fully settled.

## Severity Assessment

**Severity: HIGH**

This finding falls at HIGH rather than CRITICAL because it does not directly enable fund loss or theft. The on-chain escrow is the authoritative record of financial settlement, and the Anchor program correctly handles fund distribution. However, the severity is HIGH and not MEDIUM for three reasons:

1. **Operational blindness.** There is no way to query "all matches that settled successfully" or "what did room ABC result in" from the database. Any production incident investigation, customer dispute, or financial reconciliation requires manual on-chain forensics rather than database queries.

2. **Regulatory and accountability exposure.** A system handling real SOL wagers with no server-side record of outcomes is structurally unable to produce evidence of fair operation. If a player claims the server cheated them, the server cannot prove otherwise from its own records.

3. **Compounding with existing findings.** Combined with H-6 (`failedSettlements` in-memory only), there is also no DB record of failed settlements, meaning a match where settlement failed and funds were lost is entirely invisible in the database. The `status: 'cancelled'` written by `removeRoom()` is indistinguishable whether the match settled successfully, failed to settle, or was never started.

The finding is not CRITICAL because:
- It does not enable any attack or fund loss independently
- The on-chain record is correct and immutable
- The `User.stats` aggregate counters do survive (though without match-level linkage)

---

## Root Cause

Three independent failures combine to produce this gap:

**1. `removeRoom()` is the only post-match DB writer and it hardcodes `'cancelled'`.**

`removeRoom()` was written as a cleanup function for interrupted or cancelled matches. It was not updated when the settlement success path was added. Because `removeRoom()` is called unconditionally at the end of every match path (normal end, forfeit, disconnect), its unconditional `{ status: 'cancelled' }` write overwrites any status that might have been set earlier.

**2. The settlement success branch has no DB write.**

The `else` branch of `settleMatch()` at line 2110 captures `sResult.txSignature` into `settlementInfo` and logs it. There is no `Match.findByIdAndUpdate(room._matchId, { winner, settlementTx, settledAt, status: 'complete' })` call in this branch or anywhere after it.

**3. `persistStats()` writes to `User`, not `Match`.**

The fire-and-forget `persistStats()` at line 2243 was the only DB write added to the settlement path. It correctly records per-user aggregate stats but was not designed to create an auditable match record linking the two players, the outcome, and the transaction.

## Recommendations

### R1 — Write settlement result to Match document on success (PRIMARY)

Insert a `Match.findByIdAndUpdate` call immediately after `sResult.success` is confirmed, before `removeRoom()` is called. This call must happen while `room._matchId` is still valid (it is destroyed by `removeRoom()`):

```js
// In the withLock block, after confirming sResult.success (main.js ~line 2121)
} else {
    settlementInfo = { ... txSignature: sResult.txSignature }
    transitionState(ms, MATCH_STATES.COMPLETE)

    // Write forensic record to Match document BEFORE removeRoom() destroys _matchId
    if (room._matchId && isDbConnected()) {
        try {
            await Match.findByIdAndUpdate(room._matchId, {
                status:       'complete',
                winner:       winnerWallet,
                settlementTx: sResult.txSignature,
                settledAt:    new Date(),
                escrowPDA:    room.escrowPDA || null,
            });
        } catch (err) {
            console.error('[DB] Failed to write settlement record:', err.message);
            // Non-fatal: log and continue — on-chain record is authoritative
        }
    }
}
```

The same pattern should be applied to the forfeit path (line ~341) and disconnect forfeit path (line ~654).

### R2 — Separate `removeRoom()` cleanup from the DB status write (SUPPORTING)

`removeRoom()` should not hardcode `status: 'cancelled'`. It should only write `status: 'cancelled'` when the match genuinely was cancelled — i.e., when it did not reach COMPLETE state. Add a state check:

```js
async function removeRoom(roomId) {
    const room = rooms.get(roomId);
    const ms   = matchStates[roomId];
    rooms.delete(roomId);
    // ... state cleanup ...
    if (room && room._matchId && isDbConnected()) {
        // Only mark cancelled if the match did NOT complete successfully
        const alreadyComplete = ms?.status === MATCH_STATES.COMPLETE;
        if (!alreadyComplete) {
            try {
                await Match.findByIdAndUpdate(room._matchId, { status: 'cancelled' });
            } catch (err) {
                console.error('DB cancel error:', err.message);
            }
        }
    }
}
```

This prevents `removeRoom()` from overwriting a `status: 'complete'` record that R1 wrote.

### R3 — Write `escrowPDA` to Match document at match creation (SUPPORTING)

The `escrowPDA` is available immediately after `createMatchEscrow()` succeeds (line 1027). Write it to the Match document at that point so the on-chain PDA is recoverable from the database even after the in-memory room is destroyed:

```js
// main.js ~line 1028, after escrow creation
room.escrowPDA = escrowResult.escrowPDA
if (room._matchId && isDbConnected()) {
    Match.findByIdAndUpdate(room._matchId, {
        escrowPDA: escrowResult.escrowPDA
    }).catch(err => console.error('[DB] escrowPDA write failed:', err.message));
}
```

### R4 — Add match reference to `User.stats` increment (LONG TERM)

The `persistStats()` write to `User.stats` is correctly structured for aggregate reporting, but it provides no per-match audit trail. For production, add a `User.matchHistory` array or a separate `MatchResult` collection with entries like:

```js
{
    roomCode:     roomId,
    opponent:     loserAddr,
    won:          true,
    wagerAmount:  wagerAmt,
    payout:       solWonAmt,
    settlementTx: sResult.txSignature,
    playedAt:     new Date()
}
```

This is a schema-level change and is lower priority than R1, but it makes `User.stats.wins` auditable and enables dispute resolution without chain forensics.
