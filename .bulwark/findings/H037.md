# H037 — Dual-Write Inconsistency MongoDB vs In-Memory

**Hypothesis ID:** H037
**Investigator:** Dinh's Bulwark Pipeline — Phase 3 Hypothesis Investigation
**Date:** 2026-02-23
**Category:** DATA-01 (Database & Query Security)
**Origin:** ARCHITECTURE.md M-2 (Dual-write inconsistency User.stats), DATA-01 DB-7 (Dual fire-and-forget writes)

---

## Verdict: CONFIRMED — ACCURATELY STATED

**Severity: MEDIUM**

The hypothesis is confirmed in full. Stats are written to MongoDB via two independent fire-and-forget paths with no ordering guarantee. Match state is entirely in-memory and lost on server restart. The DB persists whatever was last written before the restart — partial writes from whichever of the two paths completed before the process died. The specific sub-finding that `stats.totalShotEarned` is written by both paths using incompatible operators (`$inc` vs `$max`) is confirmed and represents the most acute form of the inconsistency.

The hypothesis is rated **MEDIUM** rather than HIGH or CRITICAL because the affected data is soft metrics (leaderboard counters and SHOT balance) and not directly financial. No wager funds, escrow balances, or on-chain settlement outcomes are affected by this DB inconsistency. The financial blast radius is: a user's SHOT balance could be stale after a mid-write crash, potentially allowing a milestone reward to be claimed again on next authentication. This is a real but bounded economic exposure rather than a direct SOL loss path.

## Write Path 1: `persistStats()` in `main.js`

**File:** `server/socket-io/main.js` lines 2220–2243

`persistStats()` is defined as an async closure inside the settlement lock block and immediately invoked without `await`:

```js
// main.js lines 2220–2243
const persistStats = async () => {
    try {
        if (winnerAddr) {
            const winnerShotEarned = shotResults[winnerId]?.earned || 0
            await User.findOneAndUpdate(
                { walletAddress: winnerAddr },
                { $inc: { 'stats.matchesPlayed': 1, 'stats.wins': 1,
                          'stats.totalSolWon': solWonAmt,
                          'stats.totalShotEarned': winnerShotEarned },
                  $set: { lastActive: new Date() } },
                { upsert: true }
            )
        }
        if (loserAddr) {
            const loserShotEarned = shotResults[loserId]?.earned || 0
            await User.findOneAndUpdate(
                { walletAddress: loserAddr },
                { $inc: { 'stats.matchesPlayed': 1, 'stats.losses': 1,
                          'stats.totalSolLost': wagerAmt,
                          'stats.totalShotEarned': loserShotEarned },
                  $set: { lastActive: new Date() } },
                { upsert: true }
            )
        }
        logger.info('[Stats] Persisted match stats')
    } catch (err) {
        console.error('[Stats] Failed to persist:', err.message)
    }
}
persistStats() // fire-and-forget — don't await
```

**Fields written by Path 1:**

| Field | Operator | Notes |
|-------|----------|-------|
| `stats.matchesPlayed` | `$inc +1` | Both players |
| `stats.wins` | `$inc +1` | Winner only |
| `stats.losses` | `$inc +1` | Loser only |
| `stats.totalSolWon` | `$inc solWonAmt` | Winner only; `wagerAmt * 2 * 0.9` |
| `stats.totalSolLost` | `$inc wagerAmt` | Loser only |
| `stats.totalShotEarned` | `$inc shotEarned` | Both players; amount from `shotResults` |
| `lastActive` | `$set` | Both players |

**Timing:** Invoked fire-and-forget at line 2243, inside `withLock()`, after settlement completes. The lock is not held waiting for this write.

## Write Path 2: `saveMilestoneState()` in `shot-token.js`

**File:** `server/services/shot-token.js` lines 195–224

`saveMilestoneState()` is called synchronously (but executes asynchronously) at the end of `recordMatchPlayed()`, which itself is called at lines 2164 and 2176 of `main.js` — just before the `setTimeout` for `matchEnd` and before `persistStats()` is invoked:

```js
// shot-token.js lines 195–224
export function saveMilestoneState(walletAddress) {
    if (!walletAddress) return;
    const state = playerShotState[walletAddress];
    if (!state) return;

    // Fire-and-forget — errors logged but not propagated
    User.findOneAndUpdate(
        { walletAddress },
        {
            $set: {
                'stats.totalMatchesPlayed': state.totalMatchesPlayed,
                'stats.wageredMatchesPlayed': state.wageredMatchesPlayed,
                'stats.wageredWins': state.wageredWins,
                'stats.consecutiveWins': state.consecutiveWins,
                'stats.milestonesEarned': state.milestonesEarned,
                'stats.shotBalance': state.balance,
                'stats.totalBurned': state.totalBurned,
                'stats.prestigeTier': state.prestigeTier,
                'stats.claimedMatchIds': [...state.claimedMatchIds],
            },
            $max: {
                'stats.totalShotEarned': state.balance + state.totalBurned,
            },
        },
        { upsert: true }
    ).catch(err => {
        console.error(`[SHOT] Failed to save milestone state for ${walletAddress}:`, err.message);
    });
}
```

**Fields written by Path 2:**

| Field | Operator | Notes |
|-------|----------|-------|
| `stats.totalMatchesPlayed` | `$set` | In-memory `playerShotState` value |
| `stats.wageredMatchesPlayed` | `$set` | In-memory value |
| `stats.wageredWins` | `$set` | In-memory value |
| `stats.consecutiveWins` | `$set` | In-memory value |
| `stats.milestonesEarned` | `$set` | Array snapshot from in-memory Set |
| `stats.shotBalance` | `$set` | In-memory `state.balance` |
| `stats.totalBurned` | `$set` | In-memory value |
| `stats.prestigeTier` | `$set` | In-memory value |
| `stats.claimedMatchIds` | `$set` | Array snapshot of in-memory Set |
| `stats.totalShotEarned` | `$max` | `state.balance + state.totalBurned` |

**Timing:** Invoked inside `recordMatchPlayed()` at line 342 of `shot-token.js`. `recordMatchPlayed()` is called synchronously at `main.js` lines 2164 and 2176, before `persistStats()` is invoked at line 2243. However, both paths are fire-and-forget: neither is awaited, so the actual DB round-trips race against each other with no deterministic ordering.

## The `totalShotEarned` Operator Conflict

This is the sharpest form of the dual-write inconsistency. Both paths write `stats.totalShotEarned` to the same User document for the same player, using incompatible operators:

| Path | Operator | Value Written |
|------|----------|---------------|
| `persistStats()` (Path 1) | `$inc winnerShotEarned` | Adds earned amount from this match's `shotResults` |
| `saveMilestoneState()` (Path 2) | `$max state.balance + state.totalBurned` | Sets to the high-water mark of total lifetime balance |

These operators are not semantically equivalent and are not commutative in all states:

- `$inc` adds a delta (the per-match earned amount) to whatever value is currently in MongoDB.
- `$max` sets the value only if the incoming value is larger than what is currently in MongoDB.

**Scenario 1: Path 1 wins the race (lands first)**

State at match end: DB has `totalShotEarned = 500` (pre-match). This match earns 10 SHOT. In-memory `state.balance = 350`, `state.totalBurned = 160` (lifetime = 510).

- Path 1 runs: `$inc 10` → DB: `totalShotEarned = 510`
- Path 2 runs: `$max 510` → DB: 510 >= 510, no change → DB: `totalShotEarned = 510`

Result: correct.

**Scenario 2: Path 2 wins the race (lands first)**

Same values.

- Path 2 runs: `$max 510` → DB: 510 > 500, sets → DB: `totalShotEarned = 510`
- Path 1 runs: `$inc 10` → DB: `totalShotEarned = 520` ← OVERCOUNTED

Result: `totalShotEarned` is overcounted by the match's earned amount. The field exceeds the player's actual lifetime earned total.

**Scenario 3: Path 1 wins, Path 2 uses stale in-memory state**

If another match completes for the same player before `saveMilestoneState` from the first match fires (concurrent matches are not the current architecture, but concurrent socket events and Node event loop ordering can produce out-of-order delivery), Path 2 could write a stale `shotBalance` snapshot, rolling back the balance field.

**Scenario 4: Server crash between the two writes**

The server restarts between Path 1 completing and Path 2 completing (or vice versa). The MongoDB document has the fields from the completed path only. On next `loadMilestoneState`, the server restores the partially-written state into `playerShotState`. The unwritten fields retain their pre-match values. Depending on which path completed:

- If Path 1 completed but Path 2 did not: `matchesPlayed`, `wins`/`losses` are updated; but `shotBalance`, `milestonesEarned`, `consecutiveWins`, `claimedMatchIds` are stale (pre-match values). The milestone reward earned in this match is not recorded in `milestonesEarned`. On next `loadMilestoneState` + `recordMatchPlayed`, the milestone check runs against the stale (pre-match) state. If the milestone condition was met for the first time in this match (and its ID is not in `milestonesEarned`), the milestone fires again, issuing a duplicate SHOT reward.

- If Path 2 completed but Path 1 did not: `matchesPlayed`, `wins`/`losses` are NOT updated. The milestone state is correct. But `totalSolWon`/`totalSolLost` are wrong (showing pre-match values).

## The In-Memory vs DB Divergence on Restart

Beyond the dual-write conflict, the hypothesis correctly identifies the architectural separation between in-memory match state and MongoDB persistence.

**What is in-memory only (lost on restart):**

From `ARCHITECTURE.md` section 2:

| Store | Content |
|-------|---------|
| `rooms` | Active match state, players, weapons, terrain |
| `wagerStates` | Wager amounts, escrow status |
| `playerGold` | In-match gold balances |
| `authenticatedWallets` | Socket-to-wallet bindings |
| `playerShotState` | SHOT balances and milestone tracking |
| `failedSettlements` | Settlement retry queue |

`playerShotState` is the critical one for this finding. It is rebuilt on each `authenticate` call via `loadMilestoneState`, which reads from MongoDB. But `loadMilestoneState` only restores fields if the DB value is non-zero (lines 166–177 of `shot-token.js`):

```js
if (s.totalMatchesPlayed > 0) state.totalMatchesPlayed = s.totalMatchesPlayed;
if (s.wageredMatchesPlayed > 0) state.wageredMatchesPlayed = s.wageredMatchesPlayed;
if (s.wageredWins > 0) state.wageredWins = s.wageredWins;
if (s.consecutiveWins > 0) state.consecutiveWins = s.consecutiveWins;
if (s.milestonesEarned && s.milestonesEarned.length > 0) state.milestonesEarned = [...s.milestonesEarned];
if (s.shotBalance > 0) state.balance = s.shotBalance;
if (s.totalBurned > 0) state.totalBurned = s.totalBurned;
if (s.prestigeTier > 0) state.prestigeTier = s.prestigeTier;
```

All zero-valued fields in MongoDB are skipped. If a crash occurred mid-write and left a field at zero (e.g., `shotBalance` was reset to 0 by a DB write error during a new user's first match), the zero value is not restored to in-memory state — `getPlayerShotState` provides the default of 0 — so no regression, but the guard cannot distinguish "genuinely 0" from "not yet written". This is a correctness assumption rather than a bug, but it means zero-state users are not distinguished from users whose state failed to persist.

The more significant restart scenario is:

1. Match completes: Path 1 (`persistStats`) fires and lands, writing `matchesPlayed++`, `wins++`, `totalShotEarned += 10`.
2. Server crashes before Path 2 (`saveMilestoneState`) lands.
3. `claimedMatchIds` in MongoDB still contains the pre-match state (does NOT include this match's ID).
4. Server restarts. Player authenticates. `loadMilestoneState` restores `claimedMatchIds` from DB — the match ID is absent.
5. Player plays another match. `recordMatchPlayed` is called for the new match.
6. The milestone that was triggered in the crashed match is NOT in `milestonesEarned` (Path 2 never landed).
7. The milestone fires again and the player receives a duplicate SHOT reward.

This is the primary economic harm path. It requires a well-timed server crash and produces a duplicate milestone emission, not an arbitrary amount. Duplicate emissions are bounded by the milestone reward values in the schema (maximum single milestone: 100 SHOT per the DATA-01 context analysis).

## Match Result Never Written to Match Document

The hypothesis asks whether match result is included in the DB write. It is not. The only Match document writes are:

1. `persistRoom()` — writes lobby metadata (player names, socket IDs, colors) at lines 188–210. Called on join/ready.
2. `removeRoom()` — writes `{ status: 'cancelled' }` at line 232. Called on any room teardown.

There is no call that writes `{ status: 'complete', winner: winnerWallet, settlementTx: sResult.txSignature, settledAt: new Date() }` to the Match document after a successful settlement. The `winner`, `settlementTx`, `settledAt`, and `status: 'complete'` fields defined in the Match schema are permanently null/default in practice.

The only per-player record of the match outcome is the `$inc` in Path 1 (`persistStats`) — a counter increment with no foreign key to the match, and no escrow transaction signature. The `txSignature` from `sResult.txSignature` (line 2117) is emitted to the client in `settlementInfo` and logged to the console at line 2119, but is never written to any database record.

This means: after a completed wagered match, there is no MongoDB record that links:
- which match (room ID) occurred
- who won
- what the escrow settlement transaction hash was
- when it settled

The Solana chain holds the authoritative financial record. MongoDB holds only anonymous counter increments.

## Error Handling on DB Writes

Both paths are fire-and-forget. Error handling is minimal:

**Path 1 (`persistStats`):**
```js
} catch (err) {
    console.error('[Stats] Failed to persist:', err.message)
}
```
Errors are logged to console only. No retry, no dead-letter queue, no server alert, no client notification. A MongoDB outage silently drops the entire stats write for both players.

**Path 2 (`saveMilestoneState`):**
```js
.catch(err => {
    console.error(`[SHOT] Failed to save milestone state for ${walletAddress}:`, err.message);
});
```
Same: errors are logged to console only. No retry, no recovery.

The ERR-01 context report (EH-F06) notes this directly: "if the DB write fails for wins/losses and the server later restarts with MongoDB, the next `loadMilestoneState` call will restore stale (pre-match) counters, causing SHOT milestones to re-evaluate against wrong data."

There is no `isDbConnected()` guard on the `saveMilestoneState` call path (unlike `persistStats`, which checks `if (isDbConnected())` at line 2213 before creating the closure). `saveMilestoneState` calls `User.findOneAndUpdate` unconditionally. If the DB is not connected, Mongoose buffers the operation by default. If the buffer overflows or the connection never recovers, the promise rejects silently (caught only by `.catch`).

## Severity Assessment

**Severity: MEDIUM**

The dual-write inconsistency is real and exploitable (deliberately via a server restart at the right moment, or accidentally via natural crashes), but its blast radius is bounded:

**What can go wrong:**

1. **Duplicate milestone SHOT emission** — A player earns a milestone in a match; server crashes before `claimedMatchIds` is persisted; on restart the milestone fires again. Duplicate reward per milestone per crash at a good moment. Maximum single duplicate: 100 SHOT (the largest milestone reward in the schema). This is economically meaningful but bounded, and requires a crash at a precise moment.

2. **`totalShotEarned` overcounted** — Path 2 winning the race, then Path 1 adding on top via `$inc`, produces an inflated `totalShotEarned` counter. This is a leaderboard integrity issue, not a direct SOL loss. There is no code path that reads `totalShotEarned` from MongoDB and uses it to authorize an on-chain action.

3. **Stale SHOT balance after crash** — After a crash between the two writes, `shotBalance` may be restored to its pre-match value. On re-authentication the player appears to have their pre-match balance. If they attempt a prestige burn before the next `saveMilestoneState` fires, they may be blocked from burning (balance appears lower than actual). This is a UX regression, not a loss.

4. **Match history has no audit trail** — The Match document is never completed. Disputes over match outcomes have no MongoDB source of truth. This is an operational/trust issue.

**Why not HIGH:**

- No SOL wager funds are affected. The escrow and settlement logic is independent of MongoDB writes.
- The duplicate SHOT emission path requires a server crash timed precisely between the two fire-and-forget writes — a low-probability natural occurrence, and one that requires server-level access to trigger deliberately.
- `totalShotEarned` is a display metric; it is not used to gate any economic action.
- SHOT balance over-reporting after a crash is temporary and self-corrects after the next match completes its full write cycle.

**Why MEDIUM (not LOW):**

- The `totalShotEarned` operator conflict (`$inc` vs `$max`) is a structural code defect, not a transient race condition. It fires on every match completion and can produce a permanently inflated counter whenever Path 2 lands first (a roughly 50% likelihood in practice).
- The crash-triggered duplicate milestone emission is a real, if low-probability, economic exploit path.
- The complete absence of a match result write means there is no on-server audit trail for any match outcome. This is a systemic auditability gap.
- DATA-01 context report rated this MEDIUM (DB-7) with the exact same assessment.

## Attack Scenario: Crash-Timed Milestone Double-Claim

**Prerequisites:** Attacker controls or can predict server restart timing (e.g., via Render deploy webhook, or the server's known restart schedule). Alternatively: natural crash at an inopportune moment.

**Path:**

1. Player plays match, earns `first_wagered_win` milestone (10 SHOT).
2. `recordMatchPlayed()` fires: in-memory `state.milestonesEarned` now includes `'first_wagered_win'`; `state.claimedMatchIds` includes the match ID.
3. `saveMilestoneState()` is enqueued (fire-and-forget). Server crashes before the Mongoose operation reaches MongoDB. `claimedMatchIds` in DB: does NOT include this match ID. `milestonesEarned` in DB: does NOT include `'first_wagered_win'`.
4. `persistStats()` may or may not have landed — irrelevant for the milestone path.
5. Server restarts. Player authenticates. `loadMilestoneState` restores `claimedMatchIds` from DB (match ID absent) and `milestonesEarned` from DB (`'first_wagered_win'` absent).
6. Player plays another qualifying match. `recordMatchPlayed()` runs. Match ID is new (dedup passes). `milestonesEarned` does not contain `'first_wagered_win'`. Milestone check fires. Player receives 10 SHOT again.
7. `saveMilestoneState()` now persists `milestonesEarned` with `'first_wagered_win'` included. No further duplication on this milestone.

**Result:** Player receives the `first_wagered_win` milestone reward twice. With 5 milestones available (and more in the schema), an attacker who can trigger crashes at will can double every milestone reward. Maximum total: sum of all milestone rewards (per DATA-01 schema: 10 + 10 + 10 + 20 + 30 + 50 + 50 + 100 = 280 SHOT doubled = 280 extra SHOT). At scale with many users, this degrades the SHOT reward pool.

## Recommendations

### R1 — Merge Both Writes Into a Single Atomic `findOneAndUpdate` (PRIMARY)

Instead of two separate fire-and-forget writes, produce one `findOneAndUpdate` per player that includes all fields from both paths:

```js
// After match completes, for each player:
const shotResult = shotResults[playerId] || { earned: 0 };
const shotState = playerShotState[playerWallet];

if (playerWallet && isDbConnected()) {
    User.findOneAndUpdate(
        { walletAddress: playerWallet },
        {
            $inc: {
                'stats.matchesPlayed': 1,
                'stats.wins': isWinner ? 1 : 0,
                'stats.losses': isWinner ? 0 : 1,
                'stats.totalSolWon': isWinner ? solWonAmt : 0,
                'stats.totalSolLost': isWinner ? 0 : wagerAmt,
                // Remove totalShotEarned from $inc — use $set from source of truth
            },
            $set: {
                'stats.totalMatchesPlayed': shotState.totalMatchesPlayed,
                'stats.wageredMatchesPlayed': shotState.wageredMatchesPlayed,
                'stats.wageredWins': shotState.wageredWins,
                'stats.consecutiveWins': shotState.consecutiveWins,
                'stats.milestonesEarned': shotState.milestonesEarned,
                'stats.shotBalance': shotState.balance,
                'stats.totalBurned': shotState.totalBurned,
                'stats.prestigeTier': shotState.prestigeTier,
                'stats.claimedMatchIds': [...shotState.claimedMatchIds],
                'stats.totalShotEarned': shotState.balance + shotState.totalBurned, // single source
                'lastActive': new Date(),
            },
        },
        { upsert: true }
    ).catch(err => console.error('[Stats] Unified persist failed:', err.message));
}
```

This eliminates the operator conflict on `totalShotEarned` (one write, one operator) and ensures `claimedMatchIds` and `milestonesEarned` are always written together with the counter increments.

### R2 — Write Match Result to the Match Document (SECONDARY)

After successful settlement, update the Match document with outcome data:

```js
// After settleMatch() succeeds (main.js ~line 2118):
if (room._matchId && isDbConnected()) {
    Match.findByIdAndUpdate(room._matchId, {
        status: 'complete',
        winner: winnerWallet,
        settlementTx: sResult.txSignature,
        settledAt: new Date(),
    }).catch(err => console.error('[DB] Match result persist failed:', err.message));
}
```

This provides a server-side audit trail for every settled match, linking the winner wallet and the escrow settlement transaction hash to the match record.

### R3 — Add `isDbConnected()` Guard to `saveMilestoneState` (TERTIARY)

Currently `saveMilestoneState` submits to Mongoose unconditionally and relies on Mongoose's internal buffering. Add an explicit guard consistent with `persistStats`:

```js
export function saveMilestoneState(walletAddress) {
    if (!walletAddress) return;
    if (!isDbConnected()) return; // consistent with persistStats pattern
    const state = playerShotState[walletAddress];
    if (!state) return;
    // ... rest of function
}
```

This prevents silent Mongoose buffer accumulation when the DB is unavailable.

### R4 — Log Metric on DB Write Failure (OPERATIONAL)

Replace `console.error` in both write paths with a structured log that fires a Telegram alert or increments a trackable error counter:

```js
} catch (err) {
    console.error('[Stats] Failed to persist:', err.message);
    trackError(err, 'stats_persist'); // ← add this
}
```

`trackError` is already imported in `main.js` and calls the Telegram alert pipeline. Silent DB failures during match settlement are production-critical events that warrant operator notification.
