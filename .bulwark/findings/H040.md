# H040 — 45+ console.* Statements Bypass Pino Structured Logging

**Hypothesis ID:** H040
**Auditor:** DATA-04 (Logging & Information Disclosure)
**Severity:** MEDIUM
**Status:** CONFIRMED

---

## Verdict

Confirmed. The server has a pino structured logger with a wallet-address redaction configuration, but that logger is used in only 9 call sites across the 4 files that import it. The remaining 112 production logging calls (excluding `server/tests/`) use raw `console.*` and receive no structured formatting, no log-level gating, and no redaction. Wallet addresses appear in plain string interpolation in `console.error` calls. Full financial settlement objects — containing wager amounts, winner payouts, treasury fees, and transaction signatures — are dumped verbatim via `console.log` on every wagered match completion. The pino redaction config is structurally sound but covers a small minority of the actual log output; it provides no meaningful data-protection guarantee in the current state.

### 2. Pino Logger Configuration

**`server/services/logger.js`** (complete file):

```js
const logger = pino({
    level: process.env.LOG_LEVEL || 'info',
    redact: {
        paths: [
            'walletAddress', 'wallet', 'winner', 'loser', 'player',
            'p1wallet', 'p2wallet', 'winnerAddress', 'loserAddress',
            '*.walletAddress', '*.wallet',
        ],
        censor: '[REDACTED]',
    },
    transport: process.env.NODE_ENV !== 'production'
        ? { target: 'pino-pretty' }
        : undefined,
});
```

The redaction list is reasonable for structured object fields. However:

- Pino redaction applies only to **object field names** passed to `logger.*({ field: value }, message)`.
- It does **not** intercept string interpolation such as `` `error for ${walletAddress}` ``.
- It applies to zero percent of the 112 `console.*` calls regardless.
- The 9 `logger.*` calls are: `escrow.js:413`, `solana.js:203`, `solana.js:216`, `solana.js:251`, `shot-token.js:182`, `shot-token.js:386`, `main.js:542`, `main.js:1638`, `main.js:2238`.

### 3. Wallet Addresses Logged in Plain console.error

**`server/services/shot-token.js:184`:**
```js
console.error(`[SHOT] Failed to load milestone state for ${walletAddress}:`, err.message);
```

**`server/services/shot-token.js:222`:**
```js
console.error(`[SHOT] Failed to save milestone state for ${walletAddress}:`, err.message);
```

Both calls interpolate the full base58 Solana wallet address (44 characters) directly into the error string. These are on error paths that fire when MongoDB operations fail. The pino redact config cannot intercept string interpolation; `[REDACTED]` is never substituted. These are the only two call sites that expose a wallet address through the logging path — no private keys or seed phrases are present.

### 4. Full Settlement Object Dumped Verbatim (Most Significant Data Exposure)

**`server/socket-io/main.js:2119`** (normal match-end settlement path):
```js
settlementInfo = {
    wager: ws.amount,
    totalPot: ws.amount * 2,
    winnerPayout: sResult.settlement.winner,
    treasuryFee: sResult.settlement.treasury,
    opsFee: sResult.settlement.ops,
    txSignature: sResult.txSignature
}
console.log('[Solana] Match settled:', settlementInfo)
```

This fires on every successful wagered match settlement. The object dump includes the full breakdown of every financial disbursement: the per-player wager, the total pot, all three recipient amounts (winner/treasury/ops in SOL), and the Solana transaction signature. No wallet addresses are present in this specific object (winner is identified by socketId upstream), but the financial amounts and txSignature are fully disclosed in an unstructured stdout line.

**`server/socket-io/main.js:662`** (forfeit/disconnect settlement path):
```js
console.log(`[Solana] Forfeit settlement (${reason}):`, settlementResult)
```

`settlementResult` is the return value of `settleMatch()`, which has the shape:
```js
{
    success: true,
    settlement: { winner: <SOL_amount>, treasury: <SOL_amount>, ops: <SOL_amount> },
    txSignature: "<base58_signature>"
}
```
This fires on every forfeit or disconnect-triggered settlement. The same financial data (amounts and txSignature) appears in the log without any structured field tagging.

**Comparison with pino usage in the same code path:**

`server/services/solana.js:216` (dev-mode fallback):
```js
logger.info({ winnerSOL: settlement.winner, treasurySOL: settlement.treasury, opsSOL: settlement.ops, totalPot }, '[Solana] Settlement (off-chain)');
```

`server/services/solana.js:203` (on-chain settlement):
```js
logger.info({ matchId, txSignature: result.txSignature }, '[Solana] On-chain settlement');
```

These two calls correctly use the structured logger. The amount-field names (`winnerSOL`, `treasurySOL`, `opsSOL`) are not in the redact list — they appear in JSON — which is intentional for audit purposes. However, the `console.log` at `main.js:2119` produces the same financial data in an unstructured object dump that cannot be processed by log aggregators or filtered by log-level configuration.

### 5. Per-Shot Debug Logs Active in Production

**`server/socket-io/main.js:1932` and `1944`:**
```js
console.log('[Fire] tanks:', tanks.map(t => ({ id: t.id.slice(0,8), x: Math.round(t.x), y: Math.round(t.y) })))
// ... physics ...
console.log('[Fire] impact:', result.impact, 'damage:', result.damage)
```

These fire on every shot in every match in production. With ~20 turns per match and 2 shots per turn, each match generates ~40 debug log lines containing truncated socket IDs, tank XY coordinates, impact point coordinates, and damage values. There is no `process.env.LOG_LEVEL === 'debug'` guard. These are clearly leftover development-time diagnostics.

### 6. Player Name + Wager Amount Correlation

**`server/socket-io/main.js:1372`:**
```js
console.log(`[Queue] Matched: ${opponent.name} vs ${sanitizeName(playerName)} in ${matchMode} (${roundType}) @ ${wagerAmount} SOL — room ${roomId}`);
```

**`server/socket-io/main.js:1387`:**
```js
console.log(`[Queue] ${sanitizedName} queued for ${matchMode} (${matchLength}) @ ${wagerAmount} SOL — ${queue.length} waiting`);
```

These create a correlation between a player's display name and their exact wager amount in the same log line. Since display names are player-chosen and may not be unique pseudonyms, this constitutes unnecessary information correlation in the log stream.

### 7. Stack Traces via uncaughtException

**`server/index.js:178`:**
```js
process.on('uncaughtException', (err) => {
    console.error('[FATAL] Uncaught exception:', err);
});
```

Passing the full `err` object (not `err.message`) to `console.error` causes Node.js to serialize the error including its `stack` property. Stack traces contain internal file paths (e.g., `/opt/render/project/src/server/services/escrow.js:420`), which expose the deployment directory structure. This goes to server stdout only — not to any client — so the risk is limited to log aggregator exposure.

### 8. Telegram PII

**`server/middleware/telegram.js:97`:**
```js
console.log(`[Telegram] Validated user: ${user.first_name} (ID: ${user.id})`);
```

`user.first_name` is a Telegram display name and `user.id` is a Telegram numeric user ID. Both constitute PII under GDPR. They appear in server logs on every successful Telegram validation. If server logs are shipped to a third-party aggregator, this is inadvertent PII transfer.

### 9. Treasury/Ops Wallet Addresses at Startup

**`server/services/escrow.js:85-86`:**
```js
console.log(`[Escrow] Treasury: ${TREASURY_WALLET || 'NOT SET'}`);
console.log(`[Escrow] Ops: ${OPS_WALLET || 'NOT SET'}`);
```

Treasury and ops wallet addresses are logged to stdout at server startup. These are not secrets (they are also embedded as program accounts on-chain), but their presence in log aggregators creates an unnecessary operational reconnaissance surface.

## Severity Assessment

**MEDIUM.** This is classified medium rather than high for the following reasons:

1. **No private keys are logged.** The investigation found no log call that emits private key material, seed phrases, raw keypair bytes, or JWT secret values. The escrow keypair `publicKey` is logged, which is correct and acceptable.

2. **No wallet addresses appear in normal execution paths.** The two wallet-address console.error calls in `shot-token.js` are on MongoDB error paths that fire only on DB failures, not on every request.

3. **Financial data in settlement logs is real but not novel.** The settlement amounts and transaction signatures are visible on-chain; they are not secrets. However, an unstructured console.log is the wrong channel for this data — it cannot be filtered, structured, or redaction-protected by any downstream tooling.

4. **The pino config is not broken — it is underused.** The redaction paths and field names are correctly specified for structured object logging. The problem is coverage, not correctness.

The MEDIUM rating reflects that this is primarily an observability and operational integrity issue rather than a direct exploit path. In combination with a log aggregator compromise, an insider threat, or a side-channel attack on logging infrastructure, the unstructured financial data streams become more significant.

## Recommendations

### Priority 1 — Remove per-shot debug logs (main.js:1932, 1944)

Gate behind `LOG_LEVEL === 'debug'` or remove entirely:

```js
// Before:
console.log('[Fire] tanks:', tanks.map(t => ({ id: t.id.slice(0,8), x: Math.round(t.x), y: Math.round(t.y) })))

// After:
if (process.env.LOG_LEVEL === 'debug') {
    logger.debug({ tanks: tanks.map(t => ({ id: t.id.slice(0,8), x: Math.round(t.x), y: Math.round(t.y) })) }, '[Fire] tanks');
}
```

This removes ~40 unconditional log lines per match and also routes any retained debug output through the structured pipeline.

### Priority 2 — Migrate settlement logs to structured logger (main.js:2119, main.js:662)

```js
// Before (main.js:2119):
console.log('[Solana] Match settled:', settlementInfo)

// After:
logger.info({
    wager: settlementInfo.wager,
    totalPot: settlementInfo.totalPot,
    winnerPayout: settlementInfo.winnerPayout,
    treasuryFee: settlementInfo.treasuryFee,
    opsFee: settlementInfo.opsFee,
    txSignature: settlementInfo.txSignature,
}, '[Solana] Match settled');
```

```js
// Before (main.js:662):
console.log(`[Solana] Forfeit settlement (${reason}):`, settlementResult)

// After:
logger.info({
    reason,
    wager: settlementResult.settlement?.winner,
    txSignature: settlementResult.txSignature,
}, '[Solana] Forfeit settlement');
```

This routes financial data through the structured JSON pipeline, makes it queryable by log aggregators, and subjects it to pino's log-level gating.

### Priority 3 — Fix wallet-address string interpolation (shot-token.js:184, 222)

Pino redaction cannot intercept string interpolation. Migrate to structured calls:

```js
// Before:
console.error(`[SHOT] Failed to load milestone state for ${walletAddress}:`, err.message);

// After:
logger.error({ walletAddress, err: err.message }, '[SHOT] Failed to load milestone state');
```

The field name `walletAddress` is in the pino redact list, so it will be censored to `[REDACTED]` in the structured output. This is the correct pattern for the redaction to take effect.

### Priority 4 — Remove SOL balance from client error strings (main.js:986, 1141)

```js
// Before:
reason: `Insufficient SOL balance. Need ${balanceCheck.required.toFixed(3)}, have ${balanceCheck.balance.toFixed(3)}`

// After:
reason: 'Insufficient SOL balance'
```

The client's wallet adapter can display the user's own balance. The server confirming the exact balance figure in a socket error response is unnecessary.

### Priority 5 — Remove Telegram PII from logs (telegram.js:97)

```js
// Before:
console.log(`[Telegram] Validated user: ${user.first_name} (ID: ${user.id})`);

// After:
logger.info('[Telegram] User validated');
```

A success/failure counter is sufficient for operational monitoring. The display name and user ID should not appear in server logs.

### Priority 6 — Change uncaughtException handler to log message only (index.js:178)

```js
// Before:
console.error('[FATAL] Uncaught exception:', err);

// After:
logger.fatal({ err: err.message, stack: err.stack }, '[FATAL] Uncaught exception');
```

Using `logger.fatal` routes through pino's structured pipeline and makes the stack trace a named field rather than serialized inline text. This also enables log-level filtering if a deployment sets `LOG_LEVEL=error` (fatal > error).

### Priority 7 — Set LOG_LEVEL in production deployment

Ensure `LOG_LEVEL=warn` is configured in production. This suppresses all `logger.info` output (match stats, auth confirmations) that is useful in development but adds noise in production. This requires Priority 1 (debug gates) to be in place first, since the per-shot `console.log` calls currently ignore `LOG_LEVEL` entirely.

## Non-Findings

- **No private keys logged.** The escrow keypair private bytes, JWT secret value, and MongoDB credentials do not appear in any log call. Only the escrow public key is logged at startup, which is correct.
- **Client console.log calls are out of scope.** `WalletContext.js` and `BattleScreen.js` log transaction signatures and auth status to the browser console. Transaction signatures are already public on-chain; this is expected browser debugging behavior with no security impact.
- **The pino redact configuration is technically correct.** The field name list (`walletAddress`, `wallet`, `winner`, `loser`, etc.) accurately covers the object fields used in structured logger calls. The issue is scope of adoption, not configuration correctness.
