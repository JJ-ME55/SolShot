# H041 — Timing-Unsafe Secret Comparisons (HMAC and Admin Key)

**Hypothesis:** HMAC comparison uses `===` instead of `crypto.timingSafeEqual()`, enabling
timing side-channel.

**Verdict:** CONFIRMED — TWO independent instances found in different middleware files,
protecting different attack surfaces. Neither uses constant-time comparison.

**Severity:** HIGH

**Auditor:** Dinh's Bulwark — Hypothesis Investigator
**Date:** 2026-02-23

---

## Summary

Two distinct timing-unsafe comparisons exist in the server middleware layer. Both compare
secret-derived values using JavaScript's `===` operator, which is a short-circuit string
comparison and leaks information about the expected value through response timing.

| # | File | Line | What is Compared | Attack Surface |
|---|------|------|-----------------|----------------|
| 1 | `server/middleware/telegram.js` | 53 | HMAC-SHA256 digest (hex string) vs. client-supplied hash | Socket.IO handshake (external, unauthenticated) |
| 2 | `server/middleware/guards.js` | 27 | `ADMIN_API_KEY` env var vs. HTTP header value | HTTP endpoints (external, unauthenticated) |

A third comparison (`auth.js:77`, `message !== expected`) was examined and is **NOT a
vulnerability** — it compares a public-knowledge message template against client input and
reveals nothing secret.

## Instance 1: Telegram HMAC Comparison

**File:** `server/middleware/telegram.js:53`

```javascript
// server/middleware/telegram.js:41-53
const secretKey = crypto
    .createHmac('sha256', 'WebAppData')
    .update(botToken)
    .digest();

const computedHash = crypto
    .createHmac('sha256', secretKey)
    .update(dataCheckString)
    .digest('hex');

const valid = computedHash === hash;   // <-- TIMING-UNSAFE
```

### What it protects

This HMAC validates the `telegramInitData` payload passed in `socket.handshake.auth.telegramInitData`
on every incoming Socket.IO connection. The HMAC is computed from the Telegram bot token
using the two-step derivation specified in the Telegram Mini App documentation. The `hash`
parameter is the client-supplied value to be verified.

### Exposure to external requests

The comparison runs inside `telegramSocketMiddleware`, which is registered as a Socket.IO
`io.use()` middleware. It runs on **every incoming WebSocket connection** regardless of
whether the client is a Telegram user:

```javascript
// server/middleware/telegram.js:84-105
function telegramSocketMiddleware(socket, next) {
    const initData = socket.handshake.auth?.telegramInitData;

    if (!initData) {
        // Not a Telegram connection — proceed normally
        return next();
    }

    const { valid, user } = validateTelegramInitData(initData);
    // ...
    return next();  // Always proceeds regardless of valid/invalid
}
```

Any external attacker who can open a WebSocket connection and supply
`telegramInitData` in the handshake auth object can reach this comparison. The rate
limit on HTTP does not apply to WebSocket connections; there is no per-connection rate
limit on Socket.IO connections beyond the IP-level connection count cap.

### Timing oracle mechanism

JavaScript `===` on strings performs a byte-by-byte comparison and short-circuits on the
first mismatched character. The server response timing (or the delay before the `next()`
callback propagates) will vary based on how many leading bytes of the submitted hash match
the HMAC value computed from the real bot token. The target secret leakable is the
`computedHash` — a 64-character hex string (256-bit HMAC-SHA256). An attacker who can
submit crafted `hash` values and measure response latency can reconstruct this oracle.

**Note on practical exploitability:** The HMAC output changes each time `dataCheckString`
changes (which includes `auth_date` and other fields). An attacker cannot hold the
`dataCheckString` constant across multiple probing requests while varying only the `hash`
prefix, because the `auth_date` staleness check (24-hour window at line 68) limits but
does not prevent a fixed-payload attack within the window. The most practical attack is
against the second instance (admin key) which has no such complication.

### Impact if bot token is leaked

If an attacker reconstructs the `computedHash` for a fixed `dataCheckString`, they only
learn the HMAC output for that specific input — not the bot token itself. However, the
bot token is the actual secret, and this HMAC oracle is one step removed from it. The
primary risk is that the comparison **should** be constant-time as defense in depth and
for compliance with standard cryptographic practice.

## Instance 2: Admin API Key Comparison

**File:** `server/middleware/guards.js:25-31`

```javascript
export function requireAdminKey(req, res, next) {
    const apiKey = req.headers['x-admin-key'];
    if (!process.env.ADMIN_API_KEY || apiKey !== process.env.ADMIN_API_KEY) {  // <-- TIMING-UNSAFE
        return res.status(401).json({ error: 'Unauthorized' });
    }
    next();
}
```

### What it protects

`requireAdminKey` guards two endpoints registered in `server/index.js`:

```javascript
// server/index.js:121, 124
app.get('/stats', requireAdminKey, getStats)
app.post('/api/admin/reload-keys', requireAdminKey, (req, res) => { ... })
```

- **`GET /stats`** — Returns detailed operational data: active connections, match counts,
  total SOL wagered, total SOL settled, treasury fees, ops fees, SHOT token emission
  totals, and the last 5 server errors.
- **`POST /api/admin/reload-keys`** — Reloads the server's Solana authority keypair from
  disk/environment. On Linux/Render it sends `SIGHUP` to the process; on Windows it calls
  `initKeys()` and `initEscrow()` directly.

### Why this instance is higher risk

Unlike the Telegram HMAC, the admin key comparison is a **direct comparison of the raw
secret value** (`process.env.ADMIN_API_KEY`) against a client-supplied string. The target
of the timing oracle is the secret itself, not a derived value.

An attacker making automated requests to `GET /stats` with progressively longer matching
prefixes can recover `ADMIN_API_KEY` character by character. Once the key is known:

1. `/stats` exposes real-time financial data (SOL flow, wager volumes, error backtraces)
   useful for timing attacks against match settlement.
2. `POST /api/admin/reload-keys` can force a keypair reload, potentially disrupting
   in-flight escrow operations or, if combined with a keypair file substitution attack,
   redirecting escrow authority to an attacker-controlled key.

The express-rate-limit middleware (`100 req / 15 min per IP`) is applied globally. This
slows brute-force but does not prevent a timing attack: a timing attack requires far fewer
requests (on the order of `96 * key_length` for a hex key, not an exhaustive search).
With a typical `ADMIN_API_KEY` of 32-64 hex characters, reconstruction requires roughly
3,000 to 6,000 requests — achievable in ~45 minutes under the current rate limit from a
single IP, or faster from multiple IPs.

## Proof-of-Concept Attack (Admin Key)

The following pseudocode illustrates a timing oracle against `GET /stats`:

```
known_prefix = ""
charset = "0123456789abcdefghijklmnopqrstuvwxyzABCDEFGHIJKLMNOPQRSTUVWXYZ-_"

for position in range(key_length):
    timings = {}
    for char in charset:
        candidate = known_prefix + char + "A" * (key_length - position - 1)
        t_start = high_resolution_clock()
        GET /stats  with header  x-admin-key: candidate
        t_end = high_resolution_clock()
        timings[char] = t_end - t_start
    known_prefix += argmax(timings)

# known_prefix now equals ADMIN_API_KEY
```

JavaScript's V8 engine typically processes short-circuit string comparison in nanoseconds
per character. Timing measurement over HTTP introduces jitter (network, OS scheduling)
but with sufficient samples per candidate character, the signal emerges. Tools like
`timing-attack` (npm) automate this with statistical noise reduction.

## Recommendations

### Fix 1: Telegram HMAC — telegram.js:53

Replace the direct string equality with `crypto.timingSafeEqual`. Length must be
validated first, since `timingSafeEqual` throws a `RangeError` on buffers of different
lengths (which would itself leak information via the exception path).

```javascript
// Before
const valid = computedHash === hash;

// After
if (typeof hash !== 'string' || !/^[0-9a-f]{64}$/i.test(hash)) {
    return { valid: false, user: null };
}
const valid = crypto.timingSafeEqual(
    Buffer.from(computedHash, 'hex'),
    Buffer.from(hash, 'hex')
);
```

The regex validates that `hash` is exactly 64 lowercase hex characters (the format of an
HMAC-SHA256 hex digest) before the constant-time comparison. This prevents a thrown
`RangeError` from leaking via the exception path when `hash` is a different length.

### Fix 2: Admin Key — guards.js:27

```javascript
// Before
export function requireAdminKey(req, res, next) {
    const apiKey = req.headers['x-admin-key'];
    if (!process.env.ADMIN_API_KEY || apiKey !== process.env.ADMIN_API_KEY) {
        return res.status(401).json({ error: 'Unauthorized' });
    }
    next();
}

// After
import crypto from 'crypto';

export function requireAdminKey(req, res, next) {
    const expected = process.env.ADMIN_API_KEY;
    const provided = req.headers['x-admin-key'];

    if (!expected || !provided) {
        return res.status(401).json({ error: 'Unauthorized' });
    }

    // timingSafeEqual requires equal-length buffers.
    // Convert both to fixed-length Buffers; if lengths differ, comparison
    // must still take constant time — pad the shorter one to match.
    const a = Buffer.from(provided, 'utf8');
    const b = Buffer.from(expected, 'utf8');

    if (a.length !== b.length) {
        // Length mismatch is observable but cannot be avoided; padding leaks nothing
        // beyond "wrong length", which is benign compared to prefix oracle.
        return res.status(401).json({ error: 'Unauthorized' });
    }

    if (!crypto.timingSafeEqual(a, b)) {
        return res.status(401).json({ error: 'Unauthorized' });
    }

    next();
}
```

**Note on length-check early return:** Returning early on length mismatch reveals that
the submitted key has the wrong length — but this is a minor information leak compared to
the character-prefix oracle that `===` enables. Alternatively, both buffers can be padded
to a fixed maximum length before comparison, which eliminates even the length oracle:

```javascript
const MAX_KEY_LEN = 128;
const a = Buffer.alloc(MAX_KEY_LEN);
const b = Buffer.alloc(MAX_KEY_LEN);
Buffer.from(provided || '', 'utf8').copy(a);
Buffer.from(expected || '', 'utf8').copy(b);
if (!crypto.timingSafeEqual(a, b)) {
    return res.status(401).json({ error: 'Unauthorized' });
}
```

This form is fully constant-time regardless of input lengths.

### Fix 3: Operational — strengthen rate limiting on admin endpoints

While fixing the timing comparison is the primary remediation, adding a tighter rate
limit specifically on the `/stats` and `/api/admin/reload-keys` endpoints reduces
the window for any remaining timing attacks:

```javascript
const adminLimiter = rateLimit({
    windowMs: 60 * 1000,   // 1 minute
    max: 10,                // 10 requests per minute per IP
    standardHeaders: true,
    legacyHeaders: false,
});
app.get('/stats', adminLimiter, requireAdminKey, getStats);
app.post('/api/admin/reload-keys', adminLimiter, requireAdminKey, ...);
```

## Contextual Notes

- The DATA-05 auditor (context file `15-data-05-encryption.md`) correctly identified both
  vulnerabilities as `DATA-05-W3` (telegram.js) and `DATA-05-W8` (guards.js), both rated
  HIGH. This investigation independently confirms both findings through direct source
  examination.

- The ARCHITECTURE.md pre-synthesis correctly listed `H-22` ("Timing-unsafe HMAC
  comparison in telegram.js") as a HIGH finding, with 2-auditor convergence. The admin
  key comparison in guards.js was flagged by DATA-05 only, with lower convergence —
  but is arguably the higher-risk instance because it directly exposes the raw secret.

- There is no HTTP webhook endpoint for Telegram in this codebase. The ARCHITECTURE.md
  entry (`/api/telegram/webhook`) does not correspond to any registered route in
  `server/index.js`. The Telegram validation runs only in Socket.IO connection middleware.
  This reduces the Telegram HMAC risk slightly (Socket.IO handshake is harder to automate
  at scale than raw HTTP), but does not eliminate it.

- The `nacl.sign.detached.verify` function used for wallet signature verification in
  `auth.js` uses tweetnacl's internal constant-time comparison for the Ed25519 verification
  step. This is NOT affected by H041.
