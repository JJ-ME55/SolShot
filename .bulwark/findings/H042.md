# H042 — Deprecated `confirmTransaction` Reliability Failure

**Status:** CONFIRMED (SPLIT SCOPE)
**Severity:** HIGH (client-side) / NOT PRESENT (server-side)
**Confidence:** HIGH
**Origin:** Hypothesis investigation
**Files:** `client/src/wallet/WalletContext.js` (lines 234, 280–289), `server/services/escrow.js`, `server/services/solana.js`

---

## Summary

The hypothesis is **confirmed for client-side code and not present on the server side.** The deprecated `connection.confirmTransaction(signature, commitment)` overload — the legacy signature-string form — is used in exactly two places in `client/src/wallet/WalletContext.js` (lines 234 and 288). Neither `server/services/escrow.js` nor `server/services/solana.js` calls `confirmTransaction` at all; those files delegate all transaction confirmation to the Anchor provider's `.rpc()` method, which handles confirmation internally.

The two client-side usages affect distinct financial flows:

- **Line 234:** Escrow deposit confirmation in `signAndSendEscrowDeposit`
- **Line 288:** SHOT token burn confirmation in `signAndBurnShot`

Both calls use the deprecated single-argument form. Neither captures `lastValidBlockHeight`. Neither has a timeout or abort signal. The combination of these three gaps means that on a slow or congested RPC connection, both confirmation calls can silently hang indefinitely or return a false result.

---

## Evidence

### Where `confirmTransaction` is NOT present (server side)

**`server/services/escrow.js`** — grep returns zero matches for `confirmTransaction`. All server-signed instructions (`createMatch`, `settleMatch`, `cancelMatch`, `permissionlessReclaim`) are submitted via Anchor's `.rpc()`:

```js
// escrow.js:293-301 (createMatchEscrow)
const tx = await program.methods
    .createMatch(matchId, new BN(wagerLamports), playerOne, playerTwo)
    .accounts({ ... })
    .rpc();
```

Anchor's `.rpc()` internally fetches a fresh blockhash, signs the transaction with the configured `Wallet`, submits it, and waits for confirmation at the provider's configured commitment level (`'confirmed'` at line 72–74 of `escrow.js`). Anchor manages blockhash expiry internally per call. This is the correct modern pattern and is not vulnerable.

**`server/services/solana.js`** — grep also returns zero matches for `confirmTransaction`. Settlement and refund operations all delegate to `escrow.js` helpers that use Anchor `.rpc()`. Balance checks use `conn.getBalance()` without any confirmation step (no transaction is submitted here).

The server-side scope of H042 is **NOT VULNERABLE**.

### Where `confirmTransaction` IS present (client side)

**`client/src/wallet/WalletContext.js` — line 234** (escrow deposit flow):

```js
// signAndSendEscrowDeposit (lines 202–251)
const signature = await sendTransaction(tx, connection);
console.log('[SolShot] Escrow deposit TX sent:', signature);

// Confirm
await connection.confirmTransaction(signature, 'confirmed');  // <-- DEPRECATED FORM
console.log('[SolShot] Escrow deposit confirmed:', signature);

// Notify server
const socket = window.socket;
if (socket) {
    socket.emit('escrowDepositConfirm', { roomId, txSignature: signature });
}
```

The `tx` object passed to `sendTransaction` was built server-side via `buildDepositTransaction`, which correctly captures both `blockhash` and `lastValidBlockHeight` (see `escrow.js:348`). However, the client deserializes only the transaction bytes:

```js
// lines 211–212
const txBuffer = Buffer.from(serializedTxBase64, 'base64');
const tx = Transaction.from(txBuffer);
```

The `lastValidBlockHeight` is encoded in the transaction's `Transaction` constructor fields on the server side but is not surfaced as a standalone value in the socket event payload. The client has no way to pass `lastValidBlockHeight` to `confirmTransaction` without the server explicitly sending it alongside the base64 transaction string.

The call at line 234 therefore resolves to the legacy overload signature:

```
confirmTransaction(signature: TransactionSignature, commitment?: Commitment): Promise<RpcResponseAndContext<SignatureResult>>
```

This is the overload documented as deprecated in `@solana/web3.js`. It does not accept a `TransactionConfirmationStrategy` object and therefore cannot use `lastValidBlockHeight` to detect transaction expiry.

**`client/src/wallet/WalletContext.js` — line 280–289** (SHOT burn flow):

```js
// signAndBurnShot (lines 254–296)
const tx = new Transaction().add(burnIx);
tx.feePayer = publicKey;
const { blockhash } = await connection.getLatestBlockhash();  // lastValidBlockHeight DISCARDED
tx.recentBlockhash = blockhash;

const signature = await sendTransaction(tx, connection);
console.log('[SolShot] SHOT burn TX sent:', signature);

// Confirm
await connection.confirmTransaction(signature, 'confirmed');  // <-- DEPRECATED FORM
```

Here the problem is compounded: `getLatestBlockhash()` returns `{ blockhash, lastValidBlockHeight }` but the destructuring discards `lastValidBlockHeight` entirely. The transaction has a defined blockhash but the confirmation step has no mechanism to detect expiry even if the code were refactored to use the modern strategy overload, because `lastValidBlockHeight` was thrown away.

## Technical Explanation of the Deprecated Overload's Failure Modes

The `@solana/web3.js` `Connection.confirmTransaction` method has two overloads:

**Legacy (deprecated):**
```ts
confirmTransaction(signature: string, commitment?: Commitment): Promise<...>
```
This overload polls the RPC for the signature's confirmation status in a loop. It has no concept of transaction expiry. If the transaction is dropped (the leader never received it, or the blockhash expired), the poller continues indefinitely waiting for a status that will never arrive. The behavior on timeout is implementation-defined per RPC node — some nodes return an error after a period, others hang.

**Modern (correct):**
```ts
confirmTransaction(strategy: TransactionConfirmationStrategy, commitment?: Commitment): Promise<...>
```
where `TransactionConfirmationStrategy` is:
```ts
{ signature: string, blockhash: string, lastValidBlockHeight: number }
```
This overload polls for confirmation but also watches the current block height. When the chain's block height exceeds `lastValidBlockHeight` (approximately 150 slots after the blockhash was fetched), the confirmation call terminates with a `TransactionExpiredBlockheightExceededError`. This provides a deterministic timeout bound: the caller can distinguish "dropped transaction" from "pending transaction" and take appropriate action (e.g., rebuild with a fresh blockhash and retry).

## Failure Modes in SolShot Context

### Failure Mode 1: Escrow Deposit — Indefinite Client Hang

If the escrow deposit transaction is dropped (network congestion, leader skip, devnet instability), `connection.confirmTransaction(signature, 'confirmed')` at line 234 enters an indefinite polling loop. The client's `signAndSendEscrowDeposit` function never returns. The React component state is frozen on a "depositing..." UI. The user has no feedback and no timeout. They cannot proceed to the match.

The server's 2-minute deposit timeout (`DEPOSIT_TIMEOUT_MS = 120_000` in `main.js:56`) will eventually fire, cancel the escrow, and remove the room. The user's deposited SOL (if the TX was actually confirmed but the poll failed to detect it) may be locked in the escrow PDA until the cancel instruction executes. This is a liveness failure, not a fund-loss path, because the cancel refunds the depositor.

However, because the legacy `confirmTransaction` does not detect expiry, there is also a false-positive scenario: the TX is dropped and the signature is never finalized, but if the RPC node does not return a definitive error, the poll may resolve with `null` (unconfirmed) rather than throwing. In that case, `await connection.confirmTransaction(...)` returns without throwing, and the code proceeds to emit `escrowDepositConfirm` with a signature that was never on-chain. The server's `getEscrowState` verification (with its single 2-second retry) then becomes the only backstop. This is relevant to H023 (insufficient retry logic) as a compounding factor.

### Failure Mode 2: SHOT Burn — False-Positive Burn Confirmation

If the SHOT burn transaction is dropped, the same indefinite hang applies at line 288. When the hang resolves (either by RPC error or by the client navigating away), the signature may be for a transaction that was never finalized.

In this case the server's `verifyBurnTransaction` in `shot-token.js` calls `getParsedTransaction(txSignature, { commitment: 'confirmed' })` and would correctly find no transaction, returning `{ valid: false }`, and the prestige upgrade would be rejected. The server's on-chain re-verification is the backstop here.

The user experience consequence is: the client's burn flow shows "burn confirmed" (because `confirmTransaction` returned without error), the `prestigeBurn` socket event is emitted, but the server rejects it. The user believes they burned SHOT but their tier did not advance. They may retry with the same (invalid) signature (replay-protection Set would still allow it since it was never added), discover no tier advancement, and lose trust in the system.

### Failure Mode 3: No AbortController / Promise.race

Neither confirmation call uses `Promise.race` with a timeout or an `AbortController`. On an unresponsive RPC node, both calls can hang for minutes or indefinitely. The SHOT burn flow would leave the user on a non-dismissible "burning..." modal indefinitely. The escrow deposit flow would block the match from starting indefinitely on the client side.

---

## Severity Assessment

**HIGH**, not CRITICAL.

The on-chain verification in `server/socket-io/main.js` (`getEscrowState` check in `escrowDepositConfirm` handler) and `verifyBurnTransaction` in `shot-token.js` serve as backstops that prevent the deprecated confirmation from causing direct fund loss. However:

1. The liveness failure (indefinite hang) is user-facing and severe, especially for the escrow deposit — it can stall a wagered match indefinitely.
2. The false-positive confirmation case (compounding with H023's insufficient retry) creates a real path where the server accepts a deposit confirmation for a transaction that may never be on-chain, then proceeds to match start before the escrow is actually funded.
3. The SHOT burn false-positive creates a confusing UX where the client says "success" but the server rejects the upgrade.
4. The server-side is clean (Anchor `.rpc()` handles confirmation correctly), so remediation scope is bounded to the client.

## Recommendations

### Recommendation 1: Use the Modern `TransactionConfirmationStrategy` Overload

The server must send `lastValidBlockHeight` alongside the serialized transaction in the `escrowDeposit` socket event so the client can use it:

**`server/services/escrow.js` — `buildDepositTransaction`** (already captures it at line 348, just not returned):

```js
// Current (line 348)
const { blockhash, lastValidBlockHeight } = await connection.getLatestBlockhash();

// Already captured — add to return value:
return {
    success: true,
    transaction: serialized,
    escrowPDA: escrowPDA.toBase58(),
    lastValidBlockHeight,   // ADD THIS
};
```

**`client/src/wallet/WalletContext.js` — `signAndSendEscrowDeposit`:**

```js
// The event payload from server now includes lastValidBlockHeight
// Signature from sendTransaction, blockhash from the deserialized tx:
const { blockhash } = tx;  // already set on the Transaction object
const confirmResult = await connection.confirmTransaction(
    { signature, blockhash, lastValidBlockHeight },
    'confirmed'
);
if (confirmResult.value.err) {
    throw new Error('Deposit transaction failed: ' + JSON.stringify(confirmResult.value.err));
}
```

### Recommendation 2: Fix the SHOT Burn Flow — Capture `lastValidBlockHeight`

```js
// signAndBurnShot — replace line 280:
const { blockhash, lastValidBlockHeight } = await connection.getLatestBlockhash();
tx.recentBlockhash = blockhash;

const signature = await sendTransaction(tx, connection);

const confirmResult = await connection.confirmTransaction(
    { signature, blockhash, lastValidBlockHeight },
    'confirmed'
);
if (confirmResult.value.err) {
    throw new Error('Burn transaction failed: ' + JSON.stringify(confirmResult.value.err));
}
```

### Recommendation 3: Add a Hard Timeout via `Promise.race`

Until the strategy overload is adopted (which provides a block-height-based timeout), add a wall-clock timeout to prevent indefinite hangs:

```js
const CONFIRM_TIMEOUT_MS = 60_000;

const confirmWithTimeout = (connection, signature, commitment) =>
    Promise.race([
        connection.confirmTransaction(signature, commitment),
        new Promise((_, reject) =>
            setTimeout(() => reject(new Error('Transaction confirmation timeout')), CONFIRM_TIMEOUT_MS)
        ),
    ]);

// Replace both calls:
await confirmWithTimeout(connection, signature, 'confirmed');
```

This is a stopgap. The strategy overload (Recommendations 1 and 2) is the correct long-term fix.

### Recommendation 4: Handle `TransactionExpiredBlockheightExceededError`

When using the strategy overload, catch the expiry error explicitly and surface it to the user:

```js
import { TransactionExpiredBlockheightExceededError } from '@solana/web3.js';

try {
    await connection.confirmTransaction({ signature, blockhash, lastValidBlockHeight }, 'confirmed');
} catch (err) {
    if (err instanceof TransactionExpiredBlockheightExceededError) {
        // Transaction was dropped — safe to retry with a fresh blockhash
        console.warn('[SolShot] Transaction expired, may retry');
        // Emit a user-facing error rather than silently proceeding
    }
    throw err;
}
```
