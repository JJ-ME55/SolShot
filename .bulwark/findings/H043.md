# H043 — Blockhash Expiry Transaction Stalling

**Hypothesis:** Transactions constructed with stale blockhash that may expire before submission during RPC congestion.
**Target:** `server/services/escrow.js` (transaction construction); `client/src/wallet/WalletContext.js` (confirmation)
**Severity:** MEDIUM
**Status:** CONFIRMED (two distinct sub-issues; no single path to direct fund loss but confirmed liveness failures)

---

## Summary

The deposit transaction has a split-responsibility design: the server builds and serializes the transaction (capturing the blockhash), then the client signs and submits it later. This creates a time gap between blockhash fetch and actual submission. Additionally, the client uses the deprecated `confirmTransaction(signature, commitment)` overload that discards `lastValidBlockHeight` and cannot detect blockhash expiry on the confirmation side. Together these produce two confirmed liveness failure modes: (1) a late-signing player receives a `BlockhashNotFound` rejection with no recovery path, and (2) a dropped transaction cannot be distinguished from a slow one, leaving the client hung indefinitely.

The server-signed instructions (`createMatch`, `settleMatch`, `cancelMatch`) are NOT affected — Anchor's `.rpc()` fetches a fresh blockhash immediately before signing and submission. The vulnerability is isolated to the client-signed `depositWager` path.

---

## Evidence

### Path 1: Server builds TX, client signs up to 120 seconds later

**File:** `server/services/escrow.js`, lines 347–371

```js
// escrow.js:347-361
const connection = provider.connection;
const { blockhash, lastValidBlockHeight } = await connection.getLatestBlockhash();

const tx = new Transaction({
    blockhash,
    lastValidBlockHeight,
    feePayer: player,
});
tx.add(ix);

const serialized = tx.serialize({
    requireAllSignatures: false,
    verifySignatures: false,
}).toString('base64');

return { success: true, transaction: serialized, escrowPDA: escrowPDA.toBase58() };
```

The server correctly calls `getLatestBlockhash()` and captures both `blockhash` and `lastValidBlockHeight`. These are baked into the serialized transaction wire format. So far this is correct.

**File:** `server/socket-io/main.js`, line 56

```js
const DEPOSIT_TIMEOUT_MS = 120_000  // 2 minutes — litepaper escrow flow
```

The deposit window is 120 seconds. Solana blockhashes are valid for approximately 150 slots. On mainnet at ~400 ms/slot that is ~60 seconds; on devnet (which runs slower and is used here) the slot rate varies but is generally 400–600 ms, giving 60–90 seconds of blockhash validity. The 120-second timeout therefore exceeds the expected blockhash lifetime by 30–60 seconds.

The serialized transaction is emitted to the client socket immediately after `buildDepositTransaction` completes (lines 1040–1057). The client may not act on it immediately: the user must read the UI, decide to approve, and click through the wallet's signing dialog. Any user who takes more than ~60–90 seconds to sign receives a `BlockhashNotFound` rejection from the validator when `sendTransaction` is called.

**No refresh mechanism exists.** When the TX is rejected:

1. `sendTransaction` throws in `signAndSendEscrowDeposit` (WalletContext.js line 230).
2. The catch block at line 247 logs the error and returns `null`.
3. No `escrowDepositConfirm` is emitted to the server.
4. The deposit timer continues running until it fires at 120 seconds from room join.
5. The server calls `cancelMatchEscrow`, which refunds any already-deposited opponent and emits `escrowDepositTimeout` to both clients, tearing down the room.

The affected player has no indication that their transaction expired (they see a generic wallet error), no way to request a fresh version of the TX, and no retry button. The match is cancelled.

The `depositDeadlineMs` is transmitted to clients (lines 1046, 1055) but it reflects the server's 120-second timeout, not the shorter blockhash expiry — so the UI countdown does not warn users that TX signing must complete within ~60–90 seconds, only within 2 minutes.

### Path 2: Deprecated `confirmTransaction` overload discards expiry information

**File:** `client/src/wallet/WalletContext.js`, lines 230–234

```js
// signAndSendEscrowDeposit
const signature = await sendTransaction(tx, connection);
console.log('[SolShot] Escrow deposit TX sent:', signature);

// Confirm
await connection.confirmTransaction(signature, 'confirmed');
```

**File:** `client/src/wallet/WalletContext.js`, lines 284–288 (SHOT burn path, same pattern)

```js
const signature = await sendTransaction(tx, connection);
// ...
await connection.confirmTransaction(signature, 'confirmed');
```

The `connection.confirmTransaction(signature, commitment)` two-argument overload is the legacy form deprecated in `@solana/web3.js`. It subscribes to a signature notification without a blockhash-based expiry bound.

The consequences are:

- **If the TX is dropped** (validator did not receive it due to congestion, leader skip, or RPC queue overflow), the legacy overload has no way to know the transaction can never be confirmed because its blockhash has expired. Depending on the RPC implementation, it may either hang indefinitely or eventually return a timeout error after a very long wait (~30–60 seconds for some RPC providers).

- **No actionable error.** When the overload times out or errors, the catch block at line 247 returns `null` silently. The user gets no feedback, and no `escrowDepositConfirm` is ever sent. The deposit timer runs out and the match is cancelled.

- **No hang protection.** There is no `AbortController`, `Promise.race`, or explicit timeout wrapping the `confirmTransaction` call. A hung RPC subscription keeps the React component in an indefinite loading state until the user navigates away.

The modern strategy-object overload requires the `lastValidBlockHeight` from the original `getLatestBlockhash` call:

```js
await connection.confirmTransaction(
    { signature, blockhash, lastValidBlockHeight },
    'confirmed'
);
```

This overload returns a `TransactionExpiredBlockheightExceededError` as soon as the block height passes `lastValidBlockHeight`, allowing the client to handle expiry explicitly and potentially prompt the user to retry.

The `lastValidBlockHeight` is present in the serialized transaction bytes (it was set on the `Transaction` constructor on the server). However, `Transaction.from(buffer)` on the client does not surface `lastValidBlockHeight` as a standalone property; it is encoded in the wire format but not re-exposed by the SDK. The correct fix requires the server to include `lastValidBlockHeight` explicitly in the `escrowDeposit` socket event payload.

### Path 3: Server-signed transactions are NOT affected

**File:** `server/services/escrow.js`, lines 400–411 (`settleMatchEscrow`), lines 446–456 (`cancelMatchEscrow`), lines 293–301 (`createMatchEscrow`)

All three server-signed instructions use Anchor's `.rpc()` method:

```js
const tx = await program.methods
    .settleMatch(winner)
    .accounts({ ... })
    .rpc();
```

Anchor's `AnchorProvider.sendAndConfirm()` (called internally by `.rpc()`) fetches a fresh blockhash from the provider's connection immediately before signing and submitting the transaction. The blockhash is fetched per-call, so there is no stale-blockhash window. This path is not vulnerable.

### Path 4: `buildDepositTransaction` called twice concurrently (parallel fetch)

**File:** `server/socket-io/main.js`, lines 1031–1034

```js
const [hostDeposit, joinerDeposit] = await Promise.all([
    buildDepositTransaction(roomId, hostWallet),
    buildDepositTransaction(roomId, joinerWallet),
])
```

Both `buildDepositTransaction` calls are issued concurrently via `Promise.all`. Each call independently calls `connection.getLatestBlockhash()`. Because RPC blockhash responses are slot-accurate and both calls execute within milliseconds of each other, they will almost always return the same blockhash. This is not a distinct vulnerability — both transactions will have identical expiry windows — but it means there is no advantage from issuing two separate blockhash fetches. A minor observation only.

## Impact Assessment

**Severity: MEDIUM**

There is no path to direct fund loss from either sub-issue:

- If a deposit TX expires, `sendTransaction` throws and no `escrowDepositConfirm` is ever sent. The server does not credit a deposit that was not confirmed on-chain. The deposit timeout fires and cancels the escrow, refunding any already-deposited player. No funds are created or destroyed incorrectly.

- If `confirmTransaction` hangs (legacy overload on a dropped TX), the client is stuck but no server-side action is taken. The deposit timer will eventually fire and cancel the escrow cleanly.

The impact is **liveness failure**: legitimate players who take more than ~60–90 seconds to sign their deposit transaction have their match silently cancelled with no retry path. This degrades user experience significantly and could cause player churn. On a congested network (devnet is frequently congested), TX dropping makes the hung-confirmation path likely enough to matter in practice.

The CHAIN-01 audit previously catalogued the deprecated-confirm issue (finding C-01) and the blockhash-timeout mismatch (finding C-05) as separate HIGH and MEDIUM findings respectively. This investigation confirms both are real and operationally likely on devnet. The severity here is assessed MEDIUM because no funds are lost and both failures degrade gracefully (match cancelled, players refunded). Were the settlement path to use the same pattern (it does not — Anchor handles it), severity would be CRITICAL.

## Reproduction Scenario

**Blockhash expiry (devnet):**

1. Two players join a wagered room. Server calls `buildDepositTransaction` for each, fetching blockhash at time T=0.
2. Server emits `escrowDeposit` to both clients.
3. Player B's Phantom wallet is slow to respond (extension update, user distracted). Player B clicks "Sign" at T=75 seconds.
4. `sendTransaction` submits the TX to the validator. The blockhash used was fetched 75 seconds ago; on devnet with ~500 ms/slot, 75 seconds = ~150 slots. The blockhash has expired.
5. Validator returns `BlockhashNotFound`. `sendTransaction` throws.
6. `signAndSendEscrowDeposit` returns `null`. No `escrowDepositConfirm` sent.
7. Player A has already deposited. At T=120 the deposit timer fires, `cancelMatchEscrow` is called, Player A is refunded, room is removed.
8. Player B sees a generic wallet error and a "deposit timed out" message. No retry is possible.

**Hung confirmation (network congestion):**

1. Player signs deposit TX at T=10 seconds. `sendTransaction` submits successfully (RPC accepted it).
2. Due to congestion, the TX is dropped by the leader. Signature is never included in a block.
3. `confirmTransaction(signature, 'confirmed')` subscribes to a signature notification. The signature never arrives.
4. After 60 seconds (some RPC providers) or never (others), the confirmation call errors or hangs.
5. If it hangs: the client is stuck in "confirming..." state indefinitely. The 120-second server timer fires and cancels the match while the client still shows a loading screen.
6. Player has no way to determine the match was cancelled or retry the deposit.

## Recommendations

### R1: Reduce deposit timeout to match blockhash lifetime (LOW EFFORT)

Reduce `DEPOSIT_TIMEOUT_MS` from 120 seconds to 60 seconds. This aligns the UI countdown with the actual effective signing window and avoids the false expectation that users have 2 minutes to sign.

**File:** `server/socket-io/main.js`, line 56

```js
// Before:
const DEPOSIT_TIMEOUT_MS = 120_000  // 2 minutes — litepaper escrow flow

// After:
const DEPOSIT_TIMEOUT_MS = 60_000   // 60s — matches Solana blockhash lifetime (~150 slots)
```

### R2: Include `lastValidBlockHeight` in `escrowDeposit` socket event (LOW EFFORT)

Expose `lastValidBlockHeight` from the server so the client can use the modern `confirmTransaction` strategy object.

**File:** `server/services/escrow.js`, `buildDepositTransaction` return value

```js
// escrow.js — add lastValidBlockHeight to return payload:
return {
    success: true,
    transaction: serialized,
    escrowPDA: escrowPDA.toBase58(),
    lastValidBlockHeight,   // <-- add this
};
```

**File:** `server/socket-io/main.js` — forward it in the socket event

```js
hostSocket.emit('escrowDeposit', {
    roomId,
    transaction: hostDeposit.transaction,
    escrowPDA: escrowResult.escrowPDA,
    wager: roomWager,
    depositDeadlineMs: depositDeadline,
    lastValidBlockHeight: hostDeposit.lastValidBlockHeight,  // <-- add
})
```

### R3: Upgrade `confirmTransaction` to strategy-object overload (MEDIUM EFFORT)

**File:** `client/src/wallet/WalletContext.js`, `signAndSendEscrowDeposit`

```js
// Before:
const signature = await sendTransaction(tx, connection);
await connection.confirmTransaction(signature, 'confirmed');

// After (requires lastValidBlockHeight from escrowDeposit event):
const signature = await sendTransaction(tx, connection);
const confirmResult = await connection.confirmTransaction(
    {
        signature,
        blockhash: tx.recentBlockhash,
        lastValidBlockHeight,   // received from server in escrowDeposit event
    },
    'confirmed'
);
if (confirmResult.value.err) {
    throw new Error('Deposit transaction failed on-chain: ' + JSON.stringify(confirmResult.value.err));
}
```

Apply the same pattern to `signAndBurnShot` (lines 284–288), where `lastValidBlockHeight` is already available from the `getLatestBlockhash` call at line 280 (just needs to be destructured):

```js
// Before (WalletContext.js:280):
const { blockhash } = await connection.getLatestBlockhash();

// After:
const { blockhash, lastValidBlockHeight } = await connection.getLatestBlockhash();
// ... build and send TX ...
await connection.confirmTransaction(
    { signature, blockhash, lastValidBlockHeight },
    'confirmed'
);
```

### R4: Add confirmation timeout guard (LOW EFFORT)

Wrap `confirmTransaction` in a `Promise.race` with a timeout to prevent indefinite hangs:

```js
const CONFIRM_TIMEOUT_MS = 45_000;

const confirmWithTimeout = (confirmPromise) =>
    Promise.race([
        confirmPromise,
        new Promise((_, reject) =>
            setTimeout(() => reject(new Error('Confirmation timeout after 45s')), CONFIRM_TIMEOUT_MS)
        ),
    ]);

const confirmResult = await confirmWithTimeout(
    connection.confirmTransaction({ signature, blockhash, lastValidBlockHeight }, 'confirmed')
);
```

### R5: Surface blockhash expiry to the user (LOW EFFORT)

Add explicit error handling for `TransactionExpiredBlockheightExceededError` in `signAndSendEscrowDeposit`:

```js
} catch (err) {
    if (err.name === 'TransactionExpiredBlockheightExceededError') {
        console.error('[SolShot] Deposit TX expired — blockhash too old');
        // Optionally: emit a user-visible error event or request a TX refresh
        const socket = window.socket;
        if (socket) socket.emit('depositTxExpired', { roomId });
    } else {
        console.error('[SolShot] Escrow deposit error:', err.message);
    }
    return null;
}
```

## Verdict

**CONFIRMED — MEDIUM severity.** Two distinct blockhash-handling defects exist in the client-signed deposit path:

1. The 120-second deposit window exceeds the ~60–90 second Solana blockhash lifetime, so any user who takes longer than that to sign receives a silent `BlockhashNotFound` failure with no retry path and their match is cancelled.

2. The `confirmTransaction(signature, 'confirmed')` legacy overload cannot detect transaction expiry, leaving the client in an indefinite hang if the TX is dropped during network congestion.

Neither defect allows fund theft or permanent fund loss — the deposit timer and on-chain escrow state machine ensure graceful cancellation. The impact is liveness degradation: legitimate users lose their match entry on congested or slow networks. Fixes are straightforward (R1–R5 above, total engineering effort: 1–2 hours) and should be prioritised before mainnet deployment where congestion is more frequent and consequences (wasted gas fees, lost queue slots) are real.
