# H044 — 2-Second Retry Insufficient for RPC Propagation in Deposit Confirmation

**Hypothesis ID:** H044
**Auditor:** Dinh's Bulwark — Hypothesis Investigator
**Date:** 2026-02-23
**Severity:** HIGH
**Status:** CONFIRMED

---

## Verdict

CONFIRMED. The 2-second single retry in `escrowDepositConfirm` is the **confirmation
delay between attempt 1 and attempt 2 of reading on-chain PDA state** — not a
confirmation timeout on the transaction itself. Two attempts separated by 2 seconds is
insufficient for Solana devnet RPC propagation, which routinely lags 5–15 seconds after
a transaction reaches `confirmed` commitment. When both attempts fail to read the PDA
state, the server emits `escrowError` and returns, stalling the match. The deposit timer
eventually fires after 120 seconds and cancels the escrow, refunding any deposited player.

The hypothesis is partially correct about the mechanism but **wrong about the duplicate
settlement claim**. The stall path does NOT trigger duplicate settlement; it triggers a
liveness failure (match never starts) that terminates with refund. There is no path where
a correctly-settled transaction is later re-settled from this code. However, the
liveness failure itself is a genuine HIGH-severity finding because it freezes real SOL in
the escrow PDA for up to 120 seconds on every devnet RPC hiccup, silently denies the
user any diagnostic feedback about what happened, and — if the deposit timeout cancel
also fails (a separately documented HIGH — EH-F04) — can leave funds frozen until the
48-hour permissionless reclaim window.

---

## Precise Mechanism

### 1. What the 2 seconds actually is

`server/socket-io/main.js`, lines 1742–1748:

```js
// Single retry with 2s delay for devnet confirmation lag
let escrowState = await getEscrowState(rid)          // attempt 1
if (!escrowState) {
    await new Promise(r => setTimeout(r, 2000))       // wait 2 seconds
    escrowState = await getEscrowState(rid)           // attempt 2
}
```

This is NOT a "2-second confirmation timeout on the transaction." It is a **2-second
pause between two identical reads of the on-chain PDA state**. There is no timeout on
the transaction itself at the server side — the server never submits the deposit
transaction (that is done client-side). There is no retry delay after a failed
`getEscrowState` call; 2000ms is the total inter-attempt gap across a maximum of 2
attempts (attempts: 1 immediate + 1 after 2 seconds).

### 2. Why 2 seconds is insufficient

`getEscrowState` calls `program.account.matchEscrow.fetch(escrowPDA)` — an Anchor
account fetch using the provider's connection (initialized in `escrow.js` line 69 at
`confirmed` commitment):

```js
// escrow.js, line 69
const connection = new Connection(SOLANA_RPC, 'confirmed');
```

A transaction at `confirmed` commitment on Solana devnet is acknowledged by a supermajority
of validators. However, the RPC node the server is reading from may not have propagated
that account update within 2 seconds. Solana devnet RPC nodes (especially the public
`https://api.devnet.solana.com` endpoint, used by default at `solana.js` line 27 and
`escrow.js` line 42) exhibit observable propagation lag of 5–15 seconds during normal
operation and up to 30+ seconds during congestion. With only one retry at +2 seconds,
any propagation lag beyond ~2 seconds (from when the client emits `escrowDepositConfirm`
to when attempt 2 reads the PDA) produces a false-negative confirmation failure.

### 3. Failure path when both attempts return null

`server/socket-io/main.js`, lines 1750–1753:

```js
if (!escrowState) {
    client.emit('escrowError', { reason: 'Escrow PDA not found on-chain' })
    return
}
```

When both reads return `null`, the handler emits `escrowError` and returns. At this
point:
- The on-chain deposit TX is confirmed (the client only emits `escrowDepositConfirm`
  after `confirmTransaction` resolves — `WalletContext.js` line 234).
- The escrow PDA exists and holds the player's deposited SOL.
- The server's `wagerStates[rid].deposits` map is NOT updated — the deposit is not
  counted server-side.
- The deposit timer (`DEPOSIT_TIMEOUT_MS = 120_000`) continues running.
- The match never proceeds to `escrowActive`.

After 120 seconds, the deposit timer fires (`main.js` lines 1059–1082), calls
`cancelMatchEscrow`, emits `escrowDepositTimeout` to clients, and calls `removeRoom`.
If the cancel call itself fails (a separately documented HIGH — EH-F04, `main.js`
lines 1072–1076), the escrow PDA remains open with deposited funds until the 48-hour
permissionless reclaim window.

### 4. Failure path when attempt 2 reads stale state (depositConfirmed = false)

Even if `getEscrowState` succeeds but returns state that has not yet reflected the
deposit (i.e., the account exists but `playerOneDeposited` or `playerTwoDeposited` is
still `false` because the deposit instruction's account mutation has not propagated):

`server/socket-io/main.js`, lines 1761–1764:

```js
if (!depositConfirmed) {
    client.emit('escrowError', { reason: 'Deposit not confirmed on-chain' })
    return
}
```

Same outcome: handler returns, deposit not counted, timer fires after 120 seconds.

### 5. What happens if the TX confirms AFTER being classified as failed

The hypothesis asks whether a TX that eventually confirms is treated as failed and
triggers duplicate settlement. The answer is no — for the deposit confirmation path,
there is no settlement involved at this stage. Settlement only occurs when the match
ends via the fire handler. The relevant question is: can a late `escrowDepositConfirm`
re-trigger the handler after the room has been cancelled?

Looking at `main.js` lines 1733–1737:

```js
const room = findRoom(rid)
if (!room) return

const ws = wagerStates[rid]
if (!ws) return
```

After `removeRoom(roomId)` fires (from the deposit timeout callback), `findRoom(rid)`
returns null and the handler exits immediately. A late `escrowDepositConfirm` event
after room teardown is safely no-oped. No duplicate settlement, no double-cancel.

The hypothesis's claim about "duplicate settlement attempts" is NOT substantiated by the
code. The actual impact is a liveness failure, not a duplicate payment.

### 6. Settlement retry strategy (for completeness)

The `failedSettlements` retry loop (`main.js` lines 82–104) is for settlement failures
(after match end), not deposit confirmation failures. It runs on a 60-second interval
with up to 5 attempts. Critically, the recovery loop only calls `cancelMatchEscrow` —
it never retries `settleMatchEscrow`. This means a transient RPC error at match
settlement time results in refund to both players rather than retry-to-settle, which
is a separate HIGH-severity finding (ERR-01 EH-F05, ARCHITECTURE H-11).

`main.js` lines 83–104:

```js
setInterval(async () => {
    for (const [matchId, data] of failedSettlements.entries()) {
        if (data.attempts >= 5) {
            failedSettlements.delete(matchId);  // abandon after 5 cancel retries
            continue;
        }
        try {
            const result = await cancelMatchEscrow(matchId, data.p1wallet, data.p2wallet);
            // never calls settleMatchEscrow
```

`settleMatchEscrow` itself (via Anchor's `.rpc()`, `escrow.js` lines 400–411) has no
explicit timeout parameter. The Anchor `AnchorProvider` is initialized with
`commitment: 'confirmed'` (`escrow.js` line 72) but no `sendOptions.timeout`. Under
RPC congestion, `.rpc()` can hang until the provider's internal timeout (~60–120
seconds depending on the RPC node's connection timeout), blocking the `withLock`
settlement block for up to 30 seconds before the `withLock` timeout releases the lock.

## Severity Rationale

**HIGH** (not CRITICAL) for the following reasons:

1. The primary impact is a **liveness failure, not a fund-theft path**. Real SOL is
   temporarily locked in the escrow PDA for up to 120 seconds and then returned via
   cancel. No player can steal funds through this path.

2. The 48-hour permissionless reclaim (`permissionlessReclaimEscrow`, `escrow.js`
   line 479) is a backstop if the cancel also fails.

3. The bug is **reproducible on devnet under normal load** (5–15 second RPC
   propagation lag). It is not an edge case; it is expected behavior on the public
   devnet endpoint.

4. Compounded with EH-F04 (deposit timeout cancel failure is swallowed with no retry
   queue), a single RPC hiccup during deposit confirmation can lead to a 48-hour fund
   freeze instead of a 120-second one.

5. User experience impact is severe: the client receives `escrowError` with reason
   `'Escrow PDA not found on-chain'` or `'Deposit not confirmed on-chain'` even though
   the on-chain deposit succeeded. There is no guidance to retry. The client must wait
   for the match to time out.

## Recommendations

### R1 — Exponential backoff with more attempts (Immediate)

Replace the single 2-second retry with a 3-attempt exponential backoff strategy:

```js
// server/socket-io/main.js — escrowDepositConfirm handler, ~line 1742
if (isEscrowEnabled()) {
    try {
        let escrowState = null;
        const delays = [0, 2000, 5000];  // 0s, +2s, +5s = attempts at T+0, T+2, T+7
        for (const delay of delays) {
            if (delay > 0) await new Promise(r => setTimeout(r, delay));
            escrowState = await getEscrowState(rid);
            if (escrowState) break;
        }
        // ... rest of verification unchanged
    }
}
```

This brings the maximum wait to 7 seconds (T+0, T+2, T+7), covering the typical devnet
propagation window of 5–15 seconds while keeping the deposit flow responsive.

### R2 — Separate PDA-not-found from deposit-not-yet-visible

The current code returns `null` from `getEscrowState` for two distinct reasons:
(a) the PDA genuinely does not exist (escrow creation failed upstream), and
(b) the PDA exists but the RPC node has not propagated it. These are not distinguishable
from the returned `null`. Consider catching the specific Anchor `AccountNotFoundError`
and distinguishing it from a network error:

```js
// server/services/escrow.js — getEscrowState, ~line 537
} catch (err) {
    if (err.message?.includes('Account does not exist')) {
        return null;  // PDA genuinely absent
    }
    throw err;  // RPC error — let caller handle as retriable
}
```

This allows the confirmation handler to distinguish "retry worthwhile" from
"PDA not created (abort)".

### R3 — Add deposit confirmation failures to the failedSettlements retry queue

When both retry attempts fail for a room where a deposit did occur (i.e., one player
deposited but the server couldn't confirm it), the timeout cancel fires and refunds
the depositor. This is correct but results in a wasted match. Consider emitting a
server-side advisory to the depositing player with a "retry confirmation" option rather
than immediately cancelling.

### R4 — Fix compounding EH-F04 (deposit timeout cancel swallowed)

`main.js` lines 1072–1076 silently swallow cancel failure with no retry entry in
`failedSettlements`. This is the path that converts a 120-second freeze into a
48-hour freeze. At minimum, log the room and both wallet addresses in a durable
location (DB or alerting channel) so the issue can be manually remediated:

```js
// main.js, deposit timeout callback ~line 1072
try {
    await cancelMatchEscrow(roomId, p1wallet, p2wallet);
} catch (err) {
    console.error(`[Escrow] Deposit timeout cancel FAILED for ${roomId}:`, err.message);
    // Store for operator action — funds frozen until permissionless reclaim
    failedSettlements.set(roomId, {
        matchId: roomId, escrowPDA: null,
        p1wallet, p2wallet,
        wagerSOL: wsCheck?.amount || 0,
        failedAt: Date.now(), attempts: 1,
        error: `deposit_timeout_cancel: ${err.message}`,
    });
}
```

### R5 — Pass `lastValidBlockHeight` in `escrowDeposit` socket event

`buildDepositTransaction` (`escrow.js` lines 348–354) correctly captures
`lastValidBlockHeight` in the Transaction constructor. Have the server include this
value in the `escrowDeposit` socket payload:

```js
// escrow.js — buildDepositTransaction return value
return {
    success: true,
    transaction: serialized,
    escrowPDA: escrowPDA.toBase58(),
    lastValidBlockHeight,  // add this
};
```

Then the client can use the modern `confirmTransaction` strategy form
(`WalletContext.js` line 234), providing proper expiry tracking and preventing the
hang-on-drop issue documented as CHAIN-01 C-01.
