# H045 — Fragmented Connection Objects: Inconsistent RPC State Across Server Modules

**Hypothesis ID:** H045
**Auditor:** Dinh's Bulwark — CHAIN-02
**Date:** 2026-02-23
**Severity:** MEDIUM
**Verdict:** CONFIRMED — Three independent `Connection` objects exist with a structurally dangerous initialization gap; commitment levels happen to match today, but the fragmentation creates a genuine inconsistency window under SIGHUP key reload and a proven early-import race for `shot-token.js`.

---

## Verdict Summary

The hypothesis is confirmed. Three separate `Connection` objects are instantiated across `solana.js`, `escrow.js`, and `shot-token.js`. All three currently use `'confirmed'` commitment, so in the steady-state happy path their commitment levels are identical. However, the fragmentation produces two concrete problems:

1. **`shot-token.js` constructs its `Connection` at module import time** (before `dotenv.config()` is confirmed to have run), meaning it may permanently connect to the wrong cluster if import order is unfavorable.
2. **SIGHUP key reload re-creates the `escrow.js` `Connection`** (via `initEscrow()`) but cannot refresh the `shot-token.js` module-level `Connection`, leaving the two connections permanently out of sync after any credential reload event.

The third connection, in `solana.js`, is lifecycle-managed via a lazy singleton (`initSolana()` / `getConnection()`) and is the intended shared instance — but `escrow.js` and `shot-token.js` do not import it.

---

## Evidence

### Connection 1 — `solana.js` (lazy singleton)

**File:** `server/services/solana.js`

```js
// Line 68
let connection = null;

// Lines 73–82
export function initSolana() {
    connection = new Connection(SOLANA_RPC, 'confirmed');   // <-- Connection #1
    ...
    return connection;
}

export function getConnection() {
    if (!connection) {
        return initSolana();
    }
    return connection;
}
```

`getConnection()` is exported and available to any module. This is the intended shared singleton. It is initialized explicitly when `initSolana()` is called, or lazily on first call to `getConnection()`. Commitment: `'confirmed'`.

---

### Connection 2 — `escrow.js` (re-created on every `initEscrow()` call)

**File:** `server/services/escrow.js`

```js
// Line 42
const SOLANA_RPC = process.env.SOLANA_RPC || 'https://api.devnet.solana.com';

// Lines 69–74
export function initEscrow() {
    provider = null;
    program = null;
    ...
    const connection = new Connection(SOLANA_RPC, 'confirmed');   // <-- Connection #2
    const wallet = new Wallet(escrowKeypair);
    provider = new AnchorProvider(connection, wallet, {
        commitment: 'confirmed',
        preflightCommitment: 'confirmed',
    });
    ...
}
```

This connection is embedded in the `AnchorProvider` and accessed later via `provider.connection` (line 347). It is **not** the shared `getConnection()` instance from `solana.js`. Every call to `initEscrow()` creates a new `Connection` object and discards the previous one. Commitment: `'confirmed'`.

`initEscrow()` is called in three places:
- `server/index.js` line 19 (startup, via `initSolana()` which calls `initEscrow()` internally — see `solana.js` line 78)
- `server/index.js` line 132 (Windows direct key reload path)
- `server/index.js` line 169 (SIGHUP handler)

---

### Connection 3 — `shot-token.js` (module-level, never refreshed)

**File:** `server/services/shot-token.js`

```js
// Lines 35–36
const SOLANA_RPC = process.env.SOLANA_RPC || 'https://api.devnet.solana.com';
const connection = new Connection(SOLANA_RPC, 'confirmed');   // <-- Connection #3
```

This is a **bare module-level statement** outside any function. It executes at the moment `shot-token.js` is first imported. The `connection` constant is used only in `verifyBurnTransaction()` at line 471:

```js
// Lines 471–474
const tx = await connection.getParsedTransaction(txSignature, {
    commitment: 'confirmed',
    maxSupportedTransactionVersion: 0,
});
```

Commitment: `'confirmed'`. This connection is **never refreshed** — no function exists to recreate it. No equivalent of `initEscrow()` or `initSolana()` exists in this module.

---

### Import Order Race (dotenv timing)

**File:** `server/index.js`

```js
// Lines 11–16
import { initShotState } from './services/shot-token.js'   // <-- module evaluated here
...
dotenv.config()   // Line 16 — dotenv runs AFTER shot-token.js is imported
```

ES module `import` statements are evaluated in dependency order before any top-level code runs. `shot-token.js` is imported at line 11 (static import at the top of the file). `dotenv.config()` is called at line 16, which is top-level executable code. By the time `dotenv.config()` runs, `shot-token.js` has already been evaluated and Connection #3 has already been constructed with whatever `process.env.SOLANA_RPC` held at that moment — which is `undefined` if no system environment variable was set, causing the fallback `'https://api.devnet.solana.com'` to be used regardless of what `.env` specifies.

This means: if `SOLANA_RPC` is defined in `.env` (not the system environment), `shot-token.js` will silently connect to devnet while `solana.js` and `escrow.js` — initialized after `dotenv.config()` runs — connect to the correct configured endpoint.

---

### SIGHUP Reload Creates Permanent Divergence

**File:** `server/index.js`

```js
// Lines 165–174
process.on('SIGHUP', () => {
    const ok = initKeys();
    if (ok) {
        initEscrow();   // re-creates Connection #2 with new keypair
        // Connection #3 in shot-token.js is NEVER refreshed
    }
});
```

After a SIGHUP:
- `escrow.js` gets a brand new `Connection` object (Connection #2 is replaced).
- `shot-token.js` continues to use the original Connection #3 created at import time.
- `solana.js` retains Connection #1 (the singleton is not reset by SIGHUP).

If the operator changes `SOLANA_RPC` in the environment and sends SIGHUP intending to hot-reload configuration, only `escrow.js` picks up the new endpoint. `shot-token.js` and `solana.js` continue using their original connections.

### Commitment Level Comparison

| Module | Connection # | Created At | Commitment | Refreshed On SIGHUP |
|--------|-------------|------------|------------|---------------------|
| `solana.js` | #1 | First call to `getConnection()` / `initSolana()` | `'confirmed'` | No |
| `escrow.js` | #2 | Each call to `initEscrow()` | `'confirmed'` (Connection) + `'confirmed'` (AnchorProvider) | Yes |
| `shot-token.js` | #3 | Module import (before dotenv) | `'confirmed'` | No, ever |

All three use `'confirmed'` commitment. The commitment parity means the hypothesis sub-question — "can one see different state than another?" — is **no in the steady state**, but **yes in two edge cases**:

1. **dotenv import race:** `shot-token.js` may connect to a different cluster entirely if `SOLANA_RPC` is only in `.env` (not the system environment), not merely a different view of the same cluster.
2. **Connection pool divergence:** Three independent TCP/WebSocket connection pools mean that slot propagation from the RPC node may arrive at slightly different times across the three pools. Under normal operation this is sub-second and harmless. Under RPC node failover or load-balancing (where the RPC provider routes different TCP sessions to different backend nodes), the three connections could briefly observe different slot heights.

The second case is theoretical on Solana's public RPC (which load-balances at the HTTP layer, not at the connection layer for WebSocket subscriptions). The first case (dotenv race) is deterministic and reproducible on any deployment where `SOLANA_RPC` is stored in `.env` rather than as a system environment variable.

## Risk Assessment

**Primary Risk: Burn verification connects to wrong cluster (silent, permanent)**

If `SOLANA_RPC` in `.env` points to mainnet (`https://api.mainnet-beta.solana.com`) but Connection #3 was built before dotenv ran (with the devnet fallback), `verifyBurnTransaction()` will query devnet for a transaction that lives on mainnet. It will return `null` ("Transaction not found or not confirmed") and the burn will be rejected — a false negative that denies the player a legitimate prestige upgrade. Alternatively, if a devnet transaction signature happens to collide with a mainnet signature format (unlikely but possible), the verification would accept a devnet burn for a mainnet prestige unlock.

**Secondary Risk: SIGHUP partial reload**

Operators using SIGHUP to hot-reload credentials after a key rotation expect all RPC-using subsystems to reinitialize. `shot-token.js` silently does not. If the key rotation also involved an RPC endpoint change, burn verification silently continues against the stale endpoint indefinitely until process restart.

**Severity Rationale: MEDIUM (not HIGH)**

The commitment levels are identical across all three connections, so there is no active inconsistency in state visibility during the steady-state happy path. The dotenv race is real and reproducible but requires a specific deployment pattern (`.env` file rather than system env). The SIGHUP divergence requires an operator to change both the keypair and the RPC endpoint simultaneously, which is an unusual operational event. Neither path enables fund theft directly; the worst outcome is legitimate burns being rejected (false negative) or stale RPC being used for verification.

## Recommendations

### R1 — Consolidate to a single Connection (Primary Fix)

`escrow.js` and `shot-token.js` should import and use `getConnection()` from `solana.js` rather than constructing their own. This requires `initSolana()` to be called before `initEscrow()` and before any call to `verifyBurnTransaction()`, which is already the case given startup order.

**`server/services/escrow.js`** — replace the local construction with an import:

```js
// Remove:
import { Connection, ... } from '@solana/web3.js';
const SOLANA_RPC = process.env.SOLANA_RPC || ...;

// In initEscrow(), replace:
const connection = new Connection(SOLANA_RPC, 'confirmed');

// With:
import { getConnection } from './solana.js';
...
const connection = getConnection();
```

**`server/services/shot-token.js`** — remove the module-level construction:

```js
// Remove lines 35-36:
const SOLANA_RPC = process.env.SOLANA_RPC || 'https://api.devnet.solana.com';
const connection = new Connection(SOLANA_RPC, 'confirmed');

// In verifyBurnTransaction(), replace:
const tx = await connection.getParsedTransaction(...)

// With:
import { getConnection } from './solana.js';
...
const conn = getConnection();
const tx = await conn.getParsedTransaction(...)
```

This eliminates all three separate instances and ensures all RPC calls go through a single lifecycle-managed connection.

### R2 — Move dotenv before all imports (Startup Safety)

In `server/index.js`, `dotenv.config()` must run before any module that reads `process.env` at import time. The current pattern of static `import` followed by `dotenv.config()` at line 16 is inherently racy for module-level env reads.

One approach is to move dotenv initialization into a separate entry shim:

```js
// server/boot.js  (new entry point)
import dotenv from 'dotenv';
dotenv.config();
await import('./index.js');
```

Alternatively, ensure `SOLANA_RPC` (and all other env vars used at module import time) are always set as system environment variables in production (e.g., via Render's environment variable dashboard), never relying solely on `.env` file loading.

### R3 — Add SIGHUP reload coverage for shot-token.js

If consolidating to a single connection (R1) is not immediately feasible, add an explicit re-initialization function to `shot-token.js`:

```js
// server/services/shot-token.js
let connection = null;

export function initShotConnection() {
    const SOLANA_RPC = process.env.SOLANA_RPC || 'https://api.devnet.solana.com';
    connection = new Connection(SOLANA_RPC, 'confirmed');
}

export function getShotConnection() {
    if (!connection) initShotConnection();
    return connection;
}
```

Then call `initShotConnection()` in the SIGHUP handler alongside `initEscrow()`.

### R4 — Add startup cluster validation

Add an assertion after `dotenv.config()` that validates `SOLANA_RPC` is set and log a warning (or fatal error in production) if the module-level connection in any service resolved to the default devnet URL while the configured URL is different:

```js
// After dotenv.config()
const configuredRPC = process.env.SOLANA_RPC || 'https://api.devnet.solana.com';
if (!process.env.SOLANA_RPC) {
    console.warn('[Startup] SOLANA_RPC not set — using devnet fallback. All modules will connect to devnet.');
}
```
