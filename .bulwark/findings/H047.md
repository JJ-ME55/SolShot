# H047 — positionUpdate 12K px/sec Movement Speed Exploit

**Audit:** Dinh's Bulwark — Off-Chain Security
**Hypothesis ID:** H047
**Date:** 2026-02-23
**Investigator:** Hypothesis Investigator (Phase 3)
**Status:** CONFIRMED
**Verdict:** CRITICAL — The 400 px per event tolerance on `positionUpdate`, combined with the 30 events/sec global rate cap, allows a client to drift the server-authoritative tank position by up to 12,000 px/sec. The `stepLeft`/`stepRight` move-count enforcement is intact and correct, but `positionUpdate` provides an entirely separate, uncounted write path that bypasses all per-turn movement limits. The `fire` handler compounds this by accepting a client-supplied position up to 400 px away from the (already-drifted) server position.

---

## 1. Summary

SolShot's server is intended to be authoritative over tank positions. Two hardened events handle legitimate movement: `stepLeft` and `stepRight`, both of which enforce turn ownership, BATTLE-state validation, and a server-enforced 4-step limit (max 320 px per turn). A separate event, `positionUpdate`, was added to resync positions after blast knockback. The knockback use-case is legitimate, but the implementation allows any authenticated player to use `positionUpdate` as a general-purpose position write with a per-event tolerance of 400 px horizontally and 200 px vertically, at the full 30 events/sec global rate cap. This creates a 12,000 px/sec movement channel that completely circumvents the 4-step (`stepLeft`/`stepRight`) per-turn limit.

The `fire` handler then adds a compounding second vulnerability: when the client supplies a `data.position` field in the fire payload, the server accepts it as the projectile origin if it is within 400 px of the server-stored position. Because `positionUpdate` already wrote the drifted coordinates into the server-stored position, both the server-stored value and the fire-handler tolerance window are anchored to the attacker-controlled position.

## 2. Vulnerability Detail

### 2.1 positionUpdate handler (primary vulnerability)

**File:** `server/socket-io/main.js`
**Lines:** 2371–2402

```javascript
// Line 2371
client.on('positionUpdate', (data) => {
    if (!requireAuth(client, 'positionUpdate')) return      // line 2372
    if (!data || typeof data !== 'object') return           // line 2373
    const { x, y } = data                                  // line 2374
    if (!Number.isFinite(x) || !Number.isFinite(y)) return // line 2375
    // Clamp to valid bounds
    const clampedX = Math.min(1199, Math.max(0, x))        // line 2377
    const clampedY = Math.min(800, Math.max(0, y))         // line 2378
    var room = findRoom(client.roomId)
    if (!room) return
    // SA-04: Distance validation during battle — reject teleportation (DB: H034, H035)
    const ms = matchStates[client.roomId]
    if (ms && ms.status === MATCH_STATES.BATTLE) {          // line 2383
        const isHost = room.host && room.host.socketId === client.id
        const currentPos = isHost ? room.host.pos : (room.player ? room.player.pos : null)
        if (currentPos) {
            const dx = Math.abs(clampedX - currentPos.x)   // line 2387
            const dy = Math.abs(clampedY - currentPos.y)   // line 2388
            if (dx > 400 || dy > 200) {                    // line 2389
                return  // Reject — position jump too large
            }
        }
    }
    // Write accepted position unconditionally
    if (room.host && room.host.socketId === client.id) {
        room.host.pos.x = clampedX                         // line 2396
        room.host.pos.y = clampedY                         // line 2397
    } else if (room.player && room.player.socketId === client.id) {
        room.player.pos.x = clampedX                       // line 2399
        room.player.pos.y = clampedY                       // line 2400
    }
})
```

**Critical observations:**

1. **No per-turn move count check.** `stepLeft`/`stepRight` both gate on `ms.moveCounts[client.id] >= 4` (lines 2420, 2455) and increment the counter. `positionUpdate` has no reference to `moveCounts` at any line.

2. **No turn ownership check.** `stepLeft` enforces `ms.currentTurn !== client.id` (line 2414). `positionUpdate` has no `currentTurn` check — the off-turn player can continuously update their position while the opponent is shooting.

3. **No state validation.** `stepLeft`/`stepRight` call `validateAction(ms.status, 'stepLeft')` to confirm `BATTLE` state is active and the action is legal for that state. `positionUpdate` only enters the distance check branch when in `BATTLE` state (line 2383), but outside `BATTLE` state (e.g., `WEAPON_SHOP`, `ROUND_END`) it bypasses the distance check entirely and writes the position directly (lines 2395–2401).

4. **Per-event tolerance is 400 px horizontal, 200 px vertical.** The game map is 1200 px wide. The intended 4-step movement limit is 4 × 80 px = 320 px per turn. A single `positionUpdate` event allows more horizontal movement (400 px) than the entire turn-budget of `stepLeft`/`stepRight` (320 px).

5. **Rate cap is 30 events/sec global, not per-event-type.** The ring-buffer rate limiter (lines 444–529) caps all events combined at 30/sec. There is no separate cap for `positionUpdate`. An attacker sending only `positionUpdate` events can issue 30/sec: 30 × 400 px = 12,000 px/sec.

6. **Incremental chaining.** Each accepted `positionUpdate` moves the server position. The next event is measured against the newly written position. There is no anchor to the turn-start position and no cumulative cap, so 30 sequential 400 px moves (taking 1 second) traverse 12,000 px — ten full map widths. In practice the 1200 px map is crossed in under 0.1 seconds.

### 2.2 fire handler double-tolerance (compounding vulnerability)

**File:** `server/socket-io/main.js`
**Lines:** 1881–1903

```javascript
// Line 1882
const isHost = room.host && room.host.socketId === this.id
const serverPos = isHost ? room.host.pos : (room.player ? room.player.pos : null)

// Line 1892
let startX = serverPos.x   // default: server-stored (already manipulated)
let startY = serverPos.y

// Line 1894
if (data.position && typeof data.position === 'object' &&
    Number.isFinite(data.position.x) && Number.isFinite(data.position.y)) {
    const dx = Math.abs(data.position.x - serverPos.x)
    const dy = Math.abs(data.position.y - serverPos.y)
    if (dx <= 400 && dy <= 200) {             // line 1898: another 400 px tolerance
        startX = data.position.x              // client-reported origin used
        startY = data.position.y
        // SA-04: Do NOT write startX/startY back to serverPos
    }
}

// Line 1933
const result = processShot({
    startX,           // attacker-controlled origin
    startY,
    ...
})
```

The comment on line 1901 (`"Do NOT write startX/startY back to serverPos"`) protects the stored position from the `fire` payload — but it does not protect it from `positionUpdate`, which already wrote into `serverPos` before the fire event arrives. The result is:

- `serverPos.x` is the attacker's last accepted `positionUpdate` coordinate (anywhere on map).
- `startX` defaults to `serverPos.x` (already attacker-controlled).
- If the attacker also supplies `data.position` in the fire payload, they gain a further 400 px adjustment on top of the already-drifted server position.

The total controllable range for the projectile origin at the time of firing is therefore: full-map horizontal (0–1199) from `positionUpdate` chaining, plus ±400 px from the fire payload tolerance. In practice the map clamp (line 2377: `Math.min(1199, Math.max(0, x))`) prevents out-of-bounds, but within the 1200 px map the attacker can fire from any X coordinate of their choosing.

### 2.3 stepLeft/stepRight are correctly implemented (for contrast)

**File:** `server/socket-io/main.js`
**Lines:** 2408–2474

`stepLeft` (lines 2408–2439) and `stepRight` (lines 2443–2474) correctly implement:

- `requireAuth` (lines 2409, 2444)
- `validateAction(ms.status, 'stepLeft')` state guard (lines 2412, 2447)
- Turn ownership: `ms.currentTurn !== client.id` (lines 2414, 2449)
- 4-step limit: `ms.moveCounts[client.id] >= 4` (lines 2420, 2455)
- Server-computed new position via heightmap lookup (lines 2430–2435, 2465–2469), not client-supplied

These controls are sound. The `moveCounts` counter is reset per-turn at line 2015 (`ms.moveCounts[ms.currentTurn] = 0`) after each successful fire, and at line 411 after a turn timeout, and at line 2250 between rounds. The step system is not the vulnerability. The vulnerability is that `positionUpdate` bypasses the step system entirely.

## 3. Attack Scenario

**Target:** Wagered match (any mode). The attacker is playing for real SOL.

**Precondition:** Attacker has a valid authenticated session in an active BATTLE match.

**Steps:**

1. At the start of each turn (or continuously throughout the match, including off-turn), emit rapid `positionUpdate` events to drift the server-stored tank position to the optimal firing location: directly above the opponent's tank or at the angle that maximizes damage for the chosen weapon.

2. Because `positionUpdate` has no turn ownership check, this can be done during the opponent's turn as well as during the attacker's own turn, pre-positioning before the `fire` event is sent.

3. Emit the `fire` event with the optimal angle/power from the pre-positioned location. Optionally include `data.position` for an additional 400 px adjustment. The server physics engine (`processShot`) runs from `startX/startY`, which reflects the attacker-controlled coordinates.

4. Repeat each turn. Combined with weapon selection manipulation (`createWeaponArray` has no host-only guard, per ARCHITECTURE.md C-8), the attacker controls both their firing position and the available weapon pool.

**Effect:** Guaranteed or near-guaranteed maximum damage output every turn. In a wagered match (Quick Match, Duel, High Roller), this translates directly to financial advantage — the attacker wins consistently and receives 90% of the combined wager pot via escrow settlement.

**Automation complexity:** Low. A trivial script using `socket.emit('positionUpdate', {x: targetX, y: targetY})` in a loop covers the drift. Standard Socket.IO client; no binary patching required.

## 6. Design Intent vs. Implementation Gap

The comment on line 2370 describes the intended purpose:

```
// After blast knockback, client reports its new tank position
```

Blast knockback is a legitimate use case: a weapon explosion displaces a tank, the client renders the physics animation, and the resulting resting position needs to be communicated back to the server. The 400 px horizontal tolerance and 200 px vertical tolerance were sized for this purpose — a tank physically cannot be knocked further than the blast radius permits in a single event.

The gap is that this handler has no guard limiting it to the immediate post-blast moment. It accepts position updates at any time during BATTLE, on any turn, as many times as the rate limiter allows. The intended single-event, post-blast correction mechanism became a continuous, unrestricted position write channel.

A correct knockback implementation would require the update to originate from the server itself (server computes the knockback trajectory, writes the final position, and broadcasts it) or would tightly couple the `positionUpdate` event to a server-issued knockback token that can only be used once per blast event.

## 7. Recommendations

### R1 — Remove client-driven position writes; make knockback server-authoritative (Primary fix)

The physics engine (`server/services/physics.js`) already runs server-side. Blast knockback should be computed in `processShot` and the resulting post-knockback position should be written to `room.host.pos` / `room.player.pos` by the server, not reported by the client. Remove the `positionUpdate` handler entirely, or replace it with a server-emitted `positionCorrection` event that the client listens to (server pushes, client receives, never the reverse).

### R2 — If positionUpdate must remain: add per-turn budget accounting

If the knockback use-case genuinely requires a client-side report (e.g., because knockback physics run on the client's Phaser canvas), restrict the handler to:

1. **Turn coupling:** Only process one `positionUpdate` per blast event. Introduce a server-side flag `ms.pendingKnockbackFor[socketId]` that is set when the server's physics result includes a knockback for that player, and cleared after the first accepted `positionUpdate`. Reject all `positionUpdate` events when the flag is not set.

2. **Single-event tolerance:** The 400 px / 200 px tolerance per event must be bounded by the physics maximum knockback distance, not a round number. If no weapon can knock a tank more than 150 px, the tolerance should be `<= 150`, not `<= 400`.

3. **Cumulative per-turn cap:** Even with per-event bounds, chain-attacks must be prevented. Track `ms.knockbackDistance[socketId]` and reject any `positionUpdate` that would push the cumulative per-turn movement beyond the maximum single-blast knockback distance.

4. **Turn ownership:** Only the current-turn player's tank should be movable via knockback on their own turn. Off-turn tank movements should be computed server-side from the opponent's shot result, not client-reported.

### R3 — Remove the fire handler's data.position client-override path

Lines 1894–1903 in the `fire` handler accept a client-supplied `data.position` and use it as the projectile origin. The comment on line 1890 ("Client pixel-walks terrain surface which may differ from server heightmap snap") explains the intent, but this creates a second independent 400 px tolerance window on top of the already-writable `serverPos`. Since `stepLeft`/`stepRight` correctly compute the server-side Y position via `room.heightmap[newX] - 15` (lines 2433, 2468), the server already has a reliable Y coordinate that accounts for terrain surface. The fire handler should use only `serverPos.x` and `serverPos.y`; the `data.position` override path should be removed.

### R4 — Add a positionUpdate-specific rate sub-limit if the event is retained

If `positionUpdate` is kept in any form, add a dedicated ring buffer limiting it to at most 1–2 events per turn-tick (matching the expected one-per-blast-event cadence), not 30/sec. The existing ring-buffer pattern (lines 453–523) supports adding per-event-type sub-limits alongside the existing `fire` and `createRoom` throttles.

## 8. Verdict

**CONFIRMED CRITICAL.**

The `positionUpdate` handler at lines 2371–2402 of `server/socket-io/main.js` allows any authenticated player to write their server-stored tank position incrementally at 400 px per event, 30 events/sec, for a total of 12,000 px/sec — 37x the intended 4-step (320 px per turn) maximum. There is no turn ownership check, no move-count gate, and no cumulative cap. The `fire` handler at lines 1894–1903 adds a further 400 px client-supplied origin override on top of the already-drifted server position. Together, these two paths give an authenticated attacker full control over their projectile firing origin, completely bypassing the server-authoritative physics model and `stepLeft`/`stepRight` enforcement. In wagered matches, this provides a direct, repeatable path to winning real SOL.

`stepLeft` and `stepRight` are correctly implemented and are not the vulnerability.
