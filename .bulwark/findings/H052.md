# H052 — validatePayload Dead Code Leaves Gap

**Verdict:** CONFIRMED
**Severity:** MEDIUM
**Category:** INJ-05 (Prototype Pollution), API-03 (WebSocket Security)

## Evidence

### validatePayload exists but is never called

- **Definition:** `server/middleware/guards.js` lines 55-70 — well-written schema validator
- **Import:** `server/socket-io/main.js` line 15 — imported alongside other guards
- **Call sites:** ZERO — `grep -r 'validatePayload(' main.js` returns no matches
- **Contrast:** `validateFireParams` (defined at line 72) IS called in the fire handler; `requireAuth` and `validateAction` are called in 20+ handlers

### No Object.assign or spread on client payloads

`grep` for `Object.assign`, `...data`, `...payload` in main.js returns zero matches. Event handlers use destructuring (`const { terrainData, pos1, pos2 } = data`) which does NOT propagate `__proto__`.

### Socket.IO JSON parser behavior

Socket.IO 4.x uses `JSON.parse()` natively. Modern V8's `JSON.parse()` does NOT strip `__proto__` — it creates an own property named `"__proto__"`. However, because main.js uses destructuring rather than spread/assign, the `__proto__` property is never copied onto another object's prototype chain.

### Residual risk

1. **No null/type guards on most handlers** — Without `validatePayload`, most handlers rely on ad-hoc `if (!data || typeof data !== 'object') return` checks. Several handlers (e.g., `giveTurn` line 2480, `positionUpdate` line 2373) have this, but others may not.
2. **Future regression** — Any future handler using `Object.assign({}, data)` or `{...data}` would be immediately vulnerable since `validatePayload` isn't enforced.
3. **Extra properties pass through** — `validatePayload` only checks required fields exist with correct types. It does NOT strip unknown properties. Even if called, it wouldn't prevent prototype pollution from extra keys.

## Exploit Assessment

**Current state:** NOT directly exploitable via prototype pollution because destructuring is used consistently. The dead code is a defense-in-depth gap, not an active vulnerability.

**Why still MEDIUM:** The missing validation means:
- Handlers process arbitrary extra properties (information leakage into relay events)
- No schema enforcement means any field type mismatch causes runtime errors rather than clean rejection
- `giveTurn`'s `terrainData` accepts any type/size (see H017)

## Recommendations

1. **R1:** Call `validatePayload(data, schema)` at the top of every event handler, with handler-specific schemas
2. **R2:** Add a `stripUnknown: true` option to `validatePayload` that deletes properties not in the schema
3. **R3:** Add `Object.create(null)` wrapper or explicit `__proto__` deletion as defense-in-depth
