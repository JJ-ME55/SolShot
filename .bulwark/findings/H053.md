# H053 — nodemon in Production Dependencies

**Hypothesis:** nodemon in production deps adds attack surface
**Verdict:** CONFIRMED
**Severity:** HIGH (Attack Surface / Supply Chain)

---

## Summary

`nodemon` version `^1.3.3` is listed under `dependencies` in `server/package.json`, not under `devDependencies`. This means it is installed in every production deployment. `nodemon` is a file-watching process supervisor designed exclusively for development use. Its presence in production introduces unnecessary attack surface, binary bloat, and a dependency chain that is several years old and not maintained for security hardening.

---

**File:** `C:/Users/johnk/SolShot-clean/server/package.json`, lines 7-11

```json
"scripts": {
    "start": "node index.js",     // <-- production start does NOT use nodemon
    "dev": "nodemon index.js",    // <-- nodemon is only used via `dev` script
    "test": "node tests/integration.test.js"
},
```

**Key observations:**

1. **Line 27:** `nodemon` is in `dependencies`, so `npm install --production` (the standard Render/Docker production install) installs it.
2. **Lines 7-8:** The production `start` script invokes `node index.js` directly. `nodemon` is never executed in production — it is installed but not used.
3. **Line 9:** Only the `dev` script invokes `nodemon`.
4. **Version `^1.3.3`:** This resolves to the latest `1.x` release. Nodemon 1.x is an old major version; the current release series is 3.x. The `^` semver range locks to `1.x`, meaning the version installed is old and has a larger transitive dependency surface than modern nodemon.

---

## Attack Surface Analysis

Shipping `nodemon` to production adds the following risks:

1. **Transitive dependency bloat.** `nodemon` 1.x brings in `chokidar`, `anymatch`, `micromatch`, `glob`, `minimatch`, `graceful-fs`, and several other file-system watching packages. Each is an additional vector for supply-chain compromise. None of these are needed at runtime.

2. **File-system watching capability in process.** Although `nodemon` is not executed via the `start` script, it is present and importable. If server-side code injection occurs (e.g., via prototype pollution or an RCE gadget chain), an attacker could `require`/`import` nodemon or its sub-components to establish file-watching persistence or exfiltrate file change events.

3. **Version staleness.** `^1.3.3` resolves to a `1.x` release that has not received active security maintenance. The 1.x series predates many npm security advisories. Running `npm audit` on the server directory is likely to surface advisories against this version and its dependencies.

4. **Precedent for misclassification.** The misclassification signals that dependency hygiene has not been reviewed. Other dev-only tools may similarly be in the wrong section.

---

## Recommendations

1. **Move `nodemon` to `devDependencies`.** This is the primary fix:

```json
"dependencies": {
    // remove nodemon entry
},
"devDependencies": {
    "nodemon": "^3.1.0",   // also upgrade to current major version
    "pino-pretty": "^13.1.3",
    "socket.io-client": "^4.8.3"
}
```

2. **Upgrade to nodemon 3.x** while moving it. The `^1.3.3` pin is several major versions behind.

3. **Add a production install CI check.** In the deploy pipeline, run `npm install --production` and verify `nodemon` is absent from `node_modules/`. This prevents regression.

4. **Audit remaining dependencies** for similar misclassification. Any package used only in `dev` or `test` scripts belongs in `devDependencies`.
