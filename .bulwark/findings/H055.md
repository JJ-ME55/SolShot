# H055 — Terrain Generation Race Condition

**Hypothesis:** Two concurrent requestTerrain events generate different terrain maps for the same room.
**Verdict:** NOT VULNERABLE (cache guard is present and correctly placed)
**Severity:** N/A

---

## Summary

The `requestTerrain` handler in `server/socket-io/main.js` correctly implements a cache-before-generate pattern. The cache check (`room._terrainCache`) is the first action taken after authentication and room validation. Because Node.js's event loop is single-threaded and no `await` appears between the cache check and the cache write, the check-then-set sequence is atomic with respect to other incoming socket events. Two concurrent `requestTerrain` events from the same room cannot both reach the generation code — the second event will always find the cached terrain from the first.

## Race Condition Analysis

### Why the race does NOT occur

**Node.js event loop guarantee:** Socket.IO event handlers execute synchronously on the event loop. Two socket events from two different clients in the same room are queued as separate microtasks/tasks. They cannot execute concurrently — the second event handler only begins executing after the first has returned.

**No `await` in the hot path.** The entire generation code path (lines 2293–2343) is fully synchronous:
- `crypto.randomBytes(16)` — synchronous
- `generateTerrain()` — synchronous
- `generateTankPositions()` — synchronous
- `generateWind()` — synchronous
- All state mutations — synchronous
- `room._terrainCache = terrainPayload` — synchronous

Because there is no `await` between the cache check (line 2286) and the cache write (line 2340), the event loop cannot yield control to process a second `requestTerrain` event mid-execution. The check-then-set is effectively atomic.

**Execution sequence for two concurrent requests:**

```
Event 1 (host): arrives at event loop queue
Event 2 (player): arrives at event loop queue (concurrent network arrival, sequential execution)

Event 1 runs:
  → room._terrainCache is null → falls through to generation
  → generates terrain synchronously (no yield)
  → room._terrainCache = terrainPayload  ← set before event 1 returns
  → emits terrainGenerated to both clients (line 2343)
  → returns

Event 2 runs:
  → room._terrainCache is NOT null ← already set by event 1
  → emits cached terrain to requesting client only (line 2288)
  → returns (no regeneration)
```

The second client receives the same terrain via the early-return path at line 2289 OR via the broadcast on line 2343 from event 1's execution (whichever arrives at the client first). Either way, both players receive identical terrain.

### Cache reset between rounds

The cache is explicitly cleared at the end of `endShopPhase()`:

```js
// server/socket-io/main.js, line 285
if (room) delete room._terrainCache
```

This ensures that the cache guard correctly resets for each new round, preventing stale terrain from a prior round being sent for a new round. The deletion happens synchronously inside `endShopPhase`, which is itself only called from two paths:
- The shop timer expiry (line 1473–1475, inside `setTimeout` callback — runs when event loop is free)
- The `shopDone` handler when both players are ready (line 1571 — synchronous)

Both paths run in the event loop and complete before any subsequent `requestTerrain` handler can begin.

## Residual Observations (Non-Race, Non-Blocking)

While the race condition hypothesis is not confirmed, two minor observations are noted for completeness:

1. **State machine transition in `requestTerrain` (line 2315–2317):** The handler calls `transitionState(ms, MATCH_STATES.BATTLE)` if the match is not already in BATTLE state. Since `endShopPhase` (line 259) already performs this transition, the second call in `requestTerrain` will log a warning (`Invalid state transition: battle → battle`) but is otherwise harmless. The architecture file notes this at H-19 / the ARCHITECTURE.md `requestTerrain` row under "No duplicate guard (resets round state)" — this refers to HP re-initialization and turn re-initialization on lines 2323–2327 and 2318–2321, which would overwrite HP and re-roll `currentTurn` if a second `requestTerrain` somehow bypassed the cache. But as established above, the cache check prevents any second genuine generation.

2. **HP re-initialization inside requestTerrain (lines 2323–2324):** If the cache were not present, a second `requestTerrain` would reset both players' HP to 250 mid-round. This is only relevant if the cache is cleared at the wrong time. The current cache management (clear only in `endShopPhase`) is correct.

---

## Verdict Rationale

The hypothesis is **NOT VULNERABLE** because:
- The `room._terrainCache` guard is checked synchronously before any generation work.
- All generation code is synchronous (no `await`).
- Node.js's single-threaded event loop prevents concurrent execution of handlers.
- The cache is properly cleared between rounds via `endShopPhase`.

No remediation is required for the race condition hypothesis. The existing implementation is correct.
