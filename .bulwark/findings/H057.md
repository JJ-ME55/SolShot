# H057 — Gold Economy Manipulation via Concurrent Shop Events (TOCTOU in buyWeapon)

**Hypothesis:** Concurrent buyWeapon events exploit TOCTOU in gold balance check, buying more than gold permits.
**Verdict:** NOT VULNERABLE (no await between gold check and deduction; spendGold is synchronous)
**Severity:** N/A — but a related bypass via cost=0 is noted as a POTENTIAL issue

---

## Summary

The `buyWeapon` handler at line 1489 of `server/socket-io/main.js` calls `spendGold()` from `server/services/gold.js`. The `spendGold` function performs a balance check and deduction as a single synchronous, non-yielding operation with no `await` between check and mutation. Because Node.js's event loop processes socket event handlers sequentially, two concurrent `buyWeapon` events from the same client cannot interleave their execution — the second will always see the already-reduced balance from the first. The TOCTOU race condition does not apply in a single-threaded, synchronous execution context.

### spendGold function (lines 95–111)

**File:** `C:/Users/johnk/SolShot-clean/server/services/gold.js`

```js
export function spendGold(goldState, playerId, cost) {
    const balance = goldState[playerId] || 0;      // line 96: read

    if (cost < 0) {                                // line 98: invalid cost guard
        return { success: false, balance, reason: 'Invalid cost' };
    }
    if (cost === 0) {                              // line 101: free weapon guard
        return { success: true, balance };
    }
    if (balance < cost) {                          // line 105: balance check
        return { success: false, balance, reason: 'Insufficient Gold' };
    }

    goldState[playerId] = balance - cost;          // line 109: deduction (mutation)
    return { success: true, balance: goldState[playerId] };
}
```

`spendGold` is a pure synchronous function. The balance read (line 96), check (line 105), and mutation (line 109) execute without any yield point. There is no database call, no RPC call, no `await`, and no callback. The entire operation completes before Node.js can process any other event.

## Race Condition Analysis

### Why TOCTOU does NOT apply here

TOCTOU (Time Of Check To Time Of Use) requires that the state being checked can change between the check and the use. In an async context, an `await` creates a yield point where another event handler can run and mutate shared state before the original handler resumes.

In `spendGold`:
- Line 96: reads `balance`
- Line 105: compares `balance < cost`
- Line 109: mutates `goldState[playerId]`

All three lines execute in the same synchronous turn of the event loop. No other `buyWeapon` handler (or any other handler) can run between lines 96 and 109.

### Concurrent buyWeapon execution trace

Assume a player has 100 gold and sends two `buyWeapon` events simultaneously for weapons costing 60 gold each.

```
Event 1 arrives at event loop queue (weapon A, cost 60)
Event 2 arrives at event loop queue (weapon B, cost 60)

Event 1 executes (synchronous, no yield):
  spendGold(gold, id, 60):
    balance = 100
    100 < 60 → false (sufficient)
    gold[id] = 100 - 60 = 40  ← gold mutated to 40
    return { success: true, balance: 40 }
  inventory.push(weaponA)
  emits buyWeaponResult → success: true, balance: 40
Event 1 returns.

Event 2 executes:
  spendGold(gold, id, 60):
    balance = 40            ← sees updated value (40, not 100)
    40 < 60 → true (insufficient)
    return { success: false, reason: 'Insufficient Gold', balance: 40 }
  emits buyWeaponResult → success: false
Event 2 returns.
```

The second buy correctly fails. The gold is never double-spent.

## Identified Gaps (Not TOCTOU, but Related)

### Gap 1: Free weapon (cost === 0) bypass in spendGold

**File:** `C:/Users/johnk/SolShot-clean/server/services/gold.js`, lines 101–103

```js
if (cost === 0) {
    return { success: true, balance };  // free weapons always succeed without balance check
}
```

If a weapon has `goldCost: 0`, `spendGold` returns success unconditionally. This is by design for the base weapon (Single Shot, id 0). However, if weapon data is misconfigured (e.g., a future weapon erroneously has `goldCost: 0`), it would be purchasable an unlimited number of times by the same client (the `Already owned` check at line 1513 would block re-purchase of the same `weaponId`, but different zero-cost weapons could be bought repeatedly by any player regardless of balance).

This is a data validation gap, not a runtime concurrency bug. Severity: LOW (contingent on weapon data misconfiguration).

### Gap 2: No per-client rate limiting on buyWeapon

The `buyWeapon` handler has no per-client event rate limit. A client can flood the server with `buyWeapon` events. Each event executes the full validation chain synchronously. At high volume, this could degrade server performance during the shop phase. This is a minor DoS surface, not a gold economy exploit (all attempts after gold exhaustion are correctly rejected).

### Gap 3: Inventory check before balance check ordering

The handler checks `inventory.includes(weaponId)` (line 1513) before calling `spendGold` (line 1525). This is correct: an already-owned weapon is rejected before any balance check. However, if two concurrent `buyWeapon` events arrive for the same `weaponId` and the same client, the following race is theoretically possible in an async context — but not in the current synchronous implementation:

```
Event 1: inventory check (weaponId not in list) → passes → spendGold → inventory.push(weaponId)
Event 2: inventory check (weaponId now in list due to event 1) → rejected
```

In the current synchronous code, this is not a race — it is the correct sequential behavior. The `Already owned` guard is effective.

## Verdict Rationale

The hypothesis is **NOT VULNERABLE** because:
- `spendGold()` is fully synchronous with no `await` or callback between balance check and deduction.
- Node.js's single-threaded event loop ensures sequential execution of `buyWeapon` handlers.
- There is no yielding between the gold check (line 105 of gold.js) and the gold deduction (line 109 of gold.js).
- Two concurrent buy requests for the same player will always serialize: one succeeds, one sees the reduced balance and fails.

The TOCTOU race condition attack is not achievable against this implementation without fundamental changes to the concurrency model (e.g., introduction of async database gold storage with an `await` in the check-deduct path).

---

## Recommendations

While the TOCTOU is not exploitable, the following improvements are suggested for defense-in-depth:

1. **Add per-client rate limiting on `buyWeapon`** to prevent event flooding during the shop phase. A simple counter (`buyWeaponCount[socketId]` capped at e.g. 20 per shop phase) would suffice.

2. **Assert `goldCost > 0` for non-base weapons** in the weapon data validation layer. Add a startup check that iterates all weapons and logs/errors on any non-base weapon with `goldCost <= 0`.

3. **Consider making `goldStates` a class or module with a lock flag** as a forward-compatibility guard. If the gold system is ever refactored to use async persistence (e.g., Redis), the synchronous atomicity assumption will break. A documented comment in `spendGold` noting "this is intentionally synchronous for atomicity" would help future maintainers.
