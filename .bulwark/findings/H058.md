# H058 — Cross-Origin WebSocket Connection Hijacking

**Verdict:** NOT VULNERABLE

**Severity:** N/A (mitigated)

**Hypothesis:** Socket.IO doesn't verify Origin header, allowing cross-origin WebSocket connections from malicious pages.

---

## Evidence

The Socket.IO server in `server/index.js` is initialized with an explicit `cors` option that restricts the `origin` field to the `CORS_ORIGINS` array, which defaults to `['http://localhost:3000']` in development and is driven by the `CORS_ORIGINS` environment variable in production.

**`server/index.js`, lines 27–36:**

```js
const CORS_ORIGINS = process.env.CORS_ORIGINS
    ? process.env.CORS_ORIGINS.split(',').map(s => s.trim())
    : ['http://localhost:3000'];

const io = new socket.Server(server, {
    cors: {
        origin: CORS_ORIGINS,
        methods: ["GET", "POST"]
    }
})
```

Additionally, the Express-level CORS middleware at **line 97** uses the same origin list:

```js
app.use(cors({ origin: CORS_ORIGINS }))
```

When Socket.IO is initialized with `cors.origin` set to an array of specific strings (not `'*'`), the Socket.IO library enforces the allowlist during the HTTP upgrade handshake. Any WebSocket connection attempt from an origin not in the list is rejected at the transport layer with a CORS error before any event handler is reached.

The comment at line 26 explicitly references the hardening rationale: `// H008: Restrict CORS to known origins instead of wildcard`.

---

## Analysis

The hypothesis requires that `origin` be set to `'*'` or be absent entirely. Neither condition exists in this codebase. The configuration is correct:

- No wildcard (`'*'`) is used.
- No permissive function callback (e.g., `origin: (origin, cb) => cb(null, true)`) is used.
- The default falls back to `localhost:3000` rather than opening to all origins.
- The same allowlist is applied to both HTTP (Express CORS) and WebSocket (Socket.IO CORS) transports.

### Residual Operational Risk

The only residual risk is misconfiguration: if `CORS_ORIGINS` is set incorrectly in production (e.g., to `'*'` via the environment variable), the protection disappears entirely. There is no server-side validation that the `CORS_ORIGINS` value is not a wildcard. This is an operational concern, not a code vulnerability.

---

## Recommendations

1. **Validate `CORS_ORIGINS` at startup.** Add a guard that fails fast if the env var contains `*`:
   ```js
   if (CORS_ORIGINS.includes('*')) {
       console.error('[Server] FATAL: CORS_ORIGINS cannot be wildcard in production');
       if (process.env.NODE_ENV === 'production') process.exit(1);
   }
   ```
2. **Document the expected production value** in `.env.example` with a concrete example: `CORS_ORIGINS=https://solshot.gg`.
3. **Consider removing the `localhost:3000` dev fallback** if all developers are expected to set `CORS_ORIGINS` in a `.env` file — a missing env var silently becomes permissive for any localhost-hosted attacker page.
