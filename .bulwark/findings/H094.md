## H094 — Coordinated Queue Flooding

**Verdict:** CONFIRMED

**Severity:** HIGH

**Evidence:**
- server/socket-io/main.js:1213-1280 — joinQueue handler allows up to 100 connections per IP (line 41-42)
- No per-socket event rate limit on joinQueue after connection established
- server/socket-io/main.js:1231 — wagered queue entry only checks auth, not balance
- Line 1242-1255 — queue matching is first-come-first-served with no per-wallet join frequency limit
- matchmakingQueues.get(queueKey) grows unbounded (no max queue size enforced)

**Analysis:**
Attack vector:
1. Attacker with >1 wallet connects 100 sockets per IP (hits connection limit)
2. Sends joinQueue(high_roller, 1.0 SOL) on each socket repeatedly with zero delay
3. Queue grows without bound: 100 sockets × 1000 joins/second = 100K queue entries
4. Legitimate players wait forever (worst-case O(n) pairing time)
5. Server RAM consumed by queue entries (each entry: ~200 bytes = 20MB per 100K)

Per-IP limit is ineffective because:
- Attacker can rotate IPs (residential proxy, distributed botnet)
- Amplification: each joinQueue event creates minimal server cost, massive queue state

**Recommendation:**
1. Set max queue size per mode (e.g., 1000 max queue depth)
2. Add per-wallet join rate limit (e.g., 1 join per 5s per wallet)
3. Remove old queue entries after 5min timeout
