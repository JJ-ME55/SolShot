## H096 — Cross-Tab Wallet Session Confusion

**Verdict:** POTENTIAL

**Severity:** MEDIUM

**Evidence:**
- server/socket-io/main.js:44-45 — authenticatedWallets map keyed by socketId, stores walletAddress
- server/socket-io/main.js:778-838 — rejoinRoom handler allows ANY wallet to claim ANY pending reconnect if signature verifies
- Line 805-826 — No check that wallet was previously bound to the disconnected session; only checks pendingReconnects exists
- Client can open tab A (connect socket1, auth with wallet1), open tab B (connect socket2, auth with wallet2), disconnect tab A, rejoin with wallet2 → claims wallet1's match state

**Analysis:**
Attack scenario:
1. Alice opens tab A, connects socket1, authenticates with wallet_alice, joins match
2. Alice opens tab B in incognito, connects socket2, authenticates with wallet_bob (different wallet)
3. Tab A disconnects (network error or user refreshes)
4. Within 30s, tab B sends rejoinRoom(wallet_bob, validSignature)
5. rejoinRoom at line 805 reads `pendingReconnects[wallet_bob]` but should read `pendingReconnects[wallet_alice]`
6. Current code: no pre-existence check; if any wallet has a pending reconnect, ANY other wallet can claim it

**Recommendation:**
1. Bind pending reconnect to specific wallet (already done: pendingReconnects[walletAddress])
2. Verify rejoin wallet matches original wallet in pending state
3. Add check: `if (walletAddress !== pending.originalWallet) reject`
