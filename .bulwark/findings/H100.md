## H100 — Selective Disconnect Timing

**Verdict:** POTENTIAL

**Severity:** MEDIUM

**Evidence:**
- server/socket-io/main.js:705-770 — disconnect handler on 'disconnect' event; checks match state, saves reconnect, sets 30s timer
- server/socket-io/main.js:500-650 (approx) — fire handler: validates turn, processes damage, calls isMatchOver(), settles if true
- Disconnect handler: calls getRoundWinner()/isRoundOver() via different logic path than fire handler
- Line 737: setTimeout(() => { ... delete pendingReconnects ... }, 30s) — timer runs regardless of whether player reconnects
- Line 580-685 (approx): settleMatch() called in fire handler, but settlement may fail → handleSettlementFailure() called

**Analysis:**
Timing attack:
1. Player A connected, fires final shot → match resolves, server calculates settlement
2. Settlement TX sent to on-chain, awaiting confirmation
3. Player B (loser) disconnects at exact moment settlement is processing
4. Disconnect handler runs: calls getRoundWinner() independently
5. Fire handler: calls settleMatch() → fails (e.g., RPC timeout)
6. Disconnect handler: calls refundWager() → both players refunded instead of settlement

**Issue:**
- fire handler and disconnect handler determine winner via separate logic (both call getRoundWinner, but at different state)
- If disconnect occurs during settlement attempt, winner determination may differ between handlers
- This creates a race: attacker disconnects right as settlement TX is pending, forcing refund path

**Recommendation:**
1. Ensure only fire handler calls settlement (not disconnect)
2. Use withLock() in disconnect handler too if it affects settlement
3. Add flag: isSettled that prevents settlement in disconnect path
