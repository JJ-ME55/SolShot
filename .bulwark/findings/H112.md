## H112 — Prestige Tier Rollback

**Verdict:** POTENTIAL

**Severity:** MEDIUM

**Evidence:**
Prestige tier update is atomic but milestone persistence is fire-and-forget:

1. **prestigeBurn handler** (main.js:1611-1646):
   - Calls `verifyBurnTransaction(txSignature, wallet, expectedAmount)` (on-chain RPC read)
   - Calls `prestigeBurn(wallet)` (in-memory tier update)
   - Calls `saveMilestoneState(wallet)` (fire-and-forget DB write)

2. **prestigeBurn function** (shot-token.js:358-397):
   ```javascript
   state.balance -= nextTier.burnCost
   state.prestigeTier = nextTier.tier
   saveMilestoneState(walletAddress)  // fire-and-forget
   return { success: true, tier, tierName, ... }
   ```

3. **Fire-and-forget persistence**:
   - `saveMilestoneState()` is async but NOT awaited
   - If DB write fails (network, disk full, Mongoose error), client receives success response
   - In-memory state is updated; DB state is stale
   - On server restart, in-memory state is reloaded from DB
   - Tier unlock is lost (rollback to previous tier)

4. **Attack scenario**:
   - Client burns SHOT successfully
   - Client receives success response
   - Attacker crashes server before DB write commits (or triggers network partition)
   - Server restarts, reloads from DB
   - Client's tier advancement is lost
   - Attacker can repeat with same burn TX (replay protection is in-memory only)

5. **Replay protection gap** (shot-token.js:465-466):
   - `verifiedBurnTxs` is a Set in memory
   - Restored from DB on startup (shot-token.js:99-102)
   - But if DB write of prestige state fails, DB still has old tier
   - Next server start: `verifiedBurnTxs` is repopulated from DB
   - Same burn TX can be submitted again with different `expectedAmount`

**Recommendation:** Await `saveMilestoneState()`; wrap in try-catch; emit error to client on persistence failure.
