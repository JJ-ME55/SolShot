## H117 — Concurrent SHOT Burn + Settlement Fund Confusion

**Verdict:** POTENTIAL

**Severity:** MEDIUM

**Evidence:**
SHOT balance is in-memory only; verified burn transaction is added to in-memory `verifiedBurnTxs` Set (shot-token.js:549). Two concurrent `prestigeBurn` socket events with same txSignature:

1. Event 1: checks `verifiedBurnTxs.has(sig)` → false, calls `verifyBurnTransaction()` (async RPC read)
2. Event 2: checks `verifiedBurnTxs.has(sig)` → false (Event 1 still waiting on RPC), proceeds
3. Both call `verifyBurnTransaction()` → both succeed (on-chain is source of truth)
4. Both add to Set (idempotent)
5. Both unlock prestige tier

**Recommendation:** Move `.has()` check and `.add()` into a lock (`withLock()` pattern). Or: return burned tx list from RPC query and never cache client-supplied txSignature.

---

**Notes:** Burn amount is passed by client (shot-token.js:1626) but is validated against on-chain parsed transaction (shot-token.js:509-512). So client cannot forge amount. The race is on replay protection, not amount.
