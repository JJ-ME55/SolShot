# S001 — Chained Wager Bypass: Balance Fail-Open -> No Deposit Check -> Free Match

**Status:** CONFIRMED
**Severity:** CRITICAL
**Confidence:** HIGH
**Category:** LOGIC-02, ERR-01 (Attack Chain)
**Origin:** Novel — chained from CONFIRMED H001 + H004 + H012
**Target:** `server/socket-io/main.js` — joinRoom (lines 980-993), ready (lines 1399-1481), fire settlement (lines 2079-2245), playAgainRequest (lines 2498-2561)

---

## Summary

Three independently confirmed vulnerabilities in `server/socket-io/main.js` compose into a single unbroken attack chain that allows an attacker to play unlimited wagered matches at zero cost. The chain is:

1. **H001 (Balance Fail-Open):** The balance check in `joinRoom` (line 990-992) and `createRoom` (lines 1145-1147) catches any exception from `verifyBalance()` and falls through without returning, allowing a wallet with zero SOL to enter a wagered room whenever the Solana RPC throws rather than resolving.

2. **H004 (No Deposit Verification):** All three settlement paths check `ws.amount > 0` but never check `ws.deposits` to confirm both players actually deposited. In dev mode the on-chain guard is absent entirely; in production the on-chain `require!(state == Active)` is the only barrier and it can be circumvented by the timing attack described below.

3. **H012 (Wagerless Rematch):** The `playAgainRequest` handler resets match state but never calls `createMatchEscrow`, never calls `buildDepositTransaction`, never emits `escrowDeposit` to clients, and never resets `ws.deposits`. The `ready` handler (line 1420) starts the shop phase with no check on deposit status. The match proceeds with a phantom wager pointing at a closed (non-existent) PDA.

No gate between these three stages blocks the chain. The path from room entry to rematch settlement is fully open.

---

## Verdict

**CONFIRMED CRITICAL.** The chain is exploitable in two distinct scenarios:

- **Scenario A (Dev / Escrow Disabled):** The chain is trivially exploitable without any RPC manipulation. An attacker enters a wagered room (H001 passive or active), the match proceeds without any escrow at all, settlement returns `{ success: true }` unconditionally from the dev-mode logging path, and SHOT milestone rewards are emitted as if a real wagered match occurred. The legitimate opponent's SOL was never at risk because no escrow was created — but the match is treated as wagered for reward purposes. This is fund-reward fraud.

- **Scenario B (Production / Escrow Enabled — Timing Variant):** The attacker uses H001 to enter the room, never signs their deposit transaction, sends `ready` before the deposit timeout fires (the `ready` handler has no deposit gate), and the match starts. When the match ends, the server calls `settleMatch()` against an escrow PDA in `AwaitingDeposits` state (only the legitimate player deposited). The on-chain call reverts with `InvalidState`. The server calls `handleSettlementFailure()`, which attempts `cancelMatchEscrow()`. If that also fails (or if the PDA was never funded), the legitimate player's deposit is locked in the escrow until the 48-hour `permissionless_reclaim` window. Attacker pays nothing, opponent's funds are inaccessible.

- **Scenario C (Rematch Phantom Wager — H012 standalone but amplified by chain):** After any match completes, either player can trigger `playAgainRequest`. No new escrow is created (H012). Both players send `ready`; the `ready` handler has no deposit gate (line 1420, confirmed below). The rematch runs to completion. The server calls `settleMatch()` targeting a PDA that was closed by the Anchor `close` constraint after the first match settled. The TX fails. The winner of the rematch receives nothing. The attacker, who knows the rematch is financially void, plays it as a pure risk-free game — if they win, great; if they lose, they lost nothing.

## Complete Attack Chain Walkthrough

### Prerequisites

- Attacker wallet: zero SOL (or near-zero, enough for transaction fees only)
- Legitimate opponent: connected, authenticated, has sufficient SOL for wager
- Server condition for Scenario A: `MATCH_ESCROW_PROGRAM_ID` env var not set (dev/staging environment)
- Server condition for Scenario B: Solana RPC instability sufficient to cause `verifyBalance()` to throw

## Root Cause Analysis

Three root causes combine:

1. **Availability-over-security tradeoff in H001:** The `try/catch` around `verifyBalance()` was deliberately written to fail open ("best-effort — skip if RPC unavailable", line 980). This is the correct posture for a game lobby but not for a financial gate. The balance check should fail closed on RPC error.

2. **Missing deposit guard in all settlement paths (H004):** The settlement logic (`fire` handler line 2092, turn-timeout line 333, disconnect line 575) uses `ws.amount > 0` as the sole predicate for calling `settleMatch()`. The `ws.deposits` tracking object is populated by `escrowDepositConfirm` but is never consulted at any settlement call site. The invariant "both players must have deposited before settlement can be attempted" is enforced only by the on-chain program (and only when escrow is enabled), not by the server.

3. **Escrow lifecycle not replayed on rematch (H012):** The `playAgainRequest` handler deliberately preserves `wagerStates` (comment at line 2526: `// H037: Don't delete wagerStates`) but does not replay the escrow creation and deposit flow. The `ready` handler has no gate conditioned on deposit status, so the second match starts with a phantom wager backed by a closed PDA.

## Severity Justification

**CRITICAL.** The chain meets all criteria for critical severity:

- **Direct financial impact:** In production (Scenario B), a legitimate player's deposited SOL can be locked or lost. In dev mode (Scenario A), wagered-match rewards (SHOT tokens, stats) are obtained fraudulently. In Scenario C, the match winner is denied their payout on every rematch.
- **Attack complexity: Low.** Scenario A requires only that the server be running in dev mode (no `MATCH_ESCROW_PROGRAM_ID`), which is true of staging and local environments. Scenario B requires RPC instability, which occurs naturally on Solana devnet. Scenario C requires only clicking "Play Again" — zero technical skill.
- **No authentication or authorization bypass required:** All three steps use authenticated sockets. The vulnerabilities are in business logic, not authentication.
- **Repeatable:** The chain can be executed indefinitely. Each rematch (`playAgainRequest`) restarts the H012 step without any cost to the attacker.
- **Four auditor convergence on H001 (highest in the audit), two on H004, two on H012.** Each constituent finding is independently confirmed at HIGH severity; their composition elevates the combined chain to CRITICAL.

## Recommendations

Each fix is self-contained and addresses one link in the chain. All three are required to fully close the attack surface.

### Fix 1 — Close the Balance Fail-Open (H001)

Replace the silent catch in both `joinRoom` (lines 990-992) and `createRoom` (lines 1145-1147) with a hard rejection:

```js
// joinRoom — replace lines 990-992
```

### Fix 2 — Gate Settlement on Confirmed Deposits (H004)

Add a deposit guard before all three `settleMatch()` call sites:

```js
// Add before line 2092 (fire handler), line 333 (turn-timeout), and line 654 (disconnect)
const hostDeposited = ws.deposits && ws.deposits[room.host?.socketId]
const playerDeposited = ws.deposits && ws.deposits[room.player?.socketId]
if (ws.amount > 0 && isEscrowEnabled() && (!hostDeposited || !playerDeposited)) {
    // Cancel escrow and refund whoever deposited
    await refundWager(null, ws.amount, roomId,
        ws.wallets[room.host?.socketId],
        ws.wallets[room.player?.socketId])
    transitionState(ms, MATCH_STATES.CANCELLED)
    return
}
```

### Fix 3 — Re-initialize Escrow on Rematch (H012)

Inside `playAgainRequest` (lines 2521-2534 and 2545-2558), after resetting match state, re-run the full escrow initialization flow:

```js
// After line 2525 / line 2549 (after inventory resets)
```
