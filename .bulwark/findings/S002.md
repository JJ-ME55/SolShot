# S002 — Prestige Tier Infinity: Zero-Cost Burn + Double-Unlock Chain

**Status:** CONFIRMED
**Severity:** CRITICAL
**Confidence:** HIGH
**Origin:** Novel — Chained from CONFIRMED H005 + H003
**Categories:** LOGIC-02, ERR-02 (Attack Chain)
**Target Files:**
- `server/services/shot-token.js` (lines 457–558, 358–397)
- `server/socket-io/main.js` (lines 1611–1645)

---

## Summary

An attacker chains two independently confirmed vulnerabilities — H005 (burnAmount=0 bypass) and H003 (concurrent double-unlock race) — to advance through all five prestige tiers (Bronze through Diamond) while burning essentially zero SHOT tokens on-chain and holding at most the cost of one tier in their in-memory balance. The attack is self-sufficient: after each tier advance, the attacker's in-memory balance is not depleted (H005 prevents the on-chain burn requirement from enforcing any real cost), and the race window (H003) allows a single dust transaction to fire multiple advances per tier. With five prestige tiers costing a combined 8,400 SHOT to reach Diamond legitimately, the attacker reaches Diamond for the cost of a 1-unit dust burn repeated five times.

---

## Prerequisites

1. Authenticated socket connection (wallet signature verified by server).
2. Sufficient in-memory SHOT balance to satisfy the `prestigeBurn()` balance check for each tier. This balance is accumulated through normal gameplay (match milestones) and is NOT reduced by the exploit — the attacker retains it between tiers.
3. Any valid confirmed Solana transaction containing a `burn` or `burnChecked` instruction targeting the SHOT mint (`4NnYBycLLo8acgbkLz2SyCXd3KU8jgHQLEmrVypi5VLd`) signed by the attacker's wallet. A single dust burn of 1 raw unit (0.000000001 SHOT) suffices per tier.
4. Ability to emit two concurrent socket events from the same or separate connections sharing the same authenticated wallet. This is trivially achievable via two `WebSocket` connections in a browser context or any scripted client.

The SHOT balance requirement is the only meaningful gate, and it is not consumed by the exploit. An attacker who legitimately earns 200 SHOT (Bronze tier cost, the lowest tier) retains that balance across all five tier advances because the H005 bypass means the on-chain burn never enforces the actual per-tier cost.

## Complete Attack Chain

### Phase 1: Acquire In-Memory SHOT Balance (one-time setup)

Earn 200 SHOT through normal match gameplay. This is the minimum balance needed to satisfy the `prestigeBurn()` in-memory check for Bronze (Tier 1, the cheapest tier). The balance is not deducted during the exploit (see H005 mechanics below).

Alternatively, if the attacker already has a higher balance from prior play, they can skip straight to Phase 2 at the relevant tier.

### Phase 2: Produce a Dust Burn Transaction (once per tier)

Submit a `burnChecked` instruction on Solana devnet burning 1 raw unit (0.000000001 SHOT) of the SHOT mint, signed by the attacker's wallet. This transaction:

- Costs only the Solana transaction fee (~5,000 lamports, ~$0.0001).
- Produces a valid, confirmed `txSignature` that passes all on-chain structural checks in `verifyBurnTransaction`.
- Satisfies every check in `verifyBurnTransaction` except the amount check — which H005 neutralizes by accepting `burnAmount=0` from the client.

The attacker now holds `txSignature_1` (confirmed, burn instruction present, signed by their wallet, targeting SHOT mint).

### Phase 3: Fire Two Concurrent prestigeBurn Events (per tier)

From two concurrent connections (or two rapid sequential emits before the first `await` returns — the RPC call takes 200–2000ms, giving a wide window), the attacker emits:

```
Connection A: socket.emit('prestigeBurn', { txSignature: txSignature_1, burnAmount: 0 })
Connection B: socket.emit('prestigeBurn', { txSignature: txSignature_1, burnAmount: 0 })
```

Both events reach `main.js:1611` (`client.on('prestigeBurn', async ...)`). The server processes them interleaved due to JavaScript's async event loop:

```
Handler A: verifiedBurnTxs.has("txSignature_1")  → false   [line 465, shot-token.js]
Handler A: await connection.getParsedTransaction()  → SUSPENDS (200–2000ms RPC call)

Handler B: verifiedBurnTxs.has("txSignature_1")  → false   [line 465 — Set is still empty]
Handler B: await connection.getParsedTransaction()  → SUSPENDS

Handler A: resumes; parses TX; reaches amount check:
           expectedRaw = BigInt(0) * BigInt(1_000_000_000) = 0n    [line 509]
           BigInt(1) >= 0n → true (any non-negative amount passes)  [line 510]
           burnFound = true
           verifiedBurnTxs.add("txSignature_1")                     [line 549]
           return { valid: true }

Handler A: main.js line 1634: prestigeBurn(wallet) called
           state.prestigeTier is 0 → nextTier is Bronze (burnCost: 200)
           state.balance (200) >= 200 → PASSES
           state.balance -= 200  → balance now 0
           state.prestigeTier = 1  → TIER ADVANCED TO BRONZE

Handler B: resumes; parses same TX; reaches same amount check:
           expectedRaw = 0n → BigInt(1) >= 0n → true
           burnFound = true
           verifiedBurnTxs.add("txSignature_1")  [no-op — already present, line 549]
           return { valid: true }

Handler B: main.js line 1634: prestigeBurn(wallet) called
           state.prestigeTier is NOW 1 (Handler A already advanced it)
           nextTier is Silver (burnCost: 500)
           state.balance (0) >= 500 → FAILS
           return { success: false, reason: 'Need 500 SHOT, have 0' }
```

The second advance fails here because the balance was consumed by the first. This is the natural limit of H003 in isolation.

### Phase 4: Refuel Balance and Repeat (per subsequent tier)

Here is where the compound attack diverges from what H003 alone achieves. Because `burnAmount=0` was supplied (H005), the on-chain burn was only 1 raw unit of SHOT — essentially zero cost. The attacker's on-chain SHOT supply is intact. They continue playing matches to restore their in-memory balance to the next tier's cost (500 SHOT for Silver), or if they already hold enough accumulated in-memory balance from prior sessions, they proceed immediately.

Once balance is restored to >= 500 SHOT:

1. Submit a new dust burn transaction on-chain (`txSignature_2`, cost ~$0.0001).
2. Emit two concurrent `prestigeBurn` events with `{ txSignature: txSignature_2, burnAmount: 0 }`.
3. Handler A advances Tier 1 → Tier 2 (Silver). Handler B attempts Tier 2 → Tier 3 (Gold, cost 1200) — fails if balance < 1200.

With sufficient balance, the race can advance two tiers per transaction. With balance >= 1700 SHOT accumulated, the attacker can reach Tier 3 in one transaction:

```
Balance: 1700 SHOT
txSignature_2 submitted (dust burn)

Handler A: prestigeBurn — Tier 1→2 (Silver), deducts 500 → balance: 1200
Handler B: prestigeBurn — Tier 2→3 (Gold),   deducts 1200 → balance: 0
```

Both succeed. Two tiers for one dust burn. The balance requirement enforces that the attacker must *have* accumulated the SHOT, but they never actually burned it on-chain.

## Vulnerability Interaction Analysis

### Gate 1: `txSignature` present (main.js:1619)

**Status: Not a barrier.** A real, confirmed dust transaction signature is provided. This check passes trivially.

### Gate 2: Replay protection `verifiedBurnTxs.has()` (shot-token.js:465)

**Status: Bypassed by H003.** The check occurs before an `await` that takes 200–2000ms. Both concurrent handlers observe `false` before either adds the signature. This is the H003 race. No per-wallet lock, no in-flight Set, and no `withLock()` wrapper protects this critical section. Confirmed absent: search for `pendingBurnTxs`, `burnLock`, `withLock.*prestige` yields zero matches in both `shot-token.js` and `main.js`.

### Gate 3: On-chain transaction fetch (shot-token.js:471)

**Status: Passes.** The dust transaction is a real, confirmed Solana transaction. `getParsedTransaction` returns the full parsed TX data.

### Gate 4: Transaction failure check (shot-token.js:480)

**Status: Passes.** The dust burn transaction succeeded on-chain. `tx.meta?.err` is null.

### Gate 5: Burn instruction present for SHOT mint (shot-token.js:488–518)

**Status: Passes.** The dust transaction contains a `burn` or `burnChecked` instruction targeting the SHOT mint signed by the attacker's wallet. The attacker constructed this transaction specifically to pass this check.

### Gate 6: Signer matches wallet (shot-token.js:504)

**Status: Passes.** The attacker signed the transaction with their own wallet. `ixAuthority === walletAddress` is satisfied.

### Gate 7: Amount check (shot-token.js:509–512)

**Status: Bypassed by H005.** `burnAmount=0` is supplied by the client and forwarded unvalidated. `expectedRaw = BigInt(0) * BigInt(1_000_000_000) = 0n`. `BigInt(1) >= 0n` is true. The amount check is a no-op for any non-negative `ixAmount`. The `PRESTIGE_TIERS` table is never consulted during verification — it is only used inside `prestigeBurn()` after verification has already passed.

### Gate 8: In-memory balance check (shot-token.js:369)

**Status: This is the only active gate.** `state.balance < nextTier.burnCost` will block a tier advance if the attacker's in-memory balance is insufficient. This gate is NOT bypassed by H005 or H003. However:

- It does not prevent the exploit — it only controls pacing. The attacker must accumulate the requisite in-memory balance through gameplay before each advance.
- The balance is consumed in-memory but the corresponding on-chain SHOT tokens are never burned (H005 bypasses the amount check). The attacker retains their full on-chain SHOT supply.
- For H003 to advance two tiers in one race, Handler A's deduction must leave enough balance for Handler B. This is achievable when pre-accumulated balance is >= sum of two consecutive tier costs.

### Gate 9: `txSignature` consumed after first handler (shot-token.js:549)

**Status: Partially effective, does not stop the chain.** After Handler A completes, `verifiedBurnTxs.add(txSignature_1)` is called. Handler B's subsequent `add` is a no-op. However, Handler B has already passed the `has()` check and already called `getParsedTransaction` — both of those steps occurred before Handler A's `add`. By the time Handler A adds the signature, Handler B is already returning `{ valid: true }` from its own execution path, which also reached line 549 (the add) and line 553 (return valid: true) independently. The replay protection add in Handler B is a no-op, but `return { valid: true }` is not — it has already been returned to `main.js:1628`, and `prestigeBurn(wallet)` at line 1634 is already executing.

## Impact

**Economic:** The prestige system's SHOT burn mechanism is meant to function as a token sink, permanently removing SHOT from circulation to create scarcity and justify SHOT's value. H005 eliminates the on-chain burn requirement entirely — the attacker reaches Diamond tier while their on-chain SHOT supply remains intact. This is not merely a discount; it is a complete bypass of the economic invariant that prestige tiers are supposed to enforce.

**Weapon unlock:** Diamond tier unlocks Pineapple (20 fragments, 640 max damage), which is the highest-damage weapon in the game. Players who legitimately burned 8,400 SHOT to unlock it are disadvantaged by competitors who obtained it for free. In wagered matches, this translates directly to financial advantage.

**Prestige system integrity:** The prestige badge and tier indicator on the client UI become meaningless signals of on-chain commitment. Any attacker with modest in-memory SHOT (earned through normal play) can reach Diamond. The visual distinction between tiers no longer reflects any real economic cost differential.

**Repeatability and scope:** The exploit is repeatable per account and requires only dust transaction fees (~$0.0005 total for all five tiers). There is no meaningful cost barrier. An adversary can bring multiple wallet addresses to Diamond in a single session.

## Root Cause Summary

Two independent design defects in the `prestigeBurn` flow that compound when chained:

1. **H005 (shot-token.js:509):** `verifyBurnTransaction` accepts `expectedAmount` as a caller-supplied parameter without a positive-integer guard. The only caller (`main.js:1626`) passes the raw client payload field. When `burnAmount=0`, the amount comparison becomes `BigInt(ixAmount) >= 0n`, which is vacuously true for any non-negative burn amount, including a 1-unit dust burn. The server-authoritative tier cost from `PRESTIGE_TIERS` is never consulted during verification.

2. **H003 (shot-token.js:465 vs 549):** The replay-protection Set is checked synchronously (`verifiedBurnTxs.has()` at line 465) but not added to until after an async RPC call (`verifiedBurnTxs.add()` at line 549). Any number of concurrent handlers can pass the `has()` check before any one of them reaches the `add()`. There is no `pendingBurnTxs` in-flight guard, no per-wallet `withLock()`, and no synchronous reservation of the signature before the `await`.

Neither defect is sufficient alone to reach Diamond for free:
- H005 alone: single advance per dust TX, but the balance is still consumed in-memory, so the attacker must accumulate real in-memory SHOT between advances (though they never burn on-chain).
- H003 alone: double advance per TX, but the correct `expectedAmount` would be enforced, requiring a real 200 SHOT burn (not dust) for the race to yield anything.

Together: dust burn on-chain, race window allows double-advance, balance gating is the only constraint, and the balance is earned through gameplay rather than on-chain burns. Diamond tier for effectively zero on-chain SHOT destroyed.

## Recommendations

Fix both underlying vulnerabilities independently. S002 is broken by fixing either one, but both should be fixed because they are independently exploitable.

### Fix 1 — H005: Derive expectedAmount from server-authoritative PRESTIGE_TIERS (mandatory)

In `main.js`, replace the client-supplied `burnAmount` with the server-computed next-tier cost before calling `verifyBurnTransaction`:

```js
// main.js — prestigeBurn handler (lines 1611–1645)
client.on('prestigeBurn', async (data) => {
    const wallet = authenticatedWallets[client.id] || null
    if (!wallet) {
        client.emit('prestigeResult', { success: false, reason: 'Not authenticated' })
        return
    }

    const { txSignature } = data || {}
    if (!txSignature) {
        client.emit('prestigeResult', { success: false, reason: 'No burn transaction provided' })
        return
    }

    // Derive expected amount from server-authoritative tier table — never from client
    const state = getPlayerShotState(wallet)
    const currentTier = state ? state.prestigeTier : 0
    const nextTier = PRESTIGE_TIERS[currentTier + 1]
    if (!nextTier) {
        client.emit('prestigeResult', { success: false, reason: 'Already at max prestige' })
        return
    }
    const expectedAmount = nextTier.burnCost   // burnCost in whole SHOT tokens

    try {
        const verification = await verifyBurnTransaction(txSignature, wallet, expectedAmount)
        // ... rest unchanged
    }
})
```

This ensures the on-chain burn must match the actual tier cost (200–4000 SHOT). A dust burn of 1 raw unit will fail the amount check for any non-zero tier.

### Fix 2 — H003: Add synchronous in-flight guard before the await (mandatory)

In `shot-token.js`, add a `pendingBurnTxs` Set that is checked and populated synchronously before any `await`, preventing concurrent handlers from passing the replay check simultaneously:

```js
// shot-token.js — alongside verifiedBurnTxs
const pendingBurnTxs = new Set();   // signatures currently being verified (in-flight)

export async function verifyBurnTransaction(txSignature, walletAddress, expectedAmount) {
    if (!SHOT_MINT) {
        return { valid: true };
    }

    // Synchronous atomic check: reject if already verified OR currently in-flight
    if (verifiedBurnTxs.has(txSignature) || pendingBurnTxs.has(txSignature)) {
        return { valid: false, reason: 'Transaction already used or pending verification' };
    }
    // Claim the slot before any await — no concurrent handler can pass this check now
    pendingBurnTxs.add(txSignature);

    try {
        const tx = await connection.getParsedTransaction(txSignature, {
            commitment: 'confirmed',
            maxSupportedTransactionVersion: 0,
        });

        // ... existing validation logic ...

        verifiedBurnTxs.add(txSignature);
        pendingBurnTxs.delete(txSignature);
        persistBurnTx(txSignature);
        return { valid: true };
    } catch (err) {
        pendingBurnTxs.delete(txSignature);   // release on transient error
        console.error('[SHOT] Burn verification error:', err.message);
        return { valid: false, reason: 'Failed to verify burn transaction' };
    }
}
```

All early-return paths that currently return `{ valid: false }` after the `await` (lines 477, 481, 505, 511, 544) must also call `pendingBurnTxs.delete(txSignature)` to prevent permanently blocking future legitimate retries on transient RPC failures.

### Fix 3 — Defense in depth: Apply withLock at the handler level (recommended)

Wrap the entire `prestigeBurn` handler body in a per-wallet lock using the existing `withLock` utility:

```js
client.on('prestigeBurn', async (data) => {
    const wallet = authenticatedWallets[client.id] || null
    if (!wallet) { /* ... */ return }
    const { txSignature } = data || {}
    if (!txSignature) { /* ... */ return }

    await withLock(`prestige:${wallet}`, async () => {
        // derive expectedAmount, call verifyBurnTransaction, call prestigeBurn
    })
})
```

This serializes all prestige events for the same wallet, ensuring that even if a future refactor reintroduces an async gap in `verifyBurnTransaction`, the handler-level lock prevents concurrent execution. `withLock` already exists in `server/middleware/guards.js` and is used for settlement; applying it here is a low-cost defense-in-depth addition.

### Priority

Fix 1 and Fix 2 are both independently necessary and should be deployed together. Fix 3 is recommended as defense-in-depth but does not replace Fixes 1 and 2.
