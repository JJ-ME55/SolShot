# S007 — Unauthenticated Socket Storm Memory Exhaustion

**Finding ID:** S007
**Type:** Supplemental — Attack Chain
**Investigator:** Dinh's Bulwark — Phase 3 Supplemental Strategies
**Date:** 2026-02-23
**Constituent Findings:** H016 (unauthenticated relay events), H028 (maxHttpBufferSize not configured)
**Category:** API-03 (WebSocket Security), ERR-03 (Rate Limiting), Availability

---

## Verdict: CONFIRMED

**Severity: HIGH**

`maxHttpBufferSize` is not configured in the Socket.IO server initialization (`server/index.js`, lines 31–36), meaning the Socket.IO 4.5.1 default of **1 MB** per event payload applies. The `giveTurn` event at line 2479 of `server/socket-io/main.js` has no authentication check and no payload size limit beyond this 1 MB default. It relays the full received payload — including an arbitrary `terrainData` object — to all room members. An unauthenticated or authenticated socket can send ~1 MB payloads at 30 events/sec (the global rate cap), producing ~30 MB/sec of relay traffic per socket directed at the room. Multiple coordinated sockets amplify this linearly. The per-IP connection limit (100 connections per IP per line 41) is not a meaningful bound against geographically distributed sourcing.

## Investigation: maxHttpBufferSize Confirmation

**File:** `server/index.js`, lines 31–36

```js
const io = new socket.Server(server, {
    cors: {
        origin: CORS_ORIGINS,
        methods: ["GET", "POST"]
    }
    // maxHttpBufferSize: NOT SET
})
```

No `maxHttpBufferSize` option is present. The Socket.IO 4.5.1 default is confirmed at 1 MB (1e6 bytes) per the Socket.IO documentation and `socket.io` package source. All events, including `giveTurn`, accept payloads up to 1 MB.

**File:** `server/socket-io/main.js`, lines 2479–2483

```js
client.on('giveTurn', (data) => {
    if (!data || typeof data !== 'object') return
    const { terrainData, pos1, pos2, rotation1, rotation2 } = data
    client.to(client.roomId).emit('recieveTurn', {terrainData, pos1, pos2, rotation1, rotation2})
})
```

No authentication check. No `terrainData` size cap. The handler destructures `terrainData` from the incoming payload and relays it verbatim. The relay target is `client.to(client.roomId)` — all sockets in the room, including the legitimate opponent.

## Chain Analysis

### Component 1 — H016: Unauthenticated `giveTurn`

`giveTurn` is one of six unauthenticated relay events. An unauthenticated socket with `client.roomId` set (obtainable by creating or joining a free room, since auth is only required when `wagerAmount > 0`) can emit `giveTurn` without any authentication challenge.

For the memory exhaustion chain, even authenticated sockets are relevant — any socket in any room can exploit this. But the lack of authentication means the attack surface is expanded: the attacker does not need a wallet, does not need SOL, and does not need to complete any challenge. Any raw WebSocket connection that joins a free room is sufficient.

### Component 2 — H028: Default 1 MB Buffer per Event

With `maxHttpBufferSize` at the default 1 MB, each `giveTurn` event can carry up to ~900 KB of `terrainData` content (leaving ~100 KB for the Socket.IO framing and other fields). The engine accepts this payload, allocates it in V8 heap memory, and passes it to the handler. The handler then constructs a relay object containing the same `terrainData` and calls `client.to(client.roomId).emit(...)`, which allocates another copy for serialization and transmission.

### Memory Allocation Per Event

For a single `giveTurn` event with a 900 KB `terrainData` payload:

| Allocation Point | Estimated Size | Location |
|-----------------|---------------|----------|
| Incoming socket.io-parser deserialization | ~900 KB | V8 heap |
| `data` object in handler | ~900 KB (reference, same buffer) | V8 heap |
| Relay object `{terrainData, pos1, pos2, ...}` | ~900 KB + metadata | V8 heap |
| Serialization for outgoing emit | ~900 KB | V8 heap |
| **Peak per event (before GC)** | **~3.6 MB** | V8 heap |

GC cannot keep pace when events arrive at 30/sec. Peak concurrent allocation per socket pair is approximately:

```
30 events/sec × 3.6 MB/event = 108 MB/sec allocation rate
```

Even if V8 GC runs at 10/sec (optimistic), 10 events accumulate before each GC pass, holding ~36 MB of live relay objects at peak. With multiple attacking sockets this scales linearly.

### Attack Configuration

```
N attacking sockets, each:
- join a free room (no auth required)
- emit giveTurn at 30/sec with 900 KB terrainData
```

At N = 10 coordinated sockets, server-side allocation rate reaches ~1 GB/sec. Even at N = 3, the server sustains ~324 MB/sec allocation — sufficient to exhaust the Render Free tier's memory (512 MB) and trigger OOM restart within approximately 2 seconds of sustained attack.

### Rate Limiter Assessment

The global ring-buffer rate limiter (`server/socket-io/main.js`, lines 444–529) caps each socket at 30 events/sec. This is a per-socket cap, not a per-event-type cap and not a global server cap. The attacker uses N sockets to achieve N × 30 events/sec from the server's perspective.

The per-IP connection limit (`MAX_CONNECTIONS_PER_IP = 100`, line 41) limits connections from a single IP to 100. However:
- 100 sockets × 30 events/sec × 3.6 MB/event = ~10.8 GB/sec allocation rate from a single IP.
- The per-IP limit does not apply to geographically distributed sources (Tor, VPN, botnet).
- The X-Forwarded-For header is used for IP detection (line 46) — this can be spoofed if the Render proxy configuration is not airtight (H-M7: trust proxy not configured).

### Relay Amplification Factor

The relay from `client.to(client.roomId)` sends the payload to all other sockets in the room. If a room has 2 sockets (host + player), a 900 KB incoming event produces 900 KB of outgoing relay traffic to the opponent. This is a 1:1 relay amplification — not amplified across the server, but concentrated on the victim's connection. The victim receives 30 × 900 KB = 27 MB/sec of unsolicited relay traffic from a single attacking socket, which can saturate the victim's browser WebSocket connection and cause client-side memory pressure from deserialization.

## Severity Assessment

**HIGH** (approaching CRITICAL under a sustained, coordinated attack):

- **Availability impact:** Server OOM restart under sustained attack from a small number of sockets. Render auto-restarts the dyno, but all in-memory state (active matches, wager states, pending reconnects) is lost — active wagered matches cannot settle, funds are at risk.
- **Victim-targeted bandwidth:** Each attacking socket directs 27 MB/sec at a specific opponent's browser connection, degrading the victim's experience independent of server-wide impact.
- **No authentication barrier:** Free-room access requires no wallet, no SOL, no prior authentication. The attack surface is the full internet.
- **Cost to attacker:** Near-zero. Requires only a scripted WebSocket client and network bandwidth.
- **Mitigation absent:** No per-event-type rate limit exists. No `maxHttpBufferSize` is configured. No `terrainData` size cap exists in the handler.

## Recommendations

### Fix 1 — Set maxHttpBufferSize (Immediate, High Impact)

```js
// server/index.js
const io = new socket.Server(server, {
    cors: { origin: CORS_ORIGINS, methods: ["GET", "POST"] },
    maxHttpBufferSize: 64 * 1024   // 64 KB — sufficient for all legitimate game payloads
})
```

A 64 KB buffer is more than adequate for all current game events:
- `shoot`/`fire` payloads: ~100 bytes
- `positionUpdate`: ~50 bytes
- `weaponPick`/`weaponChange`/`angleChange`/`powerChange`: ~50 bytes each
- `giveTurn` with legitimate position data (no terrain): ~200 bytes

Setting this to 64 KB reduces the maximum per-event allocation from 1 MB to 64 KB, cutting the memory attack's effectiveness by 15x.

### Fix 2 — Add `requireAuth` to `giveTurn` (Closes H016 for this Event)

```js
client.on('giveTurn', (data) => {
    if (!requireAuth(client, 'giveTurn')) return  // add this
    // ...
})
```

Authentication eliminates the zero-barrier access path. Unauthenticated sockets from the open internet can no longer reach this handler.

### Fix 3 — Strip `terrainData` from `giveTurn` Relay

Server terrain is generated server-side. `terrainData` in `giveTurn` is legacy. Dropping it from the relay eliminates the large-payload vector entirely while preserving the position/rotation fields that may still be used:

```js
client.on('giveTurn', (data) => {
    if (!requireAuth(client, 'giveTurn')) return
    if (!data || typeof data !== 'object') return
    const { pos1, pos2, rotation1, rotation2 } = data
    // terrainData intentionally excluded from relay
    if (!Number.isFinite(pos1) || !Number.isFinite(pos2)) return
    client.to(client.roomId).emit('recieveTurn', {pos1, pos2, rotation1, rotation2})
})
```

### Fix 4 — Add Per-Event-Type Rate Sub-Limit for `giveTurn`

If the event is retained, add a dedicated ring buffer limiting `giveTurn` to at most 2 events/sec per socket (matching the intended one-per-turn-end cadence):

```js
// Track giveTurn rate separately
if (!client._giveTurnTs) client._giveTurnTs = 0;
const now = Date.now();
if (now - client._giveTurnTs < 500) return;  // max 2/sec
client._giveTurnTs = now;
```

### Fix 5 — Delete `giveTurn` and `recieveTurn` Entirely

The most effective fix: remove the legacy event pair. Server terrain is authoritative; the server can push position corrections directly instead of relaying client-reported data.
