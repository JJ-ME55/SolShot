# S009 — Disconnect Timer Abuse: Infinite Reconnect Extension

**Finding ID:** S009
**Type:** Supplemental — Emergent from Reconnect System
**Investigator:** Dinh's Bulwark — Phase 3 Supplemental Strategies
**Date:** 2026-02-23
**Constituent Findings:** Emergent from reconnect architecture (no prior finding ID — novel)
**Category:** LOGIC-01 (Business Logic), ERR-02 (Race Conditions), Availability

---

## Verdict: CONFIRMED

**Severity: MEDIUM**

The 30-second reconnect window can be reset to a fresh 30 seconds on every `rejoinRoom` call because the `rejoinRoom` handler deletes the existing `pendingReconnects` entry and `disconnectTimers` entry but does not prevent the newly reconnected socket from immediately disconnecting again and triggering a new 30-second timer. There is no reconnect-count ceiling, no cumulative timeout cap, and no detection of a disconnect-reconnect oscillation pattern. A malicious player who is losing can cycle disconnect → rejoin → disconnect → rejoin indefinitely, keeping the match in a perpetual "reconnect window" state where the opponent receives repeated `opponentDisconnected` events with new 30-second countdowns and cannot force a forfeit resolution.

However, the impact on match state termination is bounded: each reconnect successfully restores match play, so the opponent is not blocked from the match — they are merely annoyed by the repeated disconnect/reconnect cycle and their turn-timer resets (which is a separate issue to evaluate). The attack does not extract funds directly but can be used to drag out a losing position indefinitely or to stall a match outcome the attacker dislikes.

## Investigation

### Reconnect Timer Setup (disconnect handler)

**File:** `server/socket-io/main.js`, lines 736–760

```js
// On disconnect, during BATTLE or WEAPON_SHOP:
disconnectTimers[walletAddress] = setTimeout(async () => {
    delete pendingReconnects[walletAddress]
    delete disconnectTimers[walletAddress]
    // Re-read state
    const currentMs = matchStates[roomId]
    const currentRoom = findRoom(roomId)
    if (!currentRoom || !currentMs) return
    if (opponentId) {
        io.to(opponentId).emit('reconnectExpired', {})
    }
    // Forfeit settlement
    const fakeClient = {
        id: client.id,
        roomId: roomId,
        isHost: client.isHost,
        leave: () => {},
    }
    await cleanupRoom(fakeClient, io, 'reconnect_timeout')
    delete authenticatedWallets[client.id]
}, RECONNECT_WINDOW_MS)   // RECONNECT_WINDOW_MS = 30000 (line 140)
```

The timer is started on each disconnect. If the player reconnects via `rejoinRoom` before the 30 seconds elapse, the timer is cancelled.

### Reconnect Timer Cancellation (rejoinRoom handler)

**File:** `server/socket-io/main.js`, lines 821–826

```js
// Cancel the deferred cleanup timer
if (disconnectTimers[walletAddress]) {
    clearTimeout(disconnectTimers[walletAddress])
    delete disconnectTimers[walletAddress]
}
delete pendingReconnects[walletAddress]
```

The timer is correctly cancelled on reconnect. There is no counter here of how many times this cycle has occurred.

### No Reconnect Counter or Cumulative Cap

A full-codebase search for any counter tracking reconnection frequency:

- `pendingReconnects` stores `{ roomId, isHost, oldSocketId, name, color }` — no `reconnectCount` field
- `disconnectTimers` stores only the `setTimeout` handle — no counter
- `RECONNECT_WINDOW_MS` is a constant (line 140: `const RECONNECT_WINDOW_MS = 30000`) — no dynamic adjustment
- No `maxReconnects` constant exists anywhere in the codebase
- No rate limiting applies to `rejoinRoom` — the handler has `requireAuth` equivalent (Ed25519 re-verification at lines 798–803) but no frequency guard

The handler simply repeats identically each time it is called.

### Turn Timer Interaction

**File:** `server/socket-io/main.js` — turn timer management

The turn timer (`turnTimers[roomId]`) runs a 60-second countdown per turn. When a player disconnects, the turn timer is not paused or cancelled. If the player reconnects within 30 seconds, they resume with whatever time remains on the turn timer. If they repeatedly disconnect and reconnect within the window, each reconnect restores their socket state but the turn timer continues running down.

For the attacker, this means:
- Repeated disconnects during their own turn consume turn time, not stall it.
- Repeated disconnects during the opponent's turn are more strategically valuable — the opponent's turn timer runs down while the match is in a "waiting for reconnect" state, and the opponent may feel psychological pressure from the uncertainty.

### Can the Match Be Forced to Terminate via This Abuse?

**No** — not directly. The only outcome of a disconnect-reconnect cycle is:
1. If reconnect happens within 30 seconds: match continues normally. No settlement, no forfeit.
2. If no reconnect within 30 seconds: `cleanupRoom` runs with `reconnect_timeout` reason, triggering forfeit settlement where the opponent (who stayed connected) wins.

The attacker who is losing would want to avoid the 30-second expiry. They can do this by reconnecting just before 29 seconds elapse, then disconnecting again immediately after reconnecting, which starts a fresh 30-second window. This cycle can repeat indefinitely.

### Mathematical Upper Bound on Match Delay

In the worst case, the attacker oscillates:
- Disconnect at t=0
- Reconnect at t=29s (just before forfeit)
- Disconnect immediately at t=29s + epsilon
- Reconnect at t=58s (just before forfeit)
- ...

Each cycle extends the match by ~29 seconds. With no iteration cap, this creates an infinite extension of match state. The opponent is trapped in the match as long as they remain connected.

There is no server-side timeout on the match itself (the ARCHITECTURE.md notes a settlement timeout that applies to the Anchor 24h on-chain timeout, not to an active match duration).

### Opponent Experience During Abuse

Each disconnect cycle causes:
1. `opponentDisconnected` event emitted to opponent with a 30-second countdown
2. Opponent's client displays reconnect countdown UI
3. At reconnect: `opponentReconnected` emitted — opponent's UI resets
4. Immediate redisconnect: `opponentDisconnected` again with new 30-second countdown

After several cycles, the opponent's client may be in a confused UI state (rapid connected/disconnected toggles). The opponent cannot leave without forfeiting their own wager deposit. They are effectively held hostage in the match.

## Severity Assessment

**MEDIUM:**
- **Availability impact:** Matched opponent is trapped in an indefinitely extended match with no way to force a resolution (except forfeiting their own position, which would hand the match to the abuser).
- **Financial impact:** Indirect. If the abuser is losing and the opponent gives up (forfeits), the abuser wins the wager by attrition. In a High Roller match (large wager), this could represent significant value.
- **No financial extraction by the abuser directly:** The abuser cannot use this to extract funds — they must win the match (or cause the opponent to forfeit) to receive the settlement. This reduces severity from HIGH to MEDIUM.
- **Turn timer mitigates some abuse:** If the abuser disconnects during their own turn, the turn timer continues to run. They cannot stall indefinitely without eventually having the turn clock out (though the turn timer interaction with reconnects needs separate verification).
- **Effort required:** Moderate. Requires a script that tracks the 29-second mark and times disconnects/reconnects precisely.

## Recommendations

### Fix 1 — Add Reconnect Count Cap and Escalating Window

Track how many times a wallet has reconnected in the current match session. After N reconnects (e.g., 3), either:
- Deny further reconnect windows (force immediate forfeit on next disconnect), or
- Reduce the reconnect window to 5 seconds instead of 30 seconds.

```js
// In pendingReconnects:
pendingReconnects[walletAddress] = {
    roomId,
    isHost: client.isHost,
    oldSocketId: client.id,
    name: client.name,
    color: client.color,
    reconnectCount: (existingEntry?.reconnectCount || 0) + 1,  // track count
    firstDisconnectTime: existingEntry?.firstDisconnectTime || Date.now(),
}

// Compute window based on count:
const count = pendingReconnects[walletAddress].reconnectCount;
const window = count <= 2 ? RECONNECT_WINDOW_MS
             : count <= 4 ? 10000  // 10s on 3rd/4th disconnect
             : 0;                  // immediate forfeit after 5th
```

### Fix 2 — Cumulative Time Cap

Track the total time spent in disconnected state for a given wallet in a given match. If the cumulative disconnected time exceeds a threshold (e.g., 60 seconds total across all disconnects in a match), trigger forfeit regardless of individual window.

```js
// In disconnect handler:
const totalDisconnectTime = pendingReconnects[walletAddress]?.cumulativeDisconnectMs || 0;
if (totalDisconnectTime >= 60000) {
    // Skip reconnect window — immediate forfeit
    await cleanupRoom(client, io, 'disconnect_abuse')
    return
}

// In rejoinRoom handler — record how long they were disconnected:
const disconnectDuration = Date.now() - pendingReconnects[walletAddress].disconnectStartTime;
pendingReconnects[walletAddress].cumulativeDisconnectMs =
    (pendingReconnects[walletAddress].cumulativeDisconnectMs || 0) + disconnectDuration;
```

### Fix 3 — Rate Limit `rejoinRoom`

Add a minimum interval between successive `rejoinRoom` attempts from the same wallet:

```js
// Track last rejoin time per wallet
const lastRejoin = lastRejoinTimes.get(walletAddress);
if (lastRejoin && Date.now() - lastRejoin < 5000) {
    client.emit('rejoinError', { reason: 'Reconnect too frequent — please wait' })
    return
}
lastRejoinTimes.set(walletAddress, Date.now())
```

### Fix 4 — Notify Opponent of Repeated Disconnects

When the same player disconnects for the Nth time in a match, include a flag in `opponentDisconnected` so the opponent's UI can display "Opponent has disconnected N times" and make an informed decision about whether to continue waiting:

```js
io.to(opponentId).emit('opponentDisconnected', {
    reconnectWindowMs: effectiveWindow,
    reconnectCount: count,
})
```

This is a transparency improvement, not a security fix, but it empowers the opponent to make informed decisions.
