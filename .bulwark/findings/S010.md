# S010 — Join Race Ghost + Deposit Confusion

**Finding ID:** S010
**Type:** Supplemental — Attack Chain
**Investigator:** Dinh's Bulwark — Phase 3 Supplemental Strategies
**Date:** 2026-02-23
**Constituent Findings:** H019 (join race ghost socket), H010 (double escrowActive race condition)
**Category:** ERR-02 (Race Conditions), LOGIC-02 (Financial Logic), API-03 (WebSocket)

---

## Verdict: CONFIRMED

**Severity: HIGH**

The join race (H019) places a ghost socket in a wagered room. The ghost socket retains `client.roomId` and `client.isAuthenticated = true` (if authenticated via the free-room entry path or via a separate wagered room join that later became the non-winning socket). The `escrowDepositConfirm` handler at line 1722 requires authentication (`requireAuth`) but does not verify room membership beyond `client.roomId === rid` (line 1728). A ghost socket in the room can send `escrowDepositConfirm` for any `txSignature` string. The handler then accesses `ws.deposits[client.id]`, writing to the deposit tracking map under the ghost socket's ID. This ghost ID does not match `room.host.socketId` or `room.player.socketId`, so the `hostDeposited && playerDeposited` check at line 1790 can never become true from the ghost's action alone — but the ghost's write contaminates `ws.deposits` with a spurious entry under an unrecognized socket ID.

Combined with the double `escrowActive` race from H010, the contaminated `ws.deposits` and the timing interactions create a scenario where the legitimate deposit confirmation flow can be interrupted, deposit status can be misread, and `escrowActive` can be either suppressed or duplicated depending on timing.

## Investigation

### Can a Ghost Socket Send escrowDepositConfirm?

**File:** `server/socket-io/main.js`, lines 1722–1803

The handler's guards, in order:
1. `requireAuth` at line 1723 — requires `client.isAuthenticated === true`
2. Object and string type checks at lines 1724–1726
3. Cross-room isolation: `client.roomId !== rid` at line 1728

The ghost socket from H019:
- Has `client.roomId = roomId` set (line 1001 — set before `room.active = true`)
- Has `client.join(roomId)` called (line 1000 — subscribed to the Socket.IO room)

**Is the ghost socket authenticated?** This depends on how the ghost was created:

**Path A — Wagered room join race:** The ghost socket authenticated before sending `joinRoom` (since `wagerAmount > 0` requires auth at line 972). So the ghost socket HAS `client.isAuthenticated === true`. It passes `requireAuth`. It also has `client.roomId` set to the wagered room. It passes the cross-room check. **The ghost socket can send `escrowDepositConfirm` for the wagered room.**

**Path B — Free room join race:** The ghost socket did not authenticate (free room requires no auth). `requireAuth` would reject it. **The ghost socket cannot send `escrowDepositConfirm` in this path.**

**Path A is the exploitable case.** In a wagered room join race, the losing socket (ghost) is authenticated and has the room ID, enabling `escrowDepositConfirm` submission.

### What Happens When Ghost Sends escrowDepositConfirm?

**File:** `server/socket-io/main.js`, lines 1756–1803

```js
// Line 1756 — determine isHost
const isHost = room.host?.socketId === client.id
// Ghost socket: room.host.socketId is NOT client.id (ghost was overwritten in H019)
// So isHost = false

// Line 1757-1764 — check on-chain deposit status
const depositConfirmed = isHost
    ? escrowState.playerOneDeposited
    : escrowState.playerTwoDeposited
// Ghost is treated as "player two" (not host) — checks playerTwoDeposited

// If the legitimate player two has deposited, depositConfirmed = true
// If the legitimate player two has NOT deposited, depositConfirmed = false → handler returns

// Line 1782-1783 — write deposit flag under ghost's socket ID
if (!ws.deposits) ws.deposits = {}
ws.deposits[client.id] = txSignature   // client.id is the GHOST's socket ID
```

The ghost socket's deposit write goes into `ws.deposits[ghostSocketId]`. This is NOT `room.host.socketId` or `room.player.socketId`.

```js
// Line 1785-1786 — read deposit status for the TWO RECOGNIZED players
const hostDeposited = ws.deposits[room.host?.socketId]
const playerDeposited = ws.deposits[room.player?.socketId]
// Ghost's deposit is at ws.deposits[ghostSocketId] — NOT READ HERE
// hostDeposited and playerDeposited are unaffected by the ghost's write
```

In isolation, the ghost's `escrowDepositConfirm` is harmless to the `hostDeposited && playerDeposited` check — it writes to a different key. The `escrowActive` emission is not triggered by the ghost.

### H010 Interaction: Double escrowActive Race

**File:** `server/socket-io/main.js`, lines 1722–1803 (same handler)

H010 establishes that the `escrowDepositConfirm` handler is susceptible to a concurrent execution race when both legitimate players send their confirmations near-simultaneously. Both handlers park at `await getEscrowState(rid)` (line 1743), and both can reach the deposit write and `escrowActive` emission concurrently, emitting `escrowActive` twice.

When combined with a ghost socket that also sends `escrowDepositConfirm` near-simultaneously with the legitimate players, three concurrent handler invocations are running:
- Handler A: host's legitimate `escrowDepositConfirm`
- Handler B: player's legitimate `escrowDepositConfirm`
- Handler C: ghost's `escrowDepositConfirm`

All three park at `await getEscrowState(rid)`. Handler C's on-chain check uses `isHost = false` (ghost is not `room.host.socketId`), so it checks `escrowState.playerTwoDeposited`. If the legitimate player two has deposited, Handler C passes the on-chain check.

**Race outcome analysis:**

| Execution Order | Result |
|----------------|--------|
| A then B (normal) | One `escrowActive` emission — correct |
| A and B concurrent | Double `escrowActive` emission (H010) |
| A, B, C concurrent | Double `escrowActive` emission + ghost writes `ws.deposits[ghostId]` (noise) |
| C then A, C then B | Ghost writes first; legitimate players write and check — still correct; `hostDeposited && playerDeposited` not affected |
| A before C, C before B | Ghost write is noise; B's write triggers `hostDeposited && playerDeposited` — one emission |

The ghost socket's interaction with H010 does not meaningfully change the H010 double-emission outcome. The ghost's write to `ws.deposits[ghostId]` is not in the `hostDeposited`/`playerDeposited` read path.

### The Real Risk: depositTimers Disruption

**File:** `server/socket-io/main.js`, lines 1793–1796

```js
if (hostDeposited && playerDeposited) {
    if (depositTimers[rid]) {
        clearTimeout(depositTimers[rid])       // line 1794
        delete depositTimers[rid]              // line 1795
    }
    io.sockets.in(rid).emit('escrowActive', { ... })
}
```

The `depositTimers[rid]` is the 2-minute countdown that cancels the escrow if both players don't deposit in time. This timer is only cleared when `hostDeposited && playerDeposited` — i.e., when both RECOGNIZED players have confirmed. The ghost socket's action does not trigger the timer clear.

However, there is a subtler issue: if the ghost socket passes the `requireAuth` and cross-room checks and successfully reaches the on-chain verification step, it calls `getEscrowState(rid)` — an RPC call. This means N concurrent `escrowDepositConfirm` handlers (ghost + 2 legitimate players) all issue RPC calls simultaneously to the same endpoint for the same PDA. This is minor amplification on the Solana RPC connection (H025: 3 fragmented RPC Connection objects) but not a meaningful DoS.

### Can the Ghost Trigger escrowActive Incorrectly?

A ghost socket sending `escrowDepositConfirm` when:
- `room.host.socketId` has already deposited (`ws.deposits[hostSocketId]` is set)
- `room.player.socketId` has NOT yet deposited (`ws.deposits[playerSocketId]` is not set)
- Ghost's write goes to `ws.deposits[ghostSocketId]`

After the ghost writes, the check reads:
```js
const hostDeposited = ws.deposits[room.host?.socketId]    // true (already written by host)
const playerDeposited = ws.deposits[room.player?.socketId] // still undefined
```

`hostDeposited && playerDeposited` is `true && undefined = false`. The ghost cannot trigger `escrowActive` by itself even when one legitimate player has deposited. The ghost cannot forge the player's deposit flag because the flag is keyed to `room.player.socketId`, not to the ghost's socket ID.

**Conclusion:** The ghost cannot trigger a false `escrowActive` emission under the current implementation.

### What the Ghost CAN Do

1. **RPC consumption:** Ghost calls `getEscrowState(rid)` — additional RPC call load.
2. **Deposit map contamination:** `ws.deposits` accumulates a spurious entry `{ [ghostId]: txSignature }`. This does not affect game logic but could confuse any future diagnostic tooling that inspects `ws.deposits` to infer "how many deposits have been received."
3. **Handler timing interference:** Three concurrent async handlers executing on the same room state is noisier than two. If any future code adds logic that iterates over `ws.deposits`, the ghost entry could cause off-by-one counts.
4. **Interaction with H010:** The ghost adds a third concurrent handler invocation that holds a reference to `ws` through multiple `await` points. If `wagerStates[rid]` is deleted between the ghost's `await` calls (e.g., by a concurrent `removeRoom`), the ghost handler will operate on a stale `ws` reference — but this is the same behavior as H010's legitimate handlers.

## Severity Assessment

**HIGH** (elevated from the isolated analysis of ghost socket effects due to the compounding H010 race and the authenticated ghost in wagered rooms):

- **Ghost can send `escrowDepositConfirm` in wagered rooms:** The join race prerequisite is confirmed for wagered rooms (authenticated ghost). The handler executes through the on-chain verification and deposit write.
- **Direct escrowActive impact: NONE** — The ghost cannot trigger a false `escrowActive`. The `hostDeposited && playerDeposited` check is correctly keyed to recognized player socket IDs.
- **Indirect impact: MEDIUM** — Deposit map contamination, additional RPC calls, three-way concurrent handler execution increasing H010 race probability.
- **H010 amplification:** Adding a third concurrent invocation marginally increases the window in which both legitimate handlers can independently pass the `hostDeposited && playerDeposited` check before either has written its flag, making the double-emission race slightly more likely.
- **Severity rated HIGH** (not CRITICAL) because the ghost cannot directly cause fund loss or incorrect settlement through this specific chain. The impact is primarily reliability degradation and increased exposure of the H010 race.

## Recommendations

### Fix 1 — Verify Socket is a Recognized Player in escrowDepositConfirm

Add a recognized-player check before processing the deposit confirmation:

```js
client.on('escrowDepositConfirm', async (data) => {
    if (!requireAuth(client, 'escrowDepositConfirm')) return
    // ...existing guards...
    const room = findRoom(rid)
    if (!room) return

    // Only recognized room players can confirm deposits
    const isHost = room.host?.socketId === client.id
    const isPlayer = room.player?.socketId === client.id
    if (!isHost && !isPlayer) {
        client.emit('escrowError', { reason: 'Not a recognized player in this room' })
        return  // ghost socket rejected here
    }
    // ...rest of handler...
})
```

This closes the ghost-socket-in-wagered-room path entirely. The ghost socket cannot confirm a deposit because it is not `room.host.socketId` or `room.player.socketId`.

### Fix 2 — Apply withLock to escrowDepositConfirm (Closes H010)

```js
client.on('escrowDepositConfirm', async (data) => {
    // ...guards including Fix 1...

    // On-chain verification OUTSIDE the lock (slow RPC calls)
    // ...getEscrowState logic...

    // Write and check INSIDE the lock
    await withLock(`deposit:${rid}`, async () => {
        const wsLocked = wagerStates[rid]
        if (!wsLocked) return
        if (wsLocked.deposits?.[client.id]) return  // idempotency guard

        if (!wsLocked.deposits) wsLocked.deposits = {}
        wsLocked.deposits[client.id] = txSignature

        const hostDeposited = wsLocked.deposits[room.host?.socketId]
        const playerDeposited = wsLocked.deposits[room.player?.socketId]

        if (hostDeposited && playerDeposited) {
            // clear timer, emit escrowActive ONCE
        }
    })
})
```

This serializes the write-check-emit sequence, preventing both the H010 double-emission and any ghost-socket write contention.

### Fix 3 — Close H019 Ghost Socket (Sentinel on room.active)

The root cause of the ghost socket's existence is the missing sentinel. Adding `room.active = true` synchronously after the guard at line 962 prevents any ghost from being created:

```js
var room = findRoom(roomId)
if (!room || room.active === true) return
room.active = true  // ADD — prevents concurrent joinRoom from creating ghost
```
